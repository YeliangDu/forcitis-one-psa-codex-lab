# Registered read-only forensic entry (card #1377)

The one command agents use for production reads (ADR-0037 decisions 5 and 7; user 2026-11-05: "agree to register a read-only forensic entry; whenever it is read-only I no longer decide"):

```bash
python3 tools/ops/dba/forensic_read.py --target <name> --session <session> --purpose "<text>" --delete-at "<when the local file is deleted>" --out <file outside every git work tree> <sql-file>
```

- Sent: one SELECT only (a constant select with no table also passes) (comments removed; no write, EXEC, INTO, second statement, batch separator, linked-server name; no line starting with `:` or equal to `GO`, no `$(`, no double-quoted names, no keyword glued to a digit such as `1DELETE` (SQL Server reads it as 1 then DELETE), so a number must be plain digits or a plain decimal (write `1000`, not `1E3` or `0x01`; put a space before `AND`), no non-ASCII character outside a string or a [bracketed name], no `{` outside a string literal and no quote or `{` inside a [bracketed name] (the JDBC driver rewrites `{fn ...}` and `{limit n}` forms after the checks and knows no [names]), because `OneSql.java` rewrites such text before it runs; a further SELECT at the top level only as UNION/EXCEPT/INTERSECT). Anything else is refused before the config is read, a register line is written or anything is sent. `tools/ops/dba/OneSql.java ro` checks again on the server and rolls back. Structural gate (the line that does not depend on the text checks): on the same connection `OneSql.java` runs `SET SHOWPLAN_XML ON` as its own batch, sends the exact final batch (the server compiles it and returns the plan without running anything), requires the plan to hold exactly one statement element, a `StmtSimple` of `StatementType="SELECT"` (or `SELECT WITHOUT QUERY`, a select with no table), refuses on any parse error, then `SET SHOWPLAN_XML OFF` and runs the same string unchanged (`ONE_SQL_PLAN_GATE=1`, set by the entry for the caller's query only; the fixed account-check queries run without it, the account-check union plan is not one simple SELECT). A refusal or server error makes the entry exit nonzero and write nothing; the run counts as complete only with the `DONE batches=1` line. On the real server the login needs SHOWPLAN through the server-level ALTER TRACE permission only; never GRANT SHOWPLAN at database level. The text checks stay as an early refusal and for what a plan does not show (`NEXT VALUE FOR`, linked-server names). The database-level DENY set of the forensic account stays the defence that matters most.
- Account: the ADR-0037 forensic read-only account. Its credential stays on the servers (encrypted on the secret host to a throw-away key of the app host, decrypted only in the Java process). Every run first runs ADR-0037 decision 5 item 4: (a) effective database permissions inside the baseline with SELECT, (b) the database-level DENY set present, (c) no database role, (d) server-level permissions inside the baseline and no fixed server role, (e) owns no schema, object, role or database and holds no grant outside CONNECT/SELECT at database level; (f) is the reachable-databases check below. Baselines mirror `ReadOnlyBaseline.java` and the "有效权限平台基线" section of `docs/ops/dba-scripts/README.md`. An answer that holds an error, several results or a wrong row-count trailer counts as a mismatch. A mismatch stops the run and names the failed categories only. The catalog query is not yet run against the real server (unverified).
- Reachable databases (checked with the account check): the login reaches exactly the configured target databases (A8, legacy, and the two U8C databases, each with its own `evidence-user-*.sql` in `docs/data/evidence/dba-handoff/`; rollback in `evidence-rollback.sql`) plus the platform guest databases `master`, `msdb`, `rdscore`, `tempdb`. One more or one fewer stops the run.
- Output check: a result that holds an ID-number, mobile-number or e-mail shape, or a cell longer than 300 characters, is withheld (nothing written; the message names kinds and counts only). `--definitions` raises the cell limit to 2000 for form or field definition text; it never relaxes the personal-data shapes. Lead reads output summaries before anything leaves the notes folder.
- Result: written to `--out` (mode 0600, never inside a git work tree); the terminal shows only a row count. Row-level and personal data stay out of sessions and repo: queries return names, types, counts or aggregates (groups under 5 people suppressed), and lead reads every query before it runs (card #1373 rules).
- Register: each run first writes one fragment `docs/ops/legacy-read/<date>-<time>-<session>.md` (account, target and tables, purpose, output form, deletion time); commit it with the card's PR.
- No other production command: the prod-write gate still refuses any command text that holds a production fingerprint. This command line holds none.

## Local config (outside the repo)

Path: `~/.config/forcitis-forensic/config.json`, mode 0600 (the entry refuses a file others can read). Created by the user once; the entry never prints it.

| field | meaning |
|---|---|
| `aliyun_profile`, `region` | aliyun CLI profile and region used for the cloud assistant. The profile is a dedicated RAM sub-user limited to RunCommand (and reading its result) on the two instances below; no other permission (lead ruling 2026-11-05) |
| `app_host` | instance that runs the Java client (the host allowed to reach the database) |
| `secret_host` | instance that holds the forensic credential file |
| `app_work_dir`, `secret_work_dir` | temporary directories on those hosts (removed at the end of each run) |
| `secret_file` | path of the credential file on `secret_host` (key `EVIDENCE_DB_PASSWORD`) |
| `app_jar_process` | file name of a running application jar on `app_host` from which the JDBC driver is taken |
| `account` | forensic account login name |
| `targets` | `{ "<name>": { "database": "<database name>" } }`, exactly one entry per database the login may reach: A8, legacy, and the two U8C databases (four targets) |

Known limits: the cloud assistant keeps its invocation record at the provider (the SQL text; the command is not kept after the run, the output is kept as long as the provider retains invocation results, retention not verified); `--out` omits OneSql's `connected as` line, but a server error text can still carry field values; two runs at the same time share the fixed work directories and remove each other's files, so run one at a time; the instance ids appear in the argv of the `aliyun` child process (not in the repo, the command line you type, or output). U8C reads work only after the user has run `evidence-user-u8cloud.sql` and `evidence-user-u8cloud-qz.sql` (same login, same RDS instance); until then the databases check fails, by design.

Residual risk (decision for lead and the user): `RunCommand` runs any shell command on the two instances, and the prod-write gate matches command text literally, so a session that reads the local config can reach production hosts outside this entry (for example `aliyun ecs RunCommand --profile "$(jq ...)"` passes the gate). The gate accepts this class by design only because the user clears local production credentials (intent 2026-10-28-202108); this profile is such a credential. A narrower shape exists (pre-create one Cloud Assistant command that holds the entry's fixed server half, allow the sub-user only to invoke that command and read results, pass the SQL as a parameter, no `RunCommand`) but it is not built here. Until the user decides, create the profile knowing this.
