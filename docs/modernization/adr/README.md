# FORCITIS one 现代化 ADR

本目录记录 FORCITIS one 现代化中的架构决策。STACK_DECISION.md、NAMING_STANDARD.md、GUIDING_PRINCIPLES.md、MODERNIZATION_BRIEF.md 只引用这里的决定，不另立结论。参照文档：forcitis-one `docs/adr/0001-tech-stack.md`（只参照文本，不参照代码）。

名称：ADR 正文中的「PSA」指老系统；已采纳 ADR 正文冻结不改（SESSION_PLAYBOOK §12.1），新文档与新 ADR 一律写 FORCITIS one / 老系统（用户 2026-10-14，守护 `check_legacy_name.py`）。

**ADR 写什么、不写什么**（用户 2026-10-16 采纳研究方案 P6、P7，intent `2026-10-16-131918-one-coordinator-ADR-管理优化-采纳-集中解决.md`）

- 写 ADR，当且仅当一个选择同时满足：① 影响结构（模块与 BC 边界、依赖方向）、质量属性（安全、可追溯、性能、一致性）、外部依赖、对外接口或数据形状之一；② 回退有成本（要改数据、迁移、接口或多个模块）；③ 有两个以上可行方案，且没有现成的上位规定（已采纳 ADR、规范、准则）可直接推出。
- 不写 ADR，改放这里：
  | 内容 | 去处 |
  |---|---|
  | 会话分工、协作流程、报告与派工约定 | `SESSION_PLAYBOOK.md` |
  | 编码与命名约定 | `CODING_STANDARD.md`、`NAMING_STANDARD.md` |
  | 用语 | `glossary/terms.yaml` |
  | 清单、快照、参数（BC 与聚合登记、阶段表、权限码、阈值） | 经用户认可的进各自的 SSOT 文件（如 `architecture/ddd/contexts.yaml`、`architecture/togaf/transitions.yaml`），受守护测试保护；未经用户认可的留在提议稿（提议中的 ADR 或 `architecture/proposals/`） |
  | 业务口径与政策参数 | 配置类（SESSION_PLAYBOOK §12.2，`CONFIG_CHANGELOG.md`） |
  | 领域规则结论 | `rules/RULE_REVIEWS.json` |
  | 现状勘查、取证明细、设计细节、方案比较长文 | `architecture/proposals/` 或证据文件，ADR 只引用路径 |
- ADR 只写**决定与判据**。需要列举时分开两类（ADR-0051 决定 1 第 1 条）：
  - **规范性内容**（如 BC 的模块标识、命名空间、BC 的合并与新增、禁止边、归属规则与判据）写在 ADR；它的任何改变——包括 BC 的增、删、合并——都要新 ADR。
  - **参考性快照**（如聚合清单、计数、分层快照）在 ADR 中标「参考快照，以 <SSOT 路径或提议稿路径> 为准」，随阶段复核更新，不需新 ADR。
  - 清单经用户认可后进 SSOT（用户 2026-10-16：「我认可的规划，要进SSOT」，intent `2026-10-16-124649`），ADR 引用其路径与提交号；未经用户认可的部分留在提议稿，不进 SSOT。
- ADR-0020 中的协作规则（会话、协议、调度）以 `SESSION_PLAYBOOK.md` 为准，今后只改 SESSION_PLAYBOOK，不再为其开 ADR；ADR 正文不动（见「勘误与历史偏差」第 3 节性质登记）。

## ADR 生命周期与变更规则

用户 2026-10-14：「已采纳的 ADR 不改正文，改决定就新增 ADR，标明「取代 ADR-00xx」，旧 ADR 改为已被取代、正文保留。」「新 ADR 必须写影响面、迁移方案、回滚方案，并同步修改对应守护规则。」用户 2026-10-16 对研究方案 P1–P7 答「采纳」（intent `2026-10-16-131918-one-coordinator-ADR-管理优化-采纳-集中解决.md`），本节据此修订。完整的变更治理见 `../SESSION_PLAYBOOK.md` §12；谁可以改什么见 §12.4。

### 1. 适用范围与格式代际

- **判定字段**：头部含「档位」字段的是**新格式**（下称新稿），不含的是**旧格式**（下称旧稿）。按字段判定，不按编号。
- **生成器判定法**：在标题行与第一个二级标题之间的头部区查找匹配 `^- \*\*档位\*\*：` 的行，命中即按新稿校验全部规则，未命中按旧稿校验。为防新稿漏写档位而落入旧稿校验，生成器内置常量 `LEGACY_FORMAT`：本规则合入 main 时 `adr/src/` 中已有的全部 ADR 编号（冻结，不再追加）；不在该常量中的 ADR 必须有「档位」字段，否则生成失败。
- 本规则合入前起草、未及合入 main 的 ADR（含 ADR-0029）不在 `LEGACY_FORMAT` 中，合入时须按新格式改写。
- 旧稿不回改：不补新字段、不拆分、不改编号。旧稿状态行只允许下列改动，其余既有内容保留：
  - 整份取代或废弃时，把开头的状态词改为「已被 ADR-NNNN 取代」或「已废弃」；
  - 被部分取代时，在状态行末尾追加括注「（范围已被 ADR-NNNN 取代）」。
- ADR-0001 至 ADR-0023 早于必备小节规则，不追补必备小节。
- 编号保持全局四位顺序号 `ADR-NNNN`，不按类别分目录、不加前缀、不用日期编号；号一经占用不复用（含已撤回、已拒绝的号）。

### 2. 状态

| 状态 | 含义 | 谁来改 | 头部须有 |
|---|---|---|---|
| 提议 | 已占号，起草或待批中；正文可改 | 起草会话 | — |
| 搁置 | 复审结论为暂不决定；正文保留，满足重启条件后回到「提议」 | 进入：用户决定后由起草会话改；回到提议：one-coordinator 核对重启条件已满足后改（或通知起草会话改），日期改为当日 | 理由（含重启条件）、用户原话 |
| 已采纳 | 用户批准；**正文冻结** | 用户批准后由起草会话照原话改；one-coordinator 同（不能替用户批准，§11 边界） | 用户原话、批准证据 |
| 已拒绝 | 用户看过并否决；正文保留，供日后防止重复讨论 | 用户决定后由起草会话改 | 理由、用户原话 |
| 已撤回 | 用户裁决前收回（并入别的 ADR、前提消失、占号后不再需要）；号作废不复用 | 见下「撤回权」 | 理由；用户指派的另须用户原话 |
| 已被 ADR-NNNN 取代 | 决定被新 ADR 整份替换；正文保留 | 新 ADR 的起草会话在新 ADR 改为「已采纳」的同一提交中改（用户批准新 ADR 即批准此改） | — |
| 已废弃 | 采纳后不再适用且没有替代；正文保留 | 用户决定后由会话改 | 理由、用户原话 |

**撤回权**（参照 SESSION_PLAYBOOK §11「边界」与 §12.4，起草人补充，随本稿一并批准）：
- 非用户指派的提议（起草会话自行发起，或调度派工、触发出处不是用户 intent）：起草会话或 one-coordinator 可撤回，写理由。
- 用户指派起草的提议（「背景」所列触发出处为用户 intent 或用户原话）：撤回须提交待决定收件箱（§11 战队协作第 1 条），由用户决定后由起草会话改，头部填用户原话。

已拒绝与已撤回的区别：已拒绝是用户对决定内容的否决；已撤回是不再推进，非用户指派的不经用户。部分取代不是状态：新稿写在被取代方的「被部分取代」字段，旧稿按第 1 节括注。

### 3. 新稿头部字段

头部在标题下、第一个二级标题前，字段按下表顺序，每个字段一行（多值字段写成下一级列表，每项一行）；未列出的字段名、重复字段、顺序错一律生成失败。字段名为「批准证据」「被部分取代」（用户 2026-10-16 批准，P2 原名为「证据」「部分取代」）。。

| 字段 | 必填 | 单 / 多值 | 写法 |
|---|---|---|---|
| 状态 | 是 | 单 | 第 2 节表中的状态词原样，不加括注；取代写「已被 ADR-NNNN 取代」 |
| 日期 | 是 | 单 | `YYYY-MM-DD`，当前状态的生效日：提议 = 占号 PR 合入 main 日；其余 = 状态变更日 |
| 档位 | 是 | 单 | `正式` 或 `轻量`（第 6 节）；也是新旧格式的判定字段（第 1 节） |
| 起草 | 是 | 单 | 负责会话名（如 `one-architecture`），复审提醒发给它 |
| 类别 | 是 | 单 | 第 3.1 节枚举之一 |
| BC | 是 | 多 | `architecture/ddd/contexts.yaml` 的 `id`；跨全部 BC 写 `全局` |
| 阶段 | 是 | 多 | `architecture/togaf/transitions.yaml` 的 `id`（如 `TA-1a`）；不限阶段写 `全阶段` |
| 取代 | 否 | 多 | 见第 4 节 |
| 被部分取代 | 否 | 多 | 写在被部分取代的一方，列出取代它的 ADR 与范围；见第 4 节；只由后来的 ADR 采纳时添加 |
| 用户原话 | 视状态 | 多 | 每项：「原话」（YYYY-MM-DD，intent `文件名.md`）；只摘决定性的一句，全文在 intent |
| 批准证据 | 视状态 | 多 | 每项一个可打开的出处：批准页链接、intent 文件、评审记录路径（与正文「## 证据」小节不同：本字段只放批准出处，故名「批准证据」） |
| 理由 | 视状态 | 单 | 一两句；搁置须写「重启条件：…」 |

- 提议时 `类别`、`BC`、`阶段` 可暂写 `待定`；改为非提议状态前必须填实。
- 采纳后可改的头部字段只有：状态、日期、被部分取代、理由（废弃时）。其余字段与正文一起冻结。

| 业务主干 | 过账、期间、收入确认、单据锁定与冲销等跨 BC 不变量 |
| 方法 | 建模方法、架构知识框架、指导思想（不含协作规则） |

### 4. 取代与被部分取代

- 「取代」写在新 ADR，「被部分取代」写在被取代的新稿；两边必须成对，生成器双向核对。
- 每项一行，**以 `ADR-NNNN` 开头**（现行生成器已如此校验），后接可选的范围短语；范围只写到「小节 + 条号」，如 `ADR-0047 决定第 5 条第 4 点`、`ADR-0024 影响面「BC」`、`ADR-0041 决定 1（部分）`。
- 不写行号，不写文件路径；范围短语不超过 30 字，生成器校验（用户 2026-10-16 批准）；逐句细目（被替换的原句、替换后的写法）写进本 ADR 的「决定」或「背景」。
- 整份取代：项中只写 `ADR-NNNN`，被取代方状态改为「已被 ADR-本号 取代」。部分取代：被取代方为新稿时在其「被部分取代」加一项 `ADR-本号 范围`；为旧稿时在状态行末尾括注「（范围已被 ADR-本号 取代）」。
- 以上修改与新 ADR 改为「已采纳」在同一提交中完成。

### 5. 小节

二级标题只能取下列名称，按此顺序，不得增设（附加内容并入现有小节：与其他 ADR 的关系写入「背景」，未定事项与接口写入「后果」，评审记录写入「证据」）：

背景 / 决定 / 影响面 / 迁移方案 / 回滚方案 / 需同步修改的守护规则 / 后果 / 证据 / 备选方案（未采用）

| 档位 | 采纳时必有 | 可选 |
|---|---|---|
| 正式 | 全部九节 | — |
| 轻量 | 决定、影响面、迁移方案、回滚方案、需同步修改的守护规则、证据 | 背景、后果、备选方案（未采用） |

提议期只校验小节名与顺序，不校验是否齐全；改为「已采纳」时校验齐全。

### 6. 档位与勘误

**正式档**：默认档位。

**轻量档**用于可回退的小决定，须同时满足：
1. 回退不涉及已过账事实、已应用迁移（基线关闭后）、已发布的对外接口；
2. 不改变 BC 边界，不引入新的依赖或技术选型；
3. 不取代、不部分取代任何已采纳 ADR，只用于新的小决定；影响面、迁移方案、回滚方案、需同步修改的守护规则四节照写（可各一两句），与用户 2026-10-14 原话一致（用户 2026-10-16 批准）；
4. 源文件不超过 6 KB。

判据 1、2、4 与 6 KB 为 one-architecture 裁定（复核建议）；判据 3 与必有小节经用户 2026-10-16 批准。

任一条不满足即用正式档。轻量档的「决定」用一句话写：「在〈情境〉下，面对〈问题〉，决定〈方案〉而非〈备选〉，以达成〈目标〉，接受〈代价〉。」后接可判定的条款。轻量档同样占全局编号、经用户批准。

**勘误**不是 ADR、不占编号、不改正文：只用于不改变决定含义的问题（笔误、失效链接、文件或模块改名后的引用、残留标记）。在「勘误与历史偏差」第 2 节登记正确读法，one-coordinator 核对后合并，不需用户批准。拿不准是否改变含义的，由 one-architecture 判定；判为改变含义的按轻量档或正式档走。改变某 ADR 效力来源或性质的（如协作规则改以 SESSION_PLAYBOOK 为准），不是勘误，须有用户原话，登记在第 3 节性质登记。

### 7. 一份一决定与大小

- 新稿一份只做一个决定（可有多条实施条款，但只有一个可单独采纳或拒绝的选择）；两个可分别采纳或拒绝的选择拆成两份。
- 正式档源文件超过 20 KB（20,480 字节）须拆（P7）：提议时生成器告警，改为非提议状态时生成失败。

### 8. 占号与起草

1. **占号**：起草者用 `new_adr.py` 取下一个号，生成空壳并单独开 PR；空壳 PR 合入 main 即占号，不在分支上手查号码。两个 PR 争同号时先合入者得号，后者改号。
2. **空壳最少内容**：完整头部（状态「提议」；类别、BC、阶段可写 `待定`）+「背景」一节两到五句：要决定什么、为什么现在决定、触发出处（用户 intent、派工或评审编号；撤回权据此区分，见第 2 节；拿不准是否用户指派的，按用户指派处理）。
3. **起草即校验**：提议稿与已采纳稿一样落在 `adr/src/`，生成器对提议稿校验头部、字段取值、小节名与顺序、「取代」写法与对象存在。ADR 草稿不再放 `architecture/proposals/`（该目录留给研究、设计方案与评审记录）。
4. **提议不是结论**：其他文档不得把提议稿当作已决定引用。
5. **撤回**：按第 2 节撤回权改「已撤回」并写理由，文件保留，号不复用。

### 9. 评审

1. 首轮评审一律用 opus（现行模型分级：opus 做首轮评审）。正式档经 `code-modernization:architecture-critic` 对抗性评审；轻量档的评审即按评审模板 `quality/review-briefs/03-adr.md` 的轻量子集出题，模板子集即该档的架构评审（对应 2026-10-14 原话第 3 条「ADR 类走架构评审」，intent `2026-10-14-089`）。评审意见与处理结果写入「证据」小节。
2. **全文检索被改条款**（每份新稿必做）：起草者对本 ADR 修订或涉及的对象、表、列、枚举值、权限码、BC 标识，在 `adr/src/` 全文检索，在「证据」小节中写「检索记录」：检索词、命令、命中的 ADR 列表，以及每份的结论（相容 / 本 ADR 取代其某条 / 无关）。评审员重放检索并核对：命中而未列入「取代」又判为不相容的，评审不通过。
3. 用户批准后改为「已采纳」，填用户原话与批准证据字段。

### 10. 提议复审

1. 状态为「提议」且距「日期」超过 7 天（起算日为空壳占号合入 main 日；one-architecture 裁定（复核建议））的，生成器在 `build_all.py` 输出与 `STATUS.md` 中列为超期提议。
2. one-coordinator 在 `COORDINATOR_LEDGER.md`「ADR 提议复审」一节维护超期提议与搁置清单，每周核对一次（复审日由调度定，暂定周一）：
   - 超期提议**先通知起草会话**（由「起草」字段确定）补齐材料、推进评审，不推给用户；
   - 评审已过、材料齐全（批准页已发布）的，才提交待决定收件箱（SESSION_PLAYBOOK §11 战队协作第 1 条）；
   - 搁置项只在重启条件满足时处理：调度改回「提议」并通知起草会话，按上两条推进；
   - 每日简报只列进收件箱的项（§11 战队协作第 8 条「平时只推送卡住主线的事」）。
3. 用户复审结论只有三种：采纳、拒绝、搁置。搁置须写原因与重启条件。
4. 超期不自动作废。
5. 自动核对：intent 中出现对某 ADR 的批准、拒绝或搁置，而该 ADR 状态未相应改变的，生成时告警。
