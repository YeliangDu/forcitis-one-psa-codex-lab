# ADR-0078：工号全局唯一、复职沿用，可作唯一键与匹配键

- **状态**：提议
- **日期**：2026-10-22
- **档位**：正式
- **起草**：one-architecture
- **类别**：数据
- **BC**：
  - organization.workforce
- **阶段**：
  - TA-1b
- **取代**：
  - ADR-0033 决定 6 第 1 条的唯一键与匹配键禁止
  - ADR-0033 守护规则第 7 条
  - ADR-0033 决定 11 RULE-368 的工号不作键

## 背景

用户 2026-10-21 在 W2 设计评审中定：工号全局唯一、复职沿用、发号后禁改，迁入重复拒收进处置清单（intent `2026-10-21-100711-one-coordinator-PR-#494-评论-63111.md`，PR #494 评论 6311130069）。这与 ADR-0033 决定 6 第 1 条「任何模块不得以员工编号作主键、唯一键、外键、关联键或匹配键」及其守护 7 相冲突。ADR-0033 当时的依据是老系统员工编号不唯一（5 个重复、42 人为空）；用户的决定是新系统自己保证唯一，老系统的重复在迁入时处置。本稿由 one-coordinator 派工（RULING-COORD-20261022-05），出处为用户 intent，按用户指派处理；不阻断 W2 PR-B。

## 决定

本稿只取代 ADR-0033 对唯一键、匹配键的禁止；主键、外键、关联键的禁止不变（第 5 条）。守护 7 改写为本稿守护第 1、2 条。

1. **唯一**：`organization_workforce.employees.employee_code` 在全部员工行上唯一（含已离职），库层 `uk_employees_employee_code UNIQUE (employee_code)`。工号可空（尚未发号）；空值不参与唯一，也不参与匹配。
2. **复职沿用**：复职在原员工上开新的在职版本，不新建员工行，工号不变、不另发（W2 设计第 4 节「复职」，账号按员工唯一，ADR-0055 决定 2）。
3. **发号后禁改**：工号一经登记即不得更改，命令拒改（与法人代码「发号后禁改」同法，ADR-0033 决定 5，§14.1 D17 细则 8）；登记错的不更正工号，按 W2 设计的更正命令处置，不改写已有工号。
4. **可作唯一键与匹配键**：`organization.workforce` 的 api 可按工号取单个员工（导入、迁入匹配、检索）。匹配须恰好命中一个；工号为空或查无此号即失败并告警，不回退按姓名等其他字段猜。
5. **仍不作主键、外键、关联键**：员工的主键与一切引用仍是自有 `employee_id`（UUIDv7，ADR-0033 决定 1）。其他表不得以工号关联员工，也不复制工号作关联列；要显示工号的，经 api 读或在读模型投影。工号不作接口与事件中的 ID（ADR-0033 决定 6 第 2 条不变）。
6. **迁入不放宽**：迁入时与已有员工工号重复的行拒收，落入重复工号冲突清单（W2 设计 `employee_code_conflicts`），每行处置三选一（合并 / 改号 / 拒收不迁），带处置人与期限，业务可查（ADR-0071 第 11 条）。不为迁入临时去掉唯一约束。
7. **访问级别不变**：工号仍为 SENSITIVE、`PI`（ADR-0043 U-2 未定，本稿不改）；作匹配键不改变其个人信息性质，日志与审计照 ADR-0043 决定 3 不写工号原值。

## 影响面

- `organization.workforce`：基线普通索引 `employees_employee_code_idx` 换成唯一约束（W2 PR-B 已列，`data/W2_PR_B_EMPLOYEE_VERSIONS_DDL_DRAFT.md` 第 3 条）；工号改写命令拒改；api 增按工号取员工的方法。
- 迁入（ADR-0036、ADR-0071）：重复工号进冲突清单，表随迁入核对卡的数据设计签发。
- 其他 BC：不受影响，仍按 `employee_id` 引用。
- 守护：`DataArchitectureTest` 中 `EmployeeCodeNotKeyTest` 与 `EmployeeCodeNotKeyIT` 改写（见守护规则）。

## 迁移方案

随 W2 PR-B 落：同一 PR 中加唯一约束、删普通索引、改写守护。现库工号来自同步快照；上线前没有生产数据写入新库，基线开放期直接改基线；之后若库中已有重复，迁移前先跑重复检查，有重复即迁移失败并列出，不自动去重。

## 回滚方案

回退 W2 PR-B 中的唯一约束与守护改写即可，恢复普通索引与 ADR-0033 守护 7；回退后按工号取员工的 api 方法一并删除，调用方改回按 `employee_id`。迁入冲突清单可保留（它在回退后仍是有用的核对差异）。

## 需同步修改的守护规则

随 W2 PR-B 修改：

1. `EmployeeCodeNotKeyTest`（`DataArchitectureTest`）改写为 `EmployeeCodeKeyScopeTest`：
   - `employee_code` 只允许出现在 `organization_workforce.employees` 的唯一约束 `uk_employees_employee_code` 中，不得出现在任何主键、外键、排他约束中；
   - 除 `organization_workforce.employees` 与迁入冲突清单（`original_code`）外，任何表不得有 `employee_code` 列或以工号为名的列；
   - 按工号取对象的方法只允许在 `organization.workforce` 的 api 与其仓储中，其他模块的主代码不得定义此类方法。
   - 注入测试：别处的唯一索引、外键、其他表的工号列、其他模块的 `findByEmployeeCode` 都被拦下。
2. `EmployeeCodeNotKeyIT` 改写：
   - 同工号插入第二个员工失败；
   - 工号为空的多个员工可以并存；
   - 复职后工号不变；
   - 改工号的命令被拒、无写入；
   - 按工号查空号或无此号时失败并告警。
3. 迁入：冲突清单的守护随迁入核对卡（ADR-0071 第 11 条）。

## 后果

- 工号成为人事与导入的可靠检索键，业务可直接按工号对账与导入。
- 代价：工号一旦发错只能按更正流程处置，不能直接改；迁入要人工处置老系统的重复工号。
- 关联仍用 `employee_id`，不因工号规则变化牵动其他 BC 的表。

## 备选方案（未采用）

- 维持 ADR-0033：工号不唯一、不作键。用户已定唯一，不采用。
- 工号作外键或关联键（其他表直接存工号）：工号虽唯一，但属个人信息、可能需更正处置，用作关联会把它散到各 BC 的表里，违反 ADR-0033 决定 1 自有主键与 ADR-0043 的最小暴露，不采用。
- 迁入时临时放宽唯一约束、事后去重：与用户「迁入重复拒收进处置清单」不符，不采用。
