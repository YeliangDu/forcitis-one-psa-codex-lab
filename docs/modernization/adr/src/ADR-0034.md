- **状态**：提议（2026-10-15 起草，待 architecture-critic 评审与用户批准；采纳时在同一提交中把 ADR-0026、ADR-0027、ADR-0032 的状态行按「取代」标注）

## 决定

### 1. 角色定义版本化

1. **`platform_identity.roles` 只留不可变的部分**：`role_id`（UUIDv7）、`code`（预留码与唯一性不变）、`kind`（SYSTEM / CUSTOM）、`is_administrative`，以及乐观锁 `version` 与 `event_count`。`name`、`status`、`access_scope` 从 `roles` 移出。
   - 盘点建议把「是否管理员」放进版本。本 ADR 留在 `roles`：现有代码没有任何修改它的路径（`UpdateRole` 只改名称、范围、权限与启用），它与角色码一样决定角色的本质。以后若需要可改，再按本 ADR 的模式移入版本。
2. **新建 `platform_identity.role_versions`**（角色版本，提议术语），每次定义变化一行：
   - `role_version_id uuid`：主键，应用侧生成 UUIDv7（与 ADR-0033 草稿一致）；
   - `role_id uuid NOT NULL`：外键到 `roles`；
   - `version_number integer NOT NULL`：从 1 起递增，`uk_role_versions_role_id_version_number`；
   - `effective_from_at timestamptz NOT NULL`、`effective_to_at timestamptz`：生效时刻与失效时刻，空表示仍有效；
   - 定义内容：`role_name`、`role_status`（ENABLED / DISABLED）、`access_scope_kind`（取值同现 `roles.access_scope`）。1b 的 `legal_entity_scope` 随 ADR-0026 第 2 项加在版本上；
   - `recorded_by uuid`（记录人）：只有基线种子的版本可以为空，用 CHECK 限定为种子行；
   - `change_reason text NOT NULL`（理由）；
   - `authorization_request_id uuid`：经双人确认时必填，外键到 `authorization_requests`；
   - 约束：
     - `EXCLUDE USING gist (role_id WITH =, tstzrange(effective_from_at, effective_to_at, '[)') WITH &&)`：同一角色的版本不重叠；
     - `EXCLUDE USING gist (lower(role_name) WITH =, tstzrange(…) WITH &&)`：同一时刻角色名称唯一，取代现在的 `uq_roles_name`；
     - `CHECK (effective_to_at IS NULL OR effective_to_at > effective_from_at)`。
3. **新建 `platform_identity.role_version_permissions`**：
   - `role_version_permission_id uuid` 主键（UUIDv7）、`role_version_id uuid NOT NULL`（外键）、`permission_code text NOT NULL`，`uk_role_version_permissions_role_version_id_permission_code`；
   - 每个版本存**完整**权限集合，不存差量：任一时刻的还原只读一个版本，不需要回放；
   - 行写入后不可改：没有 UPDATE、DELETE、TRUNCATE。
4. **改角色定义 = 新增版本**：
   - 同一事务内关闭当前版本（`effective_to_at` = 变更时刻），插入新版本及其完整权限集合（`effective_from_at` = 同一时刻），并以 `roles.version` 做乐观锁；
   - 新建角色、改名、改范围、改权限、启用与停用，都是新增版本；
   - 定义没有变化时不新增版本（同现 `UserAccount.replaceRoles` 的「无变化不记录」）。
5. **删除角色 = 关闭最后一个版本、不再开新版本**：`roles` 行与全部版本保留。
   - 前提不变：仍有当前有效授予时拒绝（现 `PLATFORM_IDENTITY_ROLE_IN_USE`）；
   - 界面与事件仍称「删除角色」（`RoleDeleted`），不另造词；
   - 被删除角色的 `code` 不能再用于新角色，避免历史中同码指向两个角色。
6. **变更时刻**：取应用注入的 `Clock`（经双人确认的，取确认被应用的时刻），作为参数传入，不用数据库时钟（`TimeSourceGuardTest` 已守护）。1a 不支持预约未来生效的版本：未来能力留在规则卡。

### 2. 授予版本化

1. **`account_roles` 退役，新建 `platform_identity.account_role_grants`**（角色授予，提议术语），一行表示「某账号在一段时间内持有某角色」：
   - `account_role_grant_id uuid`：主键（UUIDv7）；
   - `user_id uuid NOT NULL`、`role_id uuid NOT NULL`：同 schema 外键；
   - `effective_from_at timestamptz NOT NULL`、`effective_to_at timestamptz`：空表示未关闭；
   - **开启**：`granted_by uuid`（授予人）、`grant_channel_kind`（授予渠道，见第 3 条）、`grant_authorization_request_id uuid`（经双人确认时必填）、`migration_batch_id uuid`（仅 `MIGRATION` 渠道，必填）；
   - **关闭**：`revoked_by uuid`（收回人）、`revocation_cause_kind`（收回原因，见第 4 条）、`revocation_authorization_request_id uuid`；
   - 约束：
     - `EXCLUDE USING gist (user_id WITH =, role_id WITH =, tstzrange(effective_from_at, effective_to_at, '[)') WITH &&)`：同一人同一角色的区间不重叠，因此同一时刻至多一条有效授予；
     - `CHECK ((effective_to_at IS NULL) = (revocation_cause_kind IS NULL))`；
     - `CHECK (effective_to_at IS NULL OR effective_to_at > effective_from_at)`；
     - 渠道与必填列的成对 CHECK：`MANUAL` 须有 `granted_by`；`MIGRATION` 须有 `migration_batch_id`，其他渠道不得有。
   - 索引：`(user_id) WHERE effective_to_at IS NULL`、`(role_id) WHERE effective_to_at IS NULL`，供当前读取与持有人计数；`(user_id, effective_from_at)`，供历史查询。
2. **只追加 + 关闭区间**：
   - 「收回」= 把开放行的 `effective_to_at` 置为收回时刻，同时写入收回人、原因与申请；
   - 行不删除；已关闭的行不能改；开放行除关闭外不能改；
   - 同一人再次获得同一角色，新增一行。
3. **授予渠道** `grant_channel_kind`（text + CHECK）：
   - `MANUAL`：账号授权界面，含经双人确认的申请；
   - `DEFAULT_ROLE`：建档时的默认角色（RULE-344）；
   - `OPERATIONS`：运维命令 `grant-role`（ADR-0026 第 5 项第 5 条、ADR-0030）。运维命令的操作人与见证人是自报文本，记在审计中，`granted_by` 为空；
   - `MIGRATION`：老角色迁入（ADR-0026 第 8 项）。
4. **收回原因** `revocation_cause_kind`（text + CHECK）：`MANUAL`（账号授权）、`SEPARATION`（离职）、`OPERATIONS`（运维命令 `revoke-role`）、`MIGRATION_ROLLBACK`（迁入批次回退）。
5. **整组替换改为按差异逐条关闭与新增**：
   - 账号授权接口仍提交「改后的完整角色集合」，接口语义与 OpenAPI 请求体不变；双人确认的申请仍存完整集合（`authorization_requests.role_codes`）；
   - 应用时（含申请被确认时）以**当时的**当前有效授予为基准求差：不再需要的关闭，新增的开启，不变的不动；
   - RULE-346 记的是老系统「插入新的、删除缺的」，只作证据，存储不照搬。
6. **老角色迁入的批次**（取代 ADR-0026 第 8 项第 7 条中的两处、回滚方案第 4 条）：
   - 迁入的授予以 `MIGRATION` 渠道开启，带 `migration_batch_id`；
   - 回退一个批次 = 关闭该批次仍开放的授予，原因 `MIGRATION_ROLLBACK`，并吊销相关会话；
   - 迁入前的授予状态按第 4 项第 3 条在批次开始前的时刻还原，不另建 `account_role_snapshots`。
7. **聚合**：
   - 授予行是 `UserAccount` 的子行：聚合加载**当前有效**授予（含授予行 ID 与开启时刻），保存时只写差异，以 `user_accounts.version` 做乐观锁；
   - 收回时刻、操作人、渠道、原因与申请由应用服务作为参数传入领域方法；
   - 不新增跨聚合事务。

### 3. 离职：关闭全部有效授予（取代 ADR-0027 第 1 项第 6 条与 ADR-0032 第 4 项第 1 条中的「删除」）

1. 同步把某人标为离职、且该运行不处于 HELD 时：**关闭其全部当前有效授予**（含 `super_admin` 与安全审计员），原因 `SEPARATION`，收回人为空（系统处置），收回时刻为处置时刻。
2. **安全效果不变**：处置完成后，此人没有任何当前有效授予，即时吊销会话并清缓存。应急账号停用、会话吊销、HELD 约束（ADR-0027 第 1 项第 7 条，经 ADR-0028、ADR-0030 修订）、不另发通知（ADR-0032 第 4 项第 1 条），全部照旧。
3. **逐条审计照旧**：每关闭一条授予写一条 `platform.identity.account.role.revoked`，detail 增加授予行 ID 与原因 `SEPARATION`。
4. **收回时刻不是离职日期**：区间记录的是系统实际收回授权的时刻。业务上的离职日期与观察时刻按离职日期规则卡另行记录；两者的差在审计与历史查询中可以对照，本 ADR 不用离职日期回填区间。
5. 重新入职不自动恢复任何授予（RULE-344「离职或已删除员工不授」不变）；需要时按授予方式重新授予，新增一行。

### 4. 读取

1. **当前有效授予**：
   - 定义：`effective_to_at IS NULL AND effective_from_at <= :at`。`:at` 取应用注入的 `Clock`，不用数据库时钟。
   - 与派工口径「区间包含 now()」的关系：本系统不预约未来的关闭，所以两者在时钟一致时相同。不同的只在一处：已关闭的行**一律不算有效**，不论读取节点的时钟是否落后于关闭节点。这是 fail-closed 的取法，保证收回不因时钟偏差延后生效。
   - 当前角色版本同理：`role_versions` 中未关闭且已开始的那一行。
2. **只看当前有效的地方**：
   - 每请求权限与数据范围；
   - I-12 自查：不能改自己的角色、自己持有角色的定义；
   - 授予上限；
   - 超管与审计员持有人计数：HELD 判定、放行下限、应急账号每日核对；
   - 敏感判定：`SensitivePermissions.roleIsSensitive` 读当前版本；ADR-0032 的「有持有人」；
   - 角色删除前的占用检查；
   - 账号详情与角色列表接口。

   这些读取都经仓储中**同一个**当前有效谓词，不在调用方各写一份。
3. **按时刻还原**：
   - 定义：`tstzrange(effective_from_at, effective_to_at, '[)') @> :asOf`，同时作用于授予与角色版本，得到「某人在 `asOf` 持有哪些角色、每个角色当时的名称、状态、范围与完整权限集合」。
   - 早于最早版本或最早授予的时刻：返回空，并在响应中标明「早于记录起点」（盘点 D17 草案第 5 条）。
4. **历史查询接口**：
   - 授权历史只读接口，按时刻还原上述内容，以及某人或某角色的授予与版本变更序列；
   - 导出接口，供审计导出；
   - 两者路径与 OpenAPI 在实现 PR 中契约先行定义，遵守 ADR-0008。
   - 权限码见 0034-Q1，建议新增 `platform.identity:authorization-history:read` 与 `platform.identity:authorization-history:export`，授予方式为双人逐人（ADR-0032 第 2 项），种入「安全审计员」；
   - 查询与导出本身写审计（ADR-0026 第 6 项第 5 条「查看审计本身也记审计」）；
   - 数据访问注册表登记为 `GLOBAL`（理由：安全审计数据）。

### 5. 角色范围明细同样版本化（F-1 依赖本 ADR）

1. ADR-0026「1a 交付范围」中的「角色范围授予明细表」（自定义部门；1b 起的 `LISTED` 法人）挂在**角色版本**下，不挂在 `roles` 下：
   - 引用 `role_version_id`，每个版本存完整明细；
   - 行写入后不可改；
   - 改明细即新增角色版本（第 1 项第 4 条）。
2. 表名与列名由 F-1 按 NAMING_STANDARD 与 `terms.yaml` 定（ADR-0026 影响面暂名 `role_scope_grants`）。
3. **F-1 依赖本 ADR**：F-1 的范围计算读当前角色版本的明细；按时刻还原同时还原范围明细。F-1 不得先按「挂在 `roles` 下、整组替换」实现再改。

### 6. 实施时机

1. 属安全项，**首次部署任何环境前完成**；在 W2 与 K-2 时态基座同期实现（`phase1a/NEXT_BATCH_PLAN.md`:52-56、:117）。
2. 区间类型、只追加触发器与守护复用 K-2 的统一写法，K-2 同时提供时刻（`timestamptz`）变体；本 ADR 的表是该变体的首批使用者。
3. 列类型按 ADR-0033（提议）的标识形态：`role_id`、`user_id` 为 `uuid`。ADR-0033 未采纳或 R-1b 未合并时，跟随当时 `roles.role_id`、`user_accounts.user_id` 的类型，R-1b 统一改。
4. 在 F-1 之前或同一 PR 中落地。

1. **没有已部署的数据**：基线开放期内直接改 `platform_identity` 基线（SESSION_PLAYBOOK §12.2 首次部署前的迁移基线第 2 条），不追加迁移。
2. **结构差异证据**：PR 附「预期表结构 diff」，由 opus 核对。用两个空库分别执行改动前后的基线，`pg_dump --schema-only` 的差异只能是：
   - `roles` 移出三列；
   - 新建三张表及其约束、索引、触发器；
   - 删除两张表。
3. **种子**：现有种子角色（`super_admin`、`employee`、安全审计员、业务管理员、组织数据管理员、流程管理员等）逐一改写为「`roles` 行 + 版本 1 + 版本 1 的权限」，权限集合与改前逐码相同。PR 中附改前后「角色 → 权限码」对照的查询结果，差异须为空。
4. **测试夹具**：现有 14 个测试文件直接读写 `account_roles`（另有若干直接写 `role_permissions`），例如 `SeparationRevokesRolesIntegrationTest.java`:54、:133，`IdentityIntegrationTest.java`:187、:212。

## 回滚方案

- **首次部署前**：回退实现提交，基线恢复为两张整组替换表，守护一并回退。没有数据需要处理。
- **首次部署后**：
  - 不再回到「删除」语义：已关闭的授予与旧版本行是授权历史，不删除；
  - 若新表的读写出现问题，以修复提交前进；
  - 确需临时退回整组读取的，由当前有效授予在只读视图中投影出「账号 → 角色」集合供旧代码读取，写入仍走新表。
- **边界**：已写入的授予行、角色版本、审计与事件不回滚；已因离职关闭的授予不会因回滚重新生效。

## 需同步修改的守护规则

与本 ADR 的实现在同一个 PR 中提交（W2，与 K-2 同期；实施会话由 one-coordinator 派定）：

1. **禁止删除与改写**（`GrantHistoryAppendOnlyIntegrationTest`，参照 `OrgHistoryAppendOnlyIntegrationTest`）：
   - `account_role_grants`、`role_versions`：DELETE、TRUNCATE 被触发器拒绝；改已关闭行被拒绝；改开放行中关闭列以外的列被拒绝；
   - `role_version_permissions`：任何 UPDATE、DELETE、TRUNCATE 被拒绝；
   - `RoleSeparatedDeploymentIT` 增加：运行角色对这三张表执行 DELETE、TRUNCATE，以及对 `role_version_permissions` 执行 UPDATE，均为 `permission denied`。
2. **区间不重叠**：
   - `DataArchitectureTest` 的 D2 扩展时刻变体：`DIMENSION_VERSIONED` 表可用 `effective_from_at timestamptz NOT NULL` + 可空 `effective_to_at` + `tstzrange` 的 `EXCLUDE` 约束；
   - 注入样例：缺 `EXCLUDE` 的时刻版本表必须失败；
   - §4b 撤销清单与注册表一致（现有核对覆盖新表）；
   - 集成测试：同一人同一角色插入重叠区间被约束拒绝。
3. **当前有效读取一致性**（`CurrentGrantReadConsistencyIntegrationTest`）：
   - 夹具含已关闭授予、开放授予、已关闭的旧角色版本与当前版本；
   - `SessionPrincipals` 权限、`PrivilegeCeiling`、I-12 自查、持有人计数（`AdministratorSeparationReview`、`RoleHolders`）、`roleIsSensitive`、账号详情、数据范围，都只反映开放授予与当前版本；
   - 文本守护：`src/main` 中触及 `account_role_grants`、`role_versions` 的 SQL，要么引用仓储的当前有效谓词常量，要么属于登记的授权历史读取类，否则失败；
   - 时钟偏差用例：读取时刻早于关闭时刻时，已关闭的授予仍不算有效。
4. **离职后无有效授予**（`SeparationRevokesRolesIntegrationTest`，即 ADR-0027 守护第 2 条，取代其中「`account_roles` 已删除」一句）：
   - 同步标为离职后，此人当前有效授予为零（含 `super_admin`）；
   - 授予行总数不变，每行原因为 `SEPARATION`、收回时刻为夹具时钟；
   - 逐条审计含授予行 ID；应急账号停用；会话吊销；
   - HELD 期间不关闭，放行后关闭。
5. **按时刻还原**（`AuthorizationHistoryAsOfIntegrationTest`）：
   - 按 t1 建角色（权限 {A}、范围 SELF）并授予某人；t2 改为 {A, B}、范围 ALL；t3 离职关闭；t4 重新授予；
   - 在 t1 与 t2 之间、t2 与 t3 之间、t3 与 t4 之间、t4 之后查询，角色、权限集合与范围逐项等于当时的值；
   - 早于 t1 的查询返回空并标明「早于记录起点」；
   - 无权限访问返回 403，查询与导出写审计。
6. **按差异写入**：
   - `ReplaceAccountRoles` 由 {X, Y} 改为 {Y, Z}：只关闭 X、只开启 Z，Y 的授予行 ID 与开启时刻不变；
   - 双人确认的申请按确认时的当前授予求差，新行带申请 ID；
   - `UpdateRole` 每次修改恰好新增一个版本；内容不变时不新增；
   - 删除仍被持有的角色返回 409。
7. **`SingleAggregateGuard` 核对**：
   - 本 ADR 不新增多聚合事务，`multi-aggregate-exceptions.txt` 不变；
   - 守护的表到聚合映射登记 `account_role_grants` → `UserAccount`，`role_versions`、`role_version_permissions` → `Role`；
   - `HandleOrgSnapshotChange` 在一个监听事务中处理多名离职者，属同一聚合类型的多个实例，现有守护按类型集合判定，核对其结论不变。
8. **其余守护同步**：
   - `RepositoryWriteGuardTest`：新表的写入经 `roles.version` 或 `user_accounts.version` 乐观锁，`unversioned-table-writes.txt` 按需登记理由；
   - `TimeSourceGuardTest`：新 SQL 不含数据库时钟；
   - `PrimaryKeyTypeGuardTest`：三张新表为 `uuid` 主键；
   - `DdlNamingTest`：新列类别词；
   - `MustAuditActionsTest`：事件改名；
   - `PermissionGrantModeTest`：0034-Q1 的新码；
   - `GlossaryTest`：提议术语；
   - SECURITY_INVARIANTS I-14 的验收测试对照（守护第 1、4、5 条）。
9. **ADR-0026、ADR-0027 守护中提到 `account_roles` 的断言**：`SensitiveGrantTwoPersonIT`、`SelfGrantForbiddenIT`、`EmergencyLoginIT` 等，改为按当前有效授予断言；断言强度不降低，逐条列在 PR 中。

## 后果

- 任何时刻「谁持有什么角色、这个角色当时含什么权限、范围多大」都能从库中直接还原，不依赖 30 天的事件归档或审计 detail 的拼接。季度授权复核（ADR-0026 第 6 项第 3 条）、安全取证与审计导出都有了数据来源。
- 离职的安全效果不变：处置后没有任何有效授予。区别只在于记录保留，且收回原因可查。
- 授予与角色定义的每次变化都带操作人、渠道或原因与申请，双人确认的结果能追到具体的授予行与角色版本。
- **代价**：
  - 读取都要带时刻谓词，靠仓储单点与守护第 3 条防止遗漏；
  - 写入从整组替换变为求差；
  - 14 个以上测试文件的夹具要改写；
  - 被删除角色的代码不能复用。
- 本 ADR 不新增「不得给离职者授予」的规则：离职者的会话按在职复核失效（ADR-0027 第 1 项第 4 条），授予本身不生效。是否在授予时拒绝离职者，另行在规则卡中提出。

## 备选方案（未采用）

- **保留删除，靠审计日志还原**：
  - 审计 detail 只有角色码，角色定义变更只有 `roleId`，拼不出「当时含哪些权限、范围多大」；
  - 事件归档 30 天，审计 3 年后归档；
  - 还原依赖解析自由文本，与 intent 155 把审计拆成结构化列的方向相反。
- **事件溯源**（授予与角色以事件流为唯一事实，当前状态为投影）：能还原，但每请求权限都要依赖投影的及时性与一致性；现有模块都以表为事实、事件为通知，单为授权引入第二种持久化范式，代价与风险都高于区间表。
- **只版本化授予、不版本化角色**：能回答「当时持有哪个角色」，回答不了「这个角色当时含哪些权限」。角色加码与放宽范围正是 ADR-0032 第 1 项第 3 条防范的扩权路径，不版本化角色就无法事后核查。
- **用 `tstzrange` 单列存区间**：NAMING_STANDARD §2.4 没有区间类别词，而现有版本表与 `refuse_version_rewrite` 都用两列。两列 `_at` + 排他约束中的 `tstzrange` 表达式，语义相同，与现有写法和守护一致。
- **当前有效按「区间包含注入时刻」判定**：时钟一致时与第 4 项第 1 条相同；但读取节点的时钟落后于关闭节点时，会把刚收回的授予算作有效。改取「未关闭且已开始」，收回 fail-closed。
