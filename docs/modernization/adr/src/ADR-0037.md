## 决定

### 1. 读取范围

1. 迁移取证与应用运行时都可以只读 A8（`a8_db`）与老系统库（`ruoyi-vue-pro`）的任意表和列，含基表、元数据与凭据列。
2. 数据库授权按库级只读给出（PR #135 已执行的形状：库级 `GRANT SELECT`；库级 DENY 写、DDL、EXECUTE、REFERENCES；不加入任何数据库角色；A8 的基表元数据可见），不再随用途逐个对象、逐列收窄。

### 2. 保留的约束

1. **只读不写**：新系统不写 A8 与老系统库的任何数据、不改其结构；账号层面以库级 DENY 与启动校验（第 4 项）双重保证。
2. **防腐层**：外部读取只在 `platform.integration` 的适配器中（SESSION_PLAYBOOK §14 第 8 项、§14.1 D11、D16；ADR-0021 第 4 项第 4 条）；领域模块不出现外部表名、列名与外部取值。老系统待办读取按 ADR-0033 第 2 项第 9 条移入集成层，移入前 `platform.approval.infrastructure.legacy` 是现存的唯一例外，不新增例外。
3. **记录系统不变**：运行时读到的 A8 与老系统业务数据只用于取证、迁入、对账与新旧等价核对，不作为新系统权责事实的输入，不形成双源（ADR-0021 第 2 条、ADR-0024 第 3 条）。组织主数据同步仍按现有规则（6e 前 A8 为源）。
4. **外部取值映射**：外部状态码、类型码在防腐层映射为自有枚举，未知取值失败并告警，不静默跳过（D16）。
5. **列最小从授权层移到代码层**：
   - 应用每条读取语句只 SELECT 用到的列，不写 `SELECT *`；读取的表与列登记在读取列登记中（第 6 项）。
   - 敏感字段（生日、银行卡、薪酬与金额、证件号、口令、令牌等）只在用到时读取，按 D13 登记在 `data-classification.txt`，不进日志、事件与分析层明细。
   - 需要在库内过滤的敏感数据（如只取正常结束且同意的离职申请，`rules/WORKFORCE_HISTORY_RULES.md`:59），过滤条件写在读取语句的 `WHERE` 中，行不离开来源库。

### 3. 凭据类数据

1. 凭据类数据（老系统令牌表 `system_oauth2_*`、口令哈希、密钥等）可以读，不排除。账号凭据泄露时，持有人能读到老系统的有效令牌并冒充老系统用户（ADR-0009 第 6 条的原理由）；**这一风险由用户接受**（「全部可读，不排除」）。
2. 使用约束：凭据值不得进入新系统的任何表、日志、事件与会话记录，也不进入仓库与取证输出（取证只出计数）。
3. 新系统仍不写老系统令牌、不校验老系统令牌、不以任何方式信任老系统签发的身份（ADR-0009 第 6 条、ADR-0027 第 4 项第 3 条的其余部分）。
4. 应用代码（`src/main`）不引用令牌表，`SecurityInvariantsTest.legacyTokenTablesAreNeverTouched` 保留：运行时没有任何用途需要令牌，不引用是「凭据值不进新系统」最便宜的机器守护；以后若有用途须另立 ADR。读取列登记中不得登记凭据列（第 6 项）。

### 4. 启动校验改口径

1. 三个只读连接（A8、老系统待办、老系统部门简称；合并后两个）启动时做同一项检查，不再检查「恰好只能读这几个视图」，只断言：
   - 库级有效权限中**没有写**（INSERT、UPDATE、DELETE）、**没有 DDL**（ALTER、CREATE 各类、ALTER ANY 各类、CONTROL、TAKE OWNERSHIP）、**没有 EXECUTE**、**没有 REFERENCES**；
   - 账号**不在任何可写角色中**：`db_owner`、`db_datawriter`、`db_ddladmin`、`db_securityadmin`、`db_accessadmin`，以及服务器角色 `sysadmin`。
2. 判断依据是 `fn_my_permissions(NULL, 'DATABASE')` 的有效权限（计入经角色得到的权限）与角色成员查询；不满足即拒绝启动，报出违规项。SELECT、VIEW DEFINITION、CONNECT 及 RDS 实例级默认授予的只读类权限放行。
3. A8 的列相等校验与配置 ID 存在性校验（RULE-356、根路径 M7）照旧，去留随第 6 项。
4. 校验实现放在 `platform.integration` 内、三个连接共用一份；`SingleObjectGuard`、`LegacyAccessGuard` 删除。类名在实现 PR 中按 NAMING_STANDARD 与 `terms.yaml` 定。
5. 实现 PR 用真实登录核实：PR #135 形状的账号通过；单独授予任一写类权限、加入任一可写角色都被拒。**首次部署前必须项。**

### 5. 账号

1. **老系统：合并为一个应用运行时账号**（推荐，作为决定提交用户批准）。理由：
   - **启动校验**：分两个账号的唯一原因是每个连接都校验「恰好一个对象」（B-5 README:37、`INFRA_RUNBOOK.md`:104、`CROSSCHECK.md`:10）；第 4 项之后共用账号两边都通过。
   - **授权范围**：两个账号现在权限完全相同（PR #135），分开已不构成安全边界，任一个泄露的后果一样。
   - **轮换**：90 天轮换从两份口令减为一份（`runbooks/C-8-kms.md`:15-16），避免只轮换了一份、另一份过期使某个模块中断。
   - **审计归属**：ADR-0033 第 2 项第 9 条之后两类读取都在 `platform.integration` 内，库侧归属到同一应用即可；应用内按用途区分——每个连接池设不同的 JDBC `applicationName`（SQL Server 记为 `program_name`），适配器按用途写读取计数日志（带 `correlationId`）。库侧要按人区分时用 RDS SQL 审计（子问题 Q5），不靠多开账号。
2. **做法**：把 `one_legacy_names_ro` 改名为 `one_legacy_ro`（`ALTER LOGIN … WITH NAME`、`ALTER USER … WITH NAME`，不换口令、不新建账号）；应用改用一组连接变量 `LEGACY_DB_RO_URL` / `_USERNAME` / `_PASSWORD`；应用切换并在 dev 验证后删除 `psa_one_legacy_ro`，从 `one.env` 移除 `FORCITIS_PLATFORM_APPROVAL_LEGACY_URL` / `_USERNAME` / `_PASSWORD`（老待办详情地址模板变量保留，名称随 ADR-0033 第 2 项第 9 条调整）。改名与删除是账号变更，执行前请用户确认（子问题 Q2）。
3. **A8：仍是一个应用运行时账号** `one_a8_views_ro`，不拆不合。若第 6 项选直接读基表，「views」名不副实，同时改名为 `one_a8_ro`（同样只改名、不换口令）；保留视图则不改名。
4. **取证与迁入不另开账号**：迁移取证、迁入抽取与运行时使用同一只读账号，只在 ECS 上使用，以不同的 `applicationName` 区分；不再用 RDS 高权限账号或老系统应用自己的可写账号做读取（现状：B-5 执行用了 RDS 高权限账号，README:5；`runtime/README.md`:6 的早期取证用了老系统应用的数据源）。高权限账号只用于授权变更本身。

### 6. 现有视图的去留（待定，附推荐）

授权放开后，视图已不是权限边界（账号直接读基表也能读到同样的数据），剩下的价值只是「契约与过滤条件放在库内」。

| | (a) 继续经视图读取 | (b) 直接读基表 |
|---|---|---|
| A8 升级隔离 | 视图是稳定契约：A8 改表后由 DBA 改视图，应用不动；但前提是有人在 A8 升级时同步改视图，否则视图同样失效 | 改表直接影响适配器语句；启动时按读取列登记校验「所需列都存在、类型相符」（子集，不是相等），A8 升级后第一次启动即报出缺列 |
| 维护 | 每次改动经 DBA 在外部库执行（老系统变更登记），正本与交接脚本两份、需 `check_view_sync.py` 对齐；排序规则修正（B-5 README:9）、R-1b-0 加标志列都要走这条路 | 只改仓库里的适配器语句，经 MSSQL 集成测试（`-Plegacy-it`）验证；少一层外部对象 |
| 过滤与敏感行 | 过滤在视图中 | 过滤在语句 `WHERE` 中，同样在库内执行，行不离开来源库 |
| 生命周期 | A8 在 6a–6e 逐步退出，视图要维护到 6e | 退出时删适配器即可 |
| 现有资产 | 4 个 A8 视图、2 个老系统视图已在生产，测试齐全 | 适配器语句要按视图正文改写（视图 SQL 可直接作为起点） |

**推荐 (b)**：视图的隔离作用依赖外部人工同步，并不比启动时的缺列检查更可靠；每次变更多一次外部库变更与两份正本对齐；A8 是退出中的系统。做法：

1. `seeyon-view-columns.yaml` 改为覆盖 A8 与老系统的读取列登记（逐列写来源表.列、分类、敏感级别；文件名在实现 PR 按 NAMING_STANDARD 定）；代码常量与登记一致（原 `SeeyonViewColumnWhitelistTest` 改写）；登记中不得出现凭据列；启动时校验所需列存在。
2. 适配器切到基表、dev 连续运行 7 天无差异后，由 one-ops 删除视图（老系统与 A8 变更登记）；删除前视图保留作回滚路径。
3. R-1b-0 改为适配器语句的改动。

选 (a) 时：列白名单相等校验与 `check_view_sync.py` 保留，R-1b-0 照原计划经 DBA 改视图；视图之外的读取（取证、迁入、新同步）仍可直接读基表，不必新增视图。

### 7. 生产取证不再逐次按对象请示

1. 取消 SESSION_PLAYBOOK §5「生产访问按对象授权」中「写明要访问的视图 / 表……执行中发现需要超出已授权对象，先停下请示」的逐次请示。
2. 保留两条底线：
   - **明细与个人信息不进会话记录与仓库**：只出计数或聚合；需要明细时落 ECS 数据盘，不带回本机，临时目录用完即删（§13 的既有规则）；凭据值任何情况下不输出。
   - **每次取证登记一行**：在运维日志或调度台账写明读了哪些表、目的、输出去向，不需审批。
3. 查询约束照旧：走索引、设语句超时；大输出放进文件，会话里只留结论。
4. SESSION_PLAYBOOK §5 该条与 §13「证据与生产访问」一句在本提交中加注修订，标「随 ADR-0037 采纳生效」；采纳前仍按原文执行。

## 后果

- 取证、迁入对账与新旧等价核对不再因授权范围中断；视图与白名单的外部变更周期缩短或取消（随 Q1）。
- **代价**：
  - 列最小、敏感行过滤、凭据不入库这些保护从数据库授权层移到代码与复审层（读取列登记、扫描守护、复审）；数据库不再替应用兜底，写错的语句能读到任何数据。
  - 只读账号凭据泄露的影响从组织与身份 33 列扩大到 A8 与老系统全库（合同、薪酬、银行卡、生日、老系统有效令牌）。缓解：账号只放行 ECS 内网地址、口令只在 `one.env`（`0640`）与 KMS、90 天轮换、库级 DENY 写与启动校验；剩余风险由用户接受。
  - 取证不再逐次请示，事后靠登记行追溯，事前没有人工把关。
- 若 Q1 选 (b)，A8 升级后的缺列在应用启动时暴露，而不是由 DBA 在视图中吸收。

- **维持视图级最小授权，按需逐个加视图**：与用户决定相反；取证与迁入每次越界都要等外部 DBA 改视图，正是本 ADR 要消除的中断。
- **只放开取证、运行时仍只读视图**：用户澄清选「两者都是」；运行时的新旧等价核对也要读基表。
- **库级只读但对凭据表 DENY**：用户答「全部可读，不排除」；凭据保护改为第 3 项的使用约束与扫描守护。
- **用 `db_datareader` 角色授权**：效果相同，但使「不在任何角色中」这条简单不变量失效，回滚时也多一步；采用直接的库级 GRANT。
- **取证与迁入另开只读账号**：库侧归属更清楚，但多一份口令与轮换，且与运行时账号权限相同、不构成边界；归属改由 `applicationName`、登记行与可选的 RDS SQL 审计（Q5）承担。
- **老系统保留两个运行时账号**：分开的唯一理由（恰好一个对象的校验）已不存在，只剩双份轮换成本。
