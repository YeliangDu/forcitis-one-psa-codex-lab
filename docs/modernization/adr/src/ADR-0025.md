# ADR-0025：OLAP 物理架构与数据流：同库分 schema 起步、事件增量加 OLTP 对账、编译期授权加 RLS、自建镜像回填

- **状态**：提议（起因：用户问「OLTP、OLAP 现在架构清晰吗」，选「现在写，并先定事件必带字段 (Recommended)」，经 psa-coordinator 转达；本 ADR 的具体设计待用户审批）
- **日期**：2026-10-14
- **取代**：ADR-0011 第 4 条

## 背景

- ADR-0011 第 4 条（OLAP）只写了「`reporting` schema（或现有 BI-olap）采用星型模型，由事件或 CDC 构建；BI 只读 `reporting`；过渡期视图保持老表的形状」。之后的决定已使它不再准确：
  - ADR-0023（已采纳）定了 L0–L4 分层，指标定义在 `operations.policy`、执行在 `reporting`；
  - Q3：BI-olap 冻结、不上线；
  - Q7：过渡镜像回填 BI 库，老 BI 不改；
  - Q1：语义层与报表包并入 FORCITIS one（选项 C）；
  - Q10：维度按生效期保留历史。
- ADR-0023 与 BI_SCOPE §3 定了逻辑分层，但没有定物理位置、构建与重算机制、行级权限的实现、镜像回填的工具，也没有定历史数据进哪一层。
- 约束与证据：
  - ADR-0016：事实只追加、单一过账管道、期间闸门；
  - ADR-0022：总账与 `accounting.reporting` 不重述；ADR-0023 L2「重述新版本」只适用于经营语义层的口径变化；
  - D-1：dev 与生产同实例分库，生产 RDS 是否另开待生产前决定；
  - R0：BI 使用量 171 人、90 天 23 万次调用；`T_FST_*` 119 个对象 1,455 列；老 PSA 的权责路径上有 3 个 BI 视图（A8_ACCESS_REGISTER #28–#31）；
  - 规模参照：BI-olap 在 PG 上的规模测试为 65 万行工时、130 万行权限，P95 约 174 毫秒。
- 第一步已定（交 1a）：领域事件的分析必带字段，见 `proposals/EVENT_ANALYTICS_FIELDS.md`，包括 `eventId`、`businessDate`、`source`、`aggregateVersion`，以及过账事件的 `postSeq`、`reversalOfPostSeq`、`originalPeriod`、`ruleVersion`。

## 决定

1. **取代关系**：部分取代 ADR-0011 第 4 条；ADR-0011 其余条款不变。细化 ADR-0023 第 2 条（分层）与第 5 条（过渡）的物理实现，不改其决定。本 ADR 采纳时，在同一提交中把 ADR-0011 状态改为「已采纳（第 4 条已被 ADR-0025 取代）」。

2. **L1 / L2 的物理位置：同一数据库、独立 schema 起步，按触发条件升级**。
   - 起步：L1、L2 放在 FORCITIS one 生产库中独立的 schema——`reporting`（L1 事实与维度、L2 期间快照），以及 `reporting_compat`（与老 `T_FST_*` 同形状的过渡视图）。
   - 两个数据库角色：
     - 构建角色：只有 `reporting` 模块的构建作业使用，可写 `reporting*`，只读 OLTP 各 schema；
     - 查询角色：语义层与过渡镜像使用，只读 `reporting*`，不能读 OLTP schema。
   - 工作负载隔离：
     - `reporting` 模块使用独立连接池，并设查询角色的 `statement_timeout` 与 `work_mem` 上限；
     - 导出走游标流式读取；
     - 构建作业用 ShedLock 单实例运行，并避开月结批处理窗口。
   - 升级触发条件（任一满足即升级；指标由 ARMS / RDS 监控）：
     - (a) OLTP 接口 p95 超出 SLO，且与 `reporting` 查询时段相关；
     - (b) 语义层查询 p95 > 2 秒持续一周；
     - (c) `reporting*` 存储超过库总量 40%，或构建作业超过 30 分钟。
   - 升级路径：
     - 第一级：加 RDS 只读实例，语义层查询路由到只读实例，L1 / L2 仍在主库构建；
     - 第二级：独立分析实例（逻辑复制 `reporting*`，或迁到列式库，GUIDING_PRINCIPLES §8）。
   - 与 D-1 的关系：两者独立。`reporting*` 跟随生产库走：生产用同实例新库，就在那个库里；另开生产 RDS，就随之迁去。dev 库 `forcitis_one_dev` 同样建这两个 schema。

3. **L1 构建：领域事件增量为主，OLTP 全量对账兜底，L2 随关账冻结**。
   - **增量**：
     - `reporting` 模块以 Modulith 异步监听器（提交后）消费事件，按 `eventId` 幂等写入；
     - 财务类事实表只来自过账事件，按 `postSeq` 追加，冲销行与原行并存；
     - 过程类事实来自对应的领域事件，不经过账管道。首个是**审批时效**：每个审批任务一行累积快照，里程碑为指派、超时（`ApprovalTaskOverdue`）、升级（`ApprovalTaskEscalated`）、办理。时限按工作日历计算（工时审批为提交日后第 1 个工作日，T+1），因此 L1 增加工作日历维度；
     - 累积快照（合同、条款、商机）按 `aggregateId` 更新，只接受 `aggregateVersion` 连续的事件；出现空洞时挂起该聚合，交给对账处理；
     - 维度事件生成按生效期的新版本（SCD2）。
   - **真相在 OLTP，不在事件**：事件发布登记表完成后会清理，不作为重放源。重建与回填一律从 OLTP 读取。`operations.facts` 本身就是只追加的明细账，按 `postSeq` 重读即可确定性重建。
   - **对账**：
     - 每日一次，按 (期间, 法人, 事实类型) 比对 L1 与 OLTP 的行数、金额与最大 `postSeq`；
     - 有差异时，自动从 OLTP 重建该分区，并记录对账结果；
     - 连续两天不一致则告警（`operations.policy` 的勾稽差异案）。
   - **迟到事件**：
     - L1 照常追加；
     - 已冻结的 L2 不改；
     - 关账后的更正以 `originalPeriod` 标注，在开放期间的 L2 中作为「对以前期间的更正」单列（与 ADR-0022 第 10 条一致）。
   - **回填**：历史迁入（§6）直接写入 OLTP（`source = MIGRATION`），完成后从 OLTP 重建相关分区；**不为批量迁入逐行发事件**。
   - **口径版本变更**：
     - L1 存事实、不存指标，口径变更不重算 L1；
     - 指标在语义层按口径版本即时计算；
     - 已发布的期间结果以「指标观测值」（OAT 的 `MetricObservation`）保存，带口径版本；口径变更时生成新版本观测值，旧版本保留。这就是 ADR-0023 L2「重述新版本」在经营语义层的含义；总账与财务报表不重述（ADR-0022）。
   - **L2 冻结**：
     - `accounting.period` 按 (期间, 法人) 发布关账事件后，生成该期间的快照：应收账龄、合同资产、剩余履约义务、预算执行、在册人数等，标为冻结；
     - 不反结账（GL-123）；冻结快照只能由新的口径版本观测值解释，不能被改写。

4. **行级权限：语义层编译时注入为主，PG 行级安全（RLS）兜底**。
   - 主：语义层编译器把调用者的授权范围（ADR-0009 的 AccessScope：法人、组织单元、项目、本人）作为条件，注入到每个事实子查询的最内层，在任何 `GROUP BY` 之前过滤，即「先授权、后聚合」；
   - 兜底：`reporting*` 的事实与快照表对查询角色启用 RLS。每个事务开始时用 `SET LOCAL` 写入授权范围，策略按 `legal_entity_id`、`org_unit_id` 过滤；过渡镜像与构建作业使用另外的角色，不受 RLS 约束但不对外提供查询；
   - 两层不一致时以更严者为准；RLS 拦下而编译器未拦的情况记安全告警。
   - **验证方法**：
     - (a) 性质测试：对随机生成的授权范围 S，语义层结果须等于「先按 S 过滤明细、再独立聚合」的结果，并且等于 S 的各子范围结果之和；
     - (b) 负向测试：不设授权范围直接查询事实表，RLS 返回 0 行；
     - (c) 编译期守护：生成的 SQL 中，授权条件必须出现在聚合之前，否则构建失败；
     - (d) 按 SECURITY_INVARIANTS 补一条不变量。

5. **过渡镜像回填老 BI：自建作业，归 `platform.integration`**。
   - 数据源：`reporting_compat` 中与老 `T_FST_*` 同形状的视图（形状来源：`r0/structure/tfst_objects.md` 与仓库外的列级元数据）。
   - 作业：`platform.integration` 中的出站适配器（老系统一侧），按小时运行，ShedLock 单实例。
   - 写入方式：
     - 小对象：在事务内整表替换（写临时表后切换）；
     - 大对象：按 `businessDate` 窗口增量替换。
   - 目标：只写 BI 库中的 `mirror_*` 表；BI 库的 `T_FST_*` 视图在对应阶段切换日改为读「A8 历史 ∪ 镜像」，或整张改读镜像（BI_SCOPE §4.2）。
   - 权限：使用只对 `mirror_*` 有写权限的独立账号；**不写 A8、不写老 PSA 表**；凭据走 KMS / 环境变量。
   - 监控：每次运行按对象记录源行数、目标行数和金额校验和，二者必须相等；延迟超过 2 小时告警；指标进 ARMS。
   - **R0 发现的 3 个视图**（`T_FST_PAY`、`T_FST_PROJECT`、`T_FST_INVALID_DELIVERY`）处在老 PSA 的权责数据路径上（A8_ACCESS_REGISTER #28–#31）。在其对应阶段（Phase 2、6a、6c / Phase 4）切换、且读取它们的 SQL Agent 作业停用之前，**不得改为读镜像，也不得改动视图定义**。
   - 镜像随 R6 老 BI 下线一并删除。

6. **历史数据：分三类，不按「一律迁入」或「一律不迁」处理**。
   - **作为事实迁入 OLTP**：带 `source = MIGRATION`、原单号与冲销关系，经 `operations.facts` 写入，进入 L1 的方式与原生事实相同。范围是：
     - (a) 继续经营需要的：未关闭合同与项目的条款、收入确认、开票、回款、预算的全部历史，用于重建累计金额，例如条款已确认、已开票累计；
     - (b) 已采纳 ADR 明确要求全量迁入的：ADR-0024 的收入确认 19,869 行与退回 434 行；
     - (c) 总账期初余额：按 GL-083 以期初余额迁入，不迁历史凭证。
   - **只进 OLAP 作历史**：写入 `reporting` 中的历史分区（`source = MIGRATION`，只读，不参与 L2 冻结快照），用于同比与趋势。范围是：
     - 已关闭项目与合同的事实（工时约 62 万行、费用、开票、回款）；
     - A8 档案的历史；
     - 老 BI 的月度快照（应收历月、风险客户、商机快照）。
     每个期间与老系统合计对账，差异须为 0 或经签字。
   - **只归档、不进任何层**：Flowable 历史与 API 日志（ADR-0011 第 2 条）、A8 流程过程数据。

## 影响面

- 模块：
  - `reporting`：构建、对账、L2 快照、语义层编译与授权注入；
  - `operations.policy`：指标观测值与口径版本；
  - `platform.integration`：镜像出站适配器；
  - `operations.facts` / `accounting.period`：过账与关账事件契约；
  - 各业务 BC 的领域事件：信封字段。
- 数据库：
  - 新 schema `reporting`、`reporting_compat`；
  - 两个数据库角色、RLS 策略；
  - BI 库新增 `mirror_*` 表，以及一个只写镜像表的账号。
- 接口与事件：AsyncAPI 事件目录采用 `EVENT_ANALYTICS_FIELDS.md` 的信封与过账负载契约（1a 定稿）。
- 阶段：
  - R1：骨架、构建与授权；
  - R2–R4：各事实入模；
  - 6a–6c：镜像就绪是入口条件；
  - Phase 2 / 6a / 6c：3 个权责路径视图的切换顺序；
  - R6：镜像删除。
- 文档：ADR-0011（采纳时标注）、BI_SCOPE §3–§4、GUIDING_PRINCIPLES §8（物理位置以本 ADR 为准）、SECURITY_INVARIANTS（新增一条）、`phase1a/infra`（schema 与角色 DDL 草稿）。

## 迁移方案

1. R1：建 `reporting`、`reporting_compat` 两个 schema 与两个数据库角色；接入事件消费、对账作业与 RLS；dev 库先行。
2. R2 起，每个事实类型入模时：先从 OLTP 全量构建，再切换到事件增量；对账连续 7 天一致后才对外提供查询。
3. 历史迁入：按 §6 分类执行；OLTP 迁入完成后从 OLTP 重建分区；只进 OLAP 的历史用一次性装载，按期间对账。
4. 过渡镜像：每个 6a–6c 阶段切换日前，受影响对象的镜像连续运行 7 天、对账一致；切换日改 `T_FST_*` 视图定义（BI 库的运维动作，经用户批准）。

## 回滚方案

- L1 / L2 出错：L1 可随时从 OLTP 重建；L2 冻结快照有误时，不改原快照，生成更正版本并标注（经营语义层的重述），并在对账记录中留痕。
- 物理位置升级失败（只读实例或独立实例）：语义层路由退回主库；`reporting*` 仍在主库，不丢数据。
- 过渡镜像出错：BI 库的 `T_FST_*` 视图定义退回切换前版本（读 A8 历史部分照常，镜像部分暂停）；镜像表保留，便于对比。切换日起 A8 不再产生新数据（不设双源期），所以回滚期间切换日后的数在老 BI 中暂缺，须向用户说明。
- 授权缺陷：一旦发现越权，立即下线受影响的语义层接口（RLS 兜底仍在），修复并补测试后恢复。

## 需同步修改的守护规则

- ArchUnit：
  - 只有 `reporting` 模块能引用 `reporting*` schema；`reporting` 不能写 OLTP schema；
  - 只有 `platform.integration` 能持有 BI 库连接；
  - 领域事件类型必须实现信封接口，且必带字段齐全。
- DDL 测试：两个数据库角色的授权与 RLS 策略存在且生效；`reporting` 事实表无 UPDATE / DELETE 授权（冲销只追加）。
- 语义层守护：编译出的 SQL 中授权条件在聚合之前；扩展 ADR-0023 的指标目录守护（OAT 声明、正式用语、禁用方言、不写死口径参数）。
- 镜像守护：镜像账号只能写 `mirror_*`；3 个权责路径视图在对应阶段出口前不在改动范围内（写入 6a / 6c / Phase 2 的出口检查）。
- 以上在 R1 骨架 PR 中提交；事件信封守护随 1a 事件目录定稿的 PR 提交。

## 后果

- OLTP 与 OLAP 同库起步：运维简单，对账可在同一事务快照内完成；代价是负载要靠角色、连接池和超时隔离，并依赖升级触发条件的监控。
- 事件只负责时效，OLTP 负责真相：L1 永远可重建；事件丢失只影响时效，不影响结果。
- 授权两层：编译期注入保证「先授权后聚合」的语义，RLS 防止绕过语义层的直接查询。
- 老 BI 在过渡期多了一个依赖：新系统按小时回填 BI 库镜像表。
- 历史分三类：OLTP 不被关闭项目的历史拖重；同比与趋势仍可在 OLAP 中看到。

## 备选方案（未采用）

- 一开始就上独立分析实例或列式库：现有规模（171 名用户、23 万次 / 90 天）用不上，多一套同步与运维。
- 以 CDC 从 OLTP 构建 L1：绕过领域语义（拿到的是行变化而不是业务事件），也不带 `businessDate`、`postSeq` 等分析必带字段。
- 只靠事件、不做 OLTP 对账：事件发布登记表会清理，丢失后无法重放。
- 只用 RLS 做授权：语义层的聚合在 RLS 之上才正确，但「先授权后聚合」无法在编译期验证；RLS 策略也难以表达项目、本人等细粒度范围。
- 只用编译期注入：任何绕过语义层的查询都没有保护。
- 用阿里云 DTS 或开源 ETL 回填 SQL Server：需额外产品与授权，且「只写镜像表、不碰老表」的约束在工具配置中难以守护；对象数量（约 119 个）和频率（每小时）自建足够。
- 用 SQL Server 链接服务器从 PG 拉数：要在老系统一侧新增配置与凭据，逆着「老系统不动」的方向。
- 历史一律迁入 OLTP：62 万行已关闭项目的工时等会拖重交易库，而它们只用于趋势分析。
