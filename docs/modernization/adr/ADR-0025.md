# ADR-0025：OLAP 物理架构与数据流：同库分 schema 起步、财务事实直读过账明细、过程事实走事件、编译期授权加 RLS 防缺陷、自建镜像回填

- **状态**：已采纳（需同步修改的守护规则中信封 `source.*` 须落在业务表上的要求已被 ADR-0039 取代）（用户 2026-10-14：「批准」ADR-0025；起因：用户问「OLTP、OLAP 现在架构清晰吗」；8 项待决的用户决定见背景）（第 6 条中「ADR-0011 第 2 条原意保留」对主键的适用已被 ADR-0033 取代）（第 6 条中「原单号」要求、守护中 `source.*` 落在业务表上对迁入行的适用已被 ADR-0036 取代）（第 3 条「更正」中例外重开时 L2 作废重建一点及回滚方案中对应一句已被 ADR-0045 取代）（决定 5、6、迁移方案（部分）已被 ADR-0054 取代）
- **日期**：2026-10-14
- **取代**：ADR-0011 第 4 条、ADR-0011 第 2 条、ADR-0023 第 2 条 L1 采集限制对一次性历史装载的适用

## 背景

- ADR-0011 第 4 条（OLAP，标为【提议】但随 ADR-0011 一并处于已采纳状态）只写了「`reporting` schema（或现有 BI-olap）星型，由事件或 CDC 构建；BI 只读 `reporting`；过渡期视图保持老表形状」。之后的决定已使它不再准确：
  - ADR-0023（已采纳）定了 L0–L4 分层；
  - Q3：BI-olap 冻结；
  - Q7：过渡镜像回填 BI 库；
  - Q1：语义层并入 FORCITIS one（选项 C）；
  - Q10：维度按生效期保留历史。
- ADR-0011 第 2 条（【提议】）写「只迁主数据和未关闭单据」。这与已采纳的 ADR-0024（收入确认 19,869 行全量迁入）以及 GUIDING_PRINCIPLES §9a「权责事实全部在新系统」都不一致。
- ADR-0023 与 BI_SCOPE §3 定了逻辑分层，但没有定物理位置、构建与对账、授权实现、镜像工具和历史数据去向。
- 约束：
  - ADR-0016：事实只追加、单一过账管道、`postSeq`；
  - ADR-0022：总账与 `accounting.reporting` 不重述；ADR-0023 L2「重述新版本」只适用于经营语义层的口径变化；关账后不反结账，例外须财务负责人审批（第 10、12 条）；
  - ADR-0009：授权范围为「法人 × 部门 × 项目角色」，不用隐式 SQL 改写拦截器；
  - D-1：dev 与生产同实例分库；生产是否另开 RDS 原待定，现由用户决定不另开、扩容现有实例共用（见下）；
  - INFRA_RUNBOOK：RDS 4 核 16G、ESSD 40G，与 it_portal 共用；运行角色只有 DML。
- R0 证据：
  - BI 近 90 天 171 名用户、23 万次调用；
  - `T_FST_*` 共 119 个对象；
  - 老系统的权责路径上有 3 个 BI 视图，并有仅存在于生产 SQL Agent 的同步作业（A8_ACCESS_REGISTER #28–#32）。
- **用户对 8 项待决的决定**（2026-10-14，经 psa-coordinator 转达，原话为所选项）：
  - 历史迁移「是，权责事实一律进交易库 (Recommended)」→ 第 6 条；
  - 分析权限部门范围「含下级，按事实发生时的组织 (Recommended)」，另给管理层「按现组织重归属」视角 → 第 4 条；
  - 快照与口径「作废重建并留版本；其余按建议 (Recommended)」→ 第 3 条；
  - 构建方式「同意 (Recommended)」→ 第 3 条；
  - 6e 敏感对象「不镜像 (Recommended)」→ 第 5 条；
  - 老库 mirror_* 只写账号「同意，6a 前执行 (Recommended)」→ 第 5 条；
  - 生产库 D-1「扩容现有实例共用」→ 第 2 条。
- 第一步已交 1a：`proposals/EVENT_ANALYTICS_FIELDS.md`（领域事件信封）。本 ADR 经评审后对它做了修订（见该文件 §6）。

## 决定

1. **取代关系**：
   - 部分取代 ADR-0011 第 4 条（OLAP）与第 2 条（迁移范围，改为第 6 条的分类）。
   - 部分取代 ADR-0023 第 2 条 L1「不再从 A8 与老系统库采集」：只放开一次性历史装载（第 6 条），持续采集的限制不变。
   - ADR-0023 其余内容不变。
   - 采纳时在同一提交中**在各自现有状态括注后追加**：ADR-0011「……；第 2、4 条已被 ADR-0025 取代」；ADR-0023「……；L1 采集限制对一次性历史装载的适用已被 ADR-0025 取代」。

2. **物理位置：生产不另开 RDS，扩容现有实例共用；同库独立 schema、按库 / schema / 角色隔离**（用户：生产库 D-1「扩容现有实例共用」）。
   - 实例：生产沿用现有 RDS PG 18 高可用实例（pgm-bp13vak0sew3m003），与 IT 服务门户（`it_portal`）、dev 库（`forcitis_one_dev`）同实例。生产另建库与 `one_prod_*` 角色（库名由 1a 运维清单定）。
   - schema（均在生产库内）：
     - `reporting`：L1 维度、过程事实、累积快照、L2 快照、指标观测值；
     - `reporting_compat`：与老 `T_FST_*` 同形状的过渡视图；
     - `reporting_archive_src`：一次性历史装载的源数据，只追加。
   - 角色（表属主另设，均不是以下角色）：

     | 角色 | 能做什么 | 不能做什么 |
     |---|---|---|
     | 构建 | 读 OLTP 各 schema 与 `reporting_archive_src`；写 `reporting` | 不能 DDL |
     | 重建 | 只能对 `reporting` 的分区做 DETACH / ATTACH | 不能读写 OLTP |
     | 查询 | 只读 `reporting` 的表与 `security_invoker` 视图 | 没有物化视图授权；不能读 OLTP |
     | 镜像 | 只读 `reporting_compat` | 其他一律不能 |

   - **同实例共用下的工作负载隔离**：
     - 每个角色设连接上限（`ALTER ROLE … CONNECTION LIMIT`），各角色与 it_portal、dev 的上限之和不超过实例 `max_connections` 减去保留；连接数预算写入 INFRA_RUNBOOK；
     - 按角色设 `statement_timeout`、`idle_in_transaction_session_timeout`；查询角色另设较低的 `work_mem`；
     - 长导出写到对象存储后再下载，单个导出事务时长有上限，防止长事务占住 xmin、导致 OLTP 与 it_portal 的表膨胀；
     - 构建与物化作业用 ShedLock，避开可配置的月结窗口与 dev 批量测试时段；
     - 监控按库与角色拆分（`pg_stat_statements`、ARMS），判断负载来自生产交易、分析、it_portal 还是 dev。
   - **升级顺序与触发条件**（任一满足即进入下一级；由 ARMS 告警）：
     1. 调参与限额：查询角色或 dev 占用异常时，先收紧该角色的限额与超时；
     2. **纵向扩容**：实例 CPU p95 > 70% 持续一周，或缓冲命中率 < 99%，或磁盘使用 > 70%；
     3. **加只读实例**，只承载交互式分析查询（长导出仍走对象存储，避免热备冲突）。在已扩容的前提下，满足任一即加：查询角色占主库 CPU > 30% 且 OLTP 接口 p95 超出 SLO；语义层查询 p95 > 2 秒持续一周；最长事务或 xmin 年龄持续 > 10 分钟且来自查询角色；
     4. 独立分析实例或列式库（GUIDING_PRINCIPLES §8）：只读实例也不能满足，或 `reporting*` 超过 100 GB。
     - dev 库在上线前应迁出生产实例，或在生产负载上来时先停用，以免与生产争用；何时迁出由用户在部署前决定。
   - **扩容规格建议**（属购买操作，执行前请用户确认）：
     - 由 4 核 16 GB、ESSD 40 GB，扩到 **8 核 32 GB、ESSD 200 GB**，并开启存储自动扩容；
     - 依据：生产库要容纳 FORCITIS one 交易库、迁入的权责历史（含已关闭项目约 62 万行工时等，第 6 条）、Flowable 运行表、`reporting*` 与归档源，首年约 30–60 GB（含索引）；还要留 WAL 与膨胀余量，并与 it_portal、dev 共用；
     - 计算侧：交易约 335 名活跃用户、分析约 171 名用户，加上月结批处理；
     - 规格名与价格以控制台为准。

3. **构建：财务事实直读过账明细；过程事实与累积快照走事件；L2 在关账水位门控下从 OLTP 生成**。
   - **财务事实**（工时成本、费用、收入确认、开票、回款、付款……）**不走事件**：
     - 起步时 L1 的财务事实就是 `operations.facts` 上的视图（`security_invoker`），零复制、天然一致；
     - 触发升级条件后，改为 ShedLock 作业按 `postSeq` 拉取、物化。幂等键为 `postSeq`；水位只推进到当前快照中已提交的部分（不越过 `pg_snapshot_xmin` 对应的未提交事务），避免并发提交造成的跳号。
   - **过程事实与累积快照**（审批时效、商机、合同、条款）**走领域事件**：
     - 监听器收到任何事件，都按 `aggregateId` 从 OLTP 读取当前状态，再覆盖累积快照行。不做版本连续性检查，乱序和重复投递都不影响结果。
     - 过程事实的首个类型是**审批时效**：每个审批任务一行，里程碑为指派、超时、升级、办理；时限按工作日历计算（工时审批 T+1），L1 增加工作日历维度，来源为 `organization.attendance` 的工作日历（1a 建，一份默认日历、预留法人专属；老系统 2016–2026 年日历拟迁入）。
     - 维度事件生成按生效期的新版本（SCD2）。
   - **事件投递**：
     - 事件发布登记表采用 `completion-mode = ARCHIVE`，保留 30 天；清理作业归 `platform.integration`；
     - 另设 ShedLock 作业，定期重投递超过 5 分钟未完成的发布；
     - 未完成数与最长滞留时间作为 ARMS 指标并告警。
   - **对账**：每日一次。
     - 物化后的财务事实：按 (期间, 法人, 事实类型) 比对条数、金额与 `postSeq` 校验和（比集合，不比最大值）；
     - 累积快照：逐聚合比对版本号，不一致的直接从 OLTP 覆盖；
     - 对账结果与差异入 `operations.policy` 的勾稽差异案；
     - 来源为 MIGRATION 且只在 OLAP 的历史分区不参与此项对账，由第 6 条的期间对账负责。
   - **重建**：
     - 「建影子分区，再原子交换」，由重建角色执行；
     - 与增量作业按 (期间, 法人, 事实类型) 用 PG 咨询锁互斥；
     - 起步阶段财务事实是视图，不需要重建。
   - **L2 冻结**：
     - `accounting.period` 的关账事件负载带该 (期间, 法人) 的最大 `postSeq` 与事实条数；
     - L2 在一个可重复读事务中直接从 OLTP 生成，生成前校验水位与条数，不满足就挂起并告警。
     - L2 的内容是经营口径的存量快照：应收账龄、未开票在制（经营口径，与合同资产的差异登记在口径差异清单）、剩余履约义务、预算执行、在册人数。**合同资产等报表行项目引用 `accounting.reporting` 的结果，不自算**（ADR-0023 第 4 条）。
   - **更正**：
     - 已冻结的 L2 不改。数据错误与迟到更正一律在开放期间作为「对以前期间的更正」列示（`originalPeriod`），与 ADR-0022 第 10 条一致；
     - 「重述新版本」只用于口径版本变化：指标观测值（`MetricObservation`，存于 `reporting`，`operations.policy` 只读引用）生成新版本，旧版本保留；
     - 期间经财务负责人审批例外重开时：该期间的 L2 快照作废并重建，带版本与审批记录（用户决定「作废重建并留版本」）。

4. **授权：语义层编译时注入为主；PG 行级安全只防应用缺陷**。
   - **范围**：沿用 ADR-0009 的「法人 × 部门 × 项目角色」；本人数据另加「本人」范围。
     - 部门范围**含下级**，**按事实发生时的组织**判定（与 SCD2 维度一致）；
     - 另给管理层「按现组织重归属」视角：按当前组织树重新归属历史事实，只用于趋势查看，需专门权限，不改变事实发生时的归属（用户决定）。
   - **主**：语义层编译器把范围作为显式谓词，注入到每一个事实表引用的最内层，包括维度连接、基期子查询、总计行与下钻，在任何聚合之前。这是编译器显式生成的条件，不是 ADR-0009 所排除的「隐式 SQL 改写拦截器」。
   - **兜底**：
     - `reporting` 的事实与快照表 `FORCE ROW LEVEL SECURITY`；
     - 策略读 `current_setting('app.scope', true)`，取不到值即拒绝（失败即拒绝）；
     - 范围在每个事务开始时用 `SET LOCAL` 设置；
     - 查询角色不得读物化视图，视图一律 `security_invoker`。
     RLS 防的是应用缺陷，不防能执行任意 SQL 的人：查询角色只由应用使用，不发给任何人。
   - **已存储的聚合**（指标观测值、L2 汇总）：按存储粒度（法人 / 组织）标注可见范围，只对覆盖该粒度的范围可见。
   - **敏感事实**：语义层为事实类型标注敏感级别，薪酬、个人审批时效等须有专门权限。
   - **验证方法**：
     - (a) 对可加指标做性质测试：对随机范围 S，语义层结果 = 用独立实现的范围语义过滤明细后再聚合的结果；只对声明为「可加」、子范围不重叠的情况再检验「等于子范围之和」；
     - (b) 负向测试：不设范围直接查询，返回 0 行；查询角色对物化视图无授权；所有视图都是 `security_invoker`；
     - (c) 在编译器中间表示上检查：每一个事实表引用都带范围谓词，否则构建失败；
     - (d) SECURITY_INVARIANTS 新增一条，按以上可测形式写。

5. **过渡镜像回填老 BI：自建作业，归 `platform.integration`**。
   - 数据源：`reporting_compat` 的同形状视图。逐列映射规格作为 6a–6c 的入口物，内容包括：
     - `timestamptz` → `datetime`，按 Asia/Shanghai 转换；
     - 类型化 ID 与老雪花 ID 的对照；
     - 状态值 → 老编码；
     - 金额精度与舍入；
     - 排序规则。
   - 写入：
     - 写入 `mirror_<对象>_staging`，再在 BI 库的一个事务里 DELETE + INSERT 到 `mirror_<对象>`；
     - 大对象按主键 MERGE，另做每日全量校验；
     - 不用改名切换（需要 Sch-M 锁与 ALTER 权限）；
     - 先查 BI 库是否开启 RCSI，以及老 BI 是否用 `NOLOCK`，据此确认读者不会读到写了一半的数据。
   - 账号：BI 库中只对 `mirror_*` 有写权限的独立账号，由对方 DBA 在老 SQL Server 实例上创建（用户决定「同意，6a 前执行」；列为部署前 / 6a 前事项，执行前再请用户确认）。账号启动时用 `fn_my_permissions` 自检，超出范围即拒绝运行。不写 A8、不写老系统表；凭据走 KMS / 环境变量。
   - 监控：每次运行按对象比对源行数、目标行数与金额校验和（按映射规格的舍入）；延迟超过 2 小时告警；指标进 ARMS。
   - **敏感对象不镜像**（6e 的薪酬、人事类；用户决定「不镜像」）。
   - **3 个权责路径视图**（`T_FST_PAY`、`T_FST_PROJECT`、`T_FST_INVALID_DELIVERY`）：在对应阶段切换、且读取它们的 SQL Agent 作业停用之前，不改为读镜像，也不改视图定义。作业 #29（同步项目档案）须在 6a 切换日或之前停用，否则老系统会被灌入过期的项目数据。
   - 镜像随 R6 老 BI 下线删除。

6. **历史数据：按是否权责事实分类**。
   - **权责事实一律作为事实迁入 OLTP**，不论项目是否已关闭：
     - 带 `source = MIGRATION`、原单号与冲销关系，经 `operations.facts` 写入（GUIDING_PRINCIPLES §9a；与 ADR-0024 一致）；
     - 包括已关闭项目的工时（约 62 万行）、费用、收入确认、开票、回款、付款；
     - 总账按 GL-083 迁期初余额，不迁历史凭证。
     这样同一项目的数据不会拆在两处，L1 也始终可以从 OLTP 重建。
   - **主数据与未关闭单据**：随各阶段迁入（ADR-0011 第 2 条原意保留）。
   - **只进 OLAP 的历史**：不是权责事实的分析历史，例如老 BI 的月度快照（应收历月、风险客户、商机快照）、A8 中只用于统计的档案字段。
     - 源数据落 `reporting_archive_src`（只追加），由它装载到 `reporting` 的历史分区；
     - 两者都可重放，不参与 OLTP 对账；
     - 按期间与老系统合计对账。
   - **只归档**：Flowable 历史、API 日志、A8 流程过程数据。

## 影响面

- 模块：
  - `reporting`：视图与物化、事件监听、对账、L2、指标观测值、编译期授权；
  - `operations.facts`：过账明细即 L1 财务事实的来源；关账水位；
  - `accounting.period`：关账事件负载；
  - `operations.policy`：只读引用观测值；
  - `platform.integration`：镜像适配器、发布登记表清理与重投递作业；
  - `platform.approval`：`ApprovalTaskOverdue`、`ApprovalTaskEscalated` 事件，尚未实现；
  - 工作日历：引用 `organization.attendance`（1a 建，一份默认日历、预留法人专属），不依赖 6e。
- 数据库：
  - 3 个 schema 与 5 个角色（含属主）、RLS 策略；
  - BI 库的 `mirror_*` 与一个写镜像的账号；
  - 事件发布登记表的 ARCHIVE 表。
- 事件：信封按 `EVENT_ANALYTICS_FIELDS.md` §6 修订；过账事件仍发布，但 L1 不依赖它。
- 阶段：
  - R1：骨架、视图、授权、对账；
  - R2–R4：各事实入模；
  - 6a–6c：镜像就绪与逐列映射规格是入口物；作业 #29 在 6a 切换日或之前停用；
  - G1：期初余额；
  - R6：镜像删除。
- 文档：
  - ADR-0011、ADR-0023（采纳时追加状态）；
  - BI_SCOPE §3–§4；GUIDING_PRINCIPLES §8（物理位置以本 ADR 为准）；
  - SECURITY_INVARIANTS（新增一条）；
  - INFRA_RUNBOOK（角色、连接数预算、导出配额、月结窗口）；
  - A8_ACCESS_REGISTER #29（停用时点）。

## 迁移方案

1. R1：
   - 建 3 个 schema 与 5 个角色；
   - 财务事实以视图接入；接入事件监听、重投递作业、对账、RLS 与编译期授权；
   - dev 库先行；实例扩容（第 2 条规格建议，属购买操作）在生产部署前执行，执行前请用户确认；连接数预算与各角色限额写入 INFRA_RUNBOOK。
2. R2–R4：每个事实类型入模时，先在 dev 用历史迁入数据验证视图与对账；累积快照的监听器上线后，对账连续 7 天一致才对外提供查询。
3. 历史迁入：
   - 权责事实经 `operations.facts` 写入 OLTP（`source = MIGRATION`），按 (期间, 法人, 来源单号) 与老系统对账；
   - 非权责分析历史落 `reporting_archive_src` 后装载，按期间对账。
4. 过渡镜像：每个 6a–6c 切换日前，受影响对象的镜像连续运行 7 天、校验一致；切换日改 BI 库 `T_FST_*` 视图定义（BI 库的运维动作，经用户批准）。

## 回滚方案

- 财务事实视图出错：修视图，无数据要恢复。物化阶段出错：退回视图读取，或从 OLTP 重建影子分区后交换。
- 事件监听出错：累积快照可随时从 OLTP 全量覆盖；关掉监听器不影响财务事实。
- 若放弃事件路径（例如事件目录推迟）：累积快照改为每日从 OLTP 全量构建，时效降到天级，结果不变。
- L2 有误：不改冻结快照，在开放期间列示更正；属例外重开期间的，按第 3 条作废重建。
- 物理位置升级失败：查询路由退回主库，数据都在主库。
- 镜像出错：BI 库视图定义退回切换前版本，镜像表保留便于对比。由于不设双源期，切换日后的数在回滚期间于老 BI 中暂缺，须向用户说明。
- 授权缺陷：立即下线受影响的语义层接口（RLS 仍在），修复并补测试后恢复。

## 需同步修改的守护规则

- DDL 授权测试：
  - 5 个角色的授权与上表一致；
  - 运行时角色无 DDL（重建角色只有分区 DETACH / ATTACH）；
  - `reporting` 事实表无 UPDATE / DELETE；
  - 事实与快照表 `FORCE ROW LEVEL SECURITY`；查询角色对物化视图无授权；所有视图 `security_invoker`。
- DataSource 限定：只有 `reporting` 模块注入查询或构建数据源；只有 `platform.integration` 注入 BI 库数据源（以 Bean 限定符加 ArchUnit 检查注入点）。
- 镜像账号：启动时用 `fn_my_permissions` 自检；6a / 6c / Phase 2 出口检查加入「3 个权责路径视图与作业 #28–#31 的状态」。
- 语义层：编译器中间表示检查范围谓词；扩展 ADR-0023 的指标目录守护（OAT 声明、正式用语、禁用方言、不写死口径参数）。
- 事件：信封必带字段测试（随 1a 事件目录 PR）；信封中的分析字段必须能从 OLTP 行推导（`businessDate`、`source.*`、`documentNumber` 落在业务表上）。
- 以上在 R1 骨架 PR 中提交；事件守护随 1a 事件目录 PR 提交。

## 后果

- 财务事实只有一套来源（`operations.facts`），没有事件丢失、乱序、水位跳号的问题；事件只负责过程事实与累积快照的时效。
- 同库起步运维简单；代价是要靠角色、连接池、导出配额和绝对阈值监控来隔离负载。
- 授权的正确性靠编译期显式谓词与可测的验证方法；RLS 只是缺陷防线。
- 已关闭项目的权责历史也进 OLTP（约 62 万行工时等），交易库会大一些，但事实只有一个来源，L1 永远可重建。
- 老 BI 在过渡期多一个依赖（按小时回填镜像），并需在老 SQL Server 实例上新建一个镜像账号。

## 备选方案（未采用）

- 一开始就上独立分析实例或列式库：现有规模用不上，多一套同步与运维。
- 财务事实走事件增量加对账（初稿）：要同时维护事件、水位、对账与重建三套机制，有竞态与跳号问题（C-1、C-2、C-7）；同库只追加的过账明细本来就是最好的来源。
- 以 CDC 构建：同库场景下没有必要；视图和按 `postSeq` 拉取更简单。
- 只用 RLS 或只用编译期注入：前者无法在编译期验证「先授权后聚合」，后者对应用缺陷没有防线。
- 用 DTS / 开源 ETL 回填 SQL Server：需额外产品，「只写镜像表」的约束难以守护。
- SQL Server 链接服务器从 PG 拉数：要在老系统一侧新增配置。
- 已关闭项目的权责历史只进 OLAP（初稿）：同一项目的数据被拆在两处，与 §9a、ADR-0024 冲突，且 L1 无法从 OLTP 重建。
