# ADR-0039：防腐层边界：外部系统概念只在 platform.integration

- **状态**：已采纳（用户 2026-10-15 在防腐层边界决策页上选 U-ACL-0「认可」、U-ACL-A「同步搬进集成层，离职暂停留组织模块」、U-ACL-C「联合身份」、U-ACL-落点「两张都放集成层」，均为推荐；第 3 项登录只定方向，见决定第 3 条；intent `2026-10-15-164527-one-architecture-防腐层边界决策页-U-ACL-0.md`）（决定 2、3、5、6（部分）；影响面、迁移方案、回滚方案、后果（部分）已被 ADR-0055 取代）
- **日期**：2026-10-15
- **取代**：ADR-0033 第 4 项第 1 条中 `external_identities` 建在 `platform_identity` 的位置、ADR-0033 迁移方案第 4 条中 `legacy_numbers` 的表路径、ADR-0036 中 `platform_numbering.legacy_numbers` 的表路径、ADR-0027 第 1 项第 7 条中「该运行保持待放行」的对象、ADR-0027 第 2 项第 1 条中同步记录查看与放行的权限码 `organization.workforce:sync-run:read` / `:execute`、ADR-0027 第 3 项中同步记录所在的模块与 schema、ADR-0028 第 1 条中两类暂停原因集中在同一次同步运行、ADR-0028 第 2 条中放行接口 `/organization/sync-runs/{id}:release` 与 `sync-run:execute` 权限、ADR-0028 第 4 条中放行时按最新源数据重跑并可重新进入待放行以及审计事件名 `organization.workforce.sync-run.released`、ADR-0025 需同步修改的守护规则中信封 `source.*` 须落在业务表上的要求

## 背景

- 用户 2026-10-15：「先等等，我没有同意所有用语」「所有用语检查下，acl用语单列，不能进入新系统模块」（经 one-coordinator 转达）。one-glossary 全量归类（`glossary/acl/acl-classification.json`，670 条：ACL 长期 18、ACL 过渡期 60、领域定义需去外部名 24、待定 6）发现外部系统概念进入了业务与平台模块。
- 代码足迹（origin/main，2026-10-15 清点）：
  - `organization.workforce` 的组织同步约 72 个 main 文件（SyncRun、ShrinkGuard、SnapshotReconciler 等），表 `sync_runs`、`sync_diffs`、`sync_run_held_separations`，5 个 `SyncRun*` 事件，3 个权限码；
  - kernel 的 `WecomUserId`（main 33 个文件引用，集成层以外 16 个）、`ExternalSystemUnavailableException`、事件信封 `source`（`SourceSystem` 取值 ONE / MIGRATION，`documentRef` 为原单号；`asyncapi.yaml:1283-1292`）；
  - `platform.identity` 的企业微信、致远单点、签名票据登录用例与表 `login_states`、`sso_ticket_uses`、`ticket_issuers`；
  - `platform.approval` 的老待办；
  - `platform.numbering` 的原编号（无调用方）。
- 方案草稿：`architecture/proposals/ACL_BOUNDARY.md`（第 2 版，one-coordinator opus 复审通过）。

## 决定

1. **判定口径**（U-ACL-0）：
   1. 只因某个外部系统（A8 / 致远、企业微信、U8C、老系统）存在才有的概念、标识、协议与取值，只在 `platform.integration` 内出现（与 ADR-0033 第 2 项第 4、9 条，ADR-0036 第 2 条一致）。
   2. 新系统自己的概念（员工、组织单元、待办、单据编号、迁入、迁入占用、历史期间等）留在业务模块，但不带外部系统名或外部取值；用语问题交 one-glossary。外部身份（某个外部提供方的账号对应本系统哪个用户）的取值是外部系统名，按第 1 款属集成层，见第 4 条。
   3. 业务模块从集成层拿到的只能是已翻译成新系统用语的结果（CS-2.29）；翻译在集成层完成，业务模块不设翻译包（回答 CODING_STANDARD §10 Q-4）。
2. **组织同步**（U-ACL-A，A1）：
   1. 同步机制搬进集成层「组织来源同步」（`org_source_sync`，提议术语）：运行记录、缩水保护（`SHRINK_GUARD`）、差异、调度、运维页面；集成层把来源数据翻译成新系统用语的「组织变更集」（`org_change_set`），调用 workforce 唯一的 api 方法「应用组织变更」（`apply_org_change_set`）。5 个 `SyncRun*` 事件改到 `platform.integration.*`，3 个权限码改为集成层前缀，仍授组织数据管理员。
   2. 管理员离职暂停（`ADMINISTRATOR_SEPARATION`，ADR-0027 第 1 项第 7 条、ADR-0028，经 `kernel.SeparationReview`）是安全业务规则，留在 workforce：应用变更集时其余变更照常应用，只把该条离职挂为 workforce 的「待放行离职」（`separation_hold`）记录（`sync_run_held_separations` 改为此表）；放行只放这一条离职，不重跑整次同步、不重新进入待放行、不绕过缩水保护；放行接口与审计事件改为针对待放行离职（名称随实施卡在事件目录与权限清单中登记，取代 ADR-0028 第 2、4 条的对应部分）；缩水暂停的放行在集成层，权限改为集成层前缀，仍授组织数据管理员（取代 ADR-0027 第 2 项第 1 条的对应部分）。锁死判定（可用 `super_admin` 少于 2 名）不变。
   3. 一致性：集成层先把运行记为「应用中」并提交，再以运行 ID 作幂等键调用 workforce；workforce 在一个事务内应用整个变更集并记下已应用的变更集 ID，重复调用返回上次结果；集成层收到结果后记「已应用」。对账作业扫描超时仍为「应用中」的运行，向 workforce 查询后补记或按失败重试；超时、补记、重试耗尽都发运维告警（指标与告警名按 G46 登记）。`multi-aggregate-exceptions.txt` 中 `ApplySourceSnapshot` 一条与 SESSION_PLAYBOOK §14 对应的已登记例外随之删除。
3. **登录**（U-ACL-C）：只定方向，细节待研究。
   - 方向：联合身份（`federated_identity`，提议术语）——外部凭据（企业微信 OAuth 态、致远票据防重放、签名票据的 HMAC 与密钥）由集成层校验，返回已验证的外部主体并按外部身份对照（第 4 条）找到 `UserId`；identity 只决定能否登录与发会话。
   - **细节暂缓**：用户备注「登陆和身份认证需要更细致的研究，我们的人员从入职到有企业微信是有时间差的，招聘入职是hr的业务过程，企业微信是it的业务过程，有前后顺序，我不是否定，而是还没想清楚」。实施前先做「人员入职到账号开通」身份生命周期研究（HR 入职、IT 开通企业微信、外部身份绑定的先后与时间差，以及时间差内能否登录、怎样登录），结论交用户确认后再定细节与实施卡。
   - 待研究后确定的初步划分（**随 C1，待研究，本 ADR 不定**）：`ticket_issuers` 中 `allowed_role_codes` 与「不得含 `super_admin`」的约束属 identity 的准入策略、留在 identity，只把签发方密钥引用与 `kid` 放到集成层；`login_states`、`sso_ticket_uses` 换到 `platform_integration`。
   - C1 的实现 PR 须另做安全复审（SECURITY_INVARIANTS、`SecurityInvariantsTest`、`ticket-issuers-allowlist.txt`）。
4. **两张对照表的落点**（U-ACL-落点）：
   1. `external_identities` 按 ADR-0033 第 4 项的结构（含按生效区间的排他约束）原样建在 `platform_integration`，不建在 identity；登录时由集成层按（提供方, 外部主体）找 `UserId`。ADR-0033 第 4 项其余内容不变：`employees` 删 `login_name`、`wecom_user_id`，`WecomUserId` 移出 kernel，收件人解析在集成层。
   2. `legacy_numbers` 原样整表搬到 `platform_integration`，表结构与 G-MG1 / G-MG6 不变，查询端点与权限码改为集成层前缀；`platform.numbering` 只管新编号。
   3. 两张表都不并入 `source_references`：`source_id` 为 `bigint`、一个自有对象在一个来源只对应一个来源对象（ADR-0033 第 2 项第 1 条），不适用于文本型外部主体和一单多号。
5. **其余各项**：
   1. 事件信封删除 `source`（含 `documentRef`）：ADR-0036 第 5 条规定迁入不发布领域事件，`MIGRATION` 与原单号在信封中没有使用场景；ADR-0025「需同步修改的守护规则」中「信封 `source.*` 落在业务表上」一项随之取消（`businessDate`、`documentNumber` 不变）；删除后不再与「来源系统」`ExternalSource`（NEXT_BATCH_PLAN C7）撞名。同步改 `asyncapi.yaml` 信封 schema 与 EVENT_ANALYTICS_FIELDS。
   2. `ExternalSystemUnavailableException` 改中性名、留在 kernel；老待办按 ADR-0033 第 2 项第 9 条移入集成层，对外契约（`InboxSource.NEW/LEGACY`、`legacyCount`、`legacyAvailable`）改中性用语。用语交 one-glossary。
6. **排期**（并入 P3b / P5 的顺序由 one-coordinator 定）：
   - 生产前完成：表的位置在 P3b 开工前定，P3b 直接写到新 schema；外部身份落点（DA-3）与 `employees` 删两列；组织同步按第 2 条拆分（含 5 个事件与 3 个权限码改名）；信封删除 `source`（P5，P5 独占 `EventEnvelope`）。
   - 可放生产后：异常改名；老待办契约中性化（首次外部对接前）；`legacy_numbers` 搬表（首个迁入阶段前，表现为空）。登录相关（`login_states`、`sso_ticket_uses`、`ticket_issuers` 的拆分）随 C1，待研究后另排。
7. **守护**：CS-2.29 的 G-C5 落地；由 one-glossary 的 ACL 归类生成禁用清单，集成层以外的模块出现即失败，现有足迹登记待清零、只拦新增（one-architecture 架构校验 PR-D 一并实现，opus 复审）。

## 影响面

- 模块：`organization.workforce`（同步机制移出，新增「应用组织变更」api 与「待放行离职」）、`platform.integration`（组织来源同步、外部身份对照、原编号对照、登录凭据校验）、`platform.identity`（登录用例改为联合身份，细节待研究）、`platform.approval`（老待办实现移出、契约中性化）、`platform.numbering`（原编号移出）、kernel（`WecomUserId` 移出、异常改名、信封删 `source`）、`platform.web`（异常映射改名）。
- 表：`sync_runs`、`sync_diffs` 换到 `platform_integration`；`sync_run_held_separations` 改为 workforce 的待放行离职表；`org_units` / `employees.last_sync_run_id` 改为引用变更集；`external_identities` 新建于 `platform_integration`；`legacy_numbers` 换 schema；登录相关的表（`login_states`、`sso_ticket_uses`、`ticket_issuers`）随 C1，待研究。
- 事件与接口：5 个 `SyncRun*` 事件改命名空间；`/api/v1/organization/sync-runs*`、`/api/v1/platform/legacy-numbers*` 改到集成层路径；同步与原编号的权限码改前缀；合并待办响应字段改名；信封 schema 删 `source`。
- 前端：同步记录页、待办页、登录页的接口调用与文字。

## 迁移方案

1. 迁移基线开放期间（ADR-0038）直接改基线：换 schema 的表在基线中改建到新 schema，不写追加迁移；本机与测试库重建。不含登录相关的表（随 C1，待研究）。
2. 基线关闭后才做的项（第 6 条「可放生产后」）：用 `ALTER TABLE … SET SCHEMA` 连数据搬迁，并同步改数据访问注册表与 `ddl-naming-baseline.txt`。
3. 顺序：P3b 开工前定表位置 → P3b → 组织同步拆分（集成层同步、workforce 变更集各一个子 PR）→ 外部身份落点与 `employees` 删列（DA-3）→ P5 删信封 `source`；登录 C1 在身份生命周期研究后另排。

## 回滚方案

- 基线开放期：回退对应子 PR 即恢复原位置与原结构（库重建）。
- 基线关闭后：搬表用 `ALTER TABLE … SET SCHEMA` 反向执行；事件命名空间与权限码改名的子 PR 回退后，事件目录与权限清单随之恢复；组织同步拆分回退时恢复 `ApplySourceSnapshot` 的同事务写法与其多聚合例外登记。

## 需同步修改的守护规则

- `backend/architecture/multi-aggregate-exceptions.txt`：删除 `ApplySourceSnapshot` 一条；SESSION_PLAYBOOK §14「已登记的例外」对应条目删除。
- `ExternalConnectionIsolationTest`：准入包去掉 `approval.infrastructure.legacy`，外部连接只在集成层。
- `legacy-shape-exceptions.txt`、`SecurityInvariantsTest` 与 `ticket-issuers-allowlist.txt` 的路径（随 C1 实施）。
- 事件目录守护（`EventCatalogueTest` 等）、`DataArchitectureTest`、`DdlNamingTest` 的登记随表与事件更新。
- 新增：CS-2.29 的 G-C5；集成层以外模块禁用 ACL 术语的守护（由 one-glossary 归类生成，只拦新增）；架构 SSOT 校验（`architecture/` 的 integration 定位）。

## 后果

- 业务与平台模块只用新系统用语；外部系统更换或下线只影响集成层。
- 组织同步从同一事务改为两个事务，运行记录可能短时落后于快照，由补偿作业与告警兜底；快照本身不会半新半旧。
- 生产前工作量约 90–110 个 main 文件、50 个测试文件、15 个前端文件，约 3–4 个子 PR。
- 需同步修改：数据访问注册表、`multi-aggregate-exceptions.txt`、`ddl-naming-baseline.txt`、事件目录与 `asyncapi.yaml`、`permission` 清单、`ExternalConnectionIsolationTest` 的准入包、架构 SSOT（`architecture/ddd/contexts.yaml` 中 integration 的定位）。
