## 决定

1. **原则**：
   1. 概念 id 永久不变：改名、加语言都不改；退役后不复用。
   2. id 不承载含义：任何命名面不得由 id 投影或解析出名字。id 的写法（可读 slug 或无含义编号）属细则。
   3. 唯一来源：命名的唯一来源是 `glossary/` 下的概念与指称源——`terms.yaml`（含 `common_words`、`standard_actions`）及其并入源，`bcs.yaml`（bc 的 id 与中文名、`kind: system` 的系统名、`words`），ACL 归类数据。各命名面上的业务名由指称投影或按决定 3 由登记的槽位渲染，不在别处另立名字；GLOSSARY.md、数据字典、OpenAPI 术语说明是投影。
   4. 领域名不含老系统与外部系统名：使用范围为领域与共享内核的命名面不出现外部系统名与老名；外部系统概念只在 ACL 范围（ADR-0039）出现；老名只作禁用指称供检索。
   5. 缺失即失败：命名面上出现未登记的词、禁用或待确认的指称，或已启用语言所需角色的指称缺失，守护失败并给出可粘贴的登记草稿；所需角色清单属细则；未启用的语言不要求登记指称。例外只有决定 6 第 4 条的运行时回退，且须告警。
2. **三层模型**：
   1. **概念层**：id、种类、所属 bc、使用范围（领域 / 共享内核 / ACL）、定义、标准依据、与其他概念的关系（语义参照 W3C SKOS 的映射与层级关系，含同名异义互列）、概念状态。bc 本身也是概念，特例是以 `bcs.yaml` 的 id 作概念 id。
   2. **指称层**（概念与指称分离，参照 ISO 704:2022、ISO 1087:2019）：一个概念有多条指称，每条带语言标签、角色、使用状态（首选 / 可用 / 禁用，对应 SKOS 的 prefLabel / altLabel / hiddenLabel）、审批状态与来源类型。角色区分同一概念在不同用途下的名字（参照 XBRL 标签角色）；本 ADR 只定一个角色「代码名」，其余角色枚举属细则。（概念, 语言, 角色）至多一条首选指称。
   3. **命名面层**：每个命名面的名字是指称的投影，规则为「取哪个语言与角色的首选指称、按什么格式变换」（如 snake_case 由代码名机械变换，不手写）。投影规则写在细则，不进词表。
3. **组合**：命令、事件、状态取值等以结构化槽位（对象、动词及细则定义的其他槽位）为源，按受控词表与语言渲染成指称，不做字符串翻译；守护只校验渲染结果等于登记的指称。由名字反解槽位只作迁移工具。不能由槽位生成的名字作为例外逐条登记并说明理由。动词表、状态词表、槽位与模板属细则。
4. **命名面归属**：`NAMING_STANDARD.md` 是全部命名面细则的唯一入口（CODING_STANDARD 同例），逐面写明格式、细则所在文件、守护与负责会话；某面细则另有专门文件时（如 `bcs.yaml`、`ddd/contexts.yaml`、ACL 归类）只指向它。命名面至少包括：
   - 领域：概念、聚合、实体、值对象、命令、事件、状态、读模型；
   - 流程与架构：流程、能力、价值流、阶段、业务对象、文档与卡编号；
   - 结构：命名空间、bc 自身的标识与中文名、Java 包；
   - 代码：领域以外的类，方法，枚举与常量；
   - 数据：schema、表、列、约束、索引、触发器、函数、序列、迁移文件、报表视图与 BI 列、存库的枚举取值码、数据库角色与账号；
   - 接口：HTTP 路径与查询参数、JSON 字段、OpenAPI schema、事件载荷键、事件主题与队列名、错误码、导入导出文件名与列头；
   - 授权：权限码、角色码；
   - 运行：业务编号规则代码、配置键、作业、锁、指标、日志字段、审计动作名、BPMN 流程与用户任务键、决策键、缓存键、对象存储与附件路径；
   - 界面：界面文字与消息键（PC、H5、服务端发给人的文字）、通知模板编号、前端路由、前端目录、文件、组件、设计令牌；
   - 外部：外部系统与 ACL 名；
   - 工程：测试名、分支、提交。

   新增命名面只在 NAMING_STANDARD 加一行并挂守护；无守护的面标「待建」并写阶段，期间由复审检查。
5. **生命周期与改名**：
   1. 概念：提议 → 已批准 → 已弃用 → 已退役。提议可先用、构建列出提醒（同 ADR-0018 决定 4）；弃用后新增使用告警，退役后拦截，id 留档。
   2. 指称的审批状态：提议（可用，构建提醒）、待确认（是正式用语还是方言未定，禁止使用）、已批准。
   3. 改名只改指称：新名登记为首选，旧名降为禁用并指向新名，概念 id 不变。各命名面的迁移列入同一变更单（SESSION_PLAYBOOK §12）；已发布接口与事件按 ADR-0035，已应用迁移按 ADR-0038。
   4. 机器可读的引用（守护数据、生成器、文档中的词条引用）用概念 id，不用名字或行号。
6. **多语言结构**：
   1. 语言标签用 BCP 47（RFC 5646、RFC 4647）。
   2. 定义以业务源语言为准，其他语言的指称是对同一概念的指称，不是对源语言名字的逐字翻译。源语言、启用哪些语言及交付阶段登记在细则，由用户定。
   3. 代码标识符恒为英文 ASCII，只由「代码名」角色投影；界面文字不由代码名投影。英文界面名能否与代码名不同由用户定，写入细则。
   4. 界面与服务端发给人的文字一律经消息键取用，不在页面或代码里写死；消息用 Unicode CLDR 与 ICU 消息格式（复数、选择），业务名词以占位符取指称。日志不属于发给人的文字。缺某语言的指称或消息时回退到源语言并告警（日志或指标），不显示键名；构建时对已启用语言做完整性检查，缺失即失败。消息语法版本与库属细则。打印单据、报表、通知模板同样一律走消息键。
   5. 地区格式：日期、数字、货币、时区的显示按 CLDR 与 BCP 47 语言标签取，不在代码里写死格式。
   6. 业务数据的多语言：业务数据中可按语言存多份的字段（如名称、说明）须在数据设计中标明，按语言标签存放；哪些字段可多语言、表结构怎么放的原则另定于细则，未标明的字段只存一份。
7. **治理**：
   1. one-glossary 起草与初裁：概念与各语言、各角色的指称（含英文代码名）、受控动词表、状态词表、同名异义、方言判定、ACL 归类；业务用语由业务 Admin 批准，会计用语（含会计动词）经财务确认（ADR-0018 决定 4）。文档中的用语问题按 `glossary/new_term_issue.py` 登记。
   2. NAMING_STANDARD 逐节写负责会话：词源与指称结构归 one-glossary，命名面清单、投影规则、格式与守护清单归 one-architecture。
   3. 会话之间有分歧，交 one-coordinator 报用户裁定。
   4. 守护不通过不得合并；改断言须写理由（CLAUDE.md 第 5 条）。
8. **变更边界**：细则与词表的变更（新增词、指称、语言、命名面、动词、模板、格式、缩写）不需 ADR；本 ADR 任一决定的变更按 ADR 生命周期另开 ADR。

## 迁移方案

排期由 one-coordinator 定；细目见 NOTES 第 2 节。

1. 采纳后：NAMING_STANDARD 按决定 4 重组并补各面细则（one-architecture）。
2. 词表一次切换为「概念 + 指称列表」（one-architecture 定，2026-10-17；one-glossary 实施）：脚本把现有条目拆成概念 + 指称，id 沿用；输出旧投影（zh、en、snake、aliases、forbidden）与新投影的逐项比对，不等即失败；读取方同批切换，旧字段只留兼容视图，读取方全部迁完后删除。
3. 存量按规则迁移（one-architecture 定，2026-10-17；one-glossary 实施，本 ADR 批准后）：先补名词，立受控动词表与状态词表，按组合规则生成命令、事件、状态并统一改名（已发布接口与事件按 ADR-0035）；生成不了的逐条人工登记。
4. 消息键：前端消息目录与服务端消息键先立结构，新页面起即用。
5. 补守护（见「需同步修改的守护规则」）。

## 回滚方案

本 ADR 只改文档、词表结构、生成器与守护，不改业务数据。

- **可回滚窗口**：词表切换后到兼容视图删除前（新旧投影逐项比对一致），回滚即把读取方切回兼容视图、恢复旧结构文件。
- **窗口之后**：读取方已只认新结构，不再整体回滚；发现问题按本 ADR 生命周期修正（改细则或另开 ADR）。已执行的改名是指称变更，撤销只需对调首选与禁用；已发布接口与事件、已应用迁移上的改名按 ADR-0035、ADR-0038 另行变更。

## 需同步修改的守护规则

- `glossary/term_rules.py`、`build_terms.py`：概念 id 唯一且不复用；（概念, 语言, 角色）至多一条首选；同 bc 内首选名不重复；禁用指称不与任何首选冲突；槽位渲染结果等于登记的指称；待确认指称不得被引用。
- 新增：命名面上出现可由概念 id 解析的名字即失败（id 写法与名字一致时以投影来源判定，细则定检测法）；文档新增 `terms.yaml:<行号>` 式引用即失败（存量登记待清零，已采纳 ADR 正文走勘误）。
- 后端 `Glossary.java` 与 GlossaryTest（G37–G42）、`NamingSurfaceTest`（G43–G48）：改读指称投影。
- `DdlNamingTest`：标识符不超过 63 字节；覆盖触发器、函数、序列、视图。
- `OutwardTextGuardTest` 与前端 `check-copy-glossary.mjs`：改为消息目录校验（键已登记、占位符取指称、无写死文字）。
- 新增：角色码、审计动作名、前端路由、测试名、ACL 名称约定的守护；每面待建守护在 NAMING_STANDARD 登记阶段。

## 后果

- 改名不再动概念与引用；加语言只加指称与消息，不改结构；代码名与界面名分角色。
- 一次性代价：词表与读取方（约 10 个）一次改读新结构、前端文字检查重写、存量命令 46、事件 95、状态 46 条按规则改名（影响已有代码与事件载荷）；越晚越贵。
- 词表源文件变长、评审 diff 变多；靠生成器投影与比对兜底。
- 交用户的事项（NOTES 第 3 节）：多语言范围、英文界面名能否与代码名不同、「确认入账」是否单立动词，均只影响细则。
