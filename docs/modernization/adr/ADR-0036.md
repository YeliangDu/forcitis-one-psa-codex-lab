# ADR-0036：历史数据迁入

- **状态**：提议（2026-10-15 起草，依据用户 2026-10-15 对原则核对 B 的待决项答「全部按推荐 (Recommended)」；待 architecture-critic 评审与用户批准）
- **日期**：2026-10-15

## 背景

- **用户决定**（2026-10-15，intent `2026-10-15-020346-one-coordinator-DDL-审计-原则核对-A-B.md`）：对原则核对 B 的待决项「全部按推荐 (Recommended)」，其中与迁入有关的是：
  - 10 历史期间的迁入过账通道，写成新 ADR；
  - 11 来源系统用中性代码，登记在集成层；
  - 12 迁入单据不发新编号；
  - 13 演练数据除 6e 外用真实数据，6e 敏感数据只在生产迁入；
  - 14 批次术语统一为「迁入批次 / MigrationBatch」。
- **已定的上位规则**：
  - GUIDING_PRINCIPLES §9a：权责事实全部在新系统，经 `operations.facts` 过账。
  - ADR-0025 第 6 条：权责事实不论项目是否已关闭，一律作为事实迁入 OLTP，带 `source = MIGRATION`、原单号与冲销关系，经 `operations.facts` 写入；主数据与未关闭单据随各阶段迁入；只进 OLAP 的历史与只归档的数据另有去向。
  - ADR-0016 第 2 条与 SESSION_PLAYBOOK §12.3：已过账事实只能冲销重做；ADR-0022 第 10 条：关账后不反结账。
  - ADR-0010 第 5 条（经 ADR-0027 保留的部分）：老编号迁为只读的「原编号」，可检索、有新旧对照。
  - ADR-0033（自有标识与来源对照，用户 2026-10-15 已批准）：新行主键一律 UUIDv7，老 ID 只登记在集成层的来源对照，业务表不加 `legacy_id`；`legacy_numbers` 加来源系统列，唯一键为（来源系统, 单据类型, 原编号）；来源系统的取值在 R-1b 定名，领域模块不出现这些取值。
- **缺口**（原则核对 B，2026-10-15，architecture-critic / opus，main @ 0366a4f1）：
  - B-7.1：`legacy_numbers` 形状不支持多来源（已由 ADR-0033 与 DA-11 处理）。
  - H-7.2：迁入的权责事实如何进入新系统中「历史上已经结束」的期间，没有定义——期间状态只有 OPEN / CLOSING / CLOSED，关账后不允许再写。
  - H-7.3：迁入时的副作用（企业微信通知、U8C 推送、编号计数器、流程实例）没有约束。
  - H-7.4：生产访问规则「只出计数或聚合」与迁入要读明细冲突（已由 SESSION_PLAYBOOK §5「迁入读取授权」处理）。
  - H-7.5：没有统一的迁入规格与运行台账；批次术语有三种写法（「导入批次」`import_batch` 等）。
  - M-7.6：来源只分原生 / 迁入，不分来源系统，且不得把供应商名写进 kernel。
  - M-7.7：演练与真实个人数据（6e 薪酬、银行卡）没有约定。

## 决定

1. **迁入通道**：抽取只在集成层的迁入适配器中进行；装载只经目标 BC `api` 中的迁入用例（与业务用例同样经领域校验，不直接写目标表）；迁入以离线命令运行，不挂在 HTTP 接口或定时作业上。迁入使用专用的数据库角色，只在批准的时间窗内启用；读取授权按 SESSION_PLAYBOOK §5「迁入读取授权」。
2. **来源标识用中性代码，登记在集成层**：来源系统按中性代码区分（建议「老系统核心库」「OA」「总账系统」三类，代码与术语在 R-1b 按 ADR-0033 第 2 项第 8 条定名），只出现在集成层的来源对照与迁入登记中；领域模块与 kernel 不出现来源系统名。老 ID 一律登记为来源对照（ADR-0033），迁入行的主键是新生成的 UUIDv7。事件信封的 `source` 仍只区分原生与迁入（`proposals/EVENT_ANALYTICS_FIELDS.md`），不携带来源系统。
3. **迁入批次**：每次运行是一个迁入批次（MigrationBatch），登记在 `platform_integration.migration_batches`（来源系统、对象类型、范围、状态、开始与结束时刻、行数、摘要、操作人）；每个迁入行带 `migration_batch_id`。「迁入批次」是唯一写法，「导入批次」`import_batch` 等其他写法在 R-1b 中改为本写法（G-MG6）。
4. **迁入单据不发新编号**：迁入单据不向编号服务取号、不耗计数器；原编号登记在原编号对照（形状按 ADR-0033），界面检索与展示用原编号。单据表的编号列对迁入行为空，列注释写明「为空表示迁入单据，原编号见原编号对照」，并以 CHECK 约束「编号为空 ⇔ 迁入批次非空」。
5. **迁入无副作用**：迁入不发通知、不向外部系统推送（出站入口对迁入来源一律拒绝，G-MG5）、不耗编号计数器、不启动流程实例；需要的流程结论（如已审批）作为单据状态迁入。
6. **迁入过账通道**：权责事实经 `operations.facts` 的迁入过账通道写入。历史期间在新系统中以「迁入中」状态建立：只接受迁入过账通道的写入，不接受业务过账；该期间对账通过（第 8 条）后由财务确认关账，此后按 ADR-0022 第 10 条不再重开。期间状态由 `accounting.period` 独占（新增取值「迁入中」，在首个迁入权责事实的阶段实现）；开放期间的业务过账不受影响。
7. **断点续跑与拒收**：
   - 按来源键集分块提交（默认每块 1,000 行），批次记录已完成的位置，中断后从断点续跑；
   - 同一来源行再次迁入时，摘要相同则跳过，不同则拒收，不覆盖已迁入的行（已迁入的权责事实只能冲销重做）；
   - 不合格的行写入 `platform_integration.migration_rejects`（批次、来源对象与来源 ID、原因代码），不静默跳过；批次关闭前每条拒收都要有处置。
8. **对账登记**：每个批次按（期间 × 法人 × 对象类型）比对来源与目标的行数、金额合计与来源 ID 摘要，结果写入 `platform_integration.migration_reconciliations`；零差异，或差异经财务签字（签字人、时间、说明），否则批次不得关闭、期间不得关账。
9. **切换窗口与回滚**：切换窗口开始前打数据库时间点；窗口内迁入失败时按时间点回滚整个窗口；上线开放业务之后发现的迁入错误，只能冲销重做（SESSION_PLAYBOOK §12.3），不改不删。演练在 dev 进行：除 6e 外可用真实数据；6e 的敏感数据（薪酬、个税社保、银行卡）只在生产迁入，dev 演练用合成数据。
10. **审计按批次**：每个批次在审计中记开始、结束、关闭、回滚与对账签字（操作人、批次、行数、摘要），不逐行写审计；逐行的追溯靠 `migration_batch_id` 与来源对照。

## 影响面

- **模块**：
  - `platform.integration`：迁入适配器、来源对照（ADR-0033）、迁入批次、拒收与对账三张登记表；
  - 各目标 BC：在 `api` 中提供迁入用例，迁入行带 `migration_batch_id`；单据表的编号列与 CHECK 按第 4 条；
  - `operations.facts`：迁入过账通道；
  - `accounting.period`：期间状态新增「迁入中」；
  - `platform.numbering`：`legacy_numbers` 形状（ADR-0033）；「导入批次」改名（第 3 条）；
  - 出站投递入口：识别并拒绝迁入来源。
- **文档**：SESSION_PLAYBOOK §5「迁入读取授权」、§14.2 迁入检查清单（M1–M10）；`NAMING_STANDARD.md` §4 登记 G-MG1–G-MG7；术语提议见 `backend/glossary/proposed/data-migration.yaml`。
- **运维**：专用迁入角色与时间窗、切换窗口前的数据库时间点（one-ops）。
- **阶段**：影响 Phase 2 起每个有迁入的阶段（含 6a–6f 的 OA 迁入）；1a 只有 `legacy_numbers` 形状与批次术语。

## 迁移方案

1. 首次部署前（R-1b）：`legacy_numbers` 按 ADR-0033 改形状；批次术语统一为「迁入批次」；实现 G-MG1、G-MG6。
2. 首个迁入权责事实的阶段之前：建迁入批次、拒收、对账三张登记表与迁入过账通道，期间状态加「迁入中」；实现 G-MG2–G-MG5、G-MG7；该阶段的迁入规格按 SESSION_PLAYBOOK §14.2 评审。
3. 每个迁入阶段：按 §5 取得读取授权 → dev 演练（含重跑与断点续跑）→ 对账签字 → 切换窗口内生产迁入 → 期间关账。
4. 6e 入口：敏感数据的迁入方案（只在生产执行、可见角色）单独评审。

## 回滚方案

1. 本 ADR 未被采纳或被取代：迁入规则回到 ADR-0025 第 6 条与 GUIDING_PRINCIPLES §9a 的原文；已建的登记表保留为只读台账。
2. 单个批次在切换窗口内失败：按窗口开始前的数据库时间点回滚，修正后重跑。
3. 开放业务后发现错误：冲销重做，不回滚数据库。
4. 「迁入中」期间状态的实现有问题：在该期间关账前可撤回迁入批次（冲销整批）后修正；关账后按冲销规则处理。

## 需同步修改的守护规则

- 新增（登记见 `NAMING_STANDARD.md` §4「待实现的守护」）：G-MG1 `legacy_numbers` 形状；G-MG2 同一批次跑两次结果相同；G-MG3 断点续跑与一次跑完结果一致；G-MG4 迁入无副作用；G-MG5 出站入口拒绝迁入来源；G-MG6 批次术语唯一；G-MG7 对账完整。
- 修改：G36（触账 BC 只经 `operations.facts` 的 api 提交）扩展到迁入过账通道——迁入用例同样只经该 api；数据访问注册表的血缘登记（DATA_SCORECARD D8）增加迁入批次字段。
- 时点：G-MG1、G-MG6 随 R-1b；其余在首个迁入权责事实的阶段之前，由该阶段的工作单元实现。不在本 ADR 的 PR 中实现。

## 后果

- 迁入有统一的通道、批次、拒收与对账，每个阶段只需写迁入规格，不再各自发明做法。
- 历史期间可以在不重开已关账期间的前提下接收迁入事实；代价是期间状态多一个取值，关账检查要区分迁入期间与业务期间。
- 迁入单据保留原编号、不发新号，编号序列不因迁入而跳号；代价是单据编号列对迁入行为空，查询与展示要经原编号对照。
- 来源系统名只在集成层，领域保持中立；新增来源系统只需登记新代码。
- 逐行不写审计，审计量可控；逐行追溯依赖批次与来源对照两张表完整。

## 备选方案（未采用）

- **历史事实只进 OLAP，不进 OLTP**：与 ADR-0025 第 6 条、GUIDING_PRINCIPLES §9a 冲突，同一项目的数据会拆在两处。
- **迁入时临时重开已关账期间**：违反 ADR-0022 第 10 条「关账后不反结账」，且重开窗口内业务过账无法区分。
- **把历史事实都落到当前开放期间并标注原期间**：期间口径失真，历史期间报表无法与老系统对账。
- **迁入单据按新格式发号**：计数器被历史数据占用，编号序列与业务时间错位；用户已定不发新号。
- **业务表加 `legacy_id` 列**：已被 ADR-0033 否决（老 ID 只在来源对照）。
- **逐行写审计**：数百万行迁入会使审计表膨胀，且逐行追溯已由批次与来源对照满足。
