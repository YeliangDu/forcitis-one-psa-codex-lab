# ADR-0035：契约演进与兼容

- **状态**：提议（2026-10-15 起草，依据用户 2026-10-15 对原则核对 A 的待决项答「全部按推荐 (Recommended)」；待 architecture-critic 评审与用户批准；采纳时在同一提交中把 ADR-0008 状态行标注「第 2 条中一句已被 ADR-0035 取代」）
- **日期**：2026-10-15
- **取代**：ADR-0008 第 2 条中「破坏性变更发布 v2，与 v1 并存直到调用方迁完」一句

## 背景

- **用户决定**（2026-10-15，intent `2026-10-15-020346-one-coordinator-DDL-审计-原则核对-A-B.md`）：对原则核对 A 的待决项「全部按推荐 (Recommended)」，其中与契约有关的是：
  - 1.1 对外 ID 一律不透明字符串；
  - 1.3 先扩后收，只有仓库外调用方时才开 `/v{n+1}`；
  - 1.4 事件破坏性变更部署前排空，不写 upcaster；
  - 1.5 兼容性比对用仓库内自写的脚本；
  - 1.6 外部消费方的弃用期 90 天或书面约定。
- **现行规则**：ADR-0008 第 2 条写「破坏性变更发布 v2，与 v1 并存直到调用方迁完」。FORCITIS one 的前端与后端在同一仓库、同一次发布，前端只用 OpenAPI 生成的客户端（ADR-0008 第 3 条）；对同版本发布的自家前端开 v2 并存，只增加维护面，没有收益。
- **缺口**（原则核对 A，2026-10-15，architecture-critic / opus，main @ 0366a4f1）：
  - 1-B1（Blocker）：A8 人员 ID 在请求、响应与查询参数中是 int64，值超过 2^53，浏览器端丢精度；生成的前端校验器把指派人 ID 定义为数字（`frontend/packages/api/src/generated/validators.ts:373`、`:512`）。转交、改派会落到错的人。
  - 1-H1：没有破坏性变更检查；CI 只比对生成物是否最新（`.github/workflows/ci.yml:68`「OpenAPI contract unchanged」）。
  - 1-H2：契约不如实——创建实际返回 201、契约写 200；`If-Match` 运行时必填（428）、契约写可选；未声明 `ETag`；部分响应无类型；`info` 是默认值。
  - 1-H3：事件演进无规则。事件发布登记按 Java 类全名存类型（`platform_integration.event_publication.event_type`），改类名会使在途与死信无法反序列化；负载形状不统一（部分模块序列化成 `{value: …}`，人员 ID 为 int64）。
  - 1-M1–1-M4：「破坏性」未定义；BI 数据集无兼容规则；状态字段是无枚举的字符串；没有弃用流程。
- **相关规则**：接口约定见 `NAMING_STANDARD.md` §2.6（A-1–A-11）；迁移基线开放期见 SESSION_PLAYBOOK §12.2「首次部署前的迁移基线」；契约先行见 SESSION_PLAYBOOK §5 写代码规则第二批第 8 条。

## 决定

1. **契约面**：以下四类都是契约，适用本 ADR：
   - OpenAPI（全部 `/api/v{n}/…` 接口）；
   - 领域事件（`events` 包的 record、序列化后的 JSON 形状、事件发布登记中的类型标识）；
   - 分析数据集（`reporting`、`reporting_compat` 与 `mirror_*` 的视图与列）；
   - 出站负载与入站回调（对外部系统的投递、外部系统回调本系统的格式）。
2. **生效时点**：迁移基线开放期内（`backend/architecture/migration-baseline-open` 存在、尚未首次部署任何环境），契约可直接改，仍须契约先行（OpenAPI 与文档同一提交更新）。标记删除后，第 3–6 条与对应守护生效。
3. **什么是破坏性变更**：
   - HTTP：删除或改名路径、方法、字段、枚举取值；改字段类型或格式；请求字段由可选改必填，或新增必填的请求字段、请求头；响应字段由必有改可选；收紧取值范围；改状态码或错误码的含义；改分页、排序语义。
   - 事件：删除或改名字段；改类型、格式或含义；改事件类型名（含改 Java 类名或包名）；改 ID 形状。
   - 数据集：删除、改名或改类型的列；改粒度或口径。
   - 兼容变更：新增路径；新增可选请求字段；响应、事件新增字段；数据集新增列或新增视图。响应与事件新增枚举取值，对自家前端（宽容读取）是兼容变更，对外部消费方按破坏性变更处理，除非契约写明取值集合开放。
4. **HTTP 演进先扩后收**：先增加新字段或新路径，调用方切换后再按第 6 条删除旧的。只有存在仓库外的调用方（外部系统、外部脚本）时，才开 `/v{n+1}` 与 `/v{n}` 并存；自家前端与后端同版本发布，不开新版本。
5. **事件演进**：
   - 兼容变更不升版本。
   - 破坏性变更二选一：(a) 新的事件类型，旧类型保留到其在途发布与死信清零后再删；(b) 同一类型 `schemaVersion + 1`，部署前排空——该事件的未完成发布与死信为 0 才部署（G-C3）。
   - 不写 upcaster（旧格式到新格式的转换器）。
   - 负载一律扁平：ID 为字符串，不出现 `{value: …}` 包装（`NAMING_STANDARD.md` §2.6 A-7 的类型表示同样适用于事件与出站负载）。
6. **弃用**：要删除的接口、字段或事件先标为弃用——OpenAPI `deprecated: true`，响应头 `Deprecation` 与 `Sunset`，并登记在弃用登记（`backend/architecture/deprecations.yaml`：对象、弃用日、到期日、消费方、出处）。期限：只有自家前端调用的，至少一个发布周期；有外部消费方的，90 天，或与对方书面约定的期限。到期即删除，到期仍在的由 G-C6 拦下。
7. **兼容性检查**：用仓库内自写的脚本比对（OpenAPI 与 merge-base 比对 G-C1，事件目录比对 G-C2），不引入 Pact 等消费者契约框架。消费者契约测试只用于外部消费方（分析数据集 G-C7、对外投递负载）。确需破坏性变更时，在提交 trailer `Contract-Break:` 中写明理由与迁移安排，复审核对。
8. **契约必须如实**：OpenAPI 与运行时一致——创建返回 201 并带 `Location`；修改类接口声明必填 `If-Match` 及 412 / 428；读取声明 `ETag`；状态、类型字段是具名枚举；没有无类型的响应体（不出现 `*/*`、无 schema 的响应）；`info` 的标题、版本与说明正确。由 G-C4 检查。

## 影响面

- **OpenAPI 与前端**：契约修正（第 8 条）后重新生成前端客户端与校验器；ID 改为字符串后，前端凡把 ID 当数字处理的地方都要改（随 R-1b）。
- **事件**：以 `{value: …}` 序列化或带 int64 人员 ID 的事件改为扁平负载与字符串 ID（随 R-1b）；事件目录增加 `schemaVersion` 与弃用标记。
- **CI 与部署**：新增 `scripts/ci/openapi_compat.py` 与事件目录比对；部署剧本增加排空预检（one-ops）。
- **分析数据集**：R1 起按第 3 条与 G-C7 管理。
- **ADR-0008**：第 2 条中「破坏性变更发布 v2……」一句被取代；第 1、3 条与 G20 不变。
- **文档**：`NAMING_STANDARD.md` §2.6、§4（G-C1–G-C7 登记）；`proposals/PHASE1A_PLATFORM_CONVENTIONS.md` §2–3 已注明升格。

## 迁移方案

1. 基线开放期内（现在至首次部署前）：按第 8 条修正契约不如实之处，按第 5 条把事件负载扁平化、ID 改字符串，与 R-1b 的自有 UUIDv7 改造同一批完成；开放期内直接改，不需要兼容过渡。
2. 首次部署前：实现 G-C1、G-C2、G-C4、G-C6，并把 G-C3 接入部署剧本；建立空的弃用登记。
3. 删除基线开放标记（部署剧本 C-3 第一步）后，第 3–6 条与上述守护生效。
4. R1 引入分析数据集时实现 G-C7。

## 回滚方案

1. 本 ADR 未被采纳或日后被取代：恢复 ADR-0008 第 2 条原句，已实现的守护保留为提示性检查或删除。
2. 守护误报：在提交 trailer `Contract-Break:` 中写明理由放行，并修正脚本；不放宽规则本身。
3. 事件破坏性变更部署后需要回滚应用版本：先排空新版本写入的该类事件（未完成发布与死信为 0），再回滚，否则旧版本无法读取新格式。

## 需同步修改的守护规则

- 新增（登记见 `NAMING_STANDARD.md` §4「待实现的守护」）：G-C1 OpenAPI 兼容比对；G-C2 事件兼容；G-C3 部署前排空预检；G-C4 契约如实（扩展 `HttpContractIT`）；G-C5 事件与出站负载扁平、ID 字符串；G-C6 弃用到期；G-C7 分析数据集契约。
- 修改：`EventCatalogueTest` 增加 `schemaVersion` 与弃用标记的登记检查（随 G-C2）。
- 不变：G20（控制器带版本前缀）、F5 / F10（只用生成的客户端）。
- 时点：G-C5 随 R-1b；G-C1–G-C4、G-C6 在首次部署前的「契约演进守护」工作单元实现；G-C7 随 R1。不在本 ADR 的 PR 中实现。

## 后果

- 自家前端不再需要多版本并存，接口演进靠先扩后收与弃用期完成。
- 外部消费方有明确的弃用期与登记，删除有守护兜底。
- 不写 upcaster，事件模型保持简单；代价是事件的破坏性变更要求部署前排空，部署窗口变长。
- 自写比对脚本只覆盖第 3 条列出的变更类型，需要用注入样例证明覆盖；未覆盖的类型靠复审。
- 契约修正与负载扁平化是一次性工作量，在开放期内完成成本最低。

## 备选方案（未采用）

- **保持 ADR-0008 第 2 条（破坏性变更一律发 v2 并存）**：自家前端与后端同版本发布，并存只增加维护面。
- **引入 Pact 等消费者契约框架**：单仓前后端已由生成的客户端保证一致；框架要引入新依赖与新流程，收益只在外部消费方，而外部消费方用第 7 条的契约测试即可。
- **写 upcaster 兼容旧事件**：每次变更都要写转换代码与测试；单体单库，部署前排空更简单可靠。
- **用第三方 OpenAPI diff 工具**：要引入新依赖（SUPPLY_CHAIN.md），且规则（如 trailer 放行、开放期豁免）仍需定制。
- **不设弃用期，直接删除**：外部消费方无法安排迁移。
