## 决定

### 第 1 条　人事命令：聚合、表、ID、事件、日期（A 类）

1. **对象**：ADR-0055 所说的「人事命令」落库为**人事命令**（暂名 PersonnelCommand，待登记），是员工聚合内的实体，表名暂定 `organization_workforce.personnel_commands`。这样做的理由：执行命令要改的员工根、任职版本和命令本身都在同一个聚合、同一个事务里，不需要登记多聚合例外。组织单元的命令另建表（见第 4 条，待批）。
2. **ID**：`personnel_command_id uuid`，UUIDv7，由 workforce 应用层经 `kernel.IdGenerator` 生成，客户端不能提供。接口的幂等仍走 `platform.idempotency`。入职、转正、调岗、停薪留职、离职、复职**共用一个 ID 空间**，因为 ADR-0055:70 的 `revocation_separation_command_id`、ADR-0055:77 的去重键「人事变更命令 ID」以及 F-1 的三列都只需要按 ID 引用一条命令，种类由 `command_kind` 区分。
3. **列**：
   - `command_kind`：text + CHECK，取值为各命令种类；停薪留职的取值等第 3 条批准。
   - `effective_date date`：人事业务生效日，即新状态开始的第一天，与版本表左闭右开的写法一致。界面按「最后工作日」录入时，由应用层换算。
   - `status`：取值为 `PENDING` 待生效、`HELD` 待放行（只用于离职）、`EFFECTIVE` 已生效、`WITHDRAWN` 已撤回。
   - `applied_at`：实际生效时刻，有值当且仅当 `status = EFFECTIVE`。
   - 录入时刻与录入人：`created_at`、`created_by`。
   - 业务内容用带类型的可空列，每种命令配 CHECK，不用 jsonb（D18）。
   - 同一员工可有多条 `PENDING` 命令，生效日不得相同（部分唯一索引）；离职命令之后不得再录更晚的命令；按生效日顺序执行（one-architecture 裁定）。
   - 触发器：拒绝 DELETE 和 TRUNCATE；种类、员工、生效日不能改；状态只能前进。
4. **何时生效**：生效日不晚于今天的命令在录入的同一事务内执行。生效日在今天之后的保持 `PENDING`，由 workforce 自声明的 `@Scheduled` + `@SchedulerLock` 作业在业务时区每日零点后执行（不依赖 `platform.scheduling`，2026-10-20 统一写法），过点没执行的告警（延迟执行也是安全空窗）。补登的命令按真实生效日写版本。生效日早于受影响版本的起始日时，拒绝并告警，不改写已有版本。跨版本更正延后：触发条件为 W2 设计签发，负责人 one-data。
5. **事件**：命令**生效时**才发布领域事件，录入时不发；`PENDING` 的录入、撤回只写审计。
   - 信封：`aggregateType = Employee`，`aggregateId` 为员工 ID，`businessDate` 为生效日，`occurredAt` 为 `applied_at`。
   - 负载：`personnelCommandId`、`employeeId`、`effectiveDate`。调岗另带触发字段（部门、岗位）和前后部门，供 ADR-0032 第 4 项与 F-1 使用。
   - 事件名暂定：`EmployeeHired`、`EmployeeTransferred`、`EmployeeSeparated`、`EmployeeReinstated`、`SeparationHeld`、`SeparationHoldReleased`，转正与停薪留职的事件随第 3 条批准后定名，全部待登记。
   - 用这些事件取代 `OrgSnapshotChanged`（`M/organization/workforce/events/OrgSnapshotChanged.java:14`）与 `EmployeeRegistered`。ADR-0034-IMPL 的 A-10 改为：从负载中取 `personnelCommandId`。
6. **落点**：契约在 A，实现在 B；表结构由 one-data 签发。WF-REINSTATE 卡撤销，复职改由 `EmployeeReinstated` 承载。

### 第 2 条　待放行离职的新载体（A 类）

1. **表**：`organization_workforce.separation_holds`（待放行离职 SeparationHold，提议中，`backend/glossary/proposed/architecture-acl.yaml:19`）。
   - 列：`separation_hold_id`（UUIDv7）；`personnel_command_id`（唯一，同 schema 外键，ON DELETE RESTRICT）；`employee_id`；暂停原因只有 `ADMINISTRATOR_SEPARATION` 一个取值（缩水保护随同步撤销）；`status`（`HELD`、`RELEASED`、`WITHDRAWN`）；`released_at`、`released_by`、`release_reason`；放行途径（`INTERFACE` 界面或 `OPERATIONS_COMMAND` 运维命令）；`version`。
   - 不引用 `sync_runs`，不使用 CASCADE。
   - 触发器：拒绝 DELETE 和 TRUNCATE；放行列只能由空变非空一次（同 ID:497-501 的写法）。
2. **与离职命令的关系**：离职命令执行前，在同一事务内调用 `kernel.SeparationReview`（`M/kernel/SeparationReview.java:17`，只把调用方由同步改为离职命令）。判定需要暂停时，命令转为 `HELD` 并写一条暂停记录：员工保持在职，不发 `EmployeeSeparated`，其他人的命令照常执行（ADR-0055:68）。
3. **单条放行**：
   - 权限沿用 `separation-hold:approve`（ID:574-578），放行人须留任（ADR-0055:69）。
   - 放行后执行该条命令：授予按实际时刻关闭，版本按生效日写入（ADR-0055:71）。
   - 不重跑，不再进入待放行。放行时重新计算「剩余可用超管数」，不计本人，也不计其他仍在 `HELD` 中的人。
   - 结果为 1 名时告警；为 0 名时界面拒绝放行。
   - 审计动作暂名 `organization.workforce.separation-hold.released`，主体为 `EMPLOYEE`，明细带命令 ID 与暂停记录 ID。这样不新增主体种类，也就不依赖 REG。
4. **0 名超管时的运维命令**：在 `identity-operations` 中新增 `release-separation-hold --separation-hold-id --reason --operator --witness`。它沿用 `OperationsCommands.java:23、34-35` 的双人参数，以及审计分区预检（`:80-86`）。ADR-0030 的单人模式不适用于生产（ADR-0055:69）。命令调用 workforce 的放行用例，途径记为 `OPERATIONS_COMMAND`。
5. **迁移次序**（硬要求 5）：
   - B：建两张新表，离职命令的暂停只写新表。
   - C：identity 改为订阅新事件，同批停掉同步调度（`OrgSnapshotSyncJob`），否则同步写出的离职无人收回。C 上线前，运维预检 `sync_run_held_separations` 中所属运行仍为 HELD 的行数，不为 0 就拒绝上线，先用旧接口处置。
   - D2：删 `sync_runs` 与旧表。如果基线已关闭，追加的迁移先在 DO 块里断言上述行数为 0，否则抛错，不经 CASCADE 静默删除（WF:471）。
   - 旧行不转入新表：已处置的放行已由审计记录（`docs/modernization/audit/MUST_AUDIT_ACTIONS.yaml:47-50`）。投产前也没有生产数据。

### 第 3 条　停薪留职（B 类，按用户批准页裁定，待批）

推荐：增加在职状态取值「停薪留职」。保留账号与会话，不吊销会话，不自动关闭显式授予；审批办理人解析跳过此人；持有双人逐人级角色的人生成「敏感角色复核」；此人不算留任，也不算可用超管。代价与受影响的 PR 见 B 类裁定稿。

### 第 4 条　组织单元与岗位命令（B 类，待批）

推荐：组织单元做新建、撤销、改名（含简称）、合并，另补调整上级、指定负责人与区域应收负责人；岗位只做新建与停用，不做职责与编制。组织单元命令另建表，与人事命令同一个 UUIDv7 生成器，不共表。F-1 来源②由撤销与合并触发。

### 第 5 条　F-1 三列改名改义（A 类）

F-1 卡第 462、478、485、520、559 行：

- `trigger_sync_run_id` 拆为两列：`trigger_personnel_command_id` 用于 `ASSIGNMENT_CHANGE`；`trigger_org_unit_command_id` 用于 `ORG_UNIT_INACTIVE`。两列各用 CHECK 与 `origin_kind` 绑定。
- 唯一索引改为 `(kind, user_id, trigger_personnel_command_id, trigger_field_kind)`（ADR-0055:77）。
- `expiry_held_sync_run_id` 改为 `expiry_separation_hold_id`：表示到期时该人正处于这条待放行离职中，放行后补生成（ADR-0044 第 2 项按人理解）。
- `closure_sync_run_id` 拆为 `closure_personnel_command_id`（`CLOSED_BY_SEPARATION`）与 `closure_org_unit_command_id`（`CLOSED_BY_REACTIVATION`）。
- 监听器（F-1:163）改为订阅 `EmployeeTransferred`、`EmployeeSeparated` 与组织单元事件。
- 落点：F-1 排在 C 之后。来源②等第 4 条批准；若不批，来源②延后，触发条件为组织单元命令立项，负责人 one-1a-par。

### 第 6 条　ADR-0034:272 的 OBSERVED（A 类）

取代该句为：「精度按日，依据是人事业务生效日（`DECLARED`）」。授予区间仍记实际时刻（ADR-0055:71）。

- 后果：补登会改变「按业务日期还原」的结果。要回答「系统当时实际执行的是什么」，须另以 `applied_at` 为界还原。这一项延后，触发条件为季度授权复核或审计导出卡立项（ADR-0026 第 6 项第 3 条），负责人 one-architecture。
- 数据访问注册表中 `org_unit_versions`、`assignment_versions` 的生效依据随 B 改为 `DECLARED`（§14.1 D17 第 2 条）。

### 第 7 条　`login_name`、`separated_at`、`last_sync_run_id` 及按 A8 登录名查人（A 类）

1. **`employees.login_name`**（WF:72、95）：删除（D2）。「为空即离职」的翻译只保留在迁入适配器内（ADR-0033 第 4 项第 3 条），A8 人员 ID 经来源对照追溯。应急账号自有的登录名不受影响。
2. **`employees.separated_at`**（WF:78、101）：删除（B），离职的业务日与实际时刻以离职命令为准。现在只有同步写这一列（`JdbcOrgSnapshotRepository.java:150-151`）。
3. **`last_sync_run_id`**（WF:40、63、79、102）：两表都删除（D2）。ADR-0039:48 的「改引用变更集」随同步一起撤销；最近一次改动由审计与命令追溯。同时删去注册表中的三处（`data-access-registry.yaml:69、79、89`）。
4. **按 A8 登录名查人**：删除 `IntegrationOperationsCommands.java:55` 的 `SEEYON_LOGIN_NAME` 分支、`ProviderKind.SEEYON_LOGIN_NAME` 与 `ExternalSubjectEmployees.withExternalLoginName`（D2），取代 ADR-0033 第 3 项第 6 条中按 A8 登录名查的一半。企业微信分支保留，直到外部身份落地（C1、DA-3）。

### 第 12 条　来源对照投产后全表只读（A 类）

1. **封存表**：选数据库触发器，仿 `legacy_numbers` 的先例（NB:82-91）。新建封存表 `platform_integration.source_reference_seals`（来源对照封存，暂名，待登记）：
   - 列：UUIDv7 主键、`sealed_at`、`sealed_by`、`witnessed_by`、`decision_ref`；
   - 至多一行；拒绝 UPDATE、DELETE、TRUNCATE。
2. **对照表**：`source_references` 增加 `BEFORE INSERT OR UPDATE` 触发器，存在封存行即抛 `restrict_violation`。DELETE 已经被拒绝（IG:213-222）。
3. **封存命令**：双人运维命令 `seal-source-references`。仍有 `PENDING` 对照，或有迁入批次未终结时，命令拒绝执行并列出计数。封存是投产出口验证项之一（ADR-0055:113）。
4. **应用层**：封存后，登记、确认、拒绝三个接口（`SourceReferenceController.java:56、67、73`）返回模块错误码。这只是为了给出可读的报错，不作为防线。
5. **不选授权层**：表属主可以给自己重新授权，迁入与运行时是否分开账号尚未核实。
6. **非生产**：重建后的库没有封存行，可以重跑迁入。
7. **落点**：PR-I，必须在投产前完成。

### 第 13 条　勘误（登记 E-008，不改 ADR-0055 正文）

ADR-0055 决定 7 第 1 句引 ADR-0037 的条号有误：运行时读取是决定 1 第 1 条，启动校验是决定 4，账号是决定 5。正确读法登记在 ADR README「勘误与历史偏差」第 2 节 E-008。ADR-0055 头部「取代」行未列决定 1、4，补全会改变效力，不算勘误，由本篇「取代」行承接。ADR-0036 只是被并入人事迁入条目，无需标取代。

### 第 14 条　审计主体种类 `SYNC_RUN`（A 类）

现状是 AU:11 的 CHECK 常量串。

1. **次序**：先完成 REG（注册表，ADR-0066 决定 4 第 5 条），再退休 `SYNC_RUN`，退休只是一行数据（`status = 'RETIRED'`），不再改 DDL。
2. **D2 先于 REG 合并时**：D2 不改 CHECK，也不删 `AuditSubjectKind.SYNC_RUN`，只删写入方，由守护断言已无写入方；REG 建表时 `SYNC_RUN` 直接以 `RETIRED` 入表。
3. **REG 先合并时**：在 D2 中追加退休这一行。
4. **已有条目**：只追加，不改写，照常可读（D8）。
5. **注册表形态（one-architecture 裁定）**：审计主体种类登记为 `platform_audit` 内的登记表（code 唯一、属主、状态、生效期），平台自有种类与组织类种类都在表中登记，代码常量只作引用；业务单据另以类型码记录（ADR-0066 决定 4 第 5 条）。这样满足 owner「退休是一行 `status = 'RETIRED'`」，也不违 ADR-0066「平台自有种类留在审计内部」。表结构由 one-data 签发；退休由 one-1a-par 负责。

## 迁移方案

1. 本篇与 B 类批准页同批入库，0 单元据此改卡。
2. 按 R → F → G → A → B → C → D1 → D2 → E → H-1 → I 的次序推进；REG 独立进行，H-2 等 T-13。
3. 第 2 条第 5 项是硬前置：B 早于 C，C 的预检和 D2 的断言缺一不可。
4. 基线开放期直接改基线；关闭后按 ADR-0038 追加迁移。

## 回滚方案

- 非生产且基线开放：退回实施变更，重建后重跑迁入。
- 已生效的命令、放行、授予关闭与审计不回滚，错误用新的命令更正。
- 封存后不提供解封；要解封须另立 ADR。

## 需同步修改的守护规则

1. **人事命令**：守护以下行为——
   - 重放幂等、未来生效作业的执行与告警；
   - 补登早于版本时拒绝；
   - 同一员工同一生效日只有一条待生效命令、离职之后不得再录更晚命令、按生效日顺序执行；
   - 只追加触发器。
2. **待放行离职**：守护以下行为——
   - 单条放行、不重跑；
   - 剩余超管数分别为 2、1、0 时的行为；
   - 运维命令缺见证人时拒绝；
   - 无 CASCADE、关闭只能一次；
   - C 的预检与 D2 的断言。
3. **F-1**：两套键各自去重；列与 `origin_kind` 的绑定 CHECK。
4. **封存**：封存后对 INSERT、UPDATE 的负向测试；封存表不可改；有 `PENDING` 对照时拒绝封存。
5. **登记与目录**：`DataArchitectureTest`、`DdlNamingTest`、事件目录、MUST_AUDIT、system-actors 随卡更新。删除 `EmergencyLoginIntegrationTest:209` 的断言（D1）须在 PR 中单列理由；其余断言不放宽。

## 后果

- **收益**：人事成为单一来源，待放行按人处理，不会因 CASCADE 丢数据，来源对照在数据库层只读。
- **代价**：
  - 新增未来生效作业，须监控；
  - 同一员工同一生效日只能有一条待生效命令，离职之后不能再预登记；
  - 封存后对照无法更正，U8C 编码变化仍待审定（ADR-0055:84）。
- **待登记用语**：人事命令、人事业务生效日、待生效、已撤回、来源对照封存、入职、调岗、复职；「转正」与 `contract.agreement` 的 `Regularized` 同名异义，须互列。上述用语交 one-glossary 登记。

## 备选方案（未采用）

- **每种命令一张表**：离职、复职各用自己的 ID 空间时，F-1 与去重键要引用多个 ID 空间。
- **把旧暂停行转入新表**：旧行带着同步的语义，投产前也没有生产数据，转入不值得。
- **用授权或应用层实现只读**：表属主可以给自己重新授权，应用层可以被绕过。
- **D2 中直接改 AU 的 CHECK**：REG 完成后还要再改一次 DDL，违背 owner 的硬要求 4。
