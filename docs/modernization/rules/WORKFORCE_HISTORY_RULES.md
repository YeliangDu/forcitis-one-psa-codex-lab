# 组织与任职历史规则卡（organization.workforce）

编号待协调者分配（候选）。依据：ADR-0026 §2；数据打分卡 T1「组织单元与任职的变化历史在交易库保留」。

## 候选规则：历史从第一次同步之日起，更早日期的历史导入在补录前不得进行

```
Given 新系统第一次同步在 D0 日完成
 And  org_unit_versions / assignment_versions 的第一条记录的生效日是 D0（回填日）
When  某历史单据（迁移导入）的业务日期早于 D0，需要按日期解析法人
Then  解析找不到该日的部门或任职，返回「员工法人无法确定」（422），不猜、不取今天的值
 And  这类历史导入被阻止，直到组织数据管理员补录 D0 之前的历史
 And  补录是追加更早的生效区间，不改写已有区间；补录后同一导入可重试

Given 员工在第一次登录时登记（EmployeeRegistered），早于下一次同步
When  同一员工被两个并发登录同时登记
Then  登记先取得快照写锁，后到者发现已登记就不再写、不再发事件（一个员工只发一次 EmployeeRegistered）
 And  登记与同步互斥：同步进行中，登记等待，不会写进同步正在重算的快照
```

为什么现在写成规则而不写代码：回填日是部署事实，补录的数据来自业务，需要组织数据管理员提供；在没有历史来源之前阻止比猜测安全。守护：解析找不到时失败（G-1），见 `EmployeeLegalEntities.on` 的契约测试；并发登记见 `OrgDirectoryIntegrationTest.concurrentFirstLoginsRegisterOnce`。

## 候选规则：离职申请的预计离职日期与离职观察时间是两件事，不混用（1b 定，1a 不变）

依据：用户 2026-10-15 问「离职申请流程会有预计离职日期，你需要的是真实的离职日期吗」，随后「安排 one-ops 去查表单字段」（intent `2026-10-15-004835-one-coordinator-离职日期-离职申请流程会有预计离.md`）。one-ops 只读查结构与计数（2026-10-15）：

- 来源是 A8「员工离职申请」流程的表单主表 `a8_db.dbo.formmain_0348`。预计离职日期 = `field0031`（SQL Server `datetime`，不带时区）；人员关联 = `field0012` 员工编号 → `ORG_MEMBER.CODE`（近 12 个月 60 / 60 可对上）；流程状态 `finishedflag`（1 结束、0 未结束、3 含义待查）、`state`、`ratifyflag`。
- 预计止薪日期 `field0032` 近 12 个月全空，不用。表单没有最后工作日、实际离职日、交接完成日。
- **待取证（登记前置）**：`state`、`ratifyflag` 各取值的含义与计数（必要时加流程摘要表），以区分「正常结束且同意」与终止、否决、撤销；流程结束时间所在的列与表；`ORG_MEMBER.CODE` 是否会被重复使用。由 one-ops 只读查，查清前本卡不作为实现依据。

```
Given 某员工在当前任职段（最近一次入职或复职之后）有离职申请
 And  申请「正常结束且同意」（条件待取证查清后写成具体取值）
When  需要该员工的预计离职日期
Then  取流程结束时间最晚的一条（相同时比记录 id）的 field0031，按 Asia/Shanghai 本地时间取日期部分（不先转 UTC）
 And  被终止、否决、撤销、未结束的申请都不是来源
 And  预计离职日期已过而员工仍在职时，标为「已过期」，消费方不得当作事实

Given 组织同步第一次把某员工的在职状态判为离职（RULE-363 口径：登录名为空，或 A8 不再返回该员工——后者可能是误判，例如调出组织路径）
When  这一变化写入快照
Then  离职观察时间 = 写入该变化的那一轮同步（SUCCEEDED 或 RELEASED）的提交时刻；HELD 期间不记，放行时才记（与 I-13 一致）
 And  它只表示「新系统这样判定了」，不是人事生效日，不冒充预计离职日期
 And  每次离职各记一条；复职后再离职是新的一条，不覆盖旧值
 And  首次部署时，首轮快照里已是离职状态的员工，离职观察时间为「未知」，不记部署时刻

Given 没有可对上的申请，或没有观察记录
When  需要上述任一属性
Then  该属性为「未知」，不推算、不编造

Given 视图返回 finishedflag = 3（含义未查清）或无法解析的状态
When  读取离职申请
Then  不作为来源；计数并告警（G-1），不静默跳过
```

敏感性与最小列：未结束的离职申请意味着「某人将要离职」尚未公开，属于敏感信息。为从源头避免，新系统读取的只读视图**在 A8 库内只返回正常结束且同意的申请**，未结束的申请不离开 A8；列只取人员关联键（优先用快照已用的人员关联键，必须用 `CODE` 时写明重复使用与对不上 / 对上多人的处理）、预计离职日期、流程结束时间；不含姓名文本、离职原因、约谈内容。

范围：两个属性目前没有具体消费方——1b 的离职者在途待办与待调整权限都由离职事件触发，工时截止需要的是实际日期，两者都给不了。因此 1b 只把来源与口径写清，在出现具体消费方之前不建列、不建视图；离职观察时间多半可由同步批次与事件审计推出，届时先评估能否不另存。实现时须同步：`forcitis_one` schema 只读视图（one-ops 建）、`backend/architecture/seeyon-view-columns.yaml` 列白名单、应用启动自检的视图清单（`phase1a/SECURITY_INVARIANTS.md` I-1）。

用语：提议术语见 `backend/glossary/proposed/organization_workforce.yaml`（离职申请 `separation_request`、预计离职日期 `expected_separation_date`、离职观察时间 `separation_observed_at`）；单说「离职日期」/ `separation_date` 有歧义，列为禁用写法。
