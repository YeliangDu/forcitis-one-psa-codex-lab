# DATA-RULE-01…08 评审（one-rules，2026-10-17；作者 one-data，评审独立于作者）

对象：`DATA_ARCHITECTURE_RULES.md` 的 8 条规则卡。对照：DATA_DESIGN_CHECKLIST §14.1（D2、D6、D8、D12、D15、D17 及其已定口径）、各卡所引用的用户决定。评审只读不改卡；结论用词与规则索引一致（沿用 / 需修正 / 待议）。本评审是评审者的意见，不是用户裁定，不写入 `RULE_REVIEWS.json`（那里只记用户作答）。

| 规则 | 结论 | 要点 |
|---|---|---|
| DATA-RULE-01 版本表只追加 | 沿用 | 与 D6、D8、D17 一致。补一句：防重叠约束（`EXCLUDE USING gist`，D17 细则）卡里没写，应写明，否则「只追加」与「同一天再变化」的空区间靠什么防重叠不清楚。 |
| DATA-RULE-02 工作日历今天之前不可修改 | 需修正 | D17 已定口径（用户 2026-10-15）：工作日历按配置型版本化，新版本须「业务管理员四眼确认」。本卡的例外路径只写「组织数据管理员 + 权限」，没写四眼确认，也没写版本表 / 确认人 / 决定出处（D15）。须补：例外修改同样要第二人确认并留确认人。 |
| DATA-RULE-03 法人版本以记录日为准 | 需修正 | D17 已定口径（用户 2026-10-15）：法人代码「未发过号前可更正，发号后禁改」，更名只改名称走版本。本卡写「代码、名称、状态变化记入版本」，没有区分代码与名称，读起来像代码可随版本改。须写明：代码在发号后不可改，只有名称、状态走版本。「不支持预约与补录」的理由（1a 无使用者）成立，不改。 |
| DATA-RULE-04 已处理事件保留与幂等 | 沿用（附核） | 设计合理（90 天大于归档期 30 天，且幂等不依赖这张表）。D12 要求保留期在 GUIDING_PRINCIPLES §6 登记并经用户认可：请 one-data 核对「90 天」「30 天」是否已登记，没有则补登记并随下一页问用户。 |
| DATA-RULE-05 组织对账悬空引用 | 沿用 | 记问题、置空、继续，不是静默跳过（CLAUDE.md 第 6 条要求告警，本卡用 ISSUE 记录满足）；生产取证 0 悬空，外键可加。补一句：ISSUE 须触发告警而不只是落表，并写明告警去向。 |
| DATA-RULE-06 归档先确认后删除 | 沿用 | 先写读回核对再删，国内地域，配置缺失启动失败，均合理；出自用户 2026-10-15 决定。 |
| DATA-RULE-07 法人归属不缩短已关闭期间 | 待议 | 卡自己标「需负责人确认」。评审意见：「过晚结束无法更正」是真实缺口（例如调动登记晚了，新法人期间要从旧结束日起，之前一段时间会归错法人），且这些期间决定费用归属。D6 只许关闭不许改写，所以不该缩短旧行，但应给出更正路径（追加更正版本、带修订序号与原因，沿用 DATA-RULE-01 的同日修订做法），而不是「没有更正路径」。建议改为这样，并交用户或业务负责人确认；确认前不实现「无更正路径」的限制。 |
| DATA-RULE-08 归档保留期 = 在线 + WORM | 沿用（附核） | 3 年 + 2557 天 = 3652 天，约 10 年，算术成立；探针要求「等于」比「不少于」更严，合理。两点须核对：保留期总年数 10 年是否已在 GUIDING_PRINCIPLES §6 登记并经用户认可（D12）；归档含个人信息，10 年保留需写明理由（审计与诉讼时效），以符合个人信息最小保存要求。 |
