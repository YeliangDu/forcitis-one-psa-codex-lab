观察：

## 状态词候选

「已 + 动词」：已通过、已驳回、已退回、已认领、已确认、已维持、已调整、已放行、已跳过、已拒绝、已超时、已锁定。
「待 + 动词」：待认领、待确认、待处理、待内部结算、待调整权限状态。
裸词：在途、停用、进行中、视为同意。
事件常见尾词：确认、停用、登记、启用、拒绝、退回、预警、关闭、认领、审批、批准。

## 待 ADR 回答的问题

1. 事件名是否统一为「对象 + 已 + 动词」，现有裸动作事件（回款、转正、开票）如何改。
2. 状态取值是否统一为「已 / 待 + 动词」，裸词状态（在途、停用）归哪类。
3. 「state」kind 里的枚举类别名是否改 kind（value_object）。
4. 受控动词表规模：近义组各取一个，其余作别名或方言。

## 迁移脚本思路（用户 2026-10-17：「现在刚开始，代价是最低的时候」，按长期正确完整采用，不因迁移量妥协）

### 目标结构（概念与名称分离）

- 概念 `concept`：稳定 id（不随改名变）、kind、bc、scope、definition、standard_ref、status、homonyms 引用。
- 指称 `designation`（一概念多条）：语言（zh / en / 表列 snake / 接口 / 权限串等命名面）、名称、角色（规范 canonical / 别名 alias / 禁用 forbidden）、生效与退役时间。当前 terms.yaml 的 zh、en、snake、aliases、forbidden 都是指称，拆开后改名只加一条指称、不动概念 id，引用方按概念 id 引用。
- 原子词表：名词（登记的概念）、受控动词、状态词；命令、事件、状态名由「名词 + 动词 / 状态词」按语法生成，生成结果作为指称写出，不手写。

### 迁移步骤

1. 抽取：从 `terms.yaml` 与 `proposed/*.yaml` 现有 994 条（664 + 330）按字段拆成概念 + 指称，id 沿用现 id，保证引用不断。
2. 分类：kind 为 state 的词条拆「状态集合名」（改 value_object）与「状态取值」（挂到所属集合）；命令、事件、状态按动词表和状态词表反解出（名词, 动词）对，反解不了的列为例外清单，逐条判。
3. 生成：用组合规则重新生成命令、事件、状态指称，与现名比对，差异进改名对照表（497 处改名表可直接作输入）。
4. 校验：不变量——每个概念有且仅有一个 zh 规范名和一个 en 规范名（同 bc 内唯一）；别名与禁用词跨概念不冲突；生成名可由原子反解。
5. 切换：生成器 `build_terms.py` 改读新结构；`terms.yaml` 由新源生成，旧字段保留一个兼容视图供未迁移的守护读取，守护全部迁完后删除视图。
