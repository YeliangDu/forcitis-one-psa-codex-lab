# 会话管理方案 — FORCITIS one（PSA 现代化）

日期：2026-10-14 · 决策记录：ADR-0020 · 用户要求：「整个改造过程会话管理很重要，需要明确的方案。」

## 0. 核心原则

1. **状态在文件里，不在对话里。** 对话会被压缩，会话会结束；凡是下一次会话需要知道的事，在本次会话结束前写进文件。聊天记录只是过程，不是记录。
2. **一个会话只做一个工作单元。** 一个工作单元 = 一个阶段的一个步骤（例如「Phase 1a · 身份桥接 · 实现」），有明确的入口、出口和交付物。不在同一会话里跨阶段。
3. **人做决定，会话执行。** 所有审批、对外动作、业务口径都由用户明确决定，并以原话记录；会话不把沉默当同意。
4. **每次开场和收尾都走固定协议**（§3、§4），任何会话都能接上任何上一次会话。

## 1. 状态文件：唯一事实来源

| 文件 | 内容 | 谁更新 | 何时更新 |
|---|---|---|---|
| `STATUS.md` | 现在在哪：当前阶段、各工作单元状态与负责会话、阻塞项、下一条命令 | 每个会话 | 开场认领、收尾更新 |
| `SESSION_LOG.md` | 只追加的会话日志：每个会话一条（目标、输入、用户决定原话、产出、未完成项、下一步） | 每个会话 | 收尾时追加 |
| `INTENT.md` | 用户的全部要求与决定原话 → 落点 | 收到用户决定时 | 即时 |
| `adr/` | 架构决策（状态：提议 / 已采纳） | 产生或改变决策时 | 即时 |
| `MODERNIZATION_BRIEF.md` | 阶段计划与入口 / 出口条件（勾选即进度） | 条件满足时只勾选，不改写条件 | 即时 |
| `SECURITY_FINDINGS.md`、`glossary/`、`DS_GAPS.md`、`RULE_REVIEWS.json` | 各专题的状态 | 对应会话 | 即时 |
| 跨会话记忆（`~/.claude/projects/.../memory/`） | 只放长期偏好与授权（全程中文、设计正本写入授权等） | 会话 | 用户给出长期规则时 |
| `~/.modernize/psa/`（权限 600） | 凭据原值、凭据补丁 | 安全会话 | 仅本机，永不进任何可共享文件 |

**版本化（待用户确认）**：`psa-modernization/` 工作区目前不是 git 仓库，状态文件没有历史。建议把 `analysis/psa/`（不含 `~/.modernize` 中的任何内容）移入 `FORCITIS/forcitis-one-psa` 的 `docs/modernization/`，每个会话收尾时提交一次；新仓库的 gitleaks 守护同时覆盖这些文件。

## 2. 会话的种类

| 种类 | 典型命令 | 产出 | 一个会话的边界 |
|---|---|---|---|
| 评估与定栈（本会话） | `assess` `map` `extract-rules` `brief` | brief、ADR、守护模板 | 到 brief 审批为止 |
| 规则评审 | `/code-modernization:modernize-review psa` | `RULE_REVIEWS.json` | 一个业务域的被标记规则 |
| 阶段实施 | `/code-modernization:modernize-reimagine` | `forcitis-one-psa` 中的代码与测试 | 一个阶段的一个 BC 切片 |
| 验证 | `/code-modernization:modernize-verify` | 影子比对、对账报告 | 一个阶段的出口条件 |
| 安全 | `/code-modernization:modernize-harden` | 补丁与复审记录 | 一组发现 |
| 设计正本同步 | `/design-sync`（在 `forcitis-one-psa` 中） | 正本更新、`DS_GAPS.md` | 一个阶段的差距清单 |
| 巡检（可选） | `/loop`、定时任务 | CI、待办、告警的检查记录 | 只读，不改代码 |

## 3. 开场协议（每个会话的前五分钟）

1. 运行 `/code-modernization:modernize-status psa`，读 `STATUS.md` 和 `SESSION_LOG.md` 最后一条。
2. 在 `STATUS.md` 中认领一个工作单元（写上会话名与开始时间）；已被其他会话认领的不碰。
3. 读该工作单元在 brief 中的入口条件；有未满足的，停下来告诉用户，不硬做。
4. 用一句话向用户确认本会话的目标和出口条件；需要时用 `/goal` 固定出口条件。
5. 会话命名：`psa-<阶段>-<单元>-<动作>`，例如 `psa-1a-identity-implement`（用 `/rename`），便于日后用 `claude --resume` 找回。

## 4. 收尾协议（结束前，或上下文接近上限时）

1. 把本会话的决定（用户原话）写进 `INTENT.md` 和相应 ADR。
2. 勾选 brief 中已满足的条件；不满足的不勾，不改写条件。
3. 在 `SESSION_LOG.md` 追加一条（模板见 §8），写明下一条要运行的命令。
4. 更新 `STATUS.md`：释放认领，标明单元状态（完成 / 部分完成 / 阻塞及原因）。
5. 需要时重新生成 brief 与 `REPORT.html`；（版本化之后）提交一次。
6. 清理临时目录；确认没有凭据原值出现在任何可共享文件中。
7. 向 `psa-coordinator` 发报告（格式见 §11「消息约定」：提交号与分支、产出文件、验证结果、未完成项、需要用户决定的事）。不论完成、部分完成还是阻塞，结束前都要报告（用户 2026-10-14：「新建会话结束后，应该向你报告结果」）。

## 5. 上下文管理

- **把大输出放进文件**：扫描结果、日志、生产查询结果写入文件，会话里只引用结论和路径。
- **探索交给子代理**：大范围读代码、复审、实测用后台子代理，主会话只保留结论。
- **子代理必须指定模型**（用户 2026-10-14：「派出子代理要指定最合适的模型，不要都默认，所有新会话都应该遵循」）：每次派子代理（`Agent` 工具，以及 Workflow 里的 `agent()`）都显式写 `model`，按任务难度选，不留默认：
  - `haiku`：机械性工作——按名称或模式查找文件、列清单、统计、格式转换、跑命令并汇总输出。
  - `sonnet`：常规工程——按骨架和规格写代码与测试、迁移单个模块、核对引用和链接、按模板生成文档、一般复审。
  - `opus`：需要判断的工作——架构设计与对抗性评审、安全审计、业务规则抽取与评审建议、行为等价判定、跨模块影响分析、拿不准该选哪个时。
  - 派工单和子代理提示中写明所选模型；同一类任务在本会话内保持一致。子代理定义文件自带 `model` 时也照此原则核对，不合适就在调用时覆盖。
- **压缩不可怕，丢状态才可怕**：会话自动压缩后只依赖摘要；所以收尾协议里的文件更新不能拖到最后一刻——每完成一个决定就写一次。
- **切换会话的信号**：一个工作单元完成；或者主题要换；或者上下文已经很长且后续需要大量新输入。此时走收尾协议，新会话从开场协议接上。

## 6. 并行

- 多个会话可以同时进行，但只在**互不相交的工作单元**上（不同 BC、不同阶段的不同步骤）。
- 写代码的并行会话各用自己的 git worktree 和分支（`feature/issue-{N}-…`），互不共享工作目录。
- 共享状态文件（`STATUS.md`、`SESSION_LOG.md`、brief）只追加或改自己认领的行；冲突时以最后一次提交为准并人工合并。
- 会话之间用 `ListAgents` / `SendMessage` 打招呼（例如「我改了 platform.identity 的 api，你那边需要重新编译」）。

## 7. 必须由用户决定的事（会话一律停下等待）

- brief 审批、ADR 从「提议」到「已采纳」；
- 业务口径、用语（正式用语还是方言）、规则评审结论；
- 推送代码、创建或更新 PR、触发 CI / 部署、生产变更（包括 nginx、Nacos）；
- 往设计正本写入（已有长期授权，但每次写入仍先列计划）；
- 访问生产（已有只读授权；任何写操作都不做）；
- 凭据轮换、历史清理。

记录方式：用户原话写进 `INTENT.md`，并在对应 ADR、brief 条件或专题文件中引用。

## 8. `SESSION_LOG.md` 条目模板

```
## <日期> · <会话名> · <工作单元>
- 目标：
- 输入（读过的状态文件、上一条日志）：
- 用户决定（原话）：
- 产出（文件 / 提交 / 发布的页面）：
- 验证（跑了什么、结果）：
- 未完成与阻塞：
- 下一步命令：
- 会话 ID（用于 claude --resume）：
```

## 9. 长时间任务与通知

- 后台子代理完成后会自动通知所在会话；会话不轮询。
- 外部状态（CI、部署）用 `Monitor` 或 `/loop` 按实际节奏检查，不做高频轮询。
- 跨天的工作（例如两个月结期间的影子比对）不靠一个长会话：每次检查开一个短会话，按开场 / 收尾协议记录。

## 10. 中断与恢复

- 会话意外结束：新会话按开场协议读 `STATUS.md` 和日志接上；需要原对话时用 `claude --resume <会话名>`。
- 后台工作流中断：同一会话内可从中断处恢复；跨会话则按日志重新发起。
- 发现状态文件与实际不一致（例如 brief 勾了但测试没过）：以可验证的事实为准，更正状态文件并在日志中说明。

## 11. 总调度会话 `psa-coordinator`（用户 2026-10-14：「新开 psa-coordinator 会话负责调度」）

**定位**：在 `forcitis-one-psa` 中常驻的一个会话，只做调度，不写业务代码、不做评审结论。

**职责**
1. 开场：读 `STATUS.md`、`SESSION_LOG.md` 最后几条、brief 待决项；`ListAgents` 查看各工作会话的状态。
2. 派发：为下一个工作单元写好「派工单」（见下），发给对应会话；工作会话尚不存在时，请用户按会话名新开。
3. 接收与核对：工作会话结束前（完成、部分完成或阻塞）都向 `psa-coordinator` 报告（§4 第 7 步）；调度会话核对产出（读分支上的文件、跑必要的只读检查），确认与用户决定一致后更新 `STATUS.md`。
4. 衔接：一个单元的改动影响其他单元时（例如 `platform.identity` 的 api 变化），通知受影响的会话。
5. 汇总给用户：把所有需要用户决定的事（审批、口径、推送 / PR、部署、生产变更）汇总成一张清单，一次问清；用户的回答以原话转达。
6. 收尾：每次调度会话结束前按 §4 收尾协议记日志。

**消息约定**
- 第一行写清是什么事：「派工：…」「报告：…」「请用户决定：…」「通知：…」。
- **建议与决定分开写**：调度会话自己的建议标「建议」；只有用户原话才标「用户决定：『…』」。工作会话不得把「建议」当成用户批准。
- 派工单包含：工作单元与会话名、目标与出口条件、入口条件是否满足、需读的文件、已知用户决定（原话）、完成后向谁报告。
- 报告包含：提交号与分支、产出文件、验证结果、未完成项、需要用户决定的事。

**边界**
- 调度会话不能替用户批准任何事，不能让其他会话代做本会话被拒绝的操作。
- 工作会话权限模式不同时可能扣住消息，需要用户在那边放行；消息无回执时不视为已执行，以对方的报告或文件为准。
- 调度会话上下文变长时，按收尾协议记好状态后重开同名会话接续。
