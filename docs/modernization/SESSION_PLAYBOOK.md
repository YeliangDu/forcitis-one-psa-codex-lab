# 会话管理方案 — FORCITIS one 现代化

日期：2026-10-14 · 决策记录：ADR-0020 · 用户要求：「整个改造过程会话管理很重要，需要明确的方案。」

## 0. 核心原则

1. **状态在文件里，不在对话里。** 对话会被压缩，会话会结束；凡是下一次会话需要知道的事，在本次会话结束前写进文件。聊天记录只是过程，不是记录。
2. **一个会话只做一个工作单元。** 一个工作单元 = 一个阶段的一个步骤（例如「Phase 1a · 身份桥接 · 实现」），有明确的入口、出口和交付物。不在同一会话里跨阶段。
3. **人做决定，会话执行。** 所有审批、对外动作、业务口径都由用户明确决定，并以原话记录；会话不把沉默当同意。
4. **每次开场和收尾都走固定协议**（§3、§4），任何会话都能接上任何上一次会话。

## 1. 状态文件：唯一事实来源

| 文件 | 内容 | 谁更新 | 何时更新 |
|---|---|---|---|

| `adr/`（生成，源文件在 `adr/src/`） | 架构决策（状态：提议 / 已采纳 / 已被取代 / 已废弃；已采纳正文冻结，见 §12），每份 ADR 一个源文件 `adr/src/ADR-NNNN.md` | 产生或改变决策时 | 即时 |

| `MODERNIZATION_BRIEF.md` | 阶段计划与入口 / 出口条件（勾选即进度） | 条件满足时只勾选，不改写条件 | 即时 |

**版本化（待用户确认）**：`psa-modernization/` 工作区目前不是 git 仓库，状态文件没有历史。建议把 `analysis/psa/`（不含 `~/.modernize` 中的任何内容）移入 `FORCITIS/forcitis-one-psa` 的 `docs/modernization/`，每个会话收尾时提交一次；新仓库的 gitleaks 守护同时覆盖这些文件。

## 2. 会话的种类

| 种类 | 典型命令 | 产出 | 一个会话的边界 |
|---|---|---|---|
| 评估与定栈（本会话） | `assess` `map` `extract-rules` `brief` | brief、ADR、守护模板 | 到 brief 审批为止 |
| 规则评审 | `/code-modernization:modernize-review psa` | `RULE_REVIEWS.json` | 一个业务域的被标记规则 |
| 阶段实施 | `/code-modernization:modernize-reimagine` | `forcitis-one-psa` 中的代码与测试 | 一个阶段的一个 BC 切片 |
| 验证 | `/code-modernization:modernize-verify` | 影子比对、对账报告 | 一个阶段的出口条件 |
| 安全 | `/code-modernization:modernize-harden` | 补丁与复审记录 | 一组发现 |
| 设计正本同步 | `/design-sync`（在 `forcitis-one-psa` 中） | 正本更新、`DS_GAPS.md` | 一个阶段的差距清单 |
| 巡检（可选） | `/loop`、定时任务 | CI、待办、告警的检查记录 | 只读，不改代码 |

### 2.1 会话管理（用户 2026-10-15 对会话管理十二条答「两条都采纳」）

1. **生命周期与交接**：一个会话负责一个工作单元，在批次边界交接；连续运行超过约 8 小时或上下文已压缩两次以上，在下一个批次边界换新会话。交接报告写明在途分支与 PR、未完事项、待用户决定的事、下一步派工草案；旧会话改名「<原名>-1（已交接）」，不再接新工作。
2. **命名与唯一性**：新会话一律 `one-*` 前缀；同名只能有一个（本机与远程会话也不得重名）；调度会话全局唯一，换人按 §11 交接。
3. **权限模式一致**：工作会话与调度会话的权限模式相同，否则跨会话消息会被扣住或过期；新开会话时就设好。
4. **推理强度与模型**：调度、整合、复审用 high；执行类按任务难度选，并写进派工单。
5. **工作区纪律**：只在自己的 worktree 分支工作并开 PR，不在主检出目录留改动（§4 第 6a 步）。
6. **必须报告**：每个完成点与收尾都向调度会话报告，未报告不算完成。
7. **用户在工作会话中的决定**：当场用 `new_intent.py` 记原话，并立即报调度会话；调度会话用会话记录搜索核实原话。
8. **子代理再派子代理**：后台派出的子代理结果会送到最上层会话，不会回到派它的子代理；需要再派时用前台等待，或在派工单中写明由调度会话转交结果。
9. **后台任务与持久配置登记**：定时器、systemd 测试单元、本机 runner、云上临时资源等，建立时登记进调度台账，用完清理并写进记录。
10. **密钥不进会话记录**：不调用会返回密钥的接口、不打印凭据；一旦进入记录，按安全事件上报与处置。
11. **长期会话关闭自动归档**：调度会话、长期运维会话关闭「PR 合并或关闭时自动归档」。
12. **收尾归档**：交接完成后归档旧会话，并更新调度台账的在途会话表。

## 3. 开场协议（每个会话的前五分钟）

1. 运行 `python3 docs/modernization/build_all.py` 在本地生成记录（或看 [generated-docs 分支](https://github.com/FORCITIS/forcitis-one-psa/tree/generated-docs)），再运行 `/code-modernization:modernize-status psa`，读 `STATUS.md` 和 `SESSION_LOG.md` 最后一条。
2. 认领一个工作单元：在该单元的片段 `status/units/<排序>-<名称>.md` 的「负责会话」写上会话名与开始时间（新单元就新增一个片段文件）；已被其他会话认领的不碰。
3. 读该工作单元在 brief 中的入口条件；有未满足的，停下来告诉用户，不硬做。
4. 用一句话向用户确认本会话的目标和出口条件；需要时用 `/goal` 固定出口条件。
5. 会话命名：`one-<阶段>-<单元>-<动作>`，例如 `one-1a-identity-implement`（用 `/rename`），便于日后用 `claude --resume` 找回（用户 2026-10-14：新开会话用 `one-*` 前缀；已有的 `psa-*` 会话名与 `psa-coordinator` 暂不改）。

## 4. 收尾协议（结束前，或上下文接近上限时）

0. **只改片段，不直接编辑生成产物**（用户 2026-10-14：「一条记录一个文件 + ADR 拆开」）：`INTENT.md`、`SESSION_LOG.md`、`STATUS.md`、`adr/ADR-*.md`、`adr/README.md`、`MODERNIZATION_BRIEF.md` 都由 `python3 docs/modernization/build_all.py` 生成；改完片段后运行它。ADR、`adr/README.md`、brief 连同产物提交，CI 的「generated docs match fragments」一步会拦下不一致；`INTENT.md`、`SESSION_LOG.md`、`STATUS.md` 不入仓（用户 2026-10-14：「改：记录类产物不入仓，main 自动生成到只读分支 (Recommended)」），只提交片段，main 更新后由 `.github/workflows/generated-docs.yml` 发布到 generated-docs 分支。
1. 把本会话的决定（用户原话）用 `python3 docs/modernization/new_intent.py --session=<会话名> "<原话>" "<落点>"` 新增为 `intent/` 片段，并写进相应 ADR 的源文件 `adr/src/`。
2. 勾选 brief 中已满足的条件；不满足的不勾，不改写条件。
3. 用 `python3 docs/modernization/new_log.py <会话名> "<工作单元>"` 新增一条会话日志片段（模板见 §8），填好各项，写明下一条要运行的命令。
4. 更新本单元的 `status/units/` 片段：释放认领，标明单元状态（完成 / 部分完成 / 阻塞及原因）；新增或解除的阻塞项在 `status/blockers/` 中增删文件。
5. 需要时重新生成 brief 与 `REPORT.html`；（版本化之后）提交一次。
6. 清理临时目录；确认没有凭据原值出现在任何可共享文件中。
   本会话若改动了 ADR、规则评审、配置（DMN、编号、口径、政策参数）或迁移脚本，按 §12 自查：已采纳 ADR 只改了状态行；新 ADR 带四个必备小节；代码改动先有 `RULE_REVIEWS.json` 结论；Flyway 只新增文件；配置变更已登记版本与生效日期。
6a. 所有改动（含记录片段、运维中修正的脚本）都在本会话自己的 worktree 分支上提交并开 PR；不在主检出目录（仓库根）留未提交改动（用户 2026-10-15 对「子代理还是会话」评估的三条改进答「采纳」）。
7. 向调度会话 `one-coordinator` 发报告（格式见 §11「消息约定」：提交号与分支、产出文件、验证结果、未完成项、需要用户决定的事）。不论完成、部分完成还是阻塞，结束前都要报告（用户 2026-10-14：「新建会话结束后，应该向你报告结果」）。

## 5. 上下文管理

- **把大输出放进文件**：扫描结果、日志、生产查询结果写入文件，会话里只引用结论和路径。
- **探索交给子代理**：大范围读代码、复审、实测用后台子代理，主会话只保留结论。
- **老代码只作证据，不得照搬**（用户 2026-10-14：「三项都加」，起因：「新系统，为什么会采用旧写法？需要禁止 agent 使用旧代码？」）：
  - 老仓库（psa、A8、U8C 及其库表）只用于理解行为：抽规则、写规则卡与 file:line 引用、做行为等价判定。
  - 新代码只从规格、规则卡、ADR 与 terms.yaml 写起；不得复制老代码的片段、类结构、表结构、接口路径或命名（含 `psa_` / `system_` / `bpm_` 表名、`/admin-api/` 路径、yudao 包名与基类、拼音缩写）。等价靠以 RULE-id 命名的测试证明，不靠代码相似。
  - 守护：`LegacyShapeTest` 扫描新代码中的老系统标识，只有已批准的防腐层（A8 视图、过渡 / 合并待办视图）可例外，例外清单经评审。
  - 每一波脚手架或模块交付后，派一个 opus 复审子代理专查「老系统形状」（照搬的数据结构、接口形状、流程），结论写进该波报告。
- **代码注释能不写就不写**（用户 2026-10-14：「给 agent 一个写代码的规则，代码注释能不写就不写。」）：
  - 默认不写注释，用命名、类型和结构表达意图；能靠改名或抽方法说清的，就不写注释。
  - 只在「为什么」从代码看不出来时写一行：反直觉的约束、规范条款、外部系统的怪癖、性能或并发上的取舍。
  - 不写：复述代码在做什么的注释、变更历史、作者 / 日期、注释掉的代码、没有编号的 TODO、对显而易见参数的 Javadoc。
  - 业务规则的出处用以 RULE-id 命名的测试表达，不在实现里逐行注释规则卡。
  - 公开契约（各模块 `api` 包、OpenAPI）只写调用方必须知道而签名表达不了的约定。
  - 复审（含每波 opus 复审）把多余注释当问题提出。
- **写代码规则第二批**（用户 2026-10-14：问「第一批agent写完代码，看看有没有需要总结约束后续agent写代码行为的？」后选「全部采纳，并把能自动化的做成守护 (Recommended)」；第 11 条为用户追加）。每条附起因（第一批的实际问题）与守护：
  1. **复刻老行为以生产为证据，不凭推测**：老系统行为不确定时，先查生产数据或运行日志（只读），结论附证据再写规则卡与实现。起因：TIMESHEET 审批的串行 / 并行被误判。
  2. **不为通过测试而放宽或删除断言**：改动已有断言或删除测试必须写明理由，并在报告与 PR 模板「改动的断言 / 测试及理由」中单列。起因：`act_ru_task == 1` 的断言被放宽。
  3. **缺失或无效输入失败并告警，不静默跳过**：除非业务规则明确允许跳过，并在规则卡中写明。起因：G-1。
  4. **只实现当前阶段规格所需**：未来阶段的能力留在规则卡，不提前移植。起因：10 种指派类型被一比一移植。
  5. **新标识符、界面文字、表列名先查 `glossary/terms.yaml`**：查不到当场登记提议术语，不自造、不撞已有词（同一词不得表达两个概念）。起因：缩水保护、总部、待办重复、claim 被用作索赔。登记时中英文都查重：中文名、英文名在已批准与全部提议术语中各自唯一（起因：工时与审批各登记一套同义错误码，「未登录」两份，「离职」状态与事件同名）。守护：词表守护 G37–G39，以及提议与已批准合并后的中文名唯一检查（R-5）；前端界面文字接入词表守护由 1a 会话负责。
  6. **测试不写密钥字面量**：密钥、口令、令牌在测试运行时生成；报告前用与 CI 同版本的 gitleaks（8.30.1）扫全历史。守护：`.pre-commit-config.yaml`（提交前 gitleaks）与 CI gitleaks job。
  7. **测试只断言本模块的效果**：异步用确定性等待（事件或轮询到条件，带上限），不写宽泛的 `never()`。起因：OrgSnapshotSync 测试抖动。
  8. **契约先行**：接口路径、必填字段、表名变化时，OpenAPI 与架构文档在同一提交中更新。起因：`/api/1`、`required` 缺失、`audit_events` 文档漂移。守护：CI「OpenAPI contract unchanged」一步；PR 模板「是否同步了 OpenAPI 与架构文档」。
  9. **并行子代理同一基线出发**：整合前同步最新 main，整合提交重跑全部守护。起因：并行子代理漏改名。
  10. **建账号、起容器、对外调用前先问用户**：本机临时环境也一样（§7）。起因：Metabase 管理员账号被擅自创建。
  11. **能一开始做对的，不留到后续阶段**（用户 2026-10-14：「能从一开始就做对的，就不要留在后续阶段，除非后续做更有价值」）：任何推迟到后续阶段的工作（已知缺陷、守护、契约、用语、数据质量），须在规则卡或相应文档写明「为何后做更有价值」，否则当期做对。与第 4 条的分工：第 4 条限制的是**范围**（不提前做未来阶段的功能），本条约束的是**质量**（本期范围内的事不打折扣、不留尾巴）。
- **提议术语按批次清理**（用户 2026-10-15 对抽规则答「提议术语按批次清理」；起因：提议术语积压 338 条，已批准 348 条，其中中文名重复 5 组）：
  - 每批整合时，整合会话对本批新增的提议术语去重、归并（同义合并、同名改开），结果写进整合报告；
  - 提议术语积压超过 100 条，或阶段出口前，调度会话必须启动一轮用语确认；阶段出口不得留有未确认的会计类提议术语（ADR-0018）。
- **生产访问按对象授权**（用户 2026-10-15 对抽规则答「生产访问按对象授权」；起因：ADR-0029 取证时为取职级与兼岗关联了只读视图以外的底表，事后才说明）：
  - 请求生产只读访问时，写明要访问的视图 / 表、输出形式（只出计数或聚合、不出姓名与明细）与查询约束（走索引、语句超时）；
  - 执行中发现需要超出已授权对象，先停下请示，不先做后报；
  - 结果按「把大输出放进文件」处理，会话里只留结论。
- **Codex 派工**（用户 2026-10-15：问「比较消耗 token 的工作又适合 codex 的由他完成编码」后「用最合适的模型，你试试」；R-4 试点）：
  - 适合交给 Codex：规格写死、量大、机械、结果可客观验证的编码（批量改名、去默认值、按已定规则卡补样板与映射、照复审意见逐条改的小缺陷卡）。不交给 Codex：ADR、规格与流程梳理等设计工作；身份、授权、单人模式防线等安全改动；复审；验收测试。
  - 调用：在独立 worktree 中 `codex exec -m <模型> -c model_reasoning_effort=<强度> -s <read-only|workspace-write> --ephemeral -o <结果文件>`，显式指定模型（与子代理同一原则；当前用本机 Codex 目录中的主力编码模型 gpt-6.1-sol），不联网；提示词要求先读 `CLAUDE.md`（Codex 读仓库根 `AGENTS.md`，它指向同一套规则）与本文件 §5、§6.1。
  - 流程不变：卡由负责会话写，验收测试由测试代理先写，Codex 产出照常开 PR、过 CI，合并前 opus 复审；PR 正文注明「Codex 实现（模型、强度）」。
  - 记录每张 Codex 卡的返工轮次与耗时，与同类 sonnet 卡对比，结论写进调度台账，据此决定是否扩大。
- **子代理必须指定模型**（用户 2026-10-14：「派出子代理要指定最合适的模型，不要都默认，所有新会话都应该遵循」）：每次派子代理（`Agent` 工具，以及 Workflow 里的 `agent()`）都显式写 `model`，按任务难度选，不留默认：
  - `haiku`：机械性工作——按名称或模式查找文件、列清单、统计、格式转换、跑命令并汇总输出。
  - `sonnet`：常规工程——按骨架和规格写代码与测试、迁移单个模块、核对引用和链接、按模板生成文档、一般复审。
  - `opus`：需要判断的工作——架构设计与对抗性评审、安全审计、业务规则抽取与评审建议、行为等价判定、跨模块影响分析、拿不准该选哪个时。
  - 派工单和子代理提示中写明所选模型；同一类任务在本会话内保持一致。子代理定义文件自带 `model` 时也照此原则核对，不合适就在调用时覆盖。
- **压缩不可怕，丢状态才可怕**：会话自动压缩后只依赖摘要；所以收尾协议里的文件更新不能拖到最后一刻——每完成一个决定就写一次。
- **切换会话的信号**：一个工作单元完成；或者主题要换；或者上下文已经很长且后续需要大量新输入。此时走收尾协议，新会话从开场协议接上。

## 6. 并行

- 多个会话可以同时进行，但只在**互不相交的工作单元**上（不同 BC、不同阶段的不同步骤）。
- 写代码的并行会话各用自己的 git worktree 和分支（`feature/issue-{N}-…`），互不共享工作目录。不论写代码、写文档还是运维，都不在主检出目录工作。
- **子代理还是会话**（用户 2026-10-15 对「子代理还是会话」评估的三条改进答「采纳」）：边界清楚、交付一个 PR、需要用户拍板的事不超过一两件、数小时内完成的（运维执行、CI / 流水线、复审、文档整理、生产只读取证）派子代理；长期工作线、需反复问用户、需再派子代理并行或需主会话专属工具（如 DesignSync）的开独立会话。开发线开会话、会话内用子代理并行；调度会话用子代理做横向基础设施与复审。
- 共享记录按「一条记录一个文件」组织（`intent/`、`session-log/`、`status/`、`adr/src/`），各会话新增自己的片段、只改自己认领单元的文件，因此并行分支之间不再在同一文件上冲突；生成产物若冲突，取任一边后重新运行 `build_all.py` 即可，不要手工合并产物。
- **公共基础先行**（用户 2026-10-14 对 1a 大修原因分析的五条建议答「采纳」）：并行写业务之前，先由一个代理建好并冻结共用构件——聚合基类与版本模型、状态机、事件信封、错误链（领域异常 → ErrorCode → ProblemDetail）、前端共用包（API 客户端、错误码、共用模型）。功能代理只使用这些构件，不各自另造；需要改共用构件时停下报告，由整合者统一改。
- **小批复审**（同上）：每个代理交付后先单独做 opus 复审（§14、§14.1），通过后才整合；整合后再做一次整体复审。复审结论到达前不合并（调度会话合并规则）。
- 会话之间用 `ListAgents` / `SendMessage` 打招呼（例如「我改了 platform.identity 的 api，你那边需要重新编译」）。

### 6.1 修复批流程（用户 2026-10-15 对修复流程优化七条答「采纳」）

1. **开工前一次问清**：派修复批前，由复审或负责会话列出可能需要用户决定的点，调度会话一次问完再开工，不在修复中途逐个停下。
2. **派工前画归属图**：每个代理负责的表、权限码、事件、迁移号段、共享构件登记在派工单中；越界改动先报告再做。
3. **复审产出失败测试**：单独复审对每条 Blocker / High / Medium 尽量给出可复现的失败测试（测试名引用复审编号）；修复以测试转绿为准，测试保留为守护。
4. **复核按严重度分流**：Blocker / High 由 opus 复核；Medium / Low 由修复代理补测试、CI 通过即关闭，负责会话抽查并在报告中列出。
5. **滚动整合**：复审通过的代理立即并入整合分支，每并入一路跑全量测试与守护；后完成的代理在整合分支上解决冲突，不等全部完成再一次整合。
6. **测试范围**：修复循环中只跑受影响模块的测试；交付前与每次并入整合分支时跑全量。
7. **按难度选模型**：修复用 sonnet，复审用 opus，机械性复核（逐条核对是否已改）用 sonnet。
8. **验收测试与实现分开**（用户 2026-10-15 对「验收测试交独立测试代理写」答「需要」）：开工前由独立测试代理（`code-modernization:test-engineer`）从 `contract.md`、规则卡、ADR 与用户原话写验收测试（Given/When/Then，测试名引用 D 编号、RULE 编号或 intent），先提交；实现代理只让它们转绿、不得修改，认为测试有误时停下报告，由复审裁定后由测试代理改。单元测试仍由实现代理写。守护：实现代理的提交改动验收测试目录即 CI 失败（测试代理与复审裁定的提交除外，以提交说明中的裁定编号为准）。验收测试目录约定：后端 `backend/src/test/java/com/forcitis/one/acceptance/**` 与 `backend/src/test/resources/acceptance/**`（顶层 `acceptance` 包，按模块再分子包，如 `acceptance/platform/identity/`；经公开接口或 HTTP 黑盒断言，不碰模块内部），前端 `frontend/**/__acceptance__/**`（不含 `node_modules`）；改动其中文件的提交（合并提交按相对自动合并结果的人工改动算：解冲突、整体取一边都算，干净合并不算；章鱼合并一律要 trailer），说明的 trailer 块须含一行 `Acceptance-Test-Author: test-engineer`（测试代理）或 `Acceptance-Ruling: <裁定编号>`（复审裁定；编号形如 `RULING-12`，匹配 `[A-Z][A-Z0-9-]*-\d+`），带 `Acceptance-Test-Author` 的提交只能改验收测试目录，由 `scripts/ci/acceptance_guard.py` 检查，每个验收测试类须有 surefire / failsafe 报告，由 `scripts/ci/acceptance_reports.py` 检查。
9. **三类工作分批**（用户 2026-10-15 对「手术式精准小范围修复」答「采纳」）：缺陷修复、功能补做（应交付未做）、结构性重构（含改名）分开派工，不混在同一批或同一提交。
10. **缺陷修复手术式**：一张缺陷卡（复审编号、复现步骤、预计改动文件）对应一次最小改动加一个回归测试（测试代理先写失败测试）；提交只改卡上文件，改卡外文件先报告；不顺手重构、改名或统一风格；复核只看该卡改动与测试；一张或几张相关卡一个小 PR，复核通过即合入 main，不攒大整合分支。无法局部修的标「结构性」并写明理由，转重构批。
11. **整合复审后收口**：Blocker / High 合并前按手术式修完并由 opus 只复核这几条；Medium / Low 不阻塞合并，逐条登记进下一批派工单（测试代理先写失败测试）；新发现的「应交付未做」进下一批，涉及安全漏洞的本批先堵。

## 10. 中断与恢复

## 12. 变更治理（用户 2026-10-14）

用户原话：「把变更治理写进 SESSION_PLAYBOOK.md 和 adr/README.md：
1. 已采纳的 ADR 不改正文，改决定就新增 ADR，标明「取代 ADR-00xx」，旧 ADR 改为已被取代、正文保留。

3. 规则调整分三类：配置类（DMN、编号、口径、政策参数）按版本和生效日期生效、不追溯；代码类先改规则评审再改测试和实现，Flyway 只追加；ADR 类走架构评审。
4. 已过账事实不改，只能冲销重做。」

### 12.1 ADR：不改正文，用新 ADR 取代

- 已采纳的 ADR 正文冻结，只允许改状态行。决定上的任何变化（修订、补充、例外）都新增一份 ADR，在「取代」中写明「取代 ADR-00xx」或「取代 ADR-00xx 第 N 条」；同一提交中把旧 ADR 状态改为「已被 ADR-00yy 取代」或「已采纳（第 N 条已被 ADR-00yy 取代）」，正文保留。
- 状态集、取代写法、必备小节见 `adr/README.md`「ADR 生命周期与变更规则」。ADR 一律从源文件 `adr/src/ADR-NNNN.md` 由 `adr/build_adrs.py` 生成（经 `build_all.py`），不手改 `adr/ADR-*.md` 与 `adr/README.md`；生成器在状态不合法、新 ADR 缺必备小节、取代未同步标注时失败。
- 新 ADR 必须写**影响面、迁移方案、回滚方案、需同步修改的守护规则**；守护规则（ArchUnit、词表、DDL、前端 lint 等）与 ADR 采纳在同一个 PR 或紧随其后的 PR 中修改，ADR 中写明是哪一个。
- 过去用「修订稿」「Proposed revision」改 ADR 的做法停止；brief 的入口 / 出口条件仍按 brief 自身的约定追加 `Proposed revision:` 行（brief 不是 ADR）。

### 12.2 规则调整的三类

| 类别 | 范围 | 怎么改 | 记录在哪里 | 生效 |
|---|---|---|---|---|
| **配置类** | DMN 决策表（审批路由、科目映射、可计费性）、业务编号规则、经营口径、政策参数（费率、阈值、期限） | 新增一个版本，不覆盖旧版本；业务口径类须用户（会计口径须财务）批准 | 运行时：所属模块的版本表（版本号、生效日期、批准人、决定出处），只追加；文档：`CONFIG_CHANGELOG.md`（只追加：配置项、版本、生效日期、用户原话、关联规则 ID） | 按生效日期（会计期间对齐）对之后的业务日期生效，**不追溯**；已按旧版本产生的结果不重算，需要更正的按 12.3 冲销重做 |
| **代码类** | 领域规则、计算、校验、状态机、DDL | **先**在 `RULE_REVIEWS.json` 新增或修订该规则的评审结论（规则 ID、结论、用户原话），**再**改以规则 ID 命名的测试，**最后**改实现；brief §5 由 `rules/build_brief.py` 重新生成 | `RULE_REVIEWS.json`（结论）、测试名（规则 ID）、提交说明（引用规则 ID） | 随发布生效；数据库迁移 **Flyway 只追加**：已应用的脚本不得修改或删除（`flyway validate` 校验和守护），修正一律写新脚本 |
| **ADR 类** | 架构决策：模块边界、技术选型、跨 BC 契约、主干不变量 | 新 ADR（提议）→ `code-modernization:architecture-critic`（opus）对抗性评审，意见与处理写入 ADR 证据 → 用户批准 → 已采纳并同步标注被取代的 ADR | `adr/build_adrs.py` → `adr/`；用户原话入 `INTENT.md` | 采纳后生效；迁移与回滚按 ADR 中的方案执行 |

拿不准属于哪一类时按更严的一类处理（配置 < 代码 < ADR）。

**修订已有评审结论**：`RULE_REVIEWS.json` 条目的原字段 `verdict`、`at`、`title`、`note` 不改；决定变化时在该条目可选数组 `revisions` 末尾追加 `{verdict, at, note, quote, source}`（`quote` 为用户原话，`source` 为 ADR 编号或 intent 文件名的数组，至少一个）。当前结论取最后一条修订，`rules/build_brief.py` 在 brief 中标注「已修订」与出处。`rules/review_revisions.py` 校验：`at` 严格递增且不早于原 `at`、`verdict` 取值同原字段、`quote` 与 `source` 必填；`build_all.py --check` 另将原字段与 HEAD 及与 `origin/main` 的合并基点比对，原字段被改写、条目或已有修订被删改即失败（git 不可用时只告警）。

**首次部署前的迁移基线**（用户 2026-10-14 对 1a 大修原因分析的五条建议答「采纳」）：「已应用」指已在任一环境（dev、生产）执行过。在本系统首次部署任何环境之前，基线保持开放（用户 2026-10-15 对迁移基线写法答「开放期内直接改基线 (Recommended)」）：
  1. 先把已合入的迁移合并为每个 schema 一份基线迁移（纯合并，不改表结构），用两个空库分别执行合并前后的迁移，`pg_dump --schema-only` 对比 diff 为空，证据写进 PR，opus 复审确认。
  2. 开放期内，表结构改动直接改基线文件，不再追加迁移；每个这样的 PR 附「预期表结构 diff」——两个空库分别执行改动前后的基线，`pg_dump --schema-only` 的差异只能是 PR 声明的改动——由 opus 核对。
  3. `scripts/ci/migrations_immutable.py` 以仓库中的基线开放标记为准：标记存在时允许修改基线文件，标记不存在时任何已合入迁移的修改、改名、删除都失败；标记文件为 `backend/architecture/migration-baseline-open`。
  4. 首次部署 dev 前删除该标记（部署剧本 C-3 的第一步），此后恢复只追加。删除标记的变更须单独成 PR，同一变更里夹带任何迁移文件的修改、改名、删除或新增，CI 失败。

### 12.3 已过账事实只能冲销重做

已过账的明细事实不改不删（ADR-0016 第 2 条，数据库层禁止 UPDATE / DELETE）。更正的唯一路径是冲销：生成反向事实和新的过账序号，原行保留并双向关联，再按正确口径重做；关账后的更正落在开放期间并标注原期间。配置新版本、规则修正、数据迁移都不得回写已过账事实。

**D17 细则**（用户 2026-10-15：「哪些主数据要版本化，检查下一次性改到位，后续新主数据要版本化」）：
1. **判定**：每张表在数据访问注册表登记数据类别——交易、事实、审计、技术、主数据（被单据、事实或授权按 ID 引用的业务实体及其关系，如员工、组织单元、法人、客户、项目、授权关系）、参考数据（受控代码表，如职级、业务线、科目）、配置（参数、模板、决策表、日历、费率）。拿不准按更严的一类。
2. **默认版本化**，三选一：
   - 维度型：按 D6 写法（生效日 / 失效日左闭右开、`EXCLUDE USING gist` 防重叠、只追加、只许关闭不许改写、UUIDv7 主键），注册表写明生效依据是同步观察日（`OBSERVED`）还是业务声明日（`DECLARED`）；授权、身份绑定等按时刻检查的关系用 `timestamptz` 区间。
   - 配置型：按 D15 / §12.2（版本只追加、生效日、作者、确认人、确认时间、决定出处 `decision_ref`、不追溯）。
   - 不需要：在注册表写理由与出处，理由只限四类——只由迁移维护（git 即版本）；单一状态且审计能完整还原；安全凭据不得留历史；个人信息最小化只留当前值。豁免清单只减不增，新增须引用户 intent 或 ADR。
3. **列覆盖**：维度型当前表的每个非技术列，要么进版本表，要么在注册表逐列写不进版本的理由。
4. **一张版本表一个来源、一个负责人**：外部同步的列与新系统自有的列分表，不让两个来源写同一行。
5. **当前值**：外部快照保留同事务写入的当前投影并有一致性测试；新系统自有、可未来生效的，根表不存可版本化的列，按业务日期取当时有效版本；授权取未关闭的行；查询日期早于最早版本时失败告警，不回退到最早版本。
6. **使用方记版本**：单据或事实用到版本化配置（编号规则、日历、税率、费率、映射）时，保存所用版本的 ID（D7）。
7. **关系**：D6 / D15 规定形状，D17 规定哪些表必须属于其一，D16 规定标识；统一走 K-2 时态基座。§13「数据模型先行」的逐表打分加 D17 一栏，新阶段主数据在表结构 PR 中就做好版本化。
8. **已定口径**（用户 2026-10-15）：工作日历按配置型版本化，新版本「业务管理员四眼确认」；法人代码「禁止修改」，细化为「未发过号前可更正，发号后禁改」，更名只改名称走版本；客户与供应商「共用往来单位身份，角色分开」（1b 规格据此）。
