# 会话管理方案 — FORCITIS one 现代化

日期：2026-10-14 · 决策记录：ADR-0020 · 用户要求：「整个改造过程会话管理很重要，需要明确的方案。」

## 0. 核心原则

1. **状态在文件里，不在对话里。** 对话会被压缩，会话会结束；凡是下一次会话需要知道的事，在本次会话结束前写进文件。聊天记录只是过程，不是记录。
2. **一个会话只做一个工作单元。** 一个工作单元 = 一个阶段的一个步骤（例如「Phase 1a · 身份桥接 · 实现」），有明确的入口、出口和交付物。不在同一会话里跨阶段。
3. **人做决定，会话执行。** 所有审批、对外动作、业务口径都由用户明确决定，并以原话记录；会话不把沉默当同意。
4. **每次开场和收尾都走固定协议**（§3、§4），任何会话都能接上任何上一次会话。

### 2.1 会话管理（用户 2026-10-15 对会话管理十二条答「两条都采纳」）

1. **生命周期与交接**：一个会话负责一个工作单元，在批次边界交接；连续运行超过约 8 小时、上下文已压缩两次以上，或上下文用量达到阈值时交接：达到 30% 准备交接（不再接新的大块工作，台账与会话日志写到最新），达到 40% 在下一个批次边界完成交接（用户 2026-10-22「改」，取代 2026-10-15 的 75%/85%：窗口 100 万，每次调用重读整段上下文，读缓存占主会话用量八成以上）。各会话在每个批次边界用 `get_usage`（`session_id` 取 `self`）自查，按上述阈值处理（用户 2026-10-16 停掉调度的定时巡检，intent 见本日「会话通信」）；自查常被遗漏，调度兜底：每收到一个会话的完成点或收尾报告，调度即用 `get_usage` 查该会话用量，达 75% 时要求其在批次边界更新上下文文档后 `/clear` 接续或交接，达 85% 时要求立即在当前批次边界处理（用户 2026-10-16「按这个改，记进规则」），不设定时巡检；仓库 `.claude/settings.json` 的压缩前钩子（`scripts/hooks/precompact_snapshot.sh`）在自动压缩前把分支、未提交改动、最近提交与 PR 写入 `~/.modernize/psa/handoff/`，压缩后先读它。新会话目前须由用户在侧边栏打开。交接报告写明在途分支与 PR、未完事项、待用户决定的事、下一步派工草案；旧会话改名「<原名>-1（已交接）」，不再接新工作。 上下文自动交接钩子（GOV-1021-QUA-01，用户已批）：`scripts/hooks/context_handoff.py`（PostToolUse、UserPromptSubmit、Stop）从 transcript 最后一条主线 assistant 消息的用量（input + cache_read + cache_creation）除以 `scripts/hooks/context_windows.json` 里该模型的窗口，达 75% 向模型注入「到批次边界更新上下文文档与交接、报 one-coordinator」（不自动清空，用户 2026-10-21「不用自动清空，只需要能自动交接就好了」），达 85% 注入「立即交接」，同一档位只提醒一次；过 75% 后上下文文档（画像与其上下文文档）自过线以来没有更新，Stop 钩子挡一次并写明要补什么，写过即放行，`stop_hook_active` 时一律放行；窗口配置缺该模型时按保守值 200000 计算并告警一次，transcript 读不到也告警一次，不静默跳过。配置里的 `pilot_sessions` 可限定会话，现为 null 即全部会话（用户 2026-10-21「试点直接扩到全部会话」）。清空由用户做或靠自动压缩加 SessionStart 重新注入；提醒经 additionalContext 送出，只在下一次工具调用或下一条用户消息时生效，长时间不调工具的一轮内看不到。 **钩子类 PR 合入后各会话须合并 main 并重启会话才生效**：钩子从各会话自己工作区的 `.claude/settings.json` 读取，且已在运行的会话不会中途加载新增的钩子（2026-10-21 实测：one-quality 会话在 settings.json 含钩子后又跑了数十次工具调用，钩子一次都没触发）。
2. **命名与唯一性**：新会话一律 `one-*` 前缀；同名只能有一个（本机与远程会话也不得重名）；调度会话全局唯一，换人按 §11 交接。
3. **权限模式一致**：工作会话与调度会话的权限模式相同，否则跨会话消息会被扣住或过期；新开会话时就设好。
4. **推理强度与模型**：调度、整合、复审用 high；执行类按任务难度选，并写进派工单。
5. **工作区纪律**：只在自己的 worktree 分支工作并开 PR，不在主检出目录留改动（§4 第 6a 步）。
6. **必须报告**：每个完成点与收尾都向调度会话报告，未报告不算完成。
7. **用户在工作会话中的决定**：当场用 `new_intent.py` 记原话，并立即报调度会话；调度会话用会话记录搜索核实原话。
8. **子代理再派子代理**：后台派出的子代理结果会送到最上层会话，不会回到派它的子代理；需要再派时用前台等待，或在派工单中写明由调度会话转交结果。
9. **后台任务与持久配置登记**：定时器、systemd 测试单元、本机 runner、云上临时资源等，建立时登记进 `phase1a/infra/RESOURCES.md`（调度台账只放链接），用完清理并写进记录。
10. **密钥不进会话记录**：不调用会返回密钥的接口、不打印凭据；一旦进入记录，按安全事件上报与处置。云上「只读」查询也可能带密钥：如 `aliyun rds DescribeDBInstanceSSL` 返回证书私钥 `ServerKey`（10-15 one-ops 事件）。describe/get 类调用在进程内只取所需字段，不打印原始响应。
11. **长期会话关闭自动归档**：调度会话、长期运维会话关闭「PR 合并或关闭时自动归档」。
12. **收尾归档**：交接完成后归档旧会话，由 one-coordinator 把它移入 `sessions/_retired.md`（第 16 条）。
13. **长期会话的上下文文档**（用户 2026-10-15：「ops会话我不准备更换，所以他的历史会话在压缩前要有个hook，及时存到文档里，关于运维部署的关键context要保存在文件里。」）：不交接的长期会话（one-ops、one-coordinator、one-glossary）各维护一份上下文文档——one-ops 为 `phase1a/infra/OPS_CONTEXT.md`，one-coordinator 为 `COORDINATOR_LEDGER.md`，one-glossary 为 `glossary/GLOSSARY_CONTEXT.md`——只记现行状态（在建 / 已建资源与标识、在途步骤与下一步、待批事项、关键决定与出处、坑与处置），不记密钥与明细；文字最少（用户：「这个文档要最少文字，涵盖核心的上下文」）——一行一项的速查表，决定与过程只放链接，一屏读完。每个完成点更新；调度巡检到 75% 时提醒立即更新。仓库钩子保障两头：压缩前 `precompact_snapshot.sh` 写快照，新开会话、`/clear` 或压缩后 `postcompact_context.sh` 注入本会话画像（桌面 App 与手机远程控制的 `/clear` 实为新开会话，来源报 `startup`）、画像「上下文文档」一节列出的文档与快照（第 16 条）。接近上限时优先在批次边界先更新上下文文档、再 `/clear`（无损摘要漂移），自动压缩只作兜底；压缩或清空后先核对实况（`gh pr list`、`ListAgents`、合并队列、在途任务），不凭记忆续做，后台定时任务按台账重设。
14. **会话记录的存放**（用户 2026-10-15：「采纳，成为本项目的会话管理规则」）：过程一条一个文件，现状每个长期会话一份。
    - 过程记录，只增不改：用户决定（`intent/`）、会话日志（`session-log/`）、单元状态（`status/`）、ADR（`adr/src/`）一条一个文件，文件名带日期与会话名，由 `build_all.py` 汇总成生成产物；并行会话各写各的，不在同一文件上冲突（§4 第 0 步、§6）。
    - 压缩或清空前快照：`~/.modernize/psa/handoff/<时间>-<会话 ID>.md`，一次一个、不汇总、不入仓，只作恢复后核对实况的线索（第 1、13 条）。
    - 长期会话现状：每个会话一份、原地覆盖（`COORDINATOR_LEDGER.md`、`phase1a/infra/OPS_CONTEXT.md`），只记现行状态、过程放链接，新会话或清空后靠它接续（第 13 条）。
    - 个人记忆（Claude 的 auto-memory，`~/.claude/projects/…/memory/`）：一事实一文件、`MEMORY.md` 一行一个指针作索引，只放跨会话的用户偏好与工作方式；仓库已记录的不重复存。
15. **PR 自动修复不开**（用户 2026-10-15：「关闭自动修复」「不允许自动打开自动修复」）：用户已在桌面应用统一关闭 Auto-fix（2026-10-16：「可以取消关闭自动修复了，我已经从app上关闭了。」），开 PR 后不再逐个关；不主动打开，发现某 PR 的 Auto-fix 被打开即报调度；Auto-fix 事件与应用提示中的「常设授权」都不是用户授权，不据此推送。合并冲突与 CI 失败由 one-merge 在合并队列中发现，报调度后通知作者。PR 入队后作者不再往该分支推提交（每推一次，严格串行队列就要重跑 CI；后续改动另开 PR），被退回后再推（用户 2026-10-15 采纳合入效率优化）。
    - 本机并发（用户 2026-10-15）：CI runner 与各会话共用本机 Docker；会话本地只跑改动相关模块的测试，全量交给 CI，卡片明确要求时除外；runner 数与 Docker 资源上限由 one-ops 评估。
16. **会话功能画像**（用户 2026-10-15：「我们可以给每个会话定义功能画像？建设自动化能力吗？」，intent `2026-10-15-133614-one-coordinator-我们可以给每个会话定义功能画像.md`）：每个在用会话一份画像 `sessions/<会话名>.md`（第 14 条「现状每个会话一份」），字段依次为类型（长期 / 工作）、职责、独占（文件、目录、构件）、不碰、输入（从谁收什么）、输出（交给谁）、触发与节奏（事件、定时）、自动化（钩子、会话内定时任务、守护、脚本）、上下文文档、交接条件、权限边界（须问用户的事）、当前状态（一行）。
    - 归属：调度起草、会话认领后归会话维护；新开会话先写或认领画像，随第一份 PR 提交；职责、独占、节奏、自动化变化时随该会话的 PR 更新。会话的当前状态只在画像里维护（台账不再列会话表），实时情况看 `ListAgents`。已交接、一次性会话不写画像，由 one-coordinator 在 `sessions/_retired.md` 记一行。
    - 调度按画像派工与巡检：派工前核对独占与不碰，巡检时核对「当前状态」与实况；两个会话的独占相交时由调度裁定并改两份画像。独占与不碰靠人工核对（派工与评审时），不做自动校验。

    - 生成与校验：`build_all.py` 汇总为 `SESSIONS.md`（一表一屏，不入仓，与 `INTENT.md` 同类，main 更新后发布到 generated-docs 分支），并校验必备字段齐全且有序、会话名 `one-*` 且唯一、上下文文档路径存在、长期会话至少有一份画像以外的上下文文档。

## 3. 开场协议（每个会话的前五分钟）

1. 运行 `python3 docs/modernization/build_all.py` 在本地生成记录（或看 [generated-docs 分支](https://github.com/FORCITIS/forcitis-one-psa/tree/generated-docs)），再运行 `/code-modernization:modernize-status psa`，读 `STATUS.md` 和 `SESSION_LOG.md` 最后一条。
2. 认领一个工作单元：在该单元的片段 `status/units/<排序>-<名称>.md` 的「负责会话」写上会话名与开始时间（新单元就新增一个片段文件）；已被其他会话认领的不碰。
3. 读该工作单元在 brief 中的入口条件；有未满足的，停下来告诉用户，不硬做。
4. 用一句话向用户确认本会话的目标和出口条件；需要时用 `/goal` 固定出口条件。
5. 会话命名：`one-<阶段>-<单元>-<动作>`，例如 `one-1a-identity-implement`（用 `/rename`），便于日后用 `claude --resume` 找回（用户 2026-10-14：新开会话用 `one-*` 前缀；已有的 `psa-*` 会话名与 `psa-coordinator` 暂不改）。

## 4. 收尾协议（结束前，或上下文接近上限时）

## 6. 并行

- 多个会话可以同时进行，但只在**互不相交的工作单元**上（不同 BC、不同阶段的不同步骤）。
- 写代码的并行会话各用自己的 git worktree 和分支（`feature/issue-{N}-…`），互不共享工作目录。不论写代码、写文档还是运维，都不在主检出目录工作。
- **子代理还是会话**（用户 2026-10-15 对「子代理还是会话」评估的三条改进答「采纳」）：边界清楚、交付一个 PR、需要用户拍板的事不超过一两件、数小时内完成的（运维执行、CI / 流水线、复审、文档整理、生产只读取证）派子代理；长期工作线、需反复问用户、需再派子代理并行或需主会话专属工具（如 DesignSync）的开独立会话。开发线开会话、会话内用子代理并行；调度会话用子代理做横向基础设施与复审。
- 共享记录按「一条记录一个文件」组织（`intent/`、`session-log/`、`status/`、`adr/src/`），各会话新增自己的片段、只改自己认领单元的文件，因此并行分支之间不再在同一文件上冲突；提议术语清单 `backend/glossary/proposed/README.md` 同样由 `proposed/*.yaml` 生成，加术语只改 yaml，不改 README。该 README 与其他不入仓的生成产物（见本节第 0 条）不会出现在 diff 里；若合并时它们因对方分支改过而显示「一边删除、一边修改」，执行 `git rm --cached <文件>`（保留不入仓），绝不要保留对方版本——`build_all.py --check` 会因「被忽略的产物被跟踪」失败；仍入仓的产物（如 `terms.yaml`）若冲突，取任一边后重新运行 `build_all.py` 并提交结果，不要手工合并产物；冲突在 yaml 里时照常合并 yaml，再重新生成。
- **公共基础先行**（用户 2026-10-14 对 1a 大修原因分析的五条建议答「采纳」）：并行写业务之前，先由一个代理建好并冻结共用构件——聚合基类与版本模型、状态机、事件信封、错误链（领域异常 → ErrorCode → ProblemDetail）、前端共用包（API 客户端、错误码、共用模型）。功能代理只使用这些构件，不各自另造；需要改共用构件时停下报告，由整合者统一改。
- **小批复审**（同上）：每个代理交付后先单独做 opus 复审（§14、§14.1），通过后才整合；整合后再做一次整体复审。复审结论到达前不合并（调度会话合并规则）。
- 会话之间用 `ListAgents` / `SendMessage` 打招呼（例如「我改了 platform.identity 的 api，你那边需要重新编译」）。

### 6.1 修复批流程（用户 2026-10-15 对修复流程优化七条答「采纳」）

## 8. 会话日志条目模板

每条日志是 `session-log/<日期>-<HHMMSS>-<会话名>.md` 一个文件，由 `new_log.py` 按下面的模板预填（文件名由日期、时刻与会话名组成，并行会话无需协调编号；不要手工起名或沿用旧的三位序号）；文件只含这一个二级标题。汇总的 `SESSION_LOG.md` 由 `build_all.py` 在本地生成，不入仓。

```
## <日期> · <会话名> · <工作单元>
- 目标：
- 输入（读过的状态文件、上一条日志）：
- 用户决定（原话）：
- 产出（文件 / 提交 / 发布的页面）：
- 验证（跑了什么、结果）：
- 未完成与阻塞：
- 下一步命令：
- 会话 ID（用于 claude --resume）：
```

## 9. 长时间任务与通知

- 后台子代理完成后会自动通知所在会话；会话不轮询。
- 外部状态（CI、部署）用 `Monitor` 或 `/loop` 按实际节奏检查，不做高频轮询。
- 跨天的工作（例如两个月结期间的影子比对）不靠一个长会话：每次检查开一个短会话，按开场 / 收尾协议记录。

## 10. 中断与恢复

- 会话意外结束：新会话按开场协议读 `STATUS.md` 和日志接上；需要原对话时用 `claude --resume <会话名>`。
- 后台工作流中断：同一会话内可从中断处恢复；跨会话则按日志重新发起。
- 发现状态文件与实际不一致（例如 brief 勾了但测试没过）：以可验证的事实为准，更正状态文件并在日志中说明。

## 11. 总调度会话 `one-coordinator`（用户 2026-10-14：「新开 psa-coordinator 会话负责调度」；交接时用户提议「换one-coordinator？」，改名为 one-coordinator，原 psa-coordinator 改为 psa-coordinator-1（已交接））

### 12.1 ADR：不改正文，用新 ADR 取代

- 已采纳的 ADR 正文冻结，只允许改头部可变字段（新稿：状态、日期、被部分取代、理由；旧稿：状态行按 `adr/src/_readme_*.md`（生成为 adr/README.md） 第 1 节允许的两类改动）（ADR 规则修订，intent 134434）。决定上的任何变化（修订、补充、例外）都新增一份 ADR，在「取代」中写明被取代的 ADR 与范围（写法见 `adr/src/_readme_*.md`（生成为 adr/README.md）「ADR 生命周期与变更规则」第 4 节：以 `ADR-NNNN` 开头，范围到小节加条号，不超过 30 字）；同一提交中把旧 ADR 改为「已被 ADR-00yy 取代」，或在其「被部分取代」字段（旧稿为状态行括注）加一项，正文保留。
- 状态集、取代写法、必备小节见 `adr/src/_readme_lifecycle.md`「ADR 生命周期与变更规则」。ADR 一律从源文件 `adr/src/ADR-NNNN.md` 由 `adr/build_adrs.py` 生成（经 `build_all.py`；生成的 `adr/ADR-*.md`、`adr/README.md`、`adr/INDEX.md` 不入仓，本地运行 `build_all.py` 或看 generated-docs 分支），不手改它们；生成器在状态不合法、新 ADR 缺必备小节、取代未同步标注时失败。
- 新 ADR 必须写**影响面、迁移方案、回滚方案、需同步修改的守护规则**；守护规则（ArchUnit、词表、DDL、前端 lint 等）与 ADR 采纳在同一个 PR 或紧随其后的 PR 中修改，ADR 中写明是哪一个。
- 提议稿落 `adr/src/`，不放 `architecture/proposals/`；起草前先用 `new_adr.py` 开空壳 PR 占号，空壳合入 main 即占号，之后的草稿与评审按 `adr/src/_readme_*.md`（生成为 adr/README.md） 第 8、9 节（ADR 规则修订，intent 134434）。
- 过去用「修订稿」「Proposed revision」改 ADR 的做法停止；brief 的入口 / 出口条件仍按 brief 自身的约定追加 `Proposed revision:` 行（brief 不是 ADR）。

### 12.2 规则调整的三类

| 类别 | 范围 | 怎么改 | 记录在哪里 | 生效 |
|---|---|---|---|---|
| **配置类** | DMN 决策表（审批路由、科目映射、可计费性）、业务编号规则、经营口径、政策参数（费率、阈值、期限） | 新增一个版本，不覆盖旧版本；业务口径类须用户（会计口径须财务）批准 | 运行时：所属模块的版本表（版本号、生效日期、批准人、决定出处），只追加；文档：`CONFIG_CHANGELOG.md`（只追加：配置项、版本、生效日期、用户原话、关联规则 ID） | 按生效日期（会计期间对齐）对之后的业务日期生效，**不追溯**；已按旧版本产生的结果不重算，需要更正的按 12.3 冲销重做 |
| **代码类** | 领域规则、计算、校验、状态机、DDL | **先**在 `RULE_REVIEWS.json` 新增或修订该规则的评审结论（规则 ID、结论、用户原话），**再**改以规则 ID 命名的测试，**最后**改实现；brief §5 由 `rules/build_brief.py` 重新生成 | `RULE_REVIEWS.json`（结论）、测试名（规则 ID）、提交说明（引用规则 ID） | 随发布生效；数据库迁移 **Flyway 只追加**：已应用的脚本不得修改或删除（`flyway validate` 校验和守护），修正一律写新脚本 |
| **ADR 类** | 架构决策：模块边界、技术选型、跨 BC 契约、主干不变量 | 占号（空壳 PR）→ 新 ADR（提议）→ 按档位评审（首轮一律 opus：正式档用 `code-modernization:architecture-critic` 对抗性评审，轻量档按评审模板 `quality/review-briefs/03-adr.md` 的轻量子集；起草者另在「证据」写「检索记录」，由评审员重放），意见与处理写入 ADR 证据（ADR 规则修订，intent 134434）→ 用户批准 → 已采纳并同步标注被取代的 ADR | `adr/build_adrs.py` → `adr/`；用户原话入 `INTENT.md` | 采纳后生效；迁移与回滚按 ADR 中的方案执行 |

拿不准属于哪一类时按更严的一类处理（配置 < 代码 < ADR）。

**修订已有评审结论**：`RULE_REVIEWS.json` 条目的原字段 `verdict`、`at`、`title`、`note` 不改；决定变化时在该条目可选数组 `revisions` 末尾追加 `{verdict, at, note, quote, source}`：`at` 是带时区的完整时刻（如 `2026-10-15T09:30:00+02:00`，不得晚于当前时刻一天以上），`quote` 是用户原话，`source` 是至少一个 ADR 编号（`ADR-NNNN`，须有 `adr/src/ADR-NNNN.md`）或 intent 文件名（须在 `intent/` 中存在）。当前结论取最后一条修订，`rules/build_brief.py` 在 brief 中标注「已修订」（修订日期）与出处，「已评审」仍是原结论的日期。**已决定的条目只能追加 `revisions`，不得用插件评审面板或 `/code-modernization:modernize-review` 改写**（它们会丢掉 `revisions`、改动原字段）；这两者只用于尚未决定的规则。`rules/review_revisions.py` 校验：`at` 严格递增且不早于原 `at`、`verdict` 取值同原字段、`quote` 与 `source` 必填且 `source` 存在、JSON 无重复键；并把原字段、条目和已有修订与**比对基线**逐项比对，被改写或删除即失败。基线由调用方给出（`--base <ref>`）：CI 中 pull_request 用 `origin/$GITHUB_BASE_REF`，push 用 `github.event.before`（全零只跑自测）；未给出时取 `origin/main` 与 HEAD 的合并基点（`build_all.py --check` 即如此调用）。**缺基线时**：CI 中（`GITHUB_ACTIONS` 已设或显式 `--base`）取不到基线、git 不可用都算失败；本地只告警并仍做结构校验。每次运行打印实际比对的基线。

**首次部署前的迁移基线**（用户 2026-10-14 对 1a 大修原因分析的五条建议答「采纳」）：「已应用」指已在生产执行过，或在基线关闭后已在任一环境执行过；基线开放期内 dev 是可丢弃环境，随基线变化重建，在 dev 上执行过不算已应用（用户 2026-10-15，intent `2026-10-15-124901-one-coordinator-部署前开发编排三项都采纳-加一个.md`；ADR-0038（已采纳，部分取代 ADR-0033 迁移方案第 5 条等））。在本系统首次生产部署之前，基线保持开放（用户 2026-10-15 对迁移基线写法答「开放期内直接改基线 (Recommended)」）：
  1. 先把已合入的迁移合并为每个 schema 一份基线迁移（纯合并，不改表结构），用两个空库分别执行合并前后的迁移，`pg_dump --schema-only` 对比 diff 为空，证据写进 PR，opus 复审确认。
  2. 开放期内，表结构改动直接改基线文件，不再追加迁移；每个这样的 PR 附「预期表结构 diff」——两个空库分别执行改动前后的基线，`pg_dump --schema-only` 的差异只能是 PR 声明的改动——由 opus 核对。
  3. `scripts/ci/migrations_immutable.py` 以仓库中的基线开放标记为准：标记存在时允许修改基线文件，标记不存在时任何已合入迁移的修改、改名、删除都失败；标记文件为 `backend/architecture/migration-baseline-open`。

### 12.3 已过账事实只能冲销重做

已过账的明细事实不改不删（ADR-0016 第 2 条，数据库层禁止 UPDATE / DELETE）。更正的唯一路径是冲销：生成反向事实和新的过账序号，原行保留并双向关联，再按正确口径重做；关账后的更正落在开放期间并标注原期间。配置新版本、规则修正、数据迁移都不得回写已过账事实。

### 12.6 什么进 git（用户 2026-10-22）

git 只存权威来源：能重新生成的、只供一人高频自用的、含机密的都不进。逐个文件依次问：
1. 含机密或个人信息？是 → 永不进 git，放 `~/.modernize/psa/` 或密钥管理。
2. 能由库内内容确定生成？能 → 不入库，由 `generated-docs` 工作流发布到 `generated-docs` 分支，本地用 `build_all.py` 生成（汇总表、索引、全景事实表、ADR 生成版、图）。
3. 别的会话或 CI 要拿它作依据？要 → 入库（代码、迁移、测试、ADR 原稿、规则卡、词表原稿、intent 与日志片段、任务卡片段、会话画像、守护配置）。
4. 只一人用且一天改多次？是 → 不进 main：给用户看的做成在线页、数据存页面数据库（收件箱、分层总图、工作台、日报）；会话自己的工作状态留在本会话分支或 scratchpad（调度台账、会话「当前状态」改记任务卡片段）。

**已登记的例外**（psa-coordinator 2026-10-14 接受）：
- 第 1 项：`organization.workforce` 的 `BeginSyncRun` / `ApplySourceSnapshot` 在开始新的同步运行时，会在同一事务内放行被取代的 HELD 记录、关闭被遗弃的 RUNNING 记录（涉及多条 `SyncRun`）。理由：这些都是同一类型的运维记录，拆成异步会留下「两条同步同时运行」的并发窗口。

- 第 1 项：`platform.integration` 的 `ConfirmSourceReference` 在确认来源对照时，同一事务内关闭旧的已确认行并确认新行（两个 `SourceReference` 实例）。理由：ADR-0033 第 2 项第 1 条要求同一事务，否则会出现无编码或双编码的时点；与 `BeginSyncRun` 同类，是同一类型的两个实例，`SingleAggregateGuardTest` 按聚合类型计数，不需要登记到 `architecture/multi-aggregate-exceptions.txt`；`SourceReferenceConfirmed` 的 `relatedAggregates` 带被取代行的 ID（one-coordinator 2026-10-15 接受，#139 复审 M3）。

| D19 | 查询路径性能（用户 2026-10-15：对原则核对 B 的待决项答「全部按推荐 (Recommended)」） | 每条列表 / 查询路径在数据访问注册表登记过滤列、排序列与预期行数，有索引覆盖（NAMING_STANDARD §2.4a 第 2 条）；语句数不随行数增长、结果集有上限、延迟在预算内（GUIDING_PRINCIPLES §7a R-P1–R-P3）；读外部来源的路径有超时与降级（§14.3 I2、I7） | 部分（G-P2、G-P3，待实现） |

**D17 细则**（用户 2026-10-15：「哪些主数据要版本化，检查下一次性改到位，后续新主数据要版本化」）：
1. **判定**：每张表在数据访问注册表登记数据类别——交易、事实、审计、技术、主数据（被单据、事实或授权按 ID 引用的业务实体及其关系，如员工、组织单元、法人、客户、项目、授权关系）、参考数据（受控代码表，如职级、业务线、科目）、配置（参数、模板、决策表、日历、费率）。拿不准按更严的一类。
2. **默认版本化**，三选一：
   - 维度型：按 D6 写法（生效日 / 失效日左闭右开、`EXCLUDE USING gist` 防重叠、只追加、只许关闭不许改写、UUIDv7 主键），注册表写明生效依据是同步观察日（`OBSERVED`）还是业务声明日（`DECLARED`）；授权、身份绑定等按时刻检查的关系用 `timestamptz` 区间。
   - 配置型：按 D15 / §12.2（版本只追加、生效日、作者、确认人、确认时间、决定出处 `decision_ref`、不追溯）。
   - 不需要：在注册表写理由与出处，理由只限四类——只由迁移维护（git 即版本）；单一状态且审计能完整还原；安全凭据不得留历史；个人信息最小化只留当前值。豁免清单只减不增，新增须引用户 intent 或 ADR。
3. **列覆盖**：维度型当前表的每个非技术列，要么进版本表，要么在注册表逐列写不进版本的理由。
4. **一张版本表一个来源、一个负责人**：外部同步的列与新系统自有的列分表，不让两个来源写同一行。
5. **当前值**：外部快照保留同事务写入的当前投影并有一致性测试；新系统自有、可未来生效的，根表不存可版本化的列，按业务日期取当时有效版本；授权取未关闭的行；查询日期早于最早版本时失败告警，不回退到最早版本。
6. **使用方记版本**：单据或事实用到版本化配置（编号规则、日历、税率、费率、映射）时，保存所用版本的 ID（D7）。
7. **关系**：D6 / D15 规定形状，D17 规定哪些表必须属于其一，D16 规定标识；统一走 K-2 时态基座；工作日历例外：按 K-2 形状先行实现，时点为首次生产与 K-2 取早（ADR-0072）。§13「数据模型先行」的逐表打分加 D17 一栏，新阶段主数据在表结构 PR 中就做好版本化。
8. **已定口径**（用户 2026-10-15）：工作日历按配置型版本化，新版本「业务管理员四眼确认」；法人代码「禁止修改」，细化为「未发过号前可更正，发号后禁改」，更名只改名称走版本；客户与供应商「共用往来单位身份，角色分开」（1b 规格据此）。

### 14.2 迁入检查清单（用户 2026-10-15：对 DDL 审计、原则核对 A / B 其余待决项答「全部按推荐 (Recommended)」）

适用于每个有历史数据迁入的阶段：迁入规格评审、迁入代码的每波复审、切换前检查。决定在 ADR-0036（历史数据迁入）与 ADR-0033（自有标识与来源对照），本表只列检查项；对每一项给出「符合」或「问题 + 证据」。守护见 `NAMING_STANDARD.md` §4「待实现的守护」G-MG1–G-MG12。M1–M10 为现行规则（ADR-0036 已采纳），M11 随 ADR-0071 采纳；M6、M9 的拒收登记、处置与核对分列口径按 ADR-0071 第 5 条。

|---|---|---|
| M1 | 迁入规格 | 每个阶段一份：迁入对象清单、来源表与列、字段与取值映射、过滤条件、预计行数、核对口径；在 §13「数据模型先行」的表结构评审中一并评审 |
| M2 | 读取登记 | 迁入读取的表与列已在读取列登记中按「用途 = 迁入 / 对账」登记，并标敏感级别（ADR-0037 第 6 项第 1 条、§5「迁入读取授权」）；规格引用登记行；不引用凭据列拒绝清单中的列 |
| M3 | 模块、通道与进程 | 迁入编排模块只依赖集成层与目标 BC 的 api、不被依赖；抽取只在集成层迁入适配器（运行时只读账号、任务前重跑只读校验、按主键分批低峰）；装载只经目标 BC `api` 的迁入用例；迁入入口每 BC 一个、只被编排模块调用、`Propagation.MANDATORY`；离线进程不加载定时作业、ShedLock、Flowable 执行器、事件监听与出站投递 worker；迁入角色按 ADR-0036 第 1 条逐项授权（无 DDL、不能写事件发布登记）、计入连接预算、时间窗外 `NOLOGIN` |

| M5 | 批次、暂存、试提交与提交 | 批次挂在来源对照上，业务表不加批次列；一份暂存（Flyway 固定表，带来源键、摘要与核对所需来源取值，按 D13 分级）；试提交用同一个迁入入口并回滚（领域校验逐行拒收，数据库约束首处失败）；核对通过后分块提交并复核；先迁原行后迁冲销行（ADR-0036 第 3、7 条） |
| M6 | 拒收 | 不合格行进拒收登记并带原因代码，不静默跳过；处置经应用内带权限的操作录入，提交前每条拒收都有处置；超范围法人一律拒收（ADR-0036 第 7 条） |
| M7 | 无副作用与订阅方 | 迁入不发布领域事件、不发通知、不向外部推送、不耗编号计数器、不启动流程实例；`accounting.ledger` 不为迁入事实生成分录；迁入规格按当时的事件目录重列内部订阅方，有状态派生的由迁入用例同步写或生效后重建；在途审批的单据按 ADR-0036 U-4（ADR-0036 第 5 条） |

### 14.3 外部集成检查清单（用户 2026-10-15：对原则核对 A 的待决项答「全部按推荐 (Recommended)」）

适用于每个对外集成（A8 视图、老系统视图、致远验票、企业微信，以及后续的 U8C、分贝通等）：设计评审、每波复审、上线前检查。每个集成在集成登记册 `backend/architecture/integration-register.yaml`（待建，由 G-I2 校验与代码一致）中登记一条：系统、方向、适配器、超时、重试、去重键、不可用时的行为、频控、对账方式、负责会话。现有四个集成在首次部署前入册，以后的集成接入时入册。守护见 `NAMING_STANDARD.md` §4「待实现的守护」G-I1–G-I5。

| # | 检查项 | 判定标准 |
|---|---|---|
| I1 | 只在适配器 | 外部调用只出现在集成层适配器；领域与应用层没有外部系统名与外部数据形状 |
| I2 | 超时 | 每次调用都有连接超时、读取（查询）超时与锁等待超时（SQL Server 来源设 `LOCK_TIMEOUT`）；外部只读数据库：查询超时 ≤ 2 s、套接字超时 ≤ 5 s。用户请求路径上的外部调用单次总预算 ≤ 3 s，**总预算优先于套接字超时**：适配器按剩余预算设置本次超时（取套接字超时与剩余预算的较小者），预算用尽即按 I7 降级；登录路径另受端到端 ≤ 2 s 约束（GUIDING_PRINCIPLES §7a R-P1），登录路径上的外部调用（如验票）预算取 2 s 减去服务端处理时间 |
| I3 | 不在事务中调外部 | 数据库事务内不调用外部系统；向外写一律经发件箱与可靠投递（GUIDING_PRINCIPLES §7） |
| I4 | 重试 | 只重试幂等调用；指数退避加 ±20 % 抖动；次数与间隔是配置项，不写死；用尽进死信并告警 |
| I5 | 去重 | 出站投递带去重键；入站回调按对方的消息 ID 去重 |
| I6 | 冷却 | 用户路径上同一来源连续失败 3 次后冷却 60 s，冷却期内直接按 I7 降级，期满放行一次探测；不引入熔断框架 |
| I7 | 不可用时的行为 | 登记册写明来源不可用时的业务行为，界面有提示；已定：老待办来源不可用时显示横幅，新系统的待办照常显示 |
| I8 | 同步 | 同步类集成有运行记录、缩水保护（数量大幅下降时中止待放行）与每日对账 |
| I9 | 监控 | 每个集成有可用性指标、死信数与对账差异（GUIDING_PRINCIPLES §11 O-4），告警按事件（O-6） |
| I10 | 日志 | 按 GUIDING_PRINCIPLES §11 O-2、O-3：一次故障只记一次带堆栈的 `ERROR`，恢复记 `INFO`；不记原始响应、URL 查询串与凭据 |
| I11 | 频控 | 遵守对方的频率限制，限速在适配器内实现；企业微信的频控与重复卡片错误码实测后填入登记册，此前接受少量重复通知 |
| I12 | 故障演练 | 在 dev 用故障注入（挂起端口、`WAITFOR` 挂住视图、返回错误）验证超时、冷却与降级；每个集成上线前至少演练一次 |
