- 请补的内容（按附录 A 填；下面是我从契约读出的、一定要回答的点，不是设计，设计由卡作者写）：
  1. **表与出处（B1、B2、B4）**：自定义部门明细表（角色 × 部门 × 是否含下级）、待调整权限表（含敏感角色复核、范围复核两类、维持与到期字段）各对到信息图 OBJ 与聚合；找不到 OBJ 的回 one-architecture 补，不自行建表。基线现有 `roles` / `role_permissions` / `account_roles` / `authorization_requests`，没有角色版本表；契约写「改明细即新增角色版本」（ADR-0034 第 5 项），卡须说明版本表是新建还是本卡前置，历史如何还原（ADR-0034 第 4 项第 5 条）。
  2. **状态与事件（B3a）**：待调整权限 `status` 的 `CHECK` 取值（OPEN、UPHELD、EXPIRED、ADJUSTED、CLOSED_BY_SEPARATION；来源②「部门恢复在用时条目关闭」契约写「取值规则卡未定」，须先定）↔ 审计动作（upheld / expired / regenerated 等）↔ 状态机 ↔ Java 枚举一一对应，事件目录同步。
  3. **不变量 → 约束（B5、O4）**：至少这些要落到约束或写无法落的理由：来源①②与 `kind` 的列取值互斥（范围复核无业务负责人、无有效至；敏感角色复核 UPHELD 时业务负责人与有效至必有，成对 CHECK）；两种去重键（人 × 触发同步运行 × 触发字段；原条目 × 有效至；角色 × 部门）各是一个唯一约束；双人逐人级角色不得含「含下级」是跨表规则，写承担者（应用校验 + 守护）；业务负责人不得为当事人本人（跨行，写承担者）。
  4. **业务键与时态（O3、O6）**：自定义部门明细的业务唯一（同一角色版本内同一部门最多一行）；类别（配置还是主数据）与版本化方式按 D17 细则选，不用「当前表覆盖写」。
  5. **引用（O5）**：部门 ID 引用 workforce 快照，跨 schema 不建外键；悬空（部门停用、合并）靠 RULE-387 的范围复核兜底，卡写明不建外键的理由与兜底。展开范围是读时按当前快照算（契约 1a），不存展开结果。
  6. **查询路径（O10 / D19）**：待调整权限列表（按收件人 / 状态 / 分页，K-3a）、每日到期作业（`status='UPHELD' and uphold_expires_at <= now`，预期行数小，评估部分索引）、按（角色，部门）找引用该部门的在用角色版本（RULE-387 每次同步用）、部门可见范围过滤。每条写过滤列、排序列、行数、分页、索引。
  7. **个人信息与自由文本（C4）**：`reason`、业务负责人员工 ID、条目详情「不含权限码与范围」都是自由文本 / 引用，写允许写入内容清单；业务负责人员工 ID 的访问级别与是否个人信息标记；审计 `detail`（`grant.refused`、`upheld`、`expired`、`regenerated`）的允许内容。
  8. **注册表与分级（C2、C3、C5）**：新表登记 role、mutability、retention（D12，待调整权限的保留期须有出处，未定的登记待决）、lineage、writers、readers；`permission-grant-modes.txt` 登记 `organization.workforce:employee:read` 为 `INDIVIDUAL`（DA-13，与「守护文件单独提交」一致）；读取方包括组织数据管理员、安全审计员、新部门负责人（凭「条目给他」）——读者清单须与契约第 16 条一致。
  9. **法人与期间（O13）、横切（O14）**：待调整权限是否带法人 ID（若不带写理由）；`created_at` 等时间列由注入时钟写，不用 `DEFAULT now()`；到期有效至是 `timestamptz`（Asia/Shanghai 季度首日换算为 UTC 存储）。
  10. **适用 ADR 条款对照（O15）**：ADR-0026 第 1、6 项、ADR-0032 第 1–5 项、ADR-0034 第 3–5 项、ADR-0043（分级）、ADR-0044 第 1–3 项，逐条对到预期 diff 或「不适用（理由）」。
  11. **分析事实、基线 / 目标 / 过渡（A、T）**：无分析事实则写一行理由；基线开放期改基线，写明随库重建。
