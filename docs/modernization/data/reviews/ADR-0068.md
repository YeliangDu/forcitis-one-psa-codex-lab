## 第 1 条　人事命令表 `personnel_commands`——退回补 DDL（材料不全）

已写部分通过：UUIDv7 主键；同一员工同一生效日至多一条待生效的部分唯一索引（`(employee_id, effective_date) WHERE status IN ('PENDING','HELD')`）；`applied_at` 当且仅当 `EFFECTIVE`；只追加触发器（拒 DELETE、TRUNCATE，种类、员工、生效日不可改，状态只前进）。需补与改的：

1. **业务内容列没写**：「带类型的可空列、每种命令配 CHECK」要给出清单，否则无法审。我建议的形状：`command_kind`（HIRE、REGULARIZE、TRANSFER、LEAVE_WITHOUT_PAY、SEPARATE、REINSTATE，后两个未批的先不写进 CHECK，B7）；`employee_id`（同 schema 外键）；调岗与入职、复职需要的 `target_org_unit_id`、`target_position_id`、`target_reports_to_employee_id`（同 schema 外键）、`is_fee_earner`；各种类的必填/必空用一条 `ck_personnel_commands_<kind>_columns`。
2. **命令表不得存个人信息列**：入职命令的姓名、性别、邮箱若放在命令行里，命令表只追加、禁删，个人信息就无法按 ADR-0043 R-2 与「离职满 180 天置空」清除。入职命令应只引用同事务创建的员工根行（个人属性写 `employees` 当前值），命令行不带 `display_name`、`email`、`gender`。
3. **状态机与事件对应（B3a）**：`PENDING→EFFECTIVE|WITHDRAWN|HELD`、`HELD→EFFECTIVE|WITHDRAWN`；`HELD` 只允许离职种类（`ck_…_held_kind`）；事件只在 `EFFECTIVE` 和 `HELD` 发（`SeparationHeld`、`SeparationHoldReleased`），`WITHDRAWN` 与录入只写审计——请在 ADR 写明这是有意的「转换无事件」，并在注册表登记。命令表有状态列，ADR-0058 要求本 schema 有 `state_transitions`（或登记例外），我建议建（命令是员工异动的第一手记录）。
4. **跨行规则的承担者（B5）**：「离职命令之后不得再录更晚的命令」「按生效日顺序执行」不是单行约束，写明由应用在锁住员工根行后校验，并有行为守护；不要指望库层。
5. **查询路径与索引（O10）**：调度作业取到期命令 `status = 'PENDING' AND effective_date <= :today`（部分索引）；按员工取命令列表（外键索引 `employee_id`）；`created_by` 等跨 schema 账号 ID 只存不建外键。
6. **补登与更正与 W2 的冲突**：第 1 条 4 写「生效日早于受影响版本的起始日时拒绝」。但**补登前史**（例如迁入写了一条初始版本，人事要把真实入职日补到它之前）正是「补登落回真实日期」要支持的场景，字面规则会拒绝它。请改为：生效日**落在某个已有版本的区间内部**（该版本起点之后）才拒绝；落在最早版本之前或版本之间的空档，允许写前史版本，其结束日取下一版本起点；更正已有版本走 W2 第 1 节的同日修订（先关为空区间再追加），那条延后的「跨版本更正」触发条件就是本设计签发，可解除。
7. **转正没有落点**：命令种类有「转正」，但员工状态只有在职/离职（及待批的停薪留职），没有试用/转正阶段，命令执行后不改变任何数据——按 B7 不写进 CHECK；请 one-architecture 定转正要存什么事实（例如 `regularized_on` 或在职阶段 `PROBATION/REGULAR`），定了我再扩 W2 的 `employee_versions`。
8. **岗位命令的归属**：第 4 条只说组织单元命令另建表，岗位只做新建与停用，没说岗位命令进哪张表。`position_versions.change_command_id` 需要一个外键目标：请定岗位命令是并入 `personnel_commands`（不合适——它不属员工聚合）还是另建 `position_commands`。
9. **保留期**：与员工记录相同（随引用存续，十年上限由用户定），登记进注册表；无个人信息列（意见 2）则无需 R-2 处理。

## 第 2 条　`separation_holds`——需修改后通过

1. 通过项：UUIDv7 主键、`personnel_command_id` 唯一且同 schema 外键、无 CASCADE、放行列只能由空变非空一次、拒 DELETE 与 TRUNCATE、`version` 乐观锁。
2. **`employee_id` 是冗余列**（由命令确定）：用复合外键 `(personnel_command_id, employee_id) → personnel_commands (personnel_command_id, employee_id)` 保一致（命令表加对应唯一约束），不然两处可不一致。
3. **不要建「暂停原因」列**：只有 `ADMINISTRATOR_SEPARATION` 一个取值，按 B7/CS-1.8 不写单值列；将来出现第二种暂停原因时无损追加。
4. **状态双源**：`separation_holds.status` 与命令 `HELD/EFFECTIVE/WITHDRAWN` 重复。要么删 `status` 列用命令状态推出，要么保留并写成对 CHECK 与同事务更新；我建议**保留 `status` 并加行为守护**（放行/撤回在同一事务写两处），因为列表查询按暂停状态过滤更直接。
5. **放行列成对 CHECK**：`released_at`、`released_by`、`release_reason`、`release_channel` 同空同非空；`RELEASED` 当且仅当 `released_at` 非空；`INTERFACE` 渠道 `released_by` 必填，`OPERATIONS_COMMAND` 渠道的操作人与见证人是自报员工 ID（ADR-0043 U-7b 例外），不进该列、记在审计；`release_reason` 长度 1–500 非空白，列入 C4 允许写入清单并按 `uphold_reason` 先例标 `PI`。
6. 权限：运行角色保留 UPDATE（放行写一次）、回收 DELETE 与 TRUNCATE（同版本表的 §4b 一项）。
7. 次序与预检（C 预检、D2 的 DO 块断言行数为 0）属非 DDL 要求，我认可；基线开放期直接改基线，D2 的断言只在关闭后需要。

## 第 12 条　来源对照封存——需修改后通过

1. **「至多一行」的写法**没给：用单例列实现——`singleton boolean NOT NULL DEFAULT true`，`CONSTRAINT ck_source_reference_seals_singleton CHECK (singleton)`，`CONSTRAINT uk_source_reference_seals_singleton UNIQUE (singleton)`，比触发器计数简单可靠。
2. **操作人列类型**：`sealed_by`、`witnessed_by` 是运维命令自报的员工 ID（ADR-0043 U-7b、FU1-1 裁定），写成 `sealed_by_employee_id`、`witnessed_by_employee_id`（跨 schema，只存 ID），加 `CHECK (sealed_by_employee_id <> witnessed_by_employee_id)`；`decision_ref` 文本长度 1–200 非空白，写入内容清单只允许 intent 文件名或决定编号（C4）。
3. 触发器：封存表拒 UPDATE、DELETE、TRUNCATE；`source_references` 的 `BEFORE INSERT OR UPDATE` 触发器检查封存表存在行即抛 `restrict_violation`。通过。性能：封存表至多一行，检查廉价。DELETE 已被拒（IG:213-222），保持。
4. 注册表：封存表 `data_category: 技术`、`APPEND_ONLY`、永久；`source_references` 的 `mutability` 登记不改，但注释写明「封存后全表只读」。
5. 封存命令的前置检查（无 `PENDING`、无未终结迁入批次）是应用逻辑，批次表尚未建，命令代码依赖 ADR-0036 迁入卡，不在表结构范围；DDL 无依赖，通过。

## 第 14 条　审计主体种类登记表——需修改后通过

1. 表形状（我建议，供 ADR 采用）：`platform_audit.audit_subject_kinds`：`audit_subject_kind_id uuid` 主键；`code text` 唯一，格式 `^[A-Z][A-Z0-9_]{0,49}$`；`owner_module text`（登记属主）；`status text`（`ACTIVE`、`RETIRED`）；`effective_from_date date`；`retired_on date`；`(status = 'RETIRED') = (retired_on IS NOT NULL)`；`created_at`/`updated_at`。数据类别：参照数据。
2. **`audit_entries.subject_kind` 如何指向登记表**：外键 `(subject_kind) → audit_subject_kinds (code)`（分区表引用非分区表可行），取代 AU:11 的 CHECK 常量串。外键不检查状态，所以「退休后新写入被拒」需要**行为守护 + 应用校验**（`SYNC_RUN` 退休后断言无写入方，ADR 第 14 条 2 已写），不要用触发器给每条审计插入加开销。
3. **谁能写登记表**：运行角色只有 SELECT；新增种类走迁移，退休走迁移或运维命令（`UPDATE status = 'RETIRED'`，由空变非空一次的触发器放行，拒 DELETE 与 TRUNCATE）。
4. 种子：基线迁移把 AU:11 现有取值全部插入登记表（`SYNC_RUN` 在 D2 先合并的情形直接以 `RETIRED` 入表，第 14 条 2 已写）。
5. 已有审计条目只追加不改（D8），引用的登记行永不删除。
6. 与 ADR-0066 决定 4 第 5 条的关系（平台自有种类留审计内部）由 one-architecture 在第 14 条第 5 点已裁定，我不再判。

## 跟进意见（2026-10-21，W2 设计第 3 版与改后复核带出）

1. **请 ADR-0068 第 1 条 3 增加命令种类 `CORRECTION`（更正）**：W2 设计的补登与更正靠 `superseding_command_id` 引用命令表，现有六个种类里没有纯更正的位置。`CORRECTION` 即时执行，不受「同一员工同一生效日只能一条待生效」的限制；是否发事件：更正使「截至今天」的状态变化时发布（暂名 `EmployeeCorrected`，载荷 `personnelCommandId`、`employeeId`、受影响区间），只改历史则只写审计。详见 `W2_EMPLOYEE_POSITION_VERSIONING_DESIGN.md` 第 10 节 5。
