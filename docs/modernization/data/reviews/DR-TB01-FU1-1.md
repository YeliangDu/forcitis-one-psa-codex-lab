## 数据设计裁定：DR-TB01-FU1「员工存在」的语义（FU1-1）

- 裁定：one-data，2026-10-17，应 one-coordinator 要求（#405 独立复审留的第二件）
- 问题：运维证明的操作人、见证人「须为存在员工」，是否要求该员工有任职。现实现 `OrgDirectory.findEmployee` 的查询联接 `assignments`，等于从未有任职的员工算不存在（实现者为此在夹具 `ensureAttestors` 里补了组织单元与两条在职任职，RULING-DR-TB01-FU1-1）。
- 裁定：**存在 = `organization_workforce.employees` 里有该 ID 的行；不要求有任职，也不要求在职。**
  - 理由：该检查的目的是审计里的操作人 / 见证人事后能解析出姓名（原卡「阅读时再解析姓名」）；员工行在快照里保留，离职员工同样可点名，实现注释已写「Separated employees still count」，对从未有任职的员工取不同口径没有依据；任职是否存在不属于「这个 ID 是不是一个人」。
  - 影响：运维证明是紧急通道，可能在组织数据尚不完整（员工行已有、任职未同步）时使用；要求任职会让它在最需要时失效（此处为设计推断，未对照上线顺序核实，上线顺序由施工方案定）。
- 实现要求（小卡，交 one-1a-next-5，随下一个涉身份的 PR；不阻断 #405，因 #405 的行为是更严的一侧，不会放过不存在的 ID）：存在性检查改为只查 `employees` 行（读取走 workforce 的对外接口，不联接任职）；夹具 `ensureAttestors` 补任职可保留，不得再成为通过的必要条件；加一例：员工行存在、无任职 → 通过。该例属验收新增，由测试代理按 `Acceptance-Ruling` 加。
- 影响面：不改表，不改约束；无数据设计门禁项。
- 结论：语义裁定如上；实现对齐前，卡 `DATA-REPAIR-timesheet-audit.md` 的 DR-TB01-FU1 条以本页为准（合集合入后由该卡正文加一行指向本页）。
