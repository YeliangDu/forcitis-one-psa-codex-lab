日期：2026-10-14

## 1. 总览：每个框架管什么

| 框架 | 核心思想（一句话） | 在本项目中回答的问题 | 主要落点 |
|---|---|---|---|
| **TOGAF** | 从基线架构到目标架构，经过一系列过渡架构，在治理下逐步演进 | 怎么分阶段走、谁批准、怎么不跑偏 | INTENT → ASSESSMENT（基线）→ STACK_DECISION（目标）→ BRIEF 各 Phase（过渡架构）→ 守护与审批（实施治理） |
| **DDD** | 按业务边界划分模型，用统一语言命名，复杂度留在模型内部 | 模块怎么切、叫什么、谁依赖谁 | 一个 BC = 一个 Modulith 模块 = 一个 PG schema；词表 `03-通用语言.md`；聚合、值对象、领域事件；防腐层 |
| **BPMN** | 用标准图形描述「谁在什么时候做什么」，流程可执行、可版本化 | 审批怎么建模和执行 | Flowable 8（`platform.approval` 模块，ADR-0007）执行 BPMN；流程只编排人工步骤、超时、退回 |
| **DMN** | 把业务决策写成决策表，与流程和代码分离，可由业务审阅 | 审批路由、级别、资格判定放在哪里 | Flowable DMN 引擎执行决策表；决策表随代码版本化，用表驱动测试覆盖 |
| **DAMA-DMBOK** | 数据是资产：要有所有者、质量规则、元数据、主数据和生命周期治理 | 数据归谁、质量怎么保证、迁移怎么验证 | 每张表一个所有者（BC）；逐列所有权矩阵；约束即质量规则；对账查询；主数据来源清单；数据分级与脱敏 |
| **OLTP** | 交易处理要规范化、事务短、约束强、并发安全 | 业务库怎么设计 | 各 BC schema 采用第三范式；事务以聚合为边界；乐观锁；`CHECK` / `NOT NULL` / 唯一约束 |
| **OLAP** | 分析与交易分离，分析用面向主题的维度模型和历史快照 | 报表、BI、月结分析放在哪里 | `reporting` schema / 现有 BI-olap：事实表 + 维度表，由事件或 CDC 构建；报表不在交易表上跑 |

## 3. DDD：边界、语言、模型

**战略设计**
- **限界上下文 = 模块 = schema**：模块路径为 `<子域>.<BC>`，schema 为 `<子域>_<BC>`（ADR-0003）。完整对照见 GLOSSARY.md §1，例如：
  - `presales.quoting` → 商机评估与报价承诺 BC
  - `delivery.execution` → 项目交付执行 BC
  - `cost.timesheet` → 工时与投入有效性 BC
  - `cost.costing` → 项目成本归集 BC
  - `receivables.wip` → WIP 与开票准入 BC
  - `expense.spend` → 费用报销与支出管控 BC
  - `accounting.ledger` → 财务总账与法定核算 BC
  - `platform.identity`、`platform.approval`、`platform.integration`、`platform.audit`、`platform.numbering` → 权限流程与集成平台 BC 的技术模块
- **上下文映射 → 依赖方向**：`architecture/module-dependencies.txt` 就是上下文映射的代码形态，由 `ModuleDependencyTest` 强制执行，修改需评审；Modulith 保证只能经 api / events 访问。
- **统一语言**：`03-通用语言.md` 是唯一词源，代码、表、事件、API 都从它派生（`NAMING_STANDARD.md`）。
- **防腐层**：A8、U8C、分贝通、企业微信、KM 各有独立的 integration 模块。老系统在过渡期也被当作一个外部系统，通过防腐层读取和反向同步。

**战术设计**
- **聚合**是一致性边界：一个用例一个事务，一个事务只改一个聚合。跨聚合、跨模块的协作用领域事件，实现上用 Modulith 事件发布登记表。
- **值对象**：自校验、不可变（守护 G21–G24）。
- **领域事件**：过去式，只描述已发生的事实（G29）。
- **规则放在领域层**：315 条规则卡中的计算、校验类规则，落在 `domain` 的聚合方法和值对象里；路由、资格判定类决策落在 DMN（见 §5）。
- **深模块、窄接口**：每个模块只有 `api` 和 `events` 两个出口（G1–G6）。

## 4. BPMN：流程只编排人，不计算业务

- **Flowable 8 在 Phase 1 引入**（用户决定），作为 `platform.approval` 模块的内部实现：
  - 引擎表放在 `platform_approval` schema；
  - 业务模块只依赖 `platform.approval::api`（G19）；
  - 已实测 Flowable 8 + Boot 4.1 + PG17，引擎表 100% 落在 `platform_approval` schema。
- **流程负责**：步骤顺序、人工任务、会签 / 或签、超时催办（定时边界事件）、退回发起人、撤回截止点、转交。
- **流程不负责**：
  - 计算金额和毛利；
  - 直接查业务表（禁止 join 业务 schema）；
  - 调用外部系统（走防腐层）；
  - 在脚本任务里写业务逻辑。
- **流程模型是代码**：`.bpmn20.xml` 放在 `platform.approval` 模块的资源目录，随版本发布，有测试。在途实例按「排空」策略处理：新提交走新版本，旧实例在旧版本上走完。
- **人物流程用 BPMN 协作图记录**：工时填报、报价到预算、差旅、月结这 4 条流程，作为业务验收的对照。

## 5. DMN：决策与流程、代码分离

**1a 不引入 DMN**：审批指派写在 BPMN 扩展属性，由 `AssigneeResolver` 计算；出现真正的多维决策表时在该阶段引入（REIMAGINED_ARCHITECTURE 评审 #9/#15）。下文是 DMN 的适用范围，不是 1a 的交付内容。

**适合用 DMN 的**：输入少、规则成表、业务需要能看懂并调整的「判定」。规则卡中的典型例子：

| 决策 | 规则卡来源 | 决策表形态 |
|---|---|---|
| 预算是否需要 CEO 终审（预算毛利 ≥ 报价毛利则跳过） | 交付域 `budgetGmNotBelowQuote` | 输入：两个毛利；输出：`needsCeoApproval` |
| 工时行由谁审批（项目行 → PM；OH 行 → 直属上级；售前 → 部门负责人） | 工时域审批人分配规则 | 输入：行类型；输出：审批人角色 |
| ETC 调增是否需要审批（预测人工成本是否超出预算） | 交付域 ETC 规则 | 输入：是否超支、是否自建包；输出：`needsApproval` |
| 商机能否填工时（渠道 S/M、赢单 90 天窗口） | 工时域可填报范围规则 | 输入：岗位渠道、关闭状态、天数；输出：`allowed` |
| 审批是否允许本人审批，否则升级给上级 | 审批域防自审规则 | 输入：流程、是否本人；输出：升级规则 |

**不用 DMN 的**：带累加、取整、分摊的**计算**，例如 OH 分摊、WIP 余额、费率 × 工时。这类计算写在 Java 领域层的值对象和聚合里，用单元测试覆盖。

**落地方式**：
- Flowable 自带 DMN 引擎，决策表与 BPMN 一起放在 `platform.approval` 模块，或放在所属 BC 的资源目录里。
- 每张决策表都有对应规则卡 ID 的表驱动测试。
- 路由所需的标志，由所属模块算好后以类型化的 `routingFlags` 传给审批（模板中的 `ApprovalRequest` 已实现）。

## 7. OLTP：交易库要短、准、稳

- 每个 BC 的 schema 用第三范式；表名和列名由词表派生（`NAMING_STANDARD.md`）。
- 事务以聚合为边界，并且短：不在事务里调用外部系统、发 HTTP 请求或跑批量计算。外部调用走发件箱和可靠投递。
- 并发控制：聚合带 `version` 列做乐观锁。批处理互斥用作业表租约，即 `(legal_entity_id, period, job_type)` 上的唯一约束，代替 Redis 锁或 advisory lock。
- 约束优先于代码校验：`CHECK` 存枚举名，金额和币种成对（ADR 硬约束），schema 内外键齐全。
- 交易表上不跑报表。列表查询只用索引覆盖的分页，禁止内存分页和全表扫描（这些是老系统的问题）。
- 大表（成本台账、WIP 变动）按期间分区。

## 8. OLAP：分析与交易分离

- **分析模型**：`reporting` schema（或现有的 BI-olap 系统）采用星型模型：
  - 事实表：工时条目、成本台账分录、收入确认、WIP 变动、凭证分录；
  - 维度：项目、合同条款、人员、部门、法人、期间、成本类型。
- **构建方式**：由领域事件（Modulith 事件发布登记表）或 CDC 增量构建。月结时生成期间快照，老系统已有 WIP 期间快照的做法，延续下来。
- **BI 只读 `reporting`**：过渡期 `reporting` 视图的形状与老表一致，BI 的迁移只是 SQL 方言的移植，而不是重建模型。
- **利润 L3、WIP 汇总、项目绩效看板**这类重报表，从分析模型读取，不在交易表上实时计算。
- 先用 PG 物化视图满足需要；数据量或并发上来之后，再迁到列式库（与现有 BI-olap 合并）。

## 9. 测试策略：最少的测试，最大的覆盖

| 层级 | 定位 | 写法 | 数量原则 |
|---|---|---|---|
| **模块级集成测试（主力）** | 一次走通 HTTP → 鉴权 → 用例 → 领域 → 跨模块 api / 事件 → Flowable / DMN → 真实 PostgreSQL | `@SpringBootTest` / Modulith `@ApplicationModuleTest` + Testcontainers PG17；不 mock 自己的模块，只用 WireMock 隔离外部系统 | 每个用例 1 条正常路径，加上每条 P0 规则的关键分支；测试名带规则 ID |
| **单元测试（补边界）** | 纯领域逻辑：值对象不变式、计算、DMN 决策表 | 等价类 + 边界值 + 参数化（从规则卡的 Given/When/Then 直接生成用例） | 只补集成测试覆盖不到的分支，用最少的用例覆盖最多的分支 |
| **契约测试** | OpenAPI 契约；反向同步写入老表的结构；BI 查询在切换后仍能运行 | 生成的客户端编译通过；对老库执行 BI SQL | 每个桥接表和 BI 查询各一 |
| **端到端（必要时）** | 4 条人物流程和登录鉴权冒烟 | Playwright（仓库已有 `e2e/`） | 只覆盖跨系统、跨前后端的关键路径 |
| **架构测试** | 守护 G1–G33 和前端 F1–F13 | ArchUnit、Modulith、ESLint | 每条规则一个测试 |

**度量门槛**：
- JaCoCo 对 domain 和 application 统计**全部测试层级的合计覆盖率**：行覆盖 ≥ 80%，分支覆盖 ≥ 70%；
- P0 规则 100% 有对应测试；
- 可选：对 domain 包跑 PIT 变异测试，检查测试是否真的能发现错误，而不只是执行到代码。

**实测**：模板工程用 11 个集成测试 + 5 个值对象单测，行覆盖率 85.9%（分支 67.9%）。说明以集成测试为主，少量测试就能覆盖大部分代码，剩余缺口用最少的单测补齐。

## 9a. 权责发生制业财一体（贯穿七个框架，ADR-0016）

弗思特以 AEC 项目为业务基础，FORCITIS one 的核心是权责发生制下的业财一体。七个框架在这一点上的落点：

| 框架 | 在权责发生制主干上的落点 |
|---|---|
| DDD | 业务 BC 只产生经营事实，不认识会计科目；`operations.facts` 是唯一的过账管道；`accounting.period` 独占期间状态；WIP 与开票是同一个一致性边界 |
| DMN | 科目映射、可计费性判定、审批路由写成决策表（收入确认口径已由 ACC-R01 定为产出法 · 客户价值确认，不做方法选择），由财务评审、按版本生效 |
| BPMN | 审批流程只决定「谁同意」；同意之后产生什么事实、记哪个期间，由领域和 DMN 决定 |
| DAMA | 明细事实只追加：更正只能冲销（反向事实 + 新序号 + 双向关联），关账后的更正落在开放期间并标注原期间；对账等式（归集守恒、合同资产滚动恒等式 F113、借贷平衡）作为数据质量规则 |
| OLTP | 过账在一个事务内完成校验、分配序号、写事实；期间校验以 (期间, 法人) 为粒度 |
| OLAP | KPI 与报表按 OAT（`08-FORCITIS Operating Accounting Taxonomy.md`）原语声明口径；月结生成期间快照；分析侧只读 |
| TOGAF | 法定账在本期仍由 U8C 承担；FORCITIS one 自任法定账（蓝图 DD-6）、跨法人结算、集团合并作为后续过渡架构 |

**权责事实全部在新系统**（用户 2026-10-14：「确保权责业务事实全部在新系统」）：凡按权责发生制需要确认的业务事实——合同签订与变更、交付与产值确认、工时与成本、费用、收入确认、开票与应收、回款、分包与应付、付款——其记录系统（system of record）一律是 FORCITIS one，并经 `operations.facts` 过账。致远 A8 等外部系统不得作为这些事实的产生地或存放地：在 OA 上发起或审批的此类流程必须迁入（不归入「视情况」），跨库读取 A8 得到的此类数据必须改为新系统自有事实。U8C 作为法定账只接收新系统推送的结果，不反向产生权责事实。每个阶段的出口条件须证明本阶段涉及的权责事实没有遗留在老系统或 OA。

## 10. 强类型

| 层 | 措施 | 守护 |
|---|---|---|
| Java 领域 | 类型化 ID（`TimesheetId`、`TaskPackageId`、`UserId`）；值对象（`Money`、`Hours`）；状态枚举；用 sealed interface 表达结果（`SubmissionResult`），由调用方用 `switch` 穷尽处理 | G21–G24、G32、G16、G17 |
| 模块契约 | `api` / `events` 只用 record、enum、类型化 ID；禁止 `Map<String, Object>` 和 `Object` | G2、G3、G32 |
| 权限 | `Permission` 枚举 + 编译期常量，杜绝手写权限字符串 | G28 |
| HTTP | 请求 / 响应 record；API 带版本号 `/api/v1/...`（已实测）；请求体不得携带身份字段 | G20、G33 |
| 数据库 | 状态存枚举名 + `CHECK`；金额 `numeric` + 币种；行直接映射为值对象（`JdbcClient` 手写映射，不用反射 ORM） | 集成测试 |
| 前端 | TypeScript strict（含 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`）；类型由 OpenAPI 生成；禁止 `any` | F 系列 lint |
