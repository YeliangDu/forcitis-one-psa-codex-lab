## 3. DDD：边界、语言、模型

**战略设计**
- **限界上下文 = 模块 = schema**：模块路径为 `<子域>.<BC>`，schema 为 `<子域>_<BC>`（ADR-0003）。完整对照见 GLOSSARY.md §1，例如：
  - `presales.quoting` → 商机评估与报价承诺 BC
  - `delivery.execution` → 项目交付执行 BC
  - `cost.timesheet` → 工时与投入有效性 BC
  - `cost.costing` → 项目成本归集 BC
  - `receivables.wip` → WIP 与开票准入 BC
  - `expense.spend` → 费用报销与支出管控 BC
  - `accounting.ledger` → 财务总账与法定核算 BC
  - `platform.identity`、`platform.approval`、`platform.integration`、`platform.audit`、`platform.numbering` → 权限流程与集成平台 BC 的技术模块
- **上下文映射 → 依赖方向**：`architecture/module-dependencies.txt` 就是上下文映射的代码形态，由 `ModuleDependencyTest` 强制执行，修改需评审；Modulith 保证只能经 api / events 访问。
- **统一语言**：`glossary/terms.yaml` 是唯一词源，代码、表、事件、API 都从它派生（`NAMING_STANDARD.md`）。
- **防腐层**：外部系统（A8、U8C、分贝通、企业微信、KM）集中在 `platform.integration` 集成层，防腐层只在此处（ADR-0039）。老系统在过渡期也被当作一个外部系统，通过防腐层读取和反向同步。

**战术设计**
- **聚合**是一致性边界：一个用例一个事务，一个事务只改一个聚合。跨聚合、跨模块的协作用领域事件，实现上用 Modulith 事件发布登记表。
- **值对象**：自校验、不可变（守护 G21–G24）。
- **领域事件**：过去式，只描述已发生的事实（G29）。
- **规则放在领域层**：315 条规则卡中的计算、校验类规则，落在 `domain` 的聚合方法和值对象里；路由、资格判定类决策落在 DMN（见 §5）。
- **深模块、窄接口**：每个模块只有 `api` 和 `events` 两个出口（G1–G6）。

## 4. BPMN：流程只编排人，不计算业务

- **Flowable 8 在 Phase 1 引入**（用户决定），作为 `platform.approval` 模块的内部实现：
  - 引擎表放在 `platform_approval` schema；
  - 业务模块只依赖 `platform.approval::api`（G19）；
  - 已实测 Flowable 8 + Boot 4.1 + PG18，引擎表 100% 落在 `platform_approval` schema。
- **流程负责**：步骤顺序、人工任务、会签 / 或签、超时催办（定时边界事件）、退回发起人、撤回截止点、转交。
- **流程不负责**：
  - 计算金额和毛利；
  - 直接查业务表（禁止 join 业务 schema）；
  - 调用外部系统（走防腐层）；
  - 在脚本任务里写业务逻辑。
- **流程模型是代码**：`.bpmn20.xml` 放在 `platform.approval` 模块的资源目录，随版本发布，有测试。在途实例按「排空」策略处理：新提交走新版本，旧实例在旧版本上走完。
- **人物流程用 BPMN 协作图记录**：工时填报、报价到预算、差旅、月结这 4 条流程，作为业务验收的对照。

## 5. DMN：决策与流程、代码分离

**1a 不引入 DMN**：审批指派写在 BPMN 扩展属性，由 `AssigneeResolver` 计算；出现真正的多维决策表时在该阶段引入（REIMAGINED_ARCHITECTURE 评审 #9/#15）。下文是 DMN 的适用范围，不是 1a 的交付内容。

**适合用 DMN 的**：输入少、规则成表、业务需要能看懂并调整的「判定」。规则卡中的典型例子：

| 决策 | 规则卡来源 | 决策表形态 |
|---|---|---|
| 预算是否需要 CEO 终审（预算毛利 ≥ 报价毛利则跳过） | 交付域 `budgetGmNotBelowQuote` | 输入：两个毛利；输出：`needsCeoApproval` |
| 工时行由谁审批（项目行 → PM；OH 行 → 直属上级；售前 → 部门负责人） | 工时域审批人分配规则 | 输入：行类型；输出：审批人角色 |
| ETC 调增是否需要审批（预测人工成本是否超出预算） | 交付域 ETC 规则 | 输入：是否超支、是否自建包；输出：`needsApproval` |
| 商机能否填工时（渠道 S/M、赢单 90 天窗口） | 工时域可填报范围规则 | 输入：岗位渠道、关闭状态、天数；输出：`allowed` |
| 审批是否允许本人审批，否则升级给上级 | 审批域防自审规则 | 输入：流程、是否本人；输出：升级规则 |

**不用 DMN 的**：带累加、取整、分摊的**计算**，例如 OH 分摊、WIP 余额、费率 × 工时。这类计算写在 Java 领域层的值对象和聚合里，用单元测试覆盖。

**落地方式**：
- Flowable 自带 DMN 引擎，决策表与 BPMN 一起放在 `platform.approval` 模块，或放在所属 BC 的资源目录里。
- 每张决策表都有对应规则卡 ID 的表驱动测试。
- 路由所需的标志，由所属模块算好后以类型化的 `routingFlags` 传给审批（模板中的 `ApprovalRequest` 已实现）。

## 7. OLTP：交易库要短、准、稳

- 每个 BC 的 schema 用第三范式；表名和列名由词表派生（`NAMING_STANDARD.md`）。
- 事务以聚合为边界，并且短：不在事务里调用外部系统、发 HTTP 请求或跑批量计算。外部调用走发件箱和可靠投递。
- 并发控制：聚合带 `version` 列做乐观锁。批处理互斥用作业表租约，即 `(legal_entity_id, period, job_type)` 上的唯一约束，代替 Redis 锁或 advisory lock。
- 约束优先于代码校验：`CHECK` 存枚举名，金额和币种成对（ADR 硬约束），schema 内外键齐全。
- 交易表上不跑报表。列表查询只用索引覆盖的分页，禁止内存分页和全表扫描（这些是老系统的问题）。
- 大表（成本台账、WIP 变动）按期间分区。

## 7a. 性能预算（用户 2026-10-15：对原则核对 B 的待决项答「全部按推荐 (Recommended)」）

预算是设计目标，也是验收与告警的依据。守护见 `NAMING_STANDARD.md` §4「待实现的守护」G-P1–G-P6；实时告警阈值（SLO）见 §11 O-5。

**R-P1 服务端延迟目标**（服务端处理时间，不含网络）：

| 接口类别 | p95 | p99 | 说明 |
|---|---|---|---|
| 单个对象详情 | 200 ms | 500 ms | |
| 列表（≤ 50 行） | 300 ms | 800 ms | |
| 提交类命令 | 500 ms | 1 s | |
| 审批办理 | 800 ms | 1.5 s | |
| 合并待办 | 1 s | 2 s | 读老库的部分 1.5 s 超时后降级，界面标注老待办暂不可用（DATA_DESIGN_CHECKLIST §14.3 I7） |
| 登录（服务端） | 300 ms | 800 ms | 端到端 ≤ 2 s |
| 事件从提交到被消费 | 5 s | 30 s | |
| 组织同步一轮 | ≤ 60 s | | |
| 月结 | 不高于老系统基线 | | 且单法人单期间 ≤ 30 分钟 |

- 某类接口的 p95 超标持续 1 天为 P3，持续 1 周升为 P2（告警方式按 §11 O-6）。这是按接口类别的**日级预算告警**，与 §11 O-5 按 5 分钟窗口的 SLO 告警是两条独立告警：各自计算、各自触发，不互相合并或抑制。
- **基线**：老系统的对照值取自老系统 API 访问日志按 URL 聚合的 p95（只读、只出聚合，不出明细与个人信息）；读取前按写明对象并取得批准。基线在 Phase 2 入口前取得；表中「不高于老系统基线」的项以它为准。

**R-P2 结果集上限**：
- 列表的 `limit` 默认值与上限见 `NAMING_STANDARD.md` §2.6 A-3（50 / 200，全系统唯一常量）；批量接口每次上限见 §2.6 A-6（100 项）。
- 不分页的小表（法人、编号规则等）硬上限 1,000 行，超出即失败并告警，不截断。
- 仓储中返回集合的方法必须带上限参数，或在注册表登记为小表。
- 同步导出 ≤ 10,000 行且 ≤ 10 s，否则改为异步导出；一次导入 ≤ 5,000 行。

**R-P3 语句数与行数无关**：列表与批量用例执行的 SQL 语句数不随返回行数增长（不得 N+1），默认预算每个请求 ≤ 5 条；超出须登记理由。

**R-P4 连接与超时**：
- 主连接池为固定池：HikariCP `maximum-pool-size` = `minimum-idle` = 20，获取连接等待 3 s，连接最长存活 30 分钟；dev 开启 10 s 的连接泄漏检测。
- 交互请求的事务设 `SET LOCAL statement_timeout = '5s'`；批处理作业按作业另设并登记。
- 外部只读连接的超时见 DATA_DESIGN_CHECKLIST §14.3 I2。

**R-P5 慢查询发现**：数据库开启 `pg_stat_statements`；`log_min_duration_statement` 生产 1 s、dev 300 ms；请求耗时 > 2 s 记一条 `WARN`（不记参数）并计数；每周查看耗时前 10 名的语句，结论记入运维记录。

**R-P6 延迟直方图**：`http.server.requests` 开直方图，SLO 桶为 200 ms、300 ms、500 ms、1 s、2 s（300 / 500 ms 与 §11 O-5 的 SLO 一致）；p95 / p99 由直方图计算。

## 8. OLAP：分析与交易分离

- **分析模型**：`reporting` schema（或现有的 BI-olap 系统）采用星型模型：
  - 事实表：工时条目、成本台账分录、收入确认、WIP 变动、凭证分录；
  - 维度：项目、合同条款、人员、部门、法人、期间、成本类型。
- **构建方式**：由领域事件（Modulith 事件发布登记表）或 CDC 增量构建。月结时生成期间快照，老系统已有 WIP 期间快照的做法，延续下来。
- **BI 只读 `reporting`**：过渡期 `reporting` 视图的形状与老表一致，BI 的迁移只是 SQL 方言的移植，而不是重建模型。
- **利润 L3、WIP 汇总、项目绩效看板**这类重报表，从分析模型读取，不在交易表上实时计算。
- 先用 PG 物化视图满足需要；数据量或并发上来之后，再迁到列式库（与现有 BI-olap 合并）。

## 9. 测试策略：最少的测试，最大的覆盖

| 层级 | 定位 | 写法 | 数量原则 |
|---|---|---|---|
| **模块级集成测试（主力）** | 一次走通 HTTP → 鉴权 → 用例 → 领域 → 跨模块 api / 事件 → Flowable / DMN → 真实 PostgreSQL | `@SpringBootTest` / Modulith `@ApplicationModuleTest` + Testcontainers PG18；不 mock 自己的模块，只用 WireMock 隔离外部系统 | 每个用例 1 条正常路径，加上每条 P0 规则的关键分支；测试名带规则 ID |
| **单元测试（补边界）** | 纯领域逻辑：值对象不变式、计算、DMN 决策表 | 等价类 + 边界值 + 参数化（从规则卡的 Given/When/Then 直接生成用例） | 只补集成测试覆盖不到的分支，用最少的用例覆盖最多的分支 |
| **契约测试** | OpenAPI 契约；反向同步写入老表的结构；BI 查询在切换后仍能运行 | 生成的客户端编译通过；对老库执行 BI SQL | 每个桥接表和 BI 查询各一 |
| **端到端（必要时）** | 4 条人物流程和登录鉴权冒烟 | Playwright（仓库已有 `e2e/`） | 只覆盖跨系统、跨前后端的关键路径 |
| **架构测试** | 守护 G1–G33 和前端 F1–F13 | ArchUnit、Modulith、ESLint | 每条规则一个测试 |

**度量门槛**：
- JaCoCo 对 domain 和 application 统计**全部测试层级的合计覆盖率**：行覆盖 ≥ 80%，分支覆盖 ≥ 70%；
- P0 规则 100% 有对应测试；
- 可选：对 domain 包跑 PIT 变异测试，检查测试是否真的能发现错误，而不只是执行到代码。

**实测**：模板工程用 11 个集成测试 + 5 个值对象单测，行覆盖率 85.9%（分支 67.9%）。说明以集成测试为主，少量测试就能覆盖大部分代码，剩余缺口用最少的单测补齐。

## 9a. 权责发生制业财一体（贯穿七个框架，ADR-0016）

弗思特以 AEC 项目为业务基础，FORCITIS one 的核心是权责发生制下的业财一体。七个框架在这一点上的落点：

| 框架 | 在权责发生制主干上的落点 |
|---|---|
| DDD | 业务 BC 只产生经营事实，不认识会计科目；`operations.facts` 是唯一的过账管道；`accounting.period` 独占期间状态；WIP 与开票是同一个一致性边界 |
| DMN | 科目映射、可计费性判定、审批路由写成决策表（收入确认口径已由 ACC-R01 定为产出法 · 客户价值确认，不做方法选择），由财务评审、按版本生效 |
| BPMN | 审批流程只决定「谁同意」；同意之后产生什么事实、记哪个期间，由领域和 DMN 决定 |
| DAMA | 明细事实只追加：更正只能冲销（反向事实 + 新序号 + 双向关联），关账后的更正落在开放期间并标注原期间；对账等式（归集守恒、合同资产滚动恒等式 F113、借贷平衡）作为数据质量规则 |
| OLTP | 过账在一个事务内完成校验、分配序号、写事实；期间校验以 (期间, 法人) 为粒度 |
| OLAP | KPI 与报表按 OAT（`08-FORCITIS Operating Accounting Taxonomy.md`）原语声明口径；月结生成期间快照；分析侧只读 |
| TOGAF | 法定账在本期仍由 U8C 承担；FORCITIS one 自任法定账（蓝图 DD-6）、跨法人结算、集团合并作为后续过渡架构 |

**权责事实全部在新系统**（用户 2026-10-14：「确保权责业务事实全部在新系统」）：凡按权责发生制需要确认的业务事实——合同签订与变更、交付与产值确认、工时与成本、费用、收入确认、开票与应收、回款、分包与应付、付款——其记录系统（system of record）一律是 FORCITIS one，并经 `operations.facts` 过账。致远 A8 等外部系统不得作为这些事实的产生地或存放地：在 OA 上发起或审批的此类流程必须迁入（不归入「视情况」），跨库读取 A8 得到的此类数据必须改为新系统自有事实。U8C 作为法定账只接收新系统推送的结果，不反向产生权责事实。每个阶段的出口条件须证明本阶段涉及的权责事实没有遗留在老系统或 OA。

## 11. 可观测性（用户 2026-10-15：对原则核对 A 的待决项答「全部按推荐 (Recommended)」；日志保留期另答「nginx 与运维日志保留改 180 天, 审计分区删除用专用维护角色」）

由 `proposals/PHASE1A_PLATFORM_CONVENTIONS.md` §4 升格而来，那一节不再是现行规则。守护见 `NAMING_STANDARD.md` §4「待实现的守护」G-O1–G-O6。

- **O-1 日志格式与关联号**：应用日志为 ECS 格式的结构化 JSON（Spring Boot structured logging），写到 `/data/forcitis-one/logs/*.json`，由 SLS 采集。每行必有：时间、级别、logger、message、`correlationId`、`userId`（只记 ID）、`module`（`<子域>.<BC>`）。
  - **关联号 `correlationId` 是唯一的追踪键**，不引入 `traceId` 与分布式追踪库：HTTP 入口读取 `X-Correlation-Id`（不是 UUID 时返回 400，不静默替换），没有就生成；写入 MDC 与响应头；发布领域事件时写入事件信封（`causationId` 指向触发它的事件）；消费事件与出站投递时从信封恢复；出站请求带上该头。
  - 发布事件时 MDC 中没有关联号属于缺陷：计数并告警（G-O6），不静默新建。
- **O-2 级别**：每条 `ERROR` 都是告警，必须以 `ALERT P1|P2|P3 <子域>.<BC> ` 开头；`WARN` 表示已降级但能自愈；`INFO` 记状态变化。一个依赖或作业由正常转为失败时记一次带堆栈的 `ERROR`，持续失败期间只记不带堆栈的 `WARN`，恢复时记一条 `INFO`。
- **O-3 日志中不得出现**：个人信息（姓名、手机号、邮箱、证件号等）、客户端 IP 地址、密钥、口令、令牌、原因的全文、消息与单据正文、SQL 参数、数据库服务端的错误详情、外部系统的原始响应、URL 查询串。JDBC 连接串设 `logServerErrorDetail=false`，使唯一约束冲突等错误不把列值带进日志。需要追溯客户端地址时，`ALERT` 行写审计条目 ID，地址只在审计条目中（按审计的权限与保留期管理）。
- **O-4 指标**：命名为 `forcitis.<子域>.<bc>.<名词>.<度量>`（G46）。必备：作业失败数；每个外部集成的可用性 gauge 与死信数；对账差异数；事件发布滞留（未完成、重投用尽）；HTTP 请求 p95 / p99（§7a R-P6）；连接池；JVM。标签不含 ID 与个人信息。生产必须暴露 Prometheus 端点，部署后检查抓取到业务指标（G-O4）。
- **O-5 SLO**：交互读取请求 p95 ≤ 300 ms，命令 p95 ≤ 500 ms；连续 3 个 5 分钟窗口超标触发 P3。按接口类别的日级预算告警见 §7a R-P1，与本条是两条独立告警。
- **O-6 告警按事件，不按次**：同一故障持续期间只算一个事件。
  - P1：立即通知，每 30 分钟重复一次，直到有人确认；
  - P2：每个事件通知一次，另有每日汇总；
  - P3：只进看板与每日汇总。
  - 通道：P1 企业微信群机器人加短信，P2 企业微信群，P3 看板；接收群与值班人的配置见 `phase1a/infra/runbooks/C-7-alerts.md`。
  - 已定的告警：

    | 告警 | 级别 | 触发 |
    |---|---|---|
    | 登录失败率 | P1 | 5 分钟内失败率 > 20 % 且 ≥ 20 次 |
    | 未完成事件发布 / 死信 | P2 | 未完成超过 10 分钟（用户 2026-10-15：「10 分钟 (Recommended)」；配置 `stale-after`），或死信数 > 0 |
    | 组织同步延迟或中止 | P2 | 超过 2 个周期无成功，或缩水保护中止 |
    | 作业失败 / 流程引擎死信 | P3 | 失败数 > 0 |
    | 接口延迟超出 SLO | P3 | 见 O-5 |
- **O-7 审计与日志分工**：审计记录「谁在何时对什么做了什么」，含来源地址，是业务与安全的证据，按 §6 保留；应用日志只用于排障，不作证据，不含 O-3 所列内容。同一件事两边都需要时，日志引用审计条目 ID。
- **O-8 保留期**：
  - SLS 应用日志（`app`）30 天；`nginx` 与运维（`ops`）日志 180 天（满足《网络安全法》网络日志不少于 6 个月；nginx 访问日志含客户端地址）。调整 Logstore 保留期前由 one-ops 核算费用并报调度会话。
  - 审计记录按 §6 的表；`audit_entries` 按月分区，分区归档到对象存储并校验后，由专用的维护角色删除在线分区（应用角色无此权限；作为只追加约束的登记例外，由审计分区工作单元实现）。
