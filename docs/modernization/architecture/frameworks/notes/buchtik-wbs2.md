## 核心思想

- **论断：WBS 以成果、服务或结果分解全部项目范围，项目管理等支持工作也须纳入。** 依据：WBS2#工作分解结构节点、WBS2#支持工作与离散组件。含义：建议核对 OBJ-30 的范围节点是否完整承接工作；内部支持工作不能因此直接归为 OBJ-35 的客户交付物。
- **论断：工作包是某条分支的末级组件，各分支不必在同一层级停止分解。** 依据：WBS2#工作包。含义：建议在规则卡或设计中说明工作包边界与分解终点，不把固定层数或统一小时数作为 OBJ-30 的实现标准。
- **论断：100% 规则逐层检查子项是否完整覆盖父项范围，不表示项目进度已经完成。** 依据：WBS2#范围完整性。含义：建议逐层核对 OBJ-30 是否多放或漏放范围，不能用范围完整性结论替代进度、客户认可或收入确认。
- **论断：WBS 允许组件重名，组件身份由 WBS ID 区分，名称与层级各有作用。** 依据：WBS2#层级标识与编号、WBS2#节点命名。含义：OBJ-30 的节点标识、名称和层级分别说明，数据库标识继续遵守现行规范，不照搬书中的层级编号。
- **论断：WBS 字典补充节点内容、边界、责任和估算，与范围说明共同形成受变更控制的基线。** 依据：WBS2#范围字典、WBS2#范围基线与变更。含义：建议用字典式说明记录工作包的包含项、排除项、责任和估算依据，批准后的范围变化走变更控制，本卡不新增字典实体或表。
- **论断：工作包与活动不是同一层次的描述，工作包估算可逐层汇总，活动及其依赖、资源和历时进入进度计划。** 依据：WBS2#范围与进度衔接、WBS2#成本估算与汇总。含义：建议对 OBJ-30、31、32 及 PRC-18、19、21 分别说明范围、计划版本和预算基线并建立追溯，不因三者有关联就合并对象。

## 对本系统的启示

- **业务对象：** WBS 组件说明项目范围如何分解，工作包是某条分支的末级组件；不能把任何业务对象直接视为 WBS 节点。书中的 deliverable 包括成果、服务和结果，其外延也不能直接等同于本项目词表中向客户交付的成果物。项目管理等支持工作同样需要纳入范围，书中另讨论 level of effort 组件。（WBS2#工作分解结构节点、WBS2#支持工作与离散组件、WBS2#工作包；对照：OBJ-30、OBJ-35）
- **价值流：** 本书不提供本项目所用的 BIZBOK 价值流及阶段判据。WBS 的父子分解用于表达范围包含关系，不能据此证明客户价值如何推进，也不能将上下相邻节点解释成先后阶段。（WBS2#工作分解结构节点、WBS2#范围与进度衔接；对照：OBJ-30）
- **能力：** 本书没有企业业务能力图的定义和分解方法。一个工作包由谁完成、需要什么资源，与企业长期具备何种业务能力，是不同层面的描述。（WBS2#工作包；对照：OBJ-30）
- **流程：** WBS 为活动识别提供范围依据，活动及其依赖、资源和历时再进入进度计划。工作包与活动不能混同；两者可以迭代或并行完善，书中的先后示意不应被解释成禁止并行的生命周期规范。（WBS2#范围与进度衔接；对照：OBJ-30）
- **数据建模：** 层级、节点标识和节点名称承担不同责任；书中允许重名组件，由 WBS ID 区分。字典补充节点的内容、边界、责任和估算等信息，使各方对节点含义达成一致。书中示范的层级编号不是本项目数据库主键标准。（WBS2#层级标识与编号、WBS2#节点命名、WBS2#范围字典；对照：OBJ-30）
- **度量与 BI：** 范围分解为工时、时间和成本估算提供坐标，工作包估算可以逐层汇总。但 100% 规则检查的是范围是否完整，并非项目进度已完成 100%，也不直接给出收入确认或挣值计算规则。（WBS2#范围完整性、WBS2#成本估算与汇总；对照：OBJ-30）
- **主数据：** WBS 是具体项目的范围结构，字典与范围说明一起形成范围基线。它可以引用服务产品和阶段类型等已有目录，但书中方法不决定这些目录的主数据所有权；批准后的范围变动需走变更控制。（WBS2#范围字典、WBS2#范围基线与变更；对照：OBJ-30）

## 我们的取舍

- **建议采纳：逐层核对范围完整性。** 对对象图中的 OBJ-30，核对节点是否承接范围、子项是否完整、项目管理等支持工作是否有归处；这是一份检查建议，不表示现有结构已通过 100% 规则。
- **建议采纳：把范围、进度、预算分别说明并建立追溯。** 对照 OBJ-30、31、32，以及流程目录 PRC-18、19、21，分别明确范围结构、计划版本与预算基线的含义，再检查关联；书中衔接关系不意味着三者应合并为同一个对象。
- **建议采纳：在规则卡或设计中说明工作包边界与分解终点。** 项目词表已使用工作包，并注明 WBS 最底层。可用字典式说明记录包含项、排除项、责任和估算依据；本卡不新增字典实体或表。
- **建议不采纳：把任意层数、编号形式或示例软件字段作为统一实现标准。** 对象图当前阶段—子项—工作包的具体结构属于项目选择，不能称为本书规定的唯一结构；数据库标识仍按现行规范。
- **建议不采纳：用工作包完成替代客户认可、阶段门或收入确认。** OBJ-30 的工作进程与 OBJ-35 的客户成果事实已有区别。书中的广义 deliverable 也不能把全部内部管理工作提升为本项目交付物对象。词表中交付包与工作包的关系仍有待确认注记，本卡不裁定同义或改名。

**使用边界：** 本书提供范围分解与项目管理方法，不提供 FORCITIS 的合同归属、阶段类型、工时可记条件、客户验收或收入政策事实。上述对象与流程编号来自当前仓库草案，只作复核落点。未审定新架构、未修改词表或流程目录、未实施或验收任何 WBS 功能；起草时记「独立页码抽查尚未运行」，后附抽查记录见「附：核对记录」。

## 附：WBS 定义依据

**WBS 定义依据（原笔记自行概括）**：WBS 是对项目全部范围的层级分解，以应形成的成果、服务或结果组织工作，逐层细化到能够估算、分派和控制的工作包；它让各方明确项目包含哪些工作及其边界。（WBS2#工作分解结构节点、WBS2#工作包）

这一定义的直接阅读依据分为三层：

- **交付物导向**：第 1 章开头说明其关注项目应交出的结果，第 3 页明确用 deliverable-oriented 描述结构。进度安排和任务清单另有用途。位置：印刷第 1–3 页，PDF 23–25；其中第 3 页页码可见，章首页与第 2 页按目录及连续页序定位。（WBS2#工作分解结构节点）
- **100% 规则**：包括范围内全部工作，也包括项目管理；不多放范围外工作，不漏范围内工作。对每个父节点都要核对其子项合起来是否完整表达父项，而非只检查全项目顶层。位置：印刷第 63–65 页，PDF 85–87。（WBS2#范围完整性）
- **分解终点**：工作包是该分支末级；能估算时间和成本并进行控制，是判断细度的重要依据。各分支可在不同层级停止，不能把固定层数或统一小时数当作所有项目的结论。位置：印刷第 52–58 页，PDF 74–80。（WBS2#工作包）

原书第 2 页转引 PMI 的 WBS 实践标准及 PMBOK 定义，第 63 页转引 Haugan 对 100% 规则的表述。本卡直接核验的是 Buchtik 本书，未独立核验这些被引原版，也未核验后续新版标准；不将转引升级为对现行标准原文的核验。
