## 核心思想

- **协作的产物首先是共同学习。** 多人把业务叙述放到同一可见空间，能够暴露词义差异、缺失情形和技术限制。书中允许探索初期暂不精确，随后借交谈修正；这种安排是探索技巧，不是规格可以含糊的许可。书中也明确提醒，大图仍可能有错，有些问题只有编码、测试和真实使用才能发现。（BES#协同学习、BES#探索成果与局限） Big Picture 与 Design-Level 的目标不同：前者扩大共同理解，后者聚焦具体问题并寻找候选解决方案。不能把一张大图直接当成完成的软件设计，也不能因参与者在现场达成一致就称业务假设已经验证。（BES#大图与设计层）
- **事件帮助定位变化，不证明系统已发布事件。** 以已发生的事情描述领域变化，可把注意力从界面动作转向变化时刻及其后果。书中列出的来源包括用户动作、外部系统、时间以及其他事件引发的反应；同一叙述还可能在精化时拆成观察到的事实和据此推导的变化。探索便签是事件候选，其存在不证明运行系统真的发布、持久保存或消费了相应事件。（BES#事件语义）
- **热点保存问题和未知。** Hot Spot 可以表示风险、问题、信息不足、选择点或需要继续探索的区域。把冲突标出来有助于继续梳理整体叙述，不必立即假装已解决。热点本身既不是业务规则，也不是已经成立的系统边界；后续还需要说明谁验证、用什么证据以及如何裁定。（BES#协同学习、BES#热点、BES#探索成果与局限）
- **策略连接后果，读模型支持决定。** Policy 表达某事件发生后应触发什么行动；实际反应可能由人、既有习惯或软件完成，并非每一条都应实现成自动订阅。用于让用户看清信息并作决定的读模型，也不应因出现在同一界面就变成一个聚合的内部结构。（BES#策略与人工反应、BES#聚合与读模型）
- **聚合与模型边界仍是待检验假设。** 书中从职责、所需信息和不变量寻找聚合，而非先把显示字段装进数据容器。大范围建模章节提出多个协作模型与 Bounded Context，但该章仅完成一小部分；不能据此补造完整的上下文划分方法。探索产出的分组和名称仍要与语言、规则及事务要求逐项核对。（BES#大图与设计层、BES#聚合与读模型、BES#模型边界与未完成范围）

## 对本系统的启示

- **检查事件推导遗漏。** 事件来源、后续反应及所需信息只用于检查；正式候选仍从信息图规则、规则卡和生产取证推导，经用户裁定，不由便签直接生成正式目录。（FRAMEWORKS §2、§4、ADR-0052 决定 4；BES#大图与设计层、BES#事件语义、BES#策略与人工反应）
- **保留待核问题。** 热点附来源、缺口和下一步验证，不把现场一致或有人提出写成业务事实；正式定名仍交 one-glossary。（ADR-0052 决定 4；BES#协同学习、BES#热点、BES#探索成果与局限）
- **区分探索词汇与实现职责。** 策略、读模型、外部系统与热点已有方法落点，但是否自动化及是否采用 BPMN/DMN，仍按所属规则与流程判据决定。（ADR-0052 决定 4；BES#策略与人工反应、BES#聚合与读模型）
- **验证运行事件与候选边界。** 正式事件分别验证发生条件、负载、业务日期、持久投递及消费结果；聚合和 BC 回到不变量、事务要求及上下文映射核对。（CS-2.5、FRAMEWORKS §4；BES#事件语义、BES#聚合与读模型、BES#模型边界与未完成范围）

## 我们的取舍

以下均为**已审定（one-architecture 2026-10-18，页码已抽查）**。现行方法见 [FRAMEWORKS](../../FRAMEWORKS.md) §2、§4 与 ADR-0052 决定 4。

- **建议借鉴：用事件来源、反应与所需信息检查推导遗漏。** 可问某变化来自用户、外部系统还是时间，之后谁依据什么信息做什么；但候选事件仍从信息图规则、规则卡和生产取证推导，再经用户裁定，不据工作坊便签直接生成正式事件目录。
- **建议借鉴：把热点作为待核问题的位置标记。** 问题应附来源、缺口和下一步验证，不把有人提出转写为事实；涉及新业务用语的正式定名仍交 one-glossary。本卡只保留来源词汇，不新增词表条目。
- **建议借鉴：区分策略、读模型、外部系统与热点的职责。** 这四个词汇已在 ADR-0052 的现行方法中有落点；并不意味着整套工作坊、颜色体系、便签种类和流程顺序都已采纳。策略是否自动化、是否涉及 BPMN 或 DMN，继续按所属业务规则与流程判据决定。
- **不建议：把协作叙述当作运行事件或完整业务证据。** 正式领域事件仍按 CS-2.5 由聚合产生并登记；需分别验证发生条件、负载、业务日期、持久投递与消费结果。本书允许探索时暂时模糊，不放宽本项目契约、命名或验收要求。
- **不建议：从便签颜色、屏幕、表结构或人员分组直接确定聚合和 BC。** 候选边界须回到不变量、事务要求与上下文映射核对；第 29 章未完成的内容不能被补成作者已经给出的完整方法。
- **不建议：把书中的 EventStorming 格式或章节中的 value stream 直接替代本项目方法。** BIZBOK 价值流、流程目录和 BPMN 分别按现行判据；本项目已用事件清单推导取代工作坊，本笔记不重开方法选择。

**使用边界：** 本书提供协同探索的经验与部分设计技巧，且本地版本尚未完成。它不证明本企业某个经济事实、业务能力、流程边界、聚合或事件已经成立，也不能证明工作坊一定发现了全部例外。本笔记没有举办或验收工作坊，没有新增领域事件、聚合、上下文边界、规则或实现；原起草边界记以上建议仍待 one-architecture 审定；原状态行及取舍节后记为已审定，本次迁移不另行裁定。
