## 2. 与本项目相关的核心思想

### 业务对象

实体的稳定身份和值对象的描述性语义不同。值对象应形成概念整体、不可变并按值比较；不能因为数据库为某项数据分配了键，就将它判成领域实体。服务应有领域必要性，不能取代所有对象行为。（I-03、I-04）

### 价值流

本书不涉及 BIZBOK 价值流判据。领域事件和长时业务协作可以承载办理事实，不等同于价值阶段。

### 能力

本书不涉及企业业务能力图。子域与限界上下文分别帮助理解问题及组织解决方案，不能直接由能力条目数量推导上下文数量。（I-01、I-02）

### 流程

领域事件应表达已发生的业务结果，并使用来源上下文的语言；命令是原因，成功发生的结果才是事件。跨聚合或跨上下文协作须明确延迟、可靠投递与后续处理，不能把一次调用链当成所有数据已一致的证据。（I-05、I-08）

### 数据建模

聚合围绕真正的不变量建立一致性边界；对象关联多不代表必须成为大聚合。小聚合、按身份引用、边界外明确最终一致性是相互配合的设计选择，仍须与业务可接受的延迟一起验证。（I-06、I-07、I-08）

### 度量与 BI

CQRS 可让查询模型满足跨聚合展示需要，避免为了查询方便扩大写模型。它不自动要求两个数据库，也不提供完整 BI、指标或历史维度设计；查询投影的时效仍需明示。（I-09）

### 主数据

限界上下文首先是语义边界，同名对象可有不同模型。上下文映射既要表达关系，也要与真实集成相符；共用身份不意味着共享所有属性和写入权。（I-01、I-02；写入权为项目应用）

## 4. 对本项目的取舍

**已审定（one-architecture 2026-10-18，页码待 sonnet 抽查）。**

- **采纳：以真实不变量和并发修改场景复核聚合。** 理由：能暴露因树形界面、对象从属或外键连通而形成的大聚合。
- **采纳：事件含义、查询投影和跨边界一致性分别说明。** 理由：与现有领域事件、读模型及可靠投递约束相容，但实际重试与幂等仍须测试证据。
- **不采纳：每个实体一个仓储、每次跨边界协作一个全局事务。** 理由：仓储服务于聚合生命周期，分布式便利不应决定领域边界。
- **不采纳：将所有模块改为 CQRS、事件溯源或微服务。** 理由：这些是不同维度的可选设计；本项目已有模块化单体及持久化决定，本卡只保存理解。
