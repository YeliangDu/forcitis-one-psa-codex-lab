## 2. 与本项目相关的核心思想

### 业务对象

模型是团队为解决特定问题形成的选择性解释，须由领域专家与开发者共同推敲。实体依靠身份和连续性识别，值对象依靠所描述的值识别；规则、约束、过程等隐含概念也可能需要显式表达，不能只从现有名词或数据库表挑对象。（E-01、E-03、E-06）

### 价值流

本书不涉及 BIZBOK 的价值流、阶段价值及导航判据。书中的业务活动和核心领域不能直接替代价值流地图。

### 能力

本书不涉及企业业务能力图。核心领域用于集中建模和设计投入，不等于企业所有重要能力，也不由部门规模或表数量决定。（E-08）

### 流程

无法自然归属实体或值对象、又具有业务意义的操作可以成为领域服务，但不能因此剥走对象本应拥有的行为。把隐含约束和过程说清楚，比把全部业务塞进通用服务更能保持模型含义。（E-04、E-06）

### 数据建模

模型与实现须持续相互检验。聚合围绕共同保持的不变量确定一致性边界，由根控制内部修改；它不是把所有关联数据圈在一起。仓储表达领域中的查找和获取，不让持久化细节主导模型。（E-02、E-05）

### 度量与 BI

本书不涉及 Kimball 事实粒度、维度和可加性的完整方法。业务分析所需概念仍可促进模型发现，但不能从 DDD 模式推导指标公式、收入或利润口径。（E-06）

### 主数据

同一词在不同限界上下文中可能有不同含义。上下文映射要说明真实的模型关系和集成边界；防腐层处理的是语义翻译，不能缩为字段格式转换。跨域共享必须明确范围，不能以统一语言为由强造一个全企业万能模型。（E-07）

## 4. 对本项目的取舍

**已审定（one-architecture 2026-10-18，已抽查）。** 现行约束以 [FRAMEWORKS](../../FRAMEWORKS.md) §1、已采纳 ADR 与 SESSION_PLAYBOOK §14 为准。

- **采纳：按业务不变量与语言边界反查模型和实现。** 理由：有助于发现对象、聚合、表和上下文被误当成同一层次的问题。
- **采纳：将规则或责任等隐含概念显式说明，并持续用真实业务场景检验。** 理由：本项目正在进行对象、规则和实现的双向核对；原书不替代企业证据。
- **不采纳：把企业对象清单逐行生成聚合或表。** 理由：业务存在依附不等于事务一致性，身份和值语义也须分别判定。
- **不采纳：以原书的持久化、对象引用和示例代码覆盖本项目标准。** 理由：聚合间类型化 ID、只追加事实、UUIDv7 及安全访问边界均已有决定；原书例子不是工程规范。
