## 2. 与本项目相关的核心思想

### 业务对象

本书的事务执行、流程实例与 JPA 实体不是同一种对象。JPA 示例中的实体按标识映射到一张或多张表的记录，属于持久化技术语境，不能据此定义企业业务对象。事务耐久性表示提交结果在故障后仍能恢复，也不等于对象拥有长期业务身份。（TP-03、TP-07）

### 价值流

本书不涉及本项目所用的 BIZBOK 干系人价值流判据。业务过程跨多个事务执行的讨论，是运行可靠性问题，不能用事务步骤直接生成价值流阶段。（TP-04）

### 能力

本书不涉及企业业务能力图的定义与分解。流程运行时具备哪些功能，与业务能力属于不同层次。

### 流程

人工等待、外部系统和资源竞争，使长流程通常无法靠一个数据库事务包住。拆成多个已提交步骤后，必须显式处理部分完成、并发可见的中间结果、后续恢复与补偿。流程状态要能关联已完成和待执行的步骤，以及相关业务实体；只保存最后一个界面状态不足以解释执行经过。（TP-04、TP-05）

### 数据建模

事务系统提供的原子性、隔离性和耐久性不能替应用程序定义业务不变量。提交成功后不能再用事务回滚撤销，需用后续业务动作纠正；补偿也未必能消除现实世界已经发生的效果。保存步骤结果和保存流程恢复位置之间还存在故障窗口，应证明两者怎样共同提交或怎样辨认步骤已经执行。（TP-01、TP-02、TP-06）

### 度量与 BI

事务吞吐要连同负载条件、响应时间分布和资源消耗解释，不能只报一个峰值。流程事件和状态也能提供业务活动监控资料，例如耗时及异常等待；这些运行记录要进一步建模才能支持经营分析，本书没有替本项目定义经营指标口径。（TP-04、TP-08）

### 主数据

本书不涉及主数据的权威来源、匹配合并与治理规则。事务一致性可保护某次修改，却不能判断多个系统的客户记录是否代表同一实体，也不能授予主数据维护权。

## 4. 对本项目的取舍

以下经 one-architecture 2026-10-18 审定（ARC-1017-ARC-21）；现行事务、事件和更正规则仍以 CODING_STANDARD CS-2.3、CS-2.25、SESSION_PLAYBOOK §12.3 和已采纳 ADR 为准。

- **采纳：把数据库提交、流程完成、外部效果分别验证。** 理由：任一步成功都不能单独证明全链路完成；恢复与重试必须辨认前一步是否已经生效。
- **采纳：为跨事务流程记录恢复所需的状态、关联标识与异常结果。** 理由：重启后需要继续或补偿，并要避免同一业务效果重复出现。具体载荷受项目敏感分级约束，不照搬书中记录参数的示例。
- **采纳：用故障窗口审查业务结果与出站记录的共同提交。** 理由：可据此检验现有发件箱、幂等与可靠投递设计；这是将原理应用于本项目，并非声称本书规定了现行实现。
- **不采纳：用一个长事务跨人工等待或外部调用，也不默认引入分布式提交或 Saga 框架。** 理由：跨步骤需要的业务语义必须先确定；机制选择按现有单体架构及例外评审处理。
- **不采纳：把补偿写成删除或改写已过账事实。** 理由：书中的一般补偿原理不能覆盖本项目冲销重做的不变量，也不能保证现实效果可逆。
- **不采纳：从 JPA 示例推导每个业务对象必须一表，或采用书中历史产品版本。** 理由：示例只解释事务与持久化抽象；项目的模型、JdbcClient 和键类型已有决定。
