## 2. 与本项目相关的核心思想

### 业务对象

数据表示需要业务语境。概念实体、具体实体实例及物理记录属于不同层次；数据建模中的实体以组织是否收集其相关信息为出发点，主数据语境则关心业务实体的可信表示。这些表述不能直接变成 BIZBOK 业务对象或 DDD 聚合的充要条件。（D2-01、D2-03、D2-07）

### 价值流

本书不涉及本项目所用的 BIZBOK 价值流建模判据。数据生命周期描述数据如何取得、流转、使用和处置；它不能替代干系人价值流，也不等于软件开发生命周期。（D2-02）

### 能力

本书讨论实现数据管理所需的业务和技术职责、治理及协作，但不据此给本项目企业能力图定边界。把知识领域列全并不表示组织已具备相应能力；还要有明确的决定权、执行责任和可观察结果。（D2-01、D2-04；后一判断为本笔记应用）

### 流程

数据质量管理要进入产生和使用数据的日常流程。只修下游报表中的坏记录，不能消除源头原因；数据问题应能追到相关流程、系统和责任人。数据生命周期与血缘相交：前者关心各阶段的管理，后者关心来源、移动与转换路径。（D2-02、D2-09）

### 数据建模

逻辑模型表达某使用语境的数据要求，仍应独立于具体数据库技术；物理表不应提前限制业务概念。数据类别也取决于语境，书中明确记录了不同业界分类口径，不能把某处的别名当成所有层次的统一同义词。（D2-03、D2-05、D2-06）

### 度量与 BI

仓库应服务业务问题，详细数据是汇总与分析的基础。元数据应能解释某个合计如何计算、从哪里来。数据质量则应按使用要求建立可测量标准、持续观察和治理；有数据或有报表都不自动证明数据适用。（D2-08、D2-09）

### 主数据

主数据管理关注核心实体的可信取值、身份及跨系统对应；参照数据管理更侧重受控分类和值域的解释。匹配与合并还要考虑误合并后的恢复、标识随时间保持一致，以及向使用方分发可信结果。主数据治理不等于新建一张字典表，也不保证所有来源可以由同一写入方覆盖。（D2-06、D2-07；写入边界为项目应用）

## 4. 对本项目的取舍

以下经 one-architecture 2026-10-18 审定（ARC-1017-ARC-21）；落地规则以 [FRAMEWORKS](../../FRAMEWORKS.md) §6、SESSION_PLAYBOOK §14.1 和既有数据登记为准。

- **采纳：业务定义、数据责任、生命周期与血缘一并考虑。** 理由：只列字段不能回答谁能更正、谁消费以及历史如何解释；在现有数据访问注册表和敏感分级登记中承载，不另建重复登记册。
- **采纳：区分实体身份、来源对应、参照值域与版本。** 理由：匹配同一客户、解释一个状态代码、查询历史归属是不同问题。具体权属和版本策略继续执行 D11、D17，不能把概念参照当成新授权。
- **采纳：质量规则同时覆盖输入约束、源头原因和使用端核对。** 理由：校验通过只能证明被校验的规则；还需要对账及异常处置证明数据满足业务用途。
- **不采纳：因书中列有治理知识领域，就新增组织、工具或一套全量治理流程。** 理由：本卡只保存可用于现有工作的思想；新增运行机制仍需适配和授权。
- **不采纳：把本地 2017 文本标作 2024 修订版。** 理由：版次年份有直接证据，未取得版本差异证据；本次只登记已读版本，不修改 FRAMEWORKS 既有条目。
