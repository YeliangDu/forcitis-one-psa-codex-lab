## 2. 与本项目相关的核心思想

### 业务对象

维度在本书中是进入分析数据的描述实体，不能据此给所有业务对象下定义。分析中区分对象的自然标识与维度行的代理键，尤其同一对象有多个历史轮廓时，按版本行计数不等于按实体计数。（K2-01、K2-04、K2-05）

### 价值流

本书不涉及本项目所用的 BIZBOK 价值流判据。总线矩阵用于识别测量活动之间可共享的维度，不用于表达干系人的价值承诺和阶段门。（K2-03）

### 能力

本书不涉及企业业务能力图的定义、命名与分解。

### 流程

分析设计应围绕业务产生测量的活动，而不是为每个部门复制一份数据。部门可能共同消费同一测量活动的数据；分部门建设而缺乏一致口径，会形成难以比较的分析孤岛。（K2-02、K2-03）

### 数据建模

粒度是对事实行含义的明确承诺，随后选择的维度与事实必须能在该粒度上成立。交易明细、期间汇总和流程累积状态是不同观察方式；累积快照会更新，事件记录也可以没有数值度量。暂存区可以使用文件或规范化结构，展示层的可理解性与查询用途才是建模重点。（K2-02、K2-06、K2-07、K2-08）

### 度量与 BI

同一事实表中不能混入另一粒度的金额或数量，可加性也不能只由数字类型判断。企业整合依靠共用维度的定义、键、属性和取值一致；物理上相同或受控复制均可，一致性并不要求所有主题共用唯一一张物理表。（K2-01、K2-03）

### 主数据

本书相关的直接贡献是维度整合与历史追踪，不是完整的主数据治理体系。Type 2 用新版本行保留历史轮廓，事实引用当时的版本键；需要业务判断哪些属性值得保留历史。第二版在该例中把维度表的生效、失效日视为辅助属性，同时说明暂存装载历史时需要有效期信息，不能把这段话推广为时态范围永远不必保存。（K2-04、K2-05）

## 4. 对本项目的取舍

以下经 one-architecture 2026-10-18 审定（ARC-1017-ARC-21）；现行维度建模参照仍锁定第三版，见 [FRAMEWORKS](../../FRAMEWORKS.md) §5。

- **采纳：作为第三版概念的历史补证。** 理由：粒度、总线矩阵、一致性维度和 Type 2 的基础思路可用于追溯已有资料，不需要另立规则来源。
- **采纳：按业务决定保留什么历史、按实体与版本分别计数。** 理由：组织、客户等属性变化会改变分析口径，按版本行去重可能高估实体数量；具体保存规则仍按项目 D6、D17。
- **不采纳：用第二版例子的可选日期属性降低现行时态约束。** 理由：第三版第 54 页明确提出 Type 2 的生效、失效和当前行属性，项目还另有区间与历史取值约束；两个版本的文字不能混写成同一要求。
- **不采纳：顺序整数代理键直接覆盖 UUIDv7，或把分析表结构反推为聚合。** 理由：键类型和事务模型已有项目决定，第二版只支持分析身份分离的原理。
- **不采纳：按部门各建一套无法对账的指标。** 理由：同一业务测量需要一致解释；构建批次与投产节奏继续按 ADR-0054，而非套用书中数据集市的交付节奏。
