## 2. B 类占位与「与倾向不同」各条的理由

**占位方式基本正确**：第 3、4、8、9、10 节都标了「B 类，待批」，只写推荐，代价与受影响的 PR 写在裁定稿里，批准后填回。有两点问题：
- 填回时，代价、受影响的 PR 和锚点必须写进 ADR 正文或附件（评论不在仓库里，现附件写「见 `B-RULING-COMMENT.md`」，仓库中没有这个文件）。否则不满足硬要求 2「不写代价不结案」（M9）。
- 体量已到上限，填回后必然超过 20 KB（M7）。

**第 3 条（停薪留职，部分不同）：理由站得住。**
- 授予按人发放，没有挂在岗位上的授予，按岗位授权的 ADR-0029 处于搁置；ADR-0032 第 4 项「不自动授收」已由 ADR-0055:75 明确保留。所以自动收回确实属于新的安全决定，裁定稿给了「改为：自动关闭」的出口，处理得当。
- 不足：用户说的「与岗位绑定的授权」，最可能指的是派生数据范围（`OWN_ORG_UNIT` 等）。裁定稿只说审批路由跳过此人，没有说停薪留职期间派生范围是否照常生效（S5）。

**第 4 条（多 3 项）：理由站得住。**
- `OrgDirectory.findOrgUnitHead`、`findRegionalReceivablesManager`（`api/OrgDirectory.java:19、22`）确有调用方；撤掉同步后，负责人两列（WF:34-35）没有别的维护途径。
- 岗位 ID 被入职、调岗引用，投产后需要能新建岗位。
- 合并要跨多个员工聚合，事务方案留给 one-data 二选一，有 owner，建议给出时点（B2 开工前）。

**第 10 条（不等 T-13）：理由站得住。**
- 决定性的理由是第 1 点：ADR-0055:48 已由用户经 TRN-05 批准「不保留 A8 单点登录」。第 3 点（保留就要保留一条 A8 运行时连接）也成立。
- 第 2 点「日活是老系统的」偏弱，可以删去，或改为「A8 门户随 ADR-0054 停用」。
- 日志取数照 ADR-0037 登记，用户要的数据保留了，只是不作为删除的闸门；差异写得明白，并给了「改为：按日活决定」的出口。

## 3. 与 W2 设计、ADR-0066/0067 的一致性；有无循环依赖

一致的部分：
- 单一 ID 空间：W2 中 `change_command_id` 与 `revocation_separation_command_id` 引用的都是同一条命令。
- 生效日左闭右开、HELD 期间员工保持 EMPLOYED、`separated_at` 删除。
- 「流程模块不建表，迁入产物落 integration」（ADR-0066 决定 8 第 4 条）。
- 审计不依赖编号模块。

冲突与遗漏：
- **W2 §1 与 ADR §1.4（补登）冲突**：W2 允许在没有版本覆盖的空档补登、在开放版本之前补前史，更正走同日修订（DATA-RULE-01）；ADR 的写法是「生效日早于受影响版本的起始日即拒绝」。两边须统一（M2）。
- **W2 §2.1 与 ADR §7.1（`login_name`）冲突**：W2 把它迁到 `external_identities`，ADR 直接删除，删除时点也不同（ADR 定 D2，W2 定在数据修复批 W2）（M10）。
- **ADR-0066 决定 1 第 3 条、ADR-0067 决定 1 第 4 条未被引用**：
  - identity（基础层）调用 workforce 的放行用例并订阅新事件，只能经 `@NamedInterface`，并须登记进《平台所用组织接口清单》；
  - kernel（`SeparationReview`、`ExternalSubjectEmployees`）、audit 的主体种类、integration 的表结构变化，如果晚于 W0 冻结点，就是破坏性变更，须走 ADR-0067 决定 5 的通道。
  - 全篇没有提到 0066、0067 的这两处约束（M4）。
- **§14.5 与 ADR-0066 决定 4 第 5 条字面不一致**：ADR-0066 写的是平台自有种类留在审计内部的「枚举」，ADR-0068 改为登记表；与 ADR-0033 第 7 项第 2 条的「text + CHECK」也不一致（M5）。业务单据「以类型码记录、审计只校格式」一点相容。
- **循环依赖：没有硬循环。**
  - W2 等 ADR-0068 的答复，ADR §1.4 的延后以 W2 签发为触发条件：这是先后次序，不是循环。
  - REG 实施 ADR-0068 §14.5 定下的形态，退休 `SYNC_RUN` 又在 REG 之后：同样只是次序。
  - 运行时有一处回调：identity 运维命令调用 workforce 放行用例，放行又经 kernel 端口回到 identity 的 `AdministratorSeparationReview`。不构成模块边上的环，但建议把运维命令放到 workforce 一侧，可以同时省掉 M4 的接口登记（S9）。

## 4. 安全

- **离职（已生效）**：沿用 ADR-0055:67。会话由 `SessionPrincipals` 逐请求校验兜底；identity 现在是 `@ApplicationModuleListener` 异步处理（`HandleOrgSnapshotChange.java:30-31、65`），这一点保留可以接受。
- **待放行（HELD）**：员工保持在职，授予和会话都保留，这符合 ADR-0028 的本意。但有两个缺口（M1）：
  - 现实现 `AdministratorSeparationReview.usableHolders`（:66-73）只看 EMPLOYED，不排除其他 HELD 中的人；`retained` 判定（:56）也不排除自己就在 HELD 中的放行人。ADR-0055:69 要求「不在待放行离职中」。ADR §2.2 写「只把调用方改为离职命令」，等于默认实现不变。
  - 同步时代一次运行一次性审完全部离职；现在改为每条命令各自一个事务，两条管理员离职并发执行时都会看到「剩余 2 名」，结果会突破「少于 2 名仍暂停」的下限。
- **复职**：由 `EmployeeReinstated` 承载，只开基础授予，与 ADR-0055:71 一致；但 §1.3「离职之后不得再录更晚的命令」把复职也挡住了（M3）。
- **停薪留职**：B 类推荐保留会话与授予，不算留任，不计入可用超管，不能进入管理模式，持双人逐人级角色的生成敏感角色复核。安全上可以接受；派生范围的说明见 S5。
- **新载体是否会丢数据：设计成立。**
  - 新表的外键用 ON DELETE RESTRICT，不使用 CASCADE，拒绝 DELETE 和 TRUNCATE；
  - C 上线前预检旧表 HELD 行数，D2 用 DO 块断言后才删表；
  - 已复核 `sync_runs` 没有拒删触发器（WF:129 起），只有测试 `EmergencyLoginEmploymentIT.java:131、208` 删过它，所以 C 之前的预检是必要的，ADR 已经写了。
  - 已放行的旧行在 D2 随表删除，以审计（MUST_AUDIT:47-50）为证，投产前没有生产数据，可以接受。
  - 新缺口：B 到 C 之间，本地离职命令已经生效，但 identity 还没有订阅新事件，授予不会关闭、应急账号不会停用（M11）。
