## 0. 一屏结论

1. **按两层分成立，且是本复核最有价值的部分**：「契约与数据形状」与「策略 / 配置 / 供应商」两层与仓库已有三套规则一一对上——ADR-0035（契约演进）、（配置类按版本与生效日）、ADR-0039（外部系统只在集成层）。冻结与变更通道可以直接挂在这两层上，不必另造机制。
2. **三档分法基本成立，但要改四处**：
   - (a) 「档」是模块属性，「层」是模块内部的切面：每个模块都有两层，档只决定骨架的稳定要求。
   - (b) `platform.integration` 不能整体标「易变」：它是零出边、被 5 个模块依赖的 L0 模块，端口（api 里的中性 record）必须最稳；易变的只是端口背后的适配器。
   - (c) 「核心层只依赖 kernel 与组织 BC」实为「组织地基例外」，须明文写出：identity、approval、numbering、签章服务都依赖 `organization.workforce`（盘点 G-5）。
   - (d) 档名「核心」与 DDD 的「核心域」（CORE DOMAIN，指最体现业务特色的部分）同名异义，意思正好相反，须交 one-glossary 改名（暂用「基础层 / 骨架层 / 易变层」）。
3. **逐模块改判 5 处**：
   - numbering 由核心改为中间：规则由财务定、常变，且 `kernel.DocumentType` 枚举了业务单据类型。
   - scheduling 由中间改为核心：L0、无业务语义。
   - 参考数据移出平台（盘点 P8）。
   - 保存期不是独立模块，而是文件服务的策略层（拆出条件按盘点 P3(b)）。
   - migration 移出平台与易变层，改为流程或工具类模块（盘点 P10）。
4. **三条守护**：
   - ① 依赖方向可以自动化，代价小，主要误伤是组织地基边，登记后即可消除；「不认识业务对象」的语义部分误伤高，只作复审项。
   - ② 无法可靠自动化，建议做成「策略项登记」加复审，不做字面量扫描。
   - ③ 已有大半（ADR-0039、`ExternalConnectionIsolationTest`、ACL 用语禁用、G-I1/G-I2），只缺「第三方 SDK 只在集成层」一条。
5. **冻结**：建议冻结「基础层与骨架层的契约与数据形状层」以及「集成层端口」，策略层按 §12.2 走版本，适配器不冻结。时点与审批通道都有三种候选，并列交用户（§3）。关键事实：TRN-03 通用审批先行上线就是首次生产（ADR-0054 决定 3 第 9 条），先行上线所用的平台模块届时无论如何都进入 ADR-0035 兼容期。
6. **准入**：9 条条件，判定人分三级（§4.1）。按这 9 条试判：
   - **退出**：migration。
   - **待准入**：AI 外发闸。使用面（3 个 BC）与无业务语义两条已满足；定名、负责会话、模块 ADR 未满足。
   - **未准入**：提醒与待办（使用方都是推断，前提 scheduling 定位未定）、出件（待版式清单）。
   - **不入平台**：参考数据。
7. **ADR 写法**：「分档、冻结、准入」是三个可以分别采纳或拒绝的选择，按 `_readme_lifecycle.md` 第 7 节「一份一决定」应拆份。草案按派工写成一份，「合一还是拆三份」单列交用户确认（U1）。

## 2. A 适配复核

### 2.1 三档分法

| 项 | 内容 |
|---|---|
| 要求 | 每个平台模块标一个档，档决定：能依赖谁、冻结多少、变更走哪条路。档的判据必须可判定，不能凭印象 |
| 收益 | 新会话与 Codex 卡一看就知道哪里不能随手改（老系统的 AI 生成错误主要就是随手改共用件，ADR-0004 背景）；把盘点里分散的「变化原因」收成三类；准入时直接给出档位 |
| 代价 | 多维护一个登记字段；档与 ADR-0051 决定 7 的 L0–L14 分层是两个维度，图上要同时表达（intent 要求「分档标签上分层总图」）；判据写不清会变成新一轮争论 |
| 把握 | 中高。三档与仓库已有的 `kind`（shared-kernel / platform / technical）大体重合，只是多出「稳定性」这一轴 |

**须修正的四点**：

1. **档是模块属性，层是模块内部的切面。** 初稿把「保存期」「预览服务商」「AI 外发闸」各列一档，混淆了模块和能力。改为：每个模块标一个档；每个模块都按两层写明内容。易变层只装集成层的适配器，以及一次性的东西。
2. **集成层要拆成端口与适配器两部分。**
   - 现状：`platform.integration` 出边为 0，被 workforce、approval、audit、identity、numbering 依赖。已批草案还会让文件服务、签章服务、AI 闸依赖它，盘点预计业务 BC 有 11 个。
   - 被依赖最多的东西必须最稳。按通行的 SDP 说法（未核实）也是如此：零出边、高入边的模块应当最稳定，而且应当是抽象。
   - 所以端口（api 里的中性 record 与接口，ADR-0039 决定 1 第 3 款）按基础层契约对待；厂商适配器（infrastructure 包内）才是易变层。
3. **组织地基例外。**
   - 现状：identity、approval、numbering 依赖 `organization.workforce`，approval 还依赖 `organization.attendance`，已批签章稿订阅 workforce 的离职事件。
   - Evans 原文正是拿组织架构图当通用子域的例子，所以把 `organization.workforce`、`organization.attendance` 定为「组织地基」，允许基础层与骨架层依赖它们，有出处。
   - 代价：组织地基本身是业务 BC，它的 api 也要按基础层的稳定要求来管。否则地基一动，平台跟着动。
   - 这一点要写进 ADR，对应盘点 G-5「平台只依赖组织 BC」的成文要求。
4. **档名与「核心域」冲突。** DDD 的核心域（CORE DOMAIN）指最体现本业务特色、最值得投入的部分；初稿的「核心」指与业务完全无关的部分，意思正好相反。按 CLAUDE.md 第 2 条交 one-glossary：在同一 bc 内查重，并处理同名异义。本稿暂用「基础层 / 骨架层 / 易变层」。

### 2.2 按两层分

| 项 | 内容 |
|---|---|
| 要求 | 每个模块写明两层各包含什么。契约与数据形状层：api 类型与方法、events、OpenAPI 路径、表 / 列 / 约束、错误码、权限码。策略层：配置版本、DMN、阈值、供应商 |
| 收益 | 冻结的对象变得可判定：两层各自已有现成的变更规则——契约层走 ADR-0035，策略层走 §12.2 配置类（新增版本、按生效日、不追溯），供应商走 ADR-0039 加 ADR-0041 决定 6 的选型适配 |
| 代价 | 中间层须为每个策略项选好载体。DMN 被 ADR-0041 决定 1 推迟到第一张真实决策表时另开 ADR 选型，所以初稿守护②里的「DMN」要改写为「版本化配置表（DATA_DESIGN_CHECKLIST §14.1 D15）或经另开 ADR 选定的 DMN」，否则与已采纳 ADR 抵触 |
| 把握 | 高 |

### 2.5 三条守护：实现、代价、误伤

**① 基础层不认识业务对象，依赖只指向 kernel、基础层、组织地基与集成层端口；骨架层另可依赖基础层与组织地基。**

- **实现**：
  - (a) 在 `architecture/ddd/contexts.yaml` 给平台模块加 `tier` 字段（一个事实只手写一处，ADR-0041 决定 4）。
  - (b) `build_architecture.py` 已实现 A1（已建边集合等于 `module-dependencies.txt`），在此基础上加「边的档位方向」校验，经 `build_all.py --check` 运行。
  - (c) `ModuleDependencyTest` 加禁止边与传递闭包断言：基础层与骨架层不得到达组织地基以外的业务 BC。ADR-0051 守护第 1、2 条已计划同类断言，可共用实现。
- **代价**：一张卡；改 SSOT schema 与生成器，加 `--self-test` 的拦截与放行用例。
- **误伤**：依赖方向检查的误伤低，只有组织地基的 5 条边，登记后即消除。「不认识业务对象」的语义检查（按 `terms.yaml` 的 bc 字段判断基础层标识符是否属业务 BC）误伤高：`EmployeeId`、`DocumentReference` 都会撞上。建议只作复审项，或只出报告不拦合并。已知命中 1 处：`kernel.DocumentType`。
- **现有编号**：G1（Modulith `verify`）、`ModuleDependencyTest`、ADR-0051 守护第 1–3 条。

**② 骨架层的策略项必须有载体（版本化配置表、DMN、集成端口），不得写死。**

- **实现**：
  - 每个骨架层模块在 `backend/architecture/` 下维护一份「策略项登记」：策略项、载体、配置键或版本表、批准人类别（§12.2）。
  - 测试只核对登记里的配置键存在且受 G46 前缀约束，版本表符合 D15。
  - 复审清单（DATA_DESIGN_CHECKLIST §14 或 `quality/review-briefs/03-adr.md`）加一项：「新增阈值、期限、路由是否登记为策略项」。
- **代价**：中等，主要是持续维护登记。
- **误伤**：如果改做「数字字面量扫描」，误伤高（分页上限、重试次数、HTTP 状态码都会被扫到），**不建议**。登记加复审的方式只会漏拦，不会误伤。
- **现有编号**：G19（Flowable 只在 approval 的 infrastructure）、G45（编号种子）、G46（配置键前缀）、ADR-0007（业务判定不进引擎）。

**③ 易变部分只在集成层（ADR-0039）。**

- **已有**：ADR-0039 决定 1 与 7、`ExternalConnectionIsolationTest`（`java.net.http`、JDBC 驱动只在集成层）、`LegacyShapeTest`、CS-2.29 / G-C5 的 ACL 用语禁用、G-I1 连接工厂、G-I2 集成登记册。
- **缺口**：第三方厂商 SDK 包（对象存储、预览、电子印章、模型客户端如选 Spring AI）没有统一的包白名单。
- **补法**：加 ArchUnit 规则「厂商 SDK 包只在 `platform.integration..`」，包清单取自集成登记册（G-I2），不另手写。
- **代价**：小。
- **误伤**：低；已批的文件、签章、预览、AI 四稿都要求适配器只在集成层，与这条规则一致。

**建议另加两条（不在初稿内）**：

- ④ 准入登记校验：`kind: platform` 的模块必须有 `tier`、`owner`、`adr`、至少 2 个使用方的出处；由 `build_architecture.py` 校验。
- ⑤ 冻结快照：见 §3.4。

## 3. B 冻结

### 3.1 要不要冻结

| 项 | 内容 |
|---|---|
| 要求 | W1–W5 的业务 BC 都建在平台上，平台契约一改，下游就要连锁返工。§6「公共基础先行」已要求共用构件「建好并冻结」，§13 第 4 条要求「地基行冻结」，但没有说清冻结的对象、时点与解冻通道 |
| 收益 | 并行建造时不会互相踩；Codex 与子代理改共用件有硬拦截；把 §6、§13 两处口头冻结落成可执行的规则 |
| 代价 | 冻结后改契约要走审批，W0 设计不足的地方会被迫靠「新增」绕开，存在接口膨胀的风险（G4 上限 12，文件服务已用 11）；还有 CS-1.8 与 CS-1.9 的张力：为了冻结而预先设计后续批次才用到的能力，就是违反 CS-1.8 |
| 把握 | 高（冻结本身）；中（时点，取决于用户的取舍） |

**结论：要冻结，但只冻契约与数据形状层，而且「冻结」不等于「不许新增」。**

### 3.2 冻结什么（档 × 层）

| | 契约与数据形状层 | 策略 / 配置 / 供应商层 |
|---|---|---|
| 基础层 | **冻结**：可做兼容新增（ADR-0035 第 3 条的定义）；破坏性变更走 §3.3 的通道 | 不冻结；配置按 §12.2 出新版本、按生效日生效 |
| 骨架层 | **冻结骨架**：同上 | 不冻结；须是已登记的策略项（守护②） |
| 集成层端口 | **冻结**（同基础层） | — |
| 集成层适配器 | — | 不冻结；但引入新类别的厂商仍要按 ADR-0041 决定 6 做适配评审并起 ADR，涉及数据外发的要做安全与法务评审 |
| 档位登记与准入清单 | 按 SSOT 冻结写法（`status: frozen`、解冻条件、`change_log` 写解冻理由与对应校验；只改文字说明不算解冻） | — |

不冻结的对象：未准入的候选模块，以及尚未建造的模块。按 CS-1.8，不为冻结而预建。

### 3.3 时点与变更通道（候选并列，不预选）

**时点**：

| 候选 | 做法 | 收益 | 代价 |
|---|---|---|---|
| T-A W0 结束统一冻结 | W1 开工前冻结 W0 已建的平台模块 | 一个节点，最好管 | W2 及以后才建的模块（一次性链接、AI 闸）要另定时点，实际还是退化成 T-B；W0 的设计必须足够完整 |
| T-B 逐模块冻结 | 每个模块在其**第二个**使用方 BC 开工前冻结（第一个使用方与模块同批建，期间可改） | 与「第二个使用方时抽模块」的先例一致；契约经第一个使用方实际用过才冻 | 节点多，需要登记；跨批次模块的冻结时点分散 |
| T-C 不另设冻结点 | 以首次生产为界，直接按 ADR-0035、ADR-0038 执行 | 不新增规则 | 建造期互相踩的问题不解决；§6、§13 的「冻结」仍然只是口头要求 |

**时点相关事实**：

- 通用审批先行上线（TRN-03）就是生产使用。按 ADR-0054 决定 3 第 9 条，迁移基线在「首次生产与首次全量模拟两者取早」时关闭；ADR-0035 的兼容规则自首次生产部署起生效。
- 因此 identity、audit、approval、文件服务、签章服务一段（实体章台账）在先行上线时，**不论选哪个候选**都进入兼容期。三个候选的差别只在：W0 建成到先行上线之间这一段，以及不参与先行上线的模块。
- 「先行上线是否就是 ADR-0035 所说的首次生产部署」，须请 one-architecture 核实读法。

**冻结后的破坏性变更通道**：

| 候选 | 兼容新增 | 破坏性变更 | 代价 |
|---|---|---|---|
| 甲 | one-architecture 审核并登记 | 新 ADR，用户批准 | 最严；投产前每次破坏性改动都要用户批，节奏慢 |
| 乙 | 同上 | 首次生产前：one-architecture 裁定，one-coordinator 核对，登记 `change_log`，告知用户；首次生产后按 ADR-0035（`Contract-Break:` trailer、复审） | 中等；可能出现会话自批 |
| 丙 | 同上 | 按档区分：基础层与集成端口走甲，骨架层走乙 | 规则多一层，但与「基础层改动面更大」相称 |

各候选共同之处：

- 改共用件的代理先停下报告，由整合者统一改（§6 原文）。
- `module-dependencies.txt` 的改动照旧经 CODEOWNERS（ADR-0003 决定 3）。

### 3.4 冻结的守护（建议⑤）

- 每个已冻结模块生成一份「api 签名快照」：api 与 events 包的类型与方法签名。另有一份平台 schema 的表结构快照；ADR-0038 开放期改基线时已有 `pg_dump --schema-only` 对比流程，可复用。
- 快照变化即失败，须提交 trailer（暂名 `Platform-Contract:`）写明是兼容新增还是破坏性变更，并附批准出处。
- 首次生产后，G-C1、G-C2（ADR-0035）接管 OpenAPI 与事件部分，快照只保留 Java api 签名与表结构两项。
- 代价：中等（一张卡）。误伤：每次兼容新增都要写 trailer，属于有意设置的摩擦。

### 3.5 与现有冻结规则的关系

| 现有规则 | 冻结对象 | 与本规则的关系 |
|---|---|---|
| 已采纳 ADR 正文冻结（§12.1） | 决定文字 | 对象不同。本规则冻结代码契约与表结构；档位与清单放在 `contexts.yaml`（SSOT），不写进 ADR 正文，避免每次改档都要新开 ADR（同 ADR-0051 决定 1「规范性 / 参考性」的做法） |
| SSOT 冻结（用户正在逐节点重做，intent `2026-10-20-154221`） | 架构源数据 | 档位登记直接采用同一写法：`frozen`、解冻条件、`change_log` |
| §6 公共基础先行、§13 第 4 条地基冻结 | 共用构件、地基行 | 本规则是它们的细化：给出对象、时点与通道；平台模块即「地基」 |
| ADR-0035 契约演进 | 对外契约（首次生产起） | 冻结属治理，管首次生产之前；兼容属技术，管首次生产之后。ADR-0035 第 2 条说首次生产前契约「可直接改」，是允许而不是要求，加审批不冲突（拟判相容，交 one-architecture 核） |
| ADR-0038 迁移基线 | 已应用迁移 | 开放期内改基线在技术上可行，冻结只增加审批；两者不冲突 |
| ADR-0054 G-9 判据冻结 | 投产判据 | 无关，同名而已 |

## 4. C 准入与退出

### 4.1 准入条件

| # | 条件 | 判据与出处 |
|---|---|---|
| C1 | 使用面 | **平台服务**：至少 2 个 BC（含平台模块）**已确认**使用。已确认指代码 import、已采纳 ADR、或用户 intent 明载；盘点矩阵中标△的推断不算。**技术模块**（无 api，经框架或 kernel 端口全局使用）以「全局隐式使用」代替。先例：「第二个使用者时抽出」 |
| C2 | 无业务语义 | 不认识组织地基以外业务 BC 的对象；业务分类经登记数据传入（访问级别、保存类别、`DocumentReference`），代码里不枚举业务单据类型。依据：Evans Generic Subdomains；ADR-0039 决定 1 |
| C3 | 依赖方向 | 基础层只依赖 kernel、基础层、组织地基、集成端口；骨架层另可依赖基础层。不依赖其他业务 BC，不订阅它们的事件（组织地基的事件除外）。并入已建边与规划边后无环（`aggregates_dep_check.py` 与 `ModuleDependencyTest`） |
