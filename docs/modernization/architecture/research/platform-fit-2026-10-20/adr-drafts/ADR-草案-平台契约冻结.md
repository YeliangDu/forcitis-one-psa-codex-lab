## 决定

### 1. 冻结范围（P2a 选 a，P2c 选 b）

1. 只冻结平台模块与 kernel 两类对象；业务 BC 不在本稿范围。
2. 冻结的内容：
   - api 签名；
   - 事件载荷；
   - 表结构。
3. 不冻结的内容：
   - infrastructure 与 web 的实现、仓储；
   - 策略面（按 §12.2 出新版本）；
   - 适配层的适配器（新增一类厂商仍按 ADR-0041 决定 6 起 ADR）；
   - 前端共用包（仍按 §6）。
4. 组织上游只冻结分层 ADR 中《平台所用组织接口清单》所列的 `@NamedInterface` 接口。这份清单复用依赖清单机制；清单内接口变更时，由人事侧守护提示通知平台 owner。
5. 暂不冻结的对象：
   - identity：等 C1 联合身份定案后冻结（ADR-0039 决定 3、ADR-0055 决定 2）；
   - 未准入的模块与尚未建造的模块：不冻结（CS-1.8）。

### 2. 冻结例外

下列类型在相应清理完成之前不冻结，清理完成后随所属 api 一起冻结。

- **integration 的 api**：
  - `LegacyInbox`、`LegacyTodo`、`SourceOrgSnapshot`、`SourceOrgUnit`、`SourcePerson`、`SourcePosition`、`OrgSource`、`OrgShortNames`，按 ADR-0055 决定 6 删除，或改为迁入适配器；
  - `SsoTicketVerifier`、`SsoVerdict`、`TicketSubjects`，随 C1 处理；
  - `Wecom*` 需中性化，用语交 one-glossary。ADR-0039 的条号待 one-architecture 在占号前核对：决定 5 第 2 点列的是 `ExternalSystemUnavailableException`、`InboxSource`。
  - `SourceObjectKind` 随迁入增加取值，按兼容新增处理。
- **kernel**：`WecomUserId` 移出、`ExternalSubjectEmployees` 随 C1、异常改为中性名（ADR-0039）。
  - `DocumentType` 不列入例外：它在收口窗口内就会按分层 ADR 决定 4 删除。

### 3. 冻结时点（P2b 选 A）

1. **冻结点**：W0 结束、W1 开工之前，冻结 W0 已建的平台模块与 kernel。之后才建的模块，在各自建造批结束时冻结。
2. **收口窗口**：冻结前给 W0 已建模块 2 周收口窗口。窗口内：
   - 完成分层 ADR 决定 4 的单据类型注册表改造，以及组织接口的 `@NamedInterface` 标注；
   - 契约改动集中批量审核。
3. **唯一契约源**：冻结时产出「版本化平台接口清单」，作为平台契约的唯一来源。
   - 清单内容：各模块的 api 签名、事件载荷、表结构，以及版本号；
   - 清单由代码生成，不手写；
   - 后续每次变更都升版本号，并写入 `change_log`。
4. **先行上线**：
   - TRN-03 先行上线承接的是生产业务，所以它就是 ADR-0035 所说的首次生产。
   - 先行上线所用的模块（approval、identity、audit、文件服务、签章服务一段、`organization.administration`）都在 W0 建造。ADR-0054 没有规定先行上线在 W0 结束之前还是之后。
   - 取代 ADR-0035 第 2 条的有效窗口，是从冻结点到首次生产为止：
     - 如果先行上线早于 W0 结束：先行上线所用的模块直接按 ADR-0035 管理，本稿的取代只对其余平台模块有效；
     - 如果先行上线晚于 W0 结束：取代的有效窗口是从冻结点到先行上线。
   - 「首次生产」按系统整体还是按模块计，交 one-architecture 核对。

### 4. 兼容新增（判据写死）

只有下列三类算兼容新增，其余一律按破坏性变更处理：

1. 接口新增方法，且带默认实现；
2. record、事件、表新增可空字段（列）；
3. 新增路径，或新增版本路径；旧路径不变。

兼容新增由 one-architecture 审核：时限为 1 个工作日，可以批量审核，审核结果登记进 `change_log` 和版本化接口清单。

### 5. 破坏性变更的批准（P2d 选丙）

| 对象 | 通道 |
|---|---|
| 基础层模块、kernel、对外接口（公开端点与对外部系统的出站契约） | 新 ADR，用户批准 |
| 公共服务层模块 | one-architecture 定，one-coordinator 核对，报用户 |

1. 基础层模块清单：kernel、identity、audit、eventing、web、idempotency、scheduling、文件服务。以分层 ADR 的分层登记为准，登记有变化时按登记执行。
2. `module-dependencies.txt` 照旧经 CODEOWNERS 评审。
3. 要改共用件的代理先停下报告，由整合者统一改（§6 原文）。
4. 首次生产之后，除上述通道外，同时适用 ADR-0035（`Contract-Break:`、排空、弃用期）。

### 6. 解冻条件

冻结的契约只在下面两种情况下整体评审或解冻：

- **年度评审窗口**：每年一次，由 one-architecture 发起，one-coordinator 排期。
- **专项评审**：出现跨 BC 的破坏性需求时发起。

两种情况的结论都按决定 5 的通道批准；解冻的范围写入 `change_log`。只改说明文字，不算解冻。

### 7. 冻结状态的记法

每个模块在分层登记中记：

- `frozen`、冻结日期、当前接口清单版本、例外项；
- `change_log`：每条写理由、类别（兼容 / 破坏性）、批准出处、对应的校验。

### 8. 与现有规则的关系

- **已采纳 ADR 正文冻结**：冻结的是 ADR 文字；本稿冻结的是代码契约。两者对象不同。
- **、§13 第 4 条**：本稿是两条的细化；手册改为引用本稿。
- **ADR-0035**：首次生产之前，第 2 条在平台模块与 kernel 范围内被取代；首次生产之后，全文照常适用。
- **ADR-0038**：基线开放期内仍可直接改基线，本稿只是在其上加审批。

## 影响面

- **登记**：分层登记新增冻结字段与 `change_log`；新增版本化平台接口清单。
- **守护**：冻结快照测试；兼容新增判定。
- **文档**：
  -、§13 第 4 条引用本稿；
  - ADR-0035 状态行追加「（第 2 条范围已被 ADR-本号 取代）」。
- **排期**：W0 末尾预留 2 周收口窗口。
- **代码与数据**：本稿本身不改；收口窗口内的改造见分层 ADR。

## 迁移方案

1. 入库：分层 ADR 入库后，本稿占号入库；在同一提交中改 ADR-0035 的状态行。
2. W0 结束前 2 周：开启收口窗口，完成改造与批量审核。
3. 冻结点：
   - 生成版本化平台接口清单 v1 与快照基线；
   - 写入第 2 条的例外项；
   - 按第 7 条登记冻结状态。
4. 之后：
   - 例外项随 ADR-0039、ADR-0055 的清理卡逐项移出；
   - C1 定案后冻结 identity；
   - 新模块在其建造批结束时冻结。

## 回滚方案

- 不采纳或废弃时，删除下列内容：
  - 冻结字段与 `change_log`；
  - 版本化接口清单与快照基线；
  - 快照测试；
  - ADR-0035 状态行的括注。
- 已经批准的契约变更保留，不回退。

## 需同步修改的守护规则

1. **冻结快照测试**（one-architecture；在冻结点之前完成）
   - 比对对象：已冻结模块的 api 签名、事件载荷、平台 schema 的表结构，与版本化接口清单比对。
   - 有变化即失败。放行条件：带 `Platform-Contract:` trailer，写明类别与批准出处；兼容新增还须符合决定 4 的三类判据。
   - 例外项不比对。
   - 首次生产之后，OpenAPI 与事件部分交由 G-C1、G-C2 负责。
2. **`build_architecture.py`**（one-architecture；采纳 PR）
   - 校验冻结字段与 `change_log` 的格式，以及每条变更都有批准出处。
   - 核对 `change_log` 与接口清单的版本是否一致。
3. **人事侧守护**：组织接口清单内的接口发生变更时，CI 提示通知平台 owner。与分层 ADR 守护第 4 条是同一实现。

## 后果

**收益**：
- 并行建造时，共用件有硬拦截；
- 兼容新增有固定判据和 1 个工作日的审核时限，不会卡住进度；
- 平台契约只有一个来源（版本化接口清单）。

**代价**：
- W0 要多出 2 周收口窗口；
- 冻结后改基础层或对外接口要用户批准，节奏变慢；
- 冻结会诱导用新增来绕开，导致接口膨胀（文件服务 api 已用 11/12），由分层 ADR 的拆分条件兜底。

**交 one-architecture**：
- 核对 `Wecom*` 引用的 ADR-0039 条号；
- 核对「首次生产」按系统整体还是按模块计；
- 安排快照测试与版本化清单生成的实现（可交 Codex）。
