## 背景

### 触发与拆份

- 触发：用户问「平台模块是不是要冻结？」（intent `2026-10-20-225316`），任务号 ARC-1020-COO-11，属用户指派。
- 拆份：按生命周期第 7 节，从《平台模块分层、依赖方向与准入退出》（另一份 ADR-NNNN，下称「分层 ADR」）拆出。本稿引用它的「两面」（契约与数据形状面、策略面）、三层与分层登记。分层 ADR 未采纳时，本稿不能采纳。
- 依据：
  - 复核：`architecture/research/platform-fit-2026-10-20/平台分档适配复核.md` §3；
  - 复审：`architecture/proposals/REVIEW_ADR_PLATFORM_TIERS_2026-10-20.md`。

### 现有「冻结」只是口头要求

用户已采纳的两条规则都要求冻结，但没写清冻结的对象、时点与解冻通道：

- SESSION_PLAYBOOK §6「公共基础先行」：并行写业务之前先建好并冻结共用构件，改动由整合者统一做。
- §13 横切矩阵第 4 条：地基行在派功能代理前做进 kernel 或 platform 并冻结。

### 与 ADR-0035 第 2 条的关系（取代的理由）

- ADR-0035 第 2 条由用户定，内容是「首次生产部署之前，契约可直接改，不需要兼容过渡与弃用期」。
- 本稿的 T-A、T-B 两个候选会在首次生产之前给平台模块契约加上审批，实质上限制了这一条。所以「取代」字段写为部分修订，范围只限平台模块。
- 如果用户选 T-C，或不批准修订（U1），删去「取代」一行。
- 取代的范围不含业务 BC 契约，也不含 ADR-0035 的其余条款（兼容定义、排空、弃用、G-C1–G-C7）。

## 决定

### 1. 首次生产的读法

- TRN-03 通用审批先行上线承接的是生产业务（ADR-0054 决定 1 唯一例外）。所以先行上线就是 ADR-0035 所说的「首次生产部署」，也是 ADR-0038、ADR-0054 决定 3 第 9 条所说的「首次生产」。
- 先行上线所用的平台模块，自先行上线起按 ADR-0035 管理，不受本稿时点候选的影响。
- **先行上线与 W0 结束的先后**：先行上线所用的模块（approval、identity、audit、文件服务、签章服务一段，以及 `organization.administration`）都在 W0 建造，所以先行上线不早于这些模块建成。但 ADR-0054 没有规定它在 W0 结束之前还是之后，具体日期由先行上线剧本定。
- **取代 ADR-0035 第 2 条的有效窗口**：从本稿冻结点（决定 5）起，到首次生产为止，只限平台模块。按先后分两种情况：
  - 先行上线早于 W0 结束：先行上线所用模块的窗口为空，直接按 ADR-0035 管理；取代只对未被先行上线使用的平台模块（一次性链接、AI 外发闸等）有效。
  - 先行上线晚于 W0 结束：先行上线所用模块的窗口是「冻结点至先行上线」；其余平台模块的窗口到其首次生产为止。
- 交 one-architecture 核对两点：ADR-0035 的「首次生产部署」是按系统整体算（先行上线后全部契约即进入兼容期，窗口随之结束），还是按模块算；ADR-0054 决定 3 第 9 条「首次生产与首次全量模拟取早」是否影响本条读法（该条管的是迁移基线关闭）。

### 2. 冻结什么

| 层（分层 ADR 决定 1） | 契约与数据形状面 | 策略面 |
|---|---|---|
| 基础层 | 冻结 | 不冻结，按 §12.2 配置类出新版本 |
| 骨架层 | 冻结骨架 | 不冻结，但须是已登记的策略项（分层 ADR 决定 4） |
| 易变层（integration） | 只冻结 `api` 包，有例外（第 3 条） | 适配器不冻结；新增一类厂商按 ADR-0041 决定 6 起 ADR |
| 组织上游（workforce、attendance） | 范围按 U3 | 不冻结 |

冻结范围之外的对象：

- 前端共用包仍按 SESSION_PLAYBOOK §6 执行，不在本稿范围。
- **kernel**：分层 ADR 决定 1 第 4 条规定 kernel 的稳定要求按基础层，所以 kernel 的契约（值对象、端口、事件信封、错误链类型）随基础层同时冻结，变更通道同基础层（决定 4、6）。kernel 冻结例外：
  - ADR-0039 的待清理项：`WecomUserId` 移出、`ExternalSubjectEmployees` 随 C1、异常改中性名，清理后冻结；
  - `DocumentType`：分层 ADR U1 选 (a) 时，新增单据类型码按兼容新增处理；选 (b) 时，列入例外直至改为登记制。
- 未准入的模块、尚未建造的模块不冻结（CS-1.8）。
- identity 在 C1 联合身份定案之前不冻结（ADR-0039 决定 3、ADR-0055 决定 2）。

### 3. integration 的 api 冻结例外

下列类型在 ADR-0039、ADR-0055 清理完成前不冻结，清理后随 api 冻结：

- `LegacyInbox`、`LegacyTodo`：ADR-0055 决定 6 删除。
- 组织同步类型 `SourceOrgSnapshot`、`SourceOrgUnit`、`SourcePerson`、`SourcePosition`、`OrgSource`、`OrgShortNames`：ADR-0055 决定 6 删除，或改为迁入适配器。
- `SsoTicketVerifier`、`SsoVerdict`、`TicketSubjects`：随 C1 处理。
- `Wecom*` 的中性化：用语交 one-glossary。ADR-0039 依据条号待 one-architecture 在占号前核对：决定 5 第 2 点列的是 `ExternalSystemUnavailableException`、`InboxSource`，没有直接列 `Wecom*`；复审原文称「决定 6 仍留中性化项」。

`SourceObjectKind` 随迁入增加取值，按兼容新增处理，不算破坏性变更。

### 4. 冻结的含义

1. **兼容新增**照常进行（定义见 ADR-0035 第 3 条），由 one-architecture 审核，并登记到分层 ADR 分层登记的 `change_log`。
2. **破坏性变更**的范围：ADR-0035 第 3 条所列；另加表的删列、改名、改类型。批准方式按第 6 条。
3. **改共用件的代理先停下报告**，由整合者统一改（§6 原文）。

### 5. 冻结时点（候选并列，见 U2）

| 候选 | 做法 | 后果与代价 |
|---|---|---|
| T-A | W0 结束、W1 开工前，冻结 W0 已建的平台模块；之后新建的模块随其建造批结束时冻结 | 节点少；W1 起每次兼容新增都要经 one-architecture 审核 |
| T-B | 逐模块冻结：在第二个使用方 BC 开工前冻结 | 契约先经第一个使用方实际用过再冻。但 approval、identity、numbering、audit 已有第二个使用方，选 T-B 等于采纳当天就冻结；与 TRN-03 扩大 approval 的工作冲突，扩的部分要逐项走兼容审核 |
| T-C | 不另设冻结点，以首次生产（第 1 条）为界，按 ADR-0035 执行 | 不修订 ADR-0035，删去「取代」；但会推翻 SESSION_PLAYBOOK §6、§13 第 4 条中「派功能代理前冻结」的要求（用户已采纳的规则）。选 T-C 须同时请用户决定是否改这两条 |

### 6. 破坏性变更的批准（候选并列，见 U4）

| 候选 | 做法 | 代价 |
|---|---|---|
| 甲 | 一律起新 ADR，由用户批准 | 最严，节奏最慢 |
| 乙 | 首次生产前：one-architecture 裁定，one-coordinator 核对，登记 `change_log`，告知用户；首次生产后：按 ADR-0035 执行 | 中等，有会话自批的风险 |
| 丙 | 基础层与 integration 的 api 走甲，骨架层走乙 | 规则多一层 |

各候选共同之处：`module-dependencies.txt` 照旧经 CODEOWNERS 评审（ADR-0003 决定 3）。

### 7. 冻结状态的记法

在分层 ADR 的分层登记中，每个模块写：`frozen`（是否冻结）、冻结日期、解冻条件，以及 `change_log`（每条写理由、类别、批准出处、对应的校验）。只改说明文字不算解冻。这一写法沿用用户逐节点冻结 SSOT 的做法（intent `2026-10-20-154221`），字段在本条定义，不依赖其他分支上的文件。

### 8. 与现有规则的关系

| 现有规则 | 关系 |
|---|---|
| 已采纳 ADR 正文冻结（§12.1） | 对象不同：那条冻结的是决定文字，本稿冻结的是代码契约与表结构 |
| SESSION_PLAYBOOK §6、§13 第 4 条 | 选 T-A 或 T-B 时，本稿是它们的细化；选 T-C 时与它们冲突（第 5 条） |
| ADR-0035 | 首次生产前，本稿部分修订其第 2 条（限平台模块）；首次生产后，ADR-0035 全文照常适用 |
| ADR-0038 | 基线开放期内改基线仍然可行，冻结只是在其上加审批 |

1. **冻结快照测试**

## 后果

- **收益**：并行建造时共用件有硬拦截；§6、§13 的冻结要求有了对象、时点与通道。
- **代价**：
  - 首次生产前改契约变慢；
  - 冻结会诱导用「新增」绕开，导致接口膨胀（文件服务 api 已用 11/12），由分层 ADR 的拆分条件兜底；
  - 例外清单要随清理卡持续维护。
