## 决定

### 1. 两面与三层

1. **两面**：每个平台模块的内容分为两面。
   - **契约与数据形状面**：api 与 events、OpenAPI 路径、本模块的表、列与约束、错误码、权限码。
   - **策略面**：配置、阈值、路由、供应商。
2. **三层**（暂名；「核心」与 DDD「核心域」同名异义，交 one-glossary 定名；`tier` 取值是标识符，须在采纳 PR 前定名）。称「层」而不称「档位」，是为了避开 ADR 头部「档位：正式 / 轻量」（生命周期第 3、6 节）；模块内容的两种切分称「面」（第 1 条），避免与「层」混用：
   - **基础层**：不认识业务对象，一次建对。
   - **骨架层**：骨架一次建对，策略常变。
   - **易变层**：随时可换。`platform.integration` 归易变层。它的 `api` 包被各层依赖，这是 ADR-0039 允许的唯一入口。端口目前并不中性（企业微信、老系统、来源对照类型都在 api 里），所以 api 不按基础层对待；它的冻结规则见冻结 ADR。
3. **组织上游例外**（暂名；原稿「组织地基」与 ADR-0051 决定 9「地基 BC」、横切矩阵的「地基行」同名异义，改名交 one-glossary）：
   - `organization.workforce`、`organization.attendance` 是业务 BC，但可以被基础层与骨架层依赖（盘点 G-5）。
   - 依据：Evans 把组织架构图列为通用子域的例子。
4. kernel 是共享内核，不计入平台模块，稳定要求按基础层。

### 2. 分层登记

1. **登记位置**：`architecture/ddd/contexts.yaml` 每个平台模块登记 `tier`、`owner`、`adr` 三项。
2. **使用方出处**：
   - import 类使用方由生成器从 `module-dependencies.txt` 推出，不手写（ADR-0041 决定 4）；
   - 只手写尚未建边的出处（已采纳 ADR、用户 intent 的条号）。
3. **规范性与参考性**（同 ADR-0051 决定 1 的分法）：
   - **所属层是规范性内容**，改层须走正式 ADR（决定 7）；
   - 使用方清单、模块所含能力是参考性内容，随复核直接更新。
4. **采纳时的分层**：
   - **基础层**：identity、audit、eventing、web、idempotency、scheduling、文件服务；
   - **骨架层**：approval、numbering、签章服务、一次性链接；
   - **易变层**：integration。
5. **登记改动**：
   - scheduling 由 `kind: platform` 改为 `kind: technical`。它与 idempotency、eventing、web 同类：无 api，经注解或框架使用。
   - migration 按 U3 改类。
6. **technical 模块与分层**：`kind: technical` 的模块（idempotency、eventing、web、scheduling）同样登记 `tier`，参与分层方向校验；不做使用方与准入字段校验，准入第 1 条按「全局隐式使用」人判。

### 3. 依赖方向

1. **基础层**只依赖：kernel、其他基础层模块、组织上游、integration 的 api。
2. **骨架层**另外可以依赖基础层。
3. 基础层与骨架层都不依赖组织上游以外的业务 BC，也不订阅它们的事件。订阅组织上游的事件属例外。
4. **业务分类经登记数据传入**（访问级别、保存类别、`DocumentReference`），不在代码里枚举业务对象。

   存量命中：`kernel.DocumentType`（QUOTE、TIMESHEET、JOURNAL_VOUCHER）被 numbering、approval（api、持久化、web、迁移）、`platform.web`、cost.timesheet 引用。处理方式二选一，见 U1：
   - (a) **明文允许单据类型码**：单据类型码作为「业务分类登记」，由 kernel 统一持有，可以被基础层与骨架层读取。
     - 理由：它是码值、不带行为，与编号种子一一对应（G45）；业务 BC 新增单据类型只加枚举值与种子行。
     - 代价：kernel 随业务 BC 的增加而增长，平台在类型层面「看得见」业务单据名。
   - (b) **限期登记例外**：在豁免登记中写明到期点（暂定：第一个 W1 业务 BC 新增单据类型之前），到期前改为登记制（字符串码经 numbering 登记表校验）。
     - 代价：numbering、approval 的 api、持久化与迁移都要改；在基线开放期（ADR-0038）内改动成本最低。

   numbering 归骨架层，理由是编号规则由财务确认、常变（ADR-0010、§12.2 配置类）。这与 DocumentType 的处理无关，不能用来豁免本条。

### 4. 策略项必须有载体

骨架层的策略项都要登记载体，三选一：
- 版本化配置表（SESSION_PLAYBOOK §14.1 D15、§12.2 配置类）；
- 经另开 ADR 选定的 DMN（ADR-0041 决定 1 的推迟条款）；
- integration 端口。

不得写死在代码里。业务判定不进流程引擎（ADR-0007）。

### 5. 易变部分只在集成层

1. 按 ADR-0039 决定 1 执行。
2. 另加一条：厂商 SDK 包只能出现在 `platform.integration..`，包清单取自集成登记册（G-I2）。
3. 新增一类厂商仍要按 ADR-0041 决定 6 做适配评审并起 ADR。

### 6. 准入条件

进入平台须满足下列 9 条。括注表示判定方式：「守护」指可以机判，「人判」指由人判断。

1. **使用面**：至少 2 个 BC（含平台模块）已确认使用。已确认指：依赖表中的边、已采纳 ADR、用户 intent 明载；推断不算（守护：生成器）。技术模块以「全局隐式使用」代替（人判）。
2. **无业务语义**：符合决定 3 第 4 条（人判，加复审）。
3. **依赖方向**：符合决定 3，并入已建边与规划边后无环（守护：`build_architecture.py`、`ModuleDependencyTest`、`aggregates_dep_check.py`）。
4. **两面写清**：两面的内容写明，策略项已登记（人判）。
5. **契约先行**：符合 CS-1.10，api 方法数 ≤12（守护：G4）。
6. **用语**：模块名与主要概念已经 one-glossary 登记，写明使用范围与 bc（守护：G37）。
7. **负责会话与守护**：有负责会话与画像，守护有落点（守护：生成器校验 `owner`）。
8. **有 ADR**：新增平台模块属模块边界，是 ADR 类（守护：生成器校验 `adr`）。
9. **同批建**：与第一个使用方同批建造，不预留（CS-1.8）（人判）。

**判定分工**：
- one-architecture 写适配判断（ADR-0041 决定 6）；
- one-coordinator 核对是否齐全；
- 用户经 ADR 批准；
- 依赖边经 CODEOWNERS 评审。

**过渡条款**：
- 6 份已批平台稿（intent `2026-10-20-221808`）与已建的 10 个模块，视同已满足第 1、8 条与适配判断，不重走评审。
- 第 6、7 条在登记时核对。未齐的登记为「待准入」，补齐后改为在册。
- 待准入期间可以按已批稿设计，但代码不落地（与已批稿「定名前代码不落地」一致）。

### 7. 退出、合并、拆分、改层

1. **触发与去向**：

   | 触发 | 去向 | 判定 |
   |---|---|---|
   | 已确认使用方降到 1 个 | 归回该 BC | 守护报告 |
   | 生命周期结束 | 下线或改类 | 人判 |
   | 与另一模块变化原因相同，合并后无环 | 合并 | 人判 |
   | api 达到 12 个 | 拆分 | 守护：G4 |
   | 出现第二种变化原因 | 拆分 | 人判 |
   | 发现业务语义，或依赖越层 | 降层或移出平台 | 守护加人判 |

2. **通道**：以上一律走正式 ADR，涉及代码与表的附迁移卡。
3. **复核时点**：每个建造批开工前随阶段复核进行（与 ADR-0051 决定 1 第 1 条同法）。
4. **本稿采纳时的状态**：

   | 模块 | 状态 | 说明 |
   |---|---|---|
   | 文件服务、签章服务、一次性链接 | 待准入 | 待定名与负责会话 |
   | AI 外发闸 | 待准入，待用户决定 | 用户首批 3 个场景（intent `2026-10-20-223058`）已触发已批 AI 底座稿「抽成平台模块」的条件。X1 补确认（`0a3706d3`）建议在第二份 AI ADR 中直接设独立平台模块（暂名 `platform.ai`，依赖 audit 与 integration，不被二者依赖），与已批稿「首个场景在所属 BC 设调用服务」不同；是否设已进收件箱问用户。如设，拟入骨架层：闸与限额的骨架稳定，限额数值与厂商常变；依赖符合决定 3 |
   | 提醒与待办 | 未准入 | 先定 scheduling 定位（盘点 G-1）；准入时须为登记制，平台不订阅业务事件 |
   | 出件 | 未准入 | W2 开工前按版式清单判定 |
   | 参考数据、全文检索、现场采集 | 不入平台 | — |
   | migration | 按 U3 处理 | — |

  - 「平台模块」：命中 0039、0051。0039 相容；0051 由文件服务基础稿处理（前置）。
  - 「准入」：命中 0039、0042、0051、0054–0057。0057 决定 3 相容，U3 选 (a) 时部分取代第 6 条；0054 是投产准入，无关；其余为别义。
  - `platform\.migration`：命中 0036。名称为「暂定」，改类不改决定。
  - 「共享内核」：命中 0003、0016、0033、0041、0046、0050、0051、0053，均相容。
  - 「DocumentType」：未命中，0010 讲的是编号规则，无关。
- **评审**：复审见上。正式档另须做 opus `architecture-critic` 对抗评审，由评审员重放检索。

## 备选方案（未采用）

- **只立准入、不分层**：回答不了依赖方向与改动面的问题。
- **把 integration 的 api 整体按基础层对待**：端口并不中性，ModuleDependencyTest 分不出端口与适配器（复审第 7 条）。
- **用 numbering 改判骨架层来豁免 DocumentType**：基础层与骨架层适用同一条规则，豁免不成立（复审第 2 条）。
- **手写 `consumers` 字段**：与依赖表重复，违反 ADR-0041 决定 4。
- **恢复 DDD 子域三分类作判据**：与 ADR-0041 决定 1 冲突。
