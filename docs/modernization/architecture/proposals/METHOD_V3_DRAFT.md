## 1. 一句话

先问**谁**（干系人）要什么价值（价值流），再找出**承载这些价值交换的业务对象**及其状态与事实，然后由**不变量**定聚合、由**语言与模型**定 BC、由 BC 归纳子域，最后把**业务流程**映射到阶段与聚合。每一层只回答自己的问题，靠「对象的状态」这一颗钉子连起来：

```
干系人 → 价值流（阶段门 = 对象状态）
              ↑
业务对象（类型 · 状态 · 关系 · 规则 · 产生的事实）←→ 能力（对象 + 动作，一个能力只改一个对象）
              ↓
不变量 → 聚合 → BC（语言 / 模型一致）→ 子域（归纳）
              ↓                         ↓
       业务流程（事件触发，跨对象，映射到阶段）   事实 → 指标
```

**两条优先级规则**
1. 已采纳、有证据的不变量 ADR（如 ADR-0016 单一过账管道、期间闸门、WIP 与开票同一事务）约束任何推导结果，反之不成立（ADR-0041 决定 3）。
2. 依据的主次：AEC 行业通行做法（法规、合同范本、准则、成熟产品）为主，用户业务事实定夺，老系统与 A8 生产数据只作参考与核对；确需复刻的老行为仍以生产数据为证据（CLAUDE.md 第 4 条，intent `2026-10-15-202634`；one-coordinator intent `2026-10-15-203001`，在 #225）。

## 3. 迭代与回溯

- 方法是迭代的：后面的步骤发现前面的缺口时回到前面修正（例如第 5 步阶段门指不到对象 → 回第 2 步补对象；第 8 步发现同名异义 → 回第 2 步拆概念）。
- **回溯检查**（用户 2026-10-15「估计我们全部结束，还要回去修改一下」）：全部段落走完第 0–9 步后，用定稿的判据把最先完成的「售前到签约」段重走一遍，更新其信息图、聚合与 BC 草案，再进入一次性 ADR。

## 4. 每步的对抗评审（用户 2026-10-15「只有一个阶段值得对抗检查吗」）

**每一步的产出在交用户之前都要经过对抗检查**，按产出的性质选检查方式，不只限于个别步骤：

| 产出性质 | 检查方式 | 适用步骤 |
|---|---|---|
| 外部事实（法规条款、标准、准则、产品字段、页码） | 另派代理独立复核出处，查不到一律标「未核实」，未核实项不作硬依据 | 第 2 步各段研究；FRAMEWORKS 出处 |
| 生产取证 | 抽查口径与计数（另一代理或本会话复跑关键查询），核对登记与无明细外泄 | 第 2 步取证 |
| 判断与推导（对象划分、不变量、聚合、BC、子域、流程映射、建议选项） | opus 对抗评审：跳步、循环论证、无依据、与已定事项冲突、过度设计 | 第 1–11 步的每份草案与确认页上的「建议」 |
| 用户给定的事实与决定 | 只查与其他已定事项是否一致，不评判对错；不一致时交用户 | 第 0 步、各确认页答复 |
| 整条链 | opus 对抗评审 + 回溯检查（第 3 节） | 全部段完成后 |

确认页上的每条「建议」都须注明是否已过对抗评审；未过的不作为推荐项展示。
