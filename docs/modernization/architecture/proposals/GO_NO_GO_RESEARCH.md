- 性质：提议稿，供下一张确认页使用；不改施工方案，建议清单经用户与财务确认后再并入 `CONSTRUCTION_PLAN_DRAFT.md` 第 5.2 节。
- 起因：施工方案第 5.2 节 12 条候选判据，用户答「需要深入研究后再定」（第 9.1 节 C-8）。
- 访问日期：2026-10-16。标注：【一手原文】官方文档已读全文；【一手·部分】只读到片段或摘要；【二手】博客、培训页、第三方转载；【推论】本稿判断。

## 0. 结论（先看这一屏）

1. **三家厂商方法论的判据类别高度一致，但都不给通用数字**：Microsoft、SAP 都只写「可接受的通过比例」「指定数量的用户完成培训」，阈值由项目在 go/no-go 会前自定。Oracle 没有查到公开的 go-live 判据原文（Oracle Unified Method 本体未取到），只有零散产品指南与博客。所以本系统的数字必须自己定，不能「照搬行业阈值」。
2. **成熟做法的骨架**：事先写定准入判据 → 多次模拟切换（同样的数据、工具、人员、步骤、时间）→ 逐任务验证与签字 → 回滚计划与截止点 → go/no-go 会议由业务干系人签字，而不是项目组自签。
3. **第 5.2 节 12 条的问题**：（a）缺：冻结窗口与窗口时长、回滚触发条件与决策时限、迁入后立即可核的结账检查、数据与日志合规（12 号文）、投产后支持与加强复核、业务连续性（税务与银行的外部窗口）、关键人员可用性、判据本身的评审与签字人；（b）重复：第 4、5 条与第 3 条同属「对平」，第 2、5 条的「差异为 0 或财务签字」是同一容忍口径，应合并成一个口径；（c）不可量化须改写：第 6 条「用户验收签字」、第 8 条「安全评审通过」、第 9 条「联调通过」、第 12 条「事件登记表为 0」。
4. **建议清单**共 22 条：必须 15、建议 7（第 5 节）。其中 9 个数值须用户或财务定（第 7 节，供下一页用）。
5. **无外部审计时的签字**：财务负责人对账与结账判据签字；内部审计不签「通过」，而是独立复核对账证据与签字过程并出意见（保持独立性）；业务负责人签业务验收与在途；技术负责人签性能、安全、回滚与运维；最终 go 由用户（决策人）在 go/no-go 会上签。这与 A1-02「替代把关」一致，内部审计角色在此处是同一机制的一次使用（第 6 节）。
6. **合规层面**：财会〔2024〕12 号第二十四条（结账前自动检查凭证全部入账）、第二十一条第三项（记账不可逆）、第二十八条（导出电子会计档案接口）、第三十二条（操作日志）可直接转成可测的判据；11 号文与《会计档案管理办法》没有「换系统上线」的专门条款（沿用 `FIT_RESEARCH_CUTOVER.md` 结论，本稿对 12 号文已用政府网站正式版附件再核一遍）。对自研软件的适用性仍【未核实】（T-9）。

## 1. 成熟方法论的 go/no-go 判据

### 1.1 Microsoft Dynamics 365（Success by Design）

来源：[go-live 准备](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/prepare-to-go-live)、[go-live 检查单](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/prepare-go-live-checklist)、[切换流程](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/prepare-go-live-cutover-strategy)、[发布策略](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/implementation-strategy-define-strategy-deployment-release)、[迁移数据](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/data-management-configuration-data-migration)【一手原文】，访问 2026-10-16。

- **判据类别**（检查单 11 个区）：go-live 准备、切换、方案范围评审、方案验收评审、用户验收测试完成、性能测试完成、系统集成测试完成、数据迁移准备与验证、外部依赖确认、变更管理（培训、用户参与、超级用户）、运营支持准备（监控、支持移交、帮助台、hypercare）。
- **谁签字**：业务干系人（business stakeholders）对每个测试周期的退出标准、范围、验收、UAT、性能、SIT 分别签字；切换在「cutover go/no-go checkpoint」由干系人签字；实施团队评估 go-live 日期是否可行，指导委员会（steering committee）据评估做 go/no-go。页面还提到「由谁做最终决定」要在切换策略里先定，判据示例是「可接受多少缺陷及如何修复或绕过」。
- **量化写法**：没有数字。写法是「退出标准已满足」「各测试周期达到退出标准」。性能：「在代表性环境、数据与用例下测峰值负载」。数据：「迁移至少在 SIT 与 UAT 环境各测一次；切换前多次演练；性能须落入切换窗口」。
- **no-go 处理**：readiness review 识别的风险与阻塞项须有缓解计划与责任人；为阻塞项找绕过办法；实施团队据此判断 go-live 日期是否可行；「预留缓冲时间」。没有写「no-go 后固定走什么流程」。
- **切换要点**：窗口通常不到 48 小时；不要选在结账或报告期；模拟切换用同样数据、工具、人员、步骤与时间；每个任务有负责人与备份负责人、验证与签字、回滚计划；入场标准含「数据迁移与验证、沟通、支持、培训、切换计划均经业务干系人批准」「培训在 go-live 前完成」。

### 1.2 SAP Activate

来源：SAP Learning「Preparing for Cutover」[培训页](https://learning.sap.com/courses/cloud-onboarding-for-sap-ipd/preparing-for-cutover_e0a6bd7a-d06f-4a82-8060-296506a2dbd4)【一手·部分】（SAP 官方培训材料，访问成功）；SAP Activate Roadmap Viewer 本体与 [SAP 博客「cutover readiness assessment」](https://blogs.sap.com/2021/11/01/sap-project-cutover-readiness-assessment/)访问失败（403），只见搜索摘要【二手】；SlideShare 的 Activate 介绍【二手】。

- **判据类别**（培训页）：集成测试与 UAT 通过比例；终端用户培训完成数；无未结关键问题（按支持单优先级）；主数据与交易数据加载后准确。摘要称 Deploy 阶段有「组织与生产就绪检查」「切换模拟」「Q-Gate 记分卡与签字文件」，【二手】。
- **谁签字**：客户在切换后「签字确认 go-live」，并可用验收标准支持决定（培训页）。Q-Gate 由客户与实施方共同评审的细节【未核实】。
- **量化写法**：「可接受的百分比」「指定数量的用户」，不给数值。
- **no-go 处理**：全部 go-live 关键问题须在生产切换前解决（SAP 远程切换博客，【二手】）；其余【未核实】。

### 1.3 Oracle

来源：[P6 升级最佳实践](https://docs.oracle.com/cd/F88967_01/English/Upgrading/p6_eppm_upgrade_best_practices/63033.htm)【一手原文，仅 6 行：建 go-live 检查单、依规划评估 go/no-go 判据、验证计划；无签字、回滚、数值】；[Oracle ERP 团队博客「what is a cutover plan」](https://blogs.oracle.com/erp-ace/what-is-a-cutover-plan)（访问 403，只见搜索摘要【二手】：尽早定切换负责人、提前至少 3 个月做计划、一份计划覆盖同时上线的各领域）；Oracle Utilities [数据转换 go-live 清单](https://docs.oracle.com/en/industries/energy-water/shared/23a/cs-implementation-guide/CS_IMPLEMENTATION_23A/Data_Upload_Support_Data_Conversion_Guidelines.13.3.html)【一手·部分，摘要：校验错误清零、期初余额与老系统对平、应收与总账对平、生产环境关闭转换功能】。
- **Oracle Unified Method 的 go/no-go 门**：【未核实】，本次只在第三方摘要里见到 Transition 阶段「从安装、验收测试到上线」的泛述。结论：Oracle 一栏**不作为本稿判据的依据**，只借「财务对平」这一类的写法。

### 1.4 小结：三家共同、可借用的写法

| 写法 | 来源 |
|---|---|
| 判据在 go/no-go 会前书面定下，会上只核对证据 | MS、Oracle P6 |
| 签字人是业务一方，不是只有项目组 | MS、SAP |
| 数据判据落到「余额与老系统对平、应收与总账对平」 | Oracle Utilities、SAP（交易数据准确） |
| 关键问题有分级，go 的条件是「无未结关键问题」，非关键问题带责任人与完成日期 | SAP、MS |
| 切换有逐任务签字与回滚计划 | MS |
| 判据数值由项目自定 | MS、SAP（均不给数值）|

## 2. 一次性大爆炸切换的额外判据

来源：Microsoft 发布策略页（大爆炸、分阶段、并行三节）【一手原文】；其余为本稿推论，不另标。

Microsoft 把大爆炸的风险写为：回退「困难甚至不可能」，须有业务连续性备用方案与上线后支持方案；失败影响全体用户；不能从早期上线学习。**并行**是「验证手段，非推广方式」，会掩盖培训与测试不足。用户已选不并行（U-10），以下判据是「不并行时必须补上的」：

| 类别 | 额外判据（推论） | 对应第 5 节判据 |
|---|---|---|
| 迁入核对 | 对账口径事先定死：按（法人，期间，科目或单据类型）的行数、金额、借贷合计、期末余额；容忍度写成「金额差 0 元；行数差 0；例外逐项有结论与签字」，不写百分比；拒收清单逐条有结论 | M-3、M-4 |
| 替代并行的重算比对 | 取最近两个已结期间用迁入明细重算并与老系统、U8C 结果逐项比；差异清单逐项归类（已知口径差、迁入错误、老数据问题），迁入错误须为 0 | M-5 |
| 回滚截止点 | 第 5.1 节 P-1 前为可回滚；写明回滚触发条件（哪些现象触发）、决策人、决策时限（例如切换开始后 N 小时）、回滚耗时已演练实测 | M-8 |
| 业务连续性 | 切换窗口内税务、银行、工资发放、报销、月结等不能中断的事项有应急办法（线下通道）；窗口内不开票、不发薪 | M-9 |
| 冻结窗口 | 老系统与 A8 冻结起止时刻、冻结期间业务的登记办法、冻结与切换窗口时长（Microsoft：通常不到 48 小时，不要选在结账或报告期）；本方案 2028-01-01 投产正落在年度首日，须与年末结账、个税与社保申报、年度开票对齐（第 6.6 节） | M-9 |
| 在途单据 | 投产日在途清单逐单有结论，且冻结时点重取一次（避免演练之后又新增） | M-6 |
| 支持与升级 | hypercare 期（投产后首个月结前后）；值班表覆盖节假日与夜间（MS 支持页）；投产后前两个月结的加强复核；热修复通道（投产后只前进修复） | M-12、S-4 |
| 关键人员 | 切换窗口内负责人及备份均在岗；关键岗位无单点 | S-1 |

  - 第三十三条：重要敏感数据加密存储与传输，按场景脱敏 → 判据：敏感数据安全（M-13）。

## 5. 建议判据清单

**阈值栏的数字全部是本稿草案**（一手来源不给数字），须用户或财务确认（见第 7 节）；证据栏写「谁拿什么证明」。签字人角色见第 6 节。no-go 处理通则：任一「必须」判据未满足即 no-go；未满足的判据登记为阻塞项，指定责任人与完成日，修复后**重跑该判据的证据，不口头放行**；影响切换演练的修复（改迁入、改结账）须重做最近一次全量模拟切换（M-1）。

### 5.1 必须（15 条）

| # | 判据 | 阈值草案 | 证据 | 签字人 | no-go 时 |

## 6. 判据评审与签字人

**问题**：无外部审计，只有内部审计；对外财报按开票确认收入（intent 收入事实页 R-9）。按开票确认意味着业务确认口径（A1）与对外口径有差，go/no-go 对账须同时看两个口径，且没有外部审计师替代把关。

**建议的角色分工**（具体人选由用户定；此处按角色）：

| 角色 | 签什么 | 不签什么 |
|---|---|---|
| 财务负责人 | M-3、M-4、M-5（对账与对平）、M-9 与 M-10 中的财务部分、M-11、S-4、S-7 | 不单独批准例外：例外超过上限须上报用户 |
| 内部审计 | 不签「通过」；对 M-3、M-4、M-5、M-11 出**独立复核意见**（抽样复算对账证据、核对签字过程、检查例外清单是否与证据一致），意见书入 go/no-go 材料 | 不签技术项；不参与对账执行，以保持独立 |
| 业务负责人 | M-6、M-7（汇总）、M-9、S-2、S-3、S-7 | — |
| 技术负责人 | M-1、M-8、M-10、M-12、M-13、M-14、S-5、S-6；对判据证据的真实性负责 | 不替业务签验收 |
| 用户（决策人）| M-2、M-8（回滚决策）、M-13（敏感数据授权）、M-15，并在会上做最终 go / no-go | — |

**规则**：（a）go/no-go 会前 N 天判据与阈值冻结（M-2），会上只核对证据；（b）任一「必须」判据的责任签字人不同意即 no-go，不以多数表决；（c）技术负责人与对账执行人不得为同一人；（d）内部审计复核意见有「保留」时，须有书面处置结论后才能 go；（e）go 决定与全部签字存档，作为投产后质疑的证据。

**与 A1-02「替代把关」的关系**：A1-02（intent 收入事实页 R-9）已定「无外部审计，把关改为内部审计与财务负责人等」，针对收入确认与财务口径。go/no-go 的把关是同一机制的**首次使用**：用同一组角色、同一原则（执行者与复核者分离、内部审计独立复核、财务负责人对口径负责），不另设一套。两处要对齐：（i）内部审计在 go/no-go 中出复核意见的格式，宜与 A1-02 后续页的日常复核格式一致；（ii）若 A1-02 后续页决定外聘一次性专项鉴证（对投产期初与重算比对），其结论应作为 M-4、M-5 的一项证据；是否外聘由用户定（Q-4），本稿不预设。
