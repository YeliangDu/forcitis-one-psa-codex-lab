## 1. 一句话与总图

先问**谁**（干系人）要什么价值（价值流），再找出**承载这些价值的业务对象**及其状态与规则，用对象状态写**阶段门**；然后由**不变量**定聚合、由**统一语言**定 BC、把引用按**依赖方式**连成无环的图，最后按阶段做流程、数据与分析，过渡上线并守护。各层只回答自己的问题，靠「对象的状态」与「稳定编号」连起来。

```
① 干系人 → 价值流
② 业务对象（信息图）──生成──▶ 按对象命名的能力图（只作视图与查漏）
③ 阶段门 = 对象状态（可回退、跳过、重入；门只预警）
④ 规则 → 不变量（A / B / C）→ 聚合 · 命令 · 事件
⑤ 聚合 → BC（统一语言）→ 依赖边（api / 事件 / 不校验）→ 查环、分层 → 命名空间
⑥ 流程（事件触发，与阶段多对多）· 表 · 分析事实 · 指标        ← 按阶段
⑦ 过渡架构 · ADR · CI 守护                                      ← 按阶段
```

**三条优先级规则**
1. 已采纳、有证据的不变量 ADR（如 ADR-0016 单一过账管道、期间闸门、WIP 与开票同一事务）约束任何推导结果，反之不成立；推导结果与之不同时，新开 ADR 并附新证据。【推出】（ADR-0041 决定 3）
2. 依据主次：AEC 项目制专业服务行业的通行做法（法规、合同范本、准则、成熟产品）为主，用户业务事实定夺，老系统与生产数据只作参考与核对；确需复刻的老行为仍以生产数据为证据（CLAUDE.md 第 4 条）。【已定】（intent `2026-10-15-202634`）
3. **业务内容以手册为准，结构以框架为准**：阶段叫什么、有几段、门的业务含义，取公司手册与行业做法；它们落到哪种建模概念（价值流阶段、对象状态、WBS 节点、参考数据、策略），按 FRAMEWORKS 的结构判。框架之间冲突时按 FRAMEWORKS 第 0 节（G178 与 BIZBOK 冲突以 BIZBOK 为准）。G178 部分【已定】（intent `2026-10-15-222350`）；写成通用规则【提议 P-01】（由 `STAGE_TYPES_DRAFT.md` §3 的做法归纳，intent `2026-10-16-053630`）。

**范围规则**：第 ①–⑤ 步做全企业【已定】（intent `2026-10-15-221201`「全部段都做到聚合和 BC」），产出为 `proposals/` 下的**提议稿**；规划中的聚合、BC 与边不登记进 SSOT，各阶段开工时按本方法复核后只登记本阶段在建部分【推出】（ADR-0041 决定 4；CS-1.8）；第 ⑥、⑦ 步按阶段做。提议稿与 SSOT 的分工【提议 P-02】（见第 2 节各步「交付物」）。

### ① 干系人与价值流

- **做什么**：干系人按 类型（内 / 外）→ 类别 → 具体干系人 列出，标与价值流的关系（触发 / 参与 / 接受）（BIZBOK §2.8）。按触发干系人列价值流，四要素：名称（触发者视角、动宾）、描述、触发干系人、价值（G178 §2.1）。阶段此时只列名称，进出条件留到 ③。
- **规则**：不拆子价值流、价值流之间不互相触发【已定】（intent `2026-10-15-222350`）；先外部后内部（G178 §3.1，与 BIZBOK 不冲突）。
- **输入 → 交付物**：`proposals/STAKEHOLDERS.md`（用户已给）→ `togaf/value-streams.yaml`。现有 `togaf/value-streams.yaml` 是 ADR-0041 前的参考草稿（含「阶段由能力支撑」「exit 即事件风暴候选」等旧口径），按本步重写【P-04】。
- **谁定 / 校验**：用户；每个类别都有归属价值流或写明不建，否则只作阶段参与者。
- **本轮示例**：干系人取自用户指定的本地文件中的干系人部分（intent `2026-10-15-213742`）；逐个干系人核对对象时，发现了只从客户维度会漏掉的检查与证据线（资本方、既有建筑业主委托的技术尽调、IDI 检查），用户决定纳入（intent `2026-10-15-213845`）。**未完成**：价值流骨架尚未单独定稿交用户；采购到付款、招聘到发薪、记录到报告等价值流的阶段门未做（`ENTERPRISE_AGGREGATES_DRAFT.md` §7 第 8 条）。

### ② 业务对象与范围

- **做什么**：
  1. 按段识别业务对象：定义、类型、状态（有限、互斥）、关系与基数、规则（拒 / 警）、产生的事实、来源（行业 / 用户 / 取证）（BIZBOK §2.5；G190 只用「从业务用语的名词里找」与「信息图不等于数据模型」）。
  2. 一级 / 次级按**依附关系**分，不按生命长短；同物异型用类型区分，不拆对象；单据、属性、估值、派生度量不是对象（BIZBOK §2.5）。
  3. **一级对象检验**用于所有一级对象：独立性、同物异型须合并、单据不是对象、属性与估值不是对象、须有自己的状态与规则【已定】（intent `2026-10-15-215658`）。
  4. **法律事实例外**：由外部权威登记的法律事实（如增值税发票、登记证书）算业务对象；票面、确认单、回单只是证据。这是对 BIZBOK §2.5「单据不是对象」的本地化偏离【已定】（intent `2026-10-15-221201`）。
  5. 外部引用对象（无自有规则、只记录）豁免「须有自己的规则」一项；无类型、状态、关系、只汇聚次级对象的，作汇聚对象（BIZBOK §2.5 第 199 页）【推出】（用户 Q38 认可检验结果，intent `2026-10-15-233152`）。
  6. **能力图由信息图生成**：每个一级对象一个一级能力，命名「对象 + 管理」，按对象拆分、不越出父对象、不按类型拆（BIZBOK §2.2、G211 §2.1.1 命名规则）【已定】（intent `2026-10-15-221201`「重建按对象命名的能力图」；`2026-10-15-222319`）。用途只有三项：一页「业务做什么」的视图；核对阶段—能力对应；对照 BIZBOK §8.6 通用参考模型一级能力的**名称**查漏对象（不抄定义）。**不用于检验信息图**（能力由对象生成，再拿来检验对象是循环论证——第 3 稿评审硬伤 2）【推出】。
  7. **能力不驱动 BC**：`togaf/capabilities.yaml` 不得出现 `bc`、`module`、`subdomain` 及同义字段，CI 拦截；明文不用 BIZBOK §6.5（业务架构与面向服务架构对齐）及 G211 中从组织结构推导能力、多级拆分的做法【推出】（intent `2026-10-15-222319` 纳入时所列代价；ADR-0041 决定 2）。字段黑名单的具体写法与 CI 落点【提议 P-05】。
- **交付物**：信息图（现为 `ENTERPRISE_INFO_MAP_DRAFT.md`，转写为 `togaf/information-map.yaml`【P-04】）；检验表（`PRIMARY_OBJECT_TEST.md`）；`togaf/capabilities.yaml`（重建，替换现有 12 项一级 + 二级参考的旧稿）。能力图生成到几级（只一级，或一级 + 次级对象的二级）【提议 P-06】。
- **谁定 / 校验**：对象与检验结果由用户确认，检验经 opus 评审；每个对象注明来源；检验无未处理的不通过项；参考模型查漏的漏项逐项写「补对象 / 不做 + 理由」。

### ③ 阶段门映射

- **做什么**：给每个价值流阶段写六要素（名称、描述、参与干系人、进入条件、退出条件、价值项，G178 §2.2）；**进出条件写成对象状态**（BIZBOK §2.4）；把公司手册的阶段结构对照到框架概念。
- **规则**：
  - 阶段可回退、跳过、重入，留痕；不采用 G178「上一阶段退出即下一阶段进入」的写法【已定】（intent `2026-10-15-222350`）。
  - 门只预警并留痕，不拦截任何对象；需审定的门走审批，审批未完成不挡下一阶段【已定】（intent `2026-10-16-061232` S2）。
  - 阶段只表示工作进程，与商务分界脱开；售前与交付的成本分界由合同回签承载【已定】（intent `2026-10-16-061232` S3；R3，intent `2026-10-15-234418`）。
  - **阶段 ≠ 状态机**：价值流阶段、企业的阶段类型目录、对象状态机是三件事。阶段门引用对象状态，但阶段本身不做成某个聚合上的大状态机；阶段进度落为 WBS 阶段节点的工作进程状态，跨聚合的门由前置检查或事件策略实现，预警由 `reporting` 或下游策略层产生，不进聚合【提议 P-07】（由 S2、S3 与 `ENTERPRISE_AGGREGATES_DRAFT.md` §4.4.1 归纳）。
  - 流程与阶段多对多（BIZBOK §3.4），一个阶段不等于一个 BPMN 流程【推出】（intent `2026-10-15-222319`）。
- **交付物**：`togaf/value-streams.yaml` 阶段段；手册概念 → 框架概念对照表（现为 `STAGE_TYPES_DRAFT.md` §3）；阶段类型目录取值登记在信息图 OBJ-25（属服务与定价目录 BC）。
- **谁定 / 校验**：用户；每个阶段门都能指到某对象的某状态，**指不到即回 ② 补对象**；可加脚本核对进出条件引用的对象与状态在信息图中存在【提议 P-08】。
- **本轮示例**：
  - 收入链走查（`ENTERPRISE_AGGREGATES_DRAFT.md` §4.3）：报价 → 投标与赢单 → 项目建立 → 合同 → 交付认可 → 收入 → 开票 → 回款，每步写命令、聚合、事件与跨 BC 依赖方向，验证没有上游读下游。
  - 阶段类型（`STAGE_TYPES_DRAFT.md`）：手册售前 BD0、BD1 落为**商机的阶段**——BD0 的门 = 线索「已确认」→ 商机新建，BD1 的门 = 商机赢单（中标或委托证据）；交付七段（启动、方案、初设、深化、招采、施工、结算，另加概念）作全局阶段类型目录，服务产品选组合与显示名、协议范围在 WBS 上裁剪（S1、S1b）；门只预警的依据是生产取证——有 ≥2 个阶段的项目中 89.5% 后段计划开始早于前段计划完成（ADR-0037 登记）。
  - 手册的七段是否等于 BIZBOK 价值流阶段，**尚未裁定**（`STAGE_TYPES_DRAFT.md` §3），属本步待办。

### ④ 不变量、聚合与事件

- **做什么**：
  1. **规则四分**：不变式放聚合；判定（路由、资格、级别）暂放版本化配置表或代码（DMN 推迟）；人工编排放 BPMN；计算放值对象或领域服务；信息图里的「警」是**策略**，不是不变量【推出】（现行 METHOD 接缝 1）。
  2. **不变量三类**【提议 P-09】（第 3 稿评审硬伤 3 的改法）：
     - **A 单聚合**：一个聚合实例内、一个事务内成立；聚合根方法守护。
     - **B 集合约束**：同类型多个实例之间的唯一、不重叠；用唯一约束、部分唯一索引或排他约束实现（§14.1 D2），不为它扩大聚合。
     - **C ADR 认可的多聚合同事务**：已采纳 ADR 明文要求一个事务修改两个聚合；登记 `multi-aggregate-exceptions.txt`，`SingleAggregateGuardTest` 守护。
  3. **跨聚合前置检查不是第四类**：命令方在执行前按 ID 经 api 读另一个聚合，只写自己。两种：一般前置（读写不同事务，竞态由策略兜底）；同事务读锁（读方在自己的写事务内对被读行加共享锁，被读方状态转换须等待）【提议 P-10】。
  4. **下游编排**：凡要读的对象在依赖图中位于下游，改由下游流程查齐条件后调上游命令，上游不读下游【提议 P-10】。
  5. **额度占用模式**：「多张单据合计不超过某个额度」的累计约束，额度与占用行放在一个额度聚合内；申请方先占用（一个事务、只改额度聚合、乐观锁防超占），拿占用 ID 再写自己的单据；驳回、作废、终止时释放；孤儿占用由定时释放与对账兜底。这是 A 类的一种实现模式，不新增 C 类【提议 P-11】。
  6. **对象—聚合对应**写明五种之一：一对一、次级在内、一拆多、无聚合（外部引用、派生值）、技术聚合（信息图无对应对象，只为守住不变量而设；期间性批处理的结果称运行单据）。**对象 ≠ 聚合**：BIZBOK 管对象层，DDD 管聚合层【推出】（FRAMEWORKS 第 4 稿第 0 节）。
  7. **事件**：每个事件由一个聚合发出，写明业务订阅方；没有订阅方的事件不预先命名【推出】（现行 METHOD 接缝 2）；经济事件复审 REA 两个问题。
- **交付物**：全企业提议稿（现为 `ENTERPRISE_AGGREGATES_DRAFT.md`）；阶段开工时登记 `ddd/aggregates.yaml`、`events/*.yaml`、`multi-aggregate-exceptions.txt`。
- **谁定 / 校验**：本会话提议，opus 首轮评审、sonnet 改后复核，用户裁定结构性选择；每条「拒」规则有落点（A / B / C / 前置 / 策略）；A 类恰在一个聚合内；B 类有对应约束；C 类每条引已采纳 ADR。
- **本轮示例**：92 个聚合；C 类全企业只有一处——开票与 WIP 同事务（INV-73，ADR-0016 决定 5）；期间闸门（INV-92）按同事务读锁实现；额度占用 7 处（框架限额、开票与收入额度、供方协议履约额度、假期余额、进项发票入账占用、往来款项核销占用、预算账户若拦截）；结项（INV-40）、关账（INV-100）由下游编排；过账、WIP、运行单据作技术聚合（N-02–N-04）。

### ⑤ BC、依赖方向与命名空间

- **做什么**：
  1. 按**统一语言与模型的一致范围**把聚合聚成 BC，同名异义处必须切开；不变量只决定聚合，不决定 BC（DDD Reference）【推出】（第 3 稿已改正，本轮实践采用）。
  2. **引用分依赖方式**：每条跨聚合引用写「目标（方式）」，方式三选一【提议 P-12】：
     - **api**：经对方 api 查询或调用对方命令，成一条本 BC → 对方 BC 的依赖边；
     - **事件**：订阅对方事件，同样成边；
     - **不校验**：只存对方的类型化 ID（kernel），不调用、不订阅，不成边；只允许用于「下游记录上游不需要知道的来源」或「对方位于下游、只作回溯线索」。
  3. **脚本查环**：由脚本从提议稿合成 BC 依赖边，并入 `module-dependencies.txt` 的已建边，查环并按层分级，与文中分层块比对；退出码 0 才算通过（现为 `proposals/aggregates_dep_check.py`；落地时并入 `build_architecture.py` 或 CI 的方式【提议 P-12】）。
  4. **方向规则**【提议 P-13】：上游不读下游、也不订阅下游事件；关联由下游一侧记录（如银行流水只追加、匹配记在收款上；工时引用加班 ID）；**证据不引用采集对象**——只由采集对象按 ID 引用证据，证据没有出边，因此证据所在 BC 须位于全部使用方上游。
  5. 上下文映射只标四种有代码后果的关系（防腐层、开放主机服务 + 发布语言、共享内核、遵奉者）；标「深建模 / 薄 CRUD」【推出】（ADR-0041 决定 1）。
  6. **子域 = 命名空间分组**：子域只是 Java 包、schema、URL、权限码的前缀分组，与 BC 一起定；已建模块以代码为准，改名须另开 ADR；不做核心 / 支撑 / 通用分类【已定】（intent `2026-10-15-221201`）。
- **交付物**：全企业：提议稿 §3、§4 与脚本输出；阶段开工：`ddd/contexts.yaml`、`ddd/subdomains.yaml`（`classification` 字段改为命名空间说明，见第 8 节 ADR 条目 6）、`ddd/context-map.yaml`、`module-dependencies.txt`。
- **谁定 / 校验**：用户定边界、深浅与命名空间，名称与用语交 one-glossary；查环脚本退出码 0；`status: built` 的边 = `module-dependencies.txt`（A1）。
- **本轮示例**：27 个业务 BC、115 条依赖边（「不校验」6 条不成边），无环，分 L0–L13；用户答复 D-1–D-6、D-8（intent `2026-10-16-061232`），D-2、D-3 改选非推荐项后重跑脚本仍无环。D-3 选三个交付 BC 后，「交付物认可改 WBS 阶段状态」会成 B-04 ↔ B-28 环，改为阶段节点只记工作进程、阶段「已认可」由 `reporting` 读模型派生（§4.4.1）——这是依赖方式与「阶段 ≠ 状态机」两条规则一起起作用的例子。

### ⑥ 流程、数据与分析（按阶段）
