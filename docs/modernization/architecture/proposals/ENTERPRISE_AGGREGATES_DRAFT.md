## 1. 不变量

### 1.1 三类与判法

| 类 | 含义 | 实现 | 例 |
|---|---|---|---|
| **A 单聚合** | 一个聚合实例内、一个事务内必须成立 | 聚合根的领域方法；非法即抛领域异常 | 线索关闭须原因 |
| **B 集合约束** | 同类型多个实例之间的唯一、不重叠 | 数据库唯一约束、部分唯一索引或排他约束（§14.1 D2），不为它扩大聚合 | 一个线索至多一个商机 |
| **C ADR 认可的多聚合同事务** | 已采纳 ADR 明文要求一个事务**修改**两个聚合 | 登记 `backend/architecture/multi-aggregate-exceptions.txt`，事件带 `relatedAggregates`，`SingleAggregateGuardTest` 守护 | 开票与 WIP（ADR-0016 决定 5），本稿唯一一处 |

**跨聚合前置检查不是第四类**：命令所在的聚合在执行前读另一个聚合的状态（按 ID 经 api），只写自己。本稿记为「A（前置）」：拒绝发生在命令方聚合。两种读法：

- **一般前置**：读与写不在同一事务，竞态窗口接受，由对应策略（§1.3）兜底；
- **同事务读锁**：读方在自己的写事务内对被读行加共享锁，被读方的状态转换（如关账）须等读方提交，没有竞态窗口；只读不写，不违反 §14 第 1 项（一个事务只修改一个聚合）。期间闸门（INV-92）按此实现，依据 ADR-0016 决定 1「过账管道内置期间校验」。

凡读取方在依赖图中位于被读方上游的（上游不得读下游），改由**下游编排**：下游流程先查齐条件，再调上游的命令（§4.2 规则 3）。

**额度占用**（一种模式，不是新类）：凡「多张单据合计不超过某个额度」的累计约束，额度与占用行放在一个额度聚合内，申请方先在额度聚合上占用（一个事务、只改额度聚合、乐观锁保证不超占），拿到占用 ID 后再写自己的单据；驳回、作废、终止时释放；申请方写单据失败留下的孤儿占用，由定时释放与对账兜底。本稿用到的：框架限额（AGG-14）、开票与收入额度（AGG-44，含付款条件项可开票额度与履约义务确认额度）、供方协议履约额度（AGG-58）、假期余额（AGG-71）、进项发票的入账占用（AGG-89 内）、往来款项的核销占用（AGG-49、52 内）、预算账户（AGG-80，若定为拦截）。

**证据规则**：证据不引用其采集对象，只由采集对象（不符合项、检查、交付物提交轮次、收入确认行、风险交付授权等）按 ID 引用证据。这样证据没有出边，可以放在所有使用方的上游。

「警」不是不变量，单列为策略（§1.3）。

## 2. 聚合

### 2.1 写法

- 每个聚合：根、内含的次级对象、不变量、对外事件（订阅方）、引用与依赖方式。
- 对象—聚合对应（METHOD 第 3 稿第 7 步五种）：**一对一**；**次级在内**；**一拆多**；**无聚合**（外部引用、派生值）；**技术聚合**（信息图里没有对应对象，只为守住不变量而设）。期间性批处理的结果称**运行单据**（AGG-41、42、43），是技术聚合的一种。
- **对外事件**一列括号里写业务订阅方（B-xx）；没有业务订阅方的写「暂无」。`reporting` 订阅全部领域事件建 L1（ADR-0023 决定 2），不在此列。
- **引用与依赖方式**一列是 `aggregates_dep_check.py` 的输入，每条写「目标 名称（方式）」，用「；」分隔。目标为 AGG-xx、REF-xx、B-xx 或模块名；方式三选：
  - **api**：本聚合的命令经对方 api 查询或调用对方命令，成一条本 BC → 对方 BC 的依赖边；
  - **事件**：订阅对方事件，同样成边；
  - **不校验**：只存对方的类型化 ID（kernel，ADR-0016 决定 8），不调用、不订阅，不成边。只允许用于「下游记录上游不需要知道的来源」或「对方位于下游、只作回溯线索」。
  同 BC 内的引用不成边，也照写，便于看清聚合关系。
- 事件名：英文名词表已有的照用（`terms.yaml` 的 `domain_event`）；其余写中文草案，交 one-glossary（§8）。
- 版本化配置统一写法：「每版本一个聚合 + 部分唯一索引（只一个生效）」，与报价版本一致；已批准版本不可改（§14.1 D15、D17）。
- 关联由下游一侧记录（§4.2 规则 5）：银行流水的匹配记在收款、付款上；设计变更与协议变更的关联记在协议变更上；加班与工时的关联记在工时条目上。

### 3.4 两处砍边论证

**`cost.costing` 的输入取自 `operations.facts`（结论：采纳）**

- 成本核算要的输入：已锁定工时的小时数与标准成本、实际薪酬、已确认收入、分包与费用成本、项目状态。前四类都是触账 BC 已经提交给过账管道的类型化事实（ADR-0016 决定 1：工时成本、费用、收入确认、薪酬都经管道），从管道读即可，不必再读各来源 BC。
- 收益：B-07 的上游从 B-06、B-04、B-05、B-03、B-02、B-15、B-11、B-12、B-08（原稿另漏 B-08）减为 B-16、B-19、B-13 加三条事件边（B-03、B-04、B-05，用于售前投入转入与结项清算）；读到的是带 `PostSeq` 的已过账数据，期间口径与总账一致；原稿评审指出的漏边 B-07 → B-08 不再需要。
- 代价：过账事实须带成本计算要的维度（工时小时数、所锁定费率版本 ID、WBS 坐标、法人），由 `operations.facts` 提供按「项目 × 期间 × 事实类型」查询的 api（开放主机服务 + 发布语言）；缺费率的检查（INV-37）随之前移到工时过账时（AGG-39）；成本侧看不到未过账的单据（草稿态工时不参与，这本就是口径要求）。

**`expense.spend` 是否并入 `payables.payment`（结论：不并入）**

- 并入只减少 B-12 → B-10 一条边（B-12 的其余上游 B-04、B-03、B-18、B-23、B-13、B-16 会原样转到 `payables.payment`），却让应付与付款依赖交付、售前、预算三个业务 BC，应付 BC 的语言（供方、不相容职务、收款账户、核销）混入报销语言（员工、发票要素、事前预批、按项目或商机分摊）。
- ADR-0022 决定 6 把费用报销与应付付款列为不同的 OA 迁入流程；决定 7 的「由来源 BC 提交应付」同样适用于报销：报销审批通过后调 `payables.payment` 确认报销应付，方向 expense → payables，无环。
- 代价：报销到付款跨两个 BC，报销应付的状态须经 api 回查；保留两个 BC 的维护成本。

### 4.2 骨架的规则

1. **合同在交付执行与质量与认可下游**：项目可先于合同（i210513），合同—项目关联与范围条目挂 WBS 都由合同登记（i210513、Q12），所以合同读交付执行、交付执行不读合同。设计变更、延期申请由合同侧的协议变更、索赔引用；合同的视为同意参数由开票与收入（B-08）读取，交付两个 BC 不读。
2. **主数据与外部引用登记在最上游**：往来单位（含外部工程登记：建设工程、招标项目登记）、服务与定价目录被售前、交付执行、质量与认可、合同、检查、成本共同引用，它们只依赖平台与人员组织。
3. **上游不读下游，也不订阅下游事件**：结项（INV-40）、关账（INV-100）的前置检查由下游编排；检查计划逾期转线索由人工完成（P-28）；工作包删除规则随 D-6（用户已定 a：未发布可删、已发布只作废，由交付执行内部状态判定，不必知道工时）；**交付执行不订阅质量与认可的事件**（§4.4.1）。
4. **证据规则**：证据不引用采集对象，只被引用（§1.1）；证据所在 BC 须位于全部使用方上游（Q29 的选项受此约束）。
5. **关联由下游一侧记录**：银行流水只追加，匹配记在收款、付款上；加班不认识工时单，工时条目引用加班 ID；联合体协议作投标的次级对象，不放合同。
6. **检查在合同、交付执行与质量与认可下游**：检查计划引用协议、检查挂项目并经质量与认可 api 发起不符合项；不符合项留在质量与认可，来源检查 ID 只作回溯线索（不校验）。
8. **质量与认可在交付执行下游，单向**：B-28 → B-04（项目、WBS 节点），B-04 不读也不订阅 B-28；跨两者的呈现（阶段已认可）由 `reporting` 读模型派生（§4.4.1）。
7. **应付由来源 BC 提交**：procurement、expense 调 `payables.payment`，不反向（ADR-0022 决定 7）。

#### 4.4.1 D-3 选 c 后：聚合分配、依赖方向与无环处理

用户选了三个 BC（交付执行 B-04、质量与认可 B-28、检查 B-26）。原稿给过 c 的代价是「认可改 WBS 阶段状态须跨 BC 调用」，下面先处理这一点，再列每个聚合的去向。

**分层原则**：按统一语言与不变量切。「计划、预算、资源、工作进程」的语言属交付执行；「裁定交付物能否签发、认可、封存，以及不合格与返工的归因」的语言属质量与认可。质量与认可单向依赖交付执行（读项目、WBS 节点），交付执行不读它。

| 聚合 | 去向 | 理由 |
|---|---|---|
| AGG-19 项目 | 交付执行 | 项目是交付一侧的根，被其余全部聚合引用，必须在最上游 |
| AGG-20 项目 WBS | 交付执行 | INV-41、42 只凭自身节点状态判；阶段节点只记工作进程（S3 定稿：阶段不承担商务或认可含义） |
| AGG-21 交付计划版本、AGG-22 项目预算版本、AGG-23 完工估算 | 交付执行 | 同一套语言（里程碑、计划工时、ETC / EAC）；INV-43、44 单聚合；彼此引用同 BC |
| AGG-24 项目团队、AGG-25 资源需求、AGG-26 资源分配 | 交付执行 | 资源与产能语言，引用工作包；Q13 待定不影响归属 |
| AGG-31 延期申请 | 交付执行 | 延期改变计划与里程碑，被合同侧协议变更、索赔引用；不涉质量裁定 |
| AGG-27 交付物（含提交轮次、送达、内部评审、签发、封存、无异议声明） | 质量与认可 | 认可、签发、封存是裁定语言；INV-46–48、51 与不符合项须同 BC 才能同事务前置读（INV-48、51 现为「同 BC」读）；D-8：视为同意期满判定在 `receivables.wip`，交付侧只记送达与无异议声明，都落在本聚合 |
| AGG-28 不符合项、AGG-29 返工认定 | 质量与认可 | INV-49、50、52 与 INV-48、51 互相引用；返工认定由不符合项产生，工时读返工认定（B-06 → B-28，INV-53） |
| AGG-30 设计变更 | 质量与认可 | 记归因与影响，归因分类与返工认定共用一套原因语言（Q08）；引用交付物、返工认定同 BC；合同侧单向引用它（P-24） |
| AGG-32 发包人提供资料 | 质量与认可 | 对输入资料「确认或退回」的裁定，与交付物认可对称而方向相反；资料不合格是设计变更与延期的起因；只引用项目，放执行也成立，择此以使两类裁定同处一个语言（可改，骨架不受影响） |
| AGG-38 证据 | 质量与认可（Q29、Q34 仍待定） | 证据规则：位置须在全部引用方上游；引用方有 AGG-27、28、35、37、17、44（及 AGG-18「不校验」），B-26、B-05、B-08 都在 B-28 下游，满足；宽口径时可上移为独立上游证据 BC（§7 第 5 条） |

**聚合数**：交付执行 9 个（AGG-19–26、31），质量与认可 6 个（AGG-27–30、32、38），检查 4 个，外部工程登记并入往来单位后往来单位 BC 为 3 个（AGG-01、02、33）加 REF-01。全企业仍 92 个聚合（其后阶段门走查新增 5 个，共 97 个，§4.3.4）。

**无环处理（阶段认可）**：不用「质量与认可发事件、交付执行订阅后改阶段状态」。原因：质量与认可已经 api 读交付执行（校验项目与 WBS 节点），交付执行再订阅质量与认可，就成 B-04 ↔ B-28 的环，查环脚本会报。采用：

1. WBS 阶段节点状态只记**工作进程**（已开始、已完成），不记客户认可；与用户已定的 S3（阶段只表示工作进程、与商务分界脱开）、S2（门全部只预警、审定不挡下一阶段）一致。
2. 「阶段已认可」是质量与认可的事实（交付物已认可事件，B-08 订阅作收入证据）；阶段页面与报表要显示时，由 `reporting` 订阅两侧事件，在读模型里合并派生，不写回 WBS。
3. 阶段门的预警（S2 定稿：全部只预警留痕）需要「阶段已完成」与「交付物已提交」两边信息，同样由 `reporting` 或下游策略层产生，不进聚合。
4. 若将来业务确需阶段状态含认可，唯一不成环的写法是 B-28 在下游**调用** B-04 的命令「登记阶段认可」（api，方向 B-28 → B-04，按认可 ID 幂等，经发件箱重试，两事务最终一致），仍不得由 B-04 订阅 B-28。
5. 代价：阶段「已认可」不在 WBS 上，只能经读模型查询；认可与阶段状态不同事务。

**查环结果**：见 §4.1，脚本退出码 0，无环；B-28 位于 B-04 下游一层，B-05、B-06、B-08、B-26 都在 B-28 下游。

## 7. 本稿没把握之处

1. **合同在交付执行与质量与认可下游**（§4.2 规则 1）依赖「关联由合同登记」的理解；若用户原意是交付侧也要读合同（例如项目页直接显示合同金额），须经 `reporting` 读模型，而不是交付 → 合同。
2. **结项编排的位置**：已论证（§4.6），须位于 B-04、B-05、B-06、B-08、B-11、B-28 下游；推荐独立流程模块，`platform.approval` 承载成环已排除，作 D-9 交用户。残余没把握：收入覆盖检查的「结论」载体随 Q20。
3. **资质证书**（AGG-02）放往来单位 BC：持证方也可能是我方法人主体；放 workforce 也说得通。
4. **法定申报**已按税务与人事拆为 AGG-90（增值税、附加税、企业所得税，归 `accounting.tax`）与 AGG-95（个税扣缴、社保公积金，归 `organization.payroll`）；残余没把握：社保公积金申报与参保（AGG-74）是否宜并为一个聚合。
5. **证据**（Q29）宽口径时可能需要一个独立的上游证据 BC；本稿暂放质量与认可（B-28），满足证据规则即可移动，骨架不受影响（证据没有出边）。
6. **额度占用的孤儿占用**：申请方写单据失败留下的占用靠定时释放与对账，释放时限与对账口径待各阶段规格定。
7. **收入确认行放在 AGG-44**：每协议一个聚合，确认行与开票占用同处，协议大时聚合偏重；若性能复审认为过重，可按付款条件项或履约义务拆分额度聚合（不改依赖）。
8. 三条价值流（采购到付款、招聘到发薪、记录到报告）已走查（§4.3.1–4.3.3），回溯见 §4.3.4；走查只核到「阶段门指到对象状态、依赖方向无环」，各阶段的价值项与干系人留给第 ⑥ 步。
9. **第 13 期启用登记**（AGG-96）与会计期间（AGG-81）同在 `accounting.period`；INV-99「12 月与第 13 期原子关账」按「同类型两个实例」放行，复审须逐一确认（§5.1）。
10. **D-4（独立性检查）** 的两点待核：沪TIS 第 6 条「承接」是否含投标（请法务读原文）；AGG-18 对书面同意证据为「不校验」，只存 ID（§4.4）。
11. **D-6** 推荐 a 依赖工作包有「已发布」这一状态，其界定交交付规格与 one-glossary。
12. **招聘需求的审批**（§4.3.4 第 4 条）：本稿按单步批准写在 AGG-65 内。若业务要求多级审批，B-13 不能实现审批钩子（与已建边成环），须把招聘需求移到位于 `platform.approval` 下游的 BC；那会改变 B-13 的范围，届时作新题交用户。
13. **供方履约确认与应付确认的过账分工**：两者都向过账管道提交候选（AGG-57、AGG-52）。本稿理解为履约确认提交成本事实、应付确认提交应付与进项税事实，同一经济事项不重复过账（幂等键含来源单据 ID）；具体事实类型与科目由财务口径定，口径未定前不得两边都按全额过账。
14. **薪酬代发经 `payables.payment`**（§4.3.4 第 8 条）是本稿据 ADR-0022 决定 7「应付由来源 BC 提交」推出的；该条原文只列员工借还款与合伙人出资的资金收付，薪酬代发是否同样放在 `payables.payment` 交财务确认；不放则改为薪酬按银行流水自行登记发放（B-15 → B-22），同样无环。
15. **「关账中」是否仍接受过账**：ADR-0045 决定 1 只写了「前置检查未通过保持或退回开放」，没写关账中能否过账；本稿未加限制，交 `accounting.period` 规格定。
16. **AGG-100 期间余额快照、AGG-101 外部法定账对账**按 ADR-0022 第 3、8 条补为聚合；G1 期间其表结构与生成时点由 `accounting.ledger` 规格定，若规格认为快照可由分录只读派生而无须单独存储，须先说明如何满足 ADR-0045 决定 2「已关账期间快照不变」。
