1. **创建命令与部分生命周期缺**（聚合稿只列了一部分命令）：AGG-60 聚合稿只有登记法人主体，词表与已建代码另有法人主体已启用 / 已停用 / 已更名 / 代码已更正 4 个事件，对应命令聚合稿与流程都没有；AGG-64 只有停用，新建 / 修改职位、职级、职位族的命令缺（`vs07.notes.md` 结构问题 8）；AGG-66 没有「登记注册执业证书」，数据模型状态列的「注销」也无命令；AGG-67 有驳回但流程无独立步骤。本稿不自造命令（CS-1.8 只实现当前阶段）：这三台状态机的初态（启用、有效）注明由初始化录入或迁入产生，请 one-architecture 判断是否随下一轮补命令。
2. **AGG-65 状态取舍**：聚合稿与数据模型状态列为「草稿 → 已提交 → 已批准 / 已驳回 → 招聘中 → 已关闭」。本稿不设「已驳回」（v1 以关闭代驳回，PRC-81 步 4 同一命令，原因入参区分）和「招聘中」（没有进入该状态的命令，录满无触发，PG-08，招聘需求与候选人关联命令也缺）。若要保留，需先补命令；数据模型状态列同步。
3. **AGG-62 两个子生命周期合成一台**：人员（候选人 → 待答复 → 录用已确认 → 待入职 → 试用期 / 正式 → 待离职 → 已离职，另有未录用、候选人已放弃两个终点）与离职申请（已申请 / 已受理 → 已批准 → 已登记 → 已生效，另有已驳回、已撤回、已撤销）。数据模型 `employees` 的用工状态列写的是「候选 → 试用 → 正式 → 待离职 → 已离职 / 未录用 / 停薪留职」，与本稿对不上的有：新增待答复、录用已确认、候选人已放弃、待入职；「停薪留职」无命令不设（A8「停薪留职申请单」见 `vs07.notes.md` 结构问题 18）。请 one-data 同步状态列。另：**VS-13.6 的进入条件「待离职」**——本稿人员进入待离职是办理离职（登记离职日）之后，而 PRC-128 步 2 的注释写「批准后状态待离职」；员工提出的离职从申请起就受理，公司终止批准后是「离职申请:已批准」。请 one-architecture 把 VS-13.6 入口改为「离职申请已受理或已批准」，或认可本稿。
4. **转正不能提前登记、到日生效**：PRC-85 步 3 说转正日是业务生效日、可提前登记（U-12），但入职、离职、调岗都有「生效」定时命令，转正没有，聚合稿也没有；事件「转正已办理」于是在办理时发出，与 U-12「事件在业务生效日发」不一致。见待用户定 C-2。
5. **AGG-63 调岗申请无表**：数据模型 `assignments`、`assignment_versions` 里没有调岗申请（提交、批准、驳回）的存放，状态机里「调岗申请:*」的状态无处落；请 one-data 增表或明确放 `assignments` 的次级。此外：调岗已写入未来版本、尚未生效时，若该员工先离职（离职日早于调岗生效日），终止任职只能处理「生效中」的任职，「变更待生效」没有出路；本稿不加转换，请 one-architecture 判断是否由离职生效作废未生效的调岗（影响 INV-62 判定）。
6. **AGG-67 离职时合同未生效的去向**：终止劳动合同只定义「已签署生效 → 已终止」；离职时若合同仍在草案 / 审批中 / 已批准（入职后一个月内离职、P-05 未签订提醒的情形）没有作废命令，PRC-128 步 9 会因前置失败告警人力。见待用户定 C-4。

8. **敏感权限判定与权限码拆分**（ADR-0032）：本稿 39 条里判 sensitive 18 条，全部是写或读个人信息（候选人与面试评价、人员主数据、离职原因类别、劳动合同薪酬条款、证书编号）的人力或审批权限，理由逐条写在 `vs07.raci.yaml`；员工本人范围内的自助（撤回离职申请、登记本人学时）与纯系统执行命令判 false 并写理由。两处请 one-rules 复核：(a)「申请离职」员工本人用与人力代办 / 发起公司终止用同一权限码 `离职.申请`，不拆则该码要么对全员判敏感（不现实）要么让人力代办漏判，建议拆「本人申请」与「代办 / 发起公司终止」两码；(b) 劳动合同条款含薪酬时算 L3，是否要登记为双人逐人级由 one-rules 对照 `two-person-resources.txt`（薪酬类资源）判定，本稿只判是否敏感。

## 格式问题

1. **状态机合成**：AGG-62、AGG-63 内两个子生命周期合成一台，状态名带「人员:」「离职申请:」「任职:」「调岗申请:」前缀，各子生命周期以 `from: null` 创建转换为入口；同事务改两处的命令（办理离职、离职生效、撤销离职登记、变更任职、任职变更生效）各列两条转换，`process_steps` 用 `also` 带出。AGG-60、AGG-117 是配置型 / 版本型根，标 `perpetual: true`，`converge_check` 会按「无终态」提示（`vs13att` 同做法）。
2. **non_state 自环**：只追加记录、不改状态的命令（记录面试、登记继续教育学时、登记劳动合同终止依据、更正法人归属）写成该状态上的自环，`kind: non_state`。
3. **unused_ok**：更正法人归属（维护用）与驳回劳动合同（骨架审批步 `on_reject` 边触发，无独立步骤）手标；撤回离职申请有骨架步骤（PRC-128 第 4 步），不需标。
4. **扩展键**：命令的 `state_change`、`platform_commands`，状态机映射的 `also`、`rule_reject`、`outcome`，RACI 的 `sensitive_reason`，沿用 `vs13pay` 的写法，请 `converge_check` 与合并脚本忽略不识别的键。
5. **RACI 的 A**：4 个聚合内批准写 `resolve: type, role: SH-M1`（与骨架 `approver: SH-M1` 一致）；驳回类命令 R 为批准人本人，不是 platform.approval（与 b31、vs13 的回调式驳回不同，因这些批准不经审批平台）；面试、录用决定、标记未录用的 A 写 `field: 招聘需求.提出人`，该字段在数据模型 `interviews`、`hiring_decisions` 靠 `recruitment_requisition_id` 解析，待 one-data 核。
6. **SH-E6 多职能**：本组用到 4 个 function（人事主数据维护、招聘、人事办理、执业证书管理），沿分片做法按 function 区分；建议 stakeholders 拆编号（`vs07.notes.md` 格式问题 3）。
7. **事件订阅 type**：沿 `vs13att` 取「流程 / 事件策略 / 仅分析」；订阅方 B-15 复核转正后薪酬的策略尚未建，type 写事件策略并注明。
