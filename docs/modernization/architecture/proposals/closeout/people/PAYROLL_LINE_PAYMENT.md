# 员工薪酬行支付状态子机（ARC-1022-COO-06，提议稿）

状态：提议｜2026-10-22｜负责：one-arch-people｜核对：one-architecture

只出设计，不含代码、DDL 与流程编号。分片改动在 `parts/vs13pay.state-machines.yaml`、`parts/vs13pay.commands.yaml`、`parts/vs13pay.raci.yaml`、`parts/b15data.data-model.yaml`，由 `parts/rebuild.py` 合并。

## 1. 依据

- 对象定义：OBJ-73 月度薪酬结算 key_states「员工薪酬行支付状态：待支付 → 已实付 / 支付失败（待补发）；部分成功时成功行保留实付，失败行待补发，整期仍为『已批准』，应付薪酬行全部实付后才转整期『已发放』」（`ssot/10-objects/objects.yaml`）。
- 转换记录：ADR-0075 决定 1–6（子实体自有状态机，主体为子行，序号取子行 `version`，乐观锁以根为准，允许跳号）；ADR-0058 决定 1、8。
- 待判清单 CF-037：本组判定「支付行状态本组状态机尚未建子机，另卡补」（`research/networks/transition-review/people.yaml`）。
- 代发明细只在 B-15：B-10 应付薪酬（AGG-52）是法人 × 月一笔合计，没有员工 × 账户 × 金额（`parts/vs13.notes.md` 结构问题 3）。
- 法规：用人单位应按约定日期支付工资（《工资支付暂行规定》第七条），故支付失败须有补发时限提醒；时限数值未定。

## 2. 状态机

状态持有者：`payroll_settlement_lines`（AGG-73 的子实体，每人每月一行）。状态列「发放状态」已在数据模型列族中，本稿给出取值与转换。

| 从 | 到 | 命令 | 守卫 | 说明 |
|---|---|---|---|---|
| 空 | 待支付 | 批准月度薪酬 | 根同时 审核中 → 已批准 | 计算时建行，`version` 为 1、无支付状态、不写转换；批准时各行同一事务置待支付，写第一条转换（序号 2，ADR-0075 决定 5 允许跳号） |
| 待支付 | 已实付 | 登记代发结果 | 回单行与本行人员、实发金额一致 | 一次登记可改多行，每行各写一条转换（决定 1） |
| 待支付 | 支付失败 | 登记代发结果 | 回单标失败并带失败原因 | 失败原因必填，缺失则拒绝并告警 |
| 支付失败 | 待支付 | 发起薪酬补发 | 员工工资卡账户已更正（账户存放位置未定，见 `parts/vs13.notes.md` 接缝问题 3、U8）；补发金额 = 原实发，不重算 | 发「薪酬补发已发起」，由 B-10 生成补发应付（接缝 J-1） |

- 终态：已实付。支付失败不是终态，只能经补发回到待支付。
- 根的推进：月度薪酬结算 已批准 → 已发放 的守卫改为「应付已结清，且全部薪酬行已实付」。两者谁后到谁触发：PRC-127 收到应付已结清时检查全部行；登记代发结果使最后一行变已实付时，同一命令在同一事务内推进根（决定 4，一条命令改多台状态机）。
- 部分失败：根保持已批准，成功行保留已实付；失败行补发成功后，根才到已发放（OBJ-73 原文）。

## 3. 转换记录（ADR-0075）

| 字段 | 取值 |
|---|---|
| `aggregate_type_code` | `PayrollSettlementLine`（暂名，交 one-glossary） |
| `aggregate_id` | 薪酬行 ID |
| `transition_sequence_number` | 薪酬行自己的 `version` |
| 所在表 | B-15 自己的 `state_transitions`（ADR-0058 决定 5 模板） |

- 每条命令都推进根 `version`，包括只改行的登记代发结果、发起薪酬补发；并发改同一结算下不同行时，后提交者在根上冲突失败（决定 3）。
- 薪酬行须带 `version` 列；本稿在数据模型列族中补上。
- 薪酬行实现 ADR-0058 决定 4 的标记接口（ADR-0075 决定 6 扩为子实体可实现）；`scan_aggregates.py` 生成时列为 AGG-73 下的历史主体。
- 迁入：历史结算按已发放迁入，各薪酬行写一条初始转换（空 → 已实付，ADR-0058 决定 8）；老系统若有失败与补发记录，先取证再定，不推定。

## 4. 命令

| 命令 | 发令（A / R） | 幂等键 | 发事件 |
|---|---|---|---|
| 批准月度薪酬（既有，扩） | 不变 | 不变 | 不变；各行置待支付 |
| 登记代发结果（新） | A 法人财务负责人；R 财务职能人员（出纳，持银行回单） | 结算 ID + 回单批次号 | 薪酬代发结果已登记（仅分析）；全部已实付时另由根发薪酬已发放 |
| 发起薪酬补发（新） | A 法人财务负责人；R 人力资源职能人员（薪酬岗） | 薪酬行 ID + 补发轮次 | 薪酬补发已发起（B-10 订阅） |

- 两条新命令不设人审：登记是对银行回单的事实登记；补发金额等于原实发，规则可守（账户已更正、金额不重算）。
- 回单导入首期为人工上传银行代发回单文件（CS-1.8），银企直联另卡，经 platform.integration。

## 5. 流程承载

两条新命令需要一个人工流程承载，建议新增业务流程「登记代发结果并补发薪酬」（VS-13.5，主对象 OBJ-73，归 B-15）：

1. 财务登记代发结果（全部成功 → 结束于已发放或待应付结清；有失败 → 2）。
2. 通知薪酬岗与失败员工更正工资卡账户（在哪里更正随 U8 定）。
3. 薪酬岗发起薪酬补发 → B-10 生成补发应付并付款 → 回到 1 登记补发结果。
4. 支付失败超过时限仍未补发，非中断提醒法人财务负责人（时限待用户定，暂估 P3D）。

流程编号由 one-architecture 给号后再写进 `parts/vs13.processes.yaml`；在此之前两条新命令在命令目录标 `orphan: true` 并注明原因。PRC-127 的守卫与说明同步改为「全部行已实付」。

## 7. 验收场景（设计级）

- S1 全部成功：批准后各行待支付；登记回单全部成功，各行已实付；应付已结清已到，根同事务到已发放。转换记录：每行 2 条（空 → 待支付、待支付 → 已实付），根 1 条。
- S2 部分失败：两行失败、其余成功；根保持已批准；失败行原因必填。
- S3 补发：员工更正账户后发起补发，失败行回待支付并发补发事件；补发回单成功后最后一行已实付，根到已发放。
- S4 应付已结清先到、回单未登记：PRC-127 不置已发放，根保持已批准。
- S5 并发：两人同时登记同一结算不同批次的回单，后提交者乐观锁冲突失败，重试。
- S6 回单与行不符（人员或金额对不上）：整批拒绝并列出差异，不部分写入。
- S7 迁入：历史已发放结算的每行写一条 空 → 已实付 初始转换，不发事件。
