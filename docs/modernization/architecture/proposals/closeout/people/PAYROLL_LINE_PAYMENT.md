- 转换记录：ADR-0075 决定 1–6（子实体自有状态机，主体为子行，序号取子行 `version`，乐观锁以根为准，允许跳号）；ADR-0058 决定 1、8。
- 待判清单 CF-037：本组判定「支付行状态本组状态机尚未建子机，另卡补」（`research/networks/transition-review/people.yaml`）。
- 代发明细只在 B-15：B-10 应付薪酬（AGG-52）是法人 × 月一笔合计，没有员工 × 账户 × 金额（`parts/vs13.notes.md` 结构问题 3）。

## 2. 状态机

状态持有者：`payroll_settlement_lines`（AGG-73 的子实体，每人每月一行）。状态列「发放状态」已在数据模型列族中，本稿给出取值与转换。

| 从 | 到 | 命令 | 守卫 | 说明 |
|---|---|---|---|---|
| 空 | 待支付 | 计算月度薪酬 | 建行时 | 建行即置待支付，`version` 1，写第一条转换（序号 1，ADR-0075 决定 3） |
| 待支付 | 待支付 | 计算月度薪酬 | 批准前重算 | 不删行，只改金额、不改状态；`version` 照常推进、不写转换（决定 5 允许跳号） |
| 待支付 | 已实付 | 登记代发结果 | 根为已批准；回单行与本行人员、实发金额一致 | 一次登记可改多行，每行各写一条转换（决定 1） |
| 待支付 | 支付失败 | 登记代发结果 | 回单标失败并带失败原因 | 失败原因必填，缺失则拒绝并告警 |
| 支付失败 | 支付失败 | 登记薪酬补发顺延 | 原截止日落在长假内；顺延日为长假前最后或长假后第一个工作日；已通知员工 | 只改补发截止日，不改状态 |
| 支付失败 | 待支付 | 发起薪酬补发 | 员工工资卡账户已更正（账户存放位置未定，见 `parts/vs13.notes.md` 接缝问题 3、U8）；补发金额 = 原实发，不重算 | 发「薪酬补发已发起」，PRC-126 调 B-10「登记薪酬补发明细」（不新建应付，J-1） |

- 终态：已实付。支付失败不是终态，只能经补发回到待支付。
- 根的推进：月度薪酬结算 已批准 → 已发放 的守卫改为「应付已结清，且全部薪酬结算行已实付」。两者谁后到谁触发：PRC-127 收到应付已结清时检查全部行；登记代发结果使最后一行变已实付时，同一命令在同一事务内推进根（决定 4，一条命令改多台状态机）。
- 部分失败：根保持已批准，成功行保留已实付；失败行补发成功后，根才到已发放（OBJ-73 原文）。
- 「应付已结清」以 B-10 应付的当前状态为准：判断时经 api 读取，不缓存结清标记。原因是同一应付可能结清两次——代发退回款登记后，原应付回到「已部分结清」，补发付清后再发一次「应付已结清」（one-arch-finance J-2，`finance/PAYROLL_REISSUE_SEAM.md` @363e1b5f）。PRC-127 因此按事件 ID 去重，不按应付 ID。

### 2.1 补发截止日与提醒（用户 FCQ-06/07，intent 2026-10-22-103824）

- **截止日**：自银行退回日的次日起算 3 天，第 3 天为补发截止日。截止日遇节假日或休息日，提前到最近的工作日。工作日按 ADR-0072 已确认的工作日历（AGG-68）判定；日历版本缺失时拒绝计算并告警，不按自然日猜。银行退回日由「登记代发结果」逐行登记，必填。
- **长假顺延**：截止日落在长假内、确实无法在截止日前办完的，薪酬岗用「登记薪酬补发顺延」顺延；顺延截止日只能是长假前最后一个工作日或长假后第一个工作日，且必须通知员工，否则拒绝。
- **逾期**：截止日（或顺延截止日）到期仍未发起补发的，该行计入补发逾期统计（薪酬结算行「是否逾期」，metric_event）；之后补发照常进行。
- **提醒**：到期未补发，同时提醒法人财务负责人与负责薪酬的人力资源职能人员（PRC-201 第 2 步 notify，how 写明到期日算法）；到期后 5 个工作日仍未补发，非中断升级到法人负责人（第 2 步 timeout，escalate_to ROLE-26 总经理按法人解析，与 LEB「我方签约法人的负责人」同口径；用语交 one-glossary）。写法同收入组 PRC-47 第 7 步，不另设字段（one-architecture 2026-10-22 核对）。与 ADR-0073 会签逾期链同一纪律。提醒经 platform.scheduling 登记，幂等键为薪酬结算行 ID + 补发轮次 + 截止日；补发成功或顺延时取消或重登。

## 5. 流程承载

两条新命令由新增业务流程 PRC-201「登记代发结果并补发薪酬」承载（VS-13.5，主对象 OBJ-73，归 B-15；one-architecture 给号，PRC_ALLOCATIONS.md）：

1. 财务登记代发结果（含银行退回日；全部成功 → 结束于已发放或待应付结清；有失败 → 2）。
2. 通知失败员工与薪酬岗更正工资卡（在哪里更正随 U8 定），按 2.1 算补发截止日并登记到期提醒；到期未补发提醒法人财务负责人与薪酬岗，再过 5 个工作日升级法人负责人。
3. 截止日落在长假内且确实办不完时，薪酬岗登记顺延并通知员工。
4. 薪酬岗发起薪酬补发 → PRC-126 调 B-10「登记薪酬补发明细」（不新建应付）→ B-10 经 PRC-75 付清。
5. 登记补发回单，回到 1 的判断。

PRC-201 已写进 `parts/vs13.processes.yaml`（5 步，场景 S01–S06）；补发由 PRC-126 第 2 步调 B-10「登记薪酬补发明细」，在原应付薪酬上挂补发明细、不新建应付，由 PRC-75 付清未结余额（J-1、J-3 定稿）；PRC-126 第 1 步仍只为薪酬已批准提交应付薪酬；退回款未登记时补发被拒，PRC-126 收到「付款已部分退回」后重发（场景 PRC-126-S03、S04）。PRC-127 的守卫与说明同步改为「全部行已实付」。

## 7. 验收场景（设计级）

- S1 全部成功：批准后各行待支付；登记回单全部成功，各行已实付；应付已结清已到，根同事务到已发放。转换记录：每行 2 条（空 → 待支付、待支付 → 已实付），根 1 条。
- S2 部分失败：两行失败、其余成功；根保持已批准；失败行原因必填。
- S3 补发：员工更正账户后发起补发，失败行回待支付并发补发事件；补发回单成功后最后一行已实付，根到已发放。
- S4 应付已结清先到、回单未登记：PRC-127 不置已发放，根保持已批准。
- S5 并发：两人同时登记同一结算不同批次的回单，后提交者乐观锁冲突失败，重试。
- S6 回单与行不符（人员或金额对不上）：整批拒绝并列出差异，不部分写入。
- S8 截止日：银行退回日周一 → 截止日周四；第 3 天是周日 → 提前到周五；长假内 → 顺延到长假前最后或长假后第一个工作日并通知员工；到期提醒两人，再 5 个工作日升级法人负责人。
- S7 迁入：历史已发放结算的每行写一条 空 → 已实付 初始转换，不发事件。
