# 薪酬代发退回与补发：B-10 侧口径（接 people J-1、J-2）

状态：提议稿｜2026-10-22｜负责：one-arch-finance｜依据 people `PAYROLL_LINE_PAYMENT.md` 第 6 节（claude/one-arch-people-closeout @4dbf3da4）｜须 one-architecture 裁定第 3 节与 J-3 的差异

## 1. 先定事实：J-1 与 J-2 是同一条链

银行代发时，整批总额先从公司账户扣出，失败的员工那部分随后退回公司账户。所以每一笔「支付失败」的薪酬行都对应一笔退回款：先有退回（J-2），后有补发（J-1）。

如果退回款到账时恢复了负债，补发时又按 J-1 新建一笔「补发应付」，同一笔工资就记了两次负债。B-10 侧的口径必须让两步只记一次负债。

## 2. J-2：部分退回的记账口径

1. 出纳凭银行退回回单登记：AGG-53 付款新增**登记代发退回**（提议命令；付款仍为「已核销」，累计退回额增加；幂等键：付款 ID + 银行回单号；发「付款已部分退回」）。全额退回仍走现有「登记退票」。
2. AGG-52 订阅「付款已部分退回」，对原应付薪酬（法人 × 月那一笔）执行现有命令**冲回应付核销**，冲回金额等于退回额：应付从「已结清」回到「已部分结清」，未结余额等于退回额。
3. 过账：借 银行存款，贷 应付职工薪酬（恢复负债）；不另记费用，不改成本。
4. 与「应付已结清」的关系：此前发出的「应付已结清」不撤回（事件只追加）；应付回到「已部分结清」后，补发付清时会再发一次「应付已结清」。B-15 已改为「应付已结清且全部薪酬行已实付」才置已发放，两次收到都按此判断，不受影响。
5. 不变量（提议）：同一笔付款累计退回额 ≤ 付款金额；应付冲回额 ≤ 该付款在此应付上的核销额（沿用 INV-77a）。

## 3. J-1：补发不新建负债，挂在原应付上

推荐：

- PRC-126 收到「薪酬补发已发起」后，仍调同一个命令**提交应付薪酬**（保留 J-3「只留一条提交应付路径」），参数带「应付类型 = 补发」、薪酬行 ID、补发轮次、金额（= 原实发）；幂等键扩为「薪酬结算 ID + 应付类型 + 薪酬行 ID + 补发轮次」（正常类型仍按薪酬结算 ID）。
- 类型为补发时，命令**不新建应付、不过账**，而是在原应付薪酬上登记一条补发明细（员工、账户、金额），供付款流程 PRC-75 按明细付清原应付的未结余额（第 2 节恢复的那部分）。
- 守卫：该应付的累计补发额 ≤ 累计冲回额；退回款还没登记的补发，拒收并告警（「退回款未到账，不能补发」），等出纳登记退回后由 B-15 重发。
- 付清后照常核销，应付回到「已结清」，发「应付已结清」。

与 J-3 的差异：J-3 写的是「生成补发应付（类型正常 / 补发）」。如果补发真的新建一笔应付，负债就要记两次（第 1 节），除非退回时不恢复负债，而是把退回款记到一个过渡科目再由补发应付冲掉；那样会多出一个过渡科目和顺序依赖（退回、补发谁先到都要处理）。本稿推荐挂在原应付上，请 one-architecture 裁定。

## 4. 本组随裁定要改的骨架

- AGG-53：加状态内转换「已核销 → 已核销」（登记代发退回）与事件「付款已部分退回」；
- AGG-52：「冲回应付核销」加订阅入口（付款已部分退回）；「提交应付薪酬」加参数与类型分支、补发明细、守卫；
- PRC-75：待付清单显示补发明细；PRC-132 的冲回路径覆盖部分退回；
- 新用语（交 one-glossary）：登记代发退回、付款已部分退回、补发明细。
