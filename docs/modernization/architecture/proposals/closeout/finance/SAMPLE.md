# finance 组流程样板：PRC-87 提交、核定并确认报销应付

用户 2026-10-16「每个会话是不是先提交一个流程样板，我看看设计是否符合我的想法」（intent 153009）。样板取自 `processes.finance.yaml` 的 PRC-87 与 `data-model.finance.yaml` 的 AGG-59、AGG-89、AGG-52、AGG-77；已按 opus 首轮评审（`REVIEW.md`）中涉及本流程的条目改过（R-01、R-03、R-04、R-07、R-11、R-12、R-14、R-21、R-22）。其余 23 个流程在用户意见回来前不改。

## 1. 泳道（谁在哪一步做什么）

| 步 | 泳道（角色） | 在哪 | 动作（聚合，BC） | 之后 |
|---|---|---|---|---|
| 1 | 员工 SH-E3 | 本系统 | 读项目、商机、人员（B-04、B-03、B-13） | 项目已结项 / 终止 / 取消 → 结束 |
| 2 | 员工 | 外部：税务平台查验（经集成） | 占用进项发票入账（AGG-89，B-23） | 发票不合规或已被占用 → 结束 |
| 3 | 员工 | 本系统自动 | 预算占用（AGG-80，B-18） | 预算不足且口径为拦截 → 9（只释放发票） |
| 4 | 员工 | 本系统（纸质原件线下交财务） | 提交报销（AGG-59，B-12） | 原始凭证要素不全 → 8（先释放预算再释放发票） |
| 5 | 部门负责人 SH-E1 | 本系统（审批平台） | 费用报销审批 | 驳回 → 8 |
| 6 | 财务 SH-E6 | 本系统（登记纸质原件签收） | 核定报销（AGG-59），发出「费用报销已核定」 | → 7；B-09 订阅本事件，见事件策略 PRC-147 |
| 7 | 系统 | 本系统自动 | 提交过账候选 → B-16 过账管道 | 已核定（结束） |
| 8 | 系统 | 本系统自动 | 释放预算占用（AGG-80） | → 9 |
| 9 | 系统 | 本系统自动 | 释放发票占用（AGG-89） | 已退回（结束） |

B-09 的事件策略 PRC-147（revenue 组，S-24）：订阅「费用报销已核定」→ 冲抵员工借款（AGG-49）→ 净额不为零时调 B-10 确认应付（AGG-52），为零时调 B-12 标记报销已付（结清方式：借款冲抵）。

图：`bpmn/PRC-87.bpmn`（BPMN 2.0.2 协作图，描述级，检查脚本 0 错 0 警）。

「在哪」的取值：本系统（用户在本系统操作）、本系统自动、外部（经集成由外部系统完成，本系统登记结果与证据）、线下（本系统只登记结果）。本流程里只有发票查验在外部；纸质原始凭证的传递在线下，由财务核定时登记签收；付款经银行、凭证推送 U8C 不在本流程（分别在 PRC-75 与总账）。

付款成功后，B-10 核销应付（PRC-131）→ 应付已结清 → B-12 把报销置为已付（PRC-133）；全额冲抵时由 PRC-147 置已付。

## 2. 关键设计点与依据（一行一条）

| # | 设计点 | 依据 |
|---|---|---|
| 1 | 报销只对一个聚合（AGG-59）做事务；发票、预算经对方 BC 的 api 调用，借款与应付由 B-09 订阅报销事件后处理 | SESSION_PLAYBOOK §14 第 1 项；聚合稿 §2.3 |
| 2 | 三步占用的顺序是发票 → 预算 → 报销，失败时按相反顺序补偿（先释放预算，再释放发票） | ⑥a 评审 H5；聚合稿 AGG-59、AGG-89 |
| 3 | 发票占用只在报销上占一次，报销产生的应付引用报销，不再占用 | 符合性审查 G-17；INV-74 |
| 4 | 不合规发票、要素不全、项目已结项都当场拒收并告警，不静默跳过 | INV-75、INV-84、INV-39；CLAUDE.md 第 6 条 |
| 5 | 审批走通用审批平台（engine: platform.approval），审批人暂用部门负责人，分级与金额阈值待定 | CONVENTIONS approval.engine；聚合稿 AGG-59 引用 platform.approval；F-01 待用户定 |
| 6 | 报销人、审批人、核定人三者必须不是同一人（流程级 segregation 约束） | 会计基础工作规范的不相容职务分离；评审 R-01；CONVENTIONS S-15 |
| 7 | 财务核定时确定所属期间，超过事前预批额度只预警 | 聚合稿 AGG-59；P-37 |
| 8 | 报销核定后发事件；B-09 订阅后先冲抵员工借款，再按净额调 B-10 确认应付（净额为零不确认应付，改由 B-09 调 B-12 置已付，S-19）；报销侧既不调借款也不调应付，依赖方向只有 B-09 → B-12、B-09 → B-10，不成环、无竞态 | intent 134134 Q-10；one-architecture 裁定 S-16、S-17、S-19，B-09 的反应独立为事件策略 PRC-147（S-24）；员工借款以 AGG-49 为准（S-18） |
| 9 | 报销不认识会计科目，只把类型化过账候选交给过账管道 | ADR-0016 决定 1、3 |
| 10 | 预算超额是拦截还是预警没有定，两种分支都画出 | INV-102 待定 |
| 11 | 表：报销根表与明细都带法人、业务日期、单据编号，落账期间存成会计年度和期间序号两列 | §14.1 D7；ADR-0046 §8.3 |
| 12 | 表：发票占用只记在进项发票的占用子表，报销只存发票引用、不存金额 | 评审 R-11；INV-74 |
| 13 | 表：应付、付款、核销按词表命名（payables、cash_payment），核销记录只追加 | terms.yaml payable、cash_payment；§14.1 D8 |
| 14 | 表：过账事实是过账 BC 的根表，只追加；迁入事实走迁入过账通道直接写，不经候选 | ADR-0016 决定 2；§14.2 M8；评审 R-03 |
| 15 | 表：历史报销、应付全部迁入（来源 A8 表单），走迁入用例，不触发审批、不发事件 | U-3、U-4（intent 133348）；§14.2 M7；ADR-0036 |
| 16 | 表：分级按两个维度判，金额是内部级，按人员 ID 引用的标个人信息 | ADR-0043 第 1 项、第 4 项第 2 条；评审 R-14 |
| 17 | 主键一律 UUIDv7，跨 BC 只存 ID、不建外键 | §14.1 D16、D2 |
| 18 | 每步标明在哪完成：只有发票查验经集成在税务平台，纸质原件线下传递只登记签收；其余都在本系统内 | CONVENTIONS where / evidence（提议中）；ADR-0022 决定 3（原始文件留存）；U-1 税务为外部服务（intent 133348） |

## 3. 待定（不在样板里替用户定；one-architecture 放进合成确认页）

**F-01　报销谁来批？**（影响第 5 步）

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 只由部门负责人批一级，财务再核定 | 最快；大额和项目上的费用，项目经理和管理层看不到 |
| B | 按金额分级：小额部门负责人批，超过某个金额加管理层批（金额由财务定） | 多一道门槛，多数单子不受影响；要维护金额档位 |
| C | 挂项目的费用先由项目经理批，再按 B 分级 | 项目成本最受控；单子多走一步，项目经理要及时处理 |

**INV-102　预算不够时怎么办？**（影响第 3 步）

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 拦住，不让提交 | 预算最硬；预算没编准时会挡住正常报销，需要先调预算 |
| B | 允许提交，标红提醒审批人 | 不挡业务；超支只能靠审批人把关，事后看报表 |
| C | 按费用类别分：差旅等可控费用拦住，其他提醒 | 兼顾两头；要逐类配置，规则多一层 |
