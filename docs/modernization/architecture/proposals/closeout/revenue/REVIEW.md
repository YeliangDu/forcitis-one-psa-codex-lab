## 一、高（8）

**H1　PRC-54 让项目经理人工「认定视为同意成立」，与 ADR-0049 决定 2 和「能规则化的不要人来守」相抵**
- 证据：P:6657 第 2 步 actor SH-E2，command「认定视为同意成立」。ADR-0049 决定 2 原文是：期满、交付侧已有无异议声明、该轮未被退回，三条齐备时「receivables.wip 才认定」，并订阅「无异议已声明」事件。三个条件系统都能算，人工判断只在 PRC-28 第 8 步的声明（P:3369）和 PRC-53 的财务复核。现稿让同一个项目经理先声明一次、再认定一次，是重复录入，也多了一个等待点。
- 附带缺陷：
  - ① PRC-28 第 8 步发出的「无异议已声明」在 revenue 组内没有订阅方，PRC-54 只订阅「交付物已送达」。
  - ② 第 1 步在送达时就判断「期满日前已收到客户退回」（P:6630），这时还不可能知道。正确的画法是等待期满（定时）与等待退回（消息）二选一的事件网关。
  - ③ 没有「期满后迟迟无声明」的分支。现在的超时升级给 SH-E6，项目经理不动时实际无人负责。
  - ④ 重新报送后旧轮次的待办没有作废分支。
- 改法：
  - 第 2 步改为 system/automatic，触发改为订阅「无异议已声明」，加上期满定时，三条件满足即认定。
  - 第 1 步改为「期满定时 / 退回」二选一。
  - 期满后若干天无声明，催办项目经理，并进阶段门预警。
  - 新送达时作废上一轮待办。
  - 场景 PRC-54-S01–S05 同步改。

**H2　Q-04 选 C 后「更正只能冲销」，但全稿没有收入冲销或更正的流程**
- 证据：DM revenue_recognitions 写明「更正只靠冲销行」；Q04_STORAGE §2 第 2 点写「更正留冲销痕迹」。但 41 个业务流程加 8 个策略里，没有一条能产生冲销行。PRC-66 的结算差额冲减是命令缺口（N 结构问题·VS-04 第 7 条，G-16）；PRC-68 协议终止对收入没有任何反应（G-08）；客户撤回认可、证据事后失效、审批误批同样没有路径。
- 改法：
  - 向 one-architecture 要号，新增「冲销收入确认」业务流程（B-08）。
  - 触发：人工（财务或项目经理发起），以及「协议已结算（差额为负）」「协议已终止」两个事件。
  - 步骤：占用反向额度 → 审批（命中 AR-06，异常加一级）→ 追加冲销行并引用原确认事实 → 提交过账候选（INV-92）。
  - 结算差额为正时，走补充确认，复用 PRC-53。
  - 补命令「冲销收入确认」进 N 新用语，补场景。

**H3　PRC-66 的触发条件会死锁，结算审减时协议永远不能结算**
- 证据：P:7610–7612 写「全部履约义务累计确认等于分摊价格」才进入完成与结算。AEC 设计、咨询合同常见情形是：范围减少、审定价低于合同价，或最后一阶段只做了一部分。这时累计确认达不到分摊价格，第 2 步永远不触发。而最终价款恰恰要靠结算来确定，等于循环依赖。另外，第 4 步「确认最终价款」是让价或审减的商业决定，没有审批，也没有 why_human。
- 改法：
  - 结算改为人工发起：商务在最后一份成果认可或项目结项后发起，触发与累计确认是否等于分摊价格脱钩。累计确认仍作为前置提示，不作为门槛。
  - 「确认最终价款」低于协议价时，走 platform.approval：approver 为 cost_object_owner，命中 AR-01、AR-02 加审。why_human 写「让价或审减是否接受属商业判断」。
  - 差额接 H2 的冲销或补充确认。
  - 「双方未能确认」的循环加出口，转索赔（PRC-49）或争议。

**H4　PRC-48 协议变更经内部审批就生效，没有发包人书面同意这一步**
- 证据：P:6198 第 5 步「生效协议变更」紧跟内部审批（第 4 步）。第 7 步发「新基线已生效」，触发 PRC-51 扩大开票与收入额度。流程 roles 里列了客户决策人「认定索赔与变更」，步骤里却没有对应的一步。现场签证（第 6 步）有发包人签认证据，非签证变更却没有。这既不符合 AEC 通行做法（变更以发包人书面指令、补充协议或变更单为准），也与「权责按客户确认」相抵：没有客户同意，额度就被抬高了。
- 改法：
  - 第 5 步前插入 external 步「登记发包人书面同意」：engine external，approver SH-C6a，evidence 为补充协议或变更确认单。
  - 拒绝出口为「变更未获发包人同意」，作为结局。
  - 内部审批改为「是否向发包人提出」的决策。
  - QC-VS-04 已发现「客户拒签现场签证无去向」，一并补上拒签出口。

**H5　付款条件项只能由「交付物已认可」转为可结算，非成果类付款节点无法开票**
- 证据：P:8782 中「标记付款条件项可结算」是 PRC-56 的唯一入口，只订阅 B-28「交付物已认可」。PRC-57 的准入要求不超过付款条件项可开票额度（INV-21）。AEC 合同大量付款节点并不是我方成果被认可，常见的有：签约后预付、施工图审查通过、工程竣工验收、按月或按季度、结算审定后付尾款、缺陷责任期满退质保金。除预收例外（P-1）以外，这些节点全都无法开票。视为同意路径同样到不了这里（N 待用户定 3）。
- 改法：
  - 在 B-05 补人工步「登记付款条件达成」（附外部证据：审图合格书、竣工验收证书等）和定时触发（时间型节点），按付款条件类型由规则决定入口。
  - 视为同意路径按 N 待用户定 3 的建议，经 B-08 → B-05 的 api 落地。
  - 命令缺口交 one-architecture。

**H6　资金与收入类不可逆动作没有审批、没有职务分离，稿内「未自作主张加审批」违背 BRIEF 硬规则**
- 证据：
  - PRC-58 红冲（P:7078 起）只有开票会计一人。AR-06 是 guard: approval，本该加审。
  - PRC-61 核销坏账（P:7427）由财务主管一人完成，不审批。
  - PRC-10 退还、没收、扣减保证金全部由出纳一人登记，无审批（N:586 的 D15 已建议复核，但未写进 yaml）。
  - PRC-86 员工借款没有任何审批（P:8291「事前预批无命令也无审批边」）。此项在 N 中**未作为待用户定列出**。
  - PRC-68 终止协议无审批（P:10644）。
- BRIEF 硬规则：「审批人、判断条件规则卡或 ADR 没定的：照最合理的 AEC 行业做法填，并在待用户定列出」。现稿是空着不填。阻碍只是缺 B-09 → platform.approval 边，而 S-25 已有先例：业务依赖平台，方向标准，可直接提请加边。
- 改法：
  - 五处补 approval（engine platform.approval，approver cost_object_owner，各写 why_human）：
    - 红冲：原发票是否确属错误或业务是否确已取消。
    - 坏账：可回收性判断。
    - 没收、扣减：违约事实与金额判断。
    - 借款：用途与必要性。
    - 终止：法律与商务后果。
  - 能规则化的部分做成 guard: rule：借款有未结余额不得再借、单笔限额；保证金退还只能付往原缴纳方账户（同 AR-09）。
  - 补 segregation：制单 ≠ 审批 ≠ 出纳。
  - 收到别人的保证金、要退出去时，应经 B-10 付款，不能只由出纳登记。
  - 写进 STRUCTURAL_ITEMS，申请 B-09 → platform.approval 边；APPROVAL_RULES 提议补「坏账核销」条目。

**H7　红冲后应收不减，B-09 自己的订阅反应缺失**
- 证据：PRC-58 向 B-09 发「发票已红冲」，revenue 组内无订阅方（N:465，G-08 仍未解决）。B-09 归本组，缺的是本组自己的流程。后果是应收虚高，账龄与催收（PRC-61）误报。已收款后再红冲的情形（需退款，或转预收再重开）也没有分支。
- 改法：
  - 新增事件策略（B-09）订阅「发票已红冲」：冲减对应应收的未结余额。
  - 已核销部分转「预收／待退」并通知财务。
  - 命令缺口交 one-architecture，补场景。

**H8　质量门未过：按 PROCESS_QUALITY_CHECKLIST，脚本项与复审项都还有未处理的不符**
- 证据：
  - QC-VS-04「主会话复跑」：bpmn_gen 41 个流程中 11 个报 R14。归因于生成器缺陷，但图本身没有通过。
  - QC-VS-04 第 2、3、5、6 节仍有「不符」：开具失败无重试、认领无撤销、红冲无审批、坏账与终止无审批、PRC-60/86 职务分离无法表达。
  - QC-VS-01 PRC-08 共 52 个元素，超 R15。
  - 「与 A8 同类模板比对」标为不适用、未做。
- 检查表原文是「脚本项不过、复审项有『不符』未处理的，不交用户」。
- 改法：
  - 先由 one-architecture 修 bpmn_gen（不中断升级接独立结束事件），复跑通过。
  - PRC-08 拆出子流程「退还投标保证金」。
  - 本评审 H1–H7 改完后重写 QC-VS-04。
  - A8 比对至少对开票、收款、借款、保证金四类补做。

## 二、中（15）

**M1　PRC-53 审批人口径自相矛盾，加审会加到自己头上**
- 证据：P:8716 approver 写 cost_object_owner，owner_object 却是「承担法人（财务负责人复核）」，实际是固定角色 SH-E6。escalation 中 AR-01 的 escalate_to 是财务负责人，与基础审批人重合。超时升级给 SH-M1（业务部门负责人）处理财务待办，也不对口。QC「审批权只给责任人：符合」是按字段字面判的。
- 改法：
  - approver 按 ADR-0047 U-2 (a) 明写「财务复核」作为法定复核。在 N 格式问题里申请例外：engine platform.approval，approver 为类型级 SH-E6，类比 aggregate 的写法。
  - 加审改为 AR-02 → 总经理、AR-07 → 总经理。
  - 超时升级给财务负责人的上级。

**M2　迁入口径三处不一致，且依赖「迁入不发事件」时不会触发的策略**
- 证据：
  - PRC-53 migration（P:8649）写「占用行按当前状态迁入，审批重新发起」；PRC-148 migration 写「审批中的占用，审批通过后按本策略转实」；DM:2565 revenue_recognition_reservations 却是 history_migration: none。按 ADR-0036 第 5 条，审批实例不迁入，所以迁入的占用行没有可以「通过」的审批，会成为孤儿。
  - PRC-147 migration 写「迁入完成后按本策略补冲抵」，但迁入不发「费用报销已核定」事件，策略不会被触发。老系统若已冲抵过，还会重复冲抵。
  - PRC-54 写「投产时生成待办」，同样需要显式的批处理。
- 改法：
  - 统一为：占用不迁；切换后由迁入编排的一次性离线命令，对在途项重新执行「占用 + 发起审批」。
  - PRC-147 改为迁入后执行一次性对账命令，按报销 ID 与老系统冲抵记录去重。
  - 三处都写明执行方：迁入编排模块，离线命令。

**M3　跨年关账没有处理**
- 证据：PRC-148 第 2 步，以及 PRC-57/58/60/61/63/86 的触账步骤，全部写「不拒绝，落开放期间」。但 ADR-0045 U-2 未定，AR-05 的 review 写「跨年暂为拒绝并告警」，ADR-0047 第 3 条第 3 点写「定前不开放跨年落账」。12 月的认可到次年 1 月才审批通过，是收入线最常见的跨年情形。
- 改法：各触账步骤加 decision「原期间所在年度已年结 → 暂挂并告警（待 ADR-0045 U-2）」，补场景。

**M4　PRC-147 未限制同一法人才能冲抵借款**
- 证据：P:9020。借款按员工所属法人（PRC-86 legal_entity），报销按承担法人（Q-06）。两者法人不同时，用 B 法人的应付冲 A 法人的借款，会造成法人间账错。
- 改法：冲抵限同一法人，不同法人时冲抵额为零并告警（规则卡），补场景。

**M5　PRC-60 收款分支缺失**
- 证据：P:7241 只有「无法对应 → 待认领结束」和「多笔应收循环」两类。缺：
  - 超收转预收或待退；
  - 第三方代付（业主委托代付、财政直付），这在 AEC 很常见；
  - 待认领挂账超期的跟进（转其他应付或退回）；
  - 收到商业汇票的登记（PRC-63 只管到期）。
- 另外，segregation 只列了一个角色（N 已知）。
- 改法：补上述出口与规则。第三方代付要求有委托付款函作证据（规则），否则拒绝认领。

**M6　PRC-57 税务平台不可用时直接作废申请**
- 证据：P:6953「开具失败 → 7 作废开票申请」。平台暂时不可用应该重试或排队，不应作废后让人重新申请。
- 改法：分「可重试（超时、平台不可用）→ 重试并告警」与「业务拒绝（税号错等）→ 退回申请人修改」，两者都不作废。作废只作为申请人或财务的主动动作。

**M7　三口径中的「经营产值」没有流程，对照也没有归入读模型**
- 证据：PRC-30 notes（P:3500）写产值「填报与复核命令聚合稿」缺。processes 的 read_models 只有 PRC-22、62。STRUCTURAL_ITEMS S-08 要求 revenue 组补产值与开票差异的承载。
- 改法：
  - 要号新增「填报经营产值」（B-04，每期）：不审批或项目经理自填，部门负责人抽查。
  - 读模型「收入三口径对照」作为 reporting 条目列入。
  - 命令缺口交 one-architecture。

**M8　检查服务「检查完成经客户现场签认」没有到收入侧的路径**
- 证据：ADR-0047 第 5 类有两种：(a) 现场签认，(b) 报告签发后送达。PRC-43 第 4 步取得了客户现场签认，却不向 B-08 发任何事件。B-08 也不依赖 B-26，两者同在 L10。现在只有经 PRC-28 报告交付物这一条路。
- 改法：二选一写明。① 现场签认单作为一份交付物，在 B-28 登记认可（复用 PRC-28 第 6 步）；② 明确第 5 类 (a) 不单独触发。写进待用户定。

**M9　PRC-53 占用金额怎么来没写**
- 证据：P PRC-53 第 1 步只写「在履约义务额度上占用」，没写交付物与履约义务、阶段比例的对应和金额派生，也没写部分认可、一份成果对应多个履约义务的情形。这是收入链的核心规则。
- 改法：引用或新开规则卡：交付物 → 付款条件项或履约义务的映射，以及金额取值（分摊价格 × 阶段比例）。部分认可要单列。

**M10　数据模型所有表都缺 pi 字段**
- 证据：DM 中 `pi:` 出现 0 次（CONVENTIONS §3 已采纳，ADR-0043 第二维）。delivery_records、customer_acceptance_records、no_objection_declarations、counterparty_contacts、agreement_owner_representatives、lead_contacts、satisfaction_surveys，以及员工借款类 receivables，都含个人信息。
- 改法：逐表补 pi（none / pi / spi），员工借款应收至少为 pi。

**M11　依赖边有两处缺口**
- 证据：
  - PRC-61 第 1 步写 api B-09 → platform.integration（P:7395），§4.1 中 B-09 没有这条边。
  - 审批回调写 event in platform.approval，但 B-02/03/04/06/08/29 到 platform.approval 的边只有 api 方式（脚本核对：PRC-07、13、19、23、36、57、148）。
- 改法：前者改为经 notify（平台通知）或申请加边。后者请 one-architecture 在 §4.1 统一补「事件」方式，或在 CONVENTIONS 写明审批回调不计边方式。

**M12　PRC-86 建模错位**
- 证据：
  - 归还分支挂在第 4 步「提交过账候选」的 decision 上，而发放与归还相隔数周，是两个实例。
  - 第 2 步「创建应收」后，没有向 B-10 发起付款请求的 cross_bc，B-10 无从得知要付款。
  - 缺逾期未还的催还或工资扣回（P-规则）。
- 改法：发放与归还拆成两个触发；补 B-09 → B-10 api「发起借款付款」（Q-10 边已有）；补逾期提醒。

**M13　AEC 常见功能缺失**
- 证据：
  - 联合体（P-4）中，我方作为牵头方代收全款后，向成员转付其份额（代收代付）、联合体开票口径都没有流程。
