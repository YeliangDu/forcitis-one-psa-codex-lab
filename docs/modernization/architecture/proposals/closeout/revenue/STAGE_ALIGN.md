## 5. 归段判据筛查（#421）

判据（用户，intent #421，见 stage_align_check.py 第 6 项）：① 流程结局造出某段的退出条件，就归该段；② 事件策略看触发状态所在的段；③ 参与者应在该段的参与者中；不按部门或时间先后归段。判据只给近似的不按近似改；阶段定义不动，只改骨架，缺口单列。阶段定义取 origin/claude/one-architecture-adr-governance（0284a188，含 VS-04.6、SD-08 的 VS-04.2 退出）。复跑（本组，同一口径）：6a 41 → 42，6b 17 → 17，6c 46 → 46（只看业务流程的 26 条逐条核过，近似项均为通用状态词撞名，不改标），6d 20 → 20；已声明支撑 15 → 16。6a 多出的一条来自 VS-04.6：脚本只看退出条件，VS-04.6 的依据是段内状态（协议变更、索赔、任务订单），PRC-48、49、50 仍报不支持，PRC-52 改支撑后少一条。QC 复跑与改前逐行一致（权责对照等全部为 0）。

注意两点使复跑数字偏保守：(1) 第 6 项取各段 exit 时没展开 `pattern`（exit_common），VS-02.1–.6 的退出只剩段内的 `all`，所以 PRC-28 等流程在 VS-02.x 上被误报「不支持」（交 one-architecture 看脚本是否要改）；(2) 第 6 项不看段内状态（in_stage_states）和进入条件，造出这两类状态的流程（PRC-01、02、06、14、17、46、48、49、50 等）都报「不支持」，已在表中逐条写明依据；VS-04.2 退出现为「缺对象状态」（MS-17），PRC-148 的结局「收入确认事实已过账」脚本匹配不了，仍报不支持。

### 7.5 BPMN 范围、生成方法与限制

业务流程 46 条经卡第 4 节 bpmn_gen 命令生成。事件策略 10 条因入口只遍历 processes 且只接受 type=business，用同一快照的 bpmn_gen.Process 绘图类补绘；输入只做 step → steps 的内存包装，单步且 emits 唯一时复用原 emits 作结束事件名，不写回骨架。56 个图均由原 bpmn_check 校验；不是可执行工作流或业务验收证据。单聚合维护 13 条、读模型 3 条不在现有入口支持范围，未绘，不改生成器。

在卡第 4 节 bpmn_gen 后，于参考 closeout 目录可按下列命令复现事件策略图（OUT 指工作区 revenue/bpmn）：

```bash
python3 -I - "$OUT" <<'PY'
import copy, sys, yaml
from pathlib import Path
sys.path.insert(0, str(Path.cwd()))
import bpmn_gen as g
out = Path(sys.argv[1])
stake = g.load_stakeholders()
doc = yaml.safe_load(Path("revenue/processes.revenue.yaml").read_text())
for source in doc["event_policies"]:
    p = copy.deepcopy(source)
    p["steps"] = p.get("steps") or [p["step"]]
    if not p.get("outcomes") and len(p["steps"]) == 1 and len(p["steps"][0].get("emits", [])) == 1:
        p["outcomes"] = p["steps"][0]["emits"]
    pr = g.Process(p, p["name"], stake)
    pr.build(); pr.wire(); pr.layout()
    (out / f"{p['id']}.bpmn").write_text(pr.xml())
PY
```

生成器提示含缺 command 的既有读取/编排步骤、超时升级同泳道布局等；PRC-59、PRC-146 缺 outcomes，生成器使用缺省结束名。保留这些警告，不改步骤结构来消除；检查通过只证明描述级规则。
