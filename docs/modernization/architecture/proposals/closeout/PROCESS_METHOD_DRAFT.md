# 流程设计方法（提议稿，待 opus 评审、用户批准）

依据：用户「流程总数也不对……流程的画法也不符合 BPMN 最新版本的要求」（intent `2026-10-16-155312`）、「可以，方法批准前不铺开」（intent `2026-10-16-155412`）；METHOD 第 4 稿 ⑥a、⑥b（ADR-0050）；调研 `PROCESS_METHOD_RESEARCH.md`；画法 `BPMN_STYLE.md`；字段 `CONVENTIONS.md`。标注：【已定】有用户决定或已采纳 ADR；【推出】由已定推出；【提议】本稿提议，待批。

## 1. 一句话

流程把「谁在什么时候、在哪里、对哪个聚合下什么命令、留下什么证据」按价值流阶段串起来；它向上对齐价值流与聚合，向下产出命令、表、规则卡、验收场景、权限、页面与迁入映射，并能双向追溯。

## 2. 往上承接（输入）

| 输入 | 来自 | 流程用它做什么 |
|---|---|---|
| 价值流阶段与门（入口、出口状态） | 价值流 v2（③）【已定】 | 每个业务流程挂一个或多个阶段；结束事件的结局词取自阶段出口 |
| 业务对象与关键状态 | 信息图（②）【已定】 | 流程改变的状态必须是对象的已登记状态 |
| 聚合、命令、事件、不变量 | 聚合稿（④）【已定】 | 每个改变系统状态的步骤＝某聚合上的一个命令；缺的标〔缺〕回补聚合稿 |
| BC 与依赖边 | ADR-0051、聚合稿 §4.1（⑤）【已定】 | 跨 BC 只走已登记的边与方式（事件或 api）；新边交 one-architecture 判后回补 |
| 流程清单 | ⑥a（STEP6A）【已定】 | 初始目录；业务流程判据沿用 ADR-0050 决定 15 |
| 用户已定口径 | intent | 判断点、审批层级、时限等直接引用 |

## 3. 流程写清什么（每个业务流程）

1. **目录登记**【提议】：在唯一目录 `process-catalog.yaml` 登记编号、名称、类型、阶段、编排 BC、组、状态；所有计数从目录生成，不手写（取代 ADR-0050 决定 20② 与 J8「流程登记由 `.bpmn20.xml` 生成」，因为事件策略、单聚合维护、读模型没有 BPMN 文件）。
2. **骨架**（`CONVENTIONS.md`）：触发、角色（SH- 编号）、步骤（actor、`where`、命令与聚合、判断点、审批、跨 BC、证据）。
3. **图**【提议】：全部业务流程画描述级 BPMN 2.0.2 协作图（`BPMN_STYLE.md`）；其中人工编排流程（目录 `human_orchestration: true`）另出 Flowable 可执行版（取代 ADR-0050「只有人工编排画 BPMN」，改为两层）。
4. **每一步在哪发生**【提议】：本系统操作、本系统自动、外部系统、线下四类；外部与线下写明登记的证据（诉讼取证与迁入的依据）。
5. **结局**：每条路径以结局状态结束，结局词与阶段出口一致。
6. **超时与升级**：有期限的步骤画边界计时事件，写清升级给谁、多久。

## 4. 往下交付（输出）

| 交付 | 怎么从流程推导 | 落到 | 检查 |
|---|---|---|---|
| 命令与不变量 | 每步命令；判断点的拒绝分支对应前置不变量 | 聚合稿 §2.2（回补） | `closeout_check.py`：命令在聚合稿可查 |
| 表 | 步骤读写的聚合（数据存储）→ 表；线下与外部证据 → 证据表 | `data-model.<组>.yaml` → 数据访问注册表、DDL | 每个聚合至少一张根表；DataArchitectureTest（建表后） |
| 规则卡 | 判断点、不变量、时限 | 规则卡（one-rules），Given/When/Then | 每个判断点至少引用一条规则卡 |
| 验收场景 | 每条从开始到结局的简单路径（循环走一次）至少一条场景；每个判断点出口、每个超时分支各至少一条【提议，借实例化需求做法】 | 验收测试（Given/When/Then） | 路径数 ≤ 场景数（脚本枚举路径） |
| 权限 | 每个用户任务 → 角色 → 权限码；审批任务 → 审批单据类型 | 权限码登记、审批单据类型 | 每个用户任务有权限码 |
| 页面 | 每个用户任务对应一个页面或页面上的一个操作；登记任务对应录入表单 | 前端页面清单 | 每个用户任务有页面引用 |
| 迁入映射 | 历史数据进入流程的哪个状态；线下与外部步骤的历史证据怎么迁 | 迁入框架（ADR-0036） | 每个结局状态有迁入口径 |
| 事件 | 跨 BC 信号事件 → 事件目录 | 事件目录 | 每个事件有发布聚合与订阅方 |

## 5. 双向追溯

- **正向**：目录 → BPMN → 步骤 → 命令 → 聚合 → 表；步骤 → 用户任务 → 权限码 → 页面；路径 → 验收场景。
- **反向**：每个命令至少被一个流程或事件策略用到（未用的标「仅维护」或删）；每个用户任务有权限码与页面；每张表能回溯到一个聚合与至少一个流程步骤。
- **工具**：`build_catalog.py --check`（目录）、`bpmn_check.py`（画法与目录一致）、`closeout_check.py`（命令、聚合、对象对应）；铺开后加路径枚举与覆盖统计。

## 6. 借鉴与取舍（出处见调研）

| 做法 | 取 | 不取 |
|---|---|---|
| BPMN 2.0.2（OMG 现行正式版） | 描述级协作图与可执行子集 | 编排图、会话图、复杂网关、升级与条件事件 |
| Silver《BPMN Method and Style》 | 结局即结束状态、网关出口写结局词、任务必须标类型、黑盒泳池与消息流、自顶向下分层 | 购买其建模工具；照搬 Level 2 全部图元 |
| 事件风暴（Brandolini） | 策略、读模型、外部系统、热点四个词汇（对应事件策略、读模型、外部泳池、待定题） | 工作坊（FRAMEWORKS §1 已用事件清单推导替代） |
| BIZBOK（v15） | 价值流阶段与流程多对多交叉 | 未核实的映射细则 |
| 实例化需求（Adzic） | 用示例说明、由路径推导验收示例 | — |

## 8. 铺开步骤（批准后）

1. 三组按本方法改样板为定稿（目录状态 sample → reviewed）。
2. 各组按目录逐个流程出骨架与描述级 BPMN；人工编排流程另出可执行版。
3. 每完成一个价值流，跑三个检查脚本，opus 首轮评审（每组一次），sonnet 复核。
4. one-architecture 合并目录、聚合稿回补、跨组接缝；生成目录页与覆盖报告。
5. 用户确认点：每个价值流一页（只问业务判断与待定题，不逐图审批）。
