## 报价发出编排与实际用印核验

B31-16 是发出前的硬门槛，不增加人工批准。CON-1017-ARC-02 按 one-architecture 已定结构，新增下游无聚合流程模块 REF-04「报价发出编排」（暂名），沿 B-29 / REF-02 先例；ADR-0057 提议稿记录职责与 ADR-0017 决定 1 的一般允许条件，尚未改为已采纳。

校验方向为 **编排方 → B-31（api）**，另外两条依赖为编排方 → B-03（api）、编排方 → platform.audit（api）。编排方核验同一报价版本、法人及拟发文件的实际用印，失败即拒绝发出并告警；投标路径调用 AGG-11「递交投标」（PRC-08 第 7 步），非投标路径在 PRC-07「生效报价版本」后的人工步调用 AGG-12「登记报价发出」（暂名）。两个命令入参均带用印登记 ID；后者只记录发出方式、日期、客户联系人及用印登记 ID，不改状态、不校验真伪。

AGG-11、AGG-12 不依赖 B-31，也不订阅其事件或维护本地用印投影。「用印已办理」仍由 B-31 发布，实际登记的核验消费方改为 REF-04，经 api 查询而非事件订阅。用印申请对报价、合同的来源引用仍只作回溯，来源审批复用经既有 B-31 → platform.approval 校验；B-31 → B-24 资产卡片引用保留。

结论：核验责任位于两个业务模块下游，聚合稿 §2.2、§3.2 及 §4.1 已按新方向同步并重算。查环器继续计算 api 与事件边，不改规则；REF-04 不挂 platform.approval，不在流程骨架增加 guard 字段，与 ADR-0007 决定 3 一致。具体检查输出见本卡结果，流程骨架与运行时入口仍由负责组另卡落实。
