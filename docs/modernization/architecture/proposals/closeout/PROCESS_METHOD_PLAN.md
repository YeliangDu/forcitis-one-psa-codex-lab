## 0. 根因与先要说清的冲突

- 数字不一致的根因：流程只在 `processes.v1.yaml`（82 个业务流程）里分五类存放，收尾新增号（PRC-136–144）记在 `PRC_ALLOCATIONS.md`，覆盖报告又把样板、合并流程算成「流程单元」，口径各不相同，没有唯一目录。
- 与已采纳 ADR-0050 的两处冲突（用户 L-10 定过，intent 112800），须在方法稿里摆出来、随过渡 ADR 由用户批：
  1. ADR-0050 决定 20② 与 J8 写「流程登记由 `.bpmn20.xml` 生成」。但事件策略、单聚合维护、读模型没有 BPMN 文件，目录无法只靠生成。提议：**目录 yaml 为唯一手写来源**，`.bpmn` 只管流程图，以流程编号关联，CI 核对两边名称、编号一致。
  2. ADR-0050 写「只有人工编排画 BPMN」。用户现在要样板用标准 BPMN 画。提议分两层：**全部业务流程画描述级 BPMN（协作图，含泳池、泳道、消息流）**；其中**人工编排流程另出 Flowable 可执行版**，只用可执行子集。

## 2. BPMN 样板

| 项 | 内容 |
|---|---|
| 版本 | BPMN 2.0.2（OMG formal/2013-12-09，同 ISO/IEC 19510:2013），`FRAMEWORKS.md` 第 2 节已锁定；开工前由子代理查 OMG 官网核实有无更新版本，结论写进 FRAMEWORKS 核实记录 |
| 源文件 | 每个样板一个 `.bpmn`（BPMN 2.0.2 XML，含 BPMNDI 图形信息）；可执行版另存 `.bpmn20.xml` |
| 画法规范 | 本会话写一页「BPMN 画法约定」：按 Bruce Silver《BPMN Method and Style》的风格规则（每个流程一个开始事件、结束事件按结局命名、网关标问句与出口标签、消息流只连泳池、不用跨泳池顺序流等）；任务类型对应 `where`：用户任务＝本系统人工，服务任务＝本系统自动或外部系统（外部方另画泳池并以消息流连接），手工任务＝线下；边界计时事件表示超时与升级；数据对象与数据存储表示读写的聚合 |
| 分工 | 三组各画自己的样板（他们最熟流程），本会话审画法与接缝 |
| 校验 | 用 bpmn-moddle 解析 XML 合法性；Silver 风格规则写成脚本能查的部分（开始结束事件、网关出口标签、消息流端点）；可执行版另查 Flowable 支持的元素子集 |
| 页面 | 样板页改用 bpmn-js 渲染（jsdelivr 或 unpkg 固定版本，发布前确认版本存在且满两周），不再手画 SVG；设计点与待定题保留 |
| 估时 | 画法约定 0.5 天；三组画样板 0.5–1 天（并行）；页面 0.5 天 |

## 3. 流程设计方法稿

承接：价值流阶段与门（③）、聚合与命令事件（④）、BC 与依赖（⑤）、流程清单（⑥a）。
写清：触发、角色、步骤（每步在哪发生）、判断点、超时与升级、跨 BC 消息、证据、审批节点。
下游交付：聚合命令与不变量（④ 回补）、表与迁入范围（DDL）、规则卡、验收测试场景（每条路径一条）、权限码与审批单据类型、页面清单（每个用户任务一页或一操作）、迁入映射（线下与外部步骤的证据如何迁入）。
双向追溯：目录 → BPMN → 命令 → 聚合 → 表；反向：每个命令至少被一个流程用到，每个用户任务对应一个权限码与页面；检查脚本扩展 `closeout_check.py`。
评审：opus 首轮，改后 sonnet 复核；与第 0 节两处 ADR-0050 冲突一起交用户批（随过渡 ADR 或单列确认页）。
估时：起草 1 天，评审与改 0.5–1 天。
