## 1. 依赖结构（描述性）

### 1.1 为什么不再设判据

第 1 版用三条阈值（层 ≤ L5、入度 ≥ 4 或传递入度 ≥ 9、下游涉及 ≥ 5 个阶段）选「地基」。评审第 7 条指出：B-30 恰等阈值、B-20 取整才达标、第 3 条用本稿自定的阶段归属（循环论证）、B-22 必须提前却没选中；而且一次投产路线下 W0–W4 全部先建，「地基」不改变任何做法。本版只列事实：层号、被谁直接依赖、传递入度。它在三种路线下的用处不同：

- 一次投产：只影响**建造顺序**（上游先建）；投产前全部建成，没有「先投产谁」的问题。
- 逐阶段（按模块）：决定**哪一段先切生产**，上游不在前段即形成第 2.5 节的冲突。
- 法人分批：主数据类上游（B-13、B-01、B-02、科目表）跨法人共用，第一批投产时就须对全部法人有效（第 5.1 节）。

P = "docs/modernization/architecture/proposals/aggregates_dep_check.py"; sys.argv = [P]
spec = importlib.util.spec_from_file_location("dc", P); dc = importlib.util.module_from_spec(spec); spec.loader.exec_module(dc)
owner, deps, counted, modules = dc.parse(dc.DRAFT.read_text(encoding="utf-8"))
edges, _ = dc.edges_from(owner, deps); built, _ = dc.built_edges(modules)
adj = {}
for s, t in edges: adj.setdefault(s, set()).add(t)
for _, _, s, t in built: adj.setdefault(s, set()).add(t)

### 1.4 事件机制（技术地基；用户经 one-coordinator 追加）

**现状（仓库证据）**：

- 选型：模块间事件用 Spring Modulith 事件发布登记表（JDBC），不保留 RocketMQ（ADR-0002 技术选型表「模块间事件」行，`adr/src/ADR-0002.md`:21）；跨聚合、跨模块协作一律用领域事件（GUIDING_PRINCIPLES:49）。Modulith 2.1.1（`backend/pom.xml`:6），`spring-modulith-starter-jdbc`。

- 116 个「仅分析」事件每个只多一行登记（`reporting` 一个监听者）；这是**上限**，因为财务事实本就不走事件（复核）；
- `reporting` 监听者失败或积压会留下未完成发布，按 ADR-0035 会**挡部署排空**；它不是过账请求，不挡关账（ADR-0031）。若要让分析侧故障不挡部署，须在 U-18 中明确分析侧死信可移入隔离登记后放行；
- 第 4.3 节 b′ 的已结历史经归档源装载，不经事件，与本节无关。

## 2. 建造顺序

### 2.1 排序原则

1. **依赖先行**：一个 BC 只在其全部上游（api、事件边）已建成后开工（聚合稿 §4.2；ADR-0041 决定 4）。
2. **业务价值**：同层内先做收入链（VS-02、VS-04，`STEP6A_PROCESSES.md` §1.2、§1.4），它承载权责事实主干（GUIDING_PRINCIPLES §9a）；其次是用量最大的工时（brief :165）。
3. **行级强耦合同批**：交付与工时同批（brief :166）；开票与 WIP 同 BC 同事务（ADR-0016 决定 5）。
4. **路线不同，顺序的含义不同**：一次投产下只是建造顺序；逐阶段下同时是生产切换顺序；法人分批下第一批的建造顺序同一次投产，之后各批不再建造、只做切换。

### 4.3 b′ 与 ADR-0025 C-3 已否决方案的关系（评审第 1、16 条）
