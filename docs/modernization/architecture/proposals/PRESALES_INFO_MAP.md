## 1. 对象一览

| 对象 | 定义 | 状态（草案） | 主要关系 | 三方依据 |
|---|---|---|---|---|
| 线索 | 尚未确认值得跟进的业务信息 | 新建 → 跟进中 → 已确认（转商机）/ 已关闭（原因必填） | 来源（类型）；0..1 客户；1 → 0..1 商机 | 行业：Deltek 线索与商机分开；用户：单独登记、确认后建商机；取证：A8 原生，近 24 个月 2,189 条，33% 无价值关闭，线索 → 商机基本一对一 |
| 商机 | 针对特定客户、特定项目要争取的机会 | 跟进中（内部阶段）→ 赢单 / 丢单（原因、竞争对手）/ 放弃（原因） | 1 客户；N 报价；0..N 投标；→ 合同；参与团队与角色 | 行业：四类终态带原因；用户：丢单记原因、多方参与；取证：近 24 个月 1,566 个，赢率 51.6% |

赢单 / 中标是**事件**（证据：中标通知书或客户委托），不是对象；招标公告、标书文件是单据。

## 2. 关系（草案）

```
线索 ──确认──▶ 商机 ──▶ 报价（N，版本链）
                 │──▶ 投标（0..N）──▶ 投标报价（引用一个报价）、保证金、资格预审、技术方案
                 │──▶ 风险交付授权（签约前）
                 └──赢单──▶ 合同 ◀──价格── 战略协议
                              │──▶ 合同变更 ──▶ 新基线版本
                              │──▶ 履约保证金
                              └──▶ 项目（交付段）
客户 ─▶ 客户集团；联系人 ─▶ 客户；供应商 ─▶ 分包合同（签约后段）
```

## 3. 三方不一致处（需用户定，见确认页）

1. 合同与项目：行业把合同（收入单位）与项目（交付单位）分开；老系统两者是同一份档案。
2. 风险交付：老系统没有授权、立项早于回签是常态；新系统做硬控制会立即影响约 90% 的项目。
3. 报价：用户说经常多轮，取证平均约 1.3 张、无版本链——多轮是否在线下改，还是同一张反复改。
4. 投标：两边系统都没有，行业与法规要求独立对象；比选、竞争性谈判、直接委托是否同一对象。
5. 战略协议：老系统按「框架 + 子项」挂靠，用户描述为「只定单价、另签合同」。
6. 虚拟客户：60% 客户是虚拟的，说明线索阶段被迫建客户档案；行业做法是线索可以没有客户档案。

## 4. 工作分解的一级 / 次级划分（用户 2026-10-15 同意，intent 见 2026-10-15 one-architecture「有权威理论来源，我同意」）

- 判据：一级 / 次级按依附关系，不按生命长短（BIZBOK v11 §2.5，第 194–195、198 页：次级概念依附其他对象存在，例 Agreement Term 依附 Agreement）。三者分别依附报价版本、合同、项目三个不同的一级对象，按依附判据即为三个不同的次级概念（2026-10-15 opus 评审指出：此前另引 DDD Reference 第 2 页属跨框架误用——限界上下文是领域模型层的概念，不用于业务对象识别，已删去）。
- 一级：服务产品与阶段类型模板（主数据，不依附任何项目）。
- 次级：报价估算分解（依附报价版本，可随版本修改）→ 合同范围条目（依附合同，只经变更修改；依法招标的不得背离投标承诺）→ 项目 WBS：阶段、工作包（依附项目，按执行调整、改后更新基线）。
- 串联：每个范围条目自报价起带稳定追溯编号；合同条目记来源报价版本条目，WBS 节点记对应合同条目（可后补，项目可先于合同），变更记「取代」关系。报价与投标时点须保留快照（合同承诺比对）。
