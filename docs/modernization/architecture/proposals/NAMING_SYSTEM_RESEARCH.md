# 命名体系 ADR 调研（只读，基线 origin/main，2026-10-17）

状态：历史记录｜2026-10-17｜负责：one-architecture

来源：one-coordinator 派子代理研究，2026-10-17 转本会话作命名体系 ADR 依据；标准链接未联网核对，起草前复核。

## 结论先行

1. **词表已是领域面的单一来源，缺的是两层：概念与指称分离（为多语言）、受控动词/状态词表（为命令/事件/状态）。** 其余命名面多数已有规范与守护，真正空白的是：消息键与多语言、角色码、审计动作名、触发器/函数/序列、测试名、读模型视图名。
2. **「原子词 + 组合规则」可行但不能靠现有词表直接生成。** 50 个抽样中 22% 能由已登记词按语法生成，48% 语法合规、只缺名词（问题在名词层未登记，不在语法），30% 须人工。
3. **ADR 只定稳定原则与分层，不定词、不定模板细则。** 动词表、模板、各命名面格式放细则文档，随守护演进。
4. 标准取舍（按用户补充「现在刚开始，代价是最低的时候」修订）：凡长期正确的结构一律完整采用，迁移量只作排期信息。采用：ISO 704/1087 概念与指称分离、XBRL 式标签角色、SKOS 式关系、CLDR/ICU 消息层、DDD/Event Storming、PostgreSQL 63 字节；TBX 采用其数据模型并作为标准导入导出格式，不作日常编辑源。
5. 链接说明：下列标准链接来自我已有的知识，本次未联网逐个复核，写 ADR 前须核一遍。

## 3. 原子词 + 组合规则可行性

方法：从 TERM_GATE_REPORT 按命令 20、事件 15、状态 15 随机抽样（种子 7），人工判断，样本不具统计意义。分三档：A 已登记名词 + 常规动词即可生成；B 语法合规、只缺名词；C 须人工。

- **命令 20**：A 1（批准风险交付授权）；B 16（如发布知识条目、关闭招聘需求、查验进项发票）；C 3（转入售前投入、占用进项发票入账、签字接受差异，为复合动作，应拆分或登记新动词）。
- **事件 15**：A 5（开票申请已作废、交付物已认可、不符合项已闭合、付款条件项已可结算、人员已登记）；B 8（如保证金已没收、请假已批准）；C 2（「已暂停」缺主体，「外部检测报告未采信」是否定式）。
- **状态 15**：A 5（已声明、已申报、已计划、内审中、未履行）；C 10，其中 5 个词汇化（拟派、可撤销、在用、草案、只读），5 个本身是动作或名词而非状态（申请、增员、减员、公示、计划），应改名或改归类。
- **合计**：A 11（22%）、B 24（48%）、C 15（30%）。

判断：瓶颈是名词层，不是语法。门禁报告中对象 60、聚合 78 未登记，名词先登记，命令/事件/状态才能生成。同时，已登记的 46 条命令和 95 条事件形式不一（「填报」「审核」「开票」「回款」与「合同缺口已豁免」并存），所以不能从现有登记反推模板，要先立模板，再迁移存量。

中英文模板差异：

| | 中文 | 英文 |
|---|---|---|
| 命令 | 动+宾：发布项目 | 动+名：`PublishProject` |
| 事件 | 宾+已+动：项目已发布 | 名+过去分词：`ProjectPublished` |
| 状态 | 已+动 / 动+中 / 未+动 | `Published` / `InReview` / `NotFulfilled` |

语序相反，不能字符串翻译，必须用结构化槽位 `{object, verb}` 再按 locale 渲染。动词表需要的列：中文动词、英文原形、英文过去分词（Approve→Approved，Write off→WrittenOff）、snake、对应标准动作（权限码）。中文一词多义也要拆开：「确认」可对应 confirm、acknowledge、recognise（确认收入）。

## 4. ADR 与细则的切分

**ADR（稳定）**：
1. 原则：概念 id 永久不变；指称可增改；词表是唯一来源；领域名不含老系统和外部系统名；缺失即失败。
2. 分层模型：概念层（id、定义、bc、标准依据）→ 指称层（locale、角色、状态：首选/可用/禁用）→ 命名面层（各面如何由指称投影）。
3. 命名面归属：每个命名面由哪份文档管、由哪类守护管（只列归属，不列格式）。
4. 生命周期：登记 → 批准 → 弃用 → 退役；改名只改指称、不改 id，改名走变更单并同步各面的迁移。
5. 多语言结构：locale 用 BCP 47；源语言为 zh-CN；代码标识符恒为英文 ASCII；界面与消息用 ICU 消息；缺失译文的回退规则。
6. 治理与守护：新词先登记；守护不通过不得合并；谁裁定（one-glossary、业务 Admin）。

**细则文档（可演进）**：动词表与状态词表；中英文组合模板；各命名面格式（DDL 类别词、URL、权限码、错误码、配置键、指标、日志、审计动作）；63 字节缩写规则；消息键约定与 ICU 用法；文档与卡编号；测试名；ACL 命名；守护清单与盲区。

**为何不会反复改 ADR**：ADR 里只有「分几层、谁是真源、改名怎么处理」，这些不随新增词、新增命名面或新增语言而变；新增一个命名面只是在细则里加一行并挂上守护。

## 5. 风险与待用户决定

1. **多语言要做到哪一步**：现有证据是「没有需求」，只立结构（locale 字段、消息键、占位符），还是同时要求英文界面在某期交付？这决定 CLDR/ICU 的采用时点。
2. **确认「概念—指称」模型落地方式**：terms.yaml 一次改为指称列表（推荐，现在最便宜），还是分阶段？
2b. **源语言与代码名关系**：是否确认「中文为业务源语言，英文为代码名，二者同为指称」。目前 terms.yaml 里英文是代码名，不是译文，合并两种角色会出问题。
3. **存量迁移**：未登记名 1143 条中命令 394、状态 346、事件 192 是否先补名词再生成，还是接受人工逐条登记。
4. **既有形式不一的 46 条命令与 95 条事件**：是否统一改名（影响已有代码与事件载荷）。
5. **状态是否单独分层**：把动作/名词误作状态的情形（申请、增员、计划）归入「改名」还是「移出」。
6. **未核实项**：DdlNamingTest 是否含 63 字节检查；角色码与审计动作名现有代码里有无事实用法；查询参数规范是否在 §2.6 内；上述标准链接是否仍有效。
