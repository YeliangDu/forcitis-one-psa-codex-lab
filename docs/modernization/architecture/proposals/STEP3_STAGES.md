## 1. 阶段写实复核

### 1.1 做法

1. **脚本核对**：读 YAML 全部条件叶子（起始、结果、进入、退出、段内、贯穿活动输入输出），状态按「/」「→」拆开（与 `vs_links_gen.py` 同一拆法），逐个比对信息图该对象「关键状态」列。机械不符只有 OBJ-35「已声明」一项（第 1.3 节）。
2. **逐段语义复核**：机械比对只证明状态名存在，不证明门写对了。逐段再查四件事：(a) 门引用的状态在对象状态序列里是否会被越过——越过后门就误报；(b) 条件结构是否表达了原意（`any` 只有一项时等于必备）；(c) 段内应引用而未引用的对象（描述里写了、走查里有、对象却不在条件里）；(d) 每个进入或起始状态有没有某个阶段或触发干系人产出它（第 1.4 节）。
3. **本步定的写法**【裁量】（写入 YAML note，供第 ⑥a 步沿用）：
   - W-1 门条件写「已达到且尚未越过」的全部状态：对象出了本段还会继续流转的，写当前状态及其后继（如协议「已签署生效 / 履行中 / 已完成」）。依据：门只预警（S2），状态越过即误报，等于让预警失去意义。
   - W-2 单项 `any` 一律改写：只适用于部分实例的条件放进 `all`，note 写「适用条件：……」；可有可无的写段内状态。依据：YAML 文件头定义 `any` 为「至少一项满足」，单项 `any` 与 `all` 等价，与原注「如需」「有票时」相反。
   - W-3 外部引用对象（招标项目、建设工程）与目录对象（阶段类型）只作段内状态，不作门。依据：外部引用「只记录、不控制」（信息图 OBJ-19、OBJ-46 豁免说明）；目录启用是服务产品与 WBS 的不变量（INV-34），不是阶段门。

## 2. 能力—阶段对账

### 2.1 对账算法【裁量，评审改】

1. **人工映射为主**：逐阶段读名称、描述与价值项，判断该阶段在做什么业务，映射到一级能力；映射的是「阶段要做的事」归哪个能力，不是「条件里引用了哪个对象」。
2. **条件引用只作佐证**：脚本列出的条件引用对照（第 2.2 节右列）用来核对人工映射有无遗漏，不能单独让一个能力过账。条件里引用、但阶段描述与价值项里没有归处的，视为凑覆盖，撤回（C-02、C-04 的 OBJ-25，C-11）。
3. **「计二级」由 G-1、G-2 推出**【推出】：能力图由对象生成（G-1），一级能力汇聚其二级能力（G-2），故阶段描述做的事归在某一级能力的二级能力上，即算该一级能力支撑该阶段；这是能力图结构的直接推论，不需另问用户（原 U-1 删除）。
4. 价值流的起始、结果与贯穿活动的输入输出**单列**，不计入「支撑阶段」：起始与结果不是阶段，活动不是阶段（W-4）。
5. 对账检验阶段覆盖与能力去向，不检验信息图（METHOD 第 ② 步第 6 条；第 3 稿评审 B2）。
