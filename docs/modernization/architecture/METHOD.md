# 施工图方法：从证据到代码（ADR-0041，2026-10-15）

依据：用户 2026-10-15「像施工图一样」（intent `2026-10-15-160111`）、「能不能彻底打通所有架构设计的核心理论，找到从愿景到代码的施工图的设计方法」（intent `2026-10-15-164119`）；按适配评审改为不变量先行（ADR-0041 取代 ADR-0040，intent `2026-10-15-195827`）。理论参照只取 `FRAMEWORKS.md`。

## 1. 一句话

BC 的边界由**不变量与一致性需求**决定，不由能力地图决定。从规则卡、会计规则与生产取证出发，推导聚合，再按统一语言聚成 BC；价值流只用来端到端验证，能力地图只用来查漏。

```
证据（OA 模板 · 规则卡 · 生产取证 · 业务走查）→ 不变量 → 聚合 · 命令 · 事件 → BC → 流程 → 表（注册表）→ 分析事实 → 指标
```

**优先级规则**：已采纳、有证据的不变量 ADR（如 ADR-0016 的单一过账管道、期间闸门、WIP 与开票同一事务边界）约束任何推导结果，反之不成立。推导结果与已采纳 ADR 不同时，新开 ADR 并附新证据。

## 3. 六条接缝

| # | 接缝 | 规则 | 可校验的交接物 |
|---|---|---|---|
| 1 | 规则卡 ↔ 聚合 | 规则分四类：**不变式**放聚合；**判定**（路由、资格、级别）暂放版本化配置表或代码（DMN 推迟，FRAMEWORKS §7）；**人工编排**放 BPMN；**计算**放值对象或领域服务 | 规则卡 `类别` 字段；聚合引用规则卡编号 |
| 2 | 聚合 ↔ 事件 | 每个事件由一个聚合发出；跨 BC 只经事件或 api；经济事件复审对偶与承诺（FRAMEWORKS §1 复审问题） | 事件目录的发布方与消费方声明（EventCatalogueTest） |
| 3 | 价值流 ↔ BPMN | 只有人工编排画成 BPMN；每个 BPMN 流程登记所属阶段 | 由 `.bpmn20.xml` 生成的流程表 |
| 4 | 聚合 ↔ 表 | 一个聚合的表在同一 schema；主数据由拥有该聚合的 BC 负责，跨 BC 只按 ID 引用；表与聚合的对应只在注册表登记 | DataArchitectureTest |
| 5 | OLTP ↔ OLAP | 分析事实来自领域事件或过账明细，不在交易表上算分析；总线矩阵的行是业务过程（过账事实类型或领域事件类型） | 生成的总线矩阵；指标以 METRIC_BASELINE 为准 |
| 6 | 架构 ↔ 代码 | BC = 模块 = schema；上下文映射 = 模块依赖图；结构变化先改 SSOT 再改代码 | CI A1–A7（DESIGN §4）；改架构文件带 `Architecture-Ref` |

**一个事实只手写一处**：上下文映射以 `module-dependencies.txt` 为准；聚合与表以数据访问注册表为准；流程登记由 `.bpmn20.xml` 生成；术语以 `terms.yaml` 为准。其余文件只引用或生成。

## 4. 怎么用在现代化上

- **老系统只作证据**：老模块、老表、老流程只出现在 `evidence` 里；规划项（来自老系统切法或已有 ADR）进入阶段前按第 1–5 步重新推导，不直接照搬为目标。
- **增量推进**：只对本阶段做第 1–5 步；已建部分以代码为准、只做合规核对。
- **决策归属**：范围、BC 边界、深建模标记、指标口径、路线图由用户定（在线决策页写明代价、不预选）；第 2、4、5 步的细节由本会话提议、评审把关。
- **度量**：`togaf/vision.yaml` 的 KPI 是阶段出口度量（迁移进度与控制有效性），不驱动 BC 推导；业务目标与目标值由用户给出后再登记。
