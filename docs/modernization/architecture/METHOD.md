# 施工图方法：从愿景到代码（ADR-0040，2026-10-15）

依据：用户 2026-10-15「能不能彻底打通所有架构设计的核心理论，找到从愿景到代码的施工图的设计方法」（intent `2026-10-15-164119`）、「像施工图一样」（intent `2026-10-15-160111`）。理论参照只取 `FRAMEWORKS.md` 锁定的版本。

## 1. 一句话

TOGAF ADM 管**走的顺序**，DDD 管**切的边界**，事件风暴、BPMN、DMN 管**动的方式**，DAMA、OLTP、OLAP 管**数据与度量**。几个框架之间的接缝没法消除，因为它们回答的是不同的问题；本方法给每条接缝定一条衔接规则和一个可校验的交接物，用稳定 ID 串成一条闭环：

```
目标 GOAL → 能力 CAP → 价值流阶段 VS.n → 子域 / BC → 聚合 · 命令 · 事件 → 流程 PROC / 决策 DEC → 数据对象 DO → 表 → 分析事实 → 指标 M → KPI → 目标 GOAL
```

## 2. 八步（每步：输入 → 交付物（SSOT 文件）→ 校验）

| 步 | 框架依据 | 做什么 | 交付物 | 谁定 | 校验 |
|---|---|---|---|---|---|
| 0 愿景与原则 | TOGAF Preliminary、A | 写下驱动力、目标、可度量的 KPI、架构原则 | `togaf/vision.yaml`（GOAL-xx；KPI 只记编号、名称与对应的指标 M-xx，口径按 OAT 原语，ADR-0016 决定 7）；原则沿用 GUIDING_PRINCIPLES | 用户 | 每个目标至少一个 KPI |
| 1 能力与价值流 | TOGAF B；G211、G178 | 列业务能力（名词 + 动词，只说「做什么」）；画价值流及其阶段，每个阶段标出支撑它的能力和产出 | `togaf/capabilities.yaml`（CAP）、`togaf/value-streams.yaml`（VS.n） | 用户确认 | 每个阶段有能力支撑；每个能力至少支撑一个阶段 |
| 2 战略设计 | DDD 战略；Vernon 子域分类 | 按战略差异化给能力打热度，热的是核心、通用的外购或沿用、其余为支撑；把能力分配到子域与 BC；定上下文关系 | `ddd/subdomains.yaml`、`ddd/contexts.yaml`、`ddd/context-map.yaml`；核心子域各写一页领域愿景声明 | 用户定分类与边界 | **接缝 1** |
| 3 行为建模 | 事件风暴；BPMN；DMN | 每个价值流阶段先做全景事件风暴，找出关键事件；再做流程级，得到命令、策略、读模型与聚合；把规则分类落位 | `ddd/aggregates.yaml`、`bpmn/processes.yaml`、`dmn/decisions.yaml`（到这一步才扩充，不预建）；规则卡带「类别」 | 本会话提议，评审 | **接缝 2、3** |
| 4 数据设计 | DAMA；OLTP | 由聚合导出数据对象，只登记数据访问注册表里没有的数据类别（D17）；表、负责 BC、记录系统引用注册表，敏感分级引用 `data-classification.txt`；逻辑模型落到每个 BC 一个 schema | `dama/data-objects.yaml`；数据访问注册表；迁移脚本 | 评审（D1–D19） | **接缝 4** |
| 5 分析设计 | Kimball 四步；OLAP | 业务过程取价值流阶段，粒度取一条事件或过账明细，维度取 BC 负责的主数据；指标口径按 OAT 原语 | 生成总线矩阵；指标以 METRIC_BASELINE 为准，不另建文件 | 用户定口径 | **接缝 5**；每个 KPI 可从分析事实算出 |
| 6 迁移规划 | TOGAF E、F | 基线与目标做差距分析，排过渡架构；每个过渡架构交付哪些能力与 BC，以及入口与出口条件 | `togaf/transitions.yaml`；brief 各阶段 | 用户批准 | 每个规划 BC 进入阶段前按第 1–5 步重新推导（README「规划项不是目标」） |
| 7 实施治理与变更 | TOGAF G、H | 先登记再写代码；CI 校验代码与 SSOT 一致；结构变化写 ADR；触发式合规评审与阶段出口评审 | 代码；`module-dependencies.txt`；事件目录；ADR；合规记录 | 守护 + 评审 | **接缝 6**；CI A1–A7 |

## 3. 六条接缝的衔接规则

| # | 接缝 | 规则 | 可校验的交接物 |
|---|---|---|---|
| 1 | 能力 ↔ 子域 / BC | 子域分类由能力的战略差异化决定，不由技术或老系统模块决定；**每个叶子能力只归一个 BC**，一个 BC 可承接多个能力；BC 边界以统一语言的一致范围为准 | `capabilities.yaml` 每项带 `bc`；生成「能力 → BC → 模块」追溯表（阶段出口评审用） |
| 2 | 价值流 ↔ 事件风暴 ↔ BPMN | 价值流阶段的边界就是关键事件；阶段内的命令、策略来自流程级事件风暴；**只有人工编排（任务、超时、退回）画成 BPMN**，自动反应写成事件策略 | 每个阶段列关键事件（eventType）；每个 BPMN 流程登记所属阶段 |
| 3 | 业务规则 ↔ DMN ↔ 聚合 | 规则分四类：**不变式**放聚合（违反即拒绝）；**判定**（路由、资格、级别）放 DMN；**人工编排**（谁处理、超时、退回）放 BPMN；**计算**放值对象或领域服务 | 规则卡 `类别` 字段；DMN 决策与聚合都引用规则卡编号 |
| 4 | 聚合 ↔ 数据对象 ↔ 表 | 数据对象 = 聚合的状态 + 它发出的事件；一个聚合的表在同一个 schema；主数据由拥有该聚合的 BC 负责，跨 BC 只按 ID 引用 | `data-objects.yaml` 只引用注册表的表键分组，并登记注册表没有的数据类别；负责 BC 由 schema 推导，不另存 |
| 5 | OLTP ↔ OLAP | 分析事实（事实表，不同于 `operations.facts` 的经营事实）来自领域事件或过账明细，不在交易表上算分析；一致性维度就是各 BC 负责的主数据，版本化对应 SCD Type 2；指标口径按 OAT 原语声明 | 总线矩阵：价值流阶段 × 主数据；KPI → 指标的对应只在 `vision.yaml` 一处登记 |
| 6 | 架构 ↔ 代码 | BC = 模块 = schema；上下文映射 = 模块依赖图；聚合、事件、命令与代码同名同界；过渡架构 = 阶段与工作卡；结构变化先改 SSOT 再改代码 | CI A1–A7（DESIGN §4）；改架构文件须带 `Architecture-Ref` |

## 4. 怎么用在现代化上

- **老系统只作证据**：老模块、老表、老流程只出现在条目的 `evidence` 里。第 1–5 步从目标、能力与价值流推导，不从老系统切法推导（intent `2026-10-15-160111`「避免按照旧系统架构直接现代化」）。
- **增量推进**：每个阶段开工前只对本阶段涉及的价值流做第 1–5 步，第 6 步更新路线图，第 7 步建设；已建部分以代码为准、只做合规核对。
- **决策归属**：第 0、1、2、5、6 步的结构性选择由用户定（在线决策页）；第 3、4 步由本会话提议、评审把关。

## 5. 与现状的差距（交 one-coordinator 排期）

| 差距 | 补什么 |
|---|---|
| 没有愿景、目标、KPI 的机器可读登记 | 第 0 步：`togaf/vision.yaml`，从 INTENT 与 MODERNIZATION_BRIEF 第 1 节提炼，交用户确认 |
| 没有能力地图与价值流（原定参照 forcitis-architecture，已撤销） | 第 1 步：在本仓库按 G211 / G178 推导，交用户确认；完成后决策页 Q6（子域分类）才有依据 |
| 规划中的 28 个 BC 来自老系统切法或 ADR | 第 2 步：能力地图完成后重新推导，再改为目标 |
| 没有事件风暴记录；规则卡没有「类别」 | 第 3 步：等第 1 步确认价值流后，先做 1a 已建 BC 的事件风暴；规则卡只补类别、不改内容（批量交 sonnet，one-architecture 抽查） |
| 指标只有草稿 M-01–M-48，KPI 尚未对应 | 第 0 步之后：在 `vision.yaml` 中给 KPI 填对应的 M-xx，口径以 OAT / METRIC_BASELINE 为准 |
| CI 只计划了 A1–A7 | 第 7 步：增加追溯完整性校验（每个已建 BC 有能力、每个指标有 KPI），只拦新增 |
