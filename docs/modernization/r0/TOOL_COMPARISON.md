## 1. 小样做了什么

三个看板取自真实在用报表的问题，用合成数据实现：
- D1 经营月报：BU × 月，收入确认、开票、回款、现金回款的实际值，对预算 / 承诺 / 挑战目标及其达成率；
- D2 应收：BU × 账龄桶，并列「账龄超 90 天」与「逾期（过到期日）」；
- D3 人效：平均在册人数、利用率（日标准工时按法人参数化）、人工成本产出倍数。

四个选项各实现一遍，逐格比对（`check.py`）：D1 402 行、D2 30 行、D3 105 行，**差异全部为 0**。A、B、C 三份是独立实现，一致有证明力；D 的视图 SQL 取自 A，它与 A 的一致只说明 Metabase 读数不改数。

实测中还发现一个教训：目标「最新版本」的口径一开始写错了，A 与 B 同样写错、彼此却一致。**结果一致只证明实现与同一份口径相符，不证明口径对**。口径正确性只能靠单一定义加上与财务、业务核对的验收基线，不能靠多份实现互相印证。

## 2. 实测对照

| 维度 | A 保留老 BI 写法 | B 以新经营分析为基础 | C 并入 FORCITIS one | D 引入 BI 工具（Metabase） |

小样里的代码量和耗时（A 约 130 行、B 约 145 行、C 约 280 行含守护测试、D 约 50 行脚本加 100 行视图）只说明「写出同样三个看板」的量级，**不代表真实建设成本**。真实成本主要在前端、权限、导出、下钻，以及与 8 个报表包的覆盖程度，这些小样都没有做。

## 4. 建议（待用户决定）

**建议：以 C 为主，B 作设计输入，D 留作可选的后续补充，A 只作过渡。**

1. **C 承担语义层与 8 个报表包**：
   - 理由：指标的唯一定义、OAT 与用语守护、按版本治理、与总账报表共用期间和维度，这四条是 R0 发现的问题（K1–K12）的根因对策。只有 C 能在同一仓库、同一语言、同一套 CI 守护里一并做到，小样已经演示了守护。
   - 代价：前端、导出、下钻、透视都要自建，是四个选项里建设量最大的。
2. **B（新经营分析）冻结作设计输入**（与 Q3 决定一致）：
   - 沿用其事实粒度 ADR、对账证据、授权模型与前端交互（透视、导出、保存分析）；
   - 不沿用其 Node 语义引擎；
   - 若 C 的前端沿用 AG Grid 的透视能力，企业版许可（B 未决项）仍需决定。
3. **D 不作为主工具**：
   - 它不能强制只用共同定义，而这正是现状要解决的问题；开源版也没有行级沙箱。
   - 若以后需要给少数分析人员开放自助探索，可以加一个 BI 工具，但只连 L1 / L2 只读视图、关闭原生 SQL；选型时优先比较开源版就有行级规则的工具（例如 Superset，未实测）。
   - 这是 R6 之后的可选项，不在 R1 范围。
4. **A 只作过渡**：老 BI 在过渡期照常运行，靠过渡镜像（Q7），R6 下线；不在其上新建模（用户已暂停）。

若用户更看重上线速度、愿意接受第二个服务，B 是次选：语义层先在 Node 中按小样扩 8 处，口径目录由 `operations.policy` 生成后同步过去。代价是两套语言、两套部署、两套身份接入，以及跨仓库的守护。

## 6. 局限

- 小样没有前端、下钻、移动端、浏览器截图，也没有 B 的授权；Superset 只做了文字比较（通用知识）。
- 合成数据规模小（几千行），性能结论不可外推。新经营分析在 PG 上 65 万行工时的规模测试见 BI_SCOPE §3.1。
- 小样目录里的「回款」OAT 符号（COLL）是样例自拟，OAT 正本中没有回款原语（基线 M-11 的 OAT 列为 —）。
- 一个流程问题：Metabase 初始化时，子代理在本机一次性容器里用随机测试凭据创建了首个管理员账号；凭据只写在本地文件，已删除，实例随容器删除。今后此类操作先征得用户同意。
