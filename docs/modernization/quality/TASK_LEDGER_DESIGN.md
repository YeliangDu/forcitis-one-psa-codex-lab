## 二、产出

1. `docs/modernization/task_ledger.py`（与 `check_tasks.py` 同目录、同源：读同一批片段与同一套字段/状态常量，不复制）：生成 `tasks/TASK_LEDGER.md`（按主线、波次、会话三种视图 + 度量节）和机读 `tasks/TASK_LEDGER.csv`。
2. 生成物不手改；**不入仓**（与 `TASKS.md` 一致，列入 `.gitignore`，看 generated-docs 分支），因为内容随 PR 状态每天变；每晚与每次合入后由 `build_all.py` 重生成。
3. 度量口径写在脚本说明和 `TASK_LEDGER.md` 页首，分母分子都列出。
4. 脚本**不联网**：git 部分直接读本地 `origin/main` 与远端分支；PR/CI 部分读一份 `gh` 导出的 JSON（`--prs-json`、`--runs-json`，与 `task_backfill.py` 同一做法），导出命令写在说明里，由人或定时任务运行。没有导出文件时对应列写「待核」，不猜。

## 四、回溯卡口径（10-14 到 10-17 没有任务号的工作）

1. **单位**：以**分支**为单位聚合已合入的 PR。同一分支名下的多个 PR（含被关闭重开的）归一张回溯卡，这样「一卡多 PR」对回溯段也有意义。分支名是会话工作区的随机名（`claude/<形容词>-<人名>-<hash>`、`claude/xin-<hash>`）时，一个分支会跨多个互不相关的工作，退回 **PR 为单位**（一个 PR 一张卡）。随机名的判定写成一条可测的正则，放在脚本里。
2. **任务号**：`RET-<MMDD>-<会话码>-<两位序号>`，MMDD 取该卡首个 PR 的合并日，会话码取分支名里的会话（`one-glossary` → GLO，对不上取 `UNK`），序号当日自增，按首个 PR 号排序，**同一输入永远生成同一编号**（可复现）。前缀 `RET` 不在 `LANES`，所以不会与正式号冲突，`check_tasks.py` 也不扫它（回溯卡不写成片段文件，只出现在台账里，片段 114 张不变）。
3. **已有片段不重复**：一个 PR 已被某张正式片段认领，就不再进回溯卡。认领规则按强弱顺序：PR 标题含任务号；片段「分支」字段等于该 PR 的 head 分支；合并说明含任务号；片段「提交」字段列出的提交在该 PR 里。38 张回填片段按它们自己写的分支/提交认领。
4. **任务名/主线/bc/会话**（回溯卡没有人填）：任务名取首个 PR 标题；主线按标题前缀推断（`feat(approval)`→代码实现，`docs(glossary)`→命名，`ci:`/`fix(merge)`→合并与 CI，`docs(adr)`→架构整合 …，映射表写在脚本里并有自测）；bc 取标题括号里的模块名对 `glossary/bcs.yaml`，对不上写跨域；会话取分支名前缀，对不上写 `待核`；执行者写 `待核`。**这些全部标「推断」**，台账里加一列「推断字段」。
5. **批次/阶段**：回溯卡按 bc→阶段映射；对不上归「未归属」，不硬编。
6. **会话日志用途**：`session-log/` 和 `SESSION_LOG.md` 只用来核对会话名与日期、补充任务名（当 PR 标题过于笼统，如 `Merge branch …`），不当计数来源。批次计划（`NEXT_BATCH_PLAN.md`）用来给 TA-1a 内的回溯卡挂批次号，对不上的不挂。
7. **不倒推**的：体量与返工指标里 10-17 前拿不到的（冲突退回、阻塞时长、片段状态历史）写「待核」，不补零。

## 五、实现分工与步骤

1. 先报本设计，确认七里的问题（不动代码）。
2. 抽取层（交 Codex）：`task_ledger_extract.py` 从 git 与导出 JSON 产出中间 JSON（卡↔PR↔提交 的映射、每 PR 的体量），自测用临时 git 仓库；统计层（交 Codex）：由中间 JSON 算度量与三种视图、CSV。**回溯卡的聚合规则与随机分支名正则、卡↔PR 的认领规则、指标口径由我写**（语义判断不交 Codex，SESSION_PLAYBOOK TEAM-33）。
3. 验收：我在真实仓库上跑，抽样 20 张卡核对 PR 数/提交数/行数与 `git` 原始输出一致；回溯卡覆盖率（432 个 PR 全部被某张卡认领，无重复认领）；两次生成逐字节一致。
4. PR 首轮 opus 复审；守护类（认领规则）单列。
