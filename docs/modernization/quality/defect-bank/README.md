# 错题本（三道防线之第三道：回测）

依据：SESSION_PLAYBOOK TEAM-71、72（用户 2026-10-16 采纳「三道防线」）。每个会话维护**本领域已知缺陷清单** `docs/modernization/quality/defect-bank/<会话名>.md`；新产出交出前，对着清单逐条回测；漏了就补一条检查项，新出的错**当日**入册。第一道（机械检查）见 `scripts/precheck.sh`，第二道（独立评审）见 [../review-briefs/](../review-briefs/README.md)。

## 一个会话一个文件，一条一个小节

文件名与会话名一致（如 `one-quality.md`、`one-1a-par.md`），一个会话只写自己的文件，所以不会和别人冲突。条目只增不删，编号不重用；改状态直接改该条的「状态」行。

```
### <前缀>-NNN　<一句话标题>

- **日期**：YYYY-MM-DD
- **类别**：转述未核 | 局部测试 | 先推后测 | 授权读宽 | 发布未验 | 提交卫生 | 沟通 | 其他   ← 受控词，只选一个；同类错在两个以上会话出现，由 one-quality 出机械守护
- **现象**：错在哪里、谁在什么时候看到（可观察的结果，不写推测）
- **根因**：为什么会出这个错（一层一层问到可以防的那一层，不写「疏忽」）
- **拦下于**：哪一道防线或哪一步发现的——机械检查（写哪个检查）/ 独立评审（写模板与评审编号）/ 回测 / 作者自审 / 调度或用户 / CI 或生产才发现。没发现过就写「未被拦下（事后发现）」
- **漏过于**：本该拦住却没拦住的防线（可多个，写各自为什么没拦住）；没有则写「无」
- **新增检查项**：补了什么，写到可以定位的地方——脚本与守护的路径、precheck 的条目、评审模板的条款号（如 `review-briefs/04` P8）、画像「工作守则」的条；还没补写「待补」并写负责人和日期
- **状态**：已落实 / 待落实 / 不适用（写理由）
```

- **编号**：前缀由会话在自己文件第一行下面声明，须与已有的册不重复（例：`one-quality` → `QUAL`，`one-1a-par` → `PAR`，`one-1a-next-4` → `NEXT4`）；后面三位序号从 001 起。
- **现象与根因要能让没经历的人看懂**，涉及生产数据时只写类型与计数，不写明细（CLAUDE.md 第 4 条）。
- **「拦下于」「漏过于」是这份表的价值**：它回答「这类错下次会被哪一道防线拦住」。三道防线都漏过的，必须补新检查项，状态不得是「不适用」。

## 机械检查

`defect_bank_check.py`（接进 `build_all.py`）检查册的格式：字段与顺序、日期、编号前缀与全局唯一、状态词；状态“已落实”须在“新增检查项”里给出存在的路径，“待落实”须写“负责：<会话>”和日期（超 7 天告警）；类别须取自受控词。同一类别出现在两个以上会话时报告，由 one-quality 出一条机械守护（防错），不再各册各补一条软约束。表格式的册先只统计，迁移成上面的条目格式后纳入检查；类别、落实路径、待落实负责人三项迁移完成前只报告，之后转为失败。

## 回测怎么做

交出新产出前（卡、PR、报告、决策页）：

1. 读自己的错题本，挑出与本次产出相关的条目（同一类对象、同一类工具）；
2. 逐条检查本次产出是否重犯，**检查方法用条目里的「新增检查项」**，不凭记忆；
3. 在交出的报告或 PR 说明里写一行：`错题本回测：相关 N 条，全部未重犯` 或 `错题本回测：重犯 <编号>，已修`；
4. 回测时发现错题本没覆盖的新错，当日补一条。

## one-quality 的汇总

one-quality 每月汇总各册：新增条数、各道防线「拦下 / 漏过」的次数、「待落实」超过一周的条目；结果报 one-coordinator。同一类问题出现第二次，说明上一次的新增检查项没落到位，由 one-quality 复盘。
