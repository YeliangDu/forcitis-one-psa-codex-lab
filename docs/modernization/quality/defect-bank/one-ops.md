# 错题本：one-ops

前缀：`OPS`。格式按 `README.md`；交出新产出前逐条回测（SESSION_PLAYBOOK §11 第 11 条）。OPS-001 至 OPS-003 来自 C-14 探针编排脚本 `c14_run.py` 及其辅助脚本 2026-10-15 至 16 的多轮复审返修（提交见各条）。

### OPS-001　错误码判定写得太宽或太窄，复审逐项返修

- **日期**：2026-10-16
- **类别**：局部测试
- **现象**：c14_run 对「平台拒绝」的识别先只认 4613，后来第 10、15 项实测给出 15151 才补认；之后又发现拒绝码应按项区分，15151 要当场查证 sa 不可见而探针可见，再改为用 sys.server_principals 判可见性（提交 8895233e、f3725d56、b19048e3、c43431bc）。每一轮都是复审或实跑才发现
- **根因**：判定函数只按已见到的一两个真实返回写，没有列出该平台对同一类拒绝可能给的全部错误码，也没有为每个判定分支准备伪造的输入去跑；错误码、拒绝原因、可见性三件事混在一个条件里
- **拦下于**：独立评审（opus 首轮与终审）、实跑
- **漏过于**：作者自审（只在真实环境跑过一条路径）；机械检查（该脚本没有自测，precheck 不覆盖）
- **新增检查项**：写运维脚本里的错误码或状态判定时，先在注释外的判定表里列出已知返回与期望结论，再为表里每一行写一条伪造输入的自测；脚本自测见 OPS-004
- **状态**：待落实（负责：one-ops，2026-10-17 起）

### OPS-002　退出码不统一，异常路径退出码与说明不符

- **日期**：2026-10-16
- **类别**：局部测试
- **现象**：预检失败、可见性对照失败、收尾时断管或收到信号，退出码各不相同或沿用 120；剧本里写的退出码与实际不符；预检失败时结果没落盘（提交 e0da9185、6c0a5b6e、284efcb2、aa147f13）
- **根因**：退出码在各处就地 `sys.exit(n)`，没有一张码表；异常路径（断开终端、信号、保存时抛错）没人跑过
- **拦下于**：独立评审（首轮、终审、再核对）
- **漏过于**：作者自审；机械检查（无自测，无退出码表与剧本的一致性检查）
- **新增检查项**：脚本顶部放一张退出码表，剧本引用同一张；自测对每个退出码造一个触发场景（含信号与断管）；待补，见 OPS-004
- **状态**：待落实（负责：one-ops，2026-10-17 起）

### OPS-003　「残留」「不存在」的判定缺信号时被当成确定结论

- **日期**：2026-10-16
- **类别**：局部测试
- **现象**：c14_orphan_test 先后因：无错误号也判残留、msdb 零行判成推断残留、基线不干净仍进第二轮、NotFound 未视作不在、读不到状态就跳过删账号，被复审要求修改；c14_run 的删库逐库容错和 clean 计数也经历同类返修（提交 bdb71c05、c2221c90、00ea413e、b19048e3）
- **根因**：把「没读到」「读到空」「读到错误」当成同一种结果；没有三态（有 / 无 / 无法判断）的设计，无法判断时应失败并告警（CLAUDE.md 第 6 条），脚本却给了结论
- **拦下于**：独立评审（opus，每轮 3–5 处）
- **漏过于**：作者自审；机械检查（无）
- **新增检查项**：残留与存在类判定一律三态，「无法判断」不得折算为有或无；自测对三态各造一个输入；待补，见 OPS-004
- **状态**：待落实（负责：one-ops，2026-10-17 起）

### OPS-004　运维脚本没有自测，靠复审来回改

- **日期**：2026-10-17
- **类别**：局部测试
- **现象**：C-14 编排脚本共经历约 9 轮复审返修（OPS-001 至 OPS-003 是其中最集中的三类），每轮 3–5 处，多数是用伪造输入跑一遍就能暴露的
- **根因**：这类脚本全部操作真实云资源与生产只读库，只能在真实环境跑，作者没有把判定与退出码部分拆成不碰云的纯函数，所以没法写自测，只能交给复审
- **拦下于**：调度（one-coordinator 日报评级 2026-10-17）
- **漏过于**：全部三道防线（无自测、precheck 不覆盖 handoff/ 下脚本）
- **新增检查项**：把 `c14_run.py` 的判定、退出码、三态逻辑拆成纯函数，加 `--self-test`（不连网、不碰凭据），接进 `scripts/precheck.sh`；该脚本须与 origin/main 逐字节一致才能运行，所以是单独一个代码 PR，走 opus 复审；待补
- **状态**：待落实（负责：one-ops，2026-10-17 起）

### OPS-005　装 rc.5 的步骤按「非首次安装」写，没先比对基线迁移是否被改

- **日期**：2026-10-17
- **类别**：转述未核
- **现象**：OPS_CONTEXT 里 rc.5 部署六步写的是非首次安装、停服 2–3 分钟；开工后比对 f7cd54d0 与 2694ecc6 发现 4 个已有基线迁移文件被改，必须先重建 dev 库（数据清空）。已在装前停下，未造成损失
- **根因**：写步骤时只核对了「rc.5 比 rc.4 多哪些迁移」的字面（无新增文件），没有核对已有迁移文件是否改过；dev-db-rebuild 剧本的触发判断没有放进部署前步骤里
- **拦下于**：作者自审（装前列迁移）
- **漏过于**：OPS_CONTEXT 的步骤清单（没写这条判断）；`deploy_gate` 对 dev 只在门禁里告警，不在手工安装路径上
- **新增检查项**：OPS_CONTEXT「坑」加一条：任何 dev 部署前先跑 `git diff --name-status <当前运行提交> <目标提交> -- backend/src/main/resources/db/migration`，有 M 即走 dev-db-rebuild.md 并先问用户
- **状态**：已落实（`docs/modernization/phase1a/infra/OPS_CONTEXT.md`「坑」；`runbooks/dev-db-rebuild.md`「何时触发」）

- **日期**：2026-10-17
- **类别**：先推后测
- **现象**：#448 补维护角色断言时，`c3_dev_db_check.sh` 有一项 FAIL，我没有读完输出就提交并推送（4ef34fd7），随后才发现并用 b4a40ccd 修复；已通报 one-coordinator，合并以最新为准
- **根因**：用 `grep -E "FAIL|verify"` 过滤输出，FAIL 行出现了却被后面的命令串（提交、推送）接着执行；没有把检查脚本的退出码当作提交的前提

- **状态**：已落实（`docs/modernization/phase1a/infra/OPS_CONTEXT.md`「坑」）

### OPS-007　回滚脚本对「角色不存在」不幂等，重建时中途报错

- **日期**：2026-10-17
- **类别**：局部测试
- **现象**：dev 重建时执行 `c3_dev_db_rollback.sql`，库删掉后在 `DROP ROLE one_dev_audit_maintainer` 处报「角色不存在」而停止（旧 dev 库按 #448 之前的脚本建，没有该角色），剩下四个角色要手工删，再重跑建库脚本；没有造成数据损失
- **根因**：#448 给建库脚本加了新角色，回滚脚本同步加了 `DROP ROLE`，但按「新建库」的状态写，没考虑旧库升级路径；`c3_dev_db_check.sh` 只测新建库
- **拦下于**：作者执行时（重建当场）；one-coordinator 指出
- **漏过于**：独立评审（#448 复审未覆盖「旧库没有新角色」）；check.sh（无回滚用例）
- **新增检查项**：回滚脚本的 `DROP ROLE` 改 `IF EXISTS`；`c3_dev_db_check.sh` 补「旧库缺维护角色时回滚仍通过」用例；待补
- **状态**：待落实（负责：one-ops，2026-10-17 起；随 c14_run 自测一起做，rc.6 部署后）

### OPS-008　导出 SQL 按猜测的取值域写条件，导出缺一整类数据却没被发现

- **日期**：2026-10-17
- **类别**：转述未核
- **现象**：C-6 工作日历导出 SQL 把休息日判成 `workday = 0`，老系统实际取值是 '1' 上班、'2' 休息；导出的 4,018 行里 HOLIDAY 一条没有（应为 207 条），只有 65 个调休日有 day_kind。导入前转换时才发现，没有导入过这份 CSV 的数据；此前是否用过它由 one-data 复核
- **根因**：写 SQL 时没有先看列的取值域（只看了「新系统要什么」），剧本 3.1 的完整性校验只核总行数与每年天数，没核每类例外日各有多少
- **拦下于**：作者在导入前转换时发现（对照 CSV 分布）
- **漏过于**：剧本 3.1 校验（只核行数）；独立评审（C-6 剧本复审没要求列出取值域）
- **新增检查项**：写取数或导出 SQL 条件前，先用只读取证查该列的取值域与分布，写进 SQL 注释和剧本；剧本校验补「每类各有计数、无意外取值」（C-6 剧本 3.1 已补：`holidays`、`make_up_workdays`、`unexpected_workday_values`）
- **状态**：已落实（`docs/modernization/phase1a/infra/runbooks/sql/c6_legacy_readonly_export.sql` 3.1；`docs/modernization/phase1a/infra/runbooks/C-6-legacy-export.md` 步骤 3）
