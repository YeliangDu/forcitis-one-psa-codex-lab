## 核心思想

- **论断：业务架构蓝图应按场景从共同知识库生成，不同架构域之间以跨域映射建立关联。** 依据：GLD#知识库与蓝图、GLD#跨域映射。含义：对象、信息、能力、价值流和流程视图从已有正本抽取，按 ADR-0041 的单一事实来源方向核对关系，避免独立副本漂移。
- **论断：价值流阶段产生价值项，能力结果对其贡献价值，同一执行流程可以关联多个价值流或阶段。** 依据：GLD#价值流与阶段、GLD#价值贡献与结果、GLD#流程多重映射。含义：VS-02、PRC-28、PRC-33 分别核对签发认可和证据封存对阶段结果的贡献，不强制一个流程只对应一个阶段。
- **论断：价值流允许非线性的增量价值累积，最终仍向干系人的价值主张收敛。** 依据：GLD#非线性价值累积。含义：VS-02 的价值阶段顺序不直接作为强制审批阻断，交付物与证据的阶段贡献须单独核对。
- **论断：信息概念显式表达业务对象、类型和状态，但业务信息不一定都有 IT 数据表示。** 依据：GLD#信息概念与对象。含义：先在信息图核对 OBJ-05、OBJ-29、OBJ-35 的类型、状态和关系，再判断需要保存哪些事实，不能出现一个名词就增一张表。
- **论断：能力分解须保持父能力聚焦的业务对象，同一能力可以由不同组织单位以不同方式实现。** 依据：GLD#能力对象边界、GLD#能力与实现。含义：OBJ-01、OBJ-54 及 PRC-80 的核对区分能力定义和组织实现，组织变动不必重造能力图，也不据映射宣称能力已实现。
- **论断：BIAN 服务域面向软件开发部署的功能分解，业务能力面向战略，行业参考模型仍须适配具体企业。** 依据：GLD#服务域与能力差异、GLD#参考模型起点。含义：PRC-92、PRC-190 不从金融或政府清单直接推导 BC，边界继续按 ADR-0041 的不变量与一致性需求确定。

## 对本系统的启示

- 对照 OBJ-05 协议、OBJ-29 项目和 OBJ-35 交付物：建议用信息图明确类型、状态和关系，再问哪些事实需要系统保存。业务对象图不因出现一个名词就增一张表，符合 ADR-0041 的单一事实来源方向。（GLD#信息概念与对象、GLD#知识库与蓝图）

- 对照 VS-02 获得交付成果、PRC-28 和 PRC-33：建议分别核对交付物签发认可及证据封存对各阶段结果的贡献，不要求一个流程只对应一个阶段，也不把价值阶段顺序直接作为强制审批阻断。（GLD#价值贡献与结果、GLD#流程多重映射、GLD#非线性价值累积）

- 对照 OBJ-01 往来单位、OBJ-54 法人主体及 PRC-80：能力定义与组织实现分离，组织变动不必重造业务能力。此为框架概念映射，不是证明任何现有能力已经实现。（GLD#能力对象边界、GLD#能力与实现）

- 对照 PRC-92 过账业务事实（PRC-190 重投领域事件已退役，属技术支撑，不作落点）：不从BIAN功能域直接推导本系统BC。边界继续遵 ADR-0041 的不变量与一致性需求，白皮书仅提示能力和软件服务粒度不同。（GLD#服务域与能力差异、GLD#服务域与实例语境）

## 我们的取舍

- 建议采纳：保留对象、信息、能力、价值流及流程之间可核对的关系，视图从已有正本抽取。理由：可以进行完整性和影响分析，避免独立模型副本漂移。（GLD#跨域映射、GLD#流程多重映射）

- 建议不采纳：直接移植金融BIAN或政府行业能力清单，并把一个能力直接变为一个BC。理由：行业和建模目的不同；改变现行BC推导方式属于与 ADR-0041 冲突的待提议事项。（GLD#参考模型起点、GLD#服务域与能力差异）
