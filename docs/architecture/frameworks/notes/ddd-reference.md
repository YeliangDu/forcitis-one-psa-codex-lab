## 核心思想

- **论断：统一语言与模型只在明确的限界上下文内保持一致，上下文之间需要显式说明关系和翻译。** 依据：DDDR#限界上下文与统一语言、DDDR#上下文映射。含义：按 FRAMEWORKS §1、DATA_DESIGN_CHECKLIST §14 判断 BC 范围并记录契约方向，不从能力名称或组织部门直接生成边界。
- **论断：实体在属性变化后仍以身份保持连续，值对象以特征和值语义表达且不承担实体身份。** 依据：DDDR#实体身份、DDDR#值对象。含义：在模型中说明同一性判据，遵守类型化 ID 等既有守护，不把有 UUID、外键或状态列当作模型正确的充分证据。
- **论断：聚合根维护边界内的不变量，外部通过根访问，仓储围绕需要直接访问的聚合根建立。** 依据：DDDR#聚合、DDDR#仓储。含义：按 DATA_DESIGN_CHECKLIST §14 的事务和并发约束落实一致性边界，跨边界变化另行协调，不为每张表或每个业务名词自动建立聚合与仓储。
- **论断：不自然归属实体或值对象的领域操作可由领域服务表达，应用、界面及存储责任与领域表达分离。** 依据：DDDR#领域服务、DDDR#分层职责。含义：按 DATA_DESIGN_CHECKLIST §14 将规则及变化含义放入领域行为，应用负责编排，避免界面修改意外改变业务规则。
- **论断：领域事件记录业务关心的发生事项，其发生时刻与录入时刻可能不同。** 依据：DDDR#领域事件。含义：按 ADR-0025 另行定义事件作为分析来源的口径、完整性和重建规则，不因出现领域事件就采用事件溯源或全套 CQRS。
- **论断：防腐层通过翻译保护本地模型，共享内核的小范围共享也须控制变更。** 依据：DDDR#共享内核与防腐层、DDDR#开放协议与发布语言。含义：上下文映射继续只用现行选定的四种关系，来源客户记录不能未经翻译就充当所有上下文的同一模型。

## 对本系统的启示

### 业务对象

实体强调跨属性变化仍是同一事物，模型必须说明怎样判断同一性；值对象表达特征及相应行为，不承担这种身份。聚合再解决一组对象共同变化时如何保持不变量。三者回答不同问题，不能把业务名词、有主键或有关联分别当成自动判定聚合的依据。（DDDR#实体身份、DDDR#值对象、DDDR#聚合） 本系统对照：FRAMEWORKS §1、DATA_DESIGN_CHECKLIST §14。

### 价值流

本书不涉及本项目所用的 BIZBOK 干系人价值流与阶段门建模。领域事件表达业务关心的发生事项，不因出现在某阶段就自动定义一条价值流。（DDDR#领域事件） 本系统对照：FRAMEWORKS §1、DATA_DESIGN_CHECKLIST §14。

### 能力

本书不涉及 BIZBOK 企业能力图的对象命名和层次映射。限界上下文描述模型和语言的适用范围，不能由能力名称或组织部门直接决定。（DDDR#限界上下文与统一语言；与能力的区别为项目应用） 本系统对照：FRAMEWORKS §1、DATA_DESIGN_CHECKLIST §14。

### 流程

领域模型应能表达重要规则和变化含义，而不是只容纳数据。实体负责自身生命周期；不自然属于实体或值对象的领域操作可用领域服务表达。应用编排、界面和存储责任应与领域表达分开，避免一个界面修改意外改变业务规则。（DDDR#分层职责、DDDR#领域事件、DDDR#领域服务） 本系统对照：FRAMEWORKS §1、DATA_DESIGN_CHECKLIST §14。

### 数据建模

聚合围住同步维护的不变量，外部引用根；跨边界变化另行协调。仓储围绕确需直接访问的聚合根提供领域可理解的访问，不因每张表存在就建一个仓储。数据库结构是实现模型的一部分，但不能以现有表关联替代身份和一致性分析。（DDDR#聚合、DDDR#仓储；表结构判断为项目应用） 本系统对照：FRAMEWORKS §1、DATA_DESIGN_CHECKLIST §14。

### 度量与 BI

本书不涉及事实表粒度、可加性和维度建模。领域事件可以提供有业务含义的活动记录，但它与技术事件、审计日志不同；发生时刻和录入时刻也可能不同。事件是否适合作为分析来源，仍需另外定义口径、完整性与重建规则。（DDDR#领域事件） 本系统对照：ADR-0025。

### 主数据

本书不涉及完整的 MDM 匹配合并或主数据治理方法。其相关贡献是显式处理不同模型之间的翻译与共享：同名不保证同义，防腐层保护本地模型，小范围共享也要控制变更。来源中的一个客户记录不能无翻译地充当所有上下文的同一模型。（DDDR#上下文映射、DDDR#共享内核与防腐层、DDDR#开放协议与发布语言） 本系统对照：FRAMEWORKS §1、DATA_DESIGN_CHECKLIST §14。

## 我们的取舍

以下经 one-architecture 2026-10-18 审定（ARC-1017-ARC-21）；现行采用范围以 [FRAMEWORKS](../../frameworks.md) §1 和 DATA_DESIGN_CHECKLIST §14 为准。

- **采纳：用模型与统一语言的一致范围判断 BC，用不变量判断聚合。** 理由：两种边界解决不同问题；一个 BC、模块和 schema 的对应是项目决定，不冒充本书的一般要求。
- **采纳：显式区分实体身份、值对象和聚合根，并通过领域行为维护不变量。** 理由：有 UUID、外键或状态列不足以说明模型正确；实现仍受本项目类型化 ID、事务和并发守护约束。
- **采纳：上下文映射记录翻译、共享和契约方向。** 理由：可检查外部语义是否泄漏；只使用现行选定的四种关系，不扩成全部团队协作模式。
- **不采纳：从每个业务对象或每张表直接生成一个聚合、仓储或 BC。** 理由：对象清单、模型边界和持久化实现需要逐步判定；词表和既有数据结构只能提供输入。
- **不采纳：出现领域事件就要求事件溯源、全套 CQRS 或消息产品。** 理由：事件表达业务含义，不自动决定全部状态怎样存储或查询；分析数据集另按 Kimball 及 ADR-0025 设计。
- **不采纳：把项目的子域命名空间约定称作本书原义。** 理由：FRAMEWORKS 已明确这一裁剪；保留原书概念以便追溯，不能据此重划当前命名空间。

**使用边界：** 本文不核对 Evans 原著 2003 年版章节，也不引用其页码。DDD 模式不是 FORCITIS 的业务政策；ISBN 和独立出版标记尚未核出，语言／模型一致也需通过实际场景与实现验证。
