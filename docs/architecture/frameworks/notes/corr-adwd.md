# 《Agile Data Warehouse Design》要点笔记

本笔记保存与 FORCITIS one 相关的阅读要点，不构成架构决定。正文为自行概括，短引 0 处。信息栏依据 PDF 第 3 页版权页：2011 年初版，2012 年有两次修订；页底另有日期标记，无法据此确认本文件对应哪次修订，故不细分月份。

**阅读边界：本机所列 PDF 是 46 页样章。** 已核读导读、第 1 章（印刷第 3–26 页）及第 2 章首页（印刷第 27 页），末页明确标明样章结束；第 2 章后续及第 3–9 章正文缺失。以下 20 个锚点均来自实际可读正文；事件矩阵只采用第 1 章表 1-3 已说明的用途，不把目录或导读中的后续章节介绍当作详细方法。正文印刷页与 PDF 页在本范围内相差 18 页。

## 核心思想

- **论断：分析模型应围绕可度量的业务过程组织，直接按现有报表反推会限制后续分析。** 依据：CORR#报表驱动局限、CORR#过程增量交付。含义：以 PRC-23 填报并审批工时单、PRC-53 确认收入为测量入口，分别声明事件与粒度，再服务 VS-10 获得期间报告，不能把一个经营看板当成一张事实表。
- **论断：业务库尚未定型时就能提出分析必采字段，等上线后补采会丢失早期历史。** 依据：CORR#前置必采数据、CORR#变更原因采集。含义：检查 OBJ-29 项目、OBJ-56 人员及 OBJ-57 任职是否能提供发生日、归属和变化原因；把缺项交回业务设计，不用分析侧猜补历史。
- **论断：业务人员提供的具体事件样例比抽象关系图更容易暴露重复事件、币种与计量差异。** 依据：CORR#示例数据、CORR#七问框架。含义：PRC-23 的样例应包含同人同日多笔工时、不同项目与认定结果，PRC-60 认领收款并核销应收的样例应包含一笔资金收付分配到多个往来款项，再判断一行代表什么。
- **论断：一个可交付的分析增量必须同时具备星型结构、装载和可查询结果。** 依据：CORR#过程增量交付、CORR#靶向剖析。含义：BI_SCOPE.md §3.2 每次选择一个可实现的过程，先验证来源可支持的维度和度量，再交付可查询结果；只有矩阵勾选或模型图不能算完成。
- **论断：跨过程的一致解释需要业务共同定义维度，不能仅靠各开发者采用同名字段。** 依据：CORR#业务共同定义、CORR#事件矩阵。含义：把 OBJ-54 法人主体、OBJ-29 项目、OBJ-01 往来单位放入共同定义范围，按 VS-04 的事件顺序核对收入确认、开票与回款使用的归属，而不由各报表自行解释。

## 对本系统的启示

- **工时分析从事件开始，不能只留工时单汇总。** terms.yaml 的「工时」是填报的时间投入记录，「工时单」是人员与期间的审核载体；PRC-23 应能提供同一工时单内的各笔记录及审批结果，项目归集落到 OBJ-29。后续再由 PRC-91 认定工时单有效性形成有效工时的口径，不能把已填报自动视为有效。（CORR#业务事件、CORR#粒度）
- **分析要用的归属必须回到业务入口检查。** OBJ-54 法人主体、OBJ-56 人员、OBJ-57 任职及 OBJ-29 项目的关系若只有当前值，就不足以解释旧期间工时。PRC-80 维护法人、组织与岗位、PRC-136 变更任职，应能提供变化依据与生效信息；这是业务库可度量原料的检查方向，尚非已完成的库表审计。（CORR#前置必采数据、CORR#变更原因采集）
- **跨流程分析先统一故事中的对象角色。** VS-04.2 确认收入、VS-04.3 开具发票、VS-04.4 回收款项分别涉及 OBJ-81 收入确认、OBJ-83 增值税发票、OBJ-85 往来款项及 OBJ-86 资金收付。按事件先后写出实际关联与分配示例，再对照 BI_SCOPE.md §3.2 勾维度；不能因名称相近便认为关联一对一。（CORR#七问框架、CORR#示例数据、CORR#事件矩阵）
- **度量定义应有业务共同确认的描述层。** PRC-168 发布口径版本、PRC-90 出具经营月报对应 VS-10；按 BI_SCOPE.md §3.3 写清词条、单位、期间、加总规则与口径版本。样章的简码只是记录手段，不替代本系统的口径登记。（CORR#业务共同定义、CORR#简码）

### 供度量设计

以下为样章已支持的方法及缺口；用于总线矩阵、度量清单和业务库可度量原料检查，不表示已检查数据库。

- **度量入口：** 用可描述的业务事件承载基础测量与上下文，先核对 PRC-23、PRC-53 的事件是否能定位到具体记录，再建立度量来源。（CORR#业务事件、CORR#事实与维度）
- **指标口径：** 对每项测量记录单位、可加维度、历史规则与来源映射，再按 BI_SCOPE.md §3.3 补税口径、期间类型和口径版本，不能只留一个显示名称。（CORR#可加度量、CORR#简码）
- **KPI、派生指标、基础指标：** 本样章未提供三层分级定义或 KPI 筛选细则；可据事件区分原始测量与后续计算，但不能把这一分级归为作者规定；该分级的本书依据未核，本系统暂无对应。（CORR#事实与维度、CORR#可加度量）
- **总线矩阵：** 采用表 1-3 已说明的事件矩阵用途，按 VS-04 的顺序列事件与共用维度；第 4 章的具体建表步骤未核，不据目录补写。（CORR#事件矩阵）
- **粒度：** 用示例明确一行的明细层级，特别检查同人同日多笔工时与 OBJ-86 多次分配，防止维度组合相同便合并事件。（CORR#粒度、CORR#示例数据）
- **事实表类型：** 样章只支持事实表记录过程活动这一基础定位；交易、周期快照、累积快照的详细选择方法未核，不能用本笔记为 BI_SCOPE.md §3.2 的类型选择背书。（CORR#事实与维度、CORR#业务事件）
- **维度一致性：** 共同定义 OBJ-54、OBJ-29、OBJ-01 等跨事件维度并记录复用关系，随后再核来源可行性；业务协作共识不能替代数据验证。（CORR#业务共同定义、CORR#事件矩阵、CORR#靶向剖析）
- **可度量原料：** 逐事件检查身份、发生时点、数值及单位、归属、变更时间与原因，缺失的关键输入在业务系统开发期提出，不能待 BI 上线后还原不存在的历史。（CORR#七问框架、CORR#前置必采数据、CORR#变更原因采集）
- **过程时效：** 先从时间线识别要保存的起止事件和时点，再设计时长指标；PRC-23 可检查填报到审批两个事件的时间输入，不把当前状态当作全程耗时。（CORR#时间线）

## 我们的取舍

- **建议采纳：用事件故事和样例表共同核对业务库输入。** 理由：可在 OBJ-29、OBJ-86 的明细设计前暴露重复事件、归属和分配歧义，与 BI_SCOPE.md §3 的事实分层相容。（CORR#示例数据、CORR#前置必采数据）
- **建议采纳：以事件矩阵规划共用维度，以单个过程交付分析增量。** 理由：既能保持全局关系，又能把范围限制在可验证的来源与查询结果。（CORR#事件矩阵、CORR#过程增量交付）
- **建议不采纳：把当前报表或源库结构直接作为分析模型。** 理由：两种单向驱动都不足以解释业务真正要测量的过程。（CORR#数据驱动分析、CORR#报表驱动局限）
- **建议不采纳：用样章未包含的章节推定事实表类型、KPI 分级或完整 BEAM 操作规则。** 理由：缺少正文证据，须由负责会话补齐资料后另行核读。（CORR#业务事件）
