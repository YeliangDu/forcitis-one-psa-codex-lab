# Silverston《The Data Model Resource Book》第 1 卷要点笔记

## 核心思想

- **论断：主体身份与业务角色分开，同一主体可同时承担客户和供应商等多个角色，主体关系可带目的和有效期。** 依据：SIL1#主体与角色、SIL1#主体关系。含义：用这些模式复核 OBJ-01 的共用身份、角色及跨期归属，不因共用概念就要求跨所有业务边界共用一张可写表。
- **论断：需求与工作投入可多对多关联，工时跟踪和计费账户另有各自的记录与追溯责任。** 依据：SIL1#需求与工作投入、SIL1#工时与计费账户。含义：分别保存需求、工作投入、人员分派、工时与计费的业务联系，不能只留汇总金额，也不将计费结算账户混入银行账户。
- **论断：物理场所与联系地址不是同一事物，联系渠道、用途和地理归属也有不同含义。** 依据：SIL1#联系方式与地理区域、SIL1#场所与联系方式。含义：复核 OBJ-01、OBJ-03、OBJ-46/47 和 OBJ-93 时分别核查联系信息、场所及资产，不让一项地址替代它们的业务语义。
- **论断：技能和资质模式描述人员或组织能够执行工作的条件。** 依据：SIL1#技能与资质。含义：OBJ-44 资源需求及 OBJ-64 人员证书核对证书以外的技能条件，不把个人技能直接当成企业业务能力，也不以技能评分替代业绩评价。
- **论断：企业逻辑模型、集成历史仓库和部门分析模型服务不同目的，向分析模型转换须重定时间、粒度和派生数据。** 依据：SIL1#企业模型与分析模型。含义：按 DATA_DESIGN_CHECKLIST §14.1 核对分析转换，不将交易模型直接改名成仓库，仍以实际决策需求选择分析结构。

## 对本系统的启示

- **业务对象（对照：OBJ-01）：** 人或组织的身份、它在企业中的角色、它与其他主体的关系承担不同语义。同一主体可以同时是客户与供应商；将角色信息压进主体类型会使关系和历史难以解释。协议、报价、工作投入和账单也各有生命周期，不能因为参与同一交易而视为一个对象。（SIL1#主体与角色、SIL1#主体关系、SIL1#需求与工作投入）

- **价值流（对照：原笔记未列本系统价值流编号）：** 本书不涉及 BIZBOK 的价值流判据。需求到工作投入、工作投入到计费的关联可供追踪业务结果，但这些数据联系不是价值流阶段定义。（SIL1#需求与工作投入、SIL1#工时与计费账户）

- **能力（对照：OBJ-44、OBJ-64）：** 本书不涉及企业业务能力图。技能及资质模式描述可执行工作的人员或组织条件，不能直接等同于企业能力。（SIL1#技能与资质）

- **流程（对照：原笔记未列本系统流程编号）：** 需求与实现需求的工作投入之间可以多对多关联；人员分派、工时和计费又是不同的记录。先保存这些业务联系，才能解释投入为何发生、由谁完成、最终向谁计费，不能只留下汇总金额。（SIL1#需求与工作投入、SIL1#工时与计费账户）

- **数据建模（对照：OBJ-01、OBJ-03、OBJ-46/47、OBJ-93）：** 通用模式用于发现结构性问题，仍须按企业需要裁剪。地址、联系方式和物理场所不能互相替代；一座建筑与其收件地址不是同一事物。关联实体可容纳有效期、目的等业务信息，不能把它们全部缩成无属性的连线。（SIL1#主体关系、SIL1#联系方式与地理区域、SIL1#场所与联系方式）

- **度量与 BI（对照：DATA_DESIGN_CHECKLIST §14.1）：** 企业逻辑模型、集成历史仓库和部门分析模型各有目的。分析转换包括时间、粒度和派生数据的重新设计，不能把交易模型直接改名成仓库；书中的分析示例依赖企业的实际决策需求。（SIL1#企业模型与分析模型）

- **主数据（对照：OBJ-01、DATA_DESIGN_CHECKLIST §14.1）：** 主体共用身份有助于减少重复，但角色、联系渠道、分类和有效期仍须明确。共用概念不要求跨所有业务边界共用一张可写表；后者是本项目仍须单独审定的一致性与归属问题。（SIL1#主体与角色、SIL1#主体关系、SIL1#联系方式与地理区域、SIL1#场所与联系方式；表归属为项目应用）

## 我们的取舍

**已审定（one-architecture 2026-10-18，页码已抽查）。** 现行边界见 [FRAMEWORKS](../../frameworks.md)、DATA_DESIGN_CHECKLIST §14.1。

- **采纳：用主体、角色、关系及其有效期复核对象模型。** 理由：与现有往来单位共用身份、角色分开的口径相容，能检查一人多角色和跨期归属。
- **采纳：用工作投入到需求、工时到计费的链路查漏。** 理由：AEC 服务既要解释履约，也要解释实际投入；两条链路不可用一项总额代替。
- **不采纳：整套通用表及角色超模型直接入库。** 理由：先按本系统用语、一致性边界及实际需求裁剪；不改变自有 UUIDv7、BC 写入权及主数据版本化规则。
- **不采纳：以通用 Invoice 代替税务平台发票、收入确认和往来款项。** 理由：账单、法律票据与经济事实不能仅按英文近义合并。

**使用边界：** 短引：0 处。通用模式不能证明本企业确有某种业务，也不决定对象应为一级、次级、关系或属性；正文仅覆盖所列主题。
