# Kimball《The Data Warehouse Toolkit》第二版要点笔记

本笔记用于保留早期版本的概念依据和版本差异，不新增一套架构标准。正文为自行概括，页码已从本地原文读取，已抽查。

## 核心思想

- **论断：事实行的粒度必须先于维度和事实的选择确定，同一事实表不能混入其他粒度的金额或数量。** 依据：KIM2#事实与维度、KIM2#粒度。含义：FRAMEWORKS §5 的分析设计先写明一行代表的测量活动，再选择该粒度上成立的维度、事实与汇总方向，不按部门复制不一致的数据。
- **论断：跨主题整合依赖维度定义、键、属性与取值一致，不要求所有主题共用唯一一张物理维度表。** 依据：KIM2#总线矩阵与一致性维度。含义：FRAMEWORKS §5 的总线矩阵用于识别可共享维度与核对跨主题口径，不用矩阵行替代价值承诺或价值流阶段门，也不按部门各建无法对账的指标。
- **论断：Type 2 以新的维度版本行保留历史，同一实体可以对应多个代理键。** 依据：KIM2#维度代理键、KIM2#缓慢变化维。含义：按实体与版本分别计数，事实引用当时版本键；组织、客户等保存哪些历史仍按 D6、D17，不用第二版的可选日期属性降低现行时态约束，也不以顺序整数键覆盖 UUIDv7。
- **论断：累积快照会随流程推进更新，事件事实也可以没有数值度量。** 依据：KIM2#累积快照、KIM2#无数值事实。含义：FRAMEWORKS §5 的建模分别说明交易明细、期间汇总与累积状态的观察用途，不把所有分析事实概括为只追加或必有金额。
- **论断：暂存区可以使用文件或规范化结构，展示层则围绕业务可理解性与查询用途建模。** 依据：KIM2#暂存区与展示层。含义：FRAMEWORKS §5 分别检查暂存与展示用途，不将分析表结构反推为业务聚合；第二版只作为第三版概念的历史补证。

## 对本系统的启示

- **业务对象（对照：原笔记未列本系统对象编号）：** 维度在本书中是进入分析数据的描述实体，不能据此给所有业务对象下定义。分析中区分对象的自然标识与维度行的代理键，尤其同一对象有多个历史轮廓时，按版本行计数不等于按实体计数。（KIM2#事实与维度、KIM2#维度代理键、KIM2#缓慢变化维）

- **价值流（对照：原笔记未列本系统价值流编号）：** 本书不涉及本项目所用的 BIZBOK 价值流判据。总线矩阵用于识别测量活动之间可共享的维度，不用于表达干系人的价值承诺和阶段门。（KIM2#总线矩阵与一致性维度）

- **能力（对照：原笔记未列本系统能力编号）：** 本书不涉及企业业务能力图的定义、命名与分解。（相关概念：KIM2#总线矩阵与一致性维度）

- **流程（对照：FRAMEWORKS §5（原笔记未列流程编号））：** 分析设计应围绕业务产生测量的活动，而不是为每个部门复制一份数据。部门可能共同消费同一测量活动的数据；分部门建设而缺乏一致口径，会形成难以比较的分析孤岛。（KIM2#粒度、KIM2#总线矩阵与一致性维度）

- **数据建模（对照：FRAMEWORKS §5）：** 粒度是对事实行含义的明确承诺，随后选择的维度与事实必须能在该粒度上成立。交易明细、期间汇总和流程累积状态是不同观察方式；累积快照会更新，事件记录也可以没有数值度量。暂存区可以使用文件或规范化结构，展示层的可理解性与查询用途才是建模重点。（KIM2#粒度、KIM2#累积快照、KIM2#无数值事实、KIM2#暂存区与展示层）

- **度量与 BI（对照：FRAMEWORKS §5）：** 同一事实表中不能混入另一粒度的金额或数量，可加性也不能只由数字类型判断。企业整合依靠共用维度的定义、键、属性和取值一致；物理上相同或受控复制均可，一致性并不要求所有主题共用唯一一张物理表。（KIM2#事实与维度、KIM2#总线矩阵与一致性维度）

- **主数据（对照：D6、D17）：** 本书相关的直接贡献是维度整合与历史追踪，不是完整的主数据治理体系。Type 2 用新版本行保留历史轮廓，事实引用当时的版本键；需要业务判断哪些属性值得保留历史。第二版在该例中把维度表的生效、失效日视为辅助属性，同时说明暂存装载历史时需要有效期信息，不能把这段话推广为时态范围永远不必保存。（KIM2#维度代理键、KIM2#缓慢变化维）

## 我们的取舍

以下经 one-architecture 2026-10-18 审定（ARC-1017-ARC-21）；现行维度建模参照仍锁定第三版，见 [FRAMEWORKS](../../frameworks.md) §5。

- **采纳：作为第三版概念的历史补证。** 理由：粒度、总线矩阵、一致性维度和 Type 2 的基础思路可用于追溯已有资料，不需要另立规则来源。
- **采纳：按业务决定保留什么历史、按实体与版本分别计数。** 理由：组织、客户等属性变化会改变分析口径，按版本行去重可能高估实体数量；具体保存规则仍按项目 D6、D17。
- **不采纳：用第二版例子的可选日期属性降低现行时态约束。** 理由：第三版第 54 页明确提出 Type 2 的生效、失效和当前行属性，项目还另有区间与历史取值约束；两个版本的文字不能混写成同一要求。
- **不采纳：顺序整数代理键直接覆盖 UUIDv7，或把分析表结构反推为聚合。** 理由：键类型和事务模型已有项目决定，第二版只支持分析身份分离的原理。
- **不采纳：按部门各建一套无法对账的指标。** 理由：同一业务测量需要一致解释；构建批次与投产节奏继续按 ADR-0054，而非套用书中数据集市的交付节奏。

**使用边界：** 本笔记与[第三版笔记](kimball-dwt3.md)分别保存书名、年份、页码和差异。第二版不自动补足第三版未读章节，也不证明现有数据仓库已符合这些原则。
