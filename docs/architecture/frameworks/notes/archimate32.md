## 核心思想

- **论断：业务对象是由行为访问的被动结构，同一业务对象可以有多种表示，自动处理的数据另以数据对象表达。** 依据：AM32#业务对象与表现形式、AM32#数据对象与实现关系。含义：按 FRAMEWORKS §9、ADR-0041 仅作语义对照，分开文件形式、业务含义与结构化数据，不引入 ArchiMate 图或额外模型正本。
- **论断：价值流表达干系人视角的价值形成，流程表达产生结果的行为顺序。** 依据：AM32#意义与价值、AM32#能力与价值流、AM32#流程与功能。含义：价值流与办理流程分别核对，价值感知不以活动成本替代；BPMN 的执行属性、审批人和异常处置仍须专门设计与验证，采用边界守 FRAMEWORKS §9、ADR-0041。
- **论断：能力由人员、流程、信息和技术等要素实现，能力描述与实现安排属于不同抽象层次。** 依据：AM32#能力与价值流。含义：按 FRAMEWORKS §9、ADR-0041 保存概念差异，不因系统提供一个功能就认定整个业务能力已具备。
- **论断：由明细关系抽象出的粗略联系不能反向证明被省略的实现细节。** 依据：AM32#关系抽象。含义：架构图不能替代实体身份、事务聚合、接口或部署的实现证据，也不据业务对象与数据对象的联系生成一概念一表；仍按 FRAMEWORKS §9、ADR-0041 分工。
- **论断：模型中的目标与结果元素不等于已经发生的业务效果。** 依据：AM32#目标与结果。含义：度量与 BI 仍需实际效果证据和指标算法，不能以画出结果元素代替验证；本笔记只保留 FRAMEWORKS §9、ADR-0041 允许的阅读对照。

## 对本系统的启示

- **业务对象：** 业务对象是业务层的被动结构概念，通常表达类型；它被行为访问，而不自行执行流程。信息的可感知载体和供自动处理的数据另有表达位置，同一业务对象可以有多种表示。因此，文件形式、业务含义和结构化数据不宜混成一个模型元素。（AM32#业务对象与表现形式、AM32#数据对象与实现关系；对照：FRAMEWORKS §9、ADR-0041）
- **价值流：** 价值流在策略层表达干系人视角的价值形成，具体个案的时间顺序任务则由流程表达。看起来都是一串活动的图，不代表两者可以相互替换；价值感知也不等于活动成本。（AM32#意义与价值、AM32#能力与价值流；对照：FRAMEWORKS §9、ADR-0041）
- **能力：** 能力表达组织、人或系统具备的本领，通过人员、流程、信息和技术等要素实现。能力描述与实现安排应分开，不能因某系统提供一个功能，就认定它构成整个业务能力。（AM32#能力与价值流；对照：FRAMEWORKS §9、ADR-0041）
- **流程：** 流程侧重产生结果的行为顺序，功能侧重按技能或资源等归组，二者可能多对多关联。抽象层面的流程描述不提供本项目 BPMN 的执行属性、审批人规则和异常处置，需要专门的流程设计及验证。（AM32#流程与功能；BPMN 落点为项目应用；对照：FRAMEWORKS §9、ADR-0041）
- **数据建模：** 业务对象、数据对象与实现工件之间的关系帮助区分抽象和实现，但不会强制每个业务概念一张表，也不规定 DDD 的实体身份和事务聚合。关系图还能从明细抽象出较粗的联系；较粗联系不能反向证明遗漏的实现细节已经存在。（AM32#业务对象与表现形式、AM32#数据对象与实现关系、AM32#关系抽象；对照：FRAMEWORKS §9、ADR-0041）
- **度量与 BI：** 本书不涉及本项目的维度建模、指标可加性或经营报表算法。其目标、结果、意义和价值等表达有助于澄清讨论对象，但画出结果元素并不证明业务效果已经发生。（AM32#意义与价值、AM32#目标与结果；证据要求为项目应用；对照：FRAMEWORKS §9、ADR-0041）
- **主数据：** 本书不涉及主数据匹配合并、权威来源和历史版本的实现方法。客户记录可以作为数据对象的例子，不能仅凭图上的实现关系认定它是主数据正本。（AM32#数据对象与实现关系；对照：FRAMEWORKS §9、ADR-0041）

## 我们的取舍

以下经 one-architecture 2026-10-18 审定（ARC-1017-ARC-21）；[FRAMEWORKS](../../frameworks.md) §9 的不采用决定保持有效。

- **采纳：仅作为跨框架阅读时的语义对照。** 理由：分清对象、信息载体、自动处理的数据和实现工件，能避免把概念与表混用；此处采纳指阅读提醒，不是采纳该语言。
- **采纳：检查架构图所表达的证据边界。** 理由：抽象关系可省略细节，但省略的细节需要实现证据补足，不能从一条关系推断事务、接口或部署已完成。
- **不采纳：引入 ArchiMate 图、元素编号或一套模型正本。** 理由：现行决定已不用，项目已有 BIZBOK、DDD、BPMN 与数据登记的分工。
- **不采纳：用 Business Object 元素判定业务对象真假，或据 Data Object 实现关系生成表。** 理由：它提供架构表达，不能覆盖本项目对象判据、DDD 不变量和数据责任决定。
- **不采纳：把语言允许的价值流表达扩展成新的项目规则。** 理由：本项目价值流结构已有 BIZBOK 与明确裁剪依据；规范对照不能悄然扩大采用范围。

**使用边界：** 本笔记不声称本项目符合 ArchiMate，也未运行模型验证器。保留该文本是为了识别术语和抽象差别；对象、能力、流程与数据设计的取舍仍回到现行框架和业务证据。
