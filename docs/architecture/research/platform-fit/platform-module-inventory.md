# 平台层模块盘点（ARC-1020-COO-10，结构评审）

- 日期：2026-10-20；只读评审，没有改仓库。
- 代码基线：`origin/main` @ `8cddaee3`（`backend/src/main/java/com/forcitis/one/`），使用方按 `import com.forcitis.one.<模块>` 统计（同模块内部的引用不计）。
- 规划依据：ADR-0051 决定 3 表与决定 7（下文用 B-xx 编号），聚合稿 `ENTERPRISE_AGGREGATES_DRAFT.md` §4.1 依赖骨架（B-31 `organization.administration` 由聚合稿收尾回补新增），`docs/legacy/runtime-usage/a8-templates.tsv`，2026-10-20 已批的 6 份 ADR 草案（intent `2026-10-20-221808`），研究稿 C/B 与 R 复核（以 R 为准）。
- 判定口径：**真平台**＝已有或预计有 ≥2 个 BC 使用，且模块里没有业务语义；**单一 BC 能力**＝只有 1 个使用方，应归那个 BC；**技术模块**＝没有 api、谁也不 import，靠端口或框架接入（ADR-0004 的「两个出口」对它不适用）。

## 1. 逐模块

### 1.1 kernel（含 kernel.event）

1. **职责**：跨模块共享的值对象与端口，如 `Money`、`LegalEntityId`、`DocumentReference`、`DomainEvents`、`EventEnvelope`、`IdempotentResponses`、`CallerPermissions`。**变化原因**：多个模块共用的类型或端口的签名变了。它是 OPEN 模块，改动面是全局的。
2. **使用方**：全部模块。`kernel.event` 被 timesheet 17 处、workforce 49 处、attendance 6 处、identity 55 处等 import。
3. **判定**：共享内核，ADR-0051 决定 2 第 3 条把它列为例外，不算平台模块。
4. **注意**：kernel 里有 `WecomUserId`、`ExternalSubjectEmployees`、`ExternalSourceBrokenException`，按 ADR-0039 决定 1、ADR-0033 应移出或改为中性名，这是已知的清理项。要不要把内容哈希收进 kernel，见 §3 D-2。

### 1.2 platform.approval（审批）

1. **职责**：通用审批与待办（Flowable 只在 `infrastructure.flowable`），对外提供审批钩子 `ApprovalHook`、审批流程 `ApprovalProcesses`、审批结果事件和待办列表。**变化原因**：审批编排规则（时限、升级、转办、退回）、引擎版本、待办口径。业务判定不进引擎（ADR-0007）。
2. **使用方**：
   - 现有 1 个：`cost.timesheet`（24 处 api、2 处 events）。
   - 预计 18 个：B-02、03、04、05、06、07、08、09、10、11、12、15、18、20、24、27、29（结项钩子）、31（TRN-03 先行上线四类事务）。
   - **不用**它的：B-13、B-14。原因是 `platform.approval → organization.workforce / attendance` 已经建边，它们一用就成环（ADR-0051 决定 4 第 5 条）。B-26、B-28 的三个检查审批按设计留在聚合内单级批准（聚合稿回补二 S-25 ②）。
   - A8 佐证：审批类模板占 A8 年用量的大头，例如用印申请 1,073、开票申请 939、差旅报销 1,900（`last_180d`）。
3. **判定**：真平台。
4. **结构备注**：它依赖业务 BC `organization.workforce`（解析审批人与汇报线）和 `organization.attendance`（工作日历算时限），所以严格说并非「与业务无关」。它的实际定位是「位于组织 BC 之上的平台服务」（ADR-0051 决定 7 第 1 条，L4）。这个位置决定了它不能承接 workforce 自己的审批与提醒，见 P5。

### 1.3 platform.audit（审计）

1. **职责**：只追加的审计记录、分区与归档。**变化原因**：留痕口径、保留期、等保要求。
2. **使用方**：
   - 现有：workforce 19 处、attendance 1 处；平台内 identity 112 处、approval 18 处。
   - 预计（聚合稿已登记）：B-01、B-13、B-14、B-19、B-27、B-29。已批草案再加文件服务、签章服务、一次性链接，以及 AI 调用侧的 3 个 BC。
   - 聚合稿没有逐一登记审计边。实际上凡有敏感操作的 BC 都会用（ADR-0043）。
3. **判定**：真平台。
4. **备注**：审计归档经 `platform.integration.api.ArchiveVault` 写入 WORM 归档桶（锁定 2557 天）。它的保留规则和文件保存期是两套口径，见 P3。

### 1.4 platform.identity（身份与权限）

1. **职责**：账号、会话、角色与授权、数据范围（`AccessScope`），以及唯一一处 Spring Security 配置和公开端点白名单。**变化原因**：安全不变量、登录方式（联合身份，ADR-0039 决定 3）、权限模型（ADR-0026）。
2. **使用方**：
   - 现有：timesheet 4 处；平台内 approval 15 处、numbering 3 处、eventing 1 处。
   - 预计：聚合稿只登记了 B-06、B-10，文件服务也会依赖它（已批草案）。
   - 实际上需要 `CurrentUser` 与数据范围过滤的 BC 都会依赖它。workforce、attendance 位于它的上游，只能经 `kernel.CallerPermissions` 端口用。
3. **判定**：真平台。

### 1.5 platform.integration（外部集成，防腐层）

1. **职责**：外部系统的协议、用语与对照，例如企业微信卡片、对象存储与归档、来源对照、外部身份；它只出现在本模块（ADR-0039）。**变化原因**：外部系统接入、更换或下线，例如 U8C、企业微信、分贝通、税务、银行，以及将来的预览、签章服务商、AI 厂商、恶意文件检测。
2. **使用方**：
   - 现有：workforce 26 处（组织同步，ADR-0055 决定 6 撤同步后会删）；平台内 identity 14 处、approval 8 处、numbering 11 处、audit 2 处。
   - 预计 11 个 BC：B-01、05、08、09、12、15、20、22、23、27，以及 B-13（撤同步后可能为 0）。
   - 平台内另有：文件服务（对象存储、检测、预览端口）、签章服务（服务商适配）、migration、AI 出站端口。
3. **判定**：真平台。它没有出边（L0），这个性质必须保住：凡是需要解析收件人、判断业务语义的能力都不能放进来（见 P5 方案 d）。
4. **遗留**：`LegacyInbox` / `LegacyTodo`，以及 `Source*` 系列中的组织同步类型（`SourceOrgSnapshot` 等），按 ADR-0055 决定 6 投产前删除；迁入要用的来源对照另行保留。

### 1.6 platform.numbering（单据编号）

1. **职责**：按规则版本发放单据编号，规则由财务确认；目前还挂着原编号查询。**变化原因**：编号规则与格式（ADR-0010）、财务确认流程。
2. **使用方**：
   - 现有 1 个：cost.timesheet（8 处）。
   - 预计：`kernel.DocumentType` 已登记 QUOTE（B-03）、TIMESHEET（B-06）、JOURNAL_VOUCHER（B-20）。NAMING_STANDARD「业务编号」一行要求所有业务编号都经它发放。
   - 按 A8 带单号的高频单据推断（△）：合同 B-05、开票申请 B-08、收款 B-09、付款 B-10、报销 B-12、用印 B-31、分包采购 B-11，合计 ≥8 个 BC。
3. **判定**：真平台，保持独立。并入 kernel 不行，因为它有表、有规则版本和财务确认；并入 approval 也不行，两者变化原因不同。
4. **重复项**：api 里还有 `FindDocumentByLegacyNumber`、`RegisterLegacyNumbers` 等 5 个原编号类型。ADR-0039 决定 4 第 2 条、ADR-0055 决定 6 规定 `legacy_numbers` 归集成层，这部分还没搬（§3 D-4）。

### 1.7 platform.scheduling（作业调度）

1. **职责（现状）**：ShedLock 配置、作业指标、`scheduler_locks` 表，以及 G-C3 规划的维护模式表；各模块自写 `@Scheduled` + `@SchedulerLock`，**不依赖本模块**（package-info，G46）。**变化原因**：调度框架、锁、维护模式。
2. **使用方**：
   - import 为 0。以注解方式使用的有 9 个模块：approval、audit、eventing、idempotency、identity、integration、numbering、timesheet、workforce。
   - 聚合稿登记了 B-05、B-07 → scheduling。依据是 closeout/CONVENTIONS.md:110：「time 触发由所属 BC 向 `platform.scheduling` 登记定时」。
3. **判定**：技术模块。**口径矛盾**：package-info 说各模块自带注解、不依赖本模块，CONVENTIONS 说登记制、要建边。这一点 C 稿 §0-3 已指出，至今未裁定，须交 one-architecture 统一。统一结果直接决定提醒的落点（P5）。

### 1.8 platform.idempotency（幂等应答）

1. **职责**：按「登录用户 × Idempotency-Key」缓存 POST 应答 24 小时，并带清理作业。web 的 `IdempotencyFilter` 经 kernel 端口 `IdempotentResponses` 调它。**变化原因**：HTTP 幂等协议与保存时长。
2. **使用方**：只有 platform.web（经 kernel 端口），没有 BC import 它。适用的端点由 `idempotent-endpoints.txt` 登记，目前 20 个，分属 workforce、identity、numbering、approval。
3. **判定**：技术模块，可以并入 web（条件式，见 P6）。
4. **口径不符**：已批的签章服务稿写「幂等键：申请 ID + 签前件 + 台账条目（`platform.idempotency`）」，外部访问稿写「只依赖 …、`platform.idempotency`」。但本模块**没有 api 包**，它只做 HTTP 应答缓存，不是业务幂等服务。两稿写的其实是业务去重，按惯例应由本模块的唯一约束或命令幂等实现。须在 X1 补确认时由 one-architecture 订正措辞，否则实施时会凭空长出一个 api（§3 D-5）。

### 1.9 platform.eventing（事件发布）

1. **职责**：把事件草稿补全成信封并发布，提供工作单元切面，对接 Spring Modulith 发布登记表。**变化原因**：事件基础设施。
2. **使用方**：import 为 0，实现的是 kernel.event 端口。所有发布事件的模块都在隐式使用：现有 9 个模块经 `DomainEvents` 发布。
3. **判定**：技术模块，保持。不并入 kernel 的理由见 P4。

### 1.10 platform.web（Web 与错误链）

1. **职责**：唯一的错误处理（异常 → ErrorCode → RFC 9457）、关联 ID、OpenAPI 契约调整、幂等过滤器。**变化原因**：HTTP 契约规范。
2. **使用方**：identity import 1 处，全局隐式使用。
3. **判定**：技术模块，保持。

### 1.11 platform.migration（迁入编排，ADR-0036 规划）

1. **职责**：离线迁入命令的编排，调用集成层暂存与来源对照，以及各目标 BC 的迁入入口；**任何模块都不依赖它**，它也没有自己的表。**变化原因**：迁入批次与对账口径，生命周期到一次投产（ADR-0054）为止。
2. **使用方**：方向是反的，它依赖目标 BC，而不是被 BC 依赖。按 ADR-0054「全业务流程与历史明细」，目标 BC 几乎是全部有历史数据的 BC。文件服务基础稿为它留了一个专用入口。
3. **判定**：**不是平台服务**。它只有出边、依赖业务 BC，形态和 `delivery.closeout` 一样，属于 `kind: process`（编排）。建议在 contexts.yaml 中改为 process 类，或者单设 `kind: tooling`；平台命名空间可以保留。理由：platform 模块的通则是「被业务依赖、不依赖业务」，它正好相反；把它记成 platform，会让「平台 → 业务」这类边看起来是正常的。
4. **条件**：如果投产后还要做增量迁入（例如并购法人），它就长期存在；否则投产后可以下线。

### 1.12 文件服务（已批，暂名 `platform.file`；含保存期、在线预览）

1. **职责**：文件写入、哈希、恶意文件检测、关联与分级、按单据授权、版本与派生、封存登记；子能力包括保存期限表与到期处置、在线预览凭据。**变化原因**：存储与安全（OSS、检测、WORM）、保存期的法规口径、预览服务商。
2. **使用方（预计）**：
   - 已批稿列出：B-31（W0）、B-28、B-03、B-22、B-20，以及签章服务、一次性链接、出件。
   - 推断（△）：合同 B-05（合同附件与归档）、报销 B-12（A8 报销单附件）、开票与证据 B-08、分包采购 B-11（供方交付成果）、检查 B-26、人事 B-13（劳动合同附件）、知识 B-30。合计 ≥12 个 BC。
   - approval **不依赖**它，审批参与人经单据所属模块读附件。
3. **判定**：真平台。
4. **风险**：api 已用 **11/12**（基础 7 项、保存期 3 项、预览 1 项，CS-1.12 上限 12）。以后任何新增都会顶破上限，自然的拆分缝在「保存期」（P3）。

### 1.13 签章服务（已批）

1. **职责**：印章台账（法人 × 印章类型，版本化）、电子用印的发起与结果回收、签章记录（含图纸签章登记）、证书元数据。**变化原因**：《电子印章管理办法》与 CA 规则、服务商、行政印章制度。
2. **使用方（预计）**：
   - 已批稿列出：B-31（W0 用印申请）、B-28（图纸签章登记）、B-05（签署证据）。
   - 推断（△）：B-08、B-11（我方先用印、再交一次性链接冻结的待阅文件）。
3. **判定**：真平台。小，但跨 3 个以上 BC，而且不能放进 B-31（ADR 草案决定 2 第 1 条：B-31 不被业务 BC 依赖）。

### 1.14 一次性链接（外部访问，已批）

1. **职责**：给外部持有人签发一次性链接，只做回签与上传两类动作，带公开端点、防转发和外部回传事件。**变化原因**：对外安全策略、公开入口规则、可开放的单据类型。
2. **使用方（预计）**：B-08（客户价值确认单）、B-28（多类签认与资料）、B-11（委外交付确认）。A8 年量约 2,845 件，是上限。
3. **判定**：真平台。

### 1.15 AI 底座（已批：不建模块，闸在调用侧）

1. **职责**：出口闸、限额、审计、提示词与评测约束，经集成层出站端口调用模型。**变化原因**：法规（个人信息保护法、出境）、厂商与模型、数据分级登记。
2. **使用方**：用户在 ADR 批准**之后**（intent `2026-10-20-223058`）给出首批 3 个场景：工时单（B-06）、报销单（B-12）、管理者查经营数据（reporting）。推断（△）：知识检索（B-30）。
3. **判定**：**需重议**。已批草案第 2 条第 2、3 点写的是「首个场景在其所属 BC 设唯一的 AI 调用服务；第二个场景时再整体抽成平台模块」。现在首批就同时有 3 个 BC。照原文做，等于先在一个 BC 建闸、马上再抽出来；要么 3 个 BC 各建一套出口闸，出口闸属安全控制，口径分叉就是外发风险。
   - 条件式结论：如果首批 3 个场景同批建造，「抽平台模块的条件」在落地时已经满足，应由 one-architecture 在 X1 补确认时判断是否直接建平台模块（暂称 `platform.ai`，依赖 audit 与 integration，不被二者依赖）。如果 3 个场景分批、首批只有 1 个，原文成立。
   - 这件事涉及已批 ADR 的执行条件，按规则「补确认结论不同则回问用户」处理。

### 1.16 待办与提醒（候选）

1. **职责**：业务 BC 登记到期事项，平台负责触发、去重、按收件人投递，并汇总成「我的待办」。**变化原因**：提醒参数、工作日历、升级规则、通知渠道。
2. **使用方（预计）**：
   - 平台内：approval（审批时限）、identity（ADR-0044 复核到期）。
   - 业务 BC：B-13（证书与试用期）、B-14 / B-27（考勤催办）、B-06（工时催填）、B-08（ADR-0047 期满待办）、B-09（保证金、质保金）、B-19 / B-20（关账提醒）、B-23（申报提醒）、B-10（付款）、B-12（发票查验）、B-01（资质到期）。
   - 合计 ≥9 个 BC、2 个平台模块（C 稿 §5.1，R 补了 ADR-0047 一项）。
3. **判定**：使用方足够多，具备成为真平台的条件；落点有结构约束，见 P5。

### 1.17 参考数据（候选）

1. **职责**：外部权威源发布的码表，例如税率、银行与联行号、汇率（取决于外币决定），带版本。**变化原因**：法规与外部发布方。
2. **使用方（预计）**：
   - 税率：B-23、B-08（销项）、B-12（进项占用，△）。
   - 银行：B-01、B-22、B-10（△）。
   - 币种：`Money.of` 已经做了 ISO 4217 校验，没有新需求（R 复核）。
   - 行政区划、标准规范库：不需要（C 稿）。
3. **判定**：不放 platform。它有业务语义（税率口径属财务政策），也不能并入 catalog（P8）。

### 1.18 出件（单据与报告生成，候选）

1. **职责**：模板加数据出 PDF / Word，并留出件记录。**变化原因**：版式、模板、法定格式（OFD）。
2. **使用方（预计）**：
   - B-03（报价单）、B-28（成果确认函）、B-08（开票申请单）、B-04 / B-29（结项报告）、B-20 / B-21（凭证与账簿 PDF/OFD，第二步）。
   - B-26 检测报告只在本公司自行出具检测报告时才需要（R §4 第 2 题未答）。
3. **判定**：条件式，见 P7。

### 1.19 中文全文检索（候选）

1. **使用方**：B-30 正文检索；B-01、B-04、B-13 的名称选择器。
2. **判定**：不成模块。它是各 BC 查询侧的能力，加上 RDS 参数组与测试镜像这两项基础设施前置（C 稿 §7a.3）。可以和 AI 向量检索的 pgvector 前置一起做（R §3 第 6 条）。

### 1.20 现场采集（候选）

1. **使用方**：B-28（证据，W2 用普通上传）、B-26（W5 前再定是否用 JS-SDK）；外勤打卡的 B-27 为推断（△）。
2. **判定**：不成模块。媒体落盘一律走文件服务「写入内容」，企业微信 JS-SDK 的签名与媒体下载放集成层（R §3 第 2 条已统一）。

## 2. 合并候选逐对评估

下表的依赖层号取自 ADR-0051 决定 7 快照（L0 最上游）；「成环」按 `module-dependencies.txt` 现有边加已批草案的边推算。

### P1 签章服务 vs 文件服务

| 维度 | 合并 | 分开（现状，已批） |
|---|---|---|
| 内聚 | 两者都处理「文件 ID + 内容哈希」，但签章还有台账、证书、授权、服务商交易，与存储无关 | 各自内聚 |
| 变化频率与原因 | 印章法规、CA、行政制度，和存储、检测、保存期是不同的变化原因 | 互不牵连 |
| 依赖与成环 | 签章 → `organization.workforce`（订阅离职事件）。合并后文件服务也要依赖 workforce，**workforce 就不能再用文件服务**，而 workforce 有劳动合同等附件需求（AGG-67），**会成环** | 签章 → 文件服务单向，无环 |
| api 预算 | 文件服务已用 11/12，合并必然超限 | 各自有余量 |
| 守护与权限面 | 签章授权按法人范围（ADR-0026），合并会把高敏感授权带进全员都用的模块 | 安全评审面各自独立 |
| ADR 改动 | 两份已批 ADR 都要重写 | 无 |

**结论**：维持分开。只有在 workforce 永远不需要附件、签章也不再订阅人事事件时，才可以重议。

### P2 一次性链接 vs identity

| 维度 | 合并 | 分开（已批） |
|---|---|---|
| 内聚 | 两者都是访问主体与公开端点；identity 已持有公开端点白名单 `PublicEndpointRegistry` 与唯一的 Security 配置 | 持有人没有账号、会话或权限，和 identity 的模型（账号、角色、范围）不相交（已批稿决定 1 第 1 条） |
| 依赖与成环 | 链接 → 文件服务，文件服务 → identity。合并后 **identity → 文件服务 → identity，成环** | 无环 |
| 安全面 | identity 是安全不变量集中地（SecurityInvariantsTest），并入公开写入端点会扩大它的评审面 | 公开入口统一规则另由「最先需要的实施卡」建 |
| ADR 改动 | 推翻已批稿「identity 不改」 | 无 |

**结论**：维持分开。将来如果改选「建外部账号」（R §4 第 3 题选项 c），外部账号应进 identity，一次性链接仍独立。附带缺口：公开入口统一规则没有明确的所有者模块（§3 G-3）。

### P3 保存期 vs 文件服务 vs 审计保留

三处都有「保留」：
- 文件保存期：按类别给年限，到期由两人处置，已批，在文件服务内。
- 审计与流程归档：WORM 锁定 2557 天，经 `integration.ArchiveVault`；保留期由「在线时长 + 锁定天数 = 总保留期」校验。
- 签章记录（库表行）：自行处置，经文件服务的「查到期日」取年限。

| 选项 | 收益 | 代价 |
|---|---|---|
| (a) 维持：保存期在文件服务内（已批） | 不新增模块；年限表与文件状态同事务 | 文件服务 api 11/12；行数据（签章记录等）要经文件服务 api 取年限，语义上不顺 |
| (b) 拆出「保存期」平台模块，文件与表行共用类别表 | 文件和表行同一套保存类别；`data-access-registry` 的 `retention.policy` 有了权威来源；文件服务 api 降到 8 | 新增模块与边：文件 → 保存期，签章 → 保存期。审计的 WORM 规则（锁定期内不可处置）和类别处置规则不同，不能硬合 |
| (c) 三者全合（含审计保留） | 只有一个「保留」入口 | 审计保留是等保与内控口径，归档是对象级 WORM，与按类别两人处置是两种机制；改动大，收益小 |

**结论（条件式）**：
- 维持 (a)。
- 出现以下任一情况时转 (b)：第二个「库表行」使用方要按类别取年限；文件服务 api 需要第 12 项以上。
- (c) 不建议。
- 附带：`ArchiveVault` 的保留期校验是本系统规则，现在放在集成层 api，转 (b) 时应一并评估移到保存期模块（§3 D-3）。

### P4 eventing vs kernel.event

| 维度 | 合并进 kernel | 分开（现状） |
|---|---|---|
| 内聚 | 端口和实现放一起 | 端口（纯类型）在共享内核，实现（Spring Modulith、AOP、Jackson 模块）在技术模块，这是标准的端口与适配器分法 |
| 依赖 | eventing → identity（取当前操作人，1 处）。合并后 kernel 依赖 identity，而全部模块依赖 kernel，**成环** | 无环 |
| 框架入侵 | kernel 带进框架依赖，会破坏「领域层不依赖框架」（CS 规则） | — |

**结论**：维持分开，无条件。

### P5 待办与提醒 vs approval 待办 vs scheduling（以及 integration）

现状有三块零件：
- approval：审批待办、时限与升级、内部通知端口；词表里的 `todo`、`inbox` 归它（terms.yaml）。
- integration：企业微信卡片队列与出站投递（`QueueWecomCard`、`DeliverWecomCards`）。
- scheduling：各模块自带的定时作业。

| 选项 | 收益 | 代价与结构障碍 |
|---|---|---|
| (a) 并入 approval（扩成「审批与待办」） | 「我的待办」只有一个入口；复用时限、升级与通知 | approval → workforce / attendance 已有边，**B-13、B-14 不能登记提醒**，证书与试用期这类 W0 提醒源就被排除；要绕开只能让 approval 订阅 workforce 事件，平台就懂了「试用期届满」这类业务语义。approval 的变化原因被稀释。词表 `todo` 的使用范围要改，须交 one-glossary |
| (b) 并入 scheduling（登记制定时） | scheduling 在 L0、无出边，**任何 BC（含 workforce）都能登记**；与 CONVENTIONS:110 一致 | 只解决「到点触发」。收件人解析要依赖 workforce，一放进 scheduling 就失去 L0 地位，workforce 再登记即成环。所以 (b) 只能承担定时，不能承担待办视图与投递 |
| (c) 新建通知或提醒平台模块（位于 workforce 之上，依赖 integration、workforce、attendance） | 参数、去重、收件人、非生产白名单、投递告警只写一次；REIMAGINED_ARCHITECTURE:293「第二个使用者时抽出 `platform.notification`」有先例 | workforce 和 attendance 自己的提醒，要么按 (d) 自带，要么由新模块订阅它们的事件（方向允许，但同样把业务语义放进了平台）；多一个模块 |
| (d) 各 BC 自带（现状写法） | 不新增模块，符合 CS-1.8 | ≥10 个提醒源各写一套参数、去重与收件人解析，离职人员仍被提醒这类不一致是可以预见的 |
| ✗ 并入 integration | 卡片队列已经在那里 | integration 必须保持零出边（防腐层），不能解析收件人、不能有业务语义（ADR-0039）。**排除** |

**结论（条件式）**：
- 第一步：由 one-architecture 先统一 scheduling 是登记制还是注解制（§1.7）。这是前提。
- 如果统一为登记制：定时登记放 scheduling (b)，待办汇总与投递放新模块 (c)，两段分开，workforce 只依赖 L0 的 scheduling。
- 如果维持注解制：选 (c) 或 (d)。提醒源 ≥3 个且有聚合到期日、需要「我的待办」时选 (c)，否则选 (d)，并配一个共用小工具。
- 不建议 (a)，因为成环约束会把人事提醒排除在外。

### P6 idempotency vs web

| 维度 | 合并 | 分开 |
|---|---|---|
| 使用方 | 唯一使用方就是 web 的过滤器，经 kernel 端口 | — |
| 依赖 | 两者都没有出边，**合并无环** | — |
| 存储 | web 现在没有 schema，合并后要持有 `platform_idempotency` 的表与清理作业，ddl 基线、数据访问注册表、schema 名都要改 | 「有表的」和「无表的」技术模块分开，清楚 |
| 收益 | 少一个模块；「HTTP 应答缓存」不再被误读成业务幂等服务（见 §1.8 两份已批稿的误用） | — |
| ADR 改动 | 改 contexts.yaml、ADR-0051 平台行（已批改为「按登记」，只改登记）、`ddl-naming-baseline`、`DataArchitectureTest` 登记 | 无 |

**结论（条件式）**：可做可不做，收益不大。如果做，要和订正两份已批稿中的「`platform.idempotency`」措辞同批进行；如果不做，至少要订正措辞。scheduling 并入 web 同样无环，但 scheduling 的定位还没定（P5），现在不并。四个技术模块整体合成一个运行时模块的方案**不可行**：identity → web 与 eventing → identity 并存，合并后成环。

### P7 出件 vs 文件服务

| 选项 | 收益 | 代价 |
|---|---|---|
| (a) 并入文件服务 | 生成后直接落盘 | 文件服务 api 超限；模板与版式的变化原因（业务、法定格式）与存储安全不同；文件服务就要依赖各业务 BC 的数据读模型，或者被推送大块数据，内聚变差 |
| (b) 新建出件平台模块（B 稿 §4.4） | 模板版本与出件记录集中，可以证明「发出版本 = 批准版本」 | 多一个模块；要不要做模板管理后台，目前没有证据 |
| (c) 不建模块，只做共用渲染库，各 BC 自己出件，再经文件服务「写入内容」（派生方式「格式转换」） | 最小、符合 CS-1.8；出件记录留在单据所属 BC | 模板版本口径分散；如果业务要自己改 Word 模板，最后还是要 (b) |

**结论（条件式）**：不并入文件服务。先补「单据版式清单」（R §2 第⑤项）：
- 业务要自己维护模板，或单据类别 ≥5 且多 BC → (b)。
- 开发维护版式，或单据类别 ≤3 → (c)。
- 决定点在 W2 开工前。

### P8 参考数据 vs masterdata.catalog

| 维度 | 并入 catalog | 另设 |
|---|---|---|
| 语义 | catalog 是公司自定的服务产品、费率、系数和协议价目，要走审批（AGG-05），变化原因是商务；参考数据是外部权威发布，变化原因是法规 | — |
| 依赖与成环 | catalog → counterparty（ADR-0051 决定 7 第 2.1 条）。银行码表的使用方是 counterparty，counterparty 去读 catalog 的银行码表就**成环** | — |

可选落点：
- (a) 按使用方分归：税率进 B-23，其他 BC 经 api 读；银行码表进 B-01。
- (b) masterdata 命名空间下新设参考数据 BC，位于 counterparty 上游。
- (c) platform 新模块：语义上属业务口径，不推荐，但可列为备选。

**结论（条件式）**：不并入 catalog（会成环）。只有税率和银行两项时选 (a)；如果选了允许外币（汇率表），或项数 ≥3 且跨 ≥3 个 BC，选 (b)。归属最终交 one-architecture（C 稿 §6.4、R §2 第⑦项）。

### P9 numbering 是否仍独立

- 现有使用方 1 个，按 DocumentType 已登记 3 个，推断 ≥8 个。规则版本与财务确认属本模块自己的不变量。
- 并入 kernel 不行：有状态、有表。并入 approval 也不行：变化原因不同，而且 approval 已经很大（api 33 个类型）。
- **结论**：独立。只需按 ADR-0039 决定 4 第 2 条、ADR-0055 决定 6 把原编号相关的 5 个 api 类型迁到集成层（§3 D-4）。

### P10 migration 是否属于平台

见 §1.11。**结论**：保留模块，类别改为流程或编排（与 `delivery.closeout` 同类），不计入「平台服务」，守护维持 G-MG5、G-MG10「只出不入」。这件事只涉及登记（contexts.yaml 的 kind），不必改 ADR-0036 的正文；是否需要改 ADR 由 one-architecture 定。

### P11 一次性链接 vs 签章服务（补充一对）

已批稿决定 10 已经分工：同一单据、同一动作只走一个通道；电子印章平台的签署链接归签章服务与集成层，持有人回签与上传归一次性链接。两者的变化原因（对外安全策略 vs 印章法规）和使用方不完全重合，合并之后签章服务也要背上公开写入端点。**结论**：维持分开。

## 3. 缺口与重复

**重复（两处做同一件事，或同一概念有两份）**

- **D-1 通知投递**：approval 有内部通知端口，integration 有卡片队列，将来提醒还要再做一份。收口方式见 P5。
- **D-2 内容哈希**：`platform.approval.api.ContentHash`（审批内容指纹，RULE-302）和文件服务的 `content_hash`（SHA-256，文件服务基础稿称其为「本系统唯一的内容哈希」）是两份；签章、证据、银行流水也都要引用「文件 ID + 哈希」。建议建文件服务时，在 kernel 定一个哈希值对象，供多个模块共用。审批的 `ContentHash` 是否就是同一概念，交 one-glossary（同名异义的风险）。
- **D-3 保留期**：审计 WORM 和文件类别年限是两套，`ArchiveVault` 的保留期规则放在集成层 api。这两套各自成立；P3 (b) 触发时应一并收口。
- **D-4 原编号**：numbering 的 api 里有 5 个 legacy 类型，与集成层的来源对照、`legacy_numbers` 落点（ADR-0039 决定 4 第 2 条）重复，搬迁未执行。
- **D-5 「幂等」一词两用**：平台的 HTTP 应答缓存，和已批稿里的业务去重。见 §1.8。

**缺口**

- **G-1 scheduling 定位未统一**：package-info 写注解制，CONVENTIONS 写登记制。它阻塞提醒的落点（P5）和聚合稿 B-05、B-07 两条边的真假。
- **G-2 AI 闸的落点**：已批 ADR 的「第二个场景时抽模块」条件在落地时已经满足（§1.15）。
- **G-3 公开入口统一规则没有所有者模块**：外部访问稿决定 6 规定由「最先需要的实施卡」建，规则本身（主机名、网关白名单、限流、统一失败、响应头）却没有归属模块。可选归属：identity（已持有公开端点白名单与 Security 配置，G33）、web（响应头与错误链），或由一次性链接模块持有、签章回调引用。建议 one-architecture 在 X1 补确认时一并定。
- **G-4 ADR-0051 平台行写死了 10 个模块**：已批的文件服务基础稿把它改成「按已采纳 ADR 与 contexts.yaml 登记」。占号入库后，contexts.yaml 要新增文件服务、签章服务、一次性链接，将来可能还有 AI、提醒，平台模块会到 13–15 个。migration 改类别后少计 1 个。
- **G-5 平台依赖业务 BC 的先例**：approval、identity、numbering 都依赖 `organization.workforce`。这是 ADR-0051 骨架认可的，但「平台不依赖业务」这条通则在本仓库实际上是「平台不依赖组织 BC 以外的业务 BC」。建议在 CODING_STANDARD 或 ADR-0051 中写明，免得新模块（签章服务已依赖 workforce）各自解释。
- **G-6 Excel 导出共用工具**：ADR-0019 定了「各模块自实现 + 共用工具」，但共用工具没有落点。如果出件选 P7 (c)，可以和渲染库同包。

## 4. 模块 × 使用 BC 矩阵

**矩阵要点**

1. 现有代码里，平台模块真正被**业务 BC** import 的只有 cost.timesheet、workforce、attendance 三处，每个平台模块现有使用方只有 0–2 个。判断「是不是平台」必须靠规划数据，靠代码现状判断不出来。
2. 规划使用方最多的是 approval（18 个）、integration（11 个）、文件服务（推断 13 个）、提醒（推断 13 个）。签章服务和一次性链接是小平台：3 个使用方，且集中在收入与交付链上，即 B-28、B-08、B-05、B-11。
3. B-28 质量与认可在聚合稿里不依赖任何平台模块，但已批草案让它一下子依赖文件服务、签章服务、一次性链接和预览四项，是新平台能力最集中的使用方，建议 W2 实施卡把它作为接缝验收点。
4. 没有一个现有平台模块属于「只有 1 个使用方、应归那个 BC」。最接近这种情况的是 AI（如果只有一个场景）和出件（如果只有 1–2 类单据）；前者按用户的 3 个场景已不成立，后者看版式清单。
