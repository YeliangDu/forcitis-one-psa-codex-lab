路径简写：`D` = `docs`；`B` = `backend`。

## 0. 先说三个关键事实（影响后面所有判断）

1. **仓库里目前没有文件服务，也没有任何出件库。** `backend/pom.xml` 只有 `aliyun-sdk-oss 3.18.1`（`B/src/main/java/com/forcitis/one/platform/integration/infrastructure/archive/OssObjectStore.java` 等，仅用于流程与审计归档桶）；没有 POI、PDFBox、OpenPDF 等。平台模块现有：approval、audit、eventing、idempotency、identity、integration、numbering、scheduling、web（`B/src/main/java/com/forcitis/one/platform/`）。ADR-0019 表格「文件 → 阿里云 OSS，平台文件服务」（`D/adr/ADR-0019.md:31` 附近）只是决定，未建。
2. **「老系统文件服务 180 天约 9 万次」不等于业务文件量。** 我按 `D/runtime/prod_usage.tsv` 重算：`/infra/file/*/get/` 合计 89,712 次，其中 png 86,295 次（单个 png 路径就 9,062、36,643、40,578 次，明显是界面静态图），jpg 3,019、pdf 89、docx 31、xlsx 14；上传只有 `/admin-api/infra/file/upload` 128 次 + `/admin-api/system/oss/upload` 4 次 + `/app-api/infra/file/upload` 58 次，合计约 190 次；路径里带 `deliverable/` 的下载 91 次。结论：真实业务文件流量很小（约每天 1 次上传），不是性能问题，而是**保全、权限、版本、证据效力**问题。（统计口径是我对该 TSV 的重算，列含义按「第 4 列为调用次数」理解，建议文件服务会话复核。）
3. **「是否持有检验检测机构资质认定（CMA）」在仓库里查不到。** 检测报告相关合规要求的强度取决于此（见 §1.2），这是需要用户或法务回答的最大单点。仓库只出现「检测办法第 26 条（参照）」（`D/architecture/proposals/ENTERPRISE_AGGREGATES_DRAFT.md:159` INV-46），说明目前只是参照。

## 3.3 可选做法（并列，不排序）

> 共同前提：文件字节已定放阿里云 OSS（ADR-0019）；PG 存元数据；版本链/封存是领域模型（AGG-27 文件版本清单），任何方案都要在 `delivery.acceptance` 里建。差别在「通用文件服务」做多厚、预览怎么做。

### 方案 A：自建（OSS + PG 元数据 + 版本链 + 自带预览）
- **要求**：新增平台层文件模块（对象键、sha256、大小、媒体类型、上传人、访问级别、所属单据引用、病毒扫描状态）；服务端签发短期预签名 URL；上传走后端或直传 + 回调校验；版本不靠 OSS 版本控制，而靠业务层「版本清单」（才能表达「被取代」「封存」）；预览仅做图片/PDF（浏览器原生或前端 PDF 查看），其余下载。
- **代价**：开发量中（文件模块约 3-5 个聚合/表 + 守护测试 + 前端上传组件；我估算，非实测）；费用：OSS 标准存储与流量，按已知业务量（§0 第 2 点）可忽略；运维：需自管 PDF 预览组件的安全（SEC-016 前车之鉴）；许可证：无新增；安全面：预签名 URL、对象访问策略、上传类型/大小限制、病毒扫描需另配。
- **收益**：与领域模型零阻抗；封存、版本、校验和、权限随单据完全可控；不引入新的数据出境点。
- **把握**：高（技术成熟；仓库已有 OSS 写入与 SHA-256 校验的先例：`INFRA_RUNBOOK.md:297`）。

### 方案 B：A + 阿里云 IMM（智能媒体管理）文档预览
- **要求**：在 A 的基础上，对 Office/PDF 用 IMM WebOffice 做在线预览，OSS 与 IMM 在同地域，签发 WebOffice token。
- **已核实的能力与限制**（一手：`https://help.aliyun.com/zh/imm/developer-reference/api-imm-2020-09-30-generatewebofficetoken`）：输入限 Word/PPT/Excel/PDF（doc、docx、xls、xlsx、ppt、pptx、pdf 等），**不含 dwg**；单文件最大 200 MB、最多 5000 页；Permission 有 Readonly、Copy、Export、Print、History 等布尔项，PDF 必须只读；**支持前端水印**（`Watermark` 参数，仅前端渲染、不写入源文件）；访问令牌 30 分钟、刷新令牌 1 天；History 需 OSS 多版本。FAQ `https://help.aliyun.com/en/imm/support/faq-about-document-processing/` 明确：转换输入不含 CAD/DWG，转换上限 200 MB 不可调。
- **计费**（一手：`https://help.aliyun.com/zh/imm/product-overview/billable-items`）：在线预览 10 元/千次、缓存预览 7 元/千次、在线编辑 20 元/千次、文档转换 80 元/千次；页面未列免费额度；注明 2025-07-28 起部分免费能力开始收费并调整存量价格；2023-12-01 后创建的项目按 API 调用次数计，一个 token 不能跨用户共享。
- **代价**：开发量小（令牌签发 + 前端嵌入）；费用：按本系统文件使用面（§0）是每月几元到几十元量级（335 人若每人每天预览 20 次也约 1,500 元/月，远高于实际，仅作上界）；运维：多一个云服务依赖与计费项，价格会变；安全面：文件在阿里云内部处理（同一云账号、国内地域），不新增跨云出境；令牌泄露即可读，需绑定用户与短时效。
- **收益**：Office/PDF 预览开箱即用，含水印与禁止复制/打印；省去自管预览组件。
- **把握**：中高（能力与价格已核实；对 CAD/BIM 无效；与 OSS 版本控制、Bucket WORM 的组合限制见 §3.5 未核实项）。

### 方案 C：接第三方文档/图纸管理产品（PDM、企业网盘、协同设计平台）
- **要求**：把交付物版本与文件放第三方产品，本系统只存引用与签发事实；需对接账号、权限（企业微信）、回调。
- **代价**：开发量中到大（双向同步、引用失效处理、权限映射）；费用：产品订阅/部署授权，量级**未查到可引报价，未核实**；运维：多一个系统、多一套账号体系，与 ADR-0055「自成体系」相冲，需单独评估；许可证与数据位置按产品而定；安全面：交付物（可能含客户敏感图纸）存放在第三方，要求一份数据处理与存放地承诺。
- **收益**：自带图纸预览（含 DWG/RVT 等）、批注、文件夹级权限；对设计院式团队成熟。
- **把握**：低到中（本次未找到可核实的具体产品与价格；是否值得需先确认公司实际要不要在线看 DWG/BIM）。

### 方案 D：只做最小附件服务（上传/下载/校验和/权限，不做预览，版本由业务聚合承担）
- **要求**：同 A 的存储与元数据，但不做预览、不做预览水印；PDF/图片用浏览器原生打开，其他下载到本地。
- **代价**：开发量最小；费用最低；运维最轻；安全面最小（不引入预览组件）。
- **收益**：最贴合已知使用面（每日约 1 次上传）；预览可以日后叠加（B 随时可接）。
- **把握**：高。

### CAD / BIM 大文件与在线预览的现实做法（本次调研能核实的有限）
- 阿里云 IMM 文档预览**不支持 DWG**（见方案 B 一手来源）。OSS 对象存储本身对大文件无障碍（分片上传），瓶颈在「预览」。
- 开源方向：LibreDWG 是 GPL-3.0，`mlightcad/libredwg-web` 同为 GPL-3.0（检索摘要 `https://awesome.ecosyste.ms/projects/github.com%2Fmlightcad%2Flibredwg-web`、`https://gitee.com/venthent/libredwg`）——放进闭源服务要走法务；商用 DWG 控件（如 DWGViewX）有开发者/服务器授权，标价摘要 1,190 美元起（`https://www.autodwg.com/dwgviewx/buy.aspx`，仅摘要）。kkFileView（Apache-2.0，Office 为主）是否真支持 DWG：只在一个 Gitee 镜像描述里看到，**未在官方 README 核实**（GitHub 抓取失败）。
- 云端 BIM 轻量化服务：广联达 BIMFACE 据第三方介绍支持 RVT、DWG、IFC 等 50+ 格式，但**计费与数据保存规则未查到一手来源**，未核实。
- 现实常见做法（行业通行，未逐项取证）：设计成果以 PDF/DWF 出图版作为「交付物」登记与预览，原始 DWG/RVT 作为附件下载保存，不在业务系统里在线渲染。本系统若遵循，则方案 A/B/D 都足够。
- **关键业务问题未知**：公司的交付物是否本身就是 DWG 图纸？仓库里只见「施工图签」成本类别（`D/BUSINESS_RULES.md:2735`）和 deliverable 路径下的图片/PDF（`prod_usage.tsv`），没有证据显示用户要求在线看 DWG。

## 3.4 落点

- **平台层**：新建 `platform.file`（暂名，命名须先查 `terms.yaml` 并登记术语，CLAUDE.md 规则 2）承载：对象元数据、上传/下载授权、校验和、访问级别、病毒扫描状态、保留类别。理由：附件需求横跨 B-03（售前）、B-28（交付）、B-08（开票证据）、B-20/22（凭证、银行流水）、AGG-113（用印），且 ADR-0019 已写明「平台文件服务」；不应并入 `platform.integration`（该模块现有 OSS 代码只服务归档，职责是外部连接）。
- **与交付物聚合的边界**：`platform.file` 只管「字节与元数据」，不懂「版本、被取代、签发、封存、认可」；这些是 AGG-27 在 `delivery.acceptance` 的不变量（INV-46、INV-47、INV-48）。聚合通过 api 包引用文件 ID + 校验和，文件模块不反向依赖业务。证据（AGG-38）同理。「已封存」由聚合发事件，文件模块据此把对象改为保留类别（WORM 对象级）——此处依赖 OSS 能力，见 §3.5。
- **建造批**：按 ADR-0054 的 W0–W5（`ADR-0054.md:54-59`），最早的使用方是 W2（售前商机委托书、投标、交付物）；CC-I03 也要求「首个上传附件的阶段」入口先有保留期、病毒扫描、权限随单据。故**文件服务最迟在 W2 开工前建成**，放 W0 平台批最顺；预览组件可晚到交付物页面开发时再定（W2 中后段）。

## 3.5 适配结论（现在需要 / 以后需要 / 不需要）

- **最小文件服务（上传、下载、校验和、权限随单据、版本与封存的数据挂点）：现在需要**。理由：已采纳的聚合与 ADR-0054 把附件、历史版本保全写成硬要求；W2 无法绕过。
- **在线预览（Office/PDF）：以后需要，条件式**：若用户希望在系统内直接看报告/合同而不先下载，可用方案 B；若可接受下载或浏览器原生打开 PDF，方案 D 足够。本研究不预选。
- **CAD/BIM 在线预览：现在不需要（条件式）**：只有用户确认「交付物审核必须在系统内看 DWG/RVT」时才升级为需要；届时要单独做一次适配研究（格式、授权、数据出境）。
- **第三方文档/图纸管理产品（方案 C）：现在不需要**：与 ADR-0055「自成体系」方向相冲，且尚无证据说明 A/B/D 不能满足。
- **电子档案管理系统级功能（四性检测、长期保存格式转换、档案移交）：以后需要，条件式**：取决于 Q34（保存期）与法务对《档案法》第三十六条的解释、是否有客户或监管要求；先在文件元数据里预留保留类别与校验和字段，不先建档案系统。
- **报告类文件的封存与不可篡改**：现在要设计（INV-46），实现手段二选一待定：Bucket 级 WORM（当前归档桶用的方式）、或对象级保留策略（见下）。

## 3.6 未核实 / 把握不大（本项）

1. OSS 对象级 WORM（Object Worm）强依赖版本控制，开启后不能关闭，且与 Bucket 级 WORM 互斥，目前只支持合规模式（一手：`https://help.aliyun.com/zh/oss/user-guide/object-level-retention-policy-object-worm` 的检索摘要；我未读正文）。**会不会与已有归档桶设计冲突、业务文件应单独建桶**——须 one-ops 复核，未核实。
2. OSS 版本控制：本身免费，当前与历史版本都计存储费；与 Bucket 级 WORM 同开时历史版本在保护期内不能删（检索摘要：`https://help.aliyun.com/zh/oss/user-guide/overview-78/`、`https://help.aliyun.com/zh/oss/user-guide/oss-retention-policies`）；未读正文。
3. 病毒/恶意文件检测：OSS 恶意文件检测 10 元/万次、单文件最大 500 MB、归档类型 Bucket 不支持；云安全中心另有多引擎检测，实时增量检测仅国内地域（检索摘要，`https://help.aliyun.com/zh/oss/user-guide/check-for-malicious-files`）；未读正文，且是否满足 CC-I03「病毒扫描」要求未评估。
4. 保存期限（交付物、证据、报告）：无一手条文可引；Q34 未定，P-050 在法务。
5. 个人信息保护法保存期限与单独同意：仓库自述未读。
6. IMM 对 PDF 的「打印/导出」限制与计费；IMM 项目 2023-12-01 前后计费口径差异对新账号的影响；价格 2025-07-28 调整的具体幅度：未核实。
7. DWG/RVT 在线预览所有候选（kkFileView 的 DWG 支持、BIMFACE 计费与数据保存、ODA 授权）：均未核实。
8. 估算的开发量与费用上界是我的判断，非实测。

## 4.3 可选做法（并列，不排序）

> 出件对象分三类，需求强度差别大：A 类内部/客户沟通单据（报价单、成果确认函、开票申请单、结项报告）；B 类受监管报告（若适用的检测报告）；C 类财务版式文件（凭证、账簿、报表 PDF/OFD，G1 之后）。

### 方案 E：Java 服务端模板引擎

分两条技术路线：**E1 Word 模板填充**（用户维护 .docx 模板，系统填值，必要时再转 PDF）；**E2 HTML 模板 + 转 PDF**（HTML/CSS 直接版式，系统内维护模板）。

候选开源库（版本与更新日期取自 Maven Central `maven-metadata.xml`，许可证取自各版本 POM；Java 25 兼容性本次**未验证**）：

|---|---|---|---|---|
| Apache POI（poi-ooxml） | 读写 docx/xlsx（底层） | 5.5.1（2025-11-30） | Apache-2.0（常识，POM 未逐项读） | 活跃；Excel 导入导出共用小工具（ADR-0019）将用它 |
| poi-tl | 基于 POI 的 docx **模板填充**（文本、表格、图片、循环、条件） | 1.12.3-beta1（2024-03-13） | Apache-2.0（POM、GitHub 均核实） | 2024-03 后无新版，已 2.5 年；依赖 POI 5.2.2+ |

- **代价**：开发量：E1 中（模板管理 + 填充 + 转 PDF 链路）；E2 中（HTML 模板 + 字体调校）；两者都需要「出件记录」聚合（谁、何时、哪个版本的模板、哪个数据快照）。费用：许可证 0；服务器资源很小（几十到几百份/月量级，我的假设）。运维：LibreOffice 路线要维护服务器组件与字体、转换进程挂死处理；HTML 路线要维护 CJK 字体与版式回归测试。许可证：LGPL 类库（openhtmltopdf、OpenPDF、JasperReports）作为未修改的依赖使用通常可行，但打成 fat jar/受控发布物时的合规动作须法务确认（我不下结论）；AGPL 的 iText 排除。安全面：模板注入（用户可编辑的 docx/HTML 模板里放表达式）是主要风险，须模板只读受控、变量白名单；转换进程要沙箱化；HTML 渲染要禁外链加载（SSRF）。
- **收益**：数据不出本系统；模板与领域读模型同一版本发布；可做版本快照；契合模块化单体与「自成体系」。
- **把握**：E1 中（Word 模板用户友好，但 docx→PDF 保真依赖 LibreOffice，中文复杂表格版式可能有偏差，需用真实报价单样张验证）；E2 中高（可控、可测试，但模板由开发维护，业务方改版要走发布）。

### 方案 F：云端文档生成/转换服务
- **要求**：把模板（docx）与数据交给云服务，取回 PDF/Word。
- **能核实的**：阿里云 IMM 有 `DocumentConvert`（文档转换，输出 JPG/PNG/PDF/TXT/VECTOR，80 元/千次，同步接口须 5 秒内完成，超时走异步；最大 200 MB）——**这是转换，不是模板填充**（一手：`https://help.aliyun.com/zh/imm/product-overview/billable-items`、`https://help.aliyun.com/zh/imm/user-guide/procedure`）。因此云端路线需要「本系统先填出 docx，再交 IMM 转 PDF」，填充仍在本系统（E1 的前半段）。
- **未核实**：国内是否有成熟的「模板填充 + 出 PDF」SaaS/API（WPS 开放平台等）、其价格、私有化、数据存放；本次搜索没有拿到可引来源。国外 SaaS（PDFMonkey、Foxit 等）数据出境，对含合同金额与客户信息的单据，我不建议未经评审使用。
- **代价**：开发量小到中；费用按调用（量小则小）；运维轻；安全面：单据内容（含金额、客户、人名）送到云端处理；同云账号国内地域内的 IMM 风险较低，第三方 SaaS 须单独做数据保护评审（ADR-0043）；许可证：不涉及。
- **收益**：省去 LibreOffice 的运维。
- **把握**：IMM 转换低到中（对复杂 Word 版式的中文还原度、印章叠加未验证）；第三方 SaaS 低（无可核实来源）。

### 方案 G：前端生成（浏览器内生成 PDF，或用打印样式）
- **要求**：React/Taro H5 里用 HTML 打印样式（`window.print`）或 pdfmake/jsPDF 类库生成 PDF。
- **代价**：开发量小；费用 0；安全面：服务端不留存生成结果，**没有「发出去的就是批准的」的服务端证据**，除非再上传回传；H5 内嵌企业微信，打印与文件下载在微信 WebView 内行为不一致；中文字体需前端内嵌，包体变大；A 类单据可用，B、C 类（监管、盖章、归档）不合适。
- **许可证**：pdfmake、jsPDF 一般为 MIT（常识，**未逐项核实**）。
- **收益**：最快出「预览/草稿」，适合内部打印。
- **把握**：中（做草稿可行；做正式出件把握低，因其与「封存」「可追溯」冲突）。

### 方案 H（对照项）：不做通用出件，只做 Excel 导出 + 一两个固定版式单据
- **要求**：沿用 ADR-0019「Excel 导入导出各模块各自实现、共用小工具」，报价单、开票申请单用固定版式的 HTML→PDF（E2）单独实现，其余用 Excel；不建模板管理。
- **代价**：开发量最小；业务方改版要发布；无 Word 可编辑稿。
- **收益**：贴近当前证据（没有版式清单）；与 CODING_STANDARD CS-1.8「只实现当前阶段」一致。
- **把握**：高。

## 4.4 落点

- **平台层**：新建 `platform.document`（暂名，命名须先查词表）承载「出件」：模板登记与版本、渲染、出件记录（模板版本、数据快照摘要、结果文件 ID）；渲染结果存 `platform.file`。**出件模块不拥有业务数据**，各 BC 通过 api 提供「出件数据读模型」，避免平台层反向依赖业务（依赖方向与 ADR-0003 一致）。
- **与 Excel 共用小工具的关系**：ADR-0019 把 Excel 定为各模块自实现 + 共用工具；如果出件走 E1，POI 会同时被 Excel 工具与 Word 填充使用，建议同一个工具包，不放进业务模块。
- **与业务单据边界**：报价单文档视图、开票申请单的「正式输出件」由 B-03/B-08 触发出件；成果确认函、结项报告由 B-28/B-04 触发；检测报告若有（见 §4.2）单独处理。盖章不属于出件模块，属于 AGG-113 用印申请（实体章）或后续电子签章能力（CC-X05，阶段 6a/G2）。
- **建造批**：A 类单据最早随 W2（报价单、成果确认函）、W3（开票申请单）需要；C 类（法定账 PDF/OFD）随 W1 建通道、W5 联调（`ADR-0054.md:82`）——出件**能力本身**可以在 W2 前建一个最小版（方案 H 或 E2），模板管理可以推迟。

## 4.5 适配结论

- **A 类单据的正式出件（报价单、成果确认函、开票申请单、结项报告）：现在需要最小版**，理由：证据（DS_GAPS:14、CC-I08、SSOT 成果确认函）说明这些单据必定要发给外部；不做则发出版本与系统批准版本脱节。最小版选哪种见条件：
  - 若业务方**必须能自己改 Word 模板**：走 E1（+ LibreOffice 转 PDF 或 F）；
  - 若可接受开发维护版式、业务改版走发布：走 E2 或 H（成本最低、可测试）；
  - 若只要内部打印草稿：前端生成（G）可作辅助，不能作正式出件。
- **模板管理后台（让业务用户上传/改模板）：以后需要**，直到出现「版式清单 + 改版频率」证据再建。
- **B 类受监管检测报告：条件式**。若公司以 CMA 资质出具检测报告，则「现在需要」且要独立设计（授权签字人、专用章、编号连续、6 年保存、系统可追溯）；若只登记外部检测报告，则「不需要出件，只需要文件服务」。**须用户先回答是否持有 CMA 并自行出报告**。
- **C 类财务版式文件（PDF/OFD、电子会计档案导出）：以后需要**（清单第 27、28 条标为第二步前需要，`GL_COMPLIANCE_CHECKLIST.md:73-74`），OFD 与国密/电子签章需单独研究，本次没有可核实一手来源。
- **电子签章（对客户出件加盖电子印章）：以后需要，条件式**：取决于客户是否接受电子签章及合同约定；CC-X05 已挂在 6a/G2；《电子签名法》第十三、十四条给出法律效力条件（摘要），实现要选 CA/电子签章服务商，本次未调研。

## 4.6 未核实 / 把握不大（本项）

1. **没有单据版式清单**：哪些单据、几个模板、是否 Word 可编辑、是否盖章、是否要 OFD、改版频率——全部未知，决定 E1/E2/F/G/H 取舍。
2. 公司是否持有 CMA、是否自行出具检测报告：未知（仓库只有「参照」）。
3. 公司所在地的检测报告保存与电子化地方规定（只核实了广东；上海只有摘要）。
4. 国家层面电子印章、OFD（版式文件国标）条款与编号：未查到一手来源，未写编号。
5. openhtmltopdf 1.1.x 的发布来源与 CJK 字体兼容、LibreOffice 转 docx 的中文表格保真度、各库对 Java 25 的兼容：均未实测。

# 综合：给调度与架构会话的三点提示

1. **文件服务与出件是两个独立决定**：文件服务是必需且证据充分（§3），出件需要先补「版式清单」与 CMA 状态再定版（§4）。
2. 已有 `platform.integration` 里的 OSS 归档桶是 Bucket 级 WORM（2557 天）；业务文件（尤其要允许「出新版本」）应单独建桶，不要复用（OSS 的 Bucket WORM 与对象级 WORM 互斥、对象级强依赖版本控制，见 §3.6 第 1 条，须 one-ops 复核）。
3. CC-I03 与 CC-I08 在 CROSS_CUTTING_MATRIX 里都标「阶段」，本研究的落点建议可直接回填这两行的「决定/实现现状」列，由 one-architecture 或相关会话决定是否采纳。
