## 背景

触发：用户问「平台模块是不是要冻结？进入平台的条件要不要约定？」（intent `2026-10-20-225316`），同意先做适配复核，再起草 ADR。任务号 ARC-1020-COO-11。本稿属用户指派，撤回须经用户。复核稿为 `platform-review/平台分档适配复核.md`（下称「复核」），盘点稿为 `docs/architecture/research/platform-fit/platform-module-inventory.md`（下称「盘点」）。

为什么现在定：

- 平台模块会从 10 个增至 13–15 个：6 份已批草案（intent `2026-10-20-221808`）新增文件服务、签章服务、一次性链接三个模块，另有 AI 闸、提醒两个候选。
- W0 要建成平台（ADR-0054 决定 1），通用审批先行上线（TRN-03）就是首次生产。
- 「冻结」现在只是口头要求，散在三处：「公共基础先行」、§13 第 4 条「地基行冻结」、ADR-0051「10 个平台模块」的写死。冻结的对象、时点、解冻通道都没写。
- 判断「是不是平台」的口径只存在于研究稿。

与已采纳 ADR 的关系：

- ADR-0003、ADR-0004（模块与守护）、ADR-0039（防腐层）、ADR-0057 决定 3（流程模块准入，本稿的写法先例）照常执行，本稿不改。
- ADR-0035 第 2 条允许首次生产前直接改契约，本稿只在其上加一道审批，拟判相容。
- ADR-0041 决定 1 已把子域三分类改为「深建模 / 薄 CRUD」，本稿的档位不是子域分类，不恢复三分类。
- ADR-0051 决定 2 第 1 条、决定 3 平台行将由已批的文件服务基础稿改为「按已采纳 ADR 与 `contexts.yaml` 登记」，本稿以此为前提。如本稿先于该稿采纳，须补「取代」，见后果 U6。
- 「取代」字段暂空。

一份一决定（生命周期第 7 节）：分档、冻结、准入三者可以分别采纳。本稿按派工写成一份，是否拆份交用户（U1）。

## 决定

### 1. 两层与三档

1. **两层**：每个平台模块的内容分两层。
   - **契约与数据形状层**：api 类型与方法、events、OpenAPI 路径、本模块的表、列与约束、错误码、权限码。
   - **策略层**：配置、阈值、路由、供应商。
2. **三档**：每个平台模块标一个档。档名暂用下面三个，「核心」与 DDD「核心域」同名异义，交 one-glossary 定名。
   - **基础层**：不认识任何业务对象，一次建对。
   - **骨架层**：骨架一次建对，策略常变。
   - **易变层**：随时可换。易变层只装 `platform.integration` 的适配器与厂商协议；集成层的端口（中性 record 与接口）按基础层对待。
3. **组织地基**：`organization.workforce`、`organization.attendance` 是业务 BC，但作为组织地基，可以被基础层与骨架层依赖（盘点 G-5）。代价是组织地基的 api 也按基础层的稳定要求管理。
4. kernel 是共享内核，不计入平台模块，稳定要求按基础层。

### 2. 档位登记

1. 档位、负责会话、准入 ADR、使用方出处登记在 `architecture/ddd/contexts.yaml`，只手写这一处（ADR-0041 决定 4）。登记按 SSOT 冻结写法：`frozen`、解冻条件、`change_log` 写解冻理由与对应校验；只改文字说明不算解冻。
2. 本稿采纳时的登记（参考性快照，随复核在登记中更新，不需新 ADR）：
   - **基础层**：identity、audit、eventing、web、idempotency、scheduling、文件服务、integration 端口。
   - **骨架层**：approval、numbering、签章服务、一次性链接。
   - **易变层**：integration 的适配器，包括企业微信、U8C、分贝通、银行、税务、电子印章服务商、预览服务商、大模型厂商、恶意文件检测、对象存储与归档。
   - **待准入**：AI 外发闸。
   - **未准入**：提醒与待办、出件。
   - **不入平台**：参考数据、全文检索、现场采集。
   - **移出平台**：migration（见决定 8 第 1 条）。

### 3. 依赖方向（守护①）

1. 基础层只依赖 kernel、其他基础层模块、组织地基、集成端口。
2. 骨架层另外可以依赖基础层。
3. 两档都不依赖组织地基以外的业务 BC，也不订阅它们的事件。订阅组织地基事件属上述例外。
4. 业务分类经登记数据传入（访问级别、保存类别、`DocumentReference` 等），代码中不枚举业务单据类型。已知待改：`kernel.DocumentType`，交 one-architecture 定是否改为登记制。

### 4. 策略项必须有载体（守护②）

骨架层的策略项都要登记载体，三选一：

- 版本化配置表（DATA_DESIGN_CHECKLIST §14.1 D15、§12.2 配置类）；
- 经另开 ADR 选定的 DMN（ADR-0041 决定 1 的推迟条款）；
- 集成端口。

不得写死在代码里。业务判定不进流程引擎（ADR-0007）。

### 5. 易变部分只在集成层（守护③）

1. 照 ADR-0039 决定 1 执行。另加一条：厂商 SDK 包只能出现在 `platform.integration..`，包清单取自集成登记册（G-I2）。
2. 新增一类厂商仍按 ADR-0041 决定 6 做适配评审并起 ADR；涉及数据外发的，另做安全与法务评审。

### 6. 冻结

1. **冻结对象**：

   | | 契约与数据形状层 | 策略层 |
   |---|---|---|
   | 基础层、集成端口 | 冻结 | 不冻结，按 §12.2 出新版本 |
   | 骨架层 | 冻结骨架 | 不冻结，但须是已登记的策略项（决定 4） |
   | 易变层（适配器） | — | 不冻结，按决定 5 第 2 条 |

2. **冻结的含义**：
   - 兼容新增（ADR-0035 第 3 条的定义）照常进行，由 one-architecture 审核并登记；
   - 破坏性变更（ADR-0035 第 3 条；表的删列、改名、改类型同此）走第 4 条的通道；
   - 改共用件的代理先停下报告，由整合者统一改（§6 原文）。
3. **冻结时点**（候选并列，交用户 U3）：

   | 候选 | 做法 |
   |---|---|
   | T-A | W0 结束、W1 开工前，冻结 W0 已建的平台模块；之后建的模块随其建造批结束冻结 |
   | T-B | 逐模块：在第二个使用方 BC 开工前冻结 |
   | T-C | 不另设冻结点，以首次生产为界，按 ADR-0035、ADR-0038 执行 |

   三者共同的一点：先行上线所用的平台模块，自先行上线起进入 ADR-0035 的兼容期。「先行上线即首次生产部署」的读法交 one-architecture 核实。
4. **破坏性变更的批准**（候选并列，交用户 U4）：

   | 候选 | 做法 |
   |---|---|
   | 甲 | 一律新 ADR，用户批准 |
   | 乙 | 首次生产前由 one-architecture 裁定、one-coordinator 核对、登记 `change_log` 并告知用户；首次生产后按 ADR-0035 执行 |
   | 丙 | 基础层与集成端口走甲，骨架层走乙 |

5. **与现有规则的关系**：
   - 已采纳 ADR 正文冻结管的是决定文字，本条管的是代码契约与表结构，对象不同；
   - SSOT 冻结写法用于档位登记；
   - 本条细化了 §6 与 §13 第 4 条的「冻结」；
   - 首次生产之后，ADR-0035、ADR-0038 照旧适用。

### 7. 准入条件

进入平台须同时满足以下 9 条：

1. **使用面**：
   - 平台服务：至少 2 个 BC（含平台模块）已确认使用。已确认指代码 import、已采纳 ADR 或用户 intent 明载，推断不算。
   - 技术模块（无 api，经框架或 kernel 端口全局使用）：以全局隐式使用代替。
2. **无业务语义**：符合决定 3 第 4 条。
3. **依赖方向**：符合决定 3；并入已建边与规划边后无环（`aggregates_dep_check.py`、`ModuleDependencyTest`）。
4. **两层写清**：两层的内容写明，策略项及其载体已登记。
5. **契约先行**：符合 CS-1.10；api 方法数 ≤12（G4）；事件、表、权限码已登记。
6. **用语**：名称与主要概念已经 one-glossary 登记，写明使用范围与 bc。
7. **负责会话与守护**：有负责会话与画像，守护有落点。
8. **有 ADR**：新增平台模块属模块边界，是 ADR 类（§12.2）。
9. **同批建**：与第一个使用方同批建造，不预留（CS-1.8）。

判定：one-architecture 写适配判断（ADR-0041 决定 6），one-coordinator 核对是否齐全，用户经 ADR 批准；依赖边经 CODEOWNERS（ADR-0003 决定 3）。

### 8. 退出、合并、拆分、改档

1. **触发与去向**：
   - 已确认使用方降到 1 个：归回该 BC。
   - 生命周期结束：下线或改类。
   - 与另一模块变化原因相同，且合并后无环：合并。
   - api 达到 12 个，或出现第二种变化原因：拆分。
   - 发现业务语义，或依赖越档：降档或移出平台。
2. **通道**：以上一律走正式 ADR；涉及代码与表的，附迁移卡。
3. **复核时点**：每个建造批开工前随阶段复核进行，与 ADR-0051 决定 1 第 1 条同法。
4. **本稿采纳时的处理**：
   - migration：不计入平台服务，类别改法见 U6。
   - AI 外发闸：由 one-architecture 在 X1 补确认时按第 7 条判定；结论与已批 AI 底座稿不同的，回问用户。
   - 提醒与待办：先定 scheduling 定位（盘点 G-1），再研究。准入时须为登记制：由业务 BC 登记到期事项，平台不订阅业务事件。
   - 出件：W2 开工前按版式清单判定。
   - 参考数据：按盘点 P8 归 masterdata 或按使用方分归。

## 回滚方案

- 本稿只改登记、生成器和守护，不改业务代码与表。
- 不采纳或废弃时：删 `contexts.yaml` 新增字段，撤回生成器校验与守护；冻结状态随登记一并撤销。
- 已按冻结通道批准的变更照常保留，不回退。

## 需同步修改的守护规则

1. `build_architecture.py`：档位方向校验，加准入字段必填（`kind: platform` 须有 `tier`、`owner`、`adr`、至少 2 个已确认使用方出处）；`--self-test` 覆盖拦截与放行两类，经 `build_all.py --check` 运行。负责：one-architecture；时点：采纳 PR。
2. `ModuleDependencyTest`：基础层、骨架层不得到达组织地基以外的业务 BC（含传递闭包），与 ADR-0051 守护第 1、2 条共用实现。负责：one-architecture；时点：采纳后首张守护卡。
3. ArchUnit：厂商 SDK 包只在 `platform.integration..`，包清单取自集成登记册（G-I2）。负责：one-architecture；时点同上。
4. 冻结快照：已冻结模块的 api 与 events 签名、平台 schema 表结构有变化即失败，须带 trailer（暂名 `Platform-Contract:`）写明类别与批准出处；首次生产后 OpenAPI 与事件部分交 G-C1、G-C2。负责：one-architecture；时点：第一个模块冻结前。
5. 复审清单（`docs/rules/review-briefs/adr.md` 或 DATA_DESIGN_CHECKLIST §14）：加一项「新增阈值、期限、路由是否登记为策略项」。「不认识业务对象」的语义检查只作复审项，不做自动拦截（误伤高，见复核 §2.5）。

## 后果

- 收益：
  - 平台模块有统一口径，回答得了「是不是平台、能不能改、改走哪条路」；
  - 并行建造时共用件有硬拦截；
  - 「第二个使用方」先例成为明文。
- 代价：
  - 多一组登记字段与 4 项守护；
  - 冻结后破坏性改动变慢；
  - 冻结会诱导靠「新增」绕开，接口会膨胀（文件服务 api 已用 11/12），由拆分条件兜底；
  - 组织地基的 api 稳定要求随之提高。

## 备选方案（未采用）

- **不分档，只立准入**：最省事，但答不了「能不能改、改走哪条路」，§6 与 §13 的冻结仍然悬空。
- **按初稿把 integration 整体标易变、不冻结**：它是零出边、被依赖最多的模块，端口一变全局返工（复核 §2.3）。
- **用字面量扫描实现守护②**：误伤分页上限、重试次数、HTTP 状态码，代价大于收益。
- **恢复 DDD 子域三分类作判据**：与 ADR-0041 决定 1 冲突。
- **把档位写进 ADR 正文**：每次改档都要新 ADR；改为登记在 SSOT，ADR 只定规则（同 ADR-0051 决定 1 规范性与参考性的分法）。
