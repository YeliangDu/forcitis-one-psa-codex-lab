## 决定

### 1. 两面与三层

1. **两面**：每个模块的内容分两面。
   - **契约与数据形状面**：api 签名、事件载荷、表结构，以及错误码与权限码。
   - **策略面**：配置、阈值、路由、供应商。
2. **三层**：层名暂定如下，交 one-glossary 终定；`tier` 的取值同时定名。称「层」不称「档位」，是为了避开 ADR 头部的「档位：正式 / 轻量」。
   - **基础层**：不认识业务单据，一次建对。
   - **公共服务层**：骨架一次建对，策略常变。
   - **适配层**：随时可换，只含 `platform.integration`。各层可以依赖它的 api 包（ADR-0039 允许的唯一入口）；端口目前不中性，冻结规则另见冻结 ADR。
3. **组织上游例外**：
   - 基础层与公共服务层可以依赖 `organization.workforce`、`organization.attendance`，但**只能依赖其 `@NamedInterface` 接口**。
   - 这些接口登记在《平台所用组织接口清单》中，与冻结 ADR 的组织上游冻结范围是同一份清单。
   - 人事侧加守护：清单中的接口有变更时，须通知相关平台模块的 owner。
4. **kernel** 是共享内核，不计入平台模块，稳定要求按基础层。

### 2. 分层登记

1. **登记位置**：每个平台模块在 `architecture/ddd/contexts.yaml` 登记 `tier`、`owner`、`adr`。`kind: technical` 的模块也要登记 `tier`，参加分层方向校验，但免做使用方检查。
2. **所属层是规范性内容**，改层须走正式 ADR；使用方与模块所含能力是参考性内容（与 ADR-0051 决定 1 同一分法）。
3. **采纳时的分层**：
   - **基础层**：identity、audit、eventing、web、idempotency、scheduling、文件服务；
   - **公共服务层**：approval、numbering、签章服务、一次性链接；
   - **适配层**：integration。
   - scheduling 改为 `kind: technical`。

### 3. 依赖方向与「不认识业务单据」

1. 基础层只依赖：kernel、其他基础层模块、组织上游清单内的接口、integration 的 api。
2. 公共服务层另外可以依赖基础层，以及其他公共服务层模块；后者须登记且无环。
3. 两层都不依赖组织上游以外的业务 BC，也不订阅它们的事件。
4. **不认识业务单据**：平台代码与表不枚举业务单据类型。这一条与下面的单据类型注册表同时成立（用户 P1 收紧第 1 条、P1a 选 b）。

### 4. 单据类型注册表（P1a 选 b，须在冻结前完成）

1. **业务 BC 声明**：业务 BC 在自己的 api 中声明单据类型码。
2. **注册表放在编号模块**：编号模块持有注册表，字段为 code（唯一）、`owner_bc`、生效期。
   - 审批与编号在写入时，经编号模块的接口校验类型码。
   - 不建跨 schema 的外键；编号模块 schema 内部可以建外键。
3. **kernel 只留值对象**：kernel 只保留 `DocumentTypeCode` 值对象，删去 `DocumentType` 枚举。
4. **审批流程键**：`ProcessKey` 去掉 `DocumentType` 入参，单据类型改为流程定义数据。
5. **审计主体种类**：`platform_audit.audit_entries.subject_kind` 的 CHECK 中列有业务对象（如 `TIMESHEET`），一并改造。
   - 平台自有的主体种类留在审计内部的枚举；业务单据以类型码记录。
   - 审计属基础层，不依赖编号模块：类型码的格式由值对象校验，是否已登记由写入方负责（写入方已经过编号模块校验）。
   - 这一写法交 one-architecture 在实施卡中核对。
6. **判据**：新增一类单据，只需在注册表插一行，再在声明它的 BC 改代码；平台模块不改代码。
7. **时点**：在冻结 ADR 规定的 W0 收口窗口内完成。
8. numbering 归公共服务层，理由是编号规则由财务确认、常变，与本条无关。

### 5. 策略项载体与适配层

1. **策略项载体**：公共服务层的策略项都要登记载体，三选一，不得写死：
   - 版本化配置表（DATA_DESIGN_CHECKLIST §14.1 D15、§12.2）；
   - 另开 ADR 选定的 DMN（ADR-0041 决定 1）；
   - integration 端口。
2. **厂商协议只在 integration**：按 ADR-0039 决定 1。另加一条：厂商 SDK 包只能出现在 `platform.integration..`，包清单取自集成登记册（G-I2）。

### 6. 准入条件

括注表示判定方式：「守护」为机器校验，「人判」为人工判断。

1. **使用面**：至少 2 个模块确认使用，其中至少 1 个是业务 BC。平台模块可以作确认方，但不计入这道门槛，只有平台模块确认的不满足（P1 收紧第 2 条）。
   - 「确认」只认两种依据：已入库的 ADR，以及代码中的实际依赖（`module-dependencies.txt`）。
   - 依据是 proposed 状态 ADR 的，登记为「待准入」作缓冲，不计为确认（P1d 选 b）。
   - 判定方式：守护，生成器校验。技术模块以「全局隐式使用」代替，人判。
2. **不认识业务单据**：符合决定 3 第 4 条与决定 4（人判，加复审）。
3. **依赖方向**：符合决定 1 第 3 条与决定 3，无环（守护：`build_architecture.py`、`ModuleDependencyTest`）。
4. **两面写清**：两面内容写明，策略项已登记（人判）。
5. **契约先行**：符合 CS-1.10，api 方法数 ≤12（守护：G4）。
6. **用语已登记**：模块名与主要概念已经 one-glossary 登记（守护：G37）。
7. **有 owner 与守护**：owner 会话已登记，守护有落点（守护：校验 `owner` 字段）。
8. **有已入库的 ADR**（守护：校验 `adr` 字段）。
9. **与第一个使用方同批建造**，不预留（CS-1.8，人判）。

**判定**：one-architecture 写适配判断，one-coordinator 核对是否齐全，用户经 ADR 批准；依赖边经 CODEOWNERS 评审。

**过渡**：
- 已建的 10 个模块，以及 ADR-0060–0065 所设的模块，视同已满足第 1、8 条与适配判断。
- 第 6、7 条在登记时核对；未齐的登记为「待准入」。

### 7. 待准入的到期条件

文件服务（ADR-0060）、签章服务（ADR-0064）、一次性链接（ADR-0063）按「待准入」登记：

- **owner**：由 one-coordinator 在登记时指派，填入 `owner` 字段。
- **到期条件**：W1 结束，或该模块的首个使用 BC 开工，两者取早。
- **到期未补齐**：首个使用 BC 不得开工，并报用户。
- **待准入期间**：可以按已采纳的 ADR 设计，代码不落地。

### 8. 迁入编排改为流程模块（P1c 选 a）

1. 迁入编排为 `kind: process`，加入 ADR-0057 决定 3 的流程模块目录。
2. 它的性质写明如下：
   - 一次性；
   - 只读老系统（ADR-0037、0055）；
   - 按批运行（ADR-0036）；
   - 没有任何模块反向依赖它。
3. 不设独立的 `platform.migration` 平台模块。
4. 流程模块不建表。迁入产物（迁入批次、拒收、对账记录）落在 `platform.integration`，与 ADR-0036 已定的 `platform_integration.migration_batches` 等表一致。
5. 命名空间例外：迁入编排没有单一的主要协调对象，不适用 ADR-0057 决定 3 第 6 条「归入主要协调对象的命名空间」。模块名与命名空间交 one-glossary 定。
6. 其余流程模块条件（ADR-0057 决定 3 第 1–5 条）照常适用。

### 9. 退出、合并、拆分、改层

1. 触发与去向：

   | 触发 | 去向 |
   |---|---|
   | 已确认的业务 BC 使用方降为 0 | 归回唯一使用方，或下线 |
   | 生命周期结束 | 下线或改类 |
   | 与另一模块变化原因相同，且合并后无环 | 合并 |
   | api 达到 12 个，或出现第二种变化原因 | 拆分 |
   | 发现业务语义，或依赖越层 | 改层或移出平台 |

2. 以上都走正式 ADR；涉及代码与表的，附迁移卡。每个建造批开工前随阶段复核一次。
3. 本稿采纳时其余模块的状态：
   - **AI 外发闸**：待准入。X1 建议在第二份 AI ADR 中设独立模块，是否设已进收件箱，待用户答复；如设，拟入公共服务层。
   - **提醒与待办**：未准入，先定 scheduling 的定位（盘点 G-1）。
   - **出件**：未准入，W2 开工前判定。
   - **参考数据、全文检索、现场采集**：不入平台。

## 需同步修改的守护规则

1. **`build_architecture.py`**（one-architecture，登记 PR）：
   - 校验分层方向与准入字段；
   - 使用方由依赖表推出，并要求至少 1 个业务 BC；

   - 待准入项到期时告警；

2. **`ModuleDependencyTest`**（one-architecture，紧随卡）：
   - 基础层与公共服务层不得到达组织上游以外的业务 BC（含传递闭包）；

3. **ArchUnit**：
   - 平台与 kernel 中不得出现业务单据枚举；
   - 厂商 SDK 包只在 integration。
4. **人事侧守护**：组织接口清单所列接口发生变更时，CI 提示并要求在 PR 中写明「已通知平台 owner」（负责：人事模块实施会话）。
5. **复审清单**：增加「策略项是否已登记」「是否认识业务单据」两项。
