## 1. 题一：切换策略

### 1.1 厂商与方法论一手资料

**Microsoft Dynamics 365 Implementation Guide**（厂商官方方法论文档，三页均已读正文）：

- 部署与发布策略页（<https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/implementation-strategy-define-strategy-deployment-release>）【已核原文】：
  - 选发布策略要看的因素包括：是否多国别 / 多组织、是否先做试点、能否与旧系统并行、集成复杂度。
  - **一次切换（big bang）**：适合「小而简单的实施」或「风险偏好高、能承受一次大变化的组织」；风险是用户接受度、上线后问题集中、难以回退；失败时全体用户同时受影响，没有从早期上线学习的机会。
  - **分阶段（phased）**：可按模块、业务优先级、业务单元、地域分；风险低、后续阶段吸收前期经验；代价是总工期长、数据迁移须错开规划、新旧系统之间需要临时接口、变更疲劳、范围蔓延。
  - **并行（parallel）**：定位是「验证手段，不是推广方式」，通常两套系统同时使用数月，用户双份录入；适合业务风险高、测试难以缓解的项目；不流行，因为成本高；还可能掩盖测试与培训不足；须有基于时间或工作量的明确退出计划。
- 迁移数据页（<https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/data-management-configuration-data-migration>）【已核原文】：迁移数据分「主数据」与「未结交易（open transactions）」两类，例子为销售订单、采购订单、库存、未清余额；分阶段多法人推广时用「配置计划」识别各法人共享与独有的配置；迁移至少在系统集成测试与用户验收环境各演练一次。
- 切换（cutover）页（<https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/prepare-go-live-cutover-strategy>）【已核原文】：切换窗口通常不到 48 小时；**不要选在结账或报告期**；在测试环境反复做「模拟切换」直到有把握（同样的数据、工具、人员、步骤与时间）；须有逐任务的验证与签字、回滚计划、事先定好准入判据的 go/no-go 会议。

| 路线 | 来源怎么说 | 对本系统：适用程度 | 代价 | 收益 | 把握 |
|---|---|---|---|---|---|
| **一次切换** | Microsoft：适合小而简单或高风险偏好；失败面大、难回退；省临时接口（已核）。Mabert：中小企业常用（只见转载）。 | **中**。335 人偏中小，但范围是全企业业务加财务闭环，不属于「小而简单」。【推论】 | 所有流程同日换系统；回退困难；须至少两次全量演练、冻结窗口；老数据清洗集中在投产前。 | 无反向同步、无新老双源、无临时接口；施工方案稿第 4.4 节对此已有判断。 | **中低**：厂商文档只给适用条件，没有按规模给数字界线。 |

### 1.3 项目制、多法人、财务闭环一起切：来源给出的建议

- **切换时点不要在结账或报告期**（Microsoft，已核原文）。
- **年度首日启用最简单**：金蝶、Deltek 两家官方文档都把「年度首日只录余额」作为简单情形，年中启用要补累计发生额或调整分录（已核原文）。与施工方案稿 Q-6 推荐一致。
- 财务系统切换的通行做法是**模拟切换若干次**、逐任务验证签字、事先定好 go/no-go 判据（Microsoft，已核原文）。
- **未查到**任何一手来源给出「项目制多法人企业应一次切还是分批切」的明确判据【未核实】。上表中法人分批一行的把握低，原因即在此。

### 1.4 小结

1. 一次切换与法人分批都有一手来源支持其存在，没有来源说其中之一对本系统更好；
2. 来源对「按模块拆财务闭环」没有明确背书，且共同指出新老并存要付接口成本；
3. 并行运行只作为验证手段有来源支持；
4. 推荐前须补的证据：法人之间的关联交易与共用项目量，见第 5 节。

## 2. 题二：期初迁移口径

### 2.1 「主数据 + 期初余额 + 未结项明细」的通行定义

- Microsoft：迁移数据 = 主数据 + 未结交易（销售订单、采购订单、库存、未清余额），并建议把迁移范围写进迁移策略（已核原文，见 1.1）。
- SAP 迁移驾驶舱：面向新实施，迁移主数据、余额、未结项（open items）；历史数据不迁，唯一例外是财务历史余额对象【只见转载】（<https://blogs.sap.com/2022/02/18/sap-s-4hana-migration-cockpit-direct-transfer-top-5-faqs-as-of-feb-2022/>，返回 403，内容来自搜索摘要）。
- Deltek Costpoint：期初是余额；项目累计数用余额或调整分录（已核原文，见 1.1）。
- Oracle Fusion 项目成本：旧系统带入的交易标记为「已转换交易」，**不能再做会引起成本、收入、发票重算的调整**【只见转载】（Oracle 文档搜索摘要，未读原文）。
- 金蝶：期初余额 + 年中启用时的本年累计发生额（已核原文）。

**对本系统**：口径 b′（主数据 + 期初 + 未结对象明细）与上述通行定义对得上；口径 b 缺「未结交易」；口径 c 超出所有查到的厂商文档范围；口径 a 无来源支持。【推论，依据上列】

### 2.2 「未结」怎么判定

没有查到任何厂商给出的统一定义【未核实】。能找到的有两类线索：

1. **会计档案规则**（已核原文）：《会计档案管理办法》第十九条「保管期满但未结清的债权债务会计凭证和涉及其他未了事项的会计凭证不得销毁」，第二十一条（分立）要求「未结清的会计事项所涉及的会计凭证，应当单独抽出由业务相关方保存」。这是监管层对「未结」的用法：债权债务未清、其他未了事项。
2. **收入准则**（已核原文，页面经摘要工具读取）：企业会计准则第 14 号第四十三条首次执行时「企业可仅对首次执行日尚未完成的合同进行调整」。准则制定者自己采用的子集是**未完成合同**。

据此对象判定的候选，**均为【推论】**：

| 对象 | 判据候选 | 依据 |
|---|---|---|
| 未结合同 | 履约义务未全部履行，或未全部收款 / 开票 | CAS 14 第四十三条的「尚未完成的合同」 |
| 未完工项目 | 未结项且有未确认收入或未结转成本 | 同上，加时段履约需要累计数（见 2.4） |
| 未清应收应付 | 余额不为零的往来明细（单据级，不只科目级） | 第十九条；Microsoft「未清余额」 |
| 质保金 | 合同约定的质保期未满、尚未收回或支付的部分 | **无一手来源**【未核实】；按未清应收应付处理 |
| 在途单据 | 审批未完成、尚未形成会计事实的单据 | 施工方案稿口径为投产前排空审批类在途（ADR-0021 决定 3）；来源未查到 SAP / Microsoft 对此的明确推荐【未核实】 |

### 2.3 历史明细是否迁入

- SAP 驾驶舱不迁历史，历史放归档 / 数据仓库 / 旧报表环境【只见转载】。
- Microsoft 迁移页只提主数据与未结交易，没有建议迁全量历史（已核原文：全文未出现历史交易的迁移建议）。
- 国内：历史会计资料的保管义务属于会计档案（第 3 节），不要求迁入新业务系统；只要求保管期内可读、可导出。
- 代价侧：全量迁入的清洗与对账量由施工方案稿自己估算（拒收率待取证）；一手来源没有给出全量迁入的收益证据。
- 反方向的理由（保留明细的价值）：红字冲销引用原单、核销对原单、收入累计可追溯。这些在本系统是内部规则（INV-72 等），不是外部来源的要求【推论】。

### 2.4 与收入准则时段履约相关的期初处理

**已核原文**（<https://kjs.mof.gov.cn/zt/kjzzss/kuaijizhunzeshishi/201709/t20170907_2694006.htm>）：

- 第十一条：时段履约的三个判定条件；
- 第十二条：时段履约义务按履约进度确认收入；方法为产出法或投入法，类似义务用同一方法；进度无法合理确定但已发生成本预计可补偿时，按已发生成本确认收入；
- 第四十一条：合同资产是已转让商品而有权收取对价、但还取决于时间流逝以外因素的权利，无条件收款权列为应收款项；
- 第四十二条：附注须披露履约进度方法与原因，以及合同资产、合同负债的期初期末账面价值。

**【未核实】**：准则正文只规定了方法类别；「累计履约进度 × 交易价格 − 前期已确认」这样的累计差额算法见企业会计准则应用指南与教材，本次没有读到原文。

**由以上推出的期初最小集**（**均为【推论】**）：

| 项 | 为何需要 |
|---|---|
| 每个未完成合同的交易价格及已确定的变更 | 累计进度算收入的基数 |
| 累计履约进度（产出法）或累计已发生投入与预计总投入（投入法） | 下一期收入 = 新累计 − 已确认累计；缺任一项，本期收入无法算 |
| 累计已确认收入 | 同上 |
| 累计已开票、累计已收款 | 合同资产 / 合同负债 = 累计已确认收入与累计已开票（或已收）之差，以及应收余额 |
| 合同资产、合同负债、应收账款的期初余额（按合同） | 第四十二条期初期末披露；核对总账 |
| 累计已发生合同履约成本 | 投入法进度；成本归集 |
| 在途工时与未结转成本 | 否则首期成本与收入错配 |

**Deltek 与金蝶的做法**与此一致：期初放余额，年中启用时补累计发生额（已核原文）。

**把握**：中。方向有来源，具体字段是推论，须财务确认（ADR-0018 要求会计用语财务确认）。

### 3.4 审计准则对期初余额的要求

《中国注册会计师审计准则第 1331 号——首次审计业务涉及的期初余额》（2010-11-01 修订，自 2012-01-01 施行；<https://www.cicpa.org.cn/ztzl1/Professional_standards/Professional_guidelines/201211/W020210421541238331440.pdf>）【已核原文】：

- 第三条：首次审计业务 = 上期财务报表**未经审计**，或由**前任注册会计师**审计的情况下承接的审计业务。第 1331 号因此**针对更换会计师事务所或首次审计**，不针对更换业务系统；
- 第八条：需确定上期期末余额是否已**正确结转**至本期，以及期初余额是否反映恰当的会计政策，并实施审计程序；
- 第十二、十三条：无法获取期初余额的充分证据 → 保留意见或无法表示意见；期初余额存在重大错报未恰当处理 → 保留意见或否定意见。

其他：
- 另有搜索摘要提到 2019-02-20 修订版与 2017 年应用指南【只见转载】，是否有后续修订**本次未核实**。
- 更换业务系统时审计师关注系统数据迁移与信息技术一般控制：只见到 CICPA 刊物的《信息系统一般控制审计（下）》，其内容是系统运维与访问权限，对数据迁移**没有专门段落**（已读正文，<https://www.cicpa.org.cn/ztzl1/hyxxhckzl/xxjhykjhy/201809/W020210419753143602487.pdf>）；连载上篇未取得。搜索摘要对数据迁移审计程序的描述【未核实】，不采用。

**含义**（【推论】）：对同一家审计师、同一主体换系统，审计关注的是**上期期末余额正确结转**（第 1331 号第八条第 1 项的思路）以及系统切换对内部控制和数据完整性的影响；投产期初余额与审定的上年末财务报表可对平，是最基本的证据。

### 3.5 数电发票红冲

国家税务总局公告 2024 年第 11 号（2024-11-12，自 2024-12-01 起施行，<https://fgk.chinatax.gov.cn/zcfgk/c100012/c5236067/content.html>）、国家税务总局「一文了解：纳税人怎样开具红字数电发票」（<https://www.chinatax.gov.cn/chinatax/n810356/n3010387/c5236346/content.html>）【已核原文】：

- 蓝字发票未做用途确认或入账确认：开票方发起红冲并直接开具红字发票；
- 已确认用途或入账：开票方或受票方发起《红字发票信息确认单》，对方确认后开票方开具；确认单发起 72 小时内未确认自动作废；
- 确认单**须与对应蓝字发票信息相符**；蓝字发票在平台上按条件查询后选择，信息自动带入；全额与部分红冲均可；
- 受票方已抵扣的，暂依确认单税额转出进项税额；
- 页面**未规定**红冲的时间期限；**未说明**蓝字发票来自旧业务系统时如何处理。

**含义**（【推论】）：红冲的蓝字发票引用发生在**税务平台**，不依赖企业业务系统里有没有那张发票的记录；所以「不迁发票」在税务层面不阻止红冲。但要把红字金额对应回合同、项目、收入确认，业务系统必须能找到原蓝字发票的号码和归属；这是施工方案稿 INV-72 的内部规则要求，并非外部强制。发票以纳税人（法人）为单位，所以法人分批切换时开票主体是自然边界。

### 4.3 研究层面的倾向（不是裁定）

1. 期初口径：**倾向 b′**，a 无支持，c 的收益证据弱；b′ 中「未结」的判据与质保金口径须财务签字。
2. 时点：**会计年度首日**有一手来源支持（金蝶、Deltek），并避开结账期（Microsoft）。
3. 切换路线：来源**不足以**在一次投产与按法人分批之间裁定；逐阶段按模块对财务闭环证据最弱；并行运行仅留作财务侧验证。若须选一条，研究倾向**一次投产 + 年度首日 + 至少两次全量模拟切换（Microsoft）**，条件是关联交易与跨法人耦合证明法人分批收益不大。
4. 合规：会计档案与 11 号 / 12 号文**不构成**投产不接老系统的阻碍，也没有要求迁入历史；须在设计中落实的有三点：(a) 老系统 / A8 退役后历史会计资料仍可读（第八条、第十二条）；(b) 总账模块须提供导出电子会计档案的接口（12 号第二十八条）；(c) 投产期初与审定上年末报表可对平。
