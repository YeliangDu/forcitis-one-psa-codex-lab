# 迁入写入通道与 ADR-0058 补写：架构判定

状态：已确认｜2026-10-22｜负责：one-architecture

触发：one-coordinator 转 one-data 两项（`claude/one-data-handoff-1` @4dc3396a1）：`data/MIGRATION_WRITER_ROLE_DESIGN.md` §3.1 请求登记对 ADR-0036 授权清单的补充；`data/ADR0058_AMENDMENT_INPUT.md` 列 ADR-0058 四处出入，请起草补写。

## 一、日历迁入版本的确认：不给迁入角色 `UPDATE`

**判定：设计 §3.1 的「迁入角色对确认列的列级 `UPDATE`」与 ADR-0036 决定 1 字面冲突，不能当作登记补充。**ADR-0036 决定 1 对目标表写明「`SELECT`、`INSERT`……不授 `UPDATE`、`DELETE`」；列级 `UPDATE` 只开给迁入登记表的批次、断点、对照状态列和期间迁入占用的状态列，这几处都是迁入自身的运行记录，不是业务表。已采纳 ADR 的正文冻结，要放开只能另起 ADR、经用户批准。

**不另起 ADR，改走应用内确认（建议 one-data 改设计）：**

1. 迁入日历版本照常以 `PENDING_CONFIRMATION` 插入并加日明细（设计 §3.1 前半不变）。
2. 由日历确认权限的业务人员在应用内确认，与编号版本表的 `MIGRATION` 行同一做法（设计 §3.1 末条：管理员与财务在界面确认）。
3. 理由：
   - 与 ADR-0036 一致：该 ADR 把需要人判断的签字（拒收处置、核对签字，第 7、8 条）都留给应用内操作，迁入角色只写数据。确认迁入的日历是业务认定（法定假日、调休是否照搬），不该由迁入进程自己完成。
   - 两张迁入版本表口径一致，守护与测试只需一套。
   - 迁入角色权限不变，§3 方案 A 的判定函数照用。
4. 代价，交 one-data 落：
   - 迁入行确认后 `confirmed_by` 有值：`ck_work_calendar_versions_confirmation_columns` 里「迁入版本 `confirmed_by` 为空」一款要改为「迁入版本由确认人确认，作者为空」。
   - 依赖已确认日历的后续迁入批次（如考勤），在迁入编排里排在日历确认之后：确认是批次之间的人工步骤，并写进该阶段迁入规格（§14.2 M1）。
   - 日历触发器确认、撤回两处判定改用 `is_owner_member`，不放行迁入角色。

若 one-data 核出应用内确认确实走不通（例如某个批次必须在迁入窗口内连续完成），带证据回来，再由 one-architecture 起草修改 ADR-0036 决定 1 的新 ADR 交用户批准。在那之前不放开。
