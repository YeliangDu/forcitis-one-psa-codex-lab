# 接缝 J1–J7 机器检查清单（交 one-quality 写脚本）

状态：评审中｜2026-10-16｜负责：one-architecture

依据：用户 2026-10-16 批准「前五步框架符合性验证」第 ② 项（经 one-coordinator 转达，原话「派」）；规则出处 `METHOD_V4_DRAFT.md` §3 接缝表 J1–J7。本清单只列可判定的检查；不可机判的（如价值流按触发干系人视角命名）列在末尾，由独立审查人工判。

## 输入

| 简称 | 文件（`docs/architecture/proposals/`） | 形式 |
|---|---|---|
| VS | `value-streams.v2.yaml` | YAML：`stakeholders`、`value_streams[].stages[]`（`entry` / `exit` 为 `{any|all: [...]}` 树，叶子 `{ref, state, note?, caveat?}`）、`state_caveats`、`out_of_scope` |
| CAP | `capabilities.v2.yaml` | YAML：`capabilities[]`（一级，含 `object`、`l2[]`，二级可有 `via`）、`pending`、`excluded` |
| IM | `ENTERPRISE_INFO_MAP_DRAFT.md` | Markdown 总表：行 `\| OBJ-nn \| 名称 \| 定义 \| 级别 \| 属性 \| 关键状态 \| …`；级别含「一级」「次级（…）」「非对象」 |
| AG | `ENTERPRISE_AGGREGATES_DRAFT.md` | Markdown：§1.2 不变量表 `\| INV-nn \| 名称 \| 类 \| 聚合 \| 对象 \|`；§2.2 各 BC 小节（`**B-nn …**`）下聚合表 `\| # \| 聚合（根） \| 内含 \| 对应 \| 不变量 \| 对外事件（订阅方） \| 引用与依赖方式 \|` |
| DEP | `aggregates_dep_check.py` | 现有查环脚本，可复用其 AG 解析 |
| VL | `vs_links_gen.py` | 现有脚本，含「状态按 / → 拆分并比对 IM 关键状态」的实现，可复用 |

状态值拆分统一用 VL 的拆法；比较前去掉括号内注释。

## J1 干系人 ↔ 价值流（VS）

- **J1.1** 每条 `value_streams[]` 的 `triggering_stakeholders` 非空，且每个 ID 在 `stakeholders` 中存在。
- **J1.2** 不拆子价值流：`stages[]` 元素不得含 `stages`、`sub_value_streams` 键；阶段 `id` 匹配 `^VS-\d{2}\.\d+$` 且前缀等于所属价值流 `id`。
- **J1.3** 跨价值流只经对象状态：`entry`、`exit` 树的每个叶子 `ref` 匹配 `^(OBJ|REF)-\d+$`；任何叶子不得引用 `VS-` 或阶段 ID。叶子 `ref` 为 `派生`（段内派生提示）的放行，但不得出现在 `entry` / `exit` 的门条件中（见 J2.4）（独立审查建-6）。
- **J1.4** 每个 `stakeholders[]` 的 ID 至少出现在一处 `triggering_stakeholders`、`value_receivers` 或 `stages[].participants`，否则须出现在 `out_of_scope`。

## J2 对象 ↔ 阶段（VS + IM）

- **J2.1** 每个阶段 `entry`、`exit` 都存在且至少一个叶子。
- **J2.2** 每个叶子 `ref` 是 IM 中存在的对象行，且该行级别不是「非对象」。
- **J2.3** 每个叶子 `state` 是该对象 IM「关键状态」列拆出的状态之一；不符者须在 `state_caveats` 中有对应条目（按 `ref` 匹配），否则失败。
- **J2.4** 门不引用派生值：叶子不得带 `derived: true`，`state` 不得含「派生」二字（METHOD 第 ④ 步第 7 条）。
  同时检查叶子是否引用聚合稿标为派生的状态（回溯检查 RD-11）：解析 AG §2.2 末的「派生值清单」（每行 `对象｜状态｜计算所在`，状态按 `/` 拆分），`entry`、`exit` 的叶子 `(ref, state)` 与清单任一项相同即失败；`in_stage_states` 与贯穿活动的叶子只报告。已知违例待 ③ 步处理：VS-04.2 `exit` 的 OBJ-08「部分履行 / 已履行」。
- **J2.5** 门只预警：阶段与叶子不得有 `block`、`blocking`、`gate_mode` 等拦截类键。

## J3 阶段 ≠ 状态机（AG）

- **J3.1** §2.2 聚合根名称不得含「阶段」「Stage」，白名单：WBS 阶段节点所在的 AGG-20（工作进程，不是阶段状态机）。
- **J3.2** 聚合「内含」「不变量」列不得出现阶段类型目录中的阶段名作为状态值（目录取 `STAGE_TYPES_DRAFT.md` 第 51 行：启动、概念、方案、初设、深化、招采、施工、结算、检查策划、现场检查、发现发布、整改跟踪、报告认可）。只报告，不失败（可能误报，人工复核）。

## J4 对象 ↔ 能力 ↔ BC（CAP + IM + VS）

- **J4.1** CAP 任何层级不得出现键 `bc`、`module`、`subdomain`、`current_bc`、`strategic_hint`。
- **J4.2** 每个一级能力的 `object` 在 IM 中级别为「一级」；每个二级能力的 `object` 在 IM 中存在且不是「非对象」；有 `via` 的，`via` 也须存在。
- **J4.3** IM 中每个级别为「一级」的对象，恰有一个一级能力以它为 `object`。
- **J4.4** 能力—阶段对账：一级能力的对象集合（自身 `object` 加其 `l2[].object`）与某阶段 `entry` / `exit` 叶子的 `ref` 有交集，或该阶段任何位置（含段内条件、贯穿活动的输入输出）引用其对象，即该能力「支撑」该阶段（「仅段内」也算支撑，独立审查建-6）。每个一级能力至少支撑一个阶段，否则须带 `unsupported_reason`（字段名待 one-quality 与 one-architecture 对齐后补进 CAP）；每个阶段至少被一个一级能力支撑。输出能力 × 阶段对照表。

## J5 规则 ↔ 不变量 ↔ 聚合（AG）

- **J5.1** §1.2 每条 INV 的「类」以 A、B 或 C 开头（可带括号说明，可为「A + B」），不得是「前置检查」「编排」「额度占用」等实现模式名。
- **J5.2** INV 的「聚合」列每个 AGG 编号在 §2.2 中存在；A 类恰引用一个 AGG。
- **J5.3** C 类 INV 的行内须有 `ADR-\d{4}` 引用。
- **J5.4** §2.2 每个聚合「不变量」列的 INV 编号在 §1.2 中存在；§1.2 每条 INV 至少被一个聚合的「不变量」列引用（双向）。

## J6 对象 ↔ 聚合（AG + IM）

- **J6.1** §2.2 每行「对应」列以五种之一开头：一对一、次级在内、一拆多、无聚合、技术聚合（运行单据算技术聚合）。
- **J6.2** IM 中每个非「非对象」的对象，至少出现在一个聚合行（根或「内含」列中的 `OBJ-nn`），或在 AG 中被标「无聚合」。
- **J6.3** 一拆多一致：对应为「一拆多」的对象须出现在两个及以上聚合行；出现在两个及以上聚合根的对象，其各行对应须为「一拆多」。
- **J6.4** 技术聚合的行不得声称对应 IM 对象为根。

## J7 聚合 ↔ BC ↔ 依赖（AG + DEP）

- **J7.1** DEP 退出码 0：无环，分层输出与 §4.1 生成块一致。
- **J7.2** 「引用与依赖方式」每条的方式 ∈ {api, 事件, 不校验}；目标为存在的 AGG、REF、B 编号或已登记模块名。
- **J7.3** 上游不读下游：任一 api / 事件引用形成的 BC 边，方向须与 §4.1 依赖骨架一致（下游 → 上游），不得出现反向边。
- **J7.4** 证据不引用采集对象：B-28 中以 OBJ-53 证据为根的聚合，其引用列对其他 BC 的聚合只允许「不校验」。
- **J7.5** 每个 AGG 只在一个 BC 小节下出现；聚合数、BC 数与 §0.1 写的计数一致。

## 输出

每条检查打印「通过 / 失败 / 仅报告」与违规明细（文件与行号）；任一失败项退出码 1。计数（价值流、阶段、对象、能力、聚合、BC、INV）一并打印，供独立审查引用。

## 不可机判（留独立审查人工判）

- J1：价值流以触发干系人视角命名。
- J2：阶段可回退、跳过、重入（只能看 `notes` 是否写明）；阶段与商务分界脱开。
- J5：规则卡「类别」四分（规则卡在 `docs/business/rules/`，不在本输入内）。
- J7：BC 按统一语言划分是否恰当。
