## 1. 框架原意（概括）

1. **BIZBOK**：业务对象是业务领域里活动、持久、业务关心的事物，用名词称呼；在信息图中由信息概念表达，必须有定义、类型、状态、关系。信息概念不一定进数据模型或数据库（第 186 页）。元模型只记类型，不记个例（第 186 页）。
2. **一级 / 次级**：不依附其他对象存在的是一级；依附他者存在的是次级（第 194–195、198 页）。BIZBOK 的「次级」即本项目的「从属对象」。
3. **汇聚对象**：如 Finance，把一组次级对象收到一个上位视角下，列入信息图但不写类型、状态、关系（第 195、198–199、204 页）。
4. **不是信息概念的**：单据、文档等业务构件，技术或建模构件（第 197 页）；估值、评级、属性（第 198–199 页）。
5. **类型**：同物异型用类型区分、不拆对象；类型由该对象下的类型管理能力管（第 200–201 页）。BIZBOK **没有「参照数据」这一类**。
6. **状态**：每个信息概念（汇聚对象除外）都有有限状态集，由能力结果改变，用作价值流阶段进出条件（第 193、205–206 页）。BIZBOK 不以「有无生命周期」区分是不是对象，也不以它决定要不要流程。
7. **身份**：BIZBOK 的对象释义没有单列「身份标识」；最接近的是「定义类能力确立并唯一标识该对象」（第 206 页）与「业务对象是持久的」（第 186 页）。
8. **TOGAF**：Business Information 是业务使用的概念及其语义；Data Entity 是业务认作独立概念的数据；前者「由」后者实现（Part 4 第 11、23 页）。数据实体 → 逻辑数据组件 → 物理数据组件是三层（Part 1 第 66 页），即概念、逻辑、物理三层数据模型。G190 附录把「信息概念」与 ArchiMate「业务对象」分为两物（第 11 页），与 BIZBOK 用法不同，本项目按 BIZBOK。

## 2. 判据：是不是业务对象

**核心判据（建议）**：业务需要**逐个区分、长期记录**的事物，**有身份标识**。三条同时满足才是业务对象：

| # | 判据 | 框架对照 |
|---|---|---|
| J1 | 是业务用语里的名词，指业务关心的一类事物（不是动作、不是单据格式、不是系统部件） | 一致：BIZBOK 第 186、197 页 |
| J2 | 业务需要逐个区分它的个例，并能说出靠什么区分（身份标识：业务编号、法定编号或组合业务键） | **本项目补充**：BIZBOK 未单列，与第 206 页「唯一标识」相容【推出】 |
| J3 | 需要长期记录（跨越一次操作或一次会话仍需查、需追溯） | 一致：BIZBOK 第 186 页「持久」 |
| J4 | 能写出定义、类型、关系；状态集有限（汇聚视图除外） | 一致：BIZBOK 第 186、194–195 页 |

排除项（任一命中即不是对象，进 ENTERPRISE_INFO_MAP §3 非对象出口表）：单据格式、文档、打印件（第 197 页）；属性、估值、评级、派生度量（第 198–199 页）；同物异型（改写为类型，第 200 页）；技术构件（第 197 页）。本地化例外照旧：外部权威登记的法律事实算对象（intent `2026-10-15-221201`）。

**生命周期的用法**：本项目只用它判断是否设流程（OBJD 判据①：有生命周期且业务人员办理→补流程）。**与 BIZBOK 不完全一致**：BIZBOK 要求非汇聚对象都有状态并用于阶段进出条件，而不是用来决定是否设流程；设流程的判据是本项目规则（intent `2026-10-17-201810`），框架未作规定，不冲突。因此「状态集」是对象的必填项，「是否设流程」是另一个独立判断。

## 3. 分类与判别

先按第 2 节判是不是对象，再按下表五选一（`kind`）。与 OBJD 三条判据（intent `2026-10-17-201810`，ENTERPRISE_INFO_MAP §2.18）对齐。

| kind | 中文 | 判据 | 流程要求 | 框架对照 | 本系统例 |
|---|---|---|---|---|---|
| `primary` | 独立对象 | 不依附其他对象存在 | 有生命周期且业务人员办理→须有承载流程（OBJD①） | BIZBOK 一级（第 194 页） | OBJ-01 往来单位、OBJ-05 协议、OBJ-29 项目、OBJ-98 会计分录 |
| `subordinate` | 从属对象 | 离开父对象就没有意义；随父对象建、随父对象终结 | 由父对象流程承载，不单独设流程，不删除（OBJD②） | BIZBOK 次级（第 194–195、198 页）；不等同于 DDD 聚合内实体（见第 5 节） | OBJ-03 联系人（父 OBJ-01）、OBJ-08 履约义务（父 OBJ-05）、OBJ-22 报价估算分解（父 OBJ-21） |
| `reference_data` | 参照数据 | 有身份、被多个对象引用，用于分类或口径；业务很少逐笔办理、变化走版本（D15、D17） | 不要求承载流程；须有维护责任人 | **BIZBOK 无此类**：其「类型」相当于参照数据的一部分（第 200–201 页）。本类为本项目分类，已由用户对 OBJ-96 定论 | OBJ-96 账簿；阶段类型若单列也属此类 |
| `view` | 视图（汇聚） | 把多个对象收到一个上位视角；自身无独立状态、无独立身份 | 不要求流程、不要求表 | BIZBOK 汇聚对象（第 195、198–199、204 页）对应「汇聚」；**衍生值（合计、余额、指标）不是对象**（第 198–199 页），不进清单，进度量层 | OBJ-103 财务 |
| （不进清单）| 技术对象 | 只为系统运行而存在：队列、幂等、锁、计数器、迁移、框架表；运行单据（批次、运行）若只为守住不变量也归此 | 不进业务对象清单 | BIZBOK 第 197 页；METHOD 第 ④ 步第 6 条「技术聚合」 | `cost_timesheet.consumed_events`（IDEMPOTENCY）|

判别顺序：是否技术 → 是否衍生（衍生则出清单）→ 是否汇聚（view）→ 是否依附（subordinate）→ 是否主要供分类与口径引用（reference_data）→ 其余 primary。

## 4. 度量角色标注（只做标注）

每个对象标 `measure_role` 三选一，并写 `main_measures`。**只是标注，不作为是不是对象的依据**（调度意见）。

| 值 | 含义 | Kimball 对照（对应而非等同） | 例 |
|---|---|---|---|
| `fact` | 其状态变化产生可加总的度量 | 事实表的一行 = 一次度量事件；对象本身不是事实表，是度量事件的来源（总线矩阵行 = 度量事件，FRAMEWORKS §5） | OBJ-98 会计分录（金额）、工时（小时） |
| `dimension` | 被度量按它切片 | 维度表；跨 BC 共用的成为一致性维度 | OBJ-01 往来单位、OBJ-29 项目、OBJ-56 人员 |
| `reference` | 只提供分类或口径，进维度属性 | 维度属性或小维度 | OBJ-96 账簿、阶段类型 |

`view` 类对象可不标（填 `none`）。一个对象可同时是维度又是度量来源（如项目），取主要角色，另一角色写在 `main_measures` 备注里。

## 5. 与 DDD、TOGAF、Kimball、DAMA 的关系（对应而非等同）

| 本标准 | DDD | TOGAF | Kimball | DAMA |
|---|---|---|---|---|
| 业务对象（概念层） | 不等于聚合；对应方式五选一：一对一、次级在内、一拆多、无聚合、技术聚合（METHOD 第 ④ 步第 6 条） | Business Information（Part 4 第 11 页） | 维度或度量事件的来源 | 概念数据模型中的实体 |
| 身份标识 | Entity 的身份（DDD Reference「Entities」） | — | 维度自然键 / 持久键 | 业务键 |
| 从属对象 | 多为聚合内实体或值对象，也可能独立成聚合（按不变量定） | Data Entity「Decomposes」（第 24 页） | 维度属性或子维度 | 从属实体 |
| 参照数据 | 值对象或小聚合 | — | 维度属性 | 参照数据 |
| 视图 | 读模型 / 投影 | — | 汇总表 | — |
| 表 | 一个聚合一张或一组表，同 schema（D3） | Data Entity → 逻辑 → 物理（Part 1 第 66 页） | 事实表、维度表在分析层另建 | 物理数据模型 |

层次：对象（BIZBOK）→ 聚合（DDD）→ 表（数据访问注册表 `aggregate` 字段）。对象与表**不直接一对一**，经聚合中转。

## 6. 对象与表的对应关系

**框架依据与一处不一致**：TOGAF 规定业务信息由数据实体实现（Part 4 第 23 页），支持「对象要有表」；但 BIZBOK 明说信息概念不一定进数据模型或数据库（第 186 页），且允许 IT 系统难以记录的概念（第 187 页）。用户「每个对象至少一张或一组表」比 BIZBOK 严。建议：对**记录系统是本系统**的对象采用用户规则；记录系统在外部的对象写明外部系统，不要求自有表（见第 8 节确认点）。

### 6.1 对象 → 表

| kind | 要求 | 怎么算 |
|---|---|---|
| primary | 至少一张自有表或一组表（经其聚合） | 现有 DDL 经注册表 `aggregate` 查到，或在 `ddd/aggregates.yaml` / ENTERPRISE_AGGREGATES_DRAFT 有已提议表 |
| subordinate | 父对象的表内承载**算**满足（子表或父表内列组均可） | 写 `carried_in`：自有子表名，或「父对象表内」 |
| reference_data | 一张配置或版本化维度表（注册表 role `CONFIG`、`CONFIG_VERSIONED`、`DIMENSION_VERSIONED`）；作为某对象的类型枚举存放时，写明所在表与列 | 同上 |
| view | 不要求表；若落为投影，登记 role `SNAPSHOT` 并可重算（D1） | — |
| 外部记录系统 | 不要求自有表；写 `system_of_record` | 本系统只存来源对照列（D16） |

对不上时的判别：
- **假对象**：对象写不出身份标识（J2 不成立），或其内容全是另一对象的属性、估值、状态 → 出清单，改为属性或状态。
- **表未设计**：判据 J1–J4 都成立、只是还没有表或聚合 → 保留对象，列入待设计清单，写负责会话。
- 两者都不像：交 one-architecture 复核，不自行删除。

### 6.2 表 → 对象

每张自有表（数据访问注册表 `tables` 键）必须归到一个对象，或判为技术表。

| 注册表 role | 归类 |
|---|---|
| `AGGREGATE_ROOT`、`AGGREGATE_CHILD`、`BUSINESS_DOCUMENT` | 业务表，须归到一个对象（child 归父对象或其从属对象） |
| `DIMENSION_VERSIONED`、`CONFIG`、`CONFIG_VERSIONED` | 业务表，归到参照数据或对象的类型 |
| `SNAPSHOT` | 归到视图，或某对象的投影 |
| `QUEUE`、`IDEMPOTENCY`、`COUNTER`、`LINEAGE`、`ONE_TIME`、`FRAMEWORK`、`PLACEHOLDER` | **技术表**，不归对象 |
| `LOG_APPEND_ONLY` | 审计日志为技术表；若是业务要查的记录（如状态历史），归到所属对象 |

归不进时的判别：
- **遗漏对象**：业务表能用 J1–J4 判为对象，但清单里没有 → 登记候选对象，走第 ② 步回补。
- **技术表**：role 属上表技术类 → 不归对象。
- **运行单据**：期间性批处理结果（成本结转批次、分摊运行）→ 技术聚合，表归到它最终改动的对象的 `acted_on`（与 PROCESS_ANCHORING_RESEARCH 第 3 条一致）。

## 7. 每个对象的必填字段与机器检查规则

字段（写入 `object-layer.yaml` 的对象条目或对象清单 SSOT，具体落点由 one-architecture 定）：

| 字段 | 说明 |
|---|---|
| `id` | OBJ-nn，唯一 |
| `name` | 中文名，取自 `terms.yaml` |
| `term` | 词表 id |
| `kind` | primary / subordinate / reference_data / view |
| `identity` | 身份标识：业务键说明（view 填 `none`） |
| `lifecycle` | 状态集（primary、subordinate 必填）或类别说明（reference_data、view） |
| `parent_object` | subordinate 必填，其余为空 |
| `stages` | 所属价值流阶段（可空，空须有 `stages_reason`） |
| `processes` | 承载流程编号；subordinate 写父对象流程；reference_data、view 可空 |
| `measure_role` | fact / dimension / reference / none |
| `main_measures` | 主要度量（fact 必填） |
| `system_of_record` | `self` 或外部系统名 |
| `tables` | 表或已提议表；subordinate 可写 `carried_in` |
| `sources` | 出处：研究、intent、ADR、法规（至少一条） |

规则（供后续写入 `object_layer_check.py`；编号 OD-）：

1. OD-1 每个对象上表必填字段齐全，`kind`、`measure_role` 取值在枚举内。
2. OD-2 `kind=subordinate` ⇔ `parent_object` 非空；父对象存在且不是 view；父链无环。
3. OD-3 `kind` 为 primary 或 subordinate 时 `lifecycle` 至少两个状态；view 的 `lifecycle`、`stages` 为空。
4. OD-4 `kind=primary` 且状态集含业务人员办理的状态时，`processes` 非空（OBJD①）；subordinate 的 `processes` 须是父对象的承载流程子集（OBJD②）。
5. OD-5 `identity` 非空且不为 `none`，view 除外。
6. OD-6 `measure_role=fact` 时 `main_measures` 非空。
7. OD-7（对象→表）`system_of_record=self` 且 kind ≠ view 时，`tables` 或 `carried_in` 非空，且每个表名在数据访问注册表或已提议聚合表中存在。
8. OD-8（表→对象）数据访问注册表中 role 属业务类的每张表，恰好被一个对象的 `tables` / `carried_in` 引用；技术类 role 的表不得被对象引用。
9. OD-9 `name` 在 `terms.yaml` 中可查到（经 `term`）。
10. OD-10 非对象出口表中的名称不得同时出现在对象清单中。

## 8. 需用户确认的点

1. 核心判据「业务需要逐个区分、长期记录、有身份标识」作为是不是业务对象的标准，可以吗？（「身份标识」是我们补的，框架没单列，但不冲突。）
2. 「参照数据」是我们自己的分类，框架里没有，框架把它当作对象的「类型」。保留这一类（如账簿、阶段类型），还是并回所属对象的类型？
3. 「每个对象至少一张或一组表」只要求记录在本系统的对象；记录在外部系统（如税务平台、银行）的对象只写来源，不要求自有表。可以吗？（框架明说对象不一定进数据库。）
4. 从属对象放在父对象的表里（子表或父表内的一组列）算满足「有表」，可以吗？
5. 合计、余额、指标这类衍生值不是对象，移出清单放到度量层；只把「汇聚」类（如财务）留为视图。可以吗？
