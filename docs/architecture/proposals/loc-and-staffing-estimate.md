5. **迁入清洗量**（T-2 拒收率、T-3）：适配器行数不大，但清洗规则与核对测试可能翻倍。
6. **返工率**：已实测 16%–18%（1.2 节），本估算是净增口径，没把返工加回；按毛产出算要再乘 1.2 左右。

**日产出（稳态，取 10-15 与 10-16）**：
- 代码总量约 1.5 万–2 万非空行 / 天，其中后端运行代码只有约 2,000–4,000 行，**测试与守护代码是运行代码的 4–8 倍**，前端几乎为零；

- 动代码的 PR 13–19 个 / 天，约占合入 PR 的 13%–26%，其余是治理、意图、规则、用语。

**和需求对比**：中值 86 万行，从 2026-11-02 到 2027-09-17 共约 319 天，平均每天要 2,700 行**做完的**代码。按行数算，现在的原始产出是需求的 5–7 倍。

**这个对比说明的是：行数不是瓶颈，「做完」才是。** 施工方案 428 车道周对应中值 86 万行，相当于每车道周约 2,000 行、每车道日约 300 行**做完**的代码；今天 3–4 条写代码车道的原始产出约每车道日 5,000 行，差 15 倍左右。这个「完成系数」包括规则卡与用户决定、返工（已测 16%–18%）、评审轮次、集成、dev 部署、验收。现在没有一个 BC 完整走完，所以完成系数**测不到**，既不能说施工方案过于保守，也不能说按行数推算过于乐观。这正是第 5 节要校准的头号参数。

再补一个今天可见的事实：10-15、10-16 两天后端运行代码净增约 6,500 行，测试净增约 32,000 行。大头是守护测试、数据修复、命名与结构修订，不是新业务能力。最近两天新增的业务聚合几乎为 0，在跑的是 R-1b P4/P5、数据修复、工时规则卡这类收口工作。

读法：
- 用户今天一天的「决定吞吐」大约 160 个，但这是在架构与方法论阶段，题目大多有现成推荐，用户主要做的是认可。到 B-08 收入确认、B-15 个税社保、迁入拒收这类题，单题要研究、要找财务或审计，吞吐会掉一个数量级（intent 142319：「收入确认是个很重要的话题，我们需要认真研究」）。
- 治理会话与代码车道之比约 2 : 1。这套治理是质量的来源，但把 12 条代码车道照这个比例放大，就是 30 个以上会话，单个调度会话和 4 台执行机撑不住。
- 用户本人实际承担 (a) 业务决策，加上 (b) 中「认可调度会话的技术取舍」这一半；合并、派工、评审由调度会话（agent）完成。

| (b) 技术主导者 | 调度车道、评审取舍、解阻塞、技术 ADR 认可、CI 与环境决策 | 每条代码车道每天约 0.5–1 小时的人类注意力（推论：今天用户在约 4 条代码车道加 8 个治理会话上投入整天，其中大半是 (a)）；12 车道约 **每天 6–12 小时**，约 **250–450 人日** | 可加人；须熟悉 PLAYBOOK、CODING_STANDARD、50 多份 ADR，上手约 1–2 周 |
| (c) 线下工作 | 每 BC 业务验收 5–15 人日（29 个 BC，150–400 人日）；培训（335 名活跃用户，每人 2–4 小时加讲师准备，100–200 人日）；迁入核对与两期重算比对（财务约 2 人 × 8 周，80–150 人日）；三次模拟切换与彩排（30–60 人日） | **约 400–800 人日**，集中在 2027-06 至 12 月 | 由财务、HR、项目管理部的关键用户做，不是工程师；agent 只能准备脚本、核对报告和培训材料 |
| (d) 外部专业确认 | 审计师（收入确认口径，A1、A10 书面意见；迁入与期初）；税务（数电发票、进项、申报）；法务（个人信息保护：薪酬与人事敏感数据迁入；会计档案保管；劳动合同电子化） | **约 20–60 人日的外部工时**；日历等待通常数周到数月 | 外部；收入确认须在 B-08 开工（2027-04）前有结论 |

### 4.3 k（每个技术主导者带几条代码车道）的依据

- **今天的观察**：1 个用户 + 1 个调度 agent，管 12 个会话，其中写业务代码的 3–4 条；最近两天新增业务聚合几乎为 0，说明这个配置下有效产出被治理与收口吃掉了大半。可作为下限：**k ≈ 4 时已经接近一个人的注意力上限**。
- **公开资料**：
  - Anthropic 内部研究（132 名工程师，2025-08 调查）：自报生产率提升约 50%；合并 PR 每人每天增加 67%；多数人表示只能「完全委派」0–20% 的工作。【已核原文】
  - METR 随机对照试验（16 名资深开源开发者、246 个任务、2025 年初的工具）：用 AI 的任务耗时多 19%，而开发者自己预期快 24%。工具已过时，不能直接外推，但说明「自我感觉的提速」不可靠。【已核原文】
  - DORA 2025：AI 采用与交付吞吐正相关，同时与不稳定（变更失败、返工）正相关。【只读到二手综述，原报告未核】
  - Faros AI：高采用团队完成任务多 21%、合并 PR 多 98%，PR 评审时间增加 91%。【二手综述，原报告与样本量未核实】
  - 同时监督几个 agent 会话：从业者经验是 2–3 个，个人上限约 5 个，先坏的是人的注意力。【厂商与个人博客，未核实，不作硬依据】
- **取值**：k = 4（区间 3–6）。前提是像现在这样由调度 agent 承担合并、派工与初审；没有调度 agent 时取 2–3。

### 4.4 配置方案

施工方案的达成配置要求 12 条车道、重叠 30%、拆 3 路、单车道产出至少达到估算的 1.05 倍，并且没有向下的容忍度（§6.5：车道 −15% 就错过）。

#### 配置一：1 个决策人（用户）兼技术主导，k = 12

- **最强的支持论证**：行数产出已经是需求的 5–7 倍；一个人决策，口径前后一致，没有人与人之间的协调损耗；用户今天能在一天里拍板 160 个决定点。
- **判断：赶不上 2027-10 的最迟线。** 今天 4 条代码车道已经占满用户一天（大半是 (a)）；(a) 本身要占用户 30%–50% 的时间，峰值期更多；k = 12 远超公开资料与今天的观察。CI 也要扩到约 3 倍（§6.7 ②）。另有单点风险：用户生病、出差或决策疲劳时全线停；照推荐作答比例约 85%，到业务口径题时有「认可而未审」的风险。

#### 配置二（推荐）：1 个决策人 + 2 个技术主导者，每人 k = 5–6，共 10–12 条车道

- **最强的反方论证**：新人要 1–2 周读懂 PLAYBOOK、CODING_STANDARD、50 多份 ADR 和词表，前一个月可能是净负贡献（Brooks 定律）；两个技术主导者对同一规则理解不同，会出现跨车道不一致，评审与调度的协调成本上升；如果完成系数实际比施工方案好（行数产出 5–7 倍并非全虚），加人就是浪费。
- **判断**：在三个前提下可以赶上 2027-09-17 至 10-08：(1) 单车道产出达到施工方案估算的 1.05 倍（第 5 节校准）；(2) CI 扩到 8–12 台执行机，或迁到云 CI；(3) 用户把约 70% 的时间留给 (a) 与验收组织，技术取舍授权给两位技术主导者（须用户决定）。余量约 0–3 周，没有缓冲。
- **风险**：两位技术主导者 2026-11 内到位并上手；不然 W0（B-13，关键路径起点）延误会一路传下去。

#### 配置三：1 个决策人 + 1 个财务口径共同决策人 + 3 个技术主导者，k = 4–5，共 12–15 条车道

- **最强的反方论证**：用户的硬规则是「用户做全部决定」，引入共同决策人会改变治理结构；三位技术主导者加上更多会话，对调度会话、合并队列、守护测试都是更大压力；成本最高。
- **判断**：最有可能赶上（相当于施工方案 §6.5「车道 +30%」一档，余量约 7 周）。财务共同决策人只在用户授权的边界内先定口径，并组织 (c) 中的迁入核对与重算比对，这正好对准 W3–W4 的决策峰值和 2027-09 以后的线下峰值。
- **风险**：与审计师的书面意见（A1、A10）仍是日历瓶颈，加人也压缩不了。

**不论选哪种**，(c) 线下工作 400–800 人日都要由财务、HR、项目管理部的关键用户承担，2027-06 前就要排定人员；这一项和工程师人数无关，是现在的模型里完全没有的人力。

## 5. 敏感性与 2–4 周的校准方案

### 5.1 最敏感的参数

1. **完成系数**（原始行数到做完功能的折算）：现在约 15 倍，测不准；它直接决定每车道周产出，施工方案对这个参数下行 30% 就错过。
2. **关键路径上的决策等待时长**：每个 BC 平均等一周，12 个关键路径 BC 就累计约 12 周。
3. **k 与 CI 吞吐**：决定实际能开几条车道。
4. **返工率**：已测 16%–18%；后续口径题（收入确认 Q-04 等）一旦推翻已建代码，会更高。
5. **深聚合体量**：只影响总量，对工期的影响通过第 1 项体现。

### 5.2 校准办法（用 one-1a-next-5 数据修复批和后续 PR）

数据修复批（PR-1 审计分区 → PR-3 → PR-6 审批 → PR-7 编号 → PR-8 workforce）的特点是「改已建表」，正好用来测**已建对象的变更成本**；随后的 B-06 全员版或 B-01 是第一个能测「一个 BC 从规则卡到 dev」全流程的样本。每个 PR 和工作卡记录：

| 指标 | 用途 | 怎么取 |
|---|---|---|
| 工作卡开始到合并的耗时（日历时间与会话活跃时长） | 车道日 / 聚合 | 工作卡时间戳、PR 创建与合并时间 |
| 分类净增与毛增（运行 / 测试 / SQL / 前端 / 文档） | 完成系数、测试比 | `git diff --numstat` 按路径分类（本目录 `loc.py` 可复用） |
| 14 天内被删除或重写的行（churn） | 返工率 | `git log -L` 或 blame 对比 |
| 评审轮次、opus 打回次数与原因 | §6.7 ③ 未建模项 | PR 评论、复审结论 |
| CI 排队时长、运行时长、重跑次数 | §6.7 ② | `gh run list` |
| 每张工作卡需要的用户决定数，与「提问到答复」的等待时长 | 决策带宽与等待 | 确认页提交时间与 intent 时间戳 |
| 用户每天投入时长，(a)、(b) 各占多少（用户自记，或从消息时间推） | k 的实测 | 用户自记一周即可 |
| 「做完」的定义达成时点：规则卡 → 规格 → 实现 → 评审 → 合并 → dev 部署 → 验收 | 真正的车道周 / 聚合 | 每聚合一行台账 |

**判据**：到 2026-12 中旬，若首个完整 BC 的实测车道周 / 聚合高于施工方案假设（薄 0.8、深 1.2）的 0.95 倍，就说明配置二没有余量，应当在 2027-01 前转向配置三或启用 §6.5 的减负杠杆（由用户决定）。建议调度会话把「建成日与最迟线的距离」和上表前 4 项作为每周监控量。
