# Q-04 研究：收入确认是无状态规则层，还是有状态对象

状态：历史记录｜2026-10-16｜负责：one-architecture

状态：已按 Q04_REVIEW 与 sonnet 复核修订（2026-10-16）。研究稿（只读研究，未改仓库）。按 `docs/architecture/proposals/research-plan-revenue-recognition-object.md`（下称「计划」）的 S1–S11、三个选项与交付格式写。基线：`origin/claude/one-architecture-adr-governance`（2026-10-16 fetch）。引用行号以 `adr/src` 与聚合稿当前实际行号为准（2026-10-16 逐条核对）。
未做：生产取证（列为第 6 节取证需求表，由调度转 one-ops，相关结论标「待取证」）；ADR-0037 登记行（取证执行时由 one-ops 登记）。

三个选项（沿用 `decision-page/PENDING.json` Q-04 与计划；C 与 B 按评审细分，见下）：
- **A 无状态规则层**（现行字面）：收入确认只是一组规则，结果只体现在过账事实（AGG-77）里，不另存确认记录。依赖前提：过账事实须携带业务坐标（履约义务、付款条件项、证据引用），否则累计与追溯无法从过账事实反推；聚合稿 AGG-77 现只带「来源单据引用」（`ENTERPRISE_AGGREGATES_DRAFT.md:516`），选 A 要加字段。
- **B 有状态对象**，分两种形态：
  - **B1 轻量 B**：AGG-44 内有状态的确认行（占用中 / 已确认 / 已释放 / 已冲销，行上可改状态），不另立聚合；
  - **B2 独立聚合 B**：收入确认是独立聚合，有生命周期（草稿 → 审批中 → 已确认 / 驳回；冲销），须另开 ADR 修订 ADR-0016 决定 4。
- **C 不可变确认事实加审批中占用行**（评审 J1 重写）：C =「AGG-44 内的不可变确认事实＋沿用额度占用模式的审批中占用行」。
  - **确认事实**：只追加、不可改，记证据引用、证据类型、认可日、规则与配置版本、金额；冲销是新追加的负额事实、`reverses_id` 指原事实；
  - **占用行**：沿用额度占用模式（聚合稿 :63），只记金额、审批实例 ID、占用状态（占用中 / 已转实 / 已释放）；证据留在证据侧，不进占用行；
  - **申请载荷（本会话判定）**：拟认可日与证据引用（交付物提交轮次 / AGG-110 证据，或期满认定 AGG-38）作为审批实例载荷快照放在 `platform.approval`，不放占用行；
  - **转实**：审批通过时，确认事实从审批实例载荷复制认可日与证据引用，在 AGG-44 一个事务内按 RULE-222 二次校验额度、追加确认事实、占用转实；
  - **与 ADR-0016 决定 4 的关系**：这是对决定 4 的**细化**，规则仍无状态，状态只在占用行、与额度占用同生共死；选 C 时须在 ADR-0016 状态行写明「细化」。
  - 与 B1 的区别：C 的确认事实本身不可改、不带状态；状态只在占用行。B1 的确认行自己有状态、可改。

## 0. 先说结论（倾向、前提、否决条件）

**倾向 C（不可变确认事实＋审批中占用行）。** one-architecture 已判定：C 是对 ADR-0016 决定 4 的细化（规则无状态，状态只在占用行、与额度占用同生共死），选 C 时在 ADR-0016 状态行写明「细化」，不必走修订 ADR；「不可改的事实」与「有状态的占用」分开存放。

理由三条：
1. **字面意义上的 A 已与已采纳的 ADR 冲突**，不是一个真实可选项：ADR-0047 影响面给「收入确认」加列 `acceptance_evidence_type`、`acceptance_date`（ADR-0047:149），迁移方案要求历史行「按原样迁入，证据类型统一记为『历史迁入』」（ADR-0047:170），U-1 (a) 要求认可前各类证据「可登记、关联到收入确认、封存」（ADR-0047:85、:116），决定 5 写「收入确认的审批流程照常」（ADR-0047:101，经 ADR-0049 第 5 条保留），U-2 (a) 写「收入确认审批中由财务复核」（ADR-0047:117）。这些都预设了一条持久的收入确认记录与一个审批对象。聚合稿 N-12 与 AGG-44「收入确认行」（`ENTERPRISE_AGGREGATES_DRAFT.md:426`、`:1053`）实际已经按「AGG-44 内有一行」写了。
2. **B2 的收益大多 C 也能拿到**：审计追溯、冲销引用、迁入表达、规则版本固定，靠的是「有一条带 ID、不可改的确认事实」，不靠独立聚合。B2 额外带来的是跨聚合额度占用（先占 AGG-44、再写独立聚合，孤儿占用要定时释放），以及修订 ADR-0016 的成本。
3. **成熟产品都存确认结果，但状态都很轻**：Deltek 存累计结果、无独立状态机；Oracle 存收入分配行、冲销行指回原行；SAP 结果分析按期间存结果、结算才过账；D365 估计有 Created / Posted / Eliminated；SAP S/4HANA EBRR（事件驱动的收入确认，随业务事务同时生成确认过账，官方页摘要未核实）接近 A 的形态，但它仍保存过账及其依据。无一是「完全不留业务依据」，也无一是重型业务单据状态机（第 4.2 节）。可比性有限：这些产品主要服务时段履约，场景与本系统不同。

**前提**：
- 设计服务按「某一时点履行」（A1，GL-026）成立；收入只由客户认可证据触发，不需要按期计量履约进度。
- 审批流程状态由 `platform.approval` 持有；AGG-44 内只有占用行记「占用中 / 已转实 / 已释放」，与额度占用同生共死；确认事实不带状态。
- 每份协议的确认事实与占用行数量不大（**待取证** E1），AGG-44 每协议一个聚合仍可接受。

**否决条件**（任一成立即改选 B1 / B2，或 C 加独立的计量记录）：
1. 财务认定某类履约义务按时段履行（检查服务部分合同、全过程咨询按月服务等，ADR-0047:26 已提示），须每期估计履约进度：估计值是判断、不能从事实重算，必须按期存，且有「已估计 / 已过账 / 已冲销」状态（D365 估计、SAP 结果分析同理）。**问财务** W-1。
2. 审计师要求确认记录自身保留完整的状态与审批履历（谁在何时提交、退回、批准），且不接受「审批履历在 `platform.approval`」。**问财务** W-6。
3. 取证显示单协议确认行量大（例如数百行以上）或开票与收入并发写同一协议很频繁，AGG-44 乐观锁冲突明显（**待取证** E1、E9）。
4. 评审或 one-architecture 日后认定占用行状态已构成收入确认的生命周期（已判定为细化；此条保留为复核点，只在出现新事实时重议）。

**与开票的对称关系（评审 J3）**：对比应是「开票申请（AGG-45）→ 发票（AGG-46）」与「收入确认申请（占用＋审批）→ 确认事实」，两者对称：都是先有申请与审批、通过后才产生不可改的事实；申请的内容（开票申请的准入检查结果 / 收入确认的拟认可日与证据引用）都在申请侧留存，收入确认的这份载荷是审批实例载荷快照，放在 `platform.approval`，占用行不存证据。唯一不对称是收入确认的申请寄在 AGG-44 的占用行上，而不是独立聚合。理由：占用行与额度同在一个聚合，审批通过时在一个事务内校验额度、追加确认事实、占用转实；没有跨聚合的先占后写，就没有孤儿占用。开票申请有自己的准入规则（INV-71）和人的审批阶段，值得独立聚合；收入确认没有额度以外要自己守的不变量（见 S7）。

**最强反证场景与处理（评审 J2，第 5 节详写）**：一笔「视为同意」收入在审计师认可前已登记证据、算出期满日、项目经理已声明，只差第 6 类开放；ADR-0047 U-1 (a) 字面要求认可前即可登记、关联、封存证据。那时确认事实还不存在，所以细化为：证据先关联交付物提交轮次 / AGG-110，确认事实形成时再引用该证据。**U-1 (a) 是用户 2026-10-16 未改动、按预选提交的条目**（ADR-0047:3），改字面须让用户知情，已写进确认页「须让你知情」一段。

**聚合稿待改项（评审 J4）**：聚合稿 AGG-44（`ENTERPRISE_AGGREGATES_DRAFT.md:426`）把「视为同意判定」写在收入确认行上，与 ADR-0049 决定 2 的次序（先认定、后确认）不一致：认定要在收入确认之前成立，不应放在收入确认行上。聚合稿须订正，ADR 本身未被违反。同行的命令「确认视为同意期满（→ 视为同意已成立）」一并列入待改。应改为期满记录证据（AGG-38）或 AGG-44 内单独的认定事实。另 ADR-0049:19 写期满待办载体「随 Q20 交用户」，本研究结论是期满待办不依赖 Q-04，应改述为「可先行，须用户确认」；同样写进确认页「须让你知情」一段。

## 2. 子问题逐题（先写最强反方，再下结论）

每题给三选项下「是否需要状态、状态记在哪」。

### S1 累计履约进度与累计已确认额

- **最强反方（主张 A 足够）**：A1 时点履行下没有履约进度要算；累计已确认额 = 该履约义务的收入过账事实合计，过账事实只追加（ADR-0016 决定 2），任何时候都能重算且与总账一致，不需要第二份存储。再存一份确认行就是双份事实，违反「同一事实两处存储」（ADR-0049 备选方案引 METHOD 第④步第 7 条）。
- **反驳**：T1、T2 说明「累计」不只包括已过账，还包括**审批中**的占用。新系统里「收入确认审批中」这一阶段的依据是已采纳的 ADR-0047：决定 5 第 4 点「收入确认的审批流程照常」（ADR-0047:101）与 U-2 (a)「收入确认审批中由财务复核」（:117）；RULE-184 只作老系统佐证；审批中的金额没有过账事实，A 下无处可算。另外过账事实是会计层（法人、期间、借贷），收入确认的累计是业务层（履约义务、付款条件项）；从过账事实反推履约义务需要过账事实携带业务坐标，聚合稿 AGG-77 只带「来源单据引用」（`ENTERPRISE_AGGREGATES_DRAFT.md:516`）。
- **结论**：
  - A：已确认部分可重算；审批中占用无载体。**不够**。
  - B：累计由 AGG-44 额度行承担（INV-22），B 的对象只存单笔。
  - C：同 B，但单笔确认事实与占用行都在 AGG-44 内，额度、占用、确认事实同一事务。
  - 若出现时段履约（否决条件 1），进度估计必须按期存，三选项都要另加计量记录（**问财务** W-1）。
- 重算与审计留痕是否一致：已过账部分一致（只追加）；审批中部分只有 B、C 留痕。

### S2 期满待办（ADR-0049 第 4 条）

- **最强反方（主张 B）**：期满待办有完整生命周期——送达后开始、退回作废、重报重算、期满待声明、声明后认定（ADR-0049 第 4 条、ADR-0047 第 5 条第 5 点）。这本身就是状态机；硬说收入确认无状态，只是把状态藏到别处。
- **反驳**：期满日是**纯函数**：期满日 = f(送达日, 合同审查期参数, 期限单位与顺延口径 F-3)。待办列表 = 「已送达、本轮未退回、未声明、未认定」的提交轮次。这些输入分别在交付侧（送达、退回、声明，AGG-27）与合同侧（AGG-13 视为同意参数），都是别人的事实；收入侧只需要一份按提交轮次为键的**投影**（订阅送达、退回、声明事件），投影可随时从事件重建，不是领域状态。待办提醒交平台待办（`platform.approval` 或通知），不需要收入确认对象。
- **载体候选**：
  - A：`receivables.wip` 内的只读投影「视为同意期满候选」（键：提交轮次 ID），加平台待办；认定结果须另存（见 S3），A 下无处存。
  - B：收入确认对象在「待期满」状态等待。缺点：交付物一送达就要建一个收入确认对象，而很多轮次最后是客户书面认可或退回，产生大量作废对象。
  - C：同 A 的投影；认定结果**不**放在收入确认行上（聚合稿 AGG-44:426 现写在行上，与 ADR-0049 决定 2 的次序（先认定、后确认）不一致，聚合稿须订正，ADR 未被违反，列为待改项，见第 0 节），改记为期满记录证据（AGG-38）或 AGG-44 内单独的认定事实。
- **结论**：期满待办**可以不依赖收入确认对象**（判定标准满足）。推荐载体：`receivables.wip` 内按提交轮次为键的投影 + 平台待办，A / C 通用。这一条交 one-architecture 写进 ADR-0049 第 4 条的落地记录。

### S3 视为同意的认定

- **最强反方（主张 A）**：认定是规则：期满 + 有声明 + 未退回 + 声明日不早于期满日（ADR-0049 守护第 1 条）。输入都在别处、都已封存，随时可重算，不必存「认定结果」。
- **反驳**：
  1. 认定的输入会变：合同审查期参数可因合同变更出新基线；F-3 期满算法参数会出新配置版本（ADR-0047 F-3）。重算用的是**新**参数，结果可能与当时不同——这正是老系统 RULE-080「红字凭证按当前规则重算」的缺陷形态。
  2. ADR-0047 守护第 4 条：「证据封存后不可修改或删除」；ADR-0049 影响面：「期满记录」由 `receivables.wip` 认定时产生，是第 6 类证据的组成部分。第 6 类证据须附「期满日的计算过程」（ADR-0047 第 5 条第 3 点）——计算过程必须**存下来**作为证据，不能每次重算。
  3. 可撤销（T4）：迟到异议后要冲销，须能引用被冲销的那次认定。
- **结论**：认定结果**必须存**。
  - A：只能塞进过账候选，过账事实承载证据计算过程不合适（会计层不该认识交付轮次）。**不够**。
  - B：存在收入确认对象上。
  - C：认定结果存为 B-28 证据（AGG-38）的「期满记录」证据（B-08 → B-28 边已有，ADR-0049 影响面），或 AGG-44 内单独的认定事实；确认事实形成时引用它。不放在收入确认行上：确认行要在认可（含视为同意）成立之后才产生。
- 会计口径（视为同意能否确认收入）已在 ADR-0047 F-2 至 F-8 交财务、审计师，本研究不重复，只在 W-2 补一问（迟到异议是估计变更还是差错）。

### S4 审计师认可闸门（ADR-0047 第 4 条）

- **最强反方（主张 B）**：U-1 (a)：认可前各类证据「都可以登记、关联到收入确认、封存」（ADR-0047:85、:116），只是不触发。「关联到收入确认」意味着收入确认在触发前就已存在，处于「已登记、待开放」状态；开放后才能推进。这是对象的状态，C 的「只存结果」装不下。
- **反驳**：闸门状态**挂在 AGG-92 证据类型开放配置**上（按类、按生效日、只追加，ADR-0047 第 4 条第 4 点），不挂在收入确认上。认可前登记的证据挂在交付物或 WBS 阶段（AGG-110 证据关联，intent 114200 F-1），并不需要先有一条收入确认。开放后提交收入确认时引用这些证据即可；「不追溯」规则（认可日早于生效日不能用）是纯规则。
- **冲突与细化（J2，one-architecture 已判定）**：U-1 (a) 字面要求认可前即可登记、关联、封存证据，那时确认事实还不存在，字面「关联到收入确认」落空。细化为：证据先关联交付物提交轮次 / AGG-110，确认事实形成时再引用该证据。不在 AGG-44 增加「待开放」行（那是一个等待态，会把 C 变成 B1）。**U-1 (a) 是用户 2026-10-16 未改动、按预选提交的条目**（ADR-0047:3），改字面须让用户知情，写进确认页「须让你知情」一段。
- **结论**：闸门状态挂 AGG-92，各选项相同；认可前后行为切换不丢证据的前提是证据挂在交付侧（AGG-110）。A、C、B1 都要求上面的字面细化；B2 不需要细化，但要接受「大量待开放对象长期挂起」（审计师可能长期不认可，ADR-0047 风险第 1 条）。

### S5 冲销与更正

- **最强反方（主张 A）**：ADR-0016 决定 2 已规定更正的唯一路径是冲销：反向事实 + 新 `PostSeq`，原行保留、双向关联。被冲销的那一笔就是原过账事实，`PostSeq` 可引用，够了。
- **反驳**：
  1. 业务侧需要引用「被冲销的那次**确认**」而不只是那几行分录：老系统退回行以 `origin_code` 指原收入确认单（434 行，ADR-0016:30），成本回冲按原确认单号找配对的结转行（RULE-080）；INV-88「转出金额配对已确认收入」（AGG-43）也按确认配对。一次确认通常生成多行事实（收入、合同资产、待转销项、配对成本），按 `PostSeq` 配对会把业务关系拆散。
  2. 退回的金额与原确认不同（部分退回），RULE-080 的缺陷正是「部分退回冲全额成本」；要正确处理，退回必须作为业务记录，带「退回额、原确认 ID」。
  3. D17-8 把「收入冲减（可变对价）」定为单独的事实类型，它也需要指向被冲减的确认或履约义务。
- **结论**：需要「被冲销的那一笔」可在业务层引用。
  - A：**不够**（只有分录级引用）。
  - B：冲销是对象的状态转换（已确认 → 已冲销）或新对象。
  - C：冲销是一条新追加的负额确认事实（`reverses_id` 指原事实），原事实不改，与 ADR-0016 决定 2 同构；Oracle 的冲销分配行指回原行（`ReversedRevenueDistributionId`）、D365 actuals 的冲销记录经 transaction connection 互联，都是这种形态（第 4.2 节）。
- 退回与迟到异议在会计上是估计变更（当期）还是差错（追溯），影响 S6，**问财务** W-2、W-3。

### S6 收入期间归属与跨期调整

- **最强反方（主张 B）**：期满日或认可日所在月已关账、审批晚到（T7、T8），需要记「原期间」与「落账期间」两个值，且跨年情形（ADR-0045 U-2）未定，可能要等窗口——这是对象在「待落账」上停留。
- **反驳**：期间路由是期间闸门（INV-92）的职责，不是收入确认自己的规则（聚合稿 :206 已把原 INV-87 并入 INV-92、INV-99）。收入确认只需给出「业务日期 = 认可日」（ADR-0047 第 3 条第 1 点），过账管道路由到开放期间并标原期间（ADR-0045 决定 2）。期间关闭后的更正一律在开放期间冲销加新事实（ADR-0045 决定 2、§12.3），三选项相同。
- **结论**：S6 **不需要收入确认的状态**，三选项无差别。跨年迟到单据（U-2）是独立待决，不应借 Q-04 解决。会计口径：迟到异议或退回若被认定为前期差错，CAS 28 要求追溯重述，与「落开放期间、不重述」的 ADR-0045 冲突，**问财务** W-3。

### S7 履约义务额度与确认行

- **最强反方（主张 A / C 已足够、B 多余）**：额度占用模式（聚合稿 :63）已经表达了「审批中占用、驳回释放、确认转实」，占用行自带状态；额度聚合一个事务内保证不超占。再给收入确认单独建聚合，就要先占额度、再写对象，跨聚合，还要定时释放孤儿占用。
- **反方的反方（主张 B）**：占用行有了「占用中 / 已转实 / 已释放」三个状态，旁边又挂着确认事实（证据引用、证据类型、认可日、AGG-44:426），合起来就是收入确认对象，只是被塞进了额度聚合。AGG-45 开票申请是一对一的独立聚合，有准入、驳回、作废（:427），同一 BC 里开票申请是有状态单据、收入确认却不是，不对称。词表 C-17 也指出 `revenue_recognition` 标 `document`「实为有状态对象」（`ENTERPRISE_INFO_MAP_DRAFT.md:503`）。
- **评估（J3）**：对比应是「开票申请（AGG-45）→ 发票（AGG-46）」与「收入确认申请（占用＋审批）→ 确认事实」，两者对称：都是先申请、审批、通过后才产生不可改的事实。申请的内容在申请侧留存：开票申请的准入检查结果在 AGG-45 内；收入确认的拟认可日与证据引用是审批实例载荷快照（`platform.approval`），占用行只记金额、审批实例 ID、占用状态，审批通过时确认事实从载荷复制认可日与证据引用。唯一不对称是收入确认的申请寄在 AGG-44 占用行上、而不是独立聚合。理由：审批通过时要在一个事务内按 RULE-222 校验额度、追加确认事实、占用转实，放在同一聚合内没有跨聚合的先占后写，也就没有孤儿占用。另外收入确认的全部「拒」规则（INV-22、23、86）要么读别处（证据、配置、协议），要么就是额度本身，没有额度以外要自己守的不变量；开票申请的准入（INV-71）则有自己的规则与人的审批阶段，值得独立聚合。所以确认事实与占用行放在额度聚合内，**一致性边界是对的**；状态只在占用行。
- **结论**：占用行**足以表达**审批中的业务状态（占用中 / 已转实 / 已释放），确认事实不带状态、冲销是新事实，前提是审批流程状态留在 `platform.approval`。这是对 ADR-0016 决定 4 的细化（规则无状态，状态只在占用行、与额度占用同生共死）。若判定要在确认行上自己带状态（B1），则与决定 4 的张力更大。单协议行数与并发冲突**待取证** E1、E9。

### S8 对账与审计追溯

- **最强反方（主张 A）**：审计追溯靠过账事实：U8C 凭证 → `PostSeq` → 来源单据引用 → 证据。来源单据引用可以直接指向证据（AGG-38），不需要中间的确认记录。
- **反驳**：一次确认引用多份证据（触发证据 + 佐证，ADR-0047 第 3 条第 2 点），还要说明用的是哪个证据类型、按哪个开放版本、期满怎么算、哪个履约义务额度。把这些放在过账事实里，会让会计层携带交付、合同、配置的业务坐标，违背「过账事实是会计层」的分工（ADR-0016 决定 3 的精神：业务 BC 不认识科目，反过来过账也不该承担业务证据链）。审计准则把收入推定为舞弊风险（中国注册会计师审计准则第 1141 号第二十七条）并做截止测试（第 4.1 节），审计师要的是「这笔收入凭什么、为什么落在这个月」，正好是确认记录的内容。
- **结论**：
  - A：追溯链断在「凭什么」一跳。**不够**。
  - B、C：凭证 → `PostSeq` → 收入确认记录（证据引用、类型、认可日、版本）→ 证据（封存）。B、C 等价。
- 对账：合同资产滚动恒等式、D17-0 对账等式按过账事实算（ADR-0016 决定 1、`GL_FINANCE_DECISIONS.md` D17-0），各选项相同；「确认事实合计 = 收入过账事实合计」成为 B、C 下多出的一条勾稽。
- **确认事实（AGG-44）与过账事实（AGG-77）不能同事务**：两者是不同聚合，ADR-0016 决定 5 只把 WIP 与开票放在同一一致性边界，没有把确认事实与过账放在一起。两种做法：
  - **同步调用**：确认事实追加后，同步调用过账管道提交过账候选，失败则回滚确认；代价是 AGG-44 事务里夹着一次跨聚合调用，期间闸门拒绝（关账）时会拒掉整笔确认，且 AGG-44 乐观锁持有时间变长；
  - **outbox＋对账**：确认事实与 outbox 行同事务写入，由事件投递过账候选，过账管道幂等接收；另设勾稽「确认事实合计 = 收入过账事实合计」，缺口告警。代价是确认与过账之间有短暂不一致，须对账兜底。
  - **倾向 outbox＋对账**（聚合稿无先例，非既有做法）：确认事实是业务事实、认可日已定，过账晚几秒不改变业务结果；同步调用会让期间闸门的拒绝反向卡住已审批通过的确认。过账失败（如期间已关）按 ADR-0045 决定 2 落开放期间，不回滚确认事实。该选择交 one-architecture 在落地时确认。
- **不可变事实的数据库守护（C 的确认事实）**：确认事实表在数据库层禁止 UPDATE / DELETE（权限回收＋触发器，与 ADR-0016 决定 2 的明细事实表同法），并加 ArchUnit 守护（仓储接口只暴露追加与查询，不暴露更新）。占用行是可改状态的，与确认事实分表。

### S9 规则版本

- **最强反方（主张 A）**：过账事实只追加，金额与期间已经冻结，规则改了也不影响历史（§12.3：配置新版本、规则修正都不得回写已过账事实）。「当时的口径」体现在结果里，不必另存版本号。
- **反驳**：冻结的是结果，不是依据。冲销时要「按原分录取反」而不是「按新规则重算」（T9，老系统 RULE-080 缺陷）；ADR-0022 回滚方案与 ADR-0045 S8「规则出错：发布新版本，已过账分录在开放期间冲销重记」要求能识别「哪些确认用了出错的那个版本」——没有版本号就只能全量重查。调研的 Deltek 与 Oracle 都**不**把规则版本写进结果记录，子代理据文档观察到的后果是更正只能靠冲销或累计差额，回不到原规则（第 4.2 节，观察而非文档原文）。
- **结论**：需要存「当时的口径」：证据类型开放配置版本（AGG-92）、视为同意期满参数版本、协议基线版本；科目映射版本由 `accounting.ledger` 在分录上记（ADR-0016 决定 3）。A 下只能塞进过账候选；B、C 存在确认记录上。

### S10 全量历史迁入

- **最强反方（主张 B）**：老系统收入确认单本身就是有状态单据（PENDING / CONFIRMED / REJECTED，RULE-222），且切换时有在途实例（A8 71 个、老系统 1 笔审批中，ADR-0024:19、ADR-0016:28）。新系统若没有对象和状态，在途单据无处迁入。
- **反驳**：ADR-0024 第 4 条：在途实例在切换前「排空或逐单给出关闭结论」，切换后在新系统重新发起；没有「迁入审批中状态」的要求。已确认历史按原样迁入（ADR-0047:170），没有过程可伪造。
- **三选项比较**：
  - A：历史只迁入过账事实。但 ADR-0047 迁移方案要求「证据类型统一记为『历史迁入』」——这是确认记录上的列，A 下没有这张表。**与已采纳 ADR 字面冲突**。
  - B：迁入时要么伪造「草稿 → 审批中 → 已确认」的转换，要么给状态机开一个「迁入即已确认」的入口（与 AGG-45 历史 31 个合同「迁入标例外」同类，聚合稿 :181）。后者可行，但状态机多一个只给迁入用的入口。
  - C：迁入为只追加的确认事实（证据类型「历史迁入」、来源系统、原单号、迁入批次），退回行按冲销关系迁入（`reverses_id`），与 ADR-0024 第 4 条、ADR-0036 一致，**不伪造过程**；历史确认事实不经占用行，直接以「已转实」之后的形态追加。
- **结论**：C 最自然；B 可行但多一个迁入入口；A 与 ADR-0047 迁移方案冲突。老系统 A8 来源「同步时整批重灌」（ADR-0016:28）意味着历史行可能被覆盖过，迁入对账口径**待取证** E6。
- **迁入两种拒收告警的拟定处置（由财务与 one-data 定）**：迁入遇到下面两种情形一律先拒收并告警，不静默跳过、不自动修正（项目规则 6）；拒收之后如何处置是**待定**，下面各列两种选项，不预设哪种：
  1. **退回行 `origin_code` 匹配不上原行**（老系统 434 行退回以 `origin_code` 指原单，ADR-0016:30；原因可能是 A8 整批重灌后原行被改写，取证 E2、E6）。
     - 选项 a：补出原行后再迁入，退回行按冲销关系挂到补出的原行；
     - 选项 b：财务书面认定后，作为「无来源引用的冲销事实」迁入，`reverses_id` 可空并标例外。**这是迁入专用例外，与 ADR-0024 第 4 条「原行与反向行双向关联」冲突，须用户知情后才能采用**；
     - 财务也可认定作废并记录。无论哪种，结果写入拒收清单与迁入批次对账。
  2. **历史行超 INV-22 额度**（某条款历史累计确认额超过条款金额；取证 E10：条款被调减或历史数据本身超额）。
     - 选项 a：财务判定条款金额当时有变更，补登协议基线版本后重迁；
     - 选项 b：财务判定为历史错误，在迁入批次内单列例外清单，经财务批准后带例外标记迁入（与 AGG-45 历史合同「迁入标例外」同类，聚合稿 :181）。不削减金额、不放宽 INV-22。
  - 两种拒收的数量由取证 E1、E2、E10 给出；验收口径（拒收清单清零或全部有书面处置）由 one-data 与 W3 迁入演练确定。

## 9. 阻断关系的更新（对计划第 6 节）

- 计划 6a「可先行」各项不变。
- 「必须等」中的 ADR-0049 第 4 条期满待办载体：本研究结论是**与 Q-04 无关**（投影 + 平台待办，A、C 通用；B 也可用），可从「必须等」移到「可先行」，交 one-architecture 确认。
- AGG-44 确认事实字段（证据引用、证据类型、认可日、配置版本、金额、`reverses_id`、来源与迁入批次、迁入例外标记（仅迁入行，见 S10）；不含「视为同意判定」，见第 0 节 J4）与占用行字段（金额、审批实例 ID、占用状态）：除 A 以外的选项字段基本相同，差别只在放 AGG-44 还是独立聚合、确认行自己是否带状态。
- **「先按 B1 轻量设计、日后提升为聚合根」的代价与 W3 时点对照**：
  - 代价：提升时要做一次表结构与仓储重构（确认行拆出为聚合根、占用改跨聚合先占后写、补孤儿占用定时释放与对账、状态转换改为只追加实现），并修订 ADR-0016 决定 4；已落库的确认数据要迁移到新表。
  - W3 时点：施工方案 W3 含 B-08 开票与收入（`CONSTRUCTION_PLAN_DRAFT.md:178`），B-08 预计 2027-04-17 至 2027-06-08（`:440`），W3 在 2027-01-28 至 2027-07-22（`:406`）；W3 同时要做全部历史收入确认 19,869 行与 434 行退回的迁入（`:229`）。提升若发生在 W3 之后，等于迁入数据再迁一次；若在 W3 迁入演练前完成，则只是 dev 上的重构。所以 B1 日后提升的窗口是 W3 迁入演练之前，之后代价陡增。
  - 对比 C：C 的确认事实不可变、不带状态，日后若要提升为聚合根，确认事实表可原样保留，只补申请与占用的拆分，代价低于 B1；但 C 日后提升为聚合根同样要修订 ADR-0016 决定 4（聚合带状态已超出「细化」）。
