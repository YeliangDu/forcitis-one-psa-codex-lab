# 人员入职到账号开通：身份生命周期研究（取证结论，供 ADR-0039 第 3 条 C1 设计）

状态：评审中｜2026-10-16｜负责：one-architecture

- 起因：用户 2026-10-15 备注「我们的人员从入职到有企业微信是有时间差的，招聘入职是hr的业务过程，企业微信是it的业务过程，有前后顺序」（intent 2026-10-15-164527）；one-coordinator 排期由 one-architecture 研究并设计 C1。
- 取证：2026-10-15，sonnet 子代理经 `one_evidence_ro` 只读（ADR-0037），登记见 `phase1a/infra/LEGACY_READ_REGISTER.md` 末行；只取汇总，无明细与个人信息。来源：A8 `ORG_MEMBER`、`ORG_PRINCIPAL`、人事档案表单；老系统 `system_users`、`system_login_log`（日志自 2024-08-14）。

## 结论（汇总数）

| 问题 | 结果 |
|---|---|
| 入职到各节点（近 24 个月入职 169 人） | A8 人员记录、HR 档案、老系统用户都在入职当天或更早建立（中位数 0 天）；首次企业微信类登录中位数 0 天、P90 1 天，超过 7 天的 5%（最长 178 天） |
| 当前在职（304 人） | 无企业微信 userid 0 人；无 A8 登录名 0 人 |
| 顺序反常 | 有企业微信却无 HR 档案 0 人；企业微信登录早于入职 1 人（早 4 天）；HR 提前建档 3 人（最早早 4 天） |
| 口令兜底 | 近 24 个月入职者 45 人（27%）用过口令登录，8 人首次就是口令，随后 0–15 天转企业微信；在职者近 180 天 135 人用过口令 |
| 离职回收 | A8 的企业微信 userid 离职后基本不清空（近 24 个月 170/174 保留），登录名都清空；老系统软删延迟中位数 3 天、P90 10 天；15% 的离职者在离职日后仍成功登录（最长 100 天，其中 5 人用口令）；企业微信账号何时停用，两库都看不到 |
| 老系统新人怎么登录 | 建号时没有企业微信 userid（晚一轮同步才写入），用户名取手机号或工号、统一默认口令；企业微信 H5 只按 userid 找人且不检查状态（`SyncServiceImpl.java:315-322、349-352`，`AdminAuthServiceImpl.java:115-131、593-604`） |

局限：企业微信 userid 只有当前值，「可用时间」用首次登录近似（是上界）；日志类型 105 含其他免密入口；无 2024-08-14 前日志。

## 对 C1 设计的含义（待做成确认页交用户）

1. 时间差很小、在职无缺口：联合身份不必为存量设计「无企业微信」模式，但要给入职首日到账号开通的窗口留一条兜底（候选：致远单点、一次性开通凭证、由 HR 入职事件预建外部身份待绑定）。
2. 老系统的「手机号 / 工号 + 统一默认口令」兜底不能带入新系统（SECURITY_INVARIANTS）；需要明确替代。
3. 在职判断以 HR 离职（或 A8 登录名清空）为准，不以企业微信 userid 是否存在为准；离职即吊销会话（RULE-363 已定）。企业微信停用时间需向 IT 要数据或接通讯录事件才能量化。
