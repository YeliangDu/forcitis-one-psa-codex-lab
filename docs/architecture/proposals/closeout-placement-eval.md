# 项目结项编排放在哪里：独立流程模块还是平台流程能力（评估，提议稿）

状态：历史记录｜2026-10-16｜负责：one-architecture

- 起因：用户问「全系统只此一个流程编排，这个不应该在平台 BC 的流程能力？」
- 范围：只评估 `delivery.closeout`（B-29）的位置，不改任何稿件。行号以 2026-10-16 本次读取为准；聚合稿与 ADR-0051 草稿另有修订人在改，行号可能漂移。
- 依据脚本：`aggregates_dep_check.py`（退出码 0，142 条边、L0–L14）；跨 BC 流程计数用 scratchpad 临时脚本，计数时读取了 `processes.v1.yaml` 与聚合稿 §2.2 的聚合归属，脚本不入仓库。

## 0. 先澄清两点

1. **(a) 本来就跑在平台流程能力上。** 结项审批走 `platform.approval`，B-29 只实现审批钩子（`ENTERPRISE_AGGREGATES_DRAFT.md`:983「提交结项申请（经 `platform.approval`，编排方实现审批钩子…）」；`processes.v1.yaml`:339）。(a) 与 (b) 的区别只在一处：**由谁把五项检查组合成「能否结项」**。(a) 由一个业务流程模块组合，(b) 由平台按注册表组合。
2. **「平台不依赖任何业务 BC」现在已经不成立。** 已建依赖中有 `platform.approval -> organization.workforce, organization.attendance`（`backend/architecture/module-dependencies.txt`:11）。另有 ADR-0036 已采纳的 `platform.migration`：它是无表的编排模块，依赖各目标 BC，任何模块都不依赖它（`docs/adr/ADR-0036.md`:46；`ddd/contexts.yaml`:445-455 标 `kind: platform`）。所以「只此一个」只在业务侧成立，平台侧已有一个同形态的先例。

## 1. 同一模式在 ⑥a 清单里有多少

判据：编排方先读多个上游 BC 的前置条件，再调一个**不属于自己**的上游聚合的命令（聚合稿 :60「下游编排」、:801 规则 3）。

- `processes.v1.yaml` 共 82 个业务流程，40 个触及 owner_bc 以外的聚合。其余 39 个都是「本 BC 写自己的聚合，读上游参考数据」或「来源 BC 提交应付、预算占用」，属于 BC 内应用层编排，与本题无关。
- 真正符合判据的只有：
  - PRC-36 结项（B-29；读 B-05、06、08、11、28，写 B-04 AGG-19；`processes.v1.yaml`:328-341）
  - PRC-101 月结检查并关账（B-17；读 B-16、19、20，写 B-19；INV-100，聚合稿 :210、:618）
  - 弱一档：PRC-66（B-08 只读自身，下游调 B-05「完成协议」；`processes.v1.yaml`:632，G-07）。
- 聚合稿标「下游编排」的不变量只有 INV-40、INV-100 两条（:135、:210）。
- **(b) 若成为通则，最多迁 2 个流程（PRC-36、PRC-101），连上 PRC-66 是 3 个。** PRC-101 的编排方 B-17 自有聚合，迁走后关账逻辑会被拆成两处；它是否适用 (b) 还要另行论证。

## 2. 平台职责会不会膨胀

- 已采纳的约束：
  - 流程只编排人，不计算业务，不查业务表，不在脚本任务里写业务逻辑（`GUIDING_PRINCIPLES.md`:55-66）。
  - BPMN 只用可执行流程（ADR-0041 决定 1，`docs/adr/ADR-0041.md`:21）。
  - BPMN「只编排人工步骤、超时与退回，不做业务计算」（`docs/architecture/frameworks.md`:33；`FRAMEWORKS_V4_DRAFT.md`:135）。
  - ADR-0039 把外部概念限定在 `platform.integration`，并把 approval 契约中性化（`docs/adr/ADR-0039.md`:47）。
- **结项前检查是业务规则，不是编排。** INV-40 的三项拒绝来自 Q10，两项预警来自 P-16；收入覆盖的「结论」载体待 Q20 定；Q09 状态机未定时有专门处理（聚合稿 :135、:974-984）。哪些项拒绝、哪些项只预警、缺项怎么处理，都是业务口径。
- (b) 下这些口径没有业务归属。可能的落点有两个：
  - 平台按注册表合成结果，并区分拒绝与预警：业务逻辑进了平台，违反 GUIDING §4。
  - 必需检查清单写进 `.bpmn20.xml` 的节点属性：业务规则进了平台资源目录，而按 GUIDING §4 第 3 条，BPMN 文件放在 `platform.approval`。
- 现有扩展点不够用，平台 api 须扩：
  - `ApprovalHook` 一个节点只挂一个键，重复键会让启动失败（`ApprovalHook.java`:3；`HookGate.java`:24-25、:31-37）。(b) 需要「一个节点挂多个检查、结果分拒绝与预警、能出检查单快照」。
  - PRC-36 第 2 步「发起结项检查」是审批前的无状态试算（`processes.v1.yaml`:337），不是审批任务。(b) 下平台还得新增一种「前置检查服务」。
  - 两项合起来，就是给平台新增一种通用的业务前置条件能力。

## 3. 检查分散后怎么集中呈现、怎么测试、漏注册怎么防

| 项 | (a) 独立流程模块 | (b) 平台扩展点 |
|---|---|---|
| 集中呈现 | 由 B-29 组装检查单（拒绝 3 项 + 预警 2 项），经 `platform.audit` 留痕；界面读 B-29 的 api | 由平台组装注册结果，检查单 DTO 定义在平台 api；或另做 `reporting` 读模型（有延迟，不能当闸门） |
| 测试 | B-29 的模块测试替换 6 个上游 api 的假实现，只断言本模块（CS-5.5）；各 BC 只测自己的查询 api | 各 BC 测自己的检查实现（契约测试）。「五项都齐才能结项」不属于任何一个模块，只能放全应用集成测试 |

## 4. 与 ADR-0041、FRAMEWORKS、方向规则是否冲突

- (a)：不冲突。BPMN 只画结项审批这一段人工步骤；检查在 Java 中，留在审批流程外；方向符合规则 3（编排方在全部被检查方下游，聚合稿 :801）。
- (b)：
  - 字面上，依赖边全部指向平台，不成环。
  - 实质上，项目能否结项取决于下游状态，这正是规则 3 要求「放在下游编排」的情形；(b) 把这层下游关系藏进平台回调。
  - 若必需清单与拒绝 / 预警语义写进 BPMN 或平台代码，与 GUIDING §4、FRAMEWORKS :33「不做业务计算」有张力。
  - 按 ADR-0041 决定 6（:29），(b) 属于架构选型变化，须先做适配研究，决策页写明代价。

## 8. 确认页题目草稿

**题干**：项目结项的「五项检查（三项拒绝、两项预警）合成能否结项」放在哪里？两种做法下，结项审批都跑在平台审批上；你在 D-9 选了 a（独立流程模块）。本题若改选，等于改 D-9。

- **(a) 保持 D-9：独立流程模块 `delivery.closeout`，单列为 `kind: process`。** 由它调 5 个 BC 的查询 api 组合检查单，并实现审批钩子。
  - 代价：多一个无聚合模块，有 8 条边，位于 L14；FRAMEWORKS 须新增 `kind: process` 一类。
  - 收益：INV-40 的拒绝 / 预警口径有唯一归属；漏项在编译期可见；平台不碰业务规则；与已采纳的 `platform.migration` 同一形态（ADR-0036）。
- **(b) 并入平台流程能力：取消模块。** 由 B-04 发起结项，5 个 BC 各自经平台注册「结项前检查」，平台合成结果。
  - 代价：
    - `platform.approval` api 须扩展：多检查挂一个节点、拒绝与预警分级、检查单快照、审批外的试算服务。
    - INV-40 口径要么写进平台，要么写进 BPMN 资源，与 GUIDING §4「不计算业务」有张力。
    - 漏注册只能在运行期发现，须另加守护。
    - 「五项齐备」只能放全应用集成测试验证。
    - 改选 D-9，ADR-0051 草稿、聚合稿、PRC-36、PR #339 都要跟着改。
  - 收益：少一个模块，少 7 条边；通则化后最多再迁 1–2 个流程（PRC-101、PRC-66）。
- **(c) 保留模块，检查改由各 BC 实现 B-29 定义的检查接口（倒置在 delivery 内）。** B-29 保留必需清单与拒绝 / 预警口径，启动时核对清单齐全。
  - 代价：5 个 BC 反向依赖结项模块；层位有变动，须先试算；比 (a) 多一套扩展点机制。
  - 收益：各 BC 自己定义「本 BC 什么算已结清」，加检查项时不改 B-29。

**推荐 a**，把握中上。理由：
1. 这种模式全系统最多 2–3 处，不值得为它给平台加一种通用业务前置能力。
2. 结项检查是有出处、有待定项（Q20、Q09）的业务规则，需要一个业务归属。
3. (a) 已经用平台审批承载人工步骤，用户担心的「编排不在平台」并不成立。
4. 用户觉得它不该算 BC，这一点由 §7 的单列 `kind: process` 解决。

残余不确定：PRC-101 关账若将来也拆成同形态，会出现第二个流程模块，那时值得回头看 (c) 或 (b) 是否通则化。
