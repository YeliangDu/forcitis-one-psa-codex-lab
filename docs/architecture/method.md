## 1. 一句话与总图

先问**谁**（干系人）要什么价值（价值流），再找出**承载这些价值的业务对象**及其状态与规则，用对象状态写**阶段门**；然后由**不变量**定聚合、由**统一语言**定 BC、把引用按**依赖方式**连成无环的图，列出全企业的流程目录、铺开骨架并生成描述级图，再按建造批实现可执行流程、数据与分析，统一投产并守护（通用审批先行局部上线仅按 ADR-0054 决定 1）。各层只回答自己的问题，靠「对象的状态」与「稳定编号」连起来。

```
① 干系人 → 价值流（骨架先定稿）
② 业务对象（信息图）──生成──▶ 按对象命名的能力图（视图 + §8.6 查漏）
③ 阶段门 = 对象状态（可回退、跳过、重入；门只预警）；能力—阶段对账
④ 规则 → 不变量（A / B / C）→ 聚合 · 命令 · 事件
⑤ 聚合 → BC（统一语言）→ 依赖边（api / 事件 / 不校验）→ 查环、分层 → 命名空间
⑥a 全企业流程目录（唯一登记；按事件与聚合判类，映射价值流阶段）
⑥b 流程图、数据与分析：全企业骨架与描述级图；可执行版、数据与分析按建造批实现
⑦ 一次投产路线 · ADR · CI 守护：全企业设计；W0–W5 建造验证；统一投产
```

**三条优先级规则**
1. 已采纳、有证据的不变量 ADR（如 ADR-0016 单一过账管道、期间闸门、WIP 与开票同一事务）约束任何推导结果，反之不成立；推导结果与之不同时，新开 ADR 并附新证据。【推出】（ADR-0041 决定 3）
2. 依据主次：AEC 项目制专业服务行业的通行做法（法规、合同范本、准则、成熟产品）为主，用户业务事实定夺，老系统与生产数据只作参考与核对；确需复刻的老行为仍以生产数据为证据（CLAUDE.md 第 4 条）。规则卡经用户评审，按用户业务事实对待，不降为参考。【已定】（intent `2026-10-15-202634`）
3. **业务内容以手册为准，结构以框架为准**：阶段叫什么、有几段、门的业务含义，取公司手册与行业做法；它们落到哪种建模概念（价值流阶段、对象状态、WBS 节点、参考数据、策略），按 FRAMEWORKS 的结构判。**只适用于建模概念的落点**，不改手册的业务叫法与内容。例：手册售前 BD0、BD1 落为商机的阶段（`STAGE_TYPES_DRAFT.md` §3）。框架之间冲突时按 FRAMEWORKS 第 0 节：G178 与 BIZBOK 冲突以 BIZBOK 为准【已定】（intent `2026-10-15-222350`）；写成通用规则【已定】（intent 072440 M-2；由 `STAGE_TYPES_DRAFT.md` §3 的做法归纳，intent `2026-10-16-053630`）。

**范围规则**：①–⑦ 的架构设计覆盖全企业（ADR-0054 决定 2），⑥b 的全部业务流程骨架与描述级图在架构收尾期铺开；人工编排的可执行版、数据承载与分析实现按 W0–W5 建造批交付，生产按 ADR-0054 决定 1 统一投产，通用审批先行局部上线仅按该决定的唯一例外。规划与实现状态分别登记，CS-1.8 限制实现范围，不禁止已认可规划进入 SSOT。BC 清单以 ADR-0051 为准；规划边与聚合含 Q-11 认可内容，随整合确认包 D 册、路线随 T 册经用户确认后写入（ADR-0054 迁移第 2 步，intent `2026-10-17-112814`），不得只登记在建部分。流程目录与对应骨架经评审、按价值流获用户确认后同批进入 `architecture/bpmn/`，描述级图为生成物；未确认内容仍留提议稿（ADR-0052 决定 5–6）。

### ① 干系人与价值流

- **做什么**：干系人按 类型（内 / 外）→ 类别 → 具体干系人 列出，标与价值流的关系（触发 / 参与 / 接受）（BIZBOK §2.8）。按触发干系人列价值流，四要素：名称（触发者视角、动宾）、描述、触发干系人、价值（G178 §2.1）。阶段此时只列名称，进出条件留到 ③。
- **规则**：
  - 不拆子价值流；跨价值流只经对象状态衔接（一条价值流的结果落在某对象的某状态上，另一条价值流的触发或进入条件引用该状态，不写「A 触发 B」）。G178 对这两点未作规定，按 BIZBOK【推出】（intent `2026-10-15-222350` 冲突规则；`2026-10-15-222319` 纳入 BIZBOK 价值流）。先外部后内部（G178 §3.1，与 BIZBOK 不冲突）。
  - **子阶段**（BIZBOK §2.4，第 153–154 页）：价值流阶段可再分子阶段，但只在子阶段处有明确的阶段门，或需表达不同业务单位的差异场景时才用；子阶段同样要有名称、定义、进出条件、价值项与参与干系人；没有明确的门就不拆父阶段。这与「不拆子价值流」是两件事：子价值流（价值流的拆分）不用，子阶段（阶段的拆分）按此条件用。手册的「工作子阶段」是服务产品版本内的模板，立项时生成 WBS 子项或工作包（`STAGE_TYPES_DRAFT.md` §3），默认落为 WBS 节点，不是价值流子阶段；某个工作子阶段若确有独立的门、其进出条件能写成对象状态，才升格为价值流子阶段，在 ③ 逐个说明【推出】。
- **输入 → 交付物**：`proposals/STAKEHOLDERS.md`（用户已给）→ `business/value-streams.yaml`。原 `togaf/value-streams.yaml` 是 ADR-0041 前的参考草稿，已退役（GOV-1023-ARC-01）（含「阶段由能力支撑」「exit 即事件风暴候选」等旧口径），按本步重写【裁量】。
- **谁定 / 校验**：用户；每条价值流有明确的触发干系人（可多个）；不拆子价值流；跨价值流只经对象状态衔接；每个类别都有归属价值流或写明不建，否则只作阶段参与者。
- **本轮示例**：干系人取自用户指定的本地文件中的干系人部分（intent `2026-10-15-213742`）；逐个干系人核对对象时，发现了只从客户维度会漏掉的检查与证据线（资本方、既有建筑业主委托的技术尽调、IDI 检查），用户决定纳入（intent `2026-10-15-213845`）。**未完成**：价值流骨架尚未单独定稿交用户（回补顺序第 1 位，§1.1）；已做阶段门走查的价值流见 `ENTERPRISE_AGGREGATES_DRAFT.md` §4.3–§4.3.4，其余价值流的阶段门尚未写实。

### ② 业务对象与范围

### ④ 不变量、聚合与事件

- **做什么**：
  1. **规则四分**：不变式放聚合；判定（路由、资格、级别）暂放版本化配置表或代码（DMN 推迟）；人工编排放 BPMN；计算放值对象或领域服务；信息图里的「警」是**策略**，不是不变量【推出】（ADR-0041 版 METHOD 接缝 1）。
  2. **不变量三类**【推出】（第 3 稿评审 B3 的改法；ADR-0016 决定 5；DDD Reference 聚合一节——聚合内同步一致、聚合间最终一致，第 3 稿评审核对为第 16 页）：
     - **A 单聚合**：一个聚合实例内、一个事务内成立；聚合根方法守护。
     - **B 集合约束**：同类型多个实例之间的唯一、不重叠；用唯一约束、部分唯一索引或排他约束实现（§14.1 D2），不为它扩大聚合。
     - **C ADR 认可的多聚合同事务**：已采纳 ADR 明文要求一个事务修改两个聚合；登记 `multi-aggregate-exceptions.txt`，`SingleAggregateGuardTest` 守护。
     每条不变量有且只有一个守护落点。
  3. **跨聚合前置检查不是第四类**：命令方在执行前按 ID 经 api 读另一个聚合，只写自己。两种：一般前置（读写不同事务，竞态由策略兜底）；同事务读锁（读方在自己的写事务内对被读行加共享锁，被读方状态转换须等待）【裁量】。
  4. **下游编排**：凡要读的对象在依赖图中位于下游，改由下游流程查齐条件后调上游命令，上游不读下游【裁量】。
  5. **额度占用模式**：「多张单据合计不超过某个额度」的累计约束，额度与占用行放在一个额度聚合内；申请方先占用（一个事务、只改额度聚合、乐观锁防超占），拿占用 ID 再写自己的单据；驳回、作废、终止时释放；孤儿占用由定时释放与对账兜底。这是 A 类的一种实现模式，不新增 C 类【裁量】。
  6. **对象—聚合对应**写明五种之一：一对一、次级在内、一拆多、无聚合（外部引用、派生值）、技术聚合（信息图无对应对象，只为守住不变量而设；期间性批处理的结果称运行单据）。**对象 ≠ 聚合**：BIZBOK 管对象层，DDD 管聚合层【推出】（FRAMEWORKS 第 0 节）。一拆多的判据：状态机不同、负责的干系人不同、不变量不同【已定】（intent `2026-10-16-112800` L-2；写成方法规则，进最终 ADR；第 3 稿评审 H6 建议）。
  7. **两层映射**【已定】（intent `2026-10-16-112800` L-1；出自第③步回溯 R-02 实践；（第④步评审））：阶段门在 ③ 引用业务对象状态；在 ④，每个对象实例（一拆多按类型或方向分别计）的该状态映射到恰一个聚合的存储状态，或一个派生值（注明在哪个 BC 计算，对应第 6 条「无聚合（派生值）」）。判据：上游聚合自身不变量要用到的状态（如协议「已结算」的前置条件「已完成」），由下游编排按第 4 条调用上游命令写回，命令携带下游给出的依据并在上游校验前置；其余由下游累计决定的状态（如履约义务「部分履行 / 已履行」）只作派生值，不写回上游；阶段门不引用派生值。同一事实不得一份存储一份派生；若存储状态以派生值为依据（AGG-13「已完成」以全部履约义务「已履行」为依据），派生值是依据、存储状态是上游的独立决定，二者差异列入对账报告。
  8. **事件**：每个事件由一个聚合发出，写明业务订阅方；分析库（`reporting`）订阅也算订阅方，无业务订阅方的事件保留，聚合稿事件列标「仅分析」【已定】（intent `2026-10-16-114200` F-4；ADR-0023 决定 2；订正：原标「现行 METHOD 接缝 2」有误，ADR-0041 版接缝 2 无「没有订阅方的事件不预先命名」一句）；经济事件复审 REA 两个问题。

### ⑥a 全企业流程目录

- **判据与四个去处**：业务流程同时满足三条：①由业务事件或人的业务决定触发；②跨两个以上聚合，或跨两个以上角色并有交接；③结果是某价值流阶段的进入或退出状态（ADR-0050 决定 15，ADR-0052 决定 5 保留）。不满足的分别归事件策略（一个事件、一步命令）、单聚合维护（第④步状态机）、读模型（只读无命令，归 `reporting`）、已合并（同一业务链合并，保留被并入编号的去向），不计入业务流程数；目录登记五类，流程与价值流阶段多对多（BIZBOK §3.4）。
- **唯一登记**：编号、名称、类型、阶段、编排 BC、组、状态只手写在流程目录，所属阶段为 `stages`（可多个）；骨架与图只引用目录编号。计数与目录页由目录生成；目录仅引用可执行实现登记，不复制 `ProcessKey` 或指派（ADR-0052 决定 1–2）。
- **交付与确认**：目录在 `ssot/09-processes/catalog.yaml`（2026-10-23 起；此前提议期在 `proposals/closeout/process-catalog.yaml`），骨架在各组 `proposals/closeout/<组>/`。每个价值流铺开并评审完成即出一页，只列业务判断与待定题（AN-02，提交 `ANM-20261017-075455-3xc`）；用户确认后，该价值流条目的 status 改为 user_confirmed，对应骨架进入 `ssot/09-processes/`，按价值流逐个进；ADR-0053（ADR-0052 决定 5–6）所写的 `bpmn/` 路径按 `ssot/PATHS.md` 读。
- **用语**：业务流程用 BIZBOK / BPMN 含义；Kimball 总线矩阵的行称「度量事件」，用语以词表为准。
- **校验**：每个价值流阶段有流程或明确无需系统支持；每个业务流程有触发，改变系统状态的步骤对应某聚合的命令；`processes_check.py` 按 ADR-0052 决定 6 改读目录与骨架，事件订阅覆盖判据保留，后续工具卡交付前不声称已覆盖新输入。

## 4. 迭代、回溯与对抗检查

- **迭代**：后面的步骤发现前面的缺口时回到前面修正（③ 阶段门指不到对象 → 回 ②；③ 能力—阶段对账有孤立能力或无能力的阶段 → 回 ② 查漏；⑤ 发现同名异义 → 回 ② 拆概念；⑤ 查出环 → 回 ④ 改依赖方式或聚合归属）。

- **每步对抗检查**（用户 2026-10-15「只有一个阶段值得对抗检查吗」，见第 3 稿 §4；【推出】）：外部事实另派代理复核出处，查不到标「未核实」；生产取证抽查口径与计数；判断与推导由 opus 对抗评审（首轮），改后由 sonnet 复核（用户额度要求，记忆「子代理额度策略」）；用户给定的事实与决定只查一致性；整条链 opus 评审 + 回溯。确认页上的每条建议须注明是否已过对抗评审。
