# ADR-0035：契约演进与兼容

- **状态**：已采纳（用户 2026-10-15：「批准 (Recommended)」，intent `2026-10-15-082825-one-coordinator-ADR-0035-契约演进与兼容.md`；此前对 DDL 审计、原则核对 A / B 其余待决项答「全部按推荐 (Recommended)」，评审后对生效时点答「首次生产部署时生效 (Recommended)」）（第 2 条「首次生产前可直接改契约」对平台模块与 kernel 部分已被 ADR-0067 取代：W0 结束起冻结平台契约，改动须经审批，用户 2026-10-21 批准页 P2）

## 决定

1. **契约面**：以下五类都是契约，适用本 ADR：
   - OpenAPI（全部 `/api/v{n}/…` 接口）；
   - 领域事件（`events` 包的 record、序列化后的 JSON 形状、事件目录 `docs/architecture/events/*.yaml` 与组合出的 `asyncapi.yaml`、发布登记中的类型）；
   - 分析数据集（`reporting`、`reporting_compat` 与 `mirror_*` 的视图与列）；
   - 出站负载（对外部系统的投递）；
   - 兼容门面（ADR-0011 第 3 条与 ADR-0008 后果：老 URL 由兼容门面承接、返回老格式）：按外部消费方处理，形状以老系统现行格式为准，不随新接口演进；随老前端下线整体删除，删除前按第 7 条登记弃用。
   - **入站回调不是我方契约**：外部系统回调本系统的格式由对方定义。我方适配器容忍对方的兼容变更——忽略未知字段；未知枚举取值失败并告警，不静默丢弃；对方的破坏性变更按集成登记册（SESSION_PLAYBOOK §14.3）另行处理。
2. **生效时点**（用户已定：「首次生产部署时生效 (Recommended)」）：
   - 首次生产部署之前（含 dev 已部署、基线开放标记已删除的阶段），契约可直接改，不需要兼容过渡与弃用期；仍须契约先行（OpenAPI 与文档同一提交更新），并受第 8 条「契约如实」约束。dev 环境的在途事件由 one-ops 在部署时清理（未完成发布与死信），不设排空守护。
   - 首次生产部署起，第 3–7 条与 G-C1、G-C2、G-C3、G-C6 生效。
   - dev 期生效的守护只有两条：G-C4（第 8 条契约如实，随 H-1）与 G-C5（第 5 条第 3 款负载扁平、ID 字符串，随 R-1b），按「迁移方案」的时点生效。
3. **什么是破坏性变更**：
   - HTTP：删除或改名路径、方法、字段、枚举取值；改字段类型或格式；请求字段由可选改必填，或新增必填的请求字段、请求头；响应字段由必有改可选；收紧取值范围；改状态码或错误码的含义；改分页、排序语义。
   - 事件：G-C2 判定序列化形状有变化的一律算破坏性——删除或改名字段；改类型、格式或含义；改 Java 类名或包名（发布登记按类全名存类型，改名后在途与死信无法反序列化）；改 ID 形状。
   - 数据集：删除、改名或改类型的列；改粒度或口径。
   - 兼容变更：新增路径；新增可选请求字段；响应、事件新增字段；数据集新增列或新增视图。响应与事件新增枚举取值，对自家前端（宽容读取）是兼容变更，对外部消费方按破坏性变更处理，除非契约写明取值集合开放。
4. **HTTP 演进先扩后收**（用户已定）：先增加新字段或新路径，调用方切换后再按第 7 条删除旧的。只有存在仓库外的调用方（外部系统、外部脚本）时，才开 `/v{n+1}` 与 `/v{n}` 并存；自家前端与后端同版本发布，不开新版本。
5. **事件演进**（第 1、3 款为用户已定，第 2、4 款为本 ADR 新提议）：
   1. 兼容变更不升版本、不排空。
   2. **一条规则**：凡 G-C2 判定序列化形状有变化，本次发布按第 6 条的顺序排空后部署。旧形状的去除方式二选一，在 PR 中写明：(a) 同一类型 `schemaVersion + 1`；(b) 新的事件类型，旧类型在本次发布中删除。两种方式都以排空为前提，不保留旧形状的读取代码。
   3. 不写 upcaster（旧格式到新格式的转换器）。负载一律扁平：ID 为字符串 uuid（ADR-0033 第 6 项第 2 条；`NAMING_STANDARD.md` §2.6 A-7），不出现 `{value: …}` 包装；同样适用于出站负载。
   4. 改事件 record 的类名或包名按破坏性变更处理：本次发布排空后部署，与形状变化同一规则。
6. **排空与回滚隔离**（本 ADR 新提议）：
   - **维护模式**：只停写请求（返回 503 并提示维护中）与业务类定时作业；事件投递与重投作业照常运行，排空才能进行；读请求照常。状态存放在库内一行标记（`platform_scheduling.maintenance_modes`，`platform.scheduling` 拥有；写请求过滤器与业务类定时作业读取），由 one-ops 部署剧本开关，开关写审计。
   - **部署顺序**：开启维护模式 → 等待未完成的事件发布为 0、死信为 0 → 停机 → 部署新版本 → 关闭维护模式。G-C3 在开启维护模式之后检查，不满足即中止部署、关闭维护模式恢复服务。
   - **隔离登记**：`platform_integration.event_quarantines`（`platform.integration` 拥有，与事件发布登记同 schema；运维命令属 one-ops 部署剧本）。排不空的发布（反复失败进入死信）由运维命令移入：保留原负载、类型、关联号与部署批次，在发布登记中标为已完成。正向部署与回滚都可使用：
     - 正向部署：旧版本写入、新版本读不了的死信移入隔离登记后再部署，由修复后的消费方或人工处理；
     - 回滚：回滚到旧版本前同样先开启维护模式并排空，新版本写入、旧版本读不了的移入隔离登记，再回滚；修复后的新版本上线时从隔离登记重新投递。
     - 隔离登记清空，本次部署或回滚才算结束；不让任何版本读取它读不了的格式。
7. **弃用**（期限为用户已定，登记与期限写法为本 ADR 新提议）：
   - 要删除的接口、字段、事件或数据集列先标为弃用：OpenAPI `deprecated: true`、事件目录弃用标记，并登记在弃用登记（`backend/architecture/deprecations.yaml`：对象、弃用日、消费方类别、到期条件、出处）。
   - 响应头 `Deprecation` 与 `Sunset` 只对外部消费方使用的接口设置；自家前端不需要。
   - **到期条件**：
     - 只有自家前端调用的：弃用后的下一次生产发布即可删除（已打开的旧页面在一次发布后刷新即换新客户端）；
     - 有外部消费方的（含兼容门面、分析数据集、出站负载）：满 90 天或与对方书面约定的期限，**且**消费方书面确认已迁完，两条都满足才可删除。
   - 到期后删除已登记的对象不算未经弃用的破坏性变更（G-C1 放行）；到期未删由 G-C6 提醒，不拦无关 PR。
8. **契约必须如实**（用户已定 dev 期保留；本条内容随 `NAMING_STANDARD.md` §2.6）：OpenAPI 与运行时一致——创建返回 201 并带 `Location`；修改类接口声明必填 `If-Match` 及 412 / 428；读取声明 `ETag`；状态、类型字段是具名枚举；没有无类型的响应体（不出现 `*/*`、无 schema 的响应）；`info` 的标题、版本与说明正确。由 G-C4 检查（G-A3、G-A4 并入）。
9. **兼容性检查**（用户已定自写脚本）：
   - G-C1 `scripts/ci/openapi_compat.py`：与 merge-base 的 OpenAPI 比对。读取弃用登记：已登记且到期条件满足的删除直接放行；其他破坏性变更即失败，只能用提交 trailer `Contract-Break:` 写明理由与迁移安排放行，复审核对，并在 PR 描述中单列。
   - G-C2：把 `docs/architecture/events/asyncapi.yaml` 中各消息的负载 schema 与 `x-event.class` 和 merge-base 比对（AsyncAPI 形状比对），按第 3 条判定；判定为破坏性的要求第 5 条第 2 款二选一之一，并把本次发布标为「需排空」供部署剧本读取（G-C3）。
   - 不引入 Pact 等消费者契约框架。消费者契约测试只用于外部消费方（分析数据集 G-C7、对外投递负载）。

## 影响面

- **OpenAPI 与前端**：ID 改为字符串 uuid 后，前端凡把 ID 当数字处理的地方都要改（随 R-1b）；契约如实修正（第 8 条）后重新生成前端客户端与校验器（随 H-1）。
- **事件**：以 `{value: …}` 序列化或带 int64 人员 ID 的事件改为扁平负载与字符串 ID（随 R-1b）；事件目录增加 `schemaVersion` 与弃用标记（随 G-C2）。
- **CI 与部署**：新增 `scripts/ci/openapi_compat.py`、事件目录比对与弃用登记检查；部署剧本增加维护模式开关、排空预检与隔离命令（one-ops）；新表 `platform_scheduling.maintenance_modes`、`platform_integration.event_quarantines`。
- **分析数据集与兼容门面**：R1 起按第 3、7 条与 G-C7 管理；兼容门面随老前端下线删除。
- **ADR-0008**：第 2 条中「破坏性变更发布 v2……」一句被取代；第 1、3 条、后果与 G20 不变。
- **文档**：`NAMING_STANDARD.md` §2.6、§4（G-C1–G-C7 登记，G-A3、G-A4 并入 G-C4）；提议术语「维护模式」「隔离登记」「弃用登记」（`backend/glossary/proposed/contract-evolution.yaml`，ADR-0018）；`proposals/PHASE1A_PLATFORM_CONVENTIONS.md` §2–3 已注明升格。

## 迁移方案

1. **R-1b**（基线开放期内）：ID 改字符串 uuid、事件与出站负载扁平化（第 5 条第 3 款），与自有 UUIDv7 改造同一批完成；G-C5 随 R-1b 实现。开放期内直接改，不需要兼容过渡。
2. **H-1 契约如实修正**（单独一张卡，排在 R-5 之后，不与 R-1b 同批）：201 与 `Location`、必填 `If-Match` 与 412 / 428、`ETag`、具名枚举、无类型响应体、`info`；同卡实现 G-C4（G-A3、G-A4 并入），合入即生效。与 R-1b 分开是因为两者都改大量控制器与生成物，同批会使 R-1b 的复审面翻倍；排在 R-5 之后是因为 R-5 统一通用错误码与错误响应，H-1 的 412 / 428 声明依赖它。
3. **首次生产部署前**：实现 G-C1、G-C2、G-C6，建维护模式标记与隔离登记两张表，把维护模式、G-C3 与隔离命令接入部署剧本；建立空的弃用登记。推迟到此时更有价值的理由：dev 期契约仍在快速成形、只有同版本发布的自家前端，破坏性比对只会产生 trailer 噪音而没有要保护的调用方；首次生产部署才开始有在途事件、外部消费方与不能清掉的数据。
4. 首次生产部署起第 3–7 条生效。
5. R1 引入分析数据集时实现 G-C7。

## 回滚方案

1. 本 ADR 未被采纳：ADR-0008 第 2 条保持原文，已登记的守护从 `NAMING_STANDARD.md` §4 删除。采纳后要改变决定：另立新 ADR 取代本 ADR 的对应条款，不恢复 ADR-0008 原句；已实现的守护按新 ADR 调整。
2. 守护误报：在提交 trailer `Contract-Break:` 中写明理由放行，并修正脚本；不放宽规则本身。
3. 事件破坏性变更部署后要回滚应用版本：按第 6 条「回滚」——维护模式、排空，排不空的移入隔离登记，再回滚；修复版本上线后从隔离登记重新投递。

## 需同步修改的守护规则

- 新增（登记见 `NAMING_STANDARD.md` §4「待实现的守护」）：G-C1 OpenAPI 兼容比对（读弃用登记）；G-C2 事件兼容（AsyncAPI 形状比对）；G-C3 部署前排空预检（维护模式之后）；G-C4 契约如实（扩展 `HttpContractIT`，G-A3、G-A4 并入）；G-C5 事件与出站负载扁平、ID 字符串 uuid；G-C6 弃用到期提醒；G-C7 分析数据集契约。
- G-C6 的判定：定时检查到期未删的弃用项，发 P3 提醒并报调度会话，不让无关 PR 变红；PR 中改动已弃用对象（删除除外）即失败——已弃用的对象只能删，不能再扩展。
- 修改：`EventCatalogueTest` 增加 `schemaVersion` 与弃用标记的登记检查（随 G-C2）。
- 不变：G20（控制器带版本前缀）、F5 / F10（只用生成的客户端）。
- 时点：G-C5 随 R-1b；G-C4 随 H-1；G-C1、G-C2、G-C3、G-C6 在首次生产部署前（理由见迁移方案第 3 条）；G-C7 随 R1。不在本 ADR 的 PR 中实现。

## 后果

- 自家前端不再需要多版本并存，接口演进靠先扩后收与弃用完成；dev 期改契约没有过渡成本。
- 外部消费方（含兼容门面）有明确的弃用期、确认迁完的要求与登记，删除有守护兜底。
- 不写 upcaster，事件模型保持简单；代价是事件形状每次变化都要维护模式加排空，部署窗口变长，回滚多一条隔离路径。
- 事件 record 改类名、包名也要排空，重构类名的成本与改形状相同；换来的是发布登记保持框架默认形态，不需要自建类型注册。
- 自写比对脚本只覆盖第 3 条列出的变更类型，需要用注入样例证明覆盖；未覆盖的类型靠复审。

## 备选方案（未采用）

- **保持 ADR-0008 第 2 条（破坏性变更一律发 v2 并存）**：自家前端与后端同版本发布，并存只增加维护面。
- **立即（dev 期）启用第 3–6 条**：dev 期只有同版本的自家前端，规则只产生放行噪音；用户已定首次生产部署时生效。
- **引入 Pact 等消费者契约框架**：单仓前后端已由生成的客户端保证一致；框架要引入新依赖与新流程，收益只在外部消费方，而外部消费方用第 9 条的契约测试即可。
- **写 upcaster 兼容旧事件**：每次变更都要写转换代码与测试；单体单库，部署前排空更简单可靠。
- **新事件类型与旧类型并存、不排空**：两套读取代码并存，回滚与死信处理更复杂；与「一条规则」相比没有收益。
- **用第三方 OpenAPI diff 工具**：要引入新依赖（SUPPLY_CHAIN.md），且规则（如弃用登记放行、trailer）仍需定制。
- **不设弃用期，直接删除**：外部消费方无法安排迁移。
