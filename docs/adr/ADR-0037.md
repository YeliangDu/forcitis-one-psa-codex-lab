## 决定

### 1. 读取范围

1. 迁移取证与应用运行时都可以只读 A8（`a8_db`）与老系统库（`ruoyi-vue-pro`）的任意表和列，含基表、元数据与凭据列。
2. 数据库授权按库级只读给出（PR #135 已执行的形状：库级 `GRANT SELECT`；库级 DENY 写、DDL、EXECUTE、REFERENCES；不加入任何数据库角色；A8 的基表元数据可见），不再随用途逐个对象、逐列收窄。

### 2. 保留的约束

1. **只读不写**：新系统不写 A8 与老系统库的任何数据、不改其结构；账号层面以库级 DENY（第一道）与启动校验（第 4 项，第二道，并正向断言第一道仍在）双重保证。
2. **防腐层**：外部读取只在 `platform.integration` 的适配器中（SESSION_PLAYBOOK §14 第 8 项、§14.1 D11、D16；ADR-0021 第 4 项第 4 条）；领域模块不出现外部表名、列名与外部取值。老系统待办读取按 ADR-0033 第 2 项第 9 条移入集成层，移入前 `platform.approval.infrastructure.legacy` 是现存的唯一例外，不新增例外。
3. **记录系统不变**：运行时读到的 A8 与老系统业务数据只用于取证、迁入、对账与新旧等价核对，不作为新系统权责事实的输入，不形成双源（ADR-0021 第 2 条、ADR-0024 第 3 条）。组织主数据同步仍按现有规则（6e 前 A8 为源）。机器守护：
   - ArchUnit：迁入、对账类适配器的端口只能被迁入、对账模块依赖，产生权责事实的业务模块不得依赖；
   - 对账结果表只存键、计数与哈希，不存来源值；需要存来源值时按 D13 分级登记，并在表结构评审中单列。
4. **外部取值映射**：外部状态码、类型码在防腐层映射为自有枚举，未知取值失败并告警，不静默跳过（D16）。
5. **列最小从授权层移到代码层**：
   - 应用每条读取语句只 SELECT 用到的列，不写 `SELECT *`；读取的表与列登记在读取列登记中（第 6 项第 1 条）。
   - 外部列的敏感级别写在读取列登记里（PUBLIC / INTERNAL / SENSITIVE / RESTRICTED，沿用 NAMING_STANDARD §2.5 的词汇），不写进 `data-classification.txt`——后者只登记自有 schema 的列，`DdlNamingTest` 要求登记的列在自有 DDL 中存在。迁入后落到自有表的列照常按 D13 登记在 `data-classification.txt`。
   - 敏感字段（生日、银行卡、薪酬与金额、证件号等）只在用到时读取，不进日志、事件与分析层明细。
   - 需要在库内过滤的敏感数据（如只取正常结束且同意的离职申请，`docs/business/rules/workforce-history-rules.md`:59），过滤条件写在读取语句的 `WHERE` 中，行不离开来源库。

### 3. 凭据类数据

1. 凭据类数据（老系统令牌表 `system_oauth2_*`、口令哈希、密钥等）可以读，不排除。账号凭据泄露时，持有人能读到老系统的有效令牌并冒充老系统用户（ADR-0009 第 6 条的原理由）；**这一风险由用户接受**（「全部可读，不排除」）。
2. 使用约束：凭据值不得进入新系统的任何表、日志、事件与会话记录，也不进入仓库与取证输出。
3. 新系统仍不写老系统令牌、不校验老系统令牌、不以任何方式信任老系统签发的身份（ADR-0009 第 6 条、ADR-0027 第 4 项第 3 条的其余部分）。
4. **凭据列拒绝清单**：
   - one-ops 用取证账号（第 5 项第 4 条）只读扫描两库元数据（`INFORMATION_SCHEMA.COLUMNS`，只取表名、列名，不取任何值），按 `DdlNamingTest.SENSITIVE_NAME` 中的凭据类词（`password`、`secret`、`totp`）加 `token`、`salt`、`hash`、`key`、`credential` 筛出候选（外部列名先转小写蛇形再匹配），人工复核后生成凭据列拒绝清单入仓（只含库、表、列名）。
   - 守护断言：`src/main` 的 SQL 文本与读取列登记都不引用清单中的任何列；`SecurityInvariantsTest.legacyTokenTablesAreNeverTouched` 保留（令牌表整表不引用）。以后若有用途需要凭据列，须另立 ADR。
   - 清单随 A8 / 老系统升级重扫；扫描登记一行（第 7 项）。
5. **异常不带值**：SQL Server 的类型转换等错误消息会带出字段值。集成层适配器出错时只记录错误号与 SQLState（以及适配器名、`correlationId`），不记录异常消息、不把原异常作为 cause 写进日志或向外抛出的异常 message。

### 4. 启动校验改口径（白名单判定）

1. 三个只读连接（A8、老系统待办、老系统部门简称；合并后两个）启动时做同一项检查，下列 (a)–(f) 任一不满足、或查询出错无法判定，都**拒绝启动**并报出违规项：
   - (a) **库级有效权限是白名单的子集**：`fn_my_permissions(NULL, 'DATABASE')` 的结果只能是 `CONNECT`、`SELECT`、`SHOWPLAN`、`VIEW DATABASE STATE`、`VIEW ANY COLUMN ENCRYPTION KEY DEFINITION`、`VIEW ANY COLUMN MASTER KEY DEFINITION`，A8 另加 `VIEW DEFINITION`。白名单以实现 PR 真实登录的输出为准，写死在代码里；B-5 README:48 实测还有 `ALTER ANY DATABASE EVENT SESSION`、`KILL DATABASE CONNECTION`（来自实例级授权），它们不是只读权限，**不进白名单**：one-ops 先对三个账号加库级 DENY 这两项，真实登录核实已从有效权限中消失；消不掉时停下报告，不放宽白名单。白名单的任何增项都要在实现 PR 中逐项写明只读理由并经 opus 复审。
   - (b) **第一道防线正向存在**：`sys.database_permissions` 中本账号库级（class=0）`DENY`（state='D'）至少包含 INSERT、UPDATE、DELETE、ALTER、EXECUTE、REFERENCES、CREATE TABLE、CREATE VIEW、CREATE PROCEDURE、CREATE FUNCTION、CREATE SCHEMA。库级 DENY 覆盖 schema 级、对象级与经自定义角色得到的 GRANT，正向断言它存在就覆盖了 (a) 看不到的下层授权。
   - (c) **不在任何角色中**：`sys.user_token` 中除 `public` 外没有任何角色（与第 1 项第 2 条一致；不列举「可写角色」）。
   - (d) **服务器层**：`fn_my_permissions(NULL, 'SERVER')` 是白名单子集（`CONNECT SQL`、`VIEW ANY DATABASE`，同样以真实登录为准、增项须逐项写理由）；对全部固定服务器角色 `IS_SRVROLEMEMBER` 都为 0（覆盖 `sysadmin`、`securityadmin` 等；`CONTROL SERVER`、`IMPERSONATE ANY LOGIN`、`ALTER ANY LOGIN` 不在白名单内即被拒）。
   - (e) **不拥有任何东西**：本账号不是 `dbo`，不拥有任何 schema、对象、角色（`sys.schemas`、`sys.objects`、`sys.database_principals` 的 `principal_id` / `owning_principal_id` 都不是本账号）；本账号没有 class 4 主体类授权（`sys.database_permissions` 中 `class = 4` 且 `grantee_principal_id` 为本账号的行为 0，覆盖 `IMPERSONATE ON USER::…`、`ALTER ON ROLE::…`）。
   - (f) **只进得了目标库**：`HAS_DBACCESS` 为 1 的用户库恰好是本连接的目标库（A8 与老系统库在同一 RDS 实例，B-5 README:7；覆盖同实例其他库的用户与 guest 写权限）。
2. **无法判定即拒绝**：查询出错、超时、返回为空都按不满足处理，与 `SeeyonStartupCheck.java`:59-60 一致；`LegacyInboxConfiguration` 吞掉 `DataAccessException` 的写法删除。
3. **不提供关闭开关**：`INTEGRATION_SEEYON_VALIDATE_ON_STARTUP`、`INTEGRATION_LEGACY_VALIDATE_ON_STARTUP` 与对应属性、`@ConditionalOnProperty` 删除，只读连接一旦配置就必须校验。若测试必须保留开关，`ProductionConfigSanityTest` 断言 dev 与 prod 配置都为 true。
4. **运行期重检**：每次同步任务（组织同步、部门简称刷新、迁入、对账）开始前重跑同一校验；失败即停掉该适配器（后续读取返回「不可用」，与 ADR-0033 第 2 项第 9 条的不可用口径一致）并告警，不只在启动时检查一次。合并待办的按请求读取至少每天重检一次。
5. A8 的列相等校验与配置 ID 存在性校验（RULE-356、根路径 M7）照旧，去留随第 6 项。
6. 校验实现放在 `platform.integration` 内、三个连接共用一份；`SingleObjectGuard`、`LegacyAccessGuard` 删除。类名在实现 PR 中按 NAMING_STANDARD 与 `terms.yaml` 定。
7. **实现 PR 用真实登录逐项构造反例核实**：PR #135 形状的账号（加上 (a) 中两项 DENY 后）通过；以下各自被拒——撤销库级 DENY INSERT 并 `GRANT INSERT ON SCHEMA::dbo`；`GRANT IMPERSONATE ON USER::<可写用户>`；本账号拥有一个 schema；加入一个自定义角色（含只有 SELECT 的角色）与 `db_datareader`；`GRANT CONTROL SERVER`；在同实例另一库建本账号用户；校验查询被拒或超时。**首次部署前必须项。**
8. **前置**：D1-1（A8 / 老系统连接只经工厂，强制查询、套接字、锁等待三种超时，`phase1a/NEXT_BATCH_PLAN.md`:261）提为本项实现 PR 的前置或同批交付，不再排在 R-1b 之后。

### 5. 账号

1. **老系统：合并为一个应用运行时账号**（推荐，作为决定提交用户批准）。理由：
   - **启动校验**：分两个账号的唯一原因是每个连接都校验「恰好一个对象」（B-5 README:37、`INFRA_RUNBOOK.md`:104、`CROSSCHECK.md`:10）；第 4 项之后共用账号两边都通过。
   - **授权范围**：两个账号现在权限完全相同（PR #135），分开已不构成安全边界，任一个泄露的后果一样。
   - **轮换**：90 天轮换从两份口令减为一份（`runbooks/C-8-kms.md`:15-16），避免只轮换了一份、另一份过期使某个模块中断。
   - **审计归属**：ADR-0033 第 2 项第 9 条之后两类读取都在 `platform.integration` 内，应用内按用途区分——每个连接池设不同的 JDBC `applicationName`（SQL Server 记为 `program_name`；客户端自填，只作应用内分类，不作库侧身份证据），适配器按用途写读取计数日志（带 `correlationId`）。库侧身份区分靠账号本身（取证另开账号，第 4 条）与 RDS SQL 审计（Q5）。
2. **做法**：
   - 应用改用一组连接变量 `LEGACY_DB_RO_URL` / `_USERNAME` / `_PASSWORD`，指向 `one_legacy_names_ro`；dev 验证合并待办与部门简称都可用后删除 `psa_one_legacy_ro`，从 `one.env` 移除 `FORCITIS_PLATFORM_APPROVAL_LEGACY_URL` / `_USERNAME` / `_PASSWORD`（老待办详情地址模板变量保留，名称随 ADR-0033 第 2 项第 9 条调整）。
   - `one_legacy_names_ro` 改名为 `one_legacy_ro`（`ALTER LOGIN … WITH NAME`、`ALTER USER … WITH NAME`）**并入下一次 90 天轮换**执行，不单独做一次生产账号变更；改名同一变更中更新 `read-all/legacy_rollback.sql`、`legacy_90_rollback.sql` 中的账号名（回滚方案第 5 条）。
   - 删除与改名是账号变更，执行前请用户确认（Q2）。
3. **A8：仍是一个应用运行时账号** `one_a8_views_ro`，不拆不合、不改名（名称中的「views」在 Q1 选 (c) 后逐步名不副实，只是名称问题，不值得一次生产账号变更）。
4. **取证另开一个同权限的取证账号**，不与运行时共用：
   - 理由：取证工具若用运行时账号，每次都要接触应用口令；疑似泄露后轮换必须重启应用；`applicationName` 可伪造，库侧无法区分应用、取证与借 ECS 出口的攻击者。另开账号后，取证口令泄露只需轮换取证账号，应用不受影响；库侧按登录名即可区分。
   - 形状：一个登录，在 A8 与老系统库各建用户；授权形状与运行时相同（库级 `GRANT SELECT`、第 4 项 (b) 的库级 DENY、不入角色、(a) 中两项 DENY）；只放行 ECS 内网地址，口令只在 ECS 上（`one.env` 同等权限的独立文件）与 KMS；C-8 轮换表多一行。名称在执行时按 NAMING_STANDARD 定。
   - 每次取证前用第 4 项同一校验检查取证账号（(f) 改为「恰好这两个库」），不通过不取证。
   - 迁入抽取与对账在应用进程内运行，用运行时账号；不再用 RDS 高权限账号或老系统应用自己的可写账号做读取（现状：B-5 执行用了 RDS 高权限账号，README:5；`docs/legacy/runtime-usage/README.md`:6 的早期取证用了老系统应用的数据源）。高权限账号只用于授权变更本身。

### 8. 读取口径与负载

A8 与老系统库共用一个 RDS 2016 标准版实例（B-5 README:7），没有可读副本分流，重查询同时压到两套生产系统上。

1. **隔离级别**：实现 PR 与第一次取证时只读查询 `sys.databases.is_read_committed_snapshot_on` 并记录两库结果；不对外部库执行 `ALTER DATABASE` 开快照。取证与对账禁止 `NOLOCK` / `READ UNCOMMITTED`（会读到脏数据、重复或漏行，结论失效）。
2. **超时**：所有只读连接经 D1-1 的工厂建立，查询、套接字、锁等待三种超时都设置；交互路径（登录未命中单人查询、合并待办）设 `LOCK_TIMEOUT`，超时按「不可用」降级，不阻塞登录与首页。
3. **大表**：迁入与对账扫大表时按主键分批、自动提交（不持有长事务）、放在低峰时段；批大小与时段写在该阶段迁入规格中。
4. **缺列检查分层**：启动时的缺列检查只覆盖运行时关键路径（组织同步、待办、部门简称）；迁入与对账用到的列在任务启动时检查，失败只停掉该任务并告警，不因 A8 升级让整个 FORCITIS one 起不来。

## 备选方案（未采用）

- **维持视图级最小授权，按需逐个加视图**：与用户决定相反；取证与迁入每次越界都要等外部 DBA 改视图，正是本 ADR 要消除的中断。
- **只放开取证、运行时仍只读视图**：用户澄清选「两者都是」；运行时的新旧等价核对也要读基表。
- **库级只读但对凭据表 DENY**：用户答「全部可读，不排除」；凭据保护改为第 3 项的拒绝清单、使用约束与扫描守护。
- **启动校验按禁止清单（黑名单）判定**（原提议稿）：库级 `fn_my_permissions` 看不到 schema 级、对象级与 class 4 授权，服务器层与同实例其他库也不覆盖，SQL Server 新增的权限会被默认放行，与 ADR-0030 第 1 项第 3 条相反；改为第 4 项白名单判定。
- **用 `db_datareader` 角色授权**：效果相同，但使「除 `public` 外不在任何角色」这条简单不变量失效，回滚时也多一步；采用直接的库级 GRANT。
- **取证与运行时共用一个账号**（原提议稿）：少一份口令，但取证工具每次都要接触应用口令、疑似泄露后轮换必须重启应用、`applicationName` 可伪造使库侧无法区分来源；改为另开同权限取证账号。
- **Q1 (b) 一次切到基表并 7 天双读**：需要一套用完即弃的逐列哈希比对工具，并安排专门的切换批次；(c) 以集成测试加一次 `EXCEPT` 比对达到同样的等价证明。
- **老系统保留两个运行时账号**：分开的唯一理由（恰好一个对象的校验）已不存在，只剩双份轮换成本。
- **立即为两个账号改名**：只有名称上的收益，多一次生产账号变更；改为并入下一次轮换（老系统）或不改（A8）。
