## 背景

要决定：一个聚合与一个请求承载多种类并带可选字段的命令（人事命令 14 种、组织结构命令 9 种）是否改为每种形状一个强类型。现在决定，是因为它让编译期错误变成运行期或评审期错误，且每个新切片都在加重：人事命令内部类型有 24 个几乎全可空的组件和 3 个渐进构造器，HTTP 请求再写一份，前端 `KIND_FIELDS` 写第三份，#1579（HTTP 缺 6 个代理字段，ACTING_START 答 422）与 #1489（前端漏一个 HIRE 字段）是同类缺陷。触发出处：用户 2026-11-06 对 lead 代码评审的「开」，工单 #1585。同一工单的另一个决定（权限与角色的模块内声明）已拆为 ADR-0091（一份 ADR 一个决定）；两稿共用设计稿 `docs/architecture/proposals/typed-commands-and-module-declarations.md`，互不依赖，可分别采纳。

## 决定

1. **按形状强类型**：每个命令家族用一个密封接口，每种**形状**一个只含自身组件的 record。人事命令的形状按命令种类，一个种类有两种形状时拆成两个（如 HIRE 的新人与已有员工）；组织结构命令的字段由（对象种类，命令种类）一对决定（职位只接受 CREATE 与 DISABLE；组织单元的 CREATE 要交付单元标志并允许简称、区域、上级和法人，职位的 CREATE 都不允许），所以形状按这一对。判据：一个家族出现不止一组随种类而变的可选字段，就按形状拆；只做分类的枚举（如会签种类）和 2 至 3 种的枚举不动；`PayrollRuleRowKind`（7 种，有随种类而变的可选列）按此判据是下一个候选，不在本稿转换。
2. **聚合、状态机、到期应用、会签冻结、审计、幂等和表保持一份，不改表。** 每种形状的 record 映射到同一行；入库后才确定的状态（会签前后法人、组织结构命令 id、雇佣关系、任职种类）仍留在聚合上，不进不可变的命令体；几种形状共有的部分（日期对、个人数据）用嵌套 record。密封类型放在 workforce 的 api。现有宽 record `EnterPersonnelCommand` 与 `EnterOrgStructureCommand` 在 S3 之前**保持原名、原组件、仍是 `enter` 的参数**：验收探针按简单名反射找到它并按组件名构造（`PersonnelCommandsProbe`、`OrgStructureCommandsProbe` 及其 `*Names`），改名、换成接口或冻结组件都会让人事与组织结构的验收测试全部变红。强类型体与宽 record 并存，由 HTTP 边缘建强类型体、再转成宽 record 交给 `enter`；S3 经测试会话的卡改探针后，才让聚合直接接收强类型体并取代宽 record。
3. **渐进路径，不大改**：之后每个动到某形状的切片，为该形状加自己的 record（只含自身组件，构造时校验该形状的必填与禁填），并提供转成宽 record 的方法；宽 record 不冻结（测试会话仍按现行做法按名加组件），但新字段先进强类型体；一个种类转换后，边缘不再直接构造宽 record。每个强类型体都有一条测试：同一份平的 JSON 经强类型体转成的宽 record，与直接解析成宽 record 相同。最后一个形状转完且探针改完时（S3），删除宽 record、多余构造器和前端手写字段表。HTTP 边缘是否用带判别字段的 `oneOf`（组织结构需要一对判别）由第一张转换卡先做原型定（设计稿 S0）；做不出时边缘仍用平的请求 record 再转成强类型，领域侧不变。**限定（lead 采纳时加）**：`oneOf` 与平边缘由 S0 的证据决定，两种结果都不需要再立 ADR。
4. **验收测试**：本决定不由实现者改验收测试（基线第 4 条）。S1、S2 不碰探针契约（`enter` 的参数名、类型与组件不变），所以不需要测试卡；S3 需要：`PersonnelCommandsProbe`、`PersonnelCommandNames`、`EmployeeHireIT`、`OrgStructureCommandsProbe`、`OrgStructureCommandNames` 以及在用旧构造器的 `GoldenSampleSupport`、`RevokeDisableFloorSupport` 共 7 个验收文件由测试会话在自己的卡里改；在那张卡合并前宽 record 与旧构造器保留。

## 影响面

- 代码：workforce 的人事命令与组织结构命令（聚合、服务、仓储、HTTP 请求、前端字段表），随后续切片转换；本稿不改代码、表、事件。
- 守护：`OpenApiExportTest`（密封 HTTP 体改变导出形状时更新基线）；`PlatformOrgInterfacesTest` 的签名快照（backend/architecture/platform-org-interfaces.signatures.txt 含两个宽 record，每次 api 形状转换都要更新）；强类型体到宽 record 的等价测试随各形状加；`NamingSurfaceTest`、`ModuleDependencyTest` 不受影响。
- 验收测试：S3 需要测试会话的卡，涉及 7 个文件（见决定 4）；S1、S2 不碰。
- 表：无变化。

## 迁移方案

设计稿第 6 节 S0 至 S3：S0 原型定 HTTP 边缘与 `oneOf` 能否导出（含 `@JsonSubTypes` 把尚未转换的种类映射到宽 record 的包装、平的 JSON 仍可解析）；S1 为第一个形状加强类型体与转宽 record 的方法；S2 逐形状转换；S3 经测试卡改探针后删宽 record（待测试卡）。每步随「下一张动到该处的切片」做，不单开大迁移卡。

## 回滚方案

每一步可单独停下：宽 record 在整个过程中与强类型体并存，停在任一步行为与今天相同。推翻须另立 ADR 取代；不改表与事件，回滚无数据迁移。

## 需同步修改的守护规则

- 各强类型体到宽 record 的等价测试（随各形状）；第一次用 `oneOf` 时更新 `OpenApiExportTest` 基线。
- `docs/rules/coding-standard.md` 是否加「按形状强类型」一条，按 CS-7.5 另走，本稿不改。
- 完成标准抄设计稿第 7 节（1 至 5 条）。

## 后果

- 好处：缺字段在编译期暴露；Java、HTTP、前端三份字段表减为一份。
- 代价：形状多时 record 多；仓储对每种形状要有映射；过渡期宽 record 与强类型体并存；HTTP `oneOf` 在本仓尚无先例，组织结构的一对判别更没有；删旧构造器要等测试卡。
- 未定：HTTP 边缘是否一定用 `oneOf`（S0 按证据定）；`ChangeKind` 等枚举是否有随种类而变的可选字段（未读到底）。

## 备选方案（未采用）

1. **每个种类家族一个聚合（及表）**：要拆开状态机、到期作业、会签冻结，并改表与迁移，没有实测收益。
2. **保留宽 record，另发布种类字段矩阵并生成前端列表**：最便宜，但编译器仍看到 24 个可空组件，后端规则与矩阵仍可不一致；只在 HTTP `oneOf` 做不出时作边缘的退路。
3. **维持现状**：每多一个种类，成本与缺陷都增加。
