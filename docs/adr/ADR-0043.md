## 背景

- **ADR-0026（已采纳）**：第 7 项第 1 条定访问级别 L1 公开 / L2 内部 / L3 敏感（工资、日薪、费率、个人联系方式与证件、银行信息）/ L4 机密；第 3 条规定 L3 / L4 不进日志、事件、审计 detail、企业微信卡片；第 7 项第 4 条（D-6）把 1a 的员工邮箱、性别、企业微信 ID 定为 L2；第 1 项的表把通讯录卡片（姓名、部门、企业微信 ID）定为 L2、全员可见（D-12）。
- **登记现状**：`backend/architecture/data-classification.txt` 文件头把 SENSITIVE 定义为「个人信息、工资与日薪、银行卡」，NAMING_STANDARD §2.5 与 GUIDING_PRINCIPLES §6 同此口径。现有 20 行：17 行 SENSITIVE（含姓名、登录名、工号、邮箱、性别、企业微信 ID、两处 IP、会话主体、两列收件人代码与 6 列安全材料），3 行 RESTRICTED（口令哈希、TOTP 密钥、会话内容）。其中姓名、登录名、企业微信 ID、工号、收件人代码是数据打分卡 K10「敏感分级漏登」之后按「个人信息即 SENSITIVE」补登的。`architecture/dama/data-objects.yaml` 的 `sensitive_columns` 照录了这 17 行。
- **冲突的实际范围**（按 D-6、D-12 把邮箱、性别、企业微信 ID、姓名改登为 INTERNAL 时）：
  - `DdlNamingTest.sensitiveColumnsAreClassified` 只对 `email`、`gender` 失败——`SENSITIVE_NAME`（`DdlNamingTest.java:94`）命中这两个列名并要求 SENSITIVE 或 RESTRICTED（`:500`）；`wecom_user_id`、`display_name` 不命中。
  - `DataArchitectureTest` D5（`:44`、`:330-336`）只要求「已登记」，不看级别，不失败。
  - `SensitiveColumnExposureGuardTest` 第 108 行（注入测试期望 `email`、`displayName` 被找到）与第 114 行（期望登记中有 `email`）失败，因为两者读的是真实登记文件；`sensitive-response-exceptions.txt` 中 `CurrentUserResponse#displayName` 一行变为多余，`responsesDoNotCarrySensitiveColumns` 随之失败。
  - 另一处不一致：GUIDING_PRINCIPLES §6 保留表写 `outbound_deliveries`「内容含收件人，按内部级处理」，登记却是 SENSITIVE。
  - 外部读取：R-1b-0a 的读取列登记（ADR-0037 第 2 项第 5 条，尚未合入 main）照现行口径把 A8 的 `WE_COM_ID`、`ENTERPRISE_EMAIL` 记为 SENSITIVE。
  - 隐患：`DdlNamingTest.readClassification`（`:485`）以 `split(..., 3)` 解析，四段行会被静默接受（第三段并入理由），标记不被读取。
- **法律口径**（个人信息保护法，全国人大网原文，2026-10-15 逐条核对）：
  - 第四条：个人信息是与已识别或者可识别的自然人有关的各种信息，**不包括匿名化处理后的信息**——去标识化后仍是个人信息。
  - 第二十八条第一款：敏感个人信息是「一旦泄露或者非法使用，容易导致自然人的人格尊严受到侵害或者人身、财产安全受到危害的个人信息，包括生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹**等**信息，以及不满十四周岁未成年人的个人信息」。列举之后有「等」，前段是概括条款，列举不是穷尽的。第二款：只有在具有特定的目的和充分的必要性，并采取严格保护措施的情形下，方可处理敏感个人信息。
  - 第五十一条：应采取措施，其中（二）对个人信息实行分类管理；（三）采取相应的加密、去标识化等安全技术措施；（四）合理确定个人信息处理的操作权限。
  - 第五十五条：处理敏感个人信息（第（一）项）、委托处理或向他人提供个人信息（第（三）项）等，应事前进行个人信息保护影响评估并记录处理情况；第五十六条：评估内容为合法正当必要、对个人权益的影响及安全风险、保护措施是否有效相称，报告和处理情况记录至少保存三年。
  - 第七十三条第（三）项：去标识化指个人信息经过处理，使其在不借助额外信息的情况下无法识别特定自然人。
  - 第十三条第一款第（二）项：按照依法制定的劳动规章制度和依法签订的集体合同实施人力资源管理所必需的，可以处理个人信息；第二款：有前款第二项至第七项情形的，不需取得个人同意。第二十九条：处理敏感个人信息应取得单独同意；第三十条：还应告知必要性及对个人权益的影响。
- **根因**：「谁能看、要不要掩码」（访问级别，业务决定）与「是不是个人信息、是不是敏感个人信息」（法律属性，第五十一条第（二）项的分类管理）是两个维度，被压成了一个。邮箱、企业微信 ID 是个人信息（第四条），但不在第二十八条的范围内，业务上可以是 L2。

## 决定

### 1. 两个维度

1. 每个登记列有两个独立属性：
   - **访问级别**：沿用 ADR-0026 第 7 项，`PUBLIC` = L1 公开、`INTERNAL` = L2 内部、`SENSITIVE` = L3 敏感、`RESTRICTED` = L4 机密，一一对应；掩码、读权限、出参规则不变。
   - **个人信息标记**：`NONE` 非个人信息 / `PI` 个人信息 / `SPI` 敏感个人信息（第四、二十八条；第五十一条第（二）项分类管理）。
2. **判定**：
   - `PI`：与已识别或可识别的自然人有关（第四条），含去标识化的标识；只有匿名化后的数据为 `NONE`。
   - `SPI`：落入第二十八条第一款的列举项，**或**符合其概括条款（泄露或非法使用容易导致人格尊严受侵害或人身、财产安全受危害）。**拿不准的按 `SPI` 登记**，直到法务确认（U-11）。
   - 访问级别由用户按业务决定（如 D-6）；个人信息标记按法律判定，不由业务选择。判定由起草会话作出、opus 复审；存疑项交 U-11。
3. **`SPI` 的访问级别不得低于 `SENSITIVE`**（第二十八条第二款「严格保护措施」、第五十一条第（四）项操作权限）。
4. **解释，不改 ADR-0026 的决定**：第 7 项第 1 条中的「个人联系方式」指非工作用联系方式（私人手机、私人邮箱、住址等）；工作邮箱、企业微信 ID 按第 7 项第 4 条（D-6）。

### 2. 登记格式

```
<schema.table.column> | PUBLIC|INTERNAL|SENSITIVE|RESTRICTED | NONE|PI|SPI | <理由>
```

- 第二段四选一，与 L1–L4 一一对应（PUBLIC = L1、INTERNAL = L2、SENSITIVE = L3、RESTRICTED = L4）；第三段三选一；理由不得含 `|`。
- `PI`、`SPI` 行的理由以「用途：」开头，写明用该列的功能（第 6 项 R-1）；`SPI` 行另写影响评估报告路径（第 6 项 R-4）。
- 未登记的列视为 `INTERNAL` + `NONE`（风险见「后果」M-7）。
- 代理键列（kernel 强类型 ID / UUID）不登记，出口与分析层按 `NONE` 处理，其法律属性（第七十三条第（三）项去标识化）由第 4 项第 2 条说明。

### 4. 个人信息的出口规则

1. **直接标识信息**（姓名、邮箱、手机、企业微信 ID、工号、登录名、IP、证件号、银行卡号等，即 `PI` / `SPI` 列中能单独指向某人的值）不得写入下列位置，依据分别为：

   | 位置 | 规则 | 依据 |
   |---|---|---|
   | 应用日志 | 不写 | GUIDING_PRINCIPLES §11 O-3（用户已认可；O-3 只管日志） |
   | 领域事件 | 不写，只带 ID | `docs/architecture/events/event-analytics-fields.md` §4 第 1、2 条（经 ADR-0025 作为事件信封依据） |
   | 审计 `detail` | 不写（现存三处违例，见第 5 条） | `archive-columns.txt` 对 `detail` 的定义（不含密钥与个人信息）；L3 / L4 另有 ADR-0026 第 7 项第 3 条 |
   | 审计 `before_text`、`after_text`、`change_reason` | 允许记录被变更字段自身的 L2 个人信息原值，L3 及以上与 `SPI` 不记原值；`change_reason` 由人填写，只提示不拦截 | 用户 U-7 (b) |
   | 企业微信卡片正文 | 允许姓名，其余直接标识不进；以法务对 U-11 第 ④ 问的答复为前提，答复前不扩大现状，只按 ADR-0026 第 7 项第 3 条禁 L3 / L4 | 用户 U-7 (b)；D-12 让姓名在待办中可见 |

2. **系统代理键**（自有 UUIDv7，如 `employee_id`、`user_id`）是去标识化的标识（第七十三条第（三）项、第五十一条第（三）项），允许出现在上述位置。它仍是个人信息（第四条只排除匿名化），不因此改为 `NONE`。
3. 审计条目的 `source_address` 是专用列，按 O-3、O-7 留在审计中，不受第 1 条影响。
4. 含直接标识字段的 record 覆写 `toString`（落实 O-3，与 ADR-0026 第 7 项第 3 条对 L3 的要求同法）。
5. **现存违例**（审计 `detail` 当前写入直接标识，与第 1 条冲突）：
   - `OperationAttestation.java:32-34`：`describe()` 把 operator、witness 姓名写入 detail；该写法出自 ADR-0027 第 1 项第 1 条（双人在场登记）。
   - `LoginAdmission.java:108-114`：detail 写入 `address=` 登录 IP。
   - `AuditSearch.java:16-21`：`describe()` 把检索条件（含 `sourceAddress` 的 IP）写入检索与导出的审计 detail；`source_address` 作为查询条件本身仍可用，违例只在写入 detail。
   - 处置选项（U-7 的 detail 子问）：① 见证人、操作人姓名改写员工 ID，阅读时再解析；② 保留姓名，在本节写明为例外并注明 ADR-0027 出处；③ IP 只留 `source_address` 列，不再写入 detail。**用户答复**：IP 选 ③（U-7c，涉及 `LoginAdmission`、`AuditSearch`）；见证人、操作人姓名选 ① 还是 ②（U-7b，涉及 `OperationAttestation`）暂不定，定前守护以带到期日的例外登记该处。修复 PR 由 one-coordinator 派工，处置按上述答复实现。

### 5. 敏感个人信息的额外义务

1. **影响评估**：任何 `SPI` 列（自有表或外部读取）在**首次读取、收集或处理之前**完成个人信息保护影响评估并记录处理情况（第五十五条第（一）项）；内容按第五十六条第一款三项。生产取证读取 `SPI` 同样适用。
2. **保存**：评估报告与处理情况记录保存不少于 3 年（第五十六条第二款）；存放位置由 U-10 定。
3. **同意与告知**：第二十九条单独同意、第三十条告知，是否因第十三条第一款第（二）项（人力资源管理所必需）与第十三条第二款而免除，交法务确认（U-11）；确认前是否暂不处理新的 `SPI` 见 U-14（暂不定，定前不处理新的 `SPI`）。
4. `SPI` 列只在用到时读取（ADR-0037 第 2 项第 5 条既有要求），不进分析层明细（第 7 项）。

### 6. 最小化与保留期（可检查规则）

- **R-1 用途**：`PI` / `SPI` 登记行的理由以「用途：」开头并写明功能；守护检查前缀与非空。
- **R-2 保留期**：数据访问注册表中含 `PI` / `SPI` 列的表，`retention.policy` 不得为 `PERMANENT`，除非注册表该条目带有可被测试读取的理由与用户决定出处（字段名由实施 PR 定）。现有违例：`user_accounts`（`last_login_address`）、`emergency_admins`（`account_name`），U-12 已分项答复：`emergency_admins` 认可永久保留并登记理由；`user_accounts.last_login_address` 改为有期限（具体期限由实施 PR 提出），提出前以带到期日的 gap 登记。
- **R-3 分析层**：按第 7 项。
- **R-4 评估先行**：`SPI` 登记行的理由含影响评估报告路径，守护检查该路径存在。

### 7. 分析层按哪个维度判定

SESSION_PLAYBOOK §14.1 D13 写「个人信息……不进分析层明细」，NAMING_STANDARD §2.5 写 SENSITIVE「不进分析层明细」，两维拆开后口径须选定：U-8 暂不定，定前按 D13 字面（全部 `PI` 不进分析层明细）。

### 8. 外部读取登记

ADR-0037 第 2 项第 5 条规定读取列登记写 PUBLIC / INTERNAL / SENSITIVE / RESTRICTED。外部读取列登记同样加个人信息标记（U-9 用户答复「加」）；本 ADR 取代该句的词汇（「取代」行第 3 项，状态行写法见影响面），访问级别词汇本身不变。

| `outbound_deliveries.recipient_codes`、`skipped_recipient_codes` | `*Response` 中对应的收件人代码字段 | 用户 U-4 (b)；GUIDING_PRINCIPLES §6 |

- `SensitiveColumnExposureGuardTest` 第 108 行：现期望 `LeakyResponse` 的 `email`、`passwordHash`、`lastLoginAddress`、`displayName` 四个字段全被找到。改为测试内固定分级表：仍注入四个应被找到的字段（一个 RESTRICTED、一个 SENSITIVE + PI、一个 SENSITIVE + NONE、一个 SENSITIVE + SPI），另加一个 INTERNAL + PI 字段断言**不**被找到。理由：原断言依赖真实登记文件，登记合法变化就失败；改后注入强度不减。
- 第 114 行：现断言登记含 `email`、`password_hash`、`last_login_address`；`email` 换为仍为 SENSITIVE 的 `login_name`（U-2 若改则换 `last_login_address` 以外的另一 SENSITIVE 列）。理由同上。

- 条件行：U-2 暂不定，`employee_code` 与 `login_name` 仍在受保护集合；若日后 U-2 选 (b)，`employee_code` 才移出。`recipient_codes`、`skipped_recipient_codes` 已按 U-4 (b) 移出受保护集合；`sessions.principal_name` 级别不变，只豁免第 3 组标记要求。

## 后果

- D-6、D-12、法律与守护三者一致；邮箱、性别、企业微信 ID、姓名不再被迫掩码。工号、登录名等是否放开等用户决定，不在本 ADR 中预设。
- 个人信息的法定义务（分类管理、去标识化、出口限制、影响评估、保存期）有了独立、可检查的落点。
- 多一列登记与三组关键字的维护成本；`SPI` 的影响评估会拖慢首次接入证件、银行卡数据的阶段（Phase 2 起）。
- **风险 M-6 企业微信卡片与导出**：卡片正文经企业微信服务端传递，若含个人信息，可能属第五十五条第（三）项的委托处理而需评估（U-11）；导出（CC-P08）只按级别掩码，L2 的 `PI` 会明文导出，导出审计与行数上限（G-X5）是唯一约束。
- **风险 M-7 未登记列默认 `INTERNAL` + `NONE`**：不命中关键字的新个人信息列（例如以业务词命名的联系人字段）会静默落入默认值。缓解：表结构评审逐列确认标记，§13 逐表打分加「个人信息标记」一栏；关键字表随新列名补充。
- 分析层口径（U-8 暂不定）若日后选 (a)，相对 D13 字面是放宽。
