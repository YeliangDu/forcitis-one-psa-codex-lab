## 决定

### 1. 地位与登记方式

1. **规范性内容与参考性快照**（评审 H-6）：
   - **规范性**：BC 清单中的模块标识、命名空间、BC 的合并与新增、深 / 薄标记（决定 2、决定 3 表的「模块标识」「命名空间」「深 / 薄」列与决定 4）；协议类型归属（决定 5）；方向规则与方向事实（决定 7 第 2 条）；禁止边（「需同步修改的守护规则」第 1–3 条）；依赖次序约束（决定 9）。
   - **参考性快照**：决定 3 表的「所含聚合」列、聚合计数、决定 7 第 1 条的分层快照与边数。它们随阶段复核在提议稿中直接更新，不需新 ADR。
   - 各阶段开工时按 ADR-0050 的方法复核本阶段的 BC、聚合与边；**「一致」指规范性部分一致**。一致的直接登记；规范性部分不一致的，另开 ADR 取代本 ADR 的相应条款并附新证据（ADR-0041 决定 3 的同一做法）。
   - 依据：规范性 / 参考性的分法为**裁量**（用户已认可，intent `2026-10-16-130636` K-51，评审 H-6）；不一致时另开 ADR 的做法为**推出（用户已认可，intent `2026-10-16-130636` K-51）**，由 ADR-0041 决定 3 推出。各项规范性内容自身的依据见决定 3、5、7、9 与守护规则各条。
2. **SSOT 与本 ADR 的关系**：本 ADR 的 BC 清单经用户认可，采纳时进 SSOT：`ddd/contexts.yaml` 登记全企业 28 个业务 BC 为 `planned`（另登记 `delivery.closeout` 为 `kind: process` 的流程模块，用户 C-1；`build_architecture.py` 与相关校验须接受该 kind），7 个被合并的旧标识（`presales.customer`、`presales.quoting`、`contract.baseline`、`contract.changeorder`、`contract.riskdelivery`、`operations.budgeting`、`organization.incentive`）改 `retired` 并写去向（去向见决定 3 表后的退役标识说明）（用户 A-1 选 c，intent `2026-10-16-124649`，修订 L-5）。依赖骨架与分层仍是提议稿的定稿快照，供阶段复核对照；规划边不登记进 `ddd/context-map.yaml` 与 `backend/architecture/module-dependencies.txt`，到阶段建边时再登记（ADR-0041 决定 4），用户尚未单独认可规划边。聚合同理留在提议稿。
3. 已建模块以代码为准（`backend/architecture/module-dependencies.txt` 与 `backend/src/main/java/com/forcitis/one/`）：现已建业务模块为 `cost.timesheet`、`organization.workforce`、`organization.attendance`，本 ADR 不改它们的标识与包路径；`delivery.execution` 曾建、已删（`retired-module-schemas.txt` 登记 `delivery_execution`），按本 ADR 重建。

### 2. 命名空间（修订 ADR-0017 决定 1）

1. 业务命名空间 13 个：既有 12 个 `presales`、`contract`、`delivery`、`cost`、`receivables`、`payables`、`procurement`、`expense`、`organization`、`operations`、`accounting`、`km`，新增 1 个 **`masterdata`（主数据）**（用户 D-2 改选 b，intent `2026-10-16-061232`；标识与中文名用户 GL2 已定，`docs/glossary/bcs.yaml`）。另有平台命名空间 `platform`（10 个模块不变）。
2. 命名空间只是 Java 包、PG schema、URL、权限码的前缀分组（用户 intent `2026-10-15-221201`；ADR-0003 决定 1、2）：`masterdata` 下的模块包路径为 `com.forcitis.one.masterdata.<bc>`，schema 为 `masterdata_<bc>`，由 `SubdomainModuleDetection` 识别为顶层模块，无须改识别策略。
3. 每个有聚合的 BC 恰属一个命名空间（`com.forcitis.one` 之后的第一段）；命名空间按 ADR-0050 决定 13 与 BC 一起定，不做核心 / 支撑 / 通用分类。**例外**（评审 M-2，同 ADR-0050 决定 13）：`kernel` 是共享内核，不属任何命名空间；`reporting` 是只读分析模块，模块路径仍按 ADR-0023 待定，定下之前不属任何命名空间；`delivery.closeout` 是无聚合的流程模块，属 `delivery` 命名空间、不建 schema。

### 4. 各段的划分结论

1. **主数据**（D-2 改选 b）：`masterdata.counterparty` 管往来单位及其角色、联系人、银行账户、资质证书，以及外部工程登记（建设工程、部位、招标项目登记、我方参与记录）；客户角色不走准入，档案已核实即可用，供应商、分包等角色走准入（P-3，intent `2026-10-16-120544`）。`masterdata.catalog` 管服务产品、阶段类型、标准成本费率表、计费系数、协议价目的版本化目录。
2. **售前合一**（i210513）：线索、商机、投标、报价、市场活动、客户活动、独立性检查同在 `presales.opportunity`；独立性检查在售前拦截，合同签约时前置读检查结论（D-4）。
3. **合同合一**（i210513「开新 ADR 合并合同三个 BC（保留签证、索赔）」）：签证是协议变更的类型，索赔独立聚合，风险交付授权同在 `contract.agreement`；签证、变更、索赔仍在合同 BC，ADR-0016 决定 9 的实质不变，只改模块名。联合体中标后我方份额记在项目合同的相对方与身份上（P-4）。
4. **交付三个 BC 加一个流程模块**（D-3 改选 c；D-9 a；F-5）：`delivery.execution` 管项目、WBS、计划、预算、资源、延期、复盘、风险与问题；`delivery.acceptance` 管交付物、不符合项、返工认定、设计变更、发包人提供资料、证据、证据关联、满意度调查，交付侧只记送达、退回与项目经理的无异议声明（ADR-0049）；`delivery.inspection` 管检查计划、检查、检查表模板、外部检测；`delivery.closeout` 是无聚合的流程模块，实现结项（INV-40）的下游编排与结项审批钩子，不持有状态、不建 schema，结项检查单经 `platform.audit` 留痕（api 依赖，评审 M-3；聚合稿 §4.6、REF-02）。
5. **人事**（D-5 b；F-3）：激励并入 `organization.payroll`；请假、加班、考勤记录、假期余额、月度考勤确认另建 `organization.leave`；`organization.attendance` 只留工作日历（D-5），另含标准工时版本（AGG-108，裁量（用户已认可，intent `2026-10-16-130636` K-51））（已建边 `platform.approval → organization.attendance` 不变，本模块不发起审批）。招聘需求、劳动合同、离职申请在 `organization.workforce` 内单级批准，不经 `platform.approval`（已建边 `platform.approval → organization.workforce`，实现审批钩子即成环）。
6. **计划与预算合一**（Q28）：`operations.budgeting` 并入 `operations.planning`，预算账户为其聚合；ADR-0023 决定 1 中「划分待用户确认」由此闭合。
7. **`accounting.tax` 提前独立**（D-7 改选 b，修订 ADR-0022 决定 7 括注）：自其首个占用方上线起即为独立 BC，先只含进项发票与入账占用（AGG-89；INV-72、74、75）；法定申报（AGG-90）到申报阶段再建。报销、应付经入账占用 api 依赖 `accounting.tax`。销项发票的开具在 `receivables.wip`（AGG-46），税费 BC 管进项发票、税费计提与申报；ADR-0022 决定 7 表中税费 BC「增值税（进项类型、销项）」的说明按此读（评审 M-7）。`accounting.cashbank`、`accounting.fixedasset` 的过渡做法仍按 ADR-0022 决定 7，本 ADR 不复述、不改。
8. **`km.knowledge` 沿用**（M-4 改选 b；K-1）：一级对象「知识条目」落此 BC（AGG-107），只依赖 `organization.workforce`；被服务与定价目录、售前、交付执行、质量与认可引用。
9. **`cost.costing` 的输入取自 `operations.facts`**（L-8「成本读已过账事实」，intent `2026-10-16-112800`）：成本数据只读已过账事实（api，开放主机服务 + 发布语言），不从各来源 BC 读成本数据；缺费率检查前移到工时过账时。成本结转批次（AGG-43）另订阅三个来源 BC 的生命周期事件——商机丢单与放弃、协议回签与终止、项目结项与终止——只作结转的**触发**（售前投入在回签且立项后转入，P-2；丢单后不转入；结项时结转），事件不携带成本金额，不是成本数据的来源（评审 M-8）。与 ADR-0016 决定 1 一致，不改其文。

### 6. 阶段类型落点（S1–S6，intent 061232；Q06，intent `2026-10-16-053630`；Q-A，intent `2026-10-16-082311`；intent `2026-10-16-090004`）

1. 全局阶段类型目录属 `masterdata.catalog`（AGG-04）；服务产品（AGG-03）选阶段组合与显示名（S1）；单个项目按协议范围在 `delivery.execution` 的 WBS 上裁剪，目录与服务产品的组合不变（S1b）。
2. 阶段门全部只预警留痕，审定走审批、不挡下一阶段（S2）；门引用对象状态，不另设拦截，对象自身的不变量照常拒绝。
3. WBS 阶段节点只表示工作进程，与商务分界脱开（S3）；「阶段已认可」是 `delivery.acceptance` 的事实，阶段页面与报表经 `reporting` 读模型派生，不写回 WBS（聚合稿 §4.4.1）。
4. 外部阶段码表（国标、RIBA 等）只作对照关系，不作阶段类型自带字段（S4）。
5. 合同范围条目挂 WBS 的阶段节点或子项，不挂工作包（S5）；挂接由 `contract.agreement` 登记（合同在交付执行下游）。
6. 检查类服务产品用目录中「检查」类下的自有阶段类型（检查策划、现场检查、发现发布、整改跟踪、报告认可），不套设计型阶段。S6 原文为「只启用招采、施工或自有子阶段」，其中「招采」「施工」两项已被 Q-A 与 intent 090004 取代，只保留「自有」（评审 L-4）。

### 9. 依赖次序约束（与阶段编号无关；评审 H-2）

本条是规范性约束，对任何过渡路线（一次投产或逐阶段）都成立；过渡阶段的划分、编号、排期与 `togaf/transitions.yaml` 的改动不在本 ADR 内，由施工方案承载（`proposals/CONSTRUCTION_PLAN_DRAFT.md`，提议稿，由用户定）。

1. **上游先于下游可用**：任一 BC 不早于其全部 api 或事件上游可用；规划边对应的功能不得先于其上游上线。依据：**推出（用户已认可，intent `2026-10-16-130636` K-51）**，由方向规则（M-3）与依赖规则推出。
2. **地基 BC 先行**：被多个下游共用的上游 BC（地基 BC，范围按施工方案的判据由用户定）先于其下游；`masterdata.counterparty`、`masterdata.catalog` 先于其全部下游（售前、交付执行、合同等；i210513「往来单位提前」，报价读费率与系数）。ADR-0021 决定 3 中「客商主档随 6b / 6c 先行」的先后表述按本条读。依据：**用户**（i210513「往来单位提前」）加**推出（用户已认可，intent `2026-10-16-130636` K-51）**（把它推广为地基 BC 先行与报价读费率、系数）。
