## 决定

### 1. 角色定义版本化

1. **`platform_identity.roles` 只留不可变的部分**：
   - 列：`role_id`（UUIDv7）、`code`、`kind`（SYSTEM / CUSTOM）、`is_administrative`，以及乐观锁 `version` 与 `event_count`；
   - `name`、`status`、`access_scope` 移出；
   - 新增 `BEFORE UPDATE` 触发器：拒绝改 `code`、`kind`、`is_administrative`；
   - `is_administrative` 不进版本：现有代码没有修改它的路径，它与角色码一样决定角色的本质。
2. **新建 `platform_identity.role_versions`**（角色版本，提议术语），每次定义变化一行：
   - `role_version_id uuid`：主键，应用侧生成 UUIDv7；
   - `role_id uuid NOT NULL`：外键到 `roles`，`ON DELETE RESTRICT`；
   - `version_number integer NOT NULL`：从 1 起递增，`uk_role_versions_role_id_version_number`；
   - `effective_from_at timestamptz NOT NULL`、`effective_to_at timestamptz`：空表示当前版本；
   - 定义内容：
     - `role_name`；
     - `role_status`（ENABLED / DISABLED）；
     - `access_scope_kind`；
     - `permission_codes text[] NOT NULL`：完整权限集合，见第 3 条；
     - 1b 的 `legal_entity_scope` 随 ADR-0026 第 2 项加在版本上；
   - 变更来源：
     - `change_channel_kind`（变更渠道，text + CHECK）：`SEED`（系统角色声明对账，第 7 条）/ `MANUAL`（角色管理界面）/ `MIGRATION`（老角色迁入）。现在没有修改角色定义的运维命令，所以不设 `OPERATIONS`；
     - `recorded_by uuid`；
     - `change_reason text NOT NULL`；
     - `authorization_request_id uuid`：经双人确认时必填，外键到 `authorization_requests`；
     - `declaration_revision integer`：声明修订号，只有 `SEED` 版本有（第 7 条）；
     - `version_audit_entry_id`：同一事务写入的审计条目 ID；
   - 关闭列（与授予对称）：
     - `closed_by uuid`、`closure_reason text`、`closure_audit_entry_id`；
     - 删除角色关闭最后版本时写入；被新版本接替而关闭时为空，由接替版本记操作人与理由；
   - 约束：
     - 成对 CHECK：
       - `SEED` 时 `recorded_by` 为空、`declaration_revision` 非空；其他渠道 `declaration_revision` 为空；
       - `MANUAL` 时 `recorded_by` 非空；
       - 关闭列只在 `effective_to_at` 非空时可以非空，且 `closed_by`、`closure_reason`、`closure_audit_entry_id` 同空同非空；
     - `permission_codes` 规范化 CHECK：用一个 `IMMUTABLE` 函数检查无 NULL 元素、无重复、按字典序升序。应用写入前先规范化，比较时按集合比较；
     - `EXCLUDE USING gist (role_id WITH =, tstzrange(effective_from_at, effective_to_at, '[)') WITH &&)`；
     - `EXCLUDE USING gist (lower(role_name) WITH =, tstzrange(…) WITH &&)`：同一时刻名称唯一，取代 `uq_roles_name`；
     - `CHECK (effective_to_at IS NULL OR effective_to_at >= effective_from_at)`：允许零长区间，与 K-2 的区间约定统一；
     - `CHECK (isfinite(effective_from_at) AND (effective_to_at IS NULL OR isfinite(effective_to_at)))`；
     - 当前版本唯一：排他约束保证同一角色至多一个开放版本；
   - 不建 `permission_codes` 的 GIN 索引：现在没有「哪些角色含某权限码」的查询，有了再按 `WHERE effective_to_at IS NULL` 建部分索引。
   - 触发器只许关闭开放版本：可改列为 `effective_to_at` 与三个关闭列，且只许由空变非空一次。
3. **权限集合存为版本行上的数组，不建子表**：
   - 与 `authorization_requests.permission_codes` 写法一致；
   - 版本行写入后不可变，集合是这个版本的值，不是可单独增删的关系。因此不需要 D1 / D2 守护的成员表特例，也不需要第三张只追加表；
   - 与 ADR-0033 草稿第 1 项第 4 条一致：成员行（UUIDv7 主键 + `(<版本 ID>, <成员>)` 唯一约束）只用于每个版本带一组需要单独约束的明细，例如日历的例外日；权限码集合是不可变版本的值，存为数组，读写都是一行；
   - **数组元素的合法性与权限目录的演进**：
     - 写入时由应用按 `Permission` 目录校验：码必须存在且未停用；
     - 目录中不再使用的码保留，标为「已停用」，不删除，所以历史版本中的码始终能在目录中找到；
     - 历史版本按原文本存储与还原，不随目录改写；
     - 运行时读到未知或已停用的码：只拒绝该码并告警（fail-closed），不抛异常，不影响同一角色的其他码；
     - 权限码改名 = 目录中新码上线、旧码标停用，并为含旧码的每个角色追加一个新版本；
     - 校验分两处：守护第 8 条在测试库检查；生产由启动对账（第 7 条）检查全部角色的当前版本，命中未知或已停用码时告警。
4. **改角色定义 = 新增版本**：
   - 同一事务内关闭当前版本，插入新版本，以 `roles.version` 做乐观锁，并持有第 6 条的行锁；
   - 新建、改名、改范围、改权限、启用与停用，都是新增版本；
   - 定义没有变化时不新增版本。
5. **删除角色 = 关闭最后一个版本、不再开新版本**：
   - `roles` 行与全部版本保留；
   - 仍有当前有效授予时拒绝（现 `PLATFORM_IDENTITY_ROLE_IN_USE`），检查在第 6 条的锁内；
   - 界面与事件仍称「删除角色」（`RoleDeleted`）；
   - 被删除角色的 `code` 不能再用于新角色：这是 RULE-345 结论的行为变更，修订草案见 0034-Q3。
6. **时刻与锁**：
   - **时刻**：
     - `:now` 取应用注入的 `Clock`，作为参数传入，不用数据库时钟；
     - 新版本开始时刻 = `greatest(:now, 当前版本.effective_from_at, 该角色已有版本的 max(effective_to_at))`；当前版本的关闭时刻取同一值，保证区间不倒挂、不与已关闭的版本重叠；
     - 实际钟点 `:now` 写进审计 detail；
     - 1a 不支持预约未来生效，未来能力留在规则卡。
   - **写锁协议**：
     - 修订、启用、停用、删除角色时，先 `SELECT … FROM roles WHERE role_id = :id FOR UPDATE`；ADR-0032 第 1 项第 3 条的「有无持有人」检查与写入都在锁内；
     - 开启授予时，对所涉角色的 `roles` 行按 `role_id` 顺序 `SELECT … FOR SHARE`，再检查当前版本并写入。这样「删除或扩大效力」与「新增持有人」不会交错穿过各自的检查。
7. **系统角色定义由代码声明，启动时对账**：
   - 系统角色（`super_admin`、`employee`、安全审计员、业务管理员、组织数据管理员、流程管理员）在 `platform.identity` 中以代码声明：
     - 固定的 UUIDv7 `role_id`，写在声明里，各环境相同；
     - 名称、范围、启用状态、权限集合；
     - 单调递增的声明修订号 `declaration_revision`；
   - **对账步骤**（每个系统角色逐个提交）：
     1. `INSERT INTO roles … ON CONFLICT (role_id) DO NOTHING`；
     2. `SELECT … FROM roles WHERE role_id = :id FOR UPDATE`，重读当前版本；
     3. 比对声明修订号与库中该角色 `SEED` 版本的最大修订号：
        - 声明更大 → 关闭当前版本、追加新版本，渠道 `SEED`，记修订号，理由写声明出处；
        - 声明更小 → 告警，不写，以库中当前版本为准（旧代码在新库上启动的情形）；
        - 相等而内容不同 → 启动失败并告警（改了声明却没提高修订号）；
        - 相等且内容相同 → 不动。
   - **为何用行锁而不用 `pg_advisory_xact_lock`**：行锁就是第 6 条的写锁协议，界面修订、删除与授予都要取它，对账因此与所有写入者天然互斥，且粒度到单个角色；咨询锁是另一套命名空间，界面写入不会取，挡不住对账与界面修订的交错。
   - **时点**：对账在上下文刷新的单例初始化阶段完成（与 ADR-0030 第 1 项第 4 条数据库判据的时点相同），先于任何 `ApplicationRunner`（含运维命令入口 `OperationsCommandRunner`）、先于事件监听与未完成事件的重新投递、先于定时任务、先于 HTTP 就绪。对账失败时进程不启动。
   - **迁移不再写角色权限**：DDL 迁移只建表，`roles`、`role_versions` 不由迁移写入，守护第 8 条扫描迁移文件。系统角色的主键来自声明中的固定 UUIDv7；ADR-0033 草稿迁移方案第 2 条须同步写明这一点（整合者同步）；
   - ADR-0032 第 1 项第 3 条第四点的约束同样适用于对账：首次部署后，若声明给已有当前持有人的系统角色加入双人逐人级权限码，启动失败并告警。首次部署时的声明即基线，不需例外。

### 2. 授予版本化

1. **`account_roles` 退役，新建 `platform_identity.account_role_grants`**（角色授予，提议术语），一行表示「某账号在一段时间内持有某角色」：
   - `account_role_grant_id uuid`：主键（UUIDv7）；
   - `user_id uuid NOT NULL`、`role_id uuid NOT NULL`：同 schema 外键，`ON DELETE RESTRICT`；
   - `effective_from_at timestamptz NOT NULL`、`effective_to_at timestamptz`：空表示未关闭；
   - **开启列**：
     - `granted_by uuid`；
     - `grant_channel_kind`：授予渠道，见第 3 条；
     - `grant_authorization_request_id uuid`；
     - `migration_batch_id uuid`；
     - `grant_audit_entry_id`：同一事务写入的审计条目 ID，跨 schema 只存 ID、不建外键。
   - 本 ADR 中所有引用其他表的 ID 列（`role_id`、`user_id`、各 `*_authorization_request_id`、`migration_batch_id`、`revocation_sync_run_id`、各 `*_audit_entry_id`），类型一律跟随 R-1b 是否已合并：已合并用 `uuid`，未合并跟随被引用列当时的类型，R-1b 统一改。
   - **关闭列**：
     - `revoked_by uuid`；
     - `revocation_cause_kind`：收回原因，见第 4 条；
     - `revocation_authorization_request_id uuid`；
     - `revocation_sync_run_id uuid`：仅离职关闭，记触发的同步运行；
     - `revocation_audit_entry_id`。
   - **约束**：
     - `EXCLUDE USING gist (user_id WITH =, role_id WITH =, tstzrange(effective_from_at, effective_to_at, '[)') WITH &&)`：同一人同一角色至多一条开放行；
     - 开启侧成对 CHECK：
       - `MANUAL` 须有 `granted_by`；
       - `MIGRATION` 须有 `migration_batch_id`，其他渠道不得有；
     - 关闭侧成对 CHECK：
       - `effective_to_at`、`revocation_cause_kind`、`revocation_audit_entry_id` 同空同非空；
       - `MANUAL` 须有 `revoked_by`；
       - `SEPARATION` 须有 `revocation_sync_run_id`、`revoked_by` 为空，其他原因不得有 `revocation_sync_run_id`；
     - `CHECK (effective_to_at IS NULL OR effective_to_at >= effective_from_at)`，以及与角色版本相同的 `isfinite` CHECK；
     - `BEFORE INSERT` 触发器：`role_id` 没有开放的角色版本（已删除）即拒绝。
   - **索引**：
     - `(user_id) WHERE effective_to_at IS NULL`、`(role_id) WHERE effective_to_at IS NULL`：当前读取与持有人计数；
     - `(user_id, effective_from_at)`：按时刻还原。
2. **只追加 + 关闭区间**：
   - 「收回」= 把开放行的 `effective_to_at` 置为 `greatest(:now, effective_from_at)`，同时写入关闭列；
   - 触发器只许改六个关闭列：`effective_to_at`、`revoked_by`、`revocation_cause_kind`、`revocation_authorization_request_id`、`revocation_sync_run_id`、`revocation_audit_entry_id`。每列只许由空变非空一次；已关闭的行不能改；任何行不能删除或清空；
   - 同一人再次获得同一角色，新增一行，开始时刻 = `greatest(:now, 此人此角色已有行的 max(effective_to_at))`。这是关闭后再开的下界：时钟较慢的节点不会开出与已关闭区间重叠的行而撞上排他约束。
3. **授予渠道** `grant_channel_kind`：
   - `MANUAL`：账号授权界面，含经双人确认的申请；
   - `DEFAULT_ROLE`：建档或复职时的默认角色（RULE-344；D-1a-17）；
   - `OPERATIONS`：运维命令 `grant-role`（ADR-0026 第 5 项第 5 条、ADR-0030）。操作人与见证人是自报文本，记在审计中，`granted_by` 为空；
   - `MIGRATION`：老角色迁入（ADR-0026 第 8 项）。
4. **收回原因** `revocation_cause_kind`：`MANUAL`（账号授权）、`SEPARATION`（离职）、`OPERATIONS`（运维命令 `revoke-role`）、`MIGRATION_ROLLBACK`（迁入批次回退）。
5. **整组替换改为按差异逐条关闭与新增**：
   - 账号授权接口仍提交「改后的完整角色集合」，请求体不变；
   - 应用时以当时的当前有效授予为基准求差：不再需要的关闭，新增的开启，不变的不动；
   - **授权申请记基准**（概念 base_version，提议术语「基准版本」）：
     - `authorization_requests` 增加两列：
       - `base_account_version_number`：账号授权申请记申请时 `user_accounts.version`；
       - 相关角色当时的 `role_version_id` 数组：账号授权申请记申请后集合与当时持有集合中每个角色的当前版本；角色修改申请记该角色的当前版本。这与 ADR-0033 草稿「引用版本行的 UUIDv7」一致，列名在实现 PR 中按 NAMING_STANDARD 定；
     - **比对在执行确认的监听器事务内**：`ApplyConfirmedAuthorization` 是 `@ApplicationModuleListener`，在同一事务内先按第 1 项第 6 条取锁，再比对账号版本与各角色当前版本；
     - 任一不一致，申请作废，提示按最新状态重新发起；
     - **状态机**：
       - 现有 PENDING → CONFIRMED / REJECTED 之外，增加 CONFIRMED → VOIDED（作废），与 ADR-0032 第 1 项第 3 条「确认时复核仍无持有人，否则作废」共用这一状态；
       - 作废写审计 `platform.identity.authorization.voided`（原因：基准已变 / 已有持有人）；
       - 监听器拒绝应用时，申请转为 VOIDED，不再停在 CONFIRMED；
   - RULE-346 记的是老系统「插入新的、删除缺的」，只作证据，存储不照搬。
6. **老角色迁入的批次**（取代 ADR-0026 第 8 项第 7 条中的两处、回滚方案第 4 条）：
   - 迁入只新增授予，渠道 `MIGRATION`，带 `migration_batch_id`；
   - 此人已有该角色的开放授予时跳过，记入差异报告，不覆盖；
   - 回退一个批次 = 关闭该批次仍开放的授予，原因 `MIGRATION_ROLLBACK`，并吊销相关会话；
   - 迁入前的状态按第 4 项第 3 条还原，不另建快照表。
7. **聚合**：
   - 授予行是 `UserAccount` 的子行：聚合加载当前有效授予（授予行 ID、角色、开启时刻），保存时只写差异，以 `user_accounts.version` 做乐观锁；
   - 时刻、操作人、渠道或原因、申请与同步运行 ID 由应用服务作为参数传入领域方法；
   - 不新增跨聚合事务。

### 3. 离职与复职

1. **离职：关闭全部有效授予**（取代 ADR-0027 第 1 项第 6 条与 ADR-0032 第 4 项第 1 条中的「删除」）：
   - 同步把某人标为离职、且该运行不处于 HELD 时，关闭其全部当前有效授予，含 `super_admin` 与安全审计员；
   - 原因 `SEPARATION`，收回人为空，记同步运行 ID。同步运行 ID 由 `OrgSnapshotChanged` 提供，现有负载没有该字段的，实现时在事件契约中补上。
2. **安全效果不变**：
   - 处置完成后，此人没有任何当前有效授予，即时吊销会话并清缓存；
   - 应急账号停用、会话吊销、HELD 约束（ADR-0027 第 1 项第 7 条，经 ADR-0028、ADR-0030 修订）、不另发通知，全部照旧。
3. **逐条审计照旧**：每关闭一条授予写一条 `platform.identity.account.role.revoked`，detail 含授予行 ID、原因与实际钟点；条目 ID 回写授予行。为此 `AuditLog.record` 返回条目 ID（api 变更）。
4. **收回时刻不是离职日期**：区间记录的是系统实际收回授权的时刻。业务上的离职日期与观察时刻按规则卡 `docs/business/rules/workforce-history-rules.md`「候选规则：离职申请的预计离职日期与离职观察时间是两件事，不混用」另行记录，本 ADR 不用离职日期回填区间。
5. **复职**（D-1a-17，用户「只授基础角色 (Recommended)」）：
   - 同步把离职者重新标为在职时，以 `DEFAULT_ROLE` 渠道新开一条 `employee` 授予，并写审计；
   - 离职前的其他授予不自动恢复，由管理员按授予方式重新授予，每次新增一行；
   - **F-13 在本 ADR 的授予表上实现**，不先在 `account_roles` 上实现再迁移。

### 4. 读取

1. **当前有效授予** = `effective_to_at IS NULL`，不带时刻参数：
   - 排他约束保证同一人同一角色至多一条开放行；
   - 授予与版本都不预约未来，所以开放行就是当前有效。
   - `effective_from_at` 只服务按时刻还原。
   - 当前角色版本同理：该角色 `effective_to_at IS NULL` 的那一行。
   - 三种谓词的比较见备选方案。
2. **只看当前有效的地方**：
   - 每请求权限与数据范围；
   - I-12 自查；授予上限；
   - 超管与审计员持有人计数：HELD 判定、放行下限、应急账号每日核对与登录、管理模式进入；
   - 敏感判定：`roleIsSensitive` 读当前版本；ADR-0032 的「有持有人」；
   - 角色删除前的占用检查；账号详情与角色列表。

   这些读取都经仓储中同一个谓词常量，不在调用方各写一份。
3. **按时刻还原**：
   - 谓词：`tstzrange(effective_from_at, effective_to_at, '[)') @> :asOf`，同时作用于授予与角色版本。
   - 得到「某人在 `asOf` 持有哪些角色，每个角色当时的名称、状态、范围类型与完整权限集合」。
   - 零长区间（开立即关）为空区间，不出现在任何时刻的还原结果中。
   - 早于最早记录的时刻：失败并告警，不回退到最早版本（D17 细则第 5 条）。
4. **还原的边界**：
   - 能还原的是范围**类型**与角色版本上的自定义部门明细（第 5 项）；
   - 相对范围（`OWN_ORG_UNIT`、`OWN_ORG_UNIT_SUBTREE`、`SELF_AND_DIRECT_REPORTS`）当时实际覆盖哪些部门和人，须再联 `assignment_versions`、`org_unit_versions` 按日期求得。精度按日，依据是同步观察日（`OBSERVED`），不是人事生效日。
5. **本 ADR 只交付仓储层的按时刻还原方法**（`AuthorizationHistory` 一类只读仓储），由守护直接测试：
   - 不交付查询接口、导出接口和新权限码，OpenAPI 不变；
   - **为何后做更有价值**：
     - 唯一的使用场景是季度授权复核（ADR-0026 第 6 项第 3 条，已推迟到 1b 之后）和审计导出，其报表形状、复核人与权限分级尚未定，现在定接口和权限码只能猜；
     - 不可逆的是数据，接口不是：从首次部署起历史就完整入库，以后随复核功能加接口不会丢任何记录。

### 5. 角色范围明细同样版本化（F-1 依赖本 ADR）

1. ADR-0026「1a 交付范围」中的「角色范围授予明细表」（自定义部门；1b 起的 `LISTED` 法人）挂在**角色版本**下：
   - 引用 `role_version_id`，`ON DELETE RESTRICT`；
   - 每个版本存完整明细，行写入后不可改；
   - 改明细即新增角色版本。
2. 表名与列名由 F-1 按 NAMING_STANDARD 与 `terms.yaml` 定（ADR-0026 影响面暂名 `role_scope_grants`）。若明细只是部门 ID 集合，可同第 1 项第 3 条存为版本行上的数组，由 F-1 择定并说明。
3. **F-1 依赖本 ADR**：F-1 的范围计算读当前角色版本的明细，按时刻还原同时还原明细。F-1 不得先按「挂在 `roles` 下、整组替换」实现再改。

### 6. 实施时机

1. 属安全项，**首次部署任何环境前完成**。在 W2 由**一张独立的卡**与 K-2 时态基座同期实现（`phase1a/NEXT_BATCH_PLAN.md`:52-56）。
2. K-2 提供时刻（`timestamptz`）变体：区间类型、只追加触发器与 D2 守护；本卡是该变体的首批使用者。
3. 列类型按 ADR-0033（提议）的标识形态：`role_id`、`user_id` 为 `uuid`。R-1b 未合并时，跟随当时的类型。
4. 在 F-1、F-13 之前或同一 PR 中落地。

## 回滚方案

- **首次部署前**：回退实现提交，基线恢复，守护一并回退。没有数据需要处理。
- **首次部署后**：
  - 不再回到「删除」语义：已关闭的授予与旧版本行是授权历史，不删除；
  - 出问题以修复提交前进；
  - 确需临时退回整组读取的，由当前有效授予在只读视图中投影出「账号 → 角色」与「角色 → 权限码」供旧代码读取，写入仍走新表；
  - 系统角色定义的回退：把声明内容改回旧值，同时**提高**声明修订号，启动对账追加一个内容为旧值的新版本。只回退代码而不提高修订号的，对账因修订号小于库中已有而告警不写，库中定义不变。
- **边界**：已写入的授予行、角色版本、审计与事件不回滚；已因离职关闭的授予不会因回滚重新生效。

## 需同步修改的守护规则

与本 ADR 的实现在同一个 PR 中提交（W2 独立卡，与 K-2 同期；实施会话由 one-coordinator 派定）：

1. **禁止删除与改写**（`GrantHistoryAppendOnlyIntegrationTest`，参照 `OrgHistoryAppendOnlyIntegrationTest`）：
   - `account_role_grants`、`role_versions`：DELETE、TRUNCATE 被拒绝；改已关闭行被拒绝；改开放行中关闭列以外的列被拒绝；关闭列二次改写被拒绝；
   - `roles`：改 `code`、`kind`、`is_administrative` 被拒绝；
   - 已删除角色上新开授予被 `BEFORE INSERT` 触发器拒绝；
   - `RoleSeparatedDeploymentIT`：运行角色对两张新表执行 DELETE、TRUNCATE 均为 `permission denied`。
2. **区间不重叠与区间形态**：
   - `DataArchitectureTest` 的 D2 扩展时刻变体：`effective_from_at timestamptz NOT NULL`、可空 `effective_to_at`、`tstzrange` 的 `EXCLUDE`、`>=` 与 `isfinite` CHECK；注入样例：缺 `EXCLUDE` 或缺 `isfinite` 的时刻版本表必须失败；§4b 清单与注册表一致；
   - **性质测试**（`GrantIntervalPropertyTest`）：
     - 随机序列包含开启、关闭、同刻开关、时钟回拨，以及「快节点关闭后、慢节点再开」；
     - 结果始终满足：每人每角色至多一条开放行；无倒挂区间；不撞排他约束；
     - 任一时刻的还原结果，等于按序列回放得到的集合；
     - 角色版本按同一序列验证。
   - `permission_codes` CHECK：含 NULL、重复或未排序的数组被拒绝；应用写入前已规范化。
3. **当前有效读取一致性**（`CurrentGrantReadConsistencyIntegrationTest`）：
   - 夹具含已关闭授予、开放授予、已关闭的旧角色版本与当前版本；
   - 下列读取方只反映开放授予与当前版本：
     - `SessionPrincipals`、`PrivilegeCeiling`、`ReplaceAccountRoles`、`UpdateRole`、`DeleteRole` 的 I-12 自查；
     - `AdministratorSeparationReview`、`RoleHolders`、`EmergencyBinding`、`ReconcileEmergencyAdmins`；
     - `EnterAdministratorMode`、`LoginAsEmergencyAdmin`、`LoginWithSignedTicket`、`ForceUserLogout`；
     - `GetCurrentUserProfile`、`GetUserAccount`、`OrgUnitScopes`；
     - `roleIsSensitive`。
   - **时钟偏差用例**：读取节点的时钟早于新授予或新版本的开启时刻时，新授予与新版本仍为当前，I-12 仍拒绝改自己持有的角色；读取时钟早于关闭时刻时，已关闭授予仍不算有效。
   - **文本守护**：`src/main` 中触及 `account_role_grants`、`role_versions` 的 SQL，要么引用当前有效谓词常量，要么属于 `AuthorizationHistory`，否则失败。
4. **离职与复职**（`SeparationRevokesRolesIntegrationTest`，即 ADR-0027 守护第 2 条，取代其中「`account_roles` 已删除」一句）：
   - 离职：
     - 同步标为离职后，当前有效授予为零（含 `super_admin`）；
     - 授予行总数不变，每行原因 `SEPARATION`、带同步运行 ID 与审计条目 ID；
     - 应急账号停用，会话吊销；
     - HELD 期间不关闭，放行后关闭；
   - 复职：
     - 重新标为在职后，只有一条新开的 `employee` 授予，渠道 `DEFAULT_ROLE`，写审计；
     - 离职前的其他授予仍为关闭。
5. **时刻边界**（`GrantClockEdgeIntegrationTest`，固定时钟）：
   - 「开立即关」：同一时刻开启并关闭，得到零长区间，关闭成功，会话被吊销；
   - 「关闭早于开启」：注入时钟回拨到开启时刻之前再关闭，关闭时刻取开启时刻，关闭成功，会话被吊销，审计 detail 记实际钟点；
   - 角色版本同理：时钟回拨时新版本开始时刻不早于当前版本。
6. **按时刻还原**（`AuthorizationHistoryAsOfIntegrationTest`，直接测仓储）：
   - 序列：t1 建角色（权限 {A}、范围 SELF）并授予某人；t2 改为 {A, B}、范围 ALL；t3 离职关闭；
   - 复职用例：t4 复职，只还原出 `employee`；
   - 手工再授予用例：t5 管理员重新授予该角色，新开一行；
   - 在各区间内查询，角色、权限集合与范围类型逐项等于当时的值；
   - 早于 t1 的查询失败并告警。
7. **按差异写入与并发**：
   - `ReplaceAccountRoles` 由 {X, Y} 改为 {Y, Z}：只关闭 X、只开启 Z，Y 的授予行 ID 与开启时刻不变；
   - 授权申请：申请后账号版本或任一相关角色的当前版本变了 → 监听器在持锁事务内把申请转为 VOIDED、写 `platform.identity.authorization.voided`，申请不停在 CONFIRMED；
   - `UpdateRole` 每次修改恰好新增一个版本，内容不变时不新增；删除仍被持有的角色返回 409；
   - **两事务交错**（`RoleGrantLockIntegrationTest`）：
     - 事务甲删除角色、事务乙同时授予该角色，只有一个成功，结果不会出现「已删除角色上有开放授予」；
     - 事务甲给无持有人的双人逐人级角色扩大效力、事务乙同时授予该角色，结果符合 ADR-0032 第 1 项第 3 条。
8. **系统角色声明与迁移**：
   - `SystemRoleDeclarationIntegrationTest`：
     - 空库启动建出全部系统角色，`role_id` 等于声明中的固定值，版本 1 记声明修订号；
     - 声明不变时重启不新增版本；修订号提高时追加 `SEED` 版本；
     - 修订号更小时告警、不写；修订号相等而内容不同时启动失败；
     - 两实例同时启动结果相同；
     - 对账先于 `ApplicationRunner`、事件监听、定时任务与 HTTP 就绪执行；
   - 首次部署后，声明给有持有人的系统角色加双人逐人级码，启动失败；
   - 迁移扫描：迁移文件写 `roles`、`role_versions` 数据即失败（扩展 ADR-0032 守护第 4 条的迁移扫描；该守护随 ADR-0032 实现落地）；
   - **权限目录**：
     - 测试库中全部角色的**当前**版本的码都存在且未停用；历史版本不要求，按原文本还原；
     - 目录中的码只能标停用，不能删除（快照比对）；
     - 运行时读到未知码：该码被忽略并告警，同一角色的其他码照常生效，不抛异常。
9. **`SingleAggregateGuardTest` 核对**：
   - 本 ADR 不新增多聚合事务，`multi-aggregate-exceptions.txt` 不变；
   - 表到聚合的映射登记 `account_role_grants` → `UserAccount`、`role_versions` → `Role`；
   - `HandleOrgSnapshotChange` 在一个监听事务中处理多名离职者，属同一聚合类型的多个实例，核对守护结论不变；
   - 启动对账按角色逐个提交。
10. **其余守护同步**：
    - `RepositoryWriteGuardTest`：新表写入经 `roles.version` 或 `user_accounts.version` 乐观锁，`unversioned-table-writes.txt` 按需登记理由；
    - `TimeSourceGuardTest`：新 SQL 不含数据库时钟，`greatest(:now, …)` 的 `:now` 为参数；
    - `PrimaryKeyTypeGuardTest`：新表为 `uuid` 主键；
    - `DdlNamingTest`：新列类别词；
    - `MustAuditActionsTest`：事件新增字段与审计动作；
    - `GlossaryTest`：提议术语；
    - SECURITY_INVARIANTS I-14 的验收测试对照（守护第 1、4、6 条）。
11. **ADR-0026、ADR-0027 守护中直接读写 `account_roles` 的测试**：`SensitiveGrantTwoPersonIntegrationTest`、`RoleManagementIntegrationTest`、`EmergencyLoginIntegrationTest`、`AdministratorModeIntegrationTest`、`SyncLockoutGuardIntegrationTest` 等，改为按当前有效授予断言，断言强度不降低，逐条列在 PR 中。

## 后果

- 任何时刻「谁持有什么角色、这个角色当时含什么权限、范围类型为何」都能从库中直接还原，不依赖 30 天的事件归档或审计 detail 的拼接；季度复核与安全取证有了数据来源。
- 离职的安全效果不变；复职按 D-1a-17 只重开 `employee`，且与离职前的授予在历史中可分辨。
- 授予与角色定义的每次变化都带操作人、渠道或原因、申请、审计条目，双人确认能追到具体的授予行与角色版本。基准版本使「申请后被别人改过」的申请自动作废。
- 系统角色定义从迁移移到代码声明，改系统角色权限即改代码，经评审与启动对账留下版本。
- **代价**：
  - 写入要求差与持锁；
  - 14 个以上测试文件的夹具要改写；
  - 被删除角色的编码不能复用（0034-Q3）；
  - 查询接口推迟，在接口落地前，历史只能经仓储或数据库只读账号查看。
- 本 ADR 不新增「不得给离职者授予」的规则：离职者的普通会话按在职复核失效（ADR-0027 第 1 项第 4 条），授予本身不生效。是否在授予时拒绝离职者，另行在规则卡中提出。

## 备选方案（未采用）

- **保留删除，靠审计日志还原**：
  - 审计 detail 只有角色码，角色定义变更只有 `roleId`，拼不出「当时含哪些权限、范围多大」；
  - 事件归档 30 天；
  - 还原依赖解析自由文本，与 intent 155 把审计拆成结构化列的方向相反。
- **事件溯源**：每请求权限要依赖投影的及时性；现有模块都以表为事实、事件为通知，单为授权引入第二种持久化范式，代价与风险都高于区间表。
- **只版本化授予、不版本化角色**：回答不了「这个角色当时含哪些权限」。角色加码与放宽范围正是 ADR-0032 第 1 项第 3 条防范的扩权路径，不版本化就无法事后核查。
- **对账用 `pg_advisory_xact_lock`**：实现简单，但界面修订与授予不会取同一把锁，挡不住对账与它们交错；行锁与第 1 项第 6 条的写锁协议同一套。
- **当前有效的三种谓词**：
  - (1) 区间包含注入时刻：读取节点的时钟落后于关闭节点时，把刚收回的授予算作有效（收回 fail-open）；
  - (2) 未关闭且已开始：读取节点的时钟落后于开启节点时，看不到刚生效的授予或新版本，I-12 的「不能改自己持有的角色」会放过（自查 fail-open）；
  - (3) 未关闭（采用）：不依赖读取节点的时钟，靠排他约束保证至多一条开放行，且授予与版本都不预约未来。若以后需要预约生效，须另立 ADR 重新选择谓词。
- **角色权限用成员子表**：版本不可变，集合是版本的值；子表多一张只追加表、多一组 D1 / D2 特例，读写都要多一次往返，换不来任何约束上的好处。
- **系统角色继续由迁移写入**：迁移无法使用注入时钟，也无法检查当前持有人；改系统角色要写新迁移，基线关闭后与 ADR-0032 的迁移约束交织。代码声明加启动对账，用同一套版本写入路径。
- **用 `tstzrange` 单列存区间**：NAMING_STANDARD §2.4 没有区间类别词，而现有版本表与触发器都用两列。两列 `_at` 加排他约束中的 `tstzrange` 表达式，语义相同。
- **现在交付历史查询接口与权限码**：报表形状与复核人未定，只能猜；数据已完整入库，接口可随季度复核再做，不丢记录。
