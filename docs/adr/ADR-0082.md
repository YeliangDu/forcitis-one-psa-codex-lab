## 背景

ADR-0081 决定 3 写明更正前当天不在职（撤销错误的离职）时不生成任职变化条目，因为待调整权限表要求任职变化条目前后部门均非空。用户 2026-11-03 就此答「应该做」：撤销错误离职、让人恢复在职时，对其原有敏感角色重新做权限复核。触发出处：one-lead 2026-11-03 转述该决定并要求裁定形状（#730 评论 6599023412），非用户指派起草。

## 决定

撤销错误离职的 `EmployeeCorrected`（更正前当天不在职、更正后在职）为当事人每个现有敏感角色生成一条敏感角色复核条目，放宽一条检查以容纳「更正前部门为空」，其余照 ADR-0081 不变。

1. **条目**：类型 `SENSITIVE_ROLE_REVIEW`，来源 `ASSIGNMENT_CHANGE`，触发字段 `ORG_UNIT`，触发命令 ID 取 `EmployeeCorrected.personnelCommandId`，更正前部门为空，更正后部门为当天部门，岗位列照事件，更正前岗位为空；每个现有敏感角色一条，去重键不变（类型，人，人事命令 ID，触发字段）；无收件人；不生成范围复核条目（用户只提敏感角色，范围复核需要前部门才有可缩的范围）。
2. **事件**：该情形的 `EmployeeCorrected` 带 `triggerFieldKinds = [ORG_UNIT]`，`previousOrgUnitId`、`previousPositionId` 为空，`newOrgUnitId`、`newPositionId` 有值；监听器不得因前部门为空而拒收或重试。
3. **表检查**：`ck_permission_adjustments_assignment_change` 放宽，只改前后部门这一条：来源为 `ASSIGNMENT_CHANGE` 当且仅当更正后部门非空；更正前部门可空，但仅限类型 `SENSITIVE_ROLE_REVIEW` 且触发字段 `ORG_UNIT` 的任职变化条目；更正前部门非空只允许任职变化条目。其余分支（触发字段与来源成对、非任职变化行四列为空、部门变化时前后不同）不变。不增列、不增枚举值。
4. **仍不覆盖**：更正后当天不在职（更正使人离职）不生成任何条目，由离职关闭路径处理；监听器不得因此重试。ADR-0081 决定 3 的其余部分不变。

## 迁移方案

表无历史数据，条目由监听器新生成，无回填。放宽检查是新迁移里的一次删除并重建约束，不触及行。

## 回滚方案

回到 ADR-0081 决定 3 只需一次迁移重建原检查；已生成的更正前部门为空的条目须先处理（办结或删除），否则新检查建不起来。F-1 尚未上线，无此类条目。

## 需同步修改的守护规则

- 表结构验收（#729 / #730）：`ck_permission_adjustments_assignment_change` 的新形状——更正前部门为空只收类型 `SENSITIVE_ROLE_REVIEW`、触发字段 `ORG_UNIT`；范围复核或岗位触发时更正前部门为空被拒；非任职变化行四列仍须为空。
- 验收（#730，one-test）：撤销错误离职的更正为每个现有敏感角色生成一条且重投不增；无敏感角色则无条目；任何情形都不生成范围复核；更正后不在职不生成且不重试。

## 后果

- 恢复在职的人在原有敏感角色上多一条复核条目，复核对象是权限本身，不改变授权。
- 更正前部门为空成为合法取值，监听器与读取方不得再假定任职变化条目的前部门必有值。
- 更正后不在职的情形仍没有条目：被更正为离职的人的敏感角色由离职关闭路径处理，若该路径不覆盖更正产生的离职，需另立卡。
