## 决定

1. **迁入通道与模块**：
   - **迁入编排模块**（提议术语「迁入编排」，模块名暂定 `platform.migration`）：依赖 `platform.integration` 的 api（迁入适配器、暂存、来源对照、迁入登记）与各目标 BC 的 api（含 `operations.facts`、`accounting.period`）；**任何模块都不依赖它**。它本身不拥有表。这与 ADR-0037 第 2 项第 3 条「迁入、对账类适配器端口只能被迁入、对账模块依赖」一致，也避免集成层反向依赖目标 BC 造成循环（例如 `platform.integration → cost.timesheet → platform.approval → platform.integration`）。
   - 抽取只在集成层的迁入适配器中进行；装载只经目标 BC `api` 中的迁入用例（与业务用例同样经领域校验，不直接写目标表）。跨 BC 的装载由编排模块按依赖顺序依次调用（例如 6e 先调 `organization.workforce` 建员工，再调 `platform.identity` 建账号）。
   - **api 预算**：每个目标 BC 的迁入只占一个 api 方法——按对象类型分派的迁入入口（入参是该 BC 的迁入命令，按对象类型分派），计入 `ArchitectureRulesTest` 的每模块 api 方法上限（`MAX_API_METHODS_PER_MODULE` = 12，`backend/src/test/java/com/forcitis/one/ArchitectureRulesTest.java`:28、:60-70），不修订该守护；迁入入口放在该 BC 已有的 `api` 包内，不新增具名接口（同文件 :398-402 只允许 `api` 与 `events` 两个出口）；试提交与正式提交共用这一个入口（第 7 条）。编排模块不暴露 api，离线命令入口在其 infrastructure。新增 ArchUnit：各 BC 的迁入入口只能被 `platform.migration` 调用。
   - **暂存记录与取值映射**：暂存记录是集成层自有的 record，只用 kernel 与 JDK 类型，经集成层 api 提供。外部取值（状态码、类型码）到自有取值的映射在集成层迁入适配器内完成（ADR-0037 第 2 项第 4 条、§14.1 D16），暂存记录里已是自有取值；编排模块只做「暂存记录 → 目标 BC 迁入命令」的形状转换，不做取值映射。
   - **事务**：迁入入口声明 `Propagation.MANDATORY`，由编排模块开启事务；不得使用 `REQUIRES_NEW`。来源对照、原编号对照、过账结果与目标行在同一事务内写入——迁入不适用 ADR-0033 第 2 项第 2 条「对照在交给领域模块之前先提交」，这样试提交回滚时对照一起回滚，不留无目标行的对照。
   - 迁入以离线命令运行，不挂在 HTTP 接口或定时作业上。离线命令进程只加载编排模块、迁入适配器与迁入用例，**不加载**：`@Scheduled` 方法、ShedLock 作业、Flowable 的异步执行器与定时执行器、事件监听（`@ApplicationModuleListener` / `@TransactionalEventListener`）、出站投递 worker。
   - **来源侧**（ADR-0037）：用运行时只读账号；每个任务开始前重跑只读校验，失败即停；读取的表与列在读取列登记中按「用途 = 迁入 / 对账」登记，随迁入规格评审（SESSION_PLAYBOOK §5「迁入读取授权」）；大表按主键分批、自动提交、低峰执行，批大小与时段写在迁入规格中；不读凭据列拒绝清单中的列。
   - **迁入数据库角色**（目标库，专用，无 DDL；命名 `one_<环境>_history_loader`，与 Flyway 迁移角色 `one_<环境>_migrator` 明显区分），授权逐项为：
     - 目标表：迁入规格列明的目标 BC 表的 `SELECT`、`INSERT`，不超过应用运行角色对这些表的授权；不授 `UPDATE`、`DELETE`（更正走冲销）；
     - 迁入登记：`migration_batches`、`migration_rejects`、`migration_tie_outs`、`source_references`、`platform_numbering.legacy_numbers` 的 `SELECT`、`INSERT`；`UPDATE` 只限批次状态列、断点列、对照状态列与对照的批次列；拒收处置与核对签字列不授（第 7、8 条由应用内操作录入）；
     - 暂存表：`SELECT`、`INSERT`，以及按批次的 `DELETE`（重新暂存时清空本批次）；
     - 期间迁入占用：经 `accounting.period` 的迁入 api 写入，表授权同上（`SELECT`、`INSERT`、状态列 `UPDATE`）；
     - 审计：`platform_audit.audit_entries` 的 `INSERT`；
     - 不授 `platform_integration.event_publication` 与出站投递表的任何写权限。
   - 连接上限计入实例连接数预算（INFRA_RUNBOOK，ADR-0025 第 2 条）；只在批准的时间窗内 `LOGIN`，时间窗外 `NOLOGIN`，开关由 one-ops 执行并记运维记录。
2. **来源标识**：来源系统沿用 ADR-0033 第 2 项第 8 条的三个代码，只出现在集成层的来源对照与迁入登记中；领域模块与 kernel 不出现来源系统名。老 ID 一律登记为来源对照，迁入行的主键是新生成的 UUIDv7。遇到文本形态的来源标识时，另立条款修订 ADR-0033 第 2 项第 1 条，本 ADR 不定。
3. **迁入批次与来源对照**：
   - 每次运行是一个迁入批次（MigrationBatch），登记在 `platform_integration.migration_batches`：来源系统、对象类型、范围（期间 × 法人）、状态、断点、开始与结束时刻、行数、来源 ID 集合摘要、关联号、操作人。
   - **批次状态机**：暂存中 `STAGING` → 待核对 `AWAITING_TIE_OUT` → 提交中 `COMMITTING` → 已生效 `EFFECTIVE`；`AWAITING_TIE_OUT` 可退回 `STAGING`（核对不通过、修正后重新暂存）；`STAGING`、`AWAITING_TIE_OUT` 可转为已放弃 `ABANDONED`；`COMMITTING`、`EFFECTIVE` 可转为已冲销 `REVERSED`。**终态只有 `ABANDONED` 与 `REVERSED`**。抽取、暂存与试提交都在 `STAGING` 内进行，试提交无拒收或拒收全部有处置后才转为 `AWAITING_TIE_OUT`。
   - **业务表不加 `migration_batch_id`**（用户已定）。批次挂在来源对照上，`source_references` 新增三列（修订 ADR-0033 第 2 项第 1 条）：
     - `migration_batch_id uuid`：为空表示由来源同步或人工登记分配，非迁入；记最近一次确认该对照的批次；
     - `source_row_digest bytea`：来源行规范化后的 SHA-256；与 `migration_batch_id` 成对 CHECK 同空同非空；
     - `source_reference_status`：对照状态，当前 `CURRENT` / 已冲销 `REVERSED`；只有事实类的来源对象类别可以为 `REVERSED`（CHECK）。ADR-0033 的两个自然键改为只约束「已确认且当前」的行。
   - 逐行追溯经「自有 ID → 来源对照 → 批次」。
   - `platform_numbering.legacy_numbers` 的「导入批次」`import_batch` 在 R-1b 改为 `migration_batch_id uuid NOT NULL`（#139）。
   - 「迁入批次」是唯一写法（G-MG6）。
4. **迁入单据的编号**（用户已定：编号列存原编号作展示号）：
   - 迁入单据的编号列存原编号，作展示号；不向编号服务取号、不耗计数器。
   - **以原编号对照为准**：`legacy_numbers`（带来源系统，ADR-0033）是权威对照；单据编号列只是展示副本，不一致时以 `legacy_numbers` 为准并告警（G-MG9）。
   - 迁入标记只在事实行（第 6 条）；单据表不加迁入标记列，是否迁入经来源对照判断。
   - 单据表的编号 CHECK 写作「编号非空，或状态为草稿」（ADR-0031：草稿未取号前可以丢弃）。
   - 原编号与已有编号在（单据类型, 编号）唯一约束上冲突时拒收（原因代码「编号冲突」），不改写原编号。
   - **适用的对象类型**：有业务编号列的单据，即 `platform.numbering` 的单据类型——工时单（Phase 2）；合同与收入确认单（6a）；开票与回款（6b）；费用、付款与预提（6c）；分包与采购（6d）。不适用：主数据（老 ID 进来源对照）；权责事实行（带迁入标记）；条款、修订等「父号-序号」的子级（随父单据）。
5. **迁入不产生副作用**：
   - 迁入用例**不发布领域事件**。理由：L1 的财务事实直接读 `operations.facts` 过账明细（ADR-0025 第 3 条），不依赖事件；累积快照可随时从 OLTP 重建（ADR-0025 回滚方案）。
   - **内部订阅方清单**（取自 `docs/architecture/events/*.yaml` 的 `x-event.consumers`，2026-10-15；每个迁入阶段的规格按当时的事件目录重列）：

     | 订阅方 | 订阅的事件 | 类别 | 迁入时的处理 |
     |---|---|---|---|
     | `platform.audit` | 各模块几乎全部事件 | 有状态派生（审计条目） | 改为按批次审计（第 11 条），不逐行补写 |
     | `cost.timesheet` | `ApprovalCompleted` | 有状态派生（工时单状态随审批结论） | 迁入不经审批，审批结论作为单据状态直接迁入 |
     | `platform.approval` | `DocumentSubmittedForApproval`（`StartApprovalOnSubmission` 据此启动流程） | 有状态派生（流程实例） | 迁入不启动流程实例；在途审批的单据按 U-4 处理 |
     | `platform.approval` | 本模块的任务、轮次、超时、升级事件 | 通知 / 外发（企业微信卡片、超时提醒） | 跳过 |
     | `platform.identity` | `OrgSnapshotChanged`、`EmployeeRegistered`、`AccountSeparated`、`AuthorizationConfirmed` | 有状态派生（建账号、离职关闭授予、应用授权） | 现有迁入对象不产生这些事件；6e 若迁入员工档案，由编排模块依次调用 `organization.workforce` 与 `platform.identity` 的迁入用例完成 |
     | 各单据模块（ADR-0031 第 7 项第 3 条） | 过账完成事件 | 有状态派生（过账结果表） | 迁入用例在同 BC、同一事务内同步写过账结果表，冲销同样同步写 |
     | `reporting` 累积快照（ADR-0025 第 3 条） | 过程事件 | 有状态派生 | 批次生效后由运维命令对受影响的累积快照从 OLTP 全量覆盖 |

   - 不发通知、不向外部系统推送、不耗编号计数器、不启动流程实例。
   - `accounting.ledger` 不为迁入标记的事实生成分录：历史凭证不迁（ADR-0025 第 6 条、GL-083 迁期初余额），在途凭证由 A8 插件推完（ADR-0022 迁移方案「在途单据」）。
6. **历史期间、迁入占用与迁入过账通道**（用户已定：新增终态「历史期间」）：
   - `accounting.period` 新增期间状态取值「历史期间」：终态，**永不接受业务过账，只接受迁入过账通道**。每个法人在 FORCITIS one 首个业务期间之前的 (期间, 法人) 经 `accounting.period` 的迁入 api 建为历史期间，写审计；历史期间不能转为其他状态，其他状态也不能转为历史期间。
   - 「历史期间」是会计类用语，按 ADR-0018 登记为提议术语，**待财务确认**（U-3）。
   - **迁入占用**（`accounting.period` 自持，表 `accounting_period.migration_period_reservations`：期间、法人、批次、占用状态「已登记 / 提交中 / 已解除」）：
     - 批次开始时经 `accounting.period` 的 api 为范围内每个 (期间, 法人) 登记占用；目标期间为 CLOSING / CLOSED 时登记失败，该部分按 U-1 处理；
     - **已登记的占用不挡关账**：批次在暂存中、待核对时，期间可照常关账；
     - 批次转为提交中时，在同一事务内**先锁期间行，再锁占用行**，复查目标期间仍是历史期间或开放期间，并把占用改为「提交中」；复查不通过即不能提交（该部分按 U-1）；
     - 批次生效、放弃或冲销时解除占用；
     - **补充 ADR-0022 第 10 条的关账前置检查一项**：该 (期间, 法人) 没有「提交中」的迁入占用。开账转关账（OPEN → CLOSING）同样**先锁期间行，再读占用行**，锁顺序与上一条一致，避免死锁；关账检查只读本模块的表；
     - 迁入过账通道写入时校验本批次对该 (期间, 法人) 有「提交中」的占用，没有即拒绝。
   - **闸门在批次上**：批次核对通过或差异经签字（第 8 条）才能提交，提交后复核一致才转为已生效；历史期间不逐期关账，不发关账事件，不触发 ADR-0025 的 L2 冻结；历史期间的经营存量分析来自只进 OLAP 的历史（ADR-0025 第 6 条）。
   - 迁入过账通道在 `operations.facts`：与业务过账同样校验借贷平衡、幂等键、法人一致；期间校验改为「历史期间或开放期间」；事实行带迁入标记（取值原生 / 迁入）；不发布事件（第 5 条）。
7. **暂存、试提交、提交与拒收**（用户已定：暂存后提交）：
   - **暂存只有一份**：迁入适配器从来源分批读出后直接转换为目标形状，写入 `platform_integration` 下按对象类型的暂存表（由 Flyway 建固定的表，带 `migration_batch_id` 列，经集成层 api 提供给编排模块；不在运行时建表）。每行带来源键、`source_row_digest` 与核对所需的来源取值（金额等），不整行复制老系统原始行。暂存表是自有表，按 D13 在 `data-classification.txt` 登记分级。批次转为提交中后，触发器拒绝改写该批次的暂存行；重新暂存时按批次 `DELETE`。
   - **来源侧聚合**：按与抽取相同的主键分段、在抽取同一段的同时对来源库单独查询该段的行数、金额合计与来源 ID 摘要，作为核对的来源侧（第 8 条），不从暂存行推算。来源侧按与迁入适配器**同一映射**分组到（期间 × 法人 × 对象类型），无法映射的行单独成组。全部分段抽取完后，再对整个范围做一次整体聚合，与各段之和比较；不一致说明抽取期间来源有变动（漂移），整批重新暂存。来源 ID 摘要与顺序无关（各 ID 哈希的模和），代价是摘要只能判断集合是否一致、不能指出差在哪个 ID，摘要不一致时要逐 ID 比对生成差异清单（第 8 条）。
   - 暂存阶段按来源主键分批，批次记录断点，中断后从断点续跑；同一来源行摘要相同则跳过。
   - **试提交**（取代单独的校验模式）：编排模块按依赖顺序（主数据 → 单据 → 原事实 → 冲销事实），用与正式提交**同一个迁入入口**把整批写入目标库，最后回滚事务。迁入入口先对每行跑完领域校验再写库：领域校验不通过的行逐行进拒收、不写库，其余行继续；数据库约束错误（唯一、外键、CHECK）在首处使整个试提交失败，修正后重跑，不为逐行定位而设 SAVEPOINT。单个试提交事务不超过 10 分钟，这是本 ADR 自定的上限：试提交事务持有的快照会阻止同实例上的清理（生产库与 it_portal、dev 共用实例），把时长限在分钟级可让膨胀停留在一次常规清理能回收的量级；超出即在迁入规格中缩小批次范围。试提交回滚会消耗过账序号的序列值，**过账序号允许空号**（水位与对账按集合比较，ADR-0025 第 3 条「比集合，不比最大值」）。
   - **先迁原行，后迁冲销行**：冲销行排在其原行之后；原行不在本批次也不在目标库中的冲销行拒收。事实行只引用对照状态为当前的行。
   - **核对针对暂存数据**（第 8 条）。核对通过或差异经签字后，批次转为提交中：按块调用迁入用例提交，每块一个事务，来源对照、原编号对照、过账结果在同一事务内写入；中断后从已提交的位置续提。
   - **提交与可见性**：涉及开放（业务）期间的提交在维护模式下进行（ADR-0035 第 6 条；ADR-0035 已采纳，随 #129 合入 main）；只涉及历史期间的提交逐块可见——历史期间不接受业务过账，但已提交的块在批次生效前可被查询到，这一点与原话「批次未生效不可见」有偏离，单列为 U-5。
   - **提交后复核**：目标库与暂存表中可提交的行（不含已移出的「确认不迁」行与未通过试提交的行）按（期间 × 法人 × 对象类型）比对行数与金额，一致才转为已生效；不一致按第 9 条整批冲销。
   - **已提交的行不覆盖**：同一来源行再次出现且摘要不同时拒收，按冲销重做或单据修正（ADR-0031）处理。
   - **拒收**：不合格的行写入 `platform_integration.migration_rejects`（批次、来源对象与来源 ID、原因代码），不静默跳过。原因代码至少包括：取值无法映射、必填缺失、编号冲突、原行缺失、法人不在范围（ADR-0022 的五家法人之外）、试提交失败。处置取值：修正后重跑 `RERUN_AFTER_FIX`、确认不迁 `EXCLUDED`。**处置经应用内带权限的操作录入并写审计**（权限码在实现 PR 按 G43 定；权责事实的「确认不迁」授财务负责人，其他授业务管理员），迁入角色与运维不能代填。处置为「确认不迁」的行从暂存中移出，只留在拒收登记。批次提交前每条拒收都要有处置。超范围法人一律拒收，不自动建法人。
   - 暂存表中的批次数据在批次生效（或放弃、冲销）且该阶段切换窗口结束后由 one-ops 按批次删除。
8. **核对（迁入核对 MigrationTieOut）**：
   - **核对等式**：每个（期间 × 法人 × 对象类型），来源侧 = 暂存中将提交的行 + 拒收（按处置分列：修正后重跑、确认不迁、未处置）。**至少**比对：行数；金额合计（收入确认类同时比对含税额、不含税额、税额，ADR-0024）；来源 ID 集合摘要；按 (期间, 法人, 来源单号) 的行数与金额（ADR-0021 第 4 条第 5 款）。冲销行按冲销关系抵消后比对。无法映射的来源组全部应在拒收中。
   - 结果写入 `platform_integration.migration_tie_outs`；摘要不一致时自动输出差异清单（来源有暂存无、暂存有来源无、金额不等的来源 ID），写入核对结果。核对结果表除键、计数与哈希外还存金额合计，属于 ADR-0037 第 2 项第 3 条「需要存来源值时」的例外：按 D13 在 `data-classification.txt` 分级登记，并在表结构评审中单列。
   - 零差异，或差异经财务签字后批次才能提交。**签字经应用内带权限的操作录入**（签字人取自会话，时间、说明，写审计），运维不能代填。
   - 应核对的（期间 × 法人 × 对象类型）集合以该阶段迁入规格的对象清单为准（SESSION_PLAYBOOK §14.2 M1），缺一项即不能提交（G-MG7）。
9. **失败处理与生效后纠错**（用户已定：失败整批冲销；实现为暂存后提交）：
   - 提交前失败（暂存、试提交、核对不通过）：修正后在同一批次内重新暂存，或放弃批次；目标库不受影响。
   - **整批冲销只用于提交阶段的失败与生效后发现的错误，且是生效后纠错的唯一路径**：
     - **冲销前查下游引用**：编排模块先查本批次的行是否已被批次外的行引用（例如新系统中原生的发票引用了迁入的合同）。有引用的，先由业务按 ADR-0031 逐张冲销或修正这些下游单据，引用清零后才能整批冲销；编排模块列出未处理的引用清单并拒绝冲销。切换窗口内通常没有下游引用；窗口结束、业务开放后发现的错误，同样按此先处理下游引用再整批冲销，不另开更正路径。
     - 事实行经迁入过账通道整批冲销（ADR-0016 第 2 条允许的更正方式），原行保留并双向关联；冲销落在历史期间的仍落该历史期间（历史期间从未关账，不属于 ADR-0016 第 2 条所说的「关账后的更正」，因此不改落开放期间）；原事实所在期间已按业务关账的，冲销按 ADR-0016 第 2 条落当前开放期间并标注原期间；
     - 同一事务内把对应事实类来源对照置为已冲销，并同步写冲销的过账结果；批次转为已冲销。
   - **已冲销批次重跑 = 新批次**：新的 `migration_batch_id`，重新抽取、暂存、试提交、核对、提交，不复用旧批次的断点。事实行重新过账并建立新的当前对照；非事实行（单据、主数据）按来源对照沿用已有自有 ID，摘要相同则不重写、对照的批次列改记新批次，摘要不同则拒收并按单据修正（ADR-0031）处理。
   - **已冲销批次留下的非事实行**：必须在该阶段切换窗口结束前被一个已生效批次沿用，否则按 ADR-0031 作废，不留无事实支撑的孤行。
   - **不按数据库时间点恢复**：生产库与 it_portal、dev 同一 RDS 实例（ADR-0025 第 2 条），时间点恢复会把共用实例上的其他库一起退回。
10. **演练**：
    - 演练在 dev 进行，至少一次完整演练（含暂存续跑、试提交拒收、核对差异、提交中断续提、整批冲销后以新批次重跑）。除 6e 外可用真实数据：演练库或 schema 只有运维角色可访问；会话只拿计数与核对结果，不看明细；该阶段核对通过后删除演练数据。
    - 6e 的敏感数据（薪酬、个税社保、银行卡）只在生产迁入，dev 演练用合成数据。员工银行卡按 ADR-0021 第 1 条属员工档案主数据，随 6e（自建 HRM）迁入，按 6e 敏感数据处理。
11. **审计与老角色迁入**：
    - 每个批次在审计中记开始、暂存完成、试提交结果、核对签字、提交开始与结束、生效、冲销、放弃（操作人、批次、行数、摘要），不逐行写审计；逐行追溯靠来源对照与批次。
    - 老角色迁入（ADR-0026 第 8 项，ADR-0034 第 2 项第 6 条）同样登记一个迁入批次（对象类型为角色授予），由编排模块调用 `platform.identity` 的迁入用例：`account_role_grants.migration_batch_id`（ADR-0034 已定）指向它。这是授予行的渠道列，不受第 3 条「业务表不加批次列」限制；暂存与核对闸门不适用，按 ADR-0026 第 8 项的差异逐项确认与 ADR-0034 的批次回退执行。

## 迁移方案

1. **R-1b**（#139，首次部署前）：`legacy_numbers` 按 ADR-0033 改形状，`import_batch text` 改为 `migration_batch_id uuid NOT NULL`；`source_references` 建表时带 `migration_batch_id uuid`（可空）、`source_row_digest` 与 `source_reference_status`，自然键按第 3 条限定为「已确认且当前」（若 #139 先于本 ADR 合入，后两列与自然键范围在首个迁入阶段之前以新迁移补上）。`migration_batches` 建成之前，批次列不建外键（`legacy_numbers` 与批次表跨 schema，永不建外键；`source_references` 与批次表同 schema，批次表建成时补外键），列注释写明「迁入批次，见 ADR-0036」。实现 G-MG1、G-MG6。
2. **首个迁入权责事实的阶段之前**：建编排模块、迁入批次、拒收、核对三张登记表、暂存表、迁入占用表与迁入过账通道，期间状态加「历史期间」；实现 G-MG2、G-MG4、G-MG5、G-MG7、G-MG9；该阶段的迁入规格按 SESSION_PLAYBOOK §14.2 评审。推迟到此时更有价值的理由：此前没有任何迁入代码与目标表，守护无对象可测；登记表与暂存表的列要由首个阶段的迁入规格验证。

## 回滚方案

1. 本 ADR 未被采纳：迁入规则回到 ADR-0025 第 6 条与 GUIDING_PRINCIPLES §9a 的原文；R-1b 已做的列改名保留（只是命名）。采纳后要改变决定：另立新 ADR 取代对应条款。
2. 批次提交前失败：重新暂存或放弃，目标库不受影响。
3. 提交阶段失败或生效后发现错误：整批冲销后以新批次重跑（第 9 条），不回滚数据库；生产库与 it_portal、dev 共用 RDS 实例，时间点恢复已因用户决定（失败整批冲销）不再需要。
4. 「历史期间」的实现有问题：问题批次整批冲销后以新批次修正；状态取值本身不撤销（终态，已有行引用）。
5. 迁入编排模块出问题：只影响离线命令，不影响在线业务；停用离线命令即可。

## 后果

- 迁入有统一的模块、通道、批次、暂存、拒收与核对，每个阶段只需写迁入规格。
- 编排模块不被任何模块依赖，集成层仍只依赖 kernel，模块图无环。
- 核对在暂存数据上做、校验用试提交，目标库只接收已核对且已试过约束的数据；代价是试提交要在一个事务里写一遍整批，批次范围受事务时长约束。
- 暂存只有一份、不整行复制老系统原始行，个人信息落库最少；代价是核对的来源侧要单独对来源库做一次聚合查询。
- 历史期间是只接受迁入的终态，不需要重开已关账期间，也不需要为历史期间逐期关账；代价是期间状态多一个取值，期间模块多一张迁入占用表。
- 迁入单据保留原编号作展示号、不耗计数器；代价是编号列里新旧格式并存，且要与原编号对照保持一致。
- 业务表不带批次列；代价是逐行追溯要经来源对照，事实类对照多一个状态列。
- 迁入不发事件、离线进程不加载作业与投递；代价是有状态的订阅方要由迁入用例同步写或在生效后重建，每个阶段要按事件目录重列订阅方。
- 生效后纠错只有「整批冲销 + 新批次重跑」一条路；代价是一处错误也要冲销整批。
- 失败整批冲销而不做时间点恢复，共用实例上的其他库不受影响；代价是冲销行留在事实表中。

## 备选方案（未采用）

- **历史事实只进 OLAP，不进 OLTP**：与 ADR-0025 第 6 条、GUIDING_PRINCIPLES §9a 冲突。
- **历史期间建为可关账的「迁入中」状态，逐期关账**：关账检查对没有总账分录的历史期间不成立；用户已定终态「历史期间」。
- **迁入时以「例外重开」写入已关账期间**：ADR-0022 第 10 条的例外须财务负责人逐次审批，批量迁入会把例外变成常规。
- **把历史事实都落到当前开放期间并标注原期间**：期间口径失真（只用于 U-1 的少量情形）。
- **迁入单据按新格式发号，或编号列留空**：用户已定存原编号作展示号。
- **业务表加 `migration_batch_id` 或 `legacy_id` 列**：用户已定业务表不加批次列；`legacy_id` 已被 ADR-0033 否决。
- **编排放在 `platform.integration` 内**：集成层要依赖各目标 BC，而多个目标 BC 又依赖集成层，模块图成环。
- **单独的「只校验不提交」模式**：查不了跨行约束与数据库约束，且与提交代码是两条路径。
- **直接写目标库、读取侧过滤未生效批次**：每条读路径都要加谓词；用户已定暂存后提交。
- **来源快照与暂存各存一份**：多一份老系统原始行（含个人信息）落入生产库，多一类只读触发器与 DDL。
- **生效后另开更正批次冲销重过账**：与原批次的当前对照冲突；统一为整批冲销 + 新批次重跑。
- **切换窗口按数据库时间点恢复**：共用 RDS 实例，会退回其他库。
- **逐行写审计**：已关闭项目工时约 62 万行、收入确认约 2 万行，逐行审计会使审计表膨胀，逐行追溯已由批次与来源对照满足。
