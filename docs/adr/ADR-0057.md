## 背景

用户在 B31 确认页定「报价发出前须已用印」（B31-16，提交 `B31-20261017-122917-ctg`）。核验需要同一报价版本、用印法人、拟发文件的实际用印登记；已批准、来源审批通过或申请登记均不能替代实际用印。调度 2026-10-17 授权结构题由设计方自定，工作卡 `CON-1017-ARC-02` 要求起草本提议稿。

基线 `2e97eded` 把校验放在 AGG-12：B-03 订阅 B-31「用印已办理」维护本地投影。`aggregates_dep_check.py` 对 api、事件都建边，该方案仍使 B-03、B-04、B-05、B-08、B-10、B-11、B-23、B-24、B-28、B-31 成为强连通分量。只改同步为异步不能消除模块依赖。

B-29 / REF-02 项目结项已采用下游无聚合流程模块（ADR-0051 决定 4 第 4 条、决定 7 第 2 条第 5 点）。ADR-0017 决定 1 的模块结构部分已由 ADR-0051 取代，蓝图编号登记要求仍保留。本稿沿用项目结项的职责分离方式，新增第二个流程模块并明确一般准入条件；取代范围仅为 ADR-0051 决定 1 第 2 条中流程模块登记只列 `delivery.closeout`、决定 2 第 3 条中流程模块命名空间例外只列 `delivery.closeout`、决定 7 第 2 条第 5 点中流程模块方向事实只列项目结项的限制。原有结项模块的登记、命名空间与依赖保持，BC 合并、蓝图对应及其余条款继续生效；本稿不重写已采纳正文，不把本提议视为已采纳。

## 决定

### 1. 新增下游报价发出编排

新增 **REF-04「报价发出编排」（暂名）**，为无聚合的流程模块，不计入业务 BC 数，不拥有报价、投标或用印申请的状态，不建自有业务表或 schema，不发布领域事件。派工卡的暂号 REF-03 在基线已用于财务汇聚对象（OBJ-103），且 S-43、OBJECT_EXEMPTIONS 与命名清单已有引用；本稿改用尚未占用的 REF-04，保留原 REF-03。模块正式中英文名、标识已交 one-glossary 定名（2026-10-17），命名空间按决定 3 第 6 条随定名一并确定；聚合稿用 B-32 作图节点编号，只为复用现有查环输入格式，不表示新增业务 BC。

REF-04 在 B-03、B-31 的下游，依赖恰为：

- REF-04 → B-03（api）：读取目标报价版本并调用 AGG-11 / AGG-12 命令。
- REF-04 → B-31（api）：核验实际用印登记。
- REF-04 → `platform.audit`（api）：保存核验、拒绝、调用结果的审计记录。

AGG-11、AGG-12 不查询或订阅 B-31，不持有 B-31 投影，也不依赖 REF-04。用印登记 ID 在两个命令中仅作为已核验事实的追溯标识，不据此增加依赖。B-31 保留 → B-24（api）的资产卡片引用；来源单据引用仍只作回溯，来源审批仍由 B-31 经 `platform.approval` 校验。

### 2. 核验门槛与两条发出路径

1. 所有报价对外发出入口先进入 REF-04。编排方确定目标报价版本、法人及拟发文件，向 B-31 的 api 核验三者与实际用印登记逐项一致，取得用印登记 ID。已用印、以及关闭后仍保留的实际用印登记可用于核验；仅已批准的申请不得放行。不能用历史核验成功、前端传入的布尔值或事件到达代替本次核验。
2. **投标路径**：核验通过且核验留痕成功后，调用 AGG-11「递交投标」（PRC-08 第 7 步），入参增加用印登记 ID。投标聚合继续执行自身 INV-33 等规则、改变自身状态并发出「投标已递交」；它不再核验用印真伪。
3. **非投标路径**：PRC-07「生效报价版本」后的人工发出步骤由 REF-04 承接；核验通过且核验留痕成功后调用 AGG-12 新命令「登记报价发出」（暂名）。命令仅在目标报价版本上记录发出方式、日期、客户联系人、用印登记 ID，不改变报价状态，不核验用印真伪，不另发领域事件。幂等键为「报价版本 + 用印登记 ID + 发出方式」；同键同参返回原结果，不重复登记，同键不同参拒绝。报价评审与生效仍执行原规则。
4. **失败即拒绝并告警**：未用印、报价版本 / 法人 / 拟发文件不符、登记 ID 或凭据缺失、读不到、超时或核验失败，均不得调用两个发出命令；拒绝原因留痕并告警，无默认放行或跳过配置。核验通过后须先经 `platform.audit` 成功保存本次核验记录，再调用命令，最后保存调用结果；核验留痕失败时不调用命令。核验留痕、下游命令或结果留痕失败均报告失败并告警，不冒称发出成功。仅命令已成功后的结果留痕失败走补记，核对命令执行结果后补记，不能盲目重调发出命令。
5. 「用印已办理」仍是 B-31 的事实事件；与本门槛有关的核验消费方改为 REF-04，消费方式为 api 查询实际登记，**不订阅事件**，因此不新增 REF-04 → B-31（事件）边。事件分析消费与发出前实时核验分开，不能靠投影推定当前已用印。

### 3. 流程模块准入条件（部分取代 ADR-0051）

在 ADR-0051 已修订的模块结构基础上，允许设立独立的无聚合流程模块。B-29 / REF-02 为第一个，REF-04 为第二个；以后不以某个模块的孤立例外作为准入依据，须同时满足：

1. 职责是跨模块的顺序协调或前置核验，无法归入某个被协调聚合而不引入反向依赖或混入其他 BC 的业务语义。
2. 位于所有被协调业务模块下游，只经其 api 调用；确需事件时须显式登记事件边，同样参与查环。业务模块不反向依赖编排方，流程模块之间不得互相依赖。
3. 不拥有业务聚合、业务状态或自有业务表 / schema；规则与状态变更留在所属 BC，过程证据经 `platform.audit` 留痕。一旦出现需持久化的业务状态或需发布领域事件，即须重新评估独立业务生命周期与 BC 边界，不能继续套用此条件。
4. 模块职责、入口、失败策略和完整依赖须在架构稿可审查；并入已建边后无环、分层一致，Modulith 构建守护不豁免。新模块按架构变更流程登记，正式名称先交 one-glossary，不自动批准其他结构变化。
5. ADR-0017 决定 1 的蓝图编号登记要求保留；流程模块按与既有 REF-02 相同的方式登记对应或「蓝图未覆盖」。
6. 流程模块归入其主要协调对象所在命名空间，不建 schema；REF-04 的命名空间随 one-glossary 定名一并确定，不因核验用印而预先归入用印模块的命名空间。

审批钩子不属于准入条件，是否需要按具体流程另判并显式登记依赖；REF-02 的结项审批钩子不作为所有流程模块的必备形态。

### 4. 与 ADR-0007 决定 3 一致

REF-04 是应用层顺序编排，**不挂 `platform.approval`，不引入审批钩子**。PRC-07 的人工发出步骤可以在 BPMN 表达为人工任务；实际用印判定、拒绝与跨模块命令调用由 REF-04 承担，不写入 BPMN 表达式或服务任务，业务决策也不塞入通用审批模块。既有报价评审与用印审批保留各自审批入口。本稿不修改 ADR-0007，也不在骨架中添加 `guard` 字段代替显式依赖。

## 影响面

- **聚合与流程**：AGG-11 增加用印登记 ID 入参；AGG-12 增加纯记录命令；AGG-113 对外核验消费方改 REF-04，保留实际用印登记。revenue 组后续同步 PRC-07 人工步、PRC-08 第 7 步及入口约束；people 组同步 B-31 查询契约与失败场景。
- **先行上线边界**：B-31 依 ADR-0054 的例外先行上线时，REF-04 尚不存在，报价发出入口不开放，不会绕过用印。
- **架构稿与告知**：聚合稿新增 REF-04、移除 B-03 → B-31 并重算 §4.1；ARCH_VS14、两处用印能力定义、B31 页首告知同步。本卡不改三组流程骨架、运行时代码、验收测试及查环脚本。
- **头部范围**：「全局」指本稿同时规定跨域编排模块的一般允许条件；B-03 与 B-31 的具体职责仍按正文标识，不以头部字段提前修改 contexts 登记。
- **命名与登记**：REF-04 模块及「登记报价发出」命令已交 one-glossary 定名（2026-10-17），命名空间随定名一并确定。正式定名后由负责会话另卡登记 `bcs.yaml`、`contexts.yaml` 的 `kind: process` 及相关模块说明；规划依赖仍按 ADR-0041 决定 4 留在聚合稿，实际实现时再登记代码依赖。

## 迁移方案

1. 本卡先交提议稿与同步后的设计文件，不改变已采纳 ADR 的头部，不把结构稿当作已上线行为。采纳提交已为 ADR-0051 头部追加部分取代标注，范围为决定 1 第 2 条的流程模块登记、决定 2 第 3 条的流程模块命名空间例外、决定 7 第 2 条第 5 点的流程模块方向事实，均只扩展原先仅列 closeout 的范围；ADR-0017 的既有取代标注与蓝图编号登记要求保留。
2. one-glossary 定模块与命令名；设计负责会话同步正式模块登记、流程步骤、用印查询与命令契约。两个发出路径均须经过 REF-04；直接调用发出命令的入口约束在实现卡中明确，不能仅靠 UI 隐藏入口。
3. 实现时撤去 B-03 的用印投影订阅及前置核验，将核验迁至 REF-04；已存在的报价评审、生效、投标状态与实际用印历史不改。核验与登记使用同一个报价版本、法人、拟发文件及用印登记 ID；「登记报价发出」按决定 2 第 3 条的幂等键处理重复提交，核验留痕、命令与结果留痕按决定 2 第 4 条的次序执行。
4. 验证匹配成功、仅批准未用印、错版本 / 法人 / 文件、凭据缺失、查询失败、审计失败及两个命令的失败路径；再以真实模块依赖守护和流程验收证明入口无法绕过。未完成前不开放报价发出入口。

## 回滚方案

本稿仍为提议，设计回退可恢复本卡前文件，但旧事件投影方案仍有依赖环，不作为可上线方案。实现后若需停用编排，关闭发出入口并保留已登记的发出、用印与审计历史，不回滚已发生的业务事实，不恢复可绕过实际用印的直接发出入口；替代方案另经架构评审。

## 需同步修改的守护规则

- `aggregates_dep_check.py` **不改规则或实现**：继续把 api 与事件都作为依赖边。更新其输入及 §4.1 生成块，要求无环且一致；不能将真实查询标成「不校验」。
- 随模块首个实现卡登记三条 api 依赖，使用既有 `ModuleDependencyTest`、`ModularityTest` / `ApplicationModules.verify()` 校验；增加 REF-04 无聚合、无自有表 / schema、无 `platform.approval` 依赖及 B-03 不依赖 B-31 / REF-04 的约束。不得放宽守护取得通过。
- 流程骨架不增 `guard` 字段。验收由独立测试方覆盖两条路径的用印核验及拒绝告警；本卡只运行设计检查与生成器，未修改或冒称已执行业务验收。

## 后果

报价版本的状态和评审语义保持在售前，用印真实性保持在行政事务，跨域顺序由下游模块承担；实际用印核验不会把售前拉到全图下游。代价是增加一个流程模块、一处运行时查询及其可用性要求；B-31 读不到即阻断发出，不能降级放行。

核验通过与实际对外发送之间的入口约束、文件不可变引用及重试核对须在实现契约落实；本稿与图检查只证明设计依赖方向，不证明物理发送、业务验收或生产行为。正式制度出处及拟发文件的具体识别方式仍按 ARCH_VS14 的材料清单补齐，不增豁免。

## 备选方案（未采用）

- **B-03 订阅用印事件建投影，查环器不计事件边**：即基线方案再放宽查环。Java 订阅仍依赖 B-31 事件类型，Modulith 构建守护仍计算模块依赖，与设计守护不一致，且投影不能替代发出前的实际登记核验。
- **拆除 B-31 → B-24 以断环**：行政资产使用与维修按公司资产卡片 ID 读取卡片，该 api 引用是真实业务边；为用印报价断环而拆除会扭曲资产语义，或将实际查询藏成「不校验」。
- **在流程骨架加 `guard` 字段**：字段不会承担跨模块运行时调用与失败策略，既隐藏真实依赖，又缺少现行骨架解析、生成与守护契约；仍须显式模块与依赖。
- **把核验放 AGG-12 / AGG-11，或挂在 `platform.approval`**：前者混入跨域编排并重建依赖环；后者让通用人工审批平台承担报价业务判断与发出命令，违背 ADR-0007 决定 3。REF-04 无新增人工批准，不需要审批依赖。
