## 背景

ADR-0079 把一个人的在职判断、版本、命令都按员工一条线建模，用人单位在不变量 4 里只是三种法人口径之一，现无存储。用户 2026-11-04 在 issue #1295 答复：一个人可以同时受雇于两个法人，目前就存在（另一家法人为了维护企业资质）；社保、个税扣缴与请假权益按雇佣关系各算（评论 6638890281、6639148601）。这与「一个员工一条在职时间线」不相容：两家单位的版本会重叠，而版本现有的不重叠排他约束按员工建立。触发出处：卡 #1308，评审笔记 `hr-boundary-stability-review.md` 7.3 与 8a；设计稿 `docs/architecture/proposals/employment-relationship.md`（下称设计稿）。

要决定的只有一件事：在员工与版本之间增加「雇佣关系」聚合，并定用人单位如何属于它。表结构、命令绑定、迁移与法律核对在设计稿，本稿只写决定。

## 决定

1. **雇佣关系聚合**：workforce 新增雇佣关系（暂名 EmploymentRelationship，名称归 one-glossary），一个自然人与一个用人单位一段；同一人可同时有多段，不同用人单位的段允许重叠；同一人与同一用人单位只有一段，复职沿用该段（沿用 ADR-0078，员工 ID 与工号终身不变）。
2. **用人单位属于关系且建立后不变**：关系记录用人单位法人 ID，不可改。连续任职中换用人单位，是旧关系离职加新关系入职，同日生效，新关系记录前一段的 ID。唯一例外是依法承继（ADR-0079 不变量 14：合并分立，原合同由承继单位履行）：以追加的承继记录表示，读用 `employerOn(关系, 日期)`，关系 ID 与按关系的键都不变；承继记录何时建见设计稿 B-G，建之前拒绝改派。不建独立的带日期用人单位维度，也不并入 `EmployeeLegalEntityChanged`；员工的数据范围与成本法人（ADR-0073）仍是员工层、独立的时间线。调岗（TRANSFER）永不改变用人单位，故 ADR-0073 决定 3 第 4 项（跨法人调动会签）含义不变。
3. **关系是员工聚合内的实体**：员工仍是聚合根和锁，关系、版本、命令在同一事务（保持 ADR-0068 第 1 条第 1 项「同一个聚合、同一个事务」的本意）。员工版本（在职状态、试用与正式、停薪留职、入职日期）、任职与人事命令各带关系 ID：HIRE 在录入时建关系，版本不重叠改为按关系，「同日一条」与「离职之后」改为按关系（可使旧关系离职与新关系入职同日）；调动、转正等命令显式写明所属关系，不从组织单元推断。员工层种类（变更数据范围法人）关系 ID 为空，按种类 CHECK。主任职不重叠仍按人（ADR-0079 不变量 2 不变）；主任职所在关系结束而另一段仍在职时，须同一录入指定新的主任职，否则拒绝；关系可以没有任职。
4. **在职判断仍只有一处，在 workforce**：一人某日在职，当且仅当某段关系当日在职。`EmploymentVerdict`、`EmployeeProfiles`、`OrgDirectory` 签名不变。员工层事件：已入职在此人从不在职变为在职（HIRE）时、已复职在由复职变为在职时、已离职在最后一段在职关系结束时发布；转正、调动、更正每次命令各发一次并带关系 ID；换用人单位（同日离职加入职）不发已入职与已离职。人员层读（停薪留职、待放行离职、将离职）按多段关系的合成规则读：停薪留职与将离职要求所有在职关系都是，待放行离职任一段即是（设计稿 6.2）。identity、approval、timesheet 代码不变。
5. **按关系各算，按支付主体扣缴**：请假权益与额度、社保公积金参保、劳动合同、试用期，以关系 ID 为键。ADR-0079 不变量 4 的三种口径中：第一种（个税扣缴与月度薪资）仍按支付工资的法人，默认取关系的用人单位，约定另一家的由 payroll 记录，因为扣缴办法按支付单位累计；第二种（社保公积金）由「劳动合同的用人单位」改为「雇佣关系的用人单位」；第三种（数据范围与成本）不变。
6. **读与事件**：workforce 提供按日期读某员工当日在职的各段关系（含用人单位、阶段、停薪留职）的只读 api，不提供返回单一用人单位的读法；新增关系层事件：已开始、已结束、阶段变更、停薪留职变更、更正（名称归 one-glossary）。请假（含 RULE-515 的触发）与薪资订阅关系层事件，不订阅员工层事件；identity 的现有订阅不变。
7. **替换写法**：ADR-0079 决定 3 第 1 条「在职由按生效日排列的员工版本判定」改为「在职由员工的各段雇佣关系的版本判定，任一段当日在职即在职」；决定 4 表第一行订阅方 leave、payroll 改为订阅关系层事件，identity 与审计不变；劳动合同事件行删「含用人单位变更」；决定 5 第 1 条改为「在职判断只有一处，在 workforce，由各段关系的版本合成」；第 4 条第二种口径中「按劳动合同的用人单位」改为「按雇佣关系的用人单位」（第一、三种不变）；ADR-0068 第 1 条第 1 项「员工根、各版本和命令本身在同一个聚合、同一个事务里」之外加「雇佣关系为聚合内实体」，第 5 项中「同日一条」「离职之后」的「同一员工」改为「同一雇佣关系」（员工层种类仍按员工）；ADR-0084 决定 2 整条改写为「用人单位（劳动合同区）是雇佣关系的不变属性，不单设带日期维度，不并入 `EmployeeLegalEntityChanged`（已建事件保留名称）；本条沿用 ADR-0079 不变量 4，具体见 ADR-0086」，并删去其中「有自己的表、api 查询与事件」一句。

## 影响面

- workforce：新增雇佣关系表；员工版本表、人事命令表、任职版本表各增关系 ID 列，版本不重叠约束改为按关系；员工版本表名随之更名（建表结构 PR 定）。
- leave（planned）：额度与请假按关系；payroll（planned）：社保、个税扣缴按关系；劳动合同区（planned）：引用关系 ID，不另存用人单位。
- 术语：`backend/glossary/proposed/employment-relationship.yaml`（提议）。数据访问注册表、事件载荷（加关系 ID，向后兼容）随建造卡。
- 不改：identity、approval、timesheet 代码；`employee_legal_entities`；EmployeeProfile 与 OrgDirectory 的字段。

## 迁移方案

每名现有员工一段关系，用人单位取该员工归属法人的首个版本日的法人，标记来源为「迁入，待人事确认」；无归属时间线的员工进拒收清单，不猜。已有版本、命令、任职按员工加关系 ID。数量与拒收清单只是聚合，由迁移卡产出。确认用人单位的人与时点待用户（设计稿 B-B）。迁入涉及的表结构单独成 PR，按数据设计门禁先审后建。

## 回滚方案

本稿不落代码。表结构落地前推翻：另立 ADR 取代，成本为零。落地后推翻：须把关系合回员工线并处理已重叠的版本，只有在没有同时受雇两家的员工时可行，故落地后视为不可回滚，推翻另立迁移方案。

## 后果

- 好处：同时受雇两家法人成为一等事实；请假、社保、个税扣缴从第一天按关系建，不需事后改键；消费在职判断的三个模块不改。
- 代价：多一张表与三处加列；员工层与关系层各有一套事件，须分清订阅；请假要选「从哪段关系请」；换用人单位是两条命令，不是一次调动。
- 未定（设计稿第 9 节 B-A 至 B-I，用户）：个税扣缴按支付单位而非用人单位，与用户「按雇佣关系各算」的字面有出入，缘由是扣缴办法按支付单位累计（决定 5），请用户确认；第二家法人的关系是否要有任职与汇报线；已有员工的用人单位由谁、何时确认；第二家法人是否实际参保（法律核对：社保实务上通常一人一处参保，仅律所文章，未核原文）；两家的法定年休假是否叠加（《企业职工带薪年休假实施办法》第四条按累计工作时间计，未写同时受雇）；连续任职中换用人单位是否带走工龄与未休假额（试用期默认不设，依 ADR-0079 不变量 13，用户可改）；一段关系结束而另一段继续时的资产交接；承继记录何时建；调动到归属法人非用人单位的组织单元是否允许；两段关系下工时提交与审批人的归属。

## 备选方案（未采用）

1. **保持按员工建模，把用人单位作为带日期维度（ADR-0084 决定 2 原状）**：无法表示两个同时存在的雇主，两条时间线在一个员工上重叠，与现有排他约束冲突；用户事实不允许。
2. **每个雇佣期一段关系（复职另起一段）**：复职多一次迁移与额度承接规则，证据里看不到好处；复职沿用现行行为。
3. **关系的用人单位可带日期变更**：额度与参保会跨两个用人单位，每个消费方都要按日期切片；换用人单位在劳动关系上本是新的用工主体。
4. **新建关系版本表，保留员工版本表作人员层汇总**：同一事实两个写入处，违反「一个对象只有一个上下文写」。
