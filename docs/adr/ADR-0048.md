# ADR-0048：审计表按月分区的主键例外

- **状态**：已采纳（用户 2026-10-16 在阶段写实、对象回补与 ADR-0048 确认页批准成文，intent `2026-10-16-090004-one-architecture-阶段写实-对象回补与-ADR-0.md`；内容为用户 2026-10-15 已定：「接受，登记为唯一例外 (Recommended)」，intent `2026-10-15-020820-one-coordinator-审计表按月分区主键须含分区键-与.md`；编号由 one-coordinator 分配；已经 opus 首轮对抗评审并按意见改写）
- **日期**：2026-10-16
- **取代**：ADR-0033 第 1 项第 1 条中「单列 `uuid` 主键」与「自有表零例外」对 `platform_audit.audit_entries` 的适用、ADR-0033 第 1 项第 8 条「豁免只剩框架自建表」与需同步修改的守护规则第 1 条「只允许第 1 项第 8 条的 5 张框架表」对 `platform_audit.audit_entries` 的适用

## 背景

- **用户已定按月分区**：GUIDING_PRINCIPLES O-8「`audit_entries` 按月分区，分区归档到对象存储并校验后，由专用的维护角色删除在线分区」（`GUIDING_PRINCIPLES.md:248`）；NAMING_STANDARD §2.4a 第 8 条要求保留期超过 3 年的只追加表在建表时定好分区键（`NAMING_STANDARD.md:149`）。
- **与 ADR-0033 冲突**：PostgreSQL 分区表的主键与唯一约束必须包含全部分区键列。ADR-0033 第 1 项第 1 条要求每张自有表是单列 `uuid` 主键、自有表零例外；第 8 条与守护 1 只允许 5 张框架表豁免。按月分区后 `audit_entries` 的主键不能是单列 `id`，`uk_audit_entries_event_id (event_id)` 也不能跨分区建立。
- **用户决定**（2026-10-15，经 one-coordinator 转达）：问题「审计表按月分区主键须含分区键，与自有表单列 UUIDv7 主键冲突」，答「接受，登记为唯一例外 (Recommended)」。落点：「audit_entries 主键 (id, created_at)、去重键 (event_id, created_at)，id 仍全局唯一 UUIDv7、引用只用 id；主键守护登记此唯一例外，新增分区表须另行批准」。
- **现状**（基线 `backend/src/main/resources/db/migration/platform_audit/V20261014134000__platform_audit_baseline.sql`）：
  - `audit_entries` 非分区表，`id uuid PRIMARY KEY`（:7），`uk_audit_entries_event_id`（:28）；`created_at` 的列注释是「审计事实发生的时间，来自注入的时钟」（:36）。
  - 事件审计写入用 `on conflict (event_id) do nothing`（`JdbcAuditEntryRepository.java:56`），`created_at` 取事件信封的发生时刻（`AuditDomainEvents.java:48` 传 `envelope.occurredAt()`）。同一事件重投时 `event_id` 与 `created_at` 都相同。
  - `audit_archive_batches.first_entry_id` / `last_entry_id` 以条目 `id` 记归档范围（:66-67），没有外键。没有任何表对 `audit_entries` 建外键。
  - `PrimaryKeyTypeGuardTest` 只查单列主键，豁免取 `DdlNamingTest.FRAMEWORK_TABLES` 与 `primary-key-type-baseline.txt`；`primary-key-exemptions.txt` 尚未建立（ADR-0033 守护 1 由 R-1b 实现）。
- **one-data 建表审查**（PR #314，`docs/data/baseline-table-review.md:62` AE-2；`review-parts/OPUS_VERIFY.md:62`）：确认冲突属实，建议主键 `(id, <分区键>)`、事件幂等唯一改为 `(event_id, <分区键>)`，基线开放期内做，否则上线后要重写全表。
- **待用户决定**：无，用户已定（按月分区为 O-8 已定；主键、去重键、引用只用 `id`、唯一例外与新增须另批，均为 2026-10-15 落点；2026-10-16 批准成文）。

## 决定

1. **主键**：`platform_audit.audit_entries` 按 `created_at` 按月范围分区（`PARTITION BY RANGE (created_at)`，分区粒度按 O-8），主键为 `(id, created_at)`，约束名 `pk_audit_entries`。
2. **去重键**：事件幂等唯一约束改为 `uk_audit_entries_event_id_created_at (event_id, created_at)`；事件审计写入改为 `on conflict (event_id, created_at) do nothing`。成立的前提是**事件条目的 `created_at` 一律取事件信封的发生时刻**（现状如此，本条把它定为规则）：同一事件重投时两列都相同，必落同一分区，唯一约束照样生效。直接审计（非事件）条目 `event_id` 为空，不受此约束。为使该前提成立，基线 `created_at` 现有的 `DEFAULT now()` 须删除，或由守护锁住写入侧赋值（写入 SQL 必须显式给 `created_at`）；二者由审计分区工作单元选一。
3. **`id` 仍是标识**：`id` 由 kernel `IdGenerator` 在应用侧生成 UUIDv7（ADR-0033 第 1 项第 1 条的生成规则不变），不由数据库生成。**任何引用只用 `id`**：跨表引用列（如 `audit_archive_batches.first_entry_id`）、事件、接口、日志、导出中都只出现 `id`，不得引用 `(id, created_at)` 复合键，也不得对 `audit_entries` 建外键（单列引用无法建外键，复合外键被本条禁止）。按 `id` 查单条时用主键索引的前导列；调用方另知时刻的，可附加 `created_at` 条件作分区裁剪，但这只是查询优化，不是引用的一部分。
4. **全局唯一性的保证**：`id` 由应用侧 IdGenerator 生成的 UUIDv7 保证（ADR-0033 第 1 项第 1、9、10 条）。分区预建、迟到条目、归档前完整性检查等实现由审计分区工作单元按 ADR-0033、ADR-0038 落地，不在本 ADR 决定。
5. **登记为唯一例外**：主键守护的例外文件 `backend/architecture/primary-key-exemptions.txt`（ADR-0033 守护 1）中，本表是唯一一行非框架表，写法：

   ```
   platform_audit.audit_entries  # 分区表：主键 (id uuid, created_at timestamptz)，按月 RANGE (created_at)；ADR-0048
   ```

   守护对这一行不是「跳过」，而是校验其形状：主键恰为 `(id, created_at)`，第一列 `id` 是 `uuid`，第二列 `created_at` 是 `timestamptz` 且是分区键；形状不符即失败。
6. **新增分区表须另立 ADR**：今后新增任何 OLTP 自有分区表，须另立 ADR 经用户批准，并在例外文件中登记该 ADR 号；守护拒绝未登记的分区表。PostgreSQL 分区表主键必须含分区键，故新增分区表必然偏离单列 `uuid` 主键。ADR-0025 已批准的 `reporting` 分区有其既有 ADR 依据，不在本条范围。
7. **不在本 ADR**：迟到事件（发生时刻早于在线分区范围）的处理，列入审计分区工作单元的必答项；维护角色删除在线分区作为只追加触发器的登记例外、归档批次改按分区或时间边界推进（PR #314 AB-1），由审计分区工作单元按 O-8 实现；本 ADR 只定主键、去重键与守护。

## 影响面

- **BC**：`platform.audit`（表结构、仓储写入、归档作业）；其他模块不受影响（不引用复合键，没有外键指向本表）。
- **表**：`platform_audit.audit_entries`（改分区表、主键、去重唯一约束；索引随分区重建，PR #314 `DATA-REPAIR-timesheet-audit.md:101` 的索引改造同批做）；`audit_archive_batches` 列不变，仍以 `id` 记范围。
- **代码**：`JdbcAuditEntryRepository.saveForEvent` 的冲突目标；`JdbcAuditEntryQueries` 按 `id` 查询不变。
- **接口与事件**：不变，只暴露 `id`。
- **例外注明**：SESSION_PLAYBOOK §14.1 D16「所有自有表主键为 UUIDv7」对本表的适用有例外：主键为 `(id uuid, created_at timestamptz)`，`id` 仍是 UUIDv7，仅主键形状不是单列；SESSION_PLAYBOOK 该条须同步注明本 ADR。
- **阶段**：基线开放期内（ADR-0038：首次部署生产前关闭）。
- **文档**：ADR-0033 状态行标注部分取代；NAMING_STANDARD §2.4a 第 8 条的分区注册表登记本表分区键；`primary-key-exemptions.txt`；基线列注释 `event_id` 改为「与 `created_at` 一起唯一」。

## 迁移方案

1. 基线开放期内（ADR-0038 第 1 项：标记 `backend/architecture/migration-baseline-open` 在首次部署生产前删除）**直接改 platform_audit 基线**，不新增版本迁移；dev 库按 ADR-0038 第 2 项随基线变化重建，数据不保留。
2. 基线中建分区父表与覆盖首个上线月份起的月分区，未来月分区的预建方式（作业或运维剧本）由审计分区工作单元定，须在首次部署生产前就绪，分区预建实现按 ADR-0033、ADR-0038 由该工作单元落地，不在本 ADR 决定。
3. 尚无任何环境有审计数据（ADR-0038 背景：没有环境执行过基线迁移），无在途数据要转换。
4. 若本 ADR 在基线关闭后才实施，须另写全表重写的迁移方案并重新报批，本方案不适用。

## 回滚方案

- **基线开放期内**：回退实现 PR 即恢复单列主键与 `uk_audit_entries_event_id`，重建 dev 库；没有数据要转换。回滚边界是实现 PR：DDL、冲突目标、归档检查与守护一起回退。回退后按月分区不能实现，O-8 的在线分区删除也随之搁置，须报用户。
- **基线关闭之后**：不回滚到非分区表（要重写全表）；问题在新迁移中修正（例如补检查或调整索引），已过账的审计条目只追加不改。

## 需同步修改的守护规则

都在**审计分区实现 PR**（与 ADR-0033 守护 1 的 R-1b 子 PR 先后均可，后合并者负责合流）中修改：

1. `PrimaryKeyTypeGuardTest`：例外读 `backend/architecture/primary-key-exemptions.txt`；除 ADR-0033 第 1 项第 8 条的 5 张框架表外，只接受 `platform_audit.audit_entries` 一行，且按第 5 条校验形状（主键恰为 `id uuid` + `created_at timestamptz`，`created_at` 是范围分区键）；其他非框架表出现在例外文件中即失败。`DdlNamingTest` 的 DDL 模型须能解析 `PARTITION BY RANGE (...)` 与复合主键。
2. **分区表守护**（新增，可并入 `PrimaryKeyTypeGuardTest`）：迁移中出现 `PARTITION BY` 的表，必须在例外文件中登记且该行注明批准它的 ADR 号；未登记即失败（第 6 条）。
3. **引用只用 `id`**（`DdlNamingTest` 中新增）：任何 `FOREIGN KEY ... REFERENCES platform_audit.audit_entries` 失败（含复合外键）；`uk_audit_entries_event_id_created_at` 存在且恰为 `(event_id, created_at)`。
4. `AuditDomainEventsIT`：同一事件重投两次只产生一条；事件条目的 `created_at` 等于信封发生时刻。
5. `primary-key-exemptions.txt` 文件头注明：「非框架表只允许 ADR-0048 的 audit_entries；新增须另立 ADR」。

## 后果

- 按月分区可以落地：在线分区归档后可整块删除，不必逐行删除只追加表；查询按时刻范围裁剪分区。
- 自有表单列主键的规则多了一个有边界的例外：只此一表，形状由守护锁定，新增须另立 ADR。
- `id` 的全局唯一由应用侧 IdGenerator 生成的 UUIDv7 保证，而不是数据库约束。
- **风险（迟到事件）**：发生时刻早于在线分区范围的事件，其处理列入审计分区工作单元必答项；无论如何处理，写入失败须失败并告警，不得静默丢弃（CLAUDE.md 第 6 条）。
- 事件幂等依赖「事件条目 `created_at` = 信封发生时刻」；若将来有人改为写入时刻，重投会产生重复条目，由守护 4 拦下。
- 按 `id` 查单条在没有时刻条件时要探查所有在线分区的主键索引；在线分区数受保留与归档节奏限制，代价可接受。

## 备选方案（未采用）

- **不分区，保留单列主键**：与 O-8 用户已定的按月分区与在线分区删除冲突；保留 10 年的只追加表只能逐行删除。
- **事件幂等另建登记表**（`event_id` 单列唯一，非分区）：多一张表与一次写入；而事件条目的 `created_at` 本就取信封发生时刻，`(event_id, created_at)` 已能保证幂等，无需另建。
- **分区键用另设的 `occurred_at` 列**（PR #314 OV 建议）：现 `created_at` 已定义为审计事实发生的时间，事件条目取信封发生时刻，含义相同，另设列是重复；用户落点也写 `created_at`。
- **用触发器或登记表强制 `id` 全局唯一**：每次写入多一次跨分区查找或一张全量表，抵消分区收益；UUIDv7 加生成器守护足以把碰撞限定为缺陷。
- **把本表放进框架表豁免、不校验形状**：会让「例外」变成「不查」，主键形状漂移无人发现。
