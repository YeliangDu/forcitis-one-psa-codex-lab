## 背景

ADR-0079 把招聘、绩效结果、劳动合同、执业证书与技能放在 organization.workforce 内的六个分区（其备选方案 1 以「招聘、绩效单级审批，留 workforce 分区」为由，本稿使该理由对绩效不再成立），并称「日后拆分只搬包与表」。触发出处：用户 2026-11-04 要求复核「绩效放在 organization.workforce 是否稳定」及其余人事分区，卡 #1295。复核由一个未读过 ADR-0079 理由的独立评审员先答（`docs/architecture/proposals/hr-boundary-independent-answer.md`），再与 ADR-0079 逐条对照（`docs/architecture/proposals/hr-boundary-stability-review.md` 第 2 节）。

要决定的只有一件事：绩效是否留在 workforce，留下的分区须满足什么条件。招聘可分别采纳，另见 ADR-0085（提议）；本稿的判据同样适用于它，但不依赖它。招聘（见 ADR-0085）、绩效、劳动合同、证书、技能现在都没有代码、表、事件或权限码，现在定位不花代价。

依据三点：（1）依赖方向：`platform.approval`、`platform.identity`、`platform.numbering`、`cost.timesheet` 都依赖 workforce，workforce 不能反向依赖 `platform.approval`（ADR-0051 守护第 3 条），所以放进 workforce 的流程类分区只能各写一套单级审批，或再加一个内核端口；（2）拆分不是搬包：事件类全名、权限码、共享的 `state_transitions` 类型检查、到 `personnel_commands` 的外键与同事务写入、审计对象种类的归属模块都要改（评审笔记 2.3；其中事件类全名、权限码守护、`state_transitions` 类型检查已核对）；（3）绩效与招聘的变化驱动、使用者、保存期与员工主记录不同（评审笔记 2.1）。

## 决定

在「一个对象只有一个上下文写」的前提下，决定 workforce 只承载与员工主记录同一变化驱动、同一使用者、同一保存期、同一事务的分区；任一项不同的分区另立上下文。本稿据此移出绩效；招聘见 ADR-0085。具体：

1. **绩效移出**：新上下文承载绩效评估（AGG-106）与绩效更正。暂名 `organization.performance`，名称归 one-glossary。依赖：`-> organization.workforce（api）、platform.approval、platform.audit`；workforce 不依赖它。发布「绩效评估已确认」，payroll 经 api 读作奖金依据（AGG-76 的引用不变）。
   - 转正：评估结果是转正的输入，不是门槛（P-46 文字）。P-46 守护列写的「AGG-62 转正前读 AGG-106」本稿**取代**为：转正命令不读绩效。P-46 是草稿，该落点会使 workforce 依赖绩效并成环。「试用期届满前无已确认的试用期评估」的预警由绩效上下文经 workforce 的试用期读 api 发出。
   - 不能胜任链（劳动合同法第四十条第二项，ADR-0079 Q10 条件）：由绩效上下文记录「不能胜任结果 → 培训或调岗 → 再次不能胜任」，其中培训或调岗一步引用 workforce 调动命令的 ID（不校验）；workforce 的解除依据只存对评估记录的引用 ID，不校验（沿用「不校验」引用方式）。
   - 审批仍为用户已答的单级（Q10 A）：一个审批节点，经 `platform.approval`。
   - 替换写法：ADR-0079 决定 1 表 C8 与 C4 行（试用期评估）的归属改为绩效上下文；决定 2 首句改为「沿用 ADR-0051，人事上下文增加绩效」；决定 2 依赖方向句 payroll 的依赖增 performance；决定 4 表「绩效结果确认」行发布方改为绩效上下文、订阅方 payroll；决定 5 第 9 条删去「绩效」；ADR-0051 决定 3 表 B-13 行删 AGG-106，业务 BC 数加一；决定 7 第 3 条的含审批聚合清单加 AGG-106。
2. **用人单位**（劳动合同区）：作为独立的带日期维度，有自己的表、api 查询与事件，事件名另起；不并入已建的 `EmployeeLegalEntityChanged`（它是 ADR-0073 的数据范围与成本法人，已建事件保留名称）。本条为沿用 ADR-0079 不变量 4 的写明，不取代它。用户已答一人可同时受雇于两个法人（见「未定」），该维度将作为雇佣关系的属性由后续设计卡（评审笔记 F1、F2）定形，那张卡的 ADR 可部分取代本条。
3. **留在 workforce 的分区**（替换 ADR-0079 决定 2 区间句的拆分语）（除本稿移出的绩效区外，六区中的各区；招聘区去留见 ADR-0085，本稿只要求留在 workforce 的区满足）：以下六条代替「日后拆分只搬包与表」。建该分区的第一张卡把六条写进完成标准：
   - 自有表；只存员工 ID，不加到 `employees`、`personnel_commands` 的外键，不与人事命令同事务写；
   - 不写 `state_transitions` 共享表，自有转换记录；
   - 自有权限资源名（`organization.workforce:<区资源>:<动作>`），不借用员工资源；
   - 自有 api 类型，不向 `EmployeeProfile`、`OrgDirectory` 加字段；
   - 自有事件类，不复用别区事件；
   - 自管保存期。
   满足六条的分区日后拆分只需改名与迁移；不满足的，其拆分成本按评审笔记 2.3 估。

## 影响面

- `contexts.yaml`：随采纳登记 organization.performance（planned）；`planned.yaml`：AGG-106 改 BC；payroll 条目引用绩效改经 api。另有卡，不在本稿。
- `module-dependencies.txt`：随建造卡加边；`ModuleDependencyTest`、`ModularityTest` 按第 1、2 条方向生效。
- 不改代码、表、事件。

## 迁移方案

无数据迁移：绩效现无任何表或代码。迁入老系统数据按 ADR-0036、0037 与各卡。

## 回滚方案

本稿不落代码。推翻须另立 ADR 取代；因为现无代码，推翻不产生迁移成本，只回到 ADR-0079 的原分区并承认评审笔记 2.3 的拆分成本。

## 需同步修改的守护规则

- 建新 BC 的卡随卡登记 `data-access-registry.yaml`、`NamingSurfaceTest`、`module-dependencies.txt`。
- 第 3 条的六条是建卡检查，不新增自动检查（无对象可检查；首张卡落地时由该卡的复审对照）。

## 后果

- 好处：workforce 不再吸收变化最快的分区；绩效可用 `platform.approval`。
- 代价：多一个模块（登记行、schema、权限前缀）；转正画面要经两个 api 拼装，不再在 workforce 内读绩效；解除依据对评估的引用不被系统校验。
- 未定：绩效建造时点（用户 2026-11-04 答：绩效结果决定奖金，故要建；时点未说）；奖金规则与评估模型（用户同日补充：A8 绩效功能很弱，只作基线了解，需要重新设计，记于 issue #1295；由绩效设计卡提出评估模型与结果到奖金的联系，交用户裁定）；决定 1 中的「单级（Q10 A）」审批是 ADR-0079 阶段的答复，待该设计卡定案后才算有效；技能与证书的位置与时点（用户答现在做，位置由后续设计卡定，评审笔记 8a F5）。已由用户答复：一个人可同时受雇于两个法人，目前就存在（issue #1295 评论 6638890281），故用人单位与员工版本模型由后续设计卡（评审笔记 F1、F2）重定，本稿决定 2 只定它不并入 `EmployeeLegalEntityChanged`。

## 备选方案（未采用）

1. **绩效放 payroll**：评估人（全体直线经理）要在薪资上下文有写权限，且试用期评估服务转正而非发薪。
2. **绩效与招聘合并为「人才」上下文**：外部应聘者与在职被评人共用的只有「人事」二字，保存期与使用者都不同；两者可分别采纳，招聘另见 ADR-0085。
3. **全部留在 workforce（ADR-0079 原状）**：需要每区一套单级审批，且拆分成本如评审笔记 2.3。
4. **现在就拆出劳动合同与执业证书**：合同与员工同使用者、同生命周期，老系统无合同审批流；证书无老系统使用证据，先按第 3 条建。
