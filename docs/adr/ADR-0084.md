## 背景

ADR-0079 把招聘、绩效结果、劳动合同、执业证书与技能放在 organization.workforce 内的六个分区，并称「日后拆分只搬包与表」。触发出处：用户 2026-11-04 要求复核「绩效放在 organization.workforce 是否稳定」及其余人事分区，卡 #1295。复核由一个未读过 ADR-0079 理由的独立评审员先答（`docs/architecture/proposals/hr-boundary-independent-answer.md`），再与 ADR-0079 逐条对照（`docs/architecture/proposals/hr-boundary-stability-review.md` 第 2 节）。

要决定的只有一件事：workforce 内哪些分区留下，留下的须满足什么条件。招聘、绩效、劳动合同、证书、技能现在都没有代码、表、事件或权限码，现在定位不花代价。

依据三点：（1）依赖方向：`platform.approval`、`platform.identity`、`platform.numbering`、`cost.timesheet` 都依赖 workforce，workforce 不能反向依赖 `platform.approval`（ADR-0051 守护第 3 条），所以放进 workforce 的流程类分区只能各写一套单级审批，或再加一个内核端口；（2）拆分不是搬包：事件类全名、权限码、共享的 `state_transitions` 类型检查、到 `personnel_commands` 的外键与同事务写入、审计对象种类的归属模块都要改（评审笔记 2.3；其中事件类全名、权限码守护、`state_transitions` 类型检查已核对）；（3）绩效与招聘的变化驱动、使用者、保存期与员工主记录不同（评审笔记 2.1）。

## 决定

在「一个对象只有一个上下文写」的前提下，决定 workforce 只承载与员工主记录同一变化驱动、同一使用者、同一保存期、同一事务的分区；任一项不同的分区另立上下文。具体：

1. **绩效移出**：新上下文承载绩效评估（AGG-106）与绩效更正。暂名 `organization.performance`，名称归 one-glossary。依赖：`-> organization.workforce（api）、platform.approval、platform.audit`；workforce 不依赖它。发布「绩效评估已确认」，payroll 经 api 读作奖金依据（AGG-76 的引用不变）。
   - 转正：评估结果是转正的输入，不是门槛（P-46 原文）；转正命令不读绩效。「试用期届满前无已确认的试用期评估」的预警由绩效上下文经 workforce 的试用期读 api 发出。
   - 不能胜任链（劳动合同法第四十条第二项）：workforce 的解除依据只存对评估记录的引用 ID，不校验（沿用「不校验」引用方式）。
   - 审批仍为用户已答的单级（Q10 A）：一个审批节点，经 `platform.approval`。
2. **招聘移出**：新上下文承载用人申请、应聘者、面试、录用。暂名 `organization.recruitment`。应聘者不是员工，录用生效前不建员工（沿用 ADR-0079 决定 2）。录用生效时经 workforce 的人事命令 api 发 HIRE；workforce 的入职、工号、账号开通不变。依赖：`-> organization.workforce（api）、platform.approval、platform.file、platform.numbering、platform.audit`。审批仍为用户已答的单级（Q9 A）。应聘者数据的保存期限自管，期限值待用户（ADR-0079 Q9）。
3. **留在 workforce 的分区**（组织结构、用工核心、劳动合同、执业资格与技能）：以下六条代替「日后拆分只搬包与表」。建该分区的第一张卡把六条写进完成标准：
   - 自有表；只存员工 ID，不加到 `employees`、`personnel_commands` 的外键，不与人事命令同事务写；
   - 不写 `state_transitions` 共享表，自有转换记录；
   - 自有权限资源名（`organization.workforce:<区资源>:<动作>`），不借用员工资源；
   - 自有 api 类型，不向 `EmployeeProfile`、`OrgDirectory` 加字段；
   - 自有事件类，不复用别区事件；
   - 自管保存期。
   满足六条的分区日后拆分只需改名与迁移；不满足的，其拆分成本按评审笔记 2.3 估。
4. **用人单位**（劳动合同区）：作为独立的带日期维度，有自己的表、api 查询与事件，事件名另起；不并入已建的 `EmployeeLegalEntityChanged`（它是 ADR-0073 的数据范围与成本法人，已建事件保留名称）。本条为沿用 ADR-0079 不变量 4 的写明，不取代它。

## 影响面

- `contexts.yaml`：随采纳登记两个 BC（planned）；`planned.yaml`：AGG-62「状态（含候选阶段、待入职）」改为不含候选阶段，AGG-65、AGG-106 改 BC；payroll 条目引用绩效改经 api。另有卡，不在本稿。
- `module-dependencies.txt`：随建造卡加边；`ModuleDependencyTest`、`ModularityTest` 按第 1、2 条方向生效。
- 不改代码、表、事件。

## 迁移方案

无数据迁移：招聘与绩效现无任何表或代码。迁入老系统数据按 ADR-0036、0037 与各卡。

## 回滚方案

本稿不落代码。推翻须另立 ADR 取代；因为现无代码，推翻不产生迁移成本，只回到 ADR-0079 的原分区并承认评审笔记 2.3 的拆分成本。

## 需同步修改的守护规则

- 建新 BC 的卡随卡登记 `data-access-registry.yaml`、`NamingSurfaceTest`、`module-dependencies.txt`。
- 第 3 条的六条是建卡检查，不新增自动检查（无对象可检查；首张卡落地时由该卡的复审对照）。

## 后果

- 好处：workforce 不再吸收变化最快、使用者最多的两个分区；绩效与招聘可用 `platform.approval`；应聘者数据与员工永久历史分开保存。
- 代价：多两个模块（登记行、schema、权限前缀）；转正画面要经两个 api 拼装，不再在 workforce 内读绩效；不能胜任链不被系统校验。
- 未定：招聘与绩效是否建、何时建（业务范围，用户）；技能的位置与时点（评审笔记 D9）；应聘者保存期；绩效结果是否真决定奖金（老系统只有标签，无字段级证据）；一人同时被两个用人单位雇用是否成立（评审笔记 7.3，决定员工版本模型是否够用）。

## 备选方案（未采用）

1. **绩效放 payroll**：评估人（全体直线经理）要在薪资上下文有写权限，且试用期评估服务转正而非发薪。
2. **绩效与招聘合并为「人才」上下文**：外部应聘者与在职被评人共用的只有「人事」二字，保存期与使用者都不同。
3. **全部留在 workforce（ADR-0079 原状）**：需要每区一套单级审批，且拆分成本如评审笔记 2.3。
4. **现在就拆出劳动合同与执业证书**：合同与员工同使用者、同生命周期，老系统无合同审批流；证书无老系统使用证据，先按第 3 条建。
