# ADR-0040：架构施工图方法与锁定版本的知识框架

- **状态**：已被 ADR-0041 取代（用户 2026-10-15 适配评审重定，intent `2026-10-15-195827`）
- **日期**：2026-10-15

## 背景

- 用户 2026-10-15：「本仓库是从旧系统现代化到新系统，要在现代化过程中完善togaf、ddd、bpmn、dmn、dama、oltp、olap等框架的ssot……避免按照旧系统架构直接现代化，我希望用上述架构来现代化，像施工图一样」（intent `2026-10-15-160111`）；「你需要有一个稳定的知识框架，不能漂移」（intent `2026-10-15-163920`）；「能不能彻底打通所有架构设计的核心理论，找到从愿景到代码的施工图的设计方法」（intent `2026-10-15-164119`）。
- 现状：GUIDING_PRINCIPLES §1–§8 说明了每个框架管什么，但框架之间怎么衔接没有规则；版本没有锁定，判断依赖记忆；没有愿景、能力、价值流的机器可读登记，规划中的 BC 来自老系统切法。

## 决定

1. **知识框架**：`docs/architecture/frameworks.md` 是架构判断唯一的理论参照，锁定版本：TOGAF Standard 第 10 版（C220，能力 G211、价值流 G178）、DDD（Evans 2003 原著与 DDD Reference 2015，支撑子域出自 Vernon 2013）、BPMN 2.0.2、DMN 1.6、DAMA-DMBOK 第 2 版修订版（2024）、Kimball 第 3 版（2013）；ArchiMate 只作建模参照。改动须引 ADR 或 intent，换版本须经用户同意；标「未核实」的条目不作硬依据。
2. **施工图方法**：`docs/architecture/method.md` 规定从愿景到代码的八步（愿景与原则、能力与价值流、战略设计、行为建模、数据设计、分析设计、迁移规划、实施治理），每步的交付物落在 `architecture/` 的 SSOT 文件中；六条接缝各有衔接规则与可校验的交接物；用稳定 ID 串成「目标 → 能力 → 价值流阶段 → BC → 聚合 · 命令 · 事件 → 流程 / 决策 → 数据对象 → 表 → 分析事实 → 指标 → KPI → 目标」的闭环。
3. **先登记、后写代码**：新 BC、聚合、事件、命令、流程、决策先在 SSOT 登记，再写代码；规划项（来自老系统切法或已有 ADR）在进入对应阶段前按第 1–5 步重新推导，不直接照搬为目标。重推可能触及已采纳 ADR 定下的边界：ADR-0016 决定 1（主干三件中的 `accounting.period`）、决定 5（`receivables.wip` 的一致性边界）、决定 9（`contract.changeorder`、`procurement.subcontracting`），ADR-0003 平台按技术能力拆模块，ADR-0039 的 `platform.integration` 定位与组织来源同步。**重推结果与这些 ADR 不同时，新开 ADR 取代，再改 SSOT**；不直接改 SSOT，也不直接改代码。
4. **KPI 只有一个来源**：KPI 与指标的口径按 OAT 原语声明（ADR-0016 决定 7，GUIDING_PRINCIPLES §9a OLAP 行），以 OAT 与 `docs/data/metric-baseline/baseline-draft.md`（确认后的正式版）为准。`togaf/vision.yaml` 只登记目标、KPI 的编号与名称、KPI 挂在哪个目标、对应哪个指标 M-xx，不写口径；不另建 `olap/metrics.yaml`，指标与事实 BC 的对应以 METRIC_BASELINE 为准。引用方向只有一个：KPI → 指标。
5. **决策归属**：第 0、1、2、5、6 步的结构性选择由用户在在线确认页上定（手机可用，推荐预选）；第 3、4 步由 one-architecture 提议、评审把关。
6. **防漂移**：两份文件列入 one-architecture 画像的「上下文文档」，压缩或清空后自动注入。

## 影响面

- 文档：`docs/architecture/frameworks.md`、`docs/architecture/method.md`（新增）。SSOT 文件到对应步骤才建，不预建（CS-1.8）：第 0、1 步建 `togaf/vision.yaml`、`togaf/capabilities.yaml`、`togaf/value-streams.yaml`；第 3、4 步扩充 `ddd/aggregates.yaml`、`bpmn/processes.yaml`、`dmn/decisions.yaml`、`dama/data-objects.yaml`（这四份目前只登记已建模块的现状，见 #208）。规则卡增加「类别」字段（只补类别，不改规则内容）。
- 流程：每个阶段开工前对本阶段涉及的价值流走第 1–5 步；GUIDING_PRINCIPLES 各框架章节以本方法为衔接依据。
- 会话：one-architecture 维护两份文件；其他会话新增 BC、聚合、事件、流程前先在 SSOT 登记。

## 迁移方案

按 one-coordinator 2026-10-15 排期补齐 METHOD 第 5 节的差距：
1. 第 0、1 步（愿景、目标、KPI；能力地图、价值流）合成一页在线确认页交用户；
2. 第 2 步按能力重新推导规划中的 BC，用户确认后作为子域分类（架构决策页 Q6）的依据，决策页余项随之一起发；
3. KPI 对应指标 M-xx（第 0 步之后，口径以 OAT / METRIC_BASELINE 为准）；
4. 事件风暴记录与规则卡补「类别」（第 2 步之后，批量补交 sonnet 子代理、one-architecture 抽查）；
5. CI 追溯完整性校验（最后，守护改动单列 PR，opus 复审）。

## 回滚方案

本 ADR 只增加文档与登记，不改代码；不采纳时撤回 `FRAMEWORKS.md`、`METHOD.md` 与新增的 SSOT 文件即可，已有的 `ddd/`、`togaf/transitions.yaml` 与图不受影响。

## 需同步修改的守护规则

- 新增（迁移方案第 5 步）：追溯完整性校验——每个已建 BC 至少承接一个能力，每个 KPI 对应已登记的指标，只拦新增。
- 改 `architecture/` 下文件的提交带 `Architecture-Ref:`（与架构校验 A6 一并实现）。

## 后果

- 架构判断有固定的理论参照与可校验的衔接规则，不随会话或记忆漂移。
- 规划中的 BC、子域分类要等能力地图与价值流确认后才能定，决策页余项相应推后。
- 增加一批登记工作；登记由 one-architecture 与子代理完成，用户只在结构性选择上确认。
- 排期：在途卡片（R-1b P2、P3b、P5，ADR-0039 的实施）不受本方法约束，照原排期进行；重推结果若改变这些卡涉及的 BC，走新 ADR 取代，再另排迁移（one-coordinator 2026-10-15）。
