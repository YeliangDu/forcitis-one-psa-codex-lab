  - 以后按 ADR-0026 第 7 项新增的 `*-sensitive:read`，或 ADR-0026 第 6 项第 2 条原列为敏感的「以后的过账 / 记账类权限」，若漏加清单就成了非敏感。
- **角色的敏感性还取决于角色码，不只取决于权限码**：
  - `roleIsSensitive` 把管理员角色与预留码也算作敏感（`SensitivePermissions.java`:25-27）；
  - `super_admin` 没有任何权限码（`V20261014130300__platform_identity_seed_roles_and_navigation.sql`:3-10），它的权限由管理模式给出；
  - 另有几处凭角色码授权：`ListAllTasks.java`:37-40 与 `ReassignTask.java`:44-47（流程管理员）、`ForceUserLogout.java`:68 与 `AdministratorSeparationReview.java`:41（`super_admin`、`security_auditor`，`Role.java`:28-29）。
- **有持有人的角色加入敏感权限，现在只需双人确认一次**：
  - 依据是 ADR-0026 第 6 项第 2 条（:116）中「或修改角色定义使其含有敏感权限」一句。ADR-0027 取代该条时（第 3 项第 2 条，`docs/adr/ADR-0027.md`:55）只重述了敏感权限清单与双人确认范围，没有重述这一句；本 ADR 取代的是 ADR-0026 中的这一句；
  - 实现上，`UpdateRole` 只在加入敏感权限码时开授权申请（`UpdateRole.java`:71-76、:74-82），放宽数据范围、停用改启用都不经申请；申请确认后直接应用，不复核持有人（:93-103）；
  - 后果：这个角色的全部现有持有人一次性拿到敏感权限，没有逐人确认；
  - 账号授权对已持有的角色又跳过敏感闸门与授予上限（`ReplaceAccountRoles.java`:82、:95、:130），所以之后也不会补上逐人确认。
- **除逐人授予外，现有的授予渠道**：
  - 默认角色：建档时授予一次（`AccountProvisioning.java`:38-54；RULE-344，`RULE_REVIEWS.md`:73），配置项 `forcitis.platform.identity.default-role`；
  - 运维命令：`GrantRoleByOperations.java`:54-77（`replaceRoles` 在 :70）；
  - 角色种子：Flyway 迁移，例如 `V20261015000800` 给安全审计员加 `separation-hold:approve`。
  - 管理模式与应急登录也是派生渠道：它们以逐人、双人确认授予的 `super_admin` 为前提（ADR-0027 第 1 项、ADR-0028 第 5 条），不另行授予。
- 本 ADR 与岗位术语之争无关，不以岗位取证为前置；按岗位分发的设计见 ADR-0029。

## 决定

### 1. 敏感权限只授给人

1. **角色的授予方式**取以下两者中较高的一级：
   - 角色所含权限的最高授予方式（第 2 项）；
   - 凭角色码授权的角色的内在授予方式：`super_admin`、`security_auditor` 为双人逐人；流程管理员为逐人。

   「双人逐人」与现在的 `roleIsSensitive` 同口径，保留管理员角色与预留码判定。
2. 授予方式为「双人逐人」的角色，只能逐人授予，并按 ADR-0027 第 3 项第 2 条双人确认。逐人授予包括账号授权，以及 ADR-0026 第 5 项第 5 条、ADR-0027 第 1 项第 7 条（未被 ADR-0028 取代的部分）规定的运维命令。默认角色、组织同步、待办处理，以及以后任何批量授予渠道，都不得授予这类角色。
3. **有持有人的双人逐人级角色不得扩大效力**（取代 ADR-0026 第 6 项第 2 条中「或修改角色定义使其含有敏感权限」一句）：
   - 「扩大效力」指加入权限码、放宽数据范围、停用改启用；角色修改后为双人逐人级（含因加入码而变成此级）即适用；
   - 有任何持有人时，上述修改一律拒绝（409），只能新建角色、再逐人授予；
   - 没有持有人时，上述修改走授权申请；确认时须复核仍无持有人，否则作废；
   - 首次部署后，Flyway 迁移不得给已有持有人的角色（不是同一迁移中新建的角色）加双人逐人级权限码；首次部署前的既有迁移列入例外清单，例外按第 2 项第 5 条处理。
4. **默认角色启动校验**：配置的默认角色不得含双人逐人级权限，也不得是凭角色码授权的角色；否则启动失败并告警。

### 2. 权限码显式声明授予方式

1. 每个权限码必须显式声明**授予方式**（提议术语），本 ADR 定两级：
   - `TWO_PERSON_INDIVIDUAL` 双人逐人：只能逐人授予，授予与收回须第二人确认；
   - `INDIVIDUAL` 逐人：只能逐人授予，即时生效（D-5）。
   - ADR-0029 若被采纳，会从「逐人」中再分出可经批量渠道分发的一级。
2. 初版：现有 `SensitivePermissions` 中的 6 个码为双人逐人，其余 19 个为逐人（`Permission.java`:42-66）。双人确认的范围与 ADR-0027 第 3 项第 2 条相同，不扩大也不缩小。`SensitivePermissions` 改为由声明派生。
3. 全部权限码及其授予方式写进快照文件 `backend/architecture/permission-grant-modes.txt`：
   - 新增权限码或改变授予方式，都必须改快照，按第 5 条评审；
   - 从双人逐人降级，须在 PR 中引用用户原话（第 5 条）。
4. **强制规则**：
   - `-sensitive:read` 结尾的码必须是双人逐人；
   - 必须为双人逐人的资源与 BC 登记在 `backend/architecture/two-person-resources.txt`（`<子域>.<bc>[:<资源>]`，各附理由），权限码命中登记项即必须为双人逐人，不论动作。首批登记：过账管道（`operations.facts`）、凭证资源（总账凭证）、薪酬与日薪等 L3 敏感读资源（ADR-0026 第 7 项）。以后新增的过账、记账类 BC 或资源在同一 PR 中登记。这份清单落实 ADR-0026 第 6 项第 2 条原列为敏感的「以后的过账 / 记账类权限」。
5. **评审落实到人**：
   - `permission-grant-modes.txt`、`two-person-resources.txt` 与迁移例外清单归用户本人。是否新增 CODEOWNERS，并在 main 分支保护中开启「需要代码所有者审查」，属仓库设置变更，交用户决定（0032-Q4）；
   - **不依赖仓库设置的兜底守护**：快照中任何从双人逐人的降级、`two-person-resources.txt` 的删减、迁移例外清单的新增，同一 PR 必须新增 `docs/decisions/` 下的片段（用户原话），且其原话或落点含被变更的权限码、资源或迁移文件名；CI 检查不到即失败。

### 3. 敏感角色的相对范围（0032-Q1）

**问题**：双人逐人级角色若用相对范围（`OWN_ORG_UNIT`、`OWN_ORG_UNIT_SUBTREE`、`SELF_AND_DIRECT_REPORTS`），调岗后范围自动变化，等于自动授予或收回敏感数据。二选一：

- (a) 双人逐人级角色只能用不随任职变化的范围：`ALL`、`CUSTOM_ORG_UNITS`、`SELF`。
- (b) 允许相对范围；调岗后，在第 4 项第 3 条的待办办结前，此人这些角色的范围按空范围计算（fail-closed）。登记为 `GLOBAL` 的资源不受范围影响。

建议 (a)：校验是静态的，没有运行期暂停状态，而且与「授给人」一致。

### 4. ADR-0026 第 6 项第 4 条重述（取代后全文）

1. **离职**：
   - 即时删除全部角色授予、停用应急账号、吊销会话（RULE-363；ADR-0027 第 1 项第 6 条），受 ADR-0027 第 1 项第 7 条（经 ADR-0028 修订）的同步暂停（HELD）约束；
   - 不另发通知：删除是确定动作，不需要人处理，逐条审计可查。
2. **调动**：
   - 相对范围随新部门变化，受第 3 项约束；
   - 含自定义部门或 `LISTED` 法人的授权，生成「待复核」条目给新部门负责人。
3. **敏感角色持有人的待调整权限**（用户原话 2026-10-14）：
   - **触发**：同步运行成功后，持有任一授予方式为双人逐人的角色的人，其任职数据字段 `assignments.org_unit_id` 或 `assignments.position_id` 发生变化。`position_id` 是 A8 `ORG_POST` 快照（`SyncedFields.java`:33-34），本条按数据字段定义，与「岗位」术语之争无关。前值按 `assignment_versions` 查前一日；不新增事件（D-1a-24）。派工中的「调岗、离岗」即指这两个字段变化；离职按第 1 条处理。
   - **送达**：生成「待调整权限」条目，送达组织数据管理员与安全审计员（0032-Q2）。收件人排除本人；没有收件人时，告警给 `account-role:update` 持有人与运维。
   - **不自动处理**：系统不自动授予，也不自动收回（后者属派工补充，见 0032-Q2）。
   - **办理**：条目只链接到标准授予流程，本身不提供授予或收回能力；收回或授予由 `account-role:update` 持有人按双人确认办理。
   - **状态**：开启 → 已确认保留（填原因）/ 已调整（关联授权申请或授予审计 id）/ 因离职关闭。超期 N 天未处理（0032-Q3）升级给 `account-role:update` 持有人。
   - **内容最小化**：只显示此人、触发前后的部门与岗位名称、「持有敏感角色」及角色名，不列权限码与范围。
4. **两类条目的关系**：第 2 条与第 3 条由同一次触发产生，是同一待办中的不同条目类型，各自送达、各自办结，互不替代，也不分先后。

### 5. 待办模型

1. 「待调整权限」（提议术语）建为通用模型：条目类型 + 去重键。
2. 本 ADR 定两种类型：
   - 敏感角色持有人：去重键为（人，触发同步运行，触发字段）；
   - 范围待复核。
3. ADR-0029 若被采纳，会追加岗位建议类型。
4. ADR-0029-Q4（「由人确认、不自动授予」是否适用于全部权限）的答复不改变本 ADR，只决定 ADR-0029 能否选择自动授予。
5. 待办表登记数据访问注册表；查看条目写审计。

## 迁移方案

1. 授予方式是代码常量，随发布生效。1a 尚未上线，没有在途数据。
2. 落地时核对：
   - 派生出的双人逐人集合与现有 `SensitivePermissions.CODES` 完全相同；
   - 默认角色 `employee` 的权限（`task:read`、`task:approve`、`own-login-record:read`，见 `V20261015000000…seed_business_roles.sql`:24）不含双人逐人级；
   - 现有带双人逐人级权限的角色（安全审计员、业务管理员）的持有人都是逐人授予的。
3. 第 3 项按 0032-Q1 落地时，核对现有双人逐人级角色的范围。不合规的角色由用户决定是改范围，还是新建角色后逐人迁移。

- 回退授予方式声明的提交，`SensitivePermissions` 恢复为清单。回退前须确认没有新增的敏感码只存在于快照中。

- 「待调整权限」待办与「敏感权限只授给人」守护是用户已定的事（intent 221958），回滚本 ADR 不撤销它们，只撤销本 ADR 新增的规则。

## 后果

- 每个权限码都显式声明授予方式。新增的码不声明就编译不过；`-sensitive:read` 结尾的码与命中双人逐人资源清单的码若标错，会被强制规则拦下；其他漏标靠快照评审发现，守护只能保证「有声明、有评审、降级有用户原话」，不能保证分级正确。
- 有持有人的双人逐人级角色不能再扩大效力（加码、放宽范围、重新启用），敏感权限的扩散始终逐人确认；代价是要多建角色。
- 「待调整权限」从派工说明变成 ADR 条款，与 ADR-0026 的调动处理一致。
- **已接受的代价**：组织数据管理员会通过待办知道谁持有敏感角色（只见角色名，不见权限码）。

## 备选方案（未采用）

- **保留排除清单**：漏标的敏感码会被当作非敏感，也无法表达凭角色码授权的角色。
- **按敏感 / 管理类 / 普通三级命名**：分别与列级敏感分级、`is_administrative`、「普通会话」撞词，而且第三级只为按岗位分发服务，留给 ADR-0029。
- **有持有人的角色加敏感权限时仍走一次双人确认**：一次确认就把敏感权限给了全部持有人，违背「授给人」。
- **待调整权限只写在派工里，不进 ADR**：ADR-0026 第 6 项第 4 条的冻结正文与系统行为不一致，以后的会话按 ADR 实现时会漏掉待办。
- **调岗即自动收回敏感角色**：用户原话只说「不自动授予」，是否自动收回交 0032-Q2；自动收回会让 A8 的一次误改直接撤掉审计员等关键角色。
