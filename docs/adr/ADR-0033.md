## 决定

### 1. 主键一律应用侧生成的 UUIDv7，自有表零例外

1. FORCITIS one 自有的每张表都有**单列 `uuid` 主键**，值由 kernel `IdGenerator` 在应用侧生成；kernel 默认实现改为 `Uuids.timeOrdered`（RFC 9562 v7）。数据库不分配标识：主键与 `_id` 列不得由序列、`GENERATED … AS IDENTITY` 或数据库默认值生成。**自有表零例外**（用户「主键统一」「也加，自有表零例外 (Recommended)」）。
2. **原以自然键或组合键为主键的表**，包括技术表，一律改为 UUIDv7 主键，原主键列改为命名唯一约束（`uk_<表>_<列>`）：`numbering_rules`（`document_type`）、`ticket_issuers`（`issuer_code`）、`login_states`（`state_hash`）、`numbering_counters`（`document_type, legal_entity_id, period_key`）、`consumed_events`（`event_id, consumer_name`）、`idempotent_responses`（`user_id, idempotency_key`）、`sso_ticket_uses`（`ticket_source, ticket_hash`）、`sync_run_held_separations`（`sync_run_id, employee_id`）、`process_archive_skips`（`process_instance_id`）。`account_roles`、`role_permissions` 由 ADR-0034（提议）取代为 `account_role_grants`、`role_versions`（权限集合为 `role_versions.permission_codes text[]`）；R-1b 合并时若两张旧表仍在，同样按本条改，不登记豁免。
3. **版本 / 生效区间表**（含带区间的归属表 `org_unit_legal_entities`、`employee_legal_entities`）：**UUIDv7 代理主键 + 自然键（实体自有 ID + 生效区间）排他约束**。区间一律用两列表示：按业务日期的用 `effective_from_date` / `effective_to_date`，排他约束写 `EXCLUDE USING gist (<实体 ID> WITH =, daterange(effective_from_date, effective_to_date, '[)') WITH &&)`；按时刻的用 `effective_from_at` / `effective_to_at`，排他约束写 `tstzrange(effective_from_at, effective_to_at, '[)')` 表达式（与 ADR-0034 一致），不建区间类型的列。去掉复合主键后，现有版本表的「实体 ID + 生效日 + 修订号」改为命名唯一约束（同一天多次修订时，空区间不参与 `&&`，排他约束管不住）；配置型版本表另有「实体 ID + 版本号」唯一约束。
4. **按 D17 / 后续 ADR 新建版本表时的标识形态**（建不建、何时建不在本 ADR）：员工、岗位、组织单元概况的版本表以 `employee_id`、`position_id`、`org_unit_id` 加日期区间作自然键；`role_versions`（`role_id` + 时刻区间，权限集合存本行 `permission_codes text[]`，不建成员行）、`account_role_grants`（`user_id` + `role_id` + 时刻区间）按 ADR-0034；日历版本见第 9 项。若某版本表另建成员行（每版本一组的明细，如日历版本的例外日），成员行是 UUIDv7 主键 + `(<版本 ID>, <成员>)` 唯一约束。
5. **引用版本时引用版本行的 UUIDv7 主键**（列名 `<版本表单数>_id`，如 `work_calendar_version_id`、`numbering_rule_version_id`），不引用「实体 ID + 版本号」组合，也不引用实体 ID 再按日期推断（§14.1 D7「使用方记所用版本 ID」）。
6. 哪些表版本化、何时改、授予由删除改为关闭等**行为**不在本 ADR 决定，见 SESSION_PLAYBOOK §14.1 D17与后续 ADR（含 ADR-0034）；实现随 W2 K-2 时态基座。本 ADR 只定第 3 至 5 条的标识与引用形态。
7. **1:1 扩展表**（`assignments`、`emergency_admins`）：主键就是所扩展实体的 UUIDv7（`employee_id`、`user_id`），同时是外键，不另设代理键；守护按单列 uuid 主键通过。`assignments` 以 `employee_id` 为主键只表示**主岗投影**（每人一行）；兼岗存在（ADR-0029 取证，兼岗 ≥ 7 人），兼岗若入模另建表，按第 1、3 条取 UUIDv7 主键。
8. **豁免只剩框架自建表**，登记在 `backend/architecture/primary-key-exemptions.txt`，每行一张表、写理由，由守护读取：
   - `platform_identity.sessions`：`primary_id char(36)`，Spring Session JDBC 的 SQL 写死列名与类型；
   - `platform_identity.sessions_attributes`：`(session_primary_id, attribute_name)` 复合主键，由框架决定；
   - `platform_scheduling.scheduler_locks`：`lock_name` 作业名自然键，ShedLock 不可配置；
   - `platform_integration.event_publication`、`event_publication_archive`：已是 `uuid`，由 Spring Modulith 生成（不经 `IdGenerator`）。
   
   Flowable `act_*` 表结构归引擎、不在本仓库迁移中，ID 值按第 8 项由 kernel 生成 UUIDv7，**不列入豁免**。
9. **聚合 ID 在构造时生成**：聚合在工厂或构造方法中向 `IdGenerator` 取 ID，不在仓储插入时生成；领域事件直接带这个 ID（平台约定 §1 方案 B 的初衷）。随 R-1b 实现。
10. **顺序**：kernel 实现须保证**单进程内**单调（同一毫秒内按 RFC 9562 §6.2 用计数位递增；现 `Uuids.java:24` 同毫秒低位随机，不满足，R-1b 改）。多实例部署时 `ORDER BY id` 不等于全局插入顺序，**任何代码不得依赖跨实例的 ID 顺序**；需要全局次序时用显式序号（如 `postSeq`）或时刻列。游标分页、归档批次、「最近一条」按「时刻列 + 主键」排序（例如 `ListSyncRuns.java:26` 现按 bigint 游标翻页，改为 `(started_at, id)`）。
11. Java 侧类型化 ID 全部包 `UUID`：`UserId`、`EmployeeId`（新，在 kernel）、`OrgUnitId`、`PositionId`、`LegalEntityId`、`ApprovalTaskId`、`DocumentId` 等由 `long` / `String` 改为 `UUID`；跨模块不出现裸 `long` / `String` ID（§14 第 6 项）。除 kernel 的 `Uuids` 外，生产代码不得调用 `UUID.randomUUID`（框架内部生成的不在此列）。
12. **序号不是标识**：过账序号 `postSeq`（ADR-0016、0025、0031）、编号计数值、轮次等是有序的数值，用于排序、水位与校验。`postSeq` 是**业务唯一键，可被引用，不作主键**：事实行仍有 UUIDv7 主键；`postSeq` 有唯一约束，列名以 `_number` 结尾（过账序号列名在实现 PR 中按 §2.4 定并登记术语），可以由数据库序列生成，可以跨模块传递与引用（ADR-0031 冲销候选引用原 `postSeq` 不改）。编号计数值、轮次同理。守护只禁止主键与 `_id` 列由序列或 identity 生成。

### 2. 外部标识只在集成层的来源对照

1. 新建 `platform_integration.source_references`（来源对照）：
   - 列：`source_reference_id uuid`（UUIDv7 代理主键）、`source_system`（来源系统，text + CHECK）、`source_object_kind`（来源对象类别，text + CHECK，取值用自有用语，如 `EMPLOYEE`、`ORG_UNIT`、`POSITION`、`LEGAL_ENTITY`，决定 `own_id` 指向哪类自有对象）、`source_id`、`own_id uuid`、`confirmation_status`（确认状态，见下）、带区间类别的 `effective_from_date` / `effective_to_date`、审计列。
   - `source_id` 按来源的实际类型存放：A8、老系统、核算系统的标识都是 64 位有符号整数，`bigint`，**允许负数和任意符号**，不加正数 CHECK；按类别另加校验，例如（核算系统, `LEGAL_ENTITY`）类别的核算组织编码须 > 0（原 `ck_legal_entities_accounting_organization_number` 的条件随之移到本表，写成限定该类别的 CHECK）。以后接入文本标识的来源时另定（修订本条或另立 ADR），不得把文本塞进 `bigint`，也不得把整数转成文本存。
   - 自然键：`(source_system, source_object_kind, source_id)` 与 `(source_system, source_object_kind, own_id)`，**在任一时点各自唯一**（一个来源对象只对应一个自有对象，一个自有对象在一个来源中只对应一个来源对象）。违反即失败并告警，不静默覆盖；来源中出现「同一人两个 ID」之类的合并需求时，另行决定。
   - **确认状态与区间**：`confirmation_status` 取 `PENDING`（待确认）/ `CONFIRMED`（已确认）/ `REJECTED`（已拒绝），沿用已有提议术语「确认状态」`confirmation_status`，取值在 R-1b 登记术语（编号规则版本的待确认写作 `PENDING_CONFIRMATION`，登记时统一写法），与编号规则版本的「待确认 / 已确认」做法一致。由来源同步分配的对照（A8 同步、老系统一次性导入）写入即为 `CONFIRMED`；人工登记的对照（只有核算组织编码，第 5 项第 3、4 条）按第 5 项第 4 条确认。上面两个自然键只约束已确认行：带区间的类别为 `EXCLUDE USING gist (source_system WITH =, source_object_kind WITH =, source_id WITH =, daterange(effective_from_date, effective_to_date, '[)') WITH &&) WHERE (confirmation_status = 'CONFIRMED')`（`own_id` 一侧同样写法）；不带区间的类别为同一 `WHERE` 条件的部分唯一索引。待确认行与已拒绝行不占约束。出站与同步只读已确认行。确认时在同一事务内关闭旧的已确认行（`effective_to_date` = 新行生效日）并把待确认行置为已确认。某类别的来源标识若会变化（如核算组织编码），该类别必须带区间（主数据版本化盘点把本表列为维度型）。任何情况下既有行的 `source_id` 与 `own_id` 都不改写；哪些类别带区间、对照保留多久见 §14.1 D17。
2. **分配**：集成层在首次见到某来源对象时用 `IdGenerator` 分配 UUIDv7。写法为 `INSERT … ON CONFLICT DO NOTHING` 后再按唯一键读回，并发同步对同一来源对象只得到一个自有 ID。对照在交给领域模块之前先提交；领域写入失败时对照保留，下次运行复用同一 ID。
3. **同步按来源 ID 匹配**：组织同步先按 `(来源系统, 类别, source_id)` 查对照，找到就用已有的自有 ID，找不到才新建对象与对照。不按姓名、编号、登录名等属性匹配。
4. **领域与其他模块只用自有 ID**：`OrgSource` 等集成层接口交出的快照只带自有 ID；`SourceUnitId`、`SourcePersonId`、`SourcePositionId` 删除，`SourceTerms` 中的 ID 翻译随之删除（枚举翻译可留在集成层的适配器内）。除 `platform.integration` 外，任何模块不出现 `Source*Id` 或其他来源标识类型。
5. **出站**：向外部系统发数据时，由该系统的出站适配器按 `(来源系统, 类别, own_id)` 查对照取外部标识；查不到即失败并告警（该笔投递挂起），不推送缺标识的数据。
6. `ShortNameAdapter.java:22`「老系统部门 ID = A8 ID」的假定不得沿用：老系统部门简称经 `(老系统, ORG_UNIT)` 对照取自有 ID；两者若确实相等，须以生产数据为证据写入 R-1b 的 PR，并仍经对照表查。DA-8（简称改为自有属性）另走结构性重构卡。
7. **迁入数据**：以后各阶段迁入的老系统数据用 UUIDv7 新主键，老 ID 登记为 `(老系统, <类别>, 老 ID)` 对照，**不在业务表加 `legacy_id` 列**。业务可见的原单据编号仍按 ADR-0010 第 5 条进 `legacy_numbers`（DA-11：加 `source_system` 列与 CHECK，唯一改为 `(source_system, document_type, legacy_number)`）。
8. `source_system` 的取值按系统登记术语（组织源、老系统、核算系统各一个），在 R-1b 中定名；领域模块不出现这些取值。
9. **老系统待办**（`JdbcLegacyInbox`、`LegacyInstanceId`）移入集成层：按 `(老系统, EMPLOYEE, …)` 对照取当前用户在老系统中的人员 ID 再查老系统视图；查不到对照时该来源返回「不可用」并在合并待办中标明，不按 0 条处理。审批模块只收到自有类型的待办条目。
10. **多态引用的规则**：同一 schema 内、目标表固定、能建外键的引用拆成分列 + 外键 + 「恰有一个非空」CHECK（第 7 项第 4 条）；需要指向任意类别对象的跨 schema 记录（来源对照、审计对象、同步差异、投递去重）允许「类别 + uuid」两列，类别取值有 CHECK，不拼成文本。
11. **老系统人员与部门的对照**（`source_system` = 老系统，类别 `EMPLOYEE`、`ORG_UNIT`）一次性导入：按生产数据核对老系统人员、部门 ID 与 A8 ID 的对应关系（证据写入导入 PR），对得上的登记对照，对不上的列差异清单、不登记；列入 R-1b 验收。以后老系统新增的对象不自动登记。

### 3. 用户账号与员工分开标识

1. `platform_identity.user_accounts.user_id` 是 identity 分配的 UUIDv7，**不等于员工 ID**；另设 `employee_id uuid NOT NULL`，唯一约束，引用员工的自有 ID（跨 schema，不建外键）。账号由 identity 的 `ensureAccount` 创建（4 个入口，见背景），写法为 `INSERT … ON CONFLICT (employee_id) DO NOTHING` 后按 `employee_id` 读回，并发时同一员工只得到一个账号。
2. 会话主体名为 `user_id` 的 uuid 字符串；`Long.parseLong` 全部改为 `UUID.fromString`，格式不对即拒绝请求（视为会话损坏），不回退。`CurrentUser` 同时给出 `userId` 与 `employeeId`，都在登录时从 identity 自己的表解析，不来自请求。
3. **「人」的引用按语义选类型**：
   - 单据与组织数据上的人（工时的填报员工、制单人、申请人、负责人、部门负责人、直属领导、任职、法人归属对象）用员工 ID（`EmployeeId`，在 kernel：ADR-0026 第 1 项第 1 条把 `AccessScope` 下沉 kernel，它要引用员工 ID）；ADR-0026 数据范围的 `owner_id` 同此，`:owners` 由 `CurrentUser.employeeId` 计算。
   - 系统操作主体（账号、角色授予、会话、应急账号、审计操作人、事件信封 `actorId`、审批任务的候选人与办理人、幂等记录的调用人）用用户 ID（`UserId`）。
   - 两者的转换只经 identity 的 api（按 `employee_id` 唯一查账号，反之亦然）。
   - **审批**：流程变量 `initiator` 存员工 ID；表单选人字段与部门变量存员工 ID、组织单元 ID 的 uuid 文本；只在写入 Flowable 办理人、候选人时转为用户 ID（`FlowableApprovalEngine.java:297-305`、`NodeAssignment.java:46`、`TaskAssignmentListener.java:57`）。员工没有账号时指派失败并告警，不静默跳过。改派与转交请求的 `assigneeId` 是员工 ID（界面选人来自通讯录），服务端转为用户 ID。`ProcessVariables.parseUsers` 等解析遇到非 uuid 或解析不到的值失败并告警，不跳过该值。
   - **「本人」判定清单**（每一处都写明在哪一侧比较，两侧类型不同的比较由编译检查拦下，见守护 14）：

     | 闸门 | 比较方 | 比较一侧 |
     |---|---|---|
     | 应急登录的在职校验（`LoginAsEmergencyAdmin.java:94`） | 应急账号绑定的用户 → 其员工 | 员工 ID：先经 identity 取 `employee_id`，再查在职快照 |
     | HELD 放行人须留任、不在离职名单（`ReleaseSyncRunHolds.java:50`、`AdministratorSeparationReview`） | 放行人 vs 待离职名单 | 员工 ID：放行人取 `CurrentUser.employeeId` |
     | 法人归属自改禁令（`OwnAttributionGuard.java:32-43`） | 操作人 vs 归属对象（员工或部门链） | 员工 ID / 组织单元 ID：操作人取 `employeeId` 及其部门链 |
     | 审批自批排除、发起人上级与部门（`AssigneeResolver.java:44,84,110`） | 发起人 vs 候选人 | 员工 ID：在转为用户 ID 之前比较 |
     | 不能改自己的角色（I-12 前半句，`SensitiveGrantTwoPersonIntegrationTest`，SECURITY_INVARIANTS.md:62） | 操作人 vs 被授予人 | 用户 ID：两侧都是账号 |
     | 修改角色定义的确认人不得持有被修改的角色（I-12 后半句） | 确认人 vs 该角色当前持有人 | 用户 ID |
     | 编号模板四眼：确认人不是该版本作者（ADR-0027 第 2 项第 4 条） | 确认人 vs 作者 | 用户 ID |
     | 核算组织编码四眼：确认人不是录入人（第 5 项第 4 条） | 确认人 vs 录入人 | 用户 ID |
     | 授权申请的确认人不是申请人（ADR-0034，提议） | 确认人 vs 申请人 | 用户 ID |
     | 审批办理只认处理人（I-7，`TaskGuard`） | 当前用户 vs 任务办理人 | 用户 ID |

   - R-1b 的「ID 承载位置清单」对每一列写明属于哪一种；拿不准的报 one-coordinator。
4. 应急账号（`emergency_admins.user_id`）引用 `user_accounts.user_id`，不变。
5. **签名票据**：外部签发方不知道自有 ID，票据 subject 按「每个签发方一个 `provider_kind`」经 `external_identities` 解析为 `user_id`（第 4 项）；解析不到即拒绝登录并审计。DA-3 落地前沿用现行解析，R-1b 只把结果类型改为 `UserId(UUID)`。
6. **运维命令**：授予与登记类命令收 `--employee-id`（员工自有 ID，uuid 文本），由 `ensureAccount`（即第 1 条 4 个入口中的 `GrantRoleByOperations`）取得或建立账号；格式不对或员工不存在时退出码非 0、不写任何数据。另提供只读查询命令：按 A8 登录名或企业微信 userid 返回匹配的员工 ID 与 `user_id` **列表**（可能多条，由运维核对后再用），不按员工编号查。INFRA_RUNBOOK 与 C-5 剧本（ADR-0030 迁移方案第 2 条的 dev 起步步骤）同步改写。
7. **应急登录的在职校验**（`LoginAsEmergencyAdmin.java:94`）：先经 identity 取绑定账号的 `employee_id`，再查在职快照。区分两种情况：
   - **快照整体不可用或过期**（A8 或同步故障，ADR-0027 第 1 项第 3 条与 D-1a-48 的本意）：按 ADR-0027 放行，并告警；
   - **快照可用但查不到该员工**：拒绝并告警（现代码为放行）。理由：快照正常而绑定人不在其中，最可能是已不在 A8 结果集（RULE-366 视为离职候选）或绑定数据错误；按「缺失或无效输入失败并告警」处理。
   ADR-0027 原文「快照缺失……放行」字面上也覆盖第二种情况，因此这一点写进「取代」行，列为待用户决定 U-4；用户不同意时保留放行、只加告警。ADR-0027 守护第 1 条 `EmergencyLoginIT` 中「快照缺失 → 允许」随之拆成两条断言。

### 4. 外部身份绑定在 identity（DA-3、DA-10）

1. identity 新建 `platform_identity.external_identities`（外部身份）：`external_identity_id uuid`（UUIDv7 代理主键）、`provider_kind`（身份提供方类别，text + CHECK：企业微信 userid、致远登录名等）、`external_subject_key text`（外部主体标识；概念名 external_subject，列名按 NAMING_STANDARD 用 `_key` 类别词）、`user_id uuid`、`effective_from_at` / `effective_to_at`（绑定时刻与解除时刻）、审计列。自然键为 `(provider_kind, external_subject_key)` 与 `(provider_kind, user_id)`，各自以 `tstzrange(effective_from_at, effective_to_at, '[)')` 表达式加排他约束（企业微信 userid 会被复用，须能回答「某一时刻这个外部身份是谁」，与主数据版本化盘点一致）。绑定、换绑、解除的行为规则见 §14.1 D17 与 DA-3 的结构性重构卡。
2. 登录时按 `(provider_kind, external_subject_key)` 找 `user_id`，不再经组织快照反查；`OrgSource.findStaffByWecomUserId` / `findStaffByLoginName` 删除。
3. 员工快照不存外部身份：`employees` 删除 `login_name`、`wecom_user_id`。集成层的防腐层把 A8「登录名为空即离职」（RULE-363）翻译为来源在职状态（`SourceEmploymentState`，集成层类型，进领域前已映射为自有 `EmploymentStatus`）；领域层不再出现「登录名」判断。
4. **收件人解析移入集成层**（DA-10）：外发投递接口收 `List<UserId>`，由集成层经 `external_identities` 解析企业微信 userid；`WecomUserId` 从 kernel 移入 `platform.integration`；审批等业务模块不再接触企业微信标识。
5. **时机**：DA-3、DA-10 是结构性重构卡，在**首次部署前**完成，不并入 R-1b；R-1b 期间 `login_name`、`wecom_user_id` 先留在快照里，并登记在 `ddl-naming-baseline.txt`（写明「随 DA-3 删除」）。外部身份的数据分级沿用 ADR-0026 第 7 项第 4 条（企业微信 ID 为 L2）。

### 5. 法人的核算组织编码移到来源对照（DA-9，用户已定）

1. 删除 `legal_entities.accounting_organization_number`；核算组织编码登记为 `(核算系统, LEGAL_ENTITY, 编码 → 法人自有 ID)` 的来源对照。法人领域事件与 `LegalEntityResponse` 不再带该编码。
2. 凭证推送等出站适配器按第 2 项第 5 条查对照；法人尚无编码时，涉及它的投递挂起并告警。
3. **维护入口在集成层**（U-2 已答「新权限，授给组织数据管理员 (Recommended)」）：组织数据管理员在法人页面看到并登记编码，接口归 `platform.integration`，权限码 `platform.integration:source-reference:update`（提议，授予组织数据管理员）。按 ADR-0032 第 4 项声明授予方式为 `INDIVIDUAL`（逐人）：资源不命中 `two-person-resources.txt` 首批清单（过账管道、总账凭证、L3 敏感读），与 ADR-0027 Q-2「组织数据管理员 1a 不列敏感」一致。
4. **核算组织编码的登记与更正**：编码决定凭证推送到核算系统的哪个组织，填错会把整月凭证推到别的账套。
   - `source-reference:update` 接口**只接受（核算系统, `LEGAL_ENTITY`）类别**；其他类别（尤其 A8 的 `EMPLOYEE`、`ORG_UNIT`、`POSITION` 与老系统类别）只由同步或一次性导入写入，人工改写一律拒绝（无权限 403；类别不允许 422），并写审计。
   - **若 U-3 选设四眼（建议）**：比照编号模板（ADR-0027 第 2 项第 4 条），每次登记或更正写入一行 `PENDING`（带生效日）；另一人确认后按第 2 项第 1 条在同一事务内转为 `CONFIRMED` 并关闭旧行，确认人不能是录入人（同一人持两个角色也不行），确认权限 `platform.integration:source-reference:approve`（提议，`INDIVIDUAL`）；也可拒绝，行置 `REJECTED`。待确认期间出站仍用原已确认、生效中的行；从未确认过编码的法人，涉及它的投递挂起并告警。
   - **若 U-3 选不设四眼**：登记即写 `CONFIRMED` 并关闭旧行，不设 `:approve`。
   - 登记、确认、拒绝都写审计。
5. **法人主键是 UUIDv7；法人代码是业务键，不作主键**，用于业务编号 `{LE}` 与显示，有唯一约束，不被任何表作外键引用。该法人**发过号之前可更正**（写审计，发 `LegalEntityCodeCorrected`），**发号后禁改**（用户 2026-10-15：「未发过号前可更正，发号后禁改 (Recommended)」；更名只改名称走版本）。「是否已发号」由 workforce 经 numbering 的 api 查询（`LegalEntityNumberUsage.hasIssuedNumbers`，现已实现，`UpdateLegalEntity.java:40`），不新增跨聚合事务。R-1b 的文档改写中纠正基线列注释「创建后不改」（workforce 基线 :222）。
6. **D-1a-28 的落点改写**（SESSION_PLAYBOOK §12）：D-1a-28 的决定（「两种代码并存 (Recommended)」：字母代码用于业务编号，对接核算系统按数字编码）不变，只改落点——由「法人表增加核算组织编码列」改为「来源对照」。该落点属代码类（DDL），依据是用户对 DA-9 的答复；`docs/business/processes/contract.md:67` 与 `docs/business/processes/org-and-personnel-sync.md:374` 不删原文，在 R-1b 的 PR 中追加「落点已由 ADR-0033 第 5 项改写」。

### 6. 员工编号不作键；ID 对外为字符串

1. A8 员工编号（`ORG_MEMBER.CODE`，自有列 `employee_code`）不唯一（5 个重复、42 人为空）。**任何模块不得以员工编号作主键、唯一键、外键、关联键或匹配键**；它只是可显示、可检索的属性。
2. 所有 ID 在 JSON（接口、事件载荷、外部投递）中一律为字符串（uuid 的标准文本形式）；OpenAPI 中 ID 字段为 `type: string, format: uuid`，不出现 `int64` 的 ID。来源对照中的 `source_id` 只在集成层内部与外部系统之间使用，不进 FORCITIS one 的接口与事件。

### 7. 文本 ID 承载位置拆为「类别 + uuid」（DA-4、DA-5）

1. 事件信封：`aggregateType` 保持文本类别，`aggregateId` 与 `actorId` 改为 `UUID`（JSON 中为 uuid 字符串）；`AggregateReference` 同。事件目录 `events/*.yaml` 的 `aggregateId` 声明 `format: uuid`。
2. 审计对象：`audit_entries.subject_key` 拆为 `subject_kind`（text + CHECK）与 `subject_id uuid`，索引 `(subject_kind, subject_id, created_at)`；`sync_diffs.subject_key` 同样拆分。员工查本人登录记录改为按 `subject_kind = USER_ACCOUNT` 且 `subject_id = 本人 user_id` 查询（取代 ADR-0027 第 3 项第 3 条中的写法；其余限定不变）。
3. 外发投递去重：`outbound_deliveries.deduplication_key` 拆为对象类别、对象 ID（uuid）、收件人 `user_id` 与用途类别等结构化列，唯一约束建在这些列上；具体列在 R-1b 的清单中列出。
4. 法人归属：`legal_entity_attributions` 与更正表的 `subject_kind + subject_id` 多态引用改为两个可空列（`org_unit_id uuid`、`employee_id uuid`）加「恰有一个非空」的 CHECK（DA-5）；`AttributionSubject` 的 `long subjectKey` 改为分别的类型化 ID。
5. 单据引用统一用 `DocumentReference(DocumentType, DocumentId)`，`DocumentId` 包 `UUID`。
6. 审计归档、会话清理等按 bigint 顺序的逻辑改为按时刻列（第 1 项第 10 条）；去掉 `COALESCE(…, 0)` 等整数哨兵。
7. R-1b 交付「ID 承载位置清单」：逐列列出存放 ID 的位置（主键、引用列、文本键、事件字段、OpenAPI 字段、会话、日志字段），每项给出改法或「不是标识」的结论，作为验收物。

### 8. Flowable 的 ID 由 kernel 生成（DA-6）

1. 流程引擎配置的 `idGenerator` 接 kernel `IdGenerator`（UUIDv7 的标准文本），**取代 NEXT_BATCH_PLAN.md:108 中「`StrongUuidGenerator`」的计划**。流程实例与任务 ID 因此就是自有 UUIDv7；流程定义 ID（`key:version:id` 形态）与 `process_key` 不是标识承载位置，保持 text。
2. `approval_tasks` 以任务 ID（`uuid` 类型）为主键；`approval_requests`、`start_rounds` 改 UUIDv7 主键；子表以 `approval_request_id uuid` 引用根，不再以 `(process_key, document_key)` 文本挂根；单据引用用 `DocumentReference`。
3. OpenAPI 与事件中的任务、实例 ID 是 uuid 字符串；不暴露 Flowable 专有的 ID 形态。

### 9. 工作日历的标识形态（DA-17）

1. 用户已定日历按配置类版本化（「版本化 (Recommended)」；SESSION_PLAYBOOK §12.2、§14.1 D15：只追加、生效日、不追溯）。**版本化本身随 W2 K-2 时态基座一次改到位**，范围与时机见 §14.1 D17；本 ADR 只定标识与引用形态。

3. 日历版本（主数据版本化盘点拟建 `work_calendar_versions` 与 `work_calendar_version_days`，取代年度与日期两表）按第 1 项第 3、4 条：UUIDv7 代理主键；自然键为「日历标识（`calendar_scope_kind` + `legal_entity_id`，同上用部分唯一索引，不用哨兵）+ 版本号」唯一；版本的例外日为成员行，`(work_calendar_version_id, calendar_date)` 唯一；使用方（如审批任务的时限计算）记所用的 `work_calendar_version_id`。新版本的确认人（盘点 Q1）与取版本的规则属行为，见 §14.1 D17 与后续 ADR。

## 迁移方案

1. **没有已部署数据**：FORCITIS one 尚未部署任何环境，基线开放（`backend/architecture/migration-baseline-open`；SESSION_PLAYBOOK §12.2「开放期内直接改基线 (Recommended)」）。R-1b 直接改各 schema 的基线文件，不追加迁移；每个 PR 附「预期表结构 diff」（两个空库分别执行改动前后的基线，`pg_dump --schema-only` 的差异只能是声明的改动），由 opus 核对。
2. 种子数据（导航、编号规则等）中的主键改为固定的 UUIDv7 字面量；系统角色的主键来自系统角色声明中的固定 UUIDv7，由 ADR-0034 的启动对账写入，迁移不写角色。种子中不出现任何人员或账号 ID（ADR-0026 第 5 项第 5 条）。
3. 本机与测试库直接重建；A8 数据在下一次同步时全部按「首次见到」分配自有 ID。
4. 以后阶段的老系统数据按第 2 项第 7 条迁入：新主键 + 老 ID 进来源对照 + 原编号进 `legacy_numbers`。
5. 基线开放标记删除（首次部署 dev 前，部署剧本 C-3 第一步）之前，R-1b 与 DA-3 / DA-10 的结构性重构卡都须合并；之后任何标识形态的变化都只能追加迁移并另立 ADR。

## 回滚方案

- **基线开放期内**（首次部署前）：按子 PR 逆序回退即恢复原基线与代码，重建本机库，没有数据需要转换。回滚边界是子 PR：同一子 PR 内的主键类型、事件、OpenAPI 与前端生成物一起回退；只回退后面的子 PR 时，前面已合并的部分保持一致可用（每个子 PR 都全量通过守护）。
- **Flowable `idGenerator` 单独出问题时**：退到 `StrongUuidGenerator`（产出 version 1 的 uuid 文本，可解析为 `uuid`），表结构不变，`FlowableIdTest` 同一提交改为接受 version 1 并注明原因；不退回引擎默认的顺序数字 ID。
- **来源对照分配出错**（重复分配或指错对象）：首次部署前清库重同步即可；部署后的更正方式随 D17 定（第 2 项第 1 条末段），任何情况下不改写既有行的 `source_id` 与 `own_id`。
- **首次部署之后**：基线已关闭，标识形态的回退只能另立 ADR 并追加迁移；本 ADR 不提供这条路径的预案，因为部署前必须完成全部改动并通过守护。
- 文档标注（平台约定、指导原则、NAMING_STANDARD）是文本，用户不批准时撤回标注即可。

## 需同步修改的守护规则

以下除另注外，都在 **R-1b 实现 PR** 中修改：

1. `PrimaryKeyTypeGuardTest`：扩到复合主键与 text 主键——每张表的主键必须是单列 `uuid`；例外只读 `backend/architecture/primary-key-exemptions.txt`，只允许第 1 项第 8 条的 5 张框架表，每行写理由，过期行失败；自有表全部通过、无基线行，`primary-key-type-baseline.txt` 在最后一个子 PR 删除。另查：主键与 `_id` 列不得由序列、`GENERATED … AS IDENTITY` 或数据库默认值生成（`_number` 序号列不受此限，第 1 项第 12 条）；带生效区间（`effective_from_date` / `effective_to_date` 或 `effective_from_at` / `effective_to_at`）的表必须有 uuid 主键与「自然键 + 区间」的排他约束；引用版本的列必须引用版本行主键（`*_version_id uuid`）。

## 后果

- 新系统的标识不依赖任何外部系统：A8 退役、换组织源或老系统下线都不改主键；同一个人、部门的自有 ID 在全部模块、事件、接口中一致。
- A8 ID 只在一张表里，唯一性、负数、并发分配集中测试；领域代码不再有「来源 ID 恰好等于自有 ID」的隐含假设。
- 用户账号与员工分开后，「人」的每个引用都要选定类型（第 3 项第 3 条），R-1b 的改动面比只换类型大；作为交换，账号停用、外部身份换绑不再牵动员工数据。
- 镜像回填老 BI（ADR-0025 第 5 条）要从来源对照取老雪花 ID；新系统中新建、没有老 ID 的对象如何在镜像中表示，由 6a–6c 入口物「逐列映射规格」决定，本 ADR 不定。
- 主键从 8 字节变为 16 字节，索引变大；UUIDv7 的时间前缀保持 B 树插入局部性。
- 排序不能再依赖主键大小，所有翻页、归档要显式带时刻列；多实例时 ID 顺序与插入顺序无关。
- 人员引用分成员工 ID 与用户 ID 后，审批指派、数据范围、签名票据多了一次经 identity api 的转换。

## 备选方案（未采用）

- **沿用来源 ID 作主键**（原平台约定 §1）：快照表主键就是 A8 ID，最省事；但外部系统的标识形态（有符号 bigint、可为负、随 A8 存续）进入所有模块、事件与接口，A8 退役或换组织源时要全库换键；与用户「改为自有 UUIDv7」「主键统一」相反。
- **在快照表加 `source_id` 列而不建对照表**：贴近「A8 ID 对照列」的字面；但 A8 ID 仍落在领域 schema，领域仓储能按来源 ID 查询，守护难以划界；老系统 ID、核算组织编码要各加一列，唯一性与并发分配分散在各模块；出站适配器要跨 schema 读领域表。
- **UUIDv4**（现默认 `UUID::randomUUID`、`StrongUuidGenerator` 的同类）：完全随机，B 树插入分散、页分裂多；不带时间信息，排查与归档无法按 ID 粗定位时间。v7 由同一 `IdGenerator` 提供，成本相同。
- **雪花 bigint**（平台约定方案 C）：与老系统形状一致、要分配机器号，平台约定已否决。
