# ADR-0038：迁移基线在生产部署前关闭

- **状态**：已采纳（用户 2026-10-15：「批准（推荐）」，经 one-coordinator 转达；依据 intent 2026-10-15-124901）（决定 1（部分）已被 ADR-0054 取代）
- **日期**：2026-10-15
- **取代**：ADR-0033 迁移方案第 5 条中「基线开放标记删除（首次部署 dev 前，部署剧本 C-3 第一步）」的时点、ADR-0033 迁移方案第 1 条中「尚未部署任何环境」作为直接改基线的前提、ADR-0033 第 4 项第 5 条中 DA-3 与 DA-10「在首次部署前完成」的时点、ADR-0033 回滚方案第 1 条「（首次部署前）」第 3 条「首次部署前清库重同步」与第 4 条「首次部署之后：基线已关闭」中以首次部署为基线开放期界限的时点、ADR-0032 第 1 项第 3 条第四点中迁移约束以「首次部署」为界的时点

## 背景

- **用户决定**（2026-10-15，经 one-coordinator 转达）：「部署前开发编排三项都采纳：加一个并行工程会话；dev 部署与结构重构解耦（基线 dev 期间保持开放、生产前关闭）；F-1 提前到 R-1b 收口（P5）后就开」（intent `2026-10-15-124901-one-coordinator-部署前开发编排三项都采纳-加一个.md`，PR #173）。落点写明「部署守护的基线开放标记检查改为只拦生产；dev 库随基线变化重建（one-ops 剧本）」。本 ADR 只落第二项；并行会话与 F-1 的编排在 NEXT_BATCH_PLAN 第 8 节（PR #175 新增，尚未合并）。
- **现行规则把基线关闭锚在首次部署 dev**：
  - ADR-0033 迁移方案第 5 条：「基线开放标记删除（首次部署 dev 前，部署剧本 C-3 第一步）之前，R-1b 与 DA-3 / DA-10 的结构性重构卡都须合并」（`docs/adr/ADR-0033.md:243`）。同一 ADR 还有几处以首次部署为界：迁移方案第 1 条的前提「尚未部署任何环境」（`:239`）、第 4 项第 5 条 DA-3 / DA-10「在首次部署前完成」（`:143`）、回滚方案第 1、3、4 条（`:247`、`:249`、`:250`）。
  - SESSION_PLAYBOOK §12.2「首次部署前的迁移基线」：「已应用」指已在任一环境（dev、生产）执行过（`SESSION_PLAYBOOK.md:258`）；第 4 步写「首次部署 dev 前删除该标记（部署剧本 C-3 的第一步）」（`:262`）。
  - `deploy_gate.py` 只要标记存在，对任何环境都拒绝部署（`scripts/release/deploy_gate.py:11-12`、`:90-91`）；自检断言 dev 与 prod 都被拦（`:137-138`）。
  - 以下各处都按 dev 前关闭来写：C-3 剧本第 0 步（`docs/ops/runbooks/dev-db.md:30`）、标记文件正文（`backend/architecture/migration-baseline-open:1`）、CS-3.5（`CODING_STANDARD.md:124`）、NEXT_BATCH_PLAN W4（`phase1a/NEXT_BATCH_PLAN.md:61`、`:216`）、DEV_DEPLOY_REMAINING 0-3（`phase1a/infra/DEV_DEPLOY_REMAINING.md:13`）、调度台账的「部署阻塞」（`COORDINATOR_LEDGER.md:31`）。
- **锚在 dev 的代价**：R-1b 的 P2–P5、R-6、R-2、R-5、R-4、DA-3 / DA-10 都要改基线。按现行规则，dev 要等这一串全部收口才能部署。
- **dev 库现状**：`forcitis_one_dev` 与 `one_dev_*` 已建，但从未执行过迁移（PREDEPLOY_CHECKLIST B-11、C-3，PR #170）。生产库 C-9 也未执行。到目前为止，没有任何环境执行过基线迁移。
- **哪些东西读这个标记**（`git grep` 核实，main @ 7ad5d529）：
  - 只有 CI 与发布脚本读它：`scripts/ci/migrations_immutable.py:27、43-44、105-115`、`scripts/release/deploy_gate.py:27、46-48、90-91`、`backend/src/test/java/com/forcitis/one/NamingSurfaceTest.java:233-238`、`scripts/precheck.sh:110`；
  - 运行时代码不读标记，标记在不在都不影响应用行为。
- **安装器对基线变化有两道检查**（`scripts/release/remote_install.sh`）：
  - 是否首次安装，看的是服务器上的 `current` 链接，不看库（`:938`）；
  - 与当前版本之间，只要有迁移文件内容变了，就拒绝安装，报「a migration file changed between releases」，这一步在 Flyway 之前（`:945`）；
  - Flowable 首装凭据只在首次安装时接受（`:725`）；
  - 回到不认识某些迁移的旧版本时只打警告，理由是「迁移只扩不缩」（`:941`；`docs/ops/runbooks/release.md:148`），开放期内这个前提不成立；
  - 以上过关之后，Flyway 校验和不符还会让迁移失败（`RELEASE.md:114`、`remote_install.sh:753`）。
  
  所以，只删库不够，dev 要能接着部署，还必须把服务器上的发布状态一起重置。

## 决定

### 1. 关闭时点改为首次部署生产前

1. 基线开放标记 `backend/architecture/migration-baseline-open` 的删除时点，由「首次部署 dev 前（C-3 第一步）」改为「**首次部署生产前**」。具体要求：
   - 早于生产库 `forcitis_one_prod` 第一次执行 Flyway 迁移；
   - 早于 `deploy_gate.py prod` 第一次放行。
2. 删除方式不变（SESSION_PLAYBOOK §12.2 第 4 步后半；`migrations_immutable.py:108-112`）：
   - 单独成 PR，同一变更里不得修改、改名、删除或新增任何迁移文件；
   - 删除后不得再加回。
   - 同一 PR 中，PREDEPLOY_CHECKLIST D 节的状态全部改回 ⬜（第 3 条第 4 步）。这一改动不碰迁移文件，`migrations_immutable.py` 不拦。
3. **生产前收口顺序**（PREDEPLOY_CHECKLIST C-15 按此列项）：
   1. **所有改基线的卡合并**：R-1b 全部子 PR、DA-3 → DA-10 结构性重构卡，以及届时仍在途、改基线的其他卡。以「删除标记前」为期限的守护也在此之前合并：NEXT_BATCH_PLAN 卡 C-1 的 G-C1 / G-C2 / G-C3 / G-C6（`:378`、`:395`；第 8 节改为「首次生产部署前、C-15 之前」）。
   2. **单独 PR 删除标记**（第 2 条）。
   3. **从空库按最终基线完整安装一次（演练）**：
      - 按 dev 库重建剧本（`docs/ops/runbooks/dev-db-rebuild.md`，C-16）最后一次重置 dev 库与服务器发布状态；
      - 经发布流水线与安装器（不手工执行 SQL），把删除标记之后构建的版本装到空库上，完整走一遍安装器的首次安装路径，含 Flowable 首装；
      - C-15 记录演练版本、提交与 Flowable 版本。之后若升级 Flowable，须重做演练。
   4. **D 节出口条件在第 3 步之后的 dev 上验证**。第 2 条已把 D 节全部改回 ⬜，`deploy_gate prod` 读到的「完成」只能来自关闭之后。
   5. **核对 C-9 与最终基线的 schema 集合一致**：C-3、C-9 的 SQL 里写死了 schema 清单（`runbooks/sql/c3_dev_db.sql`、`c9_prod_db.sql`），开放期内增删 schema 只会在 dev 上暴露。
   6. C-15 标完成后，才能进入生产部署（C-9 迁移、`deploy_gate.py prod`）。生产候选版本由 `deploy_gate.py approval` 核对其构建提交中没有标记（PR #175）。基线关闭后，`migrations_immutable.py` 保证已合入的迁移不再变化，因此关闭后构建的任何版本，基线都与演练时相同。

### 2. 开放期内 dev 是可丢弃环境

1. **「已应用」的定义**：基线开放期内，迁移在 dev 上执行过**不算「已应用」**。SESSION_PLAYBOOK §12.2 中的定义改为：已在生产执行过，或在基线关闭后已在任一环境执行过。开放期内的做法不变：
   - 照旧直接改基线；
   - 每个改表 PR 照旧附「预期表结构 diff」，由 opus 核对（§12.2 第 2 步）。
2. **dev 随基线变化重建，数据不保留**：
   - **触发条件**：自上次 dev 部署以来，任一已有基线文件被修改、改名或删除（`git diff --diff-filter=MRD`）。只新增迁移文件时不重建。
   - **做法**：下一次 dev 部署前，按 `dev-db-rebuild.md`（C-16，one-ops，PR #174）执行：
     - 删库，重建库与角色，轮换口令；
     - **重置服务器发布状态**：`current` 指回初始状态，移除旧版本目录与 `previous`，让下一次部署按首次安装处理（背景中 `:938`、`:945`、`:725`）；
     - 放 Flowable 首装项，部署；
     - 按 C-5、B-12 重新授予首任超管与流程管理员。
   - **不保留的数据**：dev 上的业务数据、会话、审计、Flowable 引擎表、事件发布记录，以及单人运维模式下的授予与应急账号，一并清空，不备份、不迁移（与 ADR-0030 第 5 项「dev 数据不流入生产」一致）。
3. **唯一允许的绕过就是上面的重置，且只限开放期内的 dev。** 不得用以下方式让旧库或旧发布状态「接上」新基线：`flyway repair`、`baselineOnMigrate`、`validateOnMigrate=false`、`cleanOnValidationError`、Flyway `clean`、修改安装器的比对逻辑。应用配置也不打开 `clean`。
   - 理由：这些做法会让 dev 的表结构偏离仓库基线，dev 上的验证就不再代表生产将要装的结构。
4. **跨基线变化不回滚**：
   - 重置之后，重置前的版本一律不能 `rollback`（剧本已移除版本目录）。要退回旧代码，在 main 上回退提交后发新版本，再按需重建。
   - 同一基线之内的回滚照旧。
5. 开放期内在 dev 上发现的结构问题，直接改基线修正，随下一次重建生效，不追加迁移。

### 3. 部署守护：只拦生产，dev 告警

1. `deploy_gate.py` 的行为改为：
   - 标记存在时，`prod` 拒绝；`approval` 子命令另查发布包的构建提交，不得含标记；
   - `dev` 放行，但输出告警，指向 C-16 的重建剧本；
   - `blocks: deploy` 阻塞项照旧，dev 与 prod 都拦。
2. C-15 加入 `PROD_PREREQUISITES`，C-15 未完成时 prod 被拒。

### 4. ADR-0033 迁移方案第 5 条的其余部分与相关条款

1. **迁移方案第 5 条**：其余部分保持，锚点改为第 1 项的生产前关闭。也就是：
   - 标记删除之前，R-1b 与 DA-3 / DA-10 的结构性重构卡都须合并；
   - 标记删除之后，任何标识形态的变化都只能追加迁移，并另立 ADR。
2. **迁移方案第 1 条**：直接改基线的前提由「尚未部署任何环境」改为「基线开放期内（含 dev 已部署）」。dev 上的数据按第 2 项第 2 条随重建作废，没有需要转换的数据。
3. **第 4 项第 5 条**：DA-3、DA-10 的完成时点由「首次部署前」改为「基线开放标记删除前（生产前）」。
   - dev 首次部署可以早于 DA-3。此时 dev 跑的是 R-1b 期间的过渡结构：`login_name`、`wecom_user_id` 仍在快照里，已登记在 `ddl-naming-baseline.txt`。
   - DA-3 合并后，dev 按第 2 项第 2 条重建。
4. **回滚方案第 1、3、4 条**：原来以「首次部署」为界的表述，改以「基线开放期内 / 基线关闭后」为界：
   - 开放期内（含 dev 已部署）：按子 PR 逆序回退，重建本机库与 dev 库；
   - 来源对照分配出错：清库（含 dev）重新同步；
   - 基线关闭后：标识形态的回退只能另立 ADR，并追加迁移。
5. **ADR-0032 第 1 项第 3 条第四点**：原文「首次部署后，Flyway 迁移不得给已有持有人的角色加双人逐人级权限码；首次部署前的既有迁移列入例外清单」。其中的界限改为基线关闭：
   - 开放期内，基线文件都算「既有迁移」；
   - 例外清单在标记删除时冻结；
   - 关闭后追加的迁移受此约束。
   
   理由：开放期内 dev 每次重建都是从空库首次安装，安装时不存在「已有持有人」。

## 迁移方案

1. **没有已部署数据**：dev 库从未执行过迁移，生产库也未执行，本 ADR 生效时不需要转换任何数据。
2. **dev 首次部署**：标记仍在，`deploy_gate dev` 告警后放行。按 RELEASE.md 首次安装执行基线迁移；Flowable 首装凭据按首次安装放置。
3. **此后每次基线文件被修改、改名或删除**：下一次 dev 部署前，按 `dev-db-rebuild.md`（C-16）一起重置 dev 库与服务器发布状态。
   - 只删库不够：安装器比对两版的 `migrations.txt`，迁移文件内容变了就拒绝安装（`remote_install.sh:945`）；是否首次安装按 `current` 链接判断（`:938`）。
   - 重置后，重置前的版本不能回滚。
   - 数据不保留。
   - 剧本合并前，dev 不在基线改动之后部署。
4. **在途单据**：dev 上的单据、审批实例、事件随重建作废。没有需要过渡到生产的在途数据（ADR-0030 第 5 项）。
5. **生产前**：按第 1 项第 3 条的顺序收口。删除标记的 PR 同时把 D 节改回 ⬜；先完成演练，再在关闭后的 dev 上重新验证 D 节，C-15 完成后进入生产部署。

## 回滚方案

- **本 ADR 采纳后、dev 首次部署前**：撤回即恢复 ADR-0033 原时点，没有数据影响。具体是：
  - `deploy_gate.py` 改回对 dev 也拦；
  - C-15 移出 `PROD_PREREQUISITES`；
  - 文档改回。
- **dev 已部署、基线仍开放时要退回原时点**：先完成全部改基线的卡，再删除标记（只能前进，不能重开），然后重建 dev，此后按原规则只追加。
  - 回滚的边界是「标记删除」：标记一旦删除，`migrations_immutable.py:108-109` 拒绝再加回。
- **单次 dev 重建失败**：停在失败的那一步，不部署，报 one-coordinator。库已删除时没有回到旧数据的路径（数据不保留），重复剧本第 3–8 步。
- **生产前演练（第 1 项第 3 条第 3 步）失败**：基线已关闭，修正只能追加迁移。如果问题出在基线本身、无法用追加迁移表达，停下报用户。重开基线须另立 ADR，并同时修改 `migrations_immutable.py` 的「不得重开」规则。

## 后果

- **好处**：
  - dev 部署不再等 P5 之后的结构性重构（R-6、R-2、R-5、R-4、DA-3 / DA-10），联调、出口条件与运维演练可以并行推进；
  - 结构问题在 dev 上暴露后仍可直接改基线，生产拿到的是一份干净的基线，而不是一串补丁迁移。
- **风险一：dev 期间数据与表结构不稳定。**
  - 每次基线改动都清空 dev 库并重置发布状态。依赖 dev 数据的验证每次重建后都要重做，包括组织同步、老系统数据回放、审批实例、首任超管与流程管理员的授予。
  - 每次重建 dev 不可用约 30 分钟（剧本估计）。
  - 重建之后不能回滚到重置前的版本。
  - dev 首次部署时跑的可能是过渡结构（第 4 项第 3 条）。
- **风险二：dev 上发现的迁移问题，要到生产前才被「不可变」守护锁住。**
  - 开放期内，`migrations_immutable.py` 放行任何基线改动。一次错误的基线修改只有「预期表结构 diff」与 opus 核对把关，dev 重建会把它当作新的正确结构接受。
  - dev 上已经验证过的结构，可能被后来的基线改动悄悄改变。
  - 缓解措施：删除标记的 PR 把 D 节改回 ⬜，强制在关闭后的 dev 上重新验证；`approval` 只放行关闭后构建的版本。
- **风险三：首次生产部署前，必须从空库按最终基线完整安装一次。**
  - 开放期内 dev 每次都是首次安装，看起来已经演练过很多次，但只有最后一次基线改动之后的安装才算数。如果跳过，生产就是第一个执行最终基线的环境。
  - 由 C-15 与 `PROD_PREREQUISITES` 强制。
  - 写死在 SQL 里的 schema 清单（C-3 / C-9）在这一步核对。
- **风险四**：关闭后才发现基线本身有问题时，只能追加迁移；追加迁移无法表达的，须另立 ADR 重开基线（回滚方案第 4 条）。
- **风险五：在途分支与 dev 部署版本错配。** 开放期内，并行会话的分支可能各自改基线。dev 只部署 main 上构建的版本，重建的触发以「上次 dev 部署的提交」与本次提交的差异为准（C-16）。
- **成本**：
  - dev 重建的运维工作量随改基线的 PR 数量增加；
  - D 节出口条件至少验证两次：开放期内一次（可选），关闭后一次（必需）。

## 备选方案（未采用）

1. **维持原时点（首次部署 dev 前关闭）**：dev 部署被结构性重构串行卡住；用户已决定解耦。
2. **dev 前关闭，结构重构改为追加迁移**：R-1b 改全部 schema 的主键与引用列。追加迁移会把一长串重构历史带进生产首装，而且每一步都要写能在有数据的库上执行的转换；生产首装前没有任何数据，这些成本没有收益。
3. **dev 上用 `flyway repair` / `baselineOnMigrate` / `cleanOnValidationError`，或放宽安装器的迁移比对，自动接上新基线**：dev 的结构与仓库基线不再一致，dev 上的验证失去代表性；安装器放宽会同时削弱生产的只追加守护；`clean` 一类开关一旦进入共用配置，有误伤生产的风险。
4. **分设 dev 与生产两个标记（dev 先关、生产后关）**：多一套标记与守护状态，换来的只是 dev 不必重建；而 dev 数据本来就不保留（ADR-0030 第 5 项），不值得。
5. **开放期内 dev 不跑 Flyway，手工建表**：脱离了发布安装器的路径，dev 上的部署演练就失去了意义。
6. **人工比对 `migrations.txt` SHA256，把生产候选钉在演练版本上**：被「构建提交不含标记」的机器检查加上关闭后的不可变守护取代，人工步骤删去。
