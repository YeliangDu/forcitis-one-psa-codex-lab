- **状态**：已采纳（用户 2026-10-15：「批准并接受例外 (Recommended)」；U-2 / U-3「两项都保留 (Recommended)」；U-4 / U-5「都不做 (Recommended)」；U-6「不放宽 (Recommended)」）（决定 2 放宽清单增第 5 项、决定 3 锁定日确认一项、守护第 8 条四值改五值已被 ADR-0072 取代）
- **日期**：2026-10-15
- **取代**：ADR-0026 第 5 项第 5 条、ADR-0026 回滚方案第 1 条、ADR-0027 第 1 项第 1 条、ADR-0027 第 1 项第 7 条、ADR-0027 第 1 项第 8 条、ADR-0027 第 2 项第 4 条、ADR-0027 第 3 项第 1 条、ADR-0028 第 1 条、ADR-0028 第 4 条

## 背景

- 用户 2026-10-15 通过 one-coordinator 转达：「dev 白名单把我也加上，我们开发过程中所有操作只有我一个人，不要给我第二个人，这些安全措施等到生产部署前再真正落实」。one-ops 据此调整 A-3：dev 阶段超级管理员 1 名、应急账号 1 个，都是用户本人；第二名超管、第二个应急账号与 C-5「双人在场」推迟到生产部署前。C-5 剧本写明，本例外获批并实现之前，不以单人绕过检查（不以同一人同时充当 `--operator` 与 `--witness`）。
- dev 上只有一个人时，以下规则会卡住：
  - **运维命令双人在场**（ADR-0027 第 1 项第 1 条；第 7 条恢复路径；ADR-0028 第 4 条「将为 0 时只能走运维命令」；ADR-0026 第 5 项第 5 条「只有 1 名持有人时经运维命令、第二人在场」）。代码要求操作人与见证人是两个不同的名字（`OperationAttestation.java:14-26`）。这两个名字只是命令行上自报的文本，系统并不核实。
  - **至少 2 个可用应急账号**，每日核对（ADR-0027 第 1 项第 1、8 条；`ReconcileEmergencyAdmins.java:26、59-60`；登记提示 `OperationsCommands.java:88-92`）。
  - **同步暂停的超管下限 2**（ADR-0028 第 1 条）。实现上，运行只在离职名单含 `super_admin` 或安全审计员持有人时进入 HELD（`ApplySourceSnapshot.java:85`）；「少于 2 名」只写进暂停原因文本（`AdministratorSeparationReview.java:24、47-49`），本身不触发暂停。
  - **编号模板四眼**（ADR-0027 第 2 项第 4 条）：用户同时是组织数据管理员（起草人）和业务管理员（确认人），界面上改过的模板自己不能确认。
- **应用内的两人确认在数据库层也有约束**，不能用配置放宽：
  - 授权申请：`ck_authorization_requests_two_people`，要求确认人既不是发起人也不是被授予人（`V20261015000600__platform_identity_create_authorization_requests.sql:23`）；
  - 编号模板：`ck_numbering_rule_versions_confirmer_is_not_author`（约束允许 `author_id` 为空）与 `ck_numbering_rule_versions_two_different_confirmers`（`V20261015000300__platform_numbering_create_rule_versions.sql:20-23`）；
  - 守护：`NumberingRuleFourEyesIT.java:303-304` 断言直接改库也被约束拒绝。

  因此本 ADR 不放宽这些约束（若要放宽，见待用户决定 U-4）。dev 的单人路径改走运维命令：敏感授予用 `grant-role`；编号模板由运维命令起草出没有作者的版本，再由用户在界面确认，这条路径数据库约束本来就允许。
- **与已采纳原则的关系**：ADR-0026 回滚方案明确「**不提供**运行时关闭范围或恢复管理员全权的配置开关，避免成为后门」（`adr/src/ADR-0026.md:186`）。本 ADR 引入的是一个降低安全控制的配置开关，因此是该原则的**一个例外**：开关不碰数据范围，不恢复管理员全权，只在 dev 生效，运行期不能切换。是否接受，作为待用户决定 U-1。
- **依赖**：ADR-0028、SECURITY_INVARIANTS I-11 至 I-13 与上述代码都在 #72 整合分支（27ac707）。#72 合并入 main 后，本 ADR 才能采纳。
- dev 与生产同构部署（`ProductionConfigSanityTest.java:92-94`）。安装器要求服务器 profile 与目标环境一致（`remote_install.sh:407-409`），要求 `one.env` 含模板的每个键（`remote_install.sh:230-232`），并逐字节比对 systemd 单元文件（`remote_install.sh:223`）。

## 决定

取代范围：上列各条只在**按第 1 项开启了单人运维模式的 dev 环境**中收窄。生产中各条全文照旧有效，模式关闭时也照旧有效。各条其余内容不变。各条的具体收窄：

- ADR-0026 第 5 项第 5 条：只收窄「第二人在场确认」；
- ADR-0026 回滚方案第 1 条：只收窄「不提供配置开关」一句，增加本例外；
- ADR-0027 第 1 项第 1 条：只收窄「至少 2 个」「不同持有人」与「双人在场」；
- ADR-0027 第 1 项第 7 条：放行部分已由 ADR-0028 取代，这里只取代剩余部分中恢复路径的「双人在场」；
- ADR-0027 第 1 项第 8 条：下限；
- ADR-0027 第 2 项第 4 条：只收窄「每个版本记录作者」——dev 上允许经运维命令起草没有作者的版本；「确认人不能是作者」与财务确认不变；
- ADR-0027 第 3 项第 1 条：dev 上安全审计员经运维命令授予，取代「按敏感权限双人确认另行授予」；
- ADR-0028 第 1 条：下限 2 改为 1；
- ADR-0028 第 4 条：只收窄运维命令的「双人在场」。

ADR-0026 迁移方案第 2 条（`adr/src/ADR-0026.md:180`）与 ADR-0027 迁移方案第 1 条（`adr/src/ADR-0027.md:101`）中的「上线」**只指生产上线**，不受本 ADR 影响。

### 1. 单人运维模式的开关

1. **配置键**：`forcitis.platform.identity.single-operator-mode`（G46 要求 `forcitis.{子域}.{BC}.` 前缀；暂名 `forcitis.security.single-operator-dev` 不合规），环境变量写法为 `FORCITIS_PLATFORM_IDENTITY_SINGLE_OPERATOR_MODE`。提议术语「单人运维模式」（`single_operator_mode`，SingleOperatorMode，bc `platform.identity`）在实现 PR 中登记到 `backend/glossary/proposed/`。
2. **取值与判定**：
   - 只认字面量 `true` 与 `false`，其余取值（包括空串）启动失败。
   - 由 `ApplicationEnvironmentPreparedEvent` 监听器检查（参照 `MigrateOnlyListener.java:36-40`）：以字符串从 `ConfigurationPropertySources` 判断键是否存在、取原值，覆盖环境变量、命令行参数、`SPRING_APPLICATION_JSON` 与宽松写法。不依赖 Boolean 宽松绑定，避免把空串当作未设置。
3. **白名单，不是黑名单**：
   - 激活 profile 含 `prod` 时，键存在即启动失败（任何取值）。
   - 值为 `true` 时，激活 profile 必须含 `dev` 且不含 `prod`。其他组合一律启动失败，包括只有 `identity-operations`、没有任何 profile、`dev,prod`。
   - `identity-operations` profile 与 `migrate` 一样，必须同时带 `dev` 或 `prod`（参照 `MigrateOnlyListener.java:54-55`）。运维手册改为在 `one.env` 的环境 profile 之上用 `--spring.profiles.include=identity-operations` 运行，不再用 `--spring.profiles.active`（`application-identity-operations.properties:4`）。
4. **独立于 `one.env` 的数据库判据（白名单）**：值为 `true` 时，连库检查以下两项，任一不满足即启动失败：
   - `current_database()` 是 `forcitis_one_dev`；
   - 会话用户以 `one_dev_` 开头。

   **时点**：检查在上下文刷新的单例初始化阶段完成。它先于任何 `ApplicationRunner`（包括运维命令入口 `OperationsCommandRunner.java:21-22`），先于 Web 服务器开始接受请求（服务器到刷新末尾才开始监听），也先于调度器启动。因此检查失败时，进程什么都没做就退出。

   **取舍**：用白名单而不是「不是生产库」的黑名单，是因为改名的生产库、临时实例、恢复演练库都会漏过黑名单。代价是：开启模式的测试必须把 Testcontainers 的库建成 `forcitis_one_dev`、角色建成 `one_dev_*`；A-7 以后若在开发机或临时实例上开发，也要沿用这两个名字。
5. **只在启动时读取**，绑定为 `platform.identity` 内的包内私有设置类型，不提供接口，不接受刷新（actuator 只暴露 `health`，`platform_identity.properties:25`）。改值必须重启。`platform.numbering` 的运维起草命令（第 2 项第 4 行）只经 `platform.identity` api 的只读查询得知模式，不自己读这个键。
6. **仓库不发布这个键**：`application*.properties`、`config/*.properties`、yaml 都不得出现。dev 只在 ECS 的 `/etc/forcitis-one/one.env` 中设置，不写进 `one.env.template`。
7. **可见性**：
   - 模式开启时，每次启动写一行固定文本的 WARN 日志，含激活 profile、数据库名与「ADR-0030」；
   - 写审计 `platform.identity.single-operator-mode.enabled`（actor 为空）；
   - 每次放宽都另写一条标注审计（第 2 项）。

### 4. 不放宽的规则

1. **应用内两人确认**：敏感授予与敏感角色定义变更（ADR-0026 第 4 项第 1 条第二点、第 6 项第 2 条；ADR-0027 第 3 项第 2 条；I-12）。数据库约束与断言都不变。
2. **编号四眼与财务确认**：确认人不能是作者；财务确认人不能是业务确认人（U-3）。
3. **放行人须留任且不在离职名单中**（ADR-0028 第 4 条；`AdministratorSeparationReview.java:46`），以及放行后超管将为 0 时界面拒绝（U-2）。
4. **审计必写**：标注只增不减，不能关闭。
5. **不能改自己的角色**，也不能改自己持有角色的定义（I-12 前半句；`ReplaceAccountRoles.java:64-68`）。敏感权限只授给具体的人（F-1）。
6. **管理模式与应急登录**（I-11）全部不变。
7. 安全不变量 I-1 至 I-10、I-13；缩水保护；流程管理员启动检查；密钥规则；企业微信只用 `touser` 投递与 dev 收件人白名单——全部不变。

### 5. dev 数据不流入生产；记录处置

1. **dev 的数据不会进入生产**，依据如下：
   - 生产使用独立的 `forcitis_one_prod` 与 `one_prod_*` 角色（C-9；ADR-0025 第 2 条）；
   - dev 库在生产切换前停用（A-7 决定 A）；
   - Flyway 只带结构与角色种子；
   - 组织与老数据直接迁入生产库，没有从 dev 导出到生产的路径。
2. 单人模式期间的授予、模板版本、应急账号与审计**不迁移、不复核**，随 dev 库按 A-7 停用一并作废。dev 中关闭模式后，已有记录同样不复核。
3. dev 的应急凭据与 TOTP 密钥不带入生产。同一台 ECS 改作生产时，重新生成 `EMERGENCY_TOTP_ENCRYPTION_KEY`。
4. **D-5 / B-8**：
   - dev 上可以按第 3 项第 1 行完成格式确认与新旧对照；
   - 生产库中的四眼确认与凭证号财务确认单列为 C-12。

### 6. 生产部署前与开放业务前

1. **硬防线只有进程内两项**，即第 1 项第 3 条的 profile 白名单与第 4 条的数据库判据。它们覆盖所有进程，包括常驻服务、运维命令与迁移。进程外的两项只是纵深防御与漂移发现，不算硬防线：
   - **systemd 预检（纵深防御）**：在 `forcitis-one.service` 中加一条 `ExecStartPre`，服务器 profile 为 `prod` 且 `one.env` 匹配 `(?i)single[-_.]?operator` 时拒绝启动。它能被绕过：drop-in 写一个空的 `ExecStartPre=`，或者用 `systemctl set-environment` 注入变量，都能跳过它。
   - **安装器（漂移发现）**：`remote_install.sh install-pending prod` 用同一正则检查 `one.env`。drop-in 改用 `systemctl show forcitis-one -p DropInPaths` 检查，覆盖 `/etc`、`/run` 与类型级 drop-in，prod 上只要有任何 drop-in 即拒绝安装。它只在安装时运行。
2. **PREDEPLOY_CHECKLIST C 节新增两项**：
   - **C-11（生产前，部署前完成）**：关闭单人运维模式。内容：
     - 生产 `one.env` 无该键、无 drop-in 目录；
     - ECS 复用时重新生成 `EMERGENCY_TOTP_ENCRYPTION_KEY`；
     - 第二名超管与见证人确定。

     C-11 加入 `deploy_gate.py` 的 `PROD_PREREQUISITES`（`deploy_gate.py:27`），自检（`:143-144`）同步，未完成时 prod 部署被拒（`:93-96`）。
   - **C-12（生产切换后、开放业务前）**：启用第二名超管与第二个应急账号。内容：
     - 双人在场，为两名不同的人授予 `super_admin`，登记 2 个分别绑定的应急账号；
     - 首次每日核对通过；
     - 编号模板四眼确认、凭证号财务确认；
     - 生产审计中 `*.single-operator-mode.*` 为 0 行。

     C-12 需要应用已装在生产上，因此不能作为部署前提，是开放业务前的检查项。有两项现成兜底：
     - 生产关闭模式后，可用应急账号少于 2 个时每日核对告警（`ReconcileEmergencyAdmins.java:59-60`）；
     - 未确认的编号模板不发号（ADR-0027 第 2 项第 4 条）。
3. A-3 的时点改为「生产前」。

## 回滚方案

- **关闭模式（dev，配置级）**：删除这个键并重启。之后运维命令又要求见证人，编号起草命令被拒绝，每日核对在可用数少于 2 时告警。已有记录不复核。
- **撤销实现（代码级）**：回退实现提交，恢复严格行为。dev `one.env` 中残留的键应删除。已起草的无作者版本保留（库层允许，dev 库随 A-7 作废）。标注审计保留。`ExecStartPre` 随单元文件一起回退。
- **如果生产被误开启**（需要同时绕过应用检查与数据库判据）：
  - 停服，删除这个键；
  - 按标注审计逐条处理：收回授予，作废无作者版本并由不同的人重新起草、确认，重新登记应急账号；
  - 写复盘。
- **边界**：审计与标注不回滚。

## 后果

- dev 上用户一个人可以完成：C-5、各角色授予与收回、编号模板确认（D-5 / B-8 的 dev 部分）、作为留任超管的同步放行、审计查询与导出。每次放宽都按动作可查。
- dev 无单人路径的有五项：凭证号财务确认（U-3）、含敏感权限的角色定义变更（U-5）、用户本人被标为离职时的同步放行（U-2）、审批防自审，以及审批转交 / 改派不能交给本人或发起人（后两项同属 U-6）。
- 应用内的两人确认在任何环境都不变，数据库约束继续是最后一道防线。
- 生产行为与 ADR-0026、0027、0028 一致。编号运维起草命令在生产不可用。生产上误开启必须同时绕过进程内的 profile 白名单与数据库白名单；systemd 预检与安装器只是纵深防御与漂移发现。
- 两人控制的真实运行推迟到生产（C-12）。
- 本例外打破 ADR-0026「不设配置开关」的原则（U-1），以封闭清单、白名单判定与守护限住。

## 备选方案（未采用）

- **在 dev 建一个真实的第二账号，由用户兼持**：一人两个身份，审计失真；违背用户「不要给我第二个人」。
- **完全不放宽**：C-5 与 B-8 在 dev 无法执行，每日核对天天告警。
- **用测试替身绕过**：dev 与生产同构部署；替身放进主代码就是认证旁路，I-4 守护禁止。
- **应用内两人确认也改为一人可完成**（评审前的初稿）：与库层约束和断言冲突，须放宽所有环境（U-4）。

- **以 dev profile 隐式放宽，不设开关**：不显式，看不到，以后有第二人也无法恢复两人控制。
