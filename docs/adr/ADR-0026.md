## 背景

- ADR-0009 第 4 条已定：功能权限用类型化 `Permission`（RBAC）；数据范围按「法人 × 部门 × 项目角色」，由 `AccessScope` **显式传入仓储**，不用隐式 SQL 改写拦截器；权限变更即时生效。规则评审结论：各角色并集、只算启用角色、「本人及下属」只算直接下属（RULE-349）；空范围返回零行（RULE-351）；不用注解开启的隐式改写，范围异常即拒绝（RULE-350）；读写同一口径（RULE-352）；新角色默认 SELF（RULE-345）；不隐式补授角色（RULE-344）；批量只处理本人待办，代理须显式（RULE-270）。
- main 上已落地：15 个权限码（`<子域>.<bc>:<资源>:<动作>`）；角色分 SYSTEM / CUSTOM，`super_admin` 只能由迁移建立（但迁移没有把它授给任何人）；`employee` 为默认最小角色，建档时显式授予一次；默认拒绝与公开端点白名单快照；授予上限 `PrivilegeCeiling`（管理员不受上限）；签名票据不能进入管理员；角色变更即时吊销会话；权限每次请求按缓存重算（缓存 ≤ 60 秒）；审批任务操作只认处理人（`TaskGuard`，I-7）。
- 只有模型、没有落地的部分（代码盘点，sonnet，2026-10-14）：
  - `AccessScopeKind` 六种、`AccessTarget`、`AccessGrant`、`AccessScope`、`AccessScopeCalculator` 在 `platform.identity` 之外**没有调用方**；`AccessGrant` 引用 `organization.workforce.api.OrgUnitId`；`roles.access_scope` 只存类型，没有授予明细表；`PendingIdentityRulesTest` 中 RULE-350/352、RULE-353 为 `@Disabled`。
  - **员工、部门都没有法人归属**：`SessionCurrentUser` 把法人写死为 `1`。
  - 组织树是邻接表；没有「直接下属」查询。
  - `organization.workforce`、`platform.audit` 不能依赖 `platform.identity`。
  - `super_admin` 当前隐含全部权限（`AccessProfile.of`），角色判断中恒为真；权限缓存按 userId 存，不区分会话。
  - 应急登录记为 `platform.identity.login.succeeded`（`method=EMERGENCY`），但没有告警；应急账号没有生产环境的登记途径。
  - `@PreAuthorize` 层的拒绝不记审计；没有敏感字段分级或脱敏机制。
- 1a 现有四类查询都不按数据范围过滤：审计、组织浏览（`ListOrgUnits` 全量读出后在内存过滤）、同步记录、合并待办（按处理人过滤，不是数据范围）。
- 职责分离证据（U8C_CAPABILITY_MAP §2.2，近 12 个月凭证）：制单 = 审核 0 张；**制单 = 记账 619 张**；审核 = 记账 998 张（约 59%）。
- GUIDING_PRINCIPLES §6：工资、日薪、个人信息为敏感级，必须脱敏并按范围授权。
- 用户 2026-10-14 问「1a 还有哪些设计需要现在考虑？权限系统？」，选「写授权模型 ADR，1a 实现数据权限 (Recommended)」。
- 本 ADR 经 architecture-critic（opus）对抗性评审后修订，评审意见与处理见「证据」。

## 决定

本 ADR 部分取代 ADR-0009 第 4 条：补充数据范围的落地机制、按权限计算范围、法人限定与审批参与访问；ADR-0009 第 4 条中「类型化 `Permission`」「法人 × 部门 × 项目角色」「显式传入仓储、不用隐式改写」「变更即时生效」仍然成立，ADR-0009 其余条款不变。

### 1. 数据范围的落地机制：仓储层显式谓词，注册表 + 守护保证不遗漏

**决定**：仓储方法显式接收 `AccessScope`，由纯函数渲染器生成 WHERE 片段；**不启用** PostgreSQL 行级安全（RLS）。

1. **类型下沉到内核**：`AccessScope`、`AccessGrant`、`AccessTarget`、`AccessScopeKind`，连同它们引用的 `OrgUnitId`、`ProjectRole`，从 identity / workforce 的 api 移到 `kernel`。内核另增接口 `CurrentAccess`，由 `platform.identity` 实现；其他模块经它取得范围，不依赖 identity。
2. **按权限计算范围**：`CurrentAccess.accessScope(Permission)` 只合并**授予该权限的启用角色**的范围（仍是 RULE-349 的并集），避免「角色甲给权限 X、范围本人，角色乙给权限 Y、范围全部」时 X 也看到全部。
3. **构造与展开在 identity**：identity 构造 `AccessScope` 时，把部门子树、直接下属、部门的法人全部展开成具体 id 集合（来自组织快照，随权限缓存 ≤ 60 秒刷新）。内核中的 `ScopePredicate.render(scope, ScopeColumns, Mode)` 是纯函数，不查库。只有 identity 能构造非空范围；`AccessScope.everything()` 与 `AccessScope.system(reason)` 也只限 identity 与带 `@SystemTask` 的类调用（ArchUnit）。
4. **渲染规则**：`none()` → `false`（零行，RULE-351）；不受限 → `true`；每条授予渲染为该授予的部门 id 集合（与法人限定，见第 2 项）的条件，各授予之间 OR；本人类渲染为 `owner_id = ANY(:owners)`。范围计算出现异常即拒绝（RULE-350）。`Mode` 区分 READ 与 WRITE：以后加入的审批参与访问只进入 READ。
5. **数据访问注册表**（`architecture/data-access-registry.yaml`，CODEOWNERS 评审）覆盖**所有 schema**（含 Flowable 的 `ACT_*`、事件发布表、会话表），每张表登记为：
   - `SCOPED`：按数据范围过滤；登记范围列，以及 `owner_id` 在该表中的含义（制单人、申请人或负责人）；范围列可以是**派生列**（例如组织表的法人经「部门 → 法人」对照 join 得到），注册表写明派生方式；
   - `ASSIGNMENT`：按处理关系过滤（待办）；
   - `GLOBAL`：只靠功能权限，不分范围；必须写理由；
   - `REFERENCE`：参照数据；
   - `EXCLUDED`：框架内部表（会话、事件发布、Flowable 运行表），写理由，只允许框架代码访问。
6. **只有登记过的持久化类能查库**：ArchUnit 规定只有带 `@DataAccess(tables = {...}, kind)` 的 `..infrastructure..` 类能依赖 `JdbcClient`、`DataSource`、Flowable 的查询 API；`@DataAccess` 列出 SQL 触及的**全部**表（含 join），且每张都要在注册表中；触及任一 `SCOPED` 表的类，其每个 public 方法都要有 `AccessScope` 参数。
7. **读写同一口径（RULE-352）**：`SCOPED` 表的更新、删除先按范围（WRITE）加载再写。按 id 直接读取时，行不在范围内返回 **404**（不暴露是否存在）并写审计。
8. **读模型与投影**：投影表复制源事实的范围列，按投影自身的列判断，不回查源表。
9. **归属口径**：业务事实的**部门**取事实发生时的部门（与核算一致，D-3）；**本人类**范围按当前的人与当前汇报线展开，即「随人走」——换领导后，新领导看得到下属的历史，原领导不再看得到。两者是不同维度，并不矛盾，在此写明。
10. **性能**：组织约 1,300 人、367 个部门，展开后的 id 数组在千级以内，`= ANY(:ids)` 走 btree；`SCOPED` 表对部门列、法人列与 `owner_id` 建索引（注册表测试检查）；count、聚合与搜索同样带范围（契约测试覆盖）。

**1a 现有查询的接入**：

| 查询 | 登记 | 做法 |
|---|---|---|
| 审计（`audit_entries`） | `GLOBAL` | 理由：安全审计数据，按操作人部门开放会让部门负责人看到下属的登录地址；只授予「安全审计员」系统角色（D-11），不按范围过滤，不补列 |
| 通讯录卡片（姓名、部门、企业微信 ID，L2） | `GLOBAL` | 全体已登录用户可见，用于选人和显示待办中的姓名（D-12） |
| 部门浏览（`org_units`） | `SCOPED`（派生法人列） | 部门按范围可见，同时返回可见部门的祖先作导航（只含名称，RULE-353）；`ListOrgUnits` 改为 SQL 过滤，不再全量读出 |
| 人员详情（`employees`、`assignments` 中卡片以外的字段） | `SCOPED` | 按所在部门与本人类范围判断 |
| 同步记录（`sync_runs`、`sync_diffs`） | `GLOBAL` | 理由：平台运维数据，只授运维角色 |
| 合并待办 | `ASSIGNMENT` | 保持按处理人 / 候选人过滤 |

`legal_entities`、`numbering_*` 为 `REFERENCE`；`user_accounts`、`roles`、`account_roles` 为 `GLOBAL`。

### 2. 法人维度

**决定**：在部门范围之上增加**可选**的法人限定；默认不限定，保持 RULE-349「任一 ALL 即不受限」的结论不变。

1. 角色的范围增加 `legal_entity_scope`：`ANY`（默认，不限定）/ `OWN`（本人所属法人）/ `LISTED`（列出的法人）。
2. 一条授予内部，部门范围与法人限定取交集；多条授予之间取并集。`ALL + ANY` 即不受限，与老系统一致；`ALL + LISTED` 是新增能力，供只看某几个法人的角色（如某法人的财务）使用。
3. 法人限定**只作用于登记了法人列的表**（事实自带的签约法人、核算法人等，由各 BC 定义）；没有法人列的表只看部门维度。因此「本部门」不会因为单据以其他法人签约而看不到。
4. 本人类范围不受法人限定（D-2）。
5. **员工的法人归属**（D-1，与流程梳理 D-1a-27「员工 → 法人生效区间表」为同一模型）：
   - 默认取「部门 → 法人」对照：子部门继承，可在子树上覆盖；
   - 个别员工可单独指定法人，单独指定优先于部门对照；
   - 两者都带生效区间（生效日、失效日），由组织数据管理员维护，区间不重叠；
   - **按日期取值**：业务事实按事实发生日解析法人；当前会话的 `CurrentUser.legalEntityId()` 按当天解析；取代 `SessionCurrentUser` 中写死的 `1`；
   - 组织表不冗余存法人列，靠按日期 join 派生，所以改对照不涉及业务数据；
   - 某日解析不到法人时，`OWN` 法人限定对该员工解析为空集（fail-closed），默认的 `ANY` 不受影响；
   - 来源可替换：以后自建 HRM 若有任职法人，改为取 HRM。
6. **1a 只交付**「部门 → 法人」与「员工 → 法人」两张生效区间表及按日期解析，以及 `CurrentUser.legalEntityId()` 的真实取值（编号已在用）；`legal_entity_scope` 随第一个带法人列的业务事实（1b 报价）交付。

### 3. 因审批获得的访问（1b 交付）

**决定**：审批参与人对该单据有**只读**访问，与数据范围并列（READ 模式下 OR），不扩大到相关单据。随第一个接入审批的业务单据（1b）交付，1a 不做。

1. **谁**：发起人；当前处理人与候选组成员；已办理者；知会对象。
2. **范围**：该单据、附件和审批历史；不含相关单据，不含另行授权的敏感字段；**不可写**。
3. **期限**（D-4）：未办理的候选人在任务关闭时收回；已办理者、发起人、知会对象保留只读，直到账号停用；管理员可按单据收回（写审计）。
4. **机制**：approval 发布参与关系事件（含业务键与人员列表）；业务模块维护 `document_participants`，以 `(task_id, user_id)` 为键、按状态幂等写入（乱序、重复投递都得到同一结果）；每天与引擎对账一次，差异告警并以引擎为准修正。投递积压超过阈值时告警（收回延迟属于已知风险，见后果）。
5. **防止旁路**：L3 及以上字段不得进入审批表单字段（`formFields`）、企业微信卡片和事件（守护测试）。
6. **审计**：参与关系由审批事件留痕；经参与关系读取含 L3 字段的单据时记 `platform.identity.access.via-approval`。

### 4. 职责分离

**决定**：授予时的冲突规则写成**代码**（枚举 + 测试），属于安全不变量，不做成可配置数据；操作时的规则由拥有对象的 BC 在领域内实现。

1. **授予时规则**（`platform.identity` 中的 `GrantConflict` 枚举，每条有测试）：
   - 不能修改自己的角色集合，**也不能修改自己持有的任何角色的定义**（I-12，1a）；
   - 敏感权限（见第 6 项）的授予不享受管理员豁免，走双人确认（1a）；
   - 以后新增的冲突组合（如「凭证制单」与「凭证记账」同时授予同一人）以新枚举值加入，命中时拒绝，除非有例外记录（理由、批准人、到期日）。
2. **操作时规则**由对应 BC 的 ADR 定义并实现：凭证制单 ≠ 审核、制单 ≠ 记账、审核 = 记账是否允许（现状 0 / 619 / 998 张）交总账 ADR 与财务决定（原 D-8 移交）；审批的防自审已实现（RULE-307）。
3. **违规报告**：列出持有冲突组合的账号与例外到期情况，随第一条组合规则交付（1b 及以后）。

### 5. super_admin 边界与应急管理员

**决定**：平台管理与业务操作在**会话**层面分开——管理员需要显式进入「管理模式」，管理模式只有平台权限（D-10）。

1. `super_admin` 角色的含义改为「可以进入管理模式」。普通会话里，持有人只有自己的业务角色；`AccessProfile` 不再把全部权限赋给它，`hasAnyRole` 不再恒为真。
2. **进入管理模式**：已登录用户在界面上选择进入，需再次验证（企业微信二次确认或 TOTP），得到的权限是显式列出的平台权限（角色定义、账号授权、编号规则、法人对照、同步放行），**不含任何业务权限、不含敏感读、不含审计查看**；有效期 1 小时，不续期；进入与退出各记一条审计并告警。权限缓存按 `(userId, 会话模式)` 计算。
3. 因为管理员身份不再跟着账号走，审批人解析**不需要**排除 `super_admin` 持有人；兼任管理员的部门负责人照常审批。管理模式会话没有任何业务权限，不能办理审批。
4. 管理模式下每个写请求，以及对授权数据的读请求，记 `platform.identity.privileged.request`。
5. **首任管理员与持有人数**：首任 `super_admin` 通过一条运维命令授予（命令记审计，不把生产 userId 写进 Flyway）；持有人至少 2 名之后启用双人确认；只有 1 名时，授予或收回敏感权限必须经运维命令，由第二人在场确认并记审计。
6. **应急管理员（break-glass）**：用于企业微信或致远不可用时。只有 `super_admin` 持有人可以登记为应急账号（运维命令，双人在场，写审计）；应急登录直接进入管理模式（第 2 条的权限集合，1 小时），并触发告警。现有 `LoginAsEmergencyAdmin` 的员工档案校验保留。

### 6. 授权治理

1. **权限拆分**：`platform.identity:role:update` 只管角色定义；账号授权改用新权限 `platform.identity:account-role:update`；账号启用 / 停用暂沿用前者。
2. **敏感权限**：`account-role:update`、进入管理模式（即 `super_admin`）、所有敏感读权限（第 7 项）、以后的过账 / 记账类权限。授予或收回含敏感权限的角色（或修改角色定义使其含有敏感权限）时，先建授权申请，由另一名持有 `account-role:update` 的人确认后生效；非敏感角色即时生效并写审计（D-5）。1a 用一张申请表实现，以后改走审批引擎。
3. **复核**：每季度生成「人员 × 角色 × 范围」报表，由**内控 / 财务**负责复核（D-13），结果写审计，不自动收回；超期未复核的提醒内控 / 财务负责人，不升级给管理员。
4. **调动与离职**：离职即时吊销会话并收回角色（RULE-363，已实现）；调动时相对范围自动随新部门变化；含自定义部门或 `LISTED` 法人的授权标记待复核并通知新部门负责人。
5. **审计补齐**：`@PreAuthorize` 拒绝与范围拒绝记 `platform.identity.access.denied`（按用户与资源聚合限流）；查看审计本身也记审计。
6. **生效时限**：ADR-0009 所说的「即时生效」指：会话吊销即时；权限与范围在缓存过期后生效，最长 60 秒。

### 7. 敏感字段

**决定**：列级分级登记在 DDL 注释中（格式与级别以命名标准为准，psa-repo-fragments 正在补），接口出参按权限给明文或掩码，守护测试保证不遗漏。

1. 级别：L1 公开、L2 内部、L3 敏感（工资、日薪、费率、个人联系方式与证件、银行信息）、L4 机密（凭据，禁止出参）。
2. 每个 L3 列对应读权限 `<子域>.<bc>:<资源>-sensitive:read`；无权限时：文本字段给保留格式的掩码；**数值字段给 `null` 并附 `<字段>Masked: true`**，不改变字段类型。
3. 实现：出参 DTO 字段用 `@SourceColumn("schema.table.column")` 显式声明来源列；来自 L3 列的字段由统一组件处理（Jackson 序列化与 Excel 导出共用同一个掩码组件）；带敏感字段的 record 覆写 `toString`；L3 / L4 不进日志、事件、审计 detail、企业微信卡片。
4. 1a 的邮箱、性别、企业微信 ID 定为 L2（D-6），机制随第一个 L3 字段（Phase 2 费率、日薪）落地。

### 8. 老角色迁移

**决定**：一次性只读导出 + 对照表 + 用户确认，按模块切换时迁入；没有对应的不授予；差异必须逐项可见。

1. **范围类型对照**：`ALL` → `ALL`；`DEPT_CUSTOM` → `CUSTOM_ORG_UNITS`；`DEPT_ONLY` → `OWN_ORG_UNIT`；`DEPT_AND_CHILD` → `OWN_ORG_UNIT_SUBTREE`；`SELF` → `SELF`；`SELF_AND_SUBORDINATES` → `SELF_AND_DIRECT_REPORTS`。法人限定一律 `ANY`（与老系统一致，不悄悄收窄）。
2. **老系统特殊语义**：老系统**不论范围类型**都会并入角色的 `data_scope_dept_ids`（IDENTITY_ORG_RULES RULE-349）。凡是「非自定义类型但带部门 id」的角色，在差异报告中单列，由用户逐个决定拆成「原类型 + 自定义部门」两条授予还是舍弃。
3. **过滤口径差异**：老系统按创建人**当前**所在部门过滤（RULE-350），新系统按事实上的部门列过滤。迁入前按人抽样，对比新旧可见范围的行数，差异交用户确认。
4. 自定义部门按 A8 部门编码对到新组织快照；对不上的不授予并列入差异清单。
5. 功能权限：老菜单权限串 → 新 `Permission` 对照表；对不上的不授予。
6. `super_admin` 持有人不自动迁入；按第 5 项另行授予。
7. **时机**：各模块的权限在该模块切换时迁入；每次迁入带批次号（`account_roles.migration_batch_id`），并保存迁入前的授予快照（`account_role_snapshots`），供回滚。
8. 1a 切换前执行一次只读导出（D-9）。

### 1a 交付范围

- **1a 做**：类型下沉、渲染器、`CurrentAccess`（按权限计算范围）、注册表与守护测试；部门浏览与人员详情接入范围；审计、同步记录、通讯录登记为 `GLOBAL`；「部门 → 法人」对照与真实的 `legalEntityId`；直接下属查询；角色范围授予明细表；`super_admin` 管理模式、应急登录进入管理模式、首任管理员命令；不能改自己的角色与自己持有角色的定义；敏感权限双人确认（1a 只涉及 `account-role:update` 与 `super_admin`）；`account-role:update` 拆分；拒绝审计。
- **推迟**：法人限定 `legal_entity_scope`（1b，随第一个带法人列的事实）；审批参与访问（1b）；职责分离组合规则与违规报告（随第一条组合规则）；季度复核（1b 之后）；敏感字段机制（Phase 2，随第一个 L3 字段）；**项目角色访问**（Phase 2 交付；1a 没有项目成员数据源；`ScopeColumns` 预留 `project_id`）；**代理审批授权模型**（1b 前单独评审，RULE-270；取决于 1b 的认领与转交语义）。

## 迁移方案

1. **1a 内分三步，每步可独立回退**：① 类型下沉与渲染器（不改行为）；② 各查询接入范围并补测试；③ 切换 `super_admin` 为管理模式。
2. **首任管理员**：第 ③ 步上线前，用运维命令授予至少两名 `super_admin`；`employee` 范围保持 `SELF`；需要浏览组织的岗位（HR、部门负责人）先授业务角色，避免切换后失去组织浏览能力。
3. **法人归属**：上线前由组织数据管理员录入部门对照与个别员工的单独指定；上线检查项：全部启用部门、全部在职员工在当天都能解析到法人。
4. **老角色**：按第 8 项在各模块切换时迁入，带批次号与授予快照；1a 切换前执行一次只读导出（D-9）。

## 回滚方案

- **范围过滤**：每个查询的接入是独立提交；出问题时回退该提交，查询恢复为只靠功能权限（与现状相同，不会放宽到匿名）。**不提供**运行时关闭范围或恢复管理员全权的配置开关，避免成为后门。
- **管理模式**：回退第 ③ 步的提交；权限集合的数据改动用新的 Flyway 迁移恢复（只追加），并在提交说明中写原因。
- **法人归属**：录错时改对照或单独指定即可，最长 60 秒后生效，不涉及业务数据（按日期派生，不回写）。
- **老角色迁入**：按 `migration_batch_id` 删除该批授予，并按 `account_role_snapshots` 恢复；授予变更即时吊销会话。
- **边界**：已写入的审计行、已发生的审批参与关系不回滚。

## 需同步修改的守护规则

## 后果

- 「查业务数据必须带范围」成为三层约束：只有登记的持久化类能查库（ArchUnit）、每张表必须登记（注册表测试）、行为由契约测试验证。新表不登记无法通过 CI。
- 仓储方法普遍多一个 `AccessScope` 参数；换来范围在代码中可见、可测。
- 不用 RLS：绕过应用直接连库的人（运维、BI）不受范围限制，由数据库账号授权管理，不在本 ADR 范围。
- 管理员日常需要显式进入管理模式，多一步验证；换来平台操作与业务操作在会话和审计中分开，兼任管理员的负责人照常审批。
- 审批参与访问依赖事件投影，收回最多延迟到下一次投递或每日对账；积压告警兜底（1b）。
- 员工法人依赖管理员维护的对照；未录入时 `OWN` 法人限定解析为空集（fail-closed），默认的 `ANY` 不受影响。

## 备选方案（未采用）

- **PostgreSQL RLS 为主**：会话变量传范围，数据库强制过滤。未采用：ADR-0009 第 4 条要求范围在仓储中显式可见；连接池下每个事务都要设置会话变量；Flowable 与定时任务需要豁免账号；子树展开要在策略函数中递归，性能与可测试性差。
- **RLS 作为第二道防线**：两套口径须保持一致，差异只表现为「查不到」，难以定位；规模小、只有应用一个写入方，收益不抵成本。若以后出现应用之外的直连写入方，再单独评审。
- **注解 + SQL 改写拦截器**（老系统做法）：RULE-350 已评审为错误。
- **所有角色的范围整体合并**（不按权限）：会让一个角色的宽范围串到另一个角色的权限上。
- **法人作为独立维度与部门取并集**：会让「只看 A 法人」的角色看到 B 法人下本部门的数据。
- **法人限定默认 `OWN`**：会让本部门以其他法人签约的单据看不到，老角色迁入后财务失去跨法人数据。
- **管理员另建独立账号**（D-10 选项 ②）：隔离更彻底，但每名管理员多一套账号与登录方式（企业微信只对应一个人），且仍需管理模式式的限时。
- **审批参与人请求时回查 approval**：每次查询跨模块调用，且无法与分页 SQL 组合。
- **职责分离规则做成配置表**：授予时冲突属于安全不变量，可被配置为「允许」就失去意义；操作时规则本来就由领域代码执行。
- **`super_admin` 保持全权**：平台管理员可不经授权查看敏感数据并参与审批，与最小权限和职责分离冲突。
