## 决定

### 一、方法的总体结构

1. **七步方法**（用户：intent `2026-10-16-072440` M-1；`2026-10-15-211634`）。方法的主线：先问谁（干系人）要什么价值（价值流），找出承载价值的业务对象及其状态与规则，用对象状态写阶段门；由不变量定聚合、由统一语言定 BC、把引用按依赖方式连成无环的图；列出全企业业务流程清单；最后按阶段做流程图、数据与分析，过渡上线并守护。各步只回答自己的问题，靠对象状态与稳定编号连接。

### 二、业务层规则（第 ①–③ 步）

4. **价值流规则**：不拆子价值流；跨价值流只经对象状态衔接——一条价值流的结果落在某对象的某状态上，另一条价值流的触发或进入条件引用该状态，不写「A 触发 B」（推出（L-11 已认可））；先外部后内部（推出（用户已认可，intent `2026-10-16-130636` D-50）：intent `2026-10-15-222319` 纳入 BIZBOK 价值流）。**子阶段**按 BIZBOK §2.4（第 153–154 页）：只在子阶段处有明确的阶段门，或需表达不同业务单位的差异场景时才拆，子阶段同样写六要素；手册的「工作子阶段」默认落为 WBS 节点，确有独立的门、其进出条件能写成对象状态才升格（用户：intent `2026-10-16-072440` M-6）。公司手册的交付七段即价值流阶段，门按对象状态重写（同 M-6）。

5. **业务对象判据**（BIZBOK §2.5）：
   1. 一级 / 次级按依附关系分，不按生命长短；同物异型用类型区分，不拆对象；单据、属性、估值、派生度量不是对象，作「非对象」出口单列（推出（用户已认可，intent `2026-10-16-130636` D-50）：intent `2026-10-15-222319`）。
   2. **一级对象检验**用于所有一级对象：独立性、同物异型须合并、单据不是对象、属性与估值不是对象、须有自己的状态与规则（用户：intent `2026-10-15-215658`）。外部引用对象（无自有规则、只记录）豁免「须有自己的规则」；无类型、状态、关系、只汇聚次级对象的作汇聚对象（用户：认可 Q38，intent `2026-10-15-233152`）。
   3. **法律事实例外**：外部权威登记的法律事实（如增值税发票、登记证书）算业务对象；票面、确认单、回单只是证据（用户：intent `2026-10-15-221201`）。
   4. 每个对象注明来源（行业 / 用户 / 取证）、范围（本系统 / 外部系统（哪个）/ 不建）与所属阶段；新名称先查 `terms.yaml`，未登记的交 one-glossary（推出（用户已认可，intent `2026-10-16-130636` D-50）：CS-1.8；CLAUDE.md 第 2 条）。规则尽量注明规则卡编号，无卡的规则登记提议。

6. **能力图由信息图推出，只作视图**（用户：intent `2026-10-15-221201`「重建按对象命名的能力图」、`2026-10-15-222319`）：每个一级对象一个一级能力，每个次级对象一个二级能力，不手写三级；命名「对象 + 管理」，按对象拆分、不越出父对象、不按类型拆（BIZBOK §2.2；G211 §2.1.1）。能力文件手写能力名称与定义，**结构**（一级、二级能力的集合与父子关系）由 CI 校验与信息图一一对应，不另手写结构（推出（用户已认可，intent `2026-10-16-130636` D-50），评审 M-5）。用途只有三项：一页「业务做什么」的视图；第 ③ 步能力—阶段对账；对照 BIZBOK §8.6 通用参考模型一级能力的**名称**查漏对象（不抄定义）。**不用于检验信息图**（能力由对象推出，再拿来检验对象是循环论证）；**不驱动 BC**：`business/capabilities.yaml` 不得出现 `bc`、`module`、`subdomain`、`current_bc`、`strategic_hint` 及同义字段，CI 拦截（推出（L-11 已认可））；明文不用 BIZBOK §6.5 与 Part 6 其余各节、G211 从组织结构推导能力与多级拆分（推出（用户已认可，intent `2026-10-16-130636` D-50）：intent `2026-10-15-222319` 纳入页所列代价）。

7. **能力—阶段对账**（用户：intent `2026-10-16-072440` M-1）：每个一级能力至少支撑一个阶段，否则写「不支撑价值流」及理由（字段 `unsupported_reason`）；每个阶段至少被一个一级能力支撑。一级能力的对象集合（自身对象加其二级能力的对象）在某阶段任何位置被引用（进出条件、段内条件、贯穿活动的输入输出），即算支撑该阶段。被检验的是阶段的覆盖与能力的去向，不是对象，阶段来自干系人、价值流与手册，独立于能力图，因此不构成循环论证（推出（用户已认可，intent `2026-10-16-130636` D-50）：BIZBOK §2.4 第 159 页）。

8. **阶段规则**：
   1. 阶段可回退、跳过、重入，留痕；不采用 G178「上一阶段退出即下一阶段进入」（用户：intent `2026-10-15-222350`）。
   2. 门只预警并留痕，门本身不另加拦截；对象自身的不变量照常拒绝；需审定的门走审批，审批未完成不挡下一阶段（用户：intent `2026-10-16-061232` S2）。
   3. 阶段只表示工作进程，与商务分界脱开；售前与交付的成本分界由合同回签承载（用户：intent `2026-10-16-061232` S3）。
   4. **阶段 ≠ 状态机**：价值流阶段、企业的阶段类型目录、对象状态机是三件事；阶段不做成某个聚合上的大状态机（推出（L-11 已认可））；阶段进度落为 WBS 阶段节点的工作进程状态，跨聚合的门由前置检查或事件策略实现，预警由 `reporting` 或下游策略层产生，不进聚合（推出（用户已认可，intent `2026-10-16-130636` D-50）：S2、S3）。
   5. 流程与阶段多对多，一个阶段不等于一个 BPMN 流程（推出（L-11 已认可）；BIZBOK §3.4）。

### 三、领域层规则（第 ④⑤ 步）

9. **规则四分与不变量三类**（推出（用户已认可，intent `2026-10-16-130636` D-50）：现行 METHOD 接缝 1；ADR-0016 决定 5；DDD Reference 聚合一节）。规则分四类：不变式放聚合；判定（路由、资格、级别）暂放版本化配置表或代码（DMN 推迟）；人工编排放 BPMN；计算放值对象或领域服务；信息图里的「警」是策略，不是不变量。不变量分三类，每条有且只有一个守护落点：
   - **A 单聚合**：一个聚合实例内、一个事务内成立，聚合根方法守护；
   - **B 集合约束**：同类型多个实例之间的唯一、不重叠，用唯一约束、部分唯一索引或排他约束实现（SESSION_PLAYBOOK §14.1 D2），不为它扩大聚合；
   - **C ADR 认可的多聚合同事务**：已采纳 ADR 明文要求一个事务修改两个聚合，登记 `multi-aggregate-exceptions.txt`，`SingleAggregateGuardTest` 守护。

10. **聚合实现做法**（用户：intent `2026-10-16-112800` L-2，写成方法规则）。以下是 A 类或跨聚合约束的实现模式，**不是新的不变量类**：
    1. **前置检查**：命令方在执行前按 ID 经 api 读另一个聚合，只写自己。两种：一般前置（读写不同事务，竞态由策略兜底）；同事务读锁（读方在自己的写事务内对被读行加共享锁，被读方状态转换须等待）。
    2. **下游编排**：凡要读的对象在依赖图中位于下游，改由下游流程查齐条件后调用上游命令，上游不读下游。
    3. **额度占用**：「多张单据合计不超过某个额度」的累计约束，额度与占用行放在一个额度聚合内；申请方先占用（一个事务、只改额度聚合、乐观锁防超占），拿占用 ID 再写自己的单据；驳回、作废、终止时释放；孤儿占用由定时释放与对账兜底。
    4. **一拆多判据**：一个业务对象拆成多个聚合，只在状态机不同、负责的干系人不同或不变量不同时才拆。
    5. **引用三种依赖方式**与**脚本查环**：见决定 12。

11. **对象—聚合对应与两层映射**：
    1. 每个聚合写明与业务对象的对应，五种之一：一对一、次级在内、一拆多、无聚合（外部引用、派生值）、技术聚合（信息图无对应对象，只为守住不变量而设；期间性批处理的结果称运行单据）。对象 ≠ 聚合：BIZBOK 管对象层，DDD 管聚合层（推出（L-11 已认可））。
    2. **两层映射**（用户：intent `2026-10-16-112800` L-1）：阶段门在第 ③ 步引用业务对象状态；在第 ④ 步，每个对象实例（一拆多按类型或方向分别计）的该状态映射到恰一个聚合的存储状态，或一个派生值（注明在哪个 BC 计算）。上游聚合自身不变量要用到的状态，由下游编排调用上游命令写回，命令携带下游给出的依据并在上游校验前置；其余由下游累计决定的状态只作派生值，不写回上游；**阶段门不引用派生值**。同一事实不得一份存储一份派生；存储状态以派生值为依据时，派生值是依据、存储状态是上游的独立决定，二者差异列入对账报告。
    3. **事件**（用户：intent `2026-10-16-114200` F-4；ADR-0023 决定 2）：每个事件由一个聚合发出（推出（L-11 已认可）），写明订阅方；分析库（`reporting`）订阅也算订阅方；无业务订阅方的事件保留，事件列标「仅分析」；经济事件按 REA 两个问题复审（决定 19）。

12. **BC、依赖方式与方向**：
    1. 按**统一语言与模型的一致范围**把聚合聚成 BC，同名异义处必须切开；不变量只决定聚合，不决定 BC（用户：intent `2026-10-16-112800` L-7；推出（L-11 已认可）；DDD Reference 2015）。
    2. **每条跨聚合引用写「目标（方式）」**，方式三选一（用户：L-2）：**api**（经对方 api 查询或调用对方命令，成一条本 BC → 对方 BC 的依赖边）；**事件**（订阅对方事件，同样成边）；**不校验**（只存对方的 ID，不调用、不订阅，不成边；只用于下游记录上游不需要知道的来源，或对方位于下游、只作回溯线索）。「不校验」引用的 ID 类型不得取自对方 BC 的 `api` 包（否则 `ModuleDependencyTest` 判为依赖），只能用：`kernel` 中已有的通用 ID（如 `ProjectId`、`WbsNodeId`、`EmployeeId`）与 `DocumentReference`，或本 BC 内的不透明 ID（值对象只包一个 UUID，不带对方语义）。新增 `kernel` 通用 ID 须按 CS-2.7 逐个评审，本 ADR 不预先扩大共享内核（裁量（用户已认可，intent `2026-10-16-130636-one-architecture-ADR-0050-0051-批准.md` K-50），评审 M-4）。
    3. **依赖边的手写位置与查环**（用户：L-2、L-4；手写位置的分工为裁量（用户已认可，intent `2026-10-16-130636-one-architecture-ADR-0050-0051-批准.md` K-50），评审 H-5）：
       - **已建边**只在 `backend/architecture/module-dependencies.txt` 手写，经 CODEOWNERS 评审，上下文映射以它为准（ADR-0003 决定 3、ADR-0041 决定 4，不变）。
       - **规划边**只在聚合提议稿每个聚合的「引用与依赖方式」列手写：现为 `proposals/ENTERPRISE_AGGREGATES_DRAFT.md` §2.2，按 L-4 转写为 `proposals/aggregates.yaml` 后以 YAML 为准，Markdown 改为由 YAML 生成或降为说明，不两处手写。
       - **一致性**：脚本由规划边合成 BC 边，并入已建边查环、按层分级，与提交的分层块比对，退出码 0 才算通过；同时校验已建业务 BC 之间的每条已建边都出现在聚合引用合成的边中（现脚本已输出「已建边在 §2.2 中未出现：无」）。规划边在阶段登记前不进 `module-dependencies.txt`。

    4. **方向规则**（用户：intent `2026-10-16-072440` M-3）：上游不读下游、也不订阅下游事件；关联由下游一侧记录。

### 四、全企业业务流程清单（第 ⑥a 步）

15. **业务流程判据与四个去处**（依据：用户 A-2，intent `2026-10-16-130636-one-architecture-ADR-0050-0051-批准.md`。判据与分类方法写进本 ADR；判据原出自 `proposals/STEP6A_PROCESSES.md` §0.3，用户在售前回溯中按此口径移入三项，intent `2026-10-16-120544` P-5。⑥a 清单是提议稿，到各阶段画流程图（⑥b）时逐阶段确认）。清单只收**业务流程**，同时满足三条：① 由业务事件或人的业务决定触发；② 跨两个以上聚合，或跨两个以上角色并有交接；③ 结果是某价值流阶段的进入或退出状态。不满足的分四处放，不计入业务流程数，编号全局唯一：
    - **事件策略**：一个事件、一步命令的自动反应；
    - **单聚合维护**：单聚合的生命周期或维护，归第 ④ 步状态机；
    - **读模型**：只读、无命令（如阶段门预警），归 `reporting`；
    - **合并**：同一业务链被拆碎的编号并入一个流程，被并入编号保留去向。

    流程字段：名称（业务语言）、触发（事件 / 定时 / 人工发起 / 调用）、映射的价值流阶段（多对多）、编排 BC（一个；事件触发的取订阅方，人工发起的取承担该动作的下游 BC）、步骤（命令 → 聚合 → 事件）、是否含人工编排。步骤涉及的聚合须在编排 BC 自身或其上游；一步只改一个聚合（C 类不变量除外）。「人工编排」须有平台审批任务、带超时的分支或退回分支之一。用语：本方法用「业务流程」（BIZBOK / BPMN 意义）与「度量事件」（决定 20），不用含义冲突的「业务过程」（已交 one-glossary，issue `2026-10-15-212917`）。

## 后果

- 方法有了业务层（干系人、价值流、业务对象、阶段门），BC 推导从「证据 → 不变量」改为「价值流 → 对象 → 不变量 → 聚合 → 语言 → BC」；不变量 ADR 的优先级不变。
- 能力图回到视图角色，并由 CI 阻止它决定 BC 或子域；对象由行业做法为主识别，老系统只作参考。
- 聚合的几种实现做法与依赖方式成为方法规则，各阶段推导与评审有统一判据；规划边由脚本合成并查环，已建边仍手写于 `module-dependencies.txt`，二者由脚本校验一致。
- 子域不再分类，只作命名空间；深浅标记集中在 BC 上。
- 代价：多三份业务层 SSOT 与一批校验要维护；信息图与聚合稿要先转写一次 YAML；生成器路径要改（L-3 改选所致）；手册「门完成才能进入下一阶段」的字面与系统「门只预警」不同，须在用户文档中说明；放弃了 G190、G211 从能力出发的方法与 BIZBOK 业务架构与 IT 对齐章节，若将来扩为多系统、需能力热图，须重新评审。
