## Scope

Signed: schema `organization_workforce`, new table `acting_duties`; new columns, checks, foreign keys and indexes on `personnel_commands`; the three new command kinds `ACTING_START`, `ACTING_END`, `ACTING_EXTEND`; the payloads of `EmployeeActingDutyStarted` and `EmployeeActingDutyEnded` (section "Event payloads" below; they are **not** written into `docs/architecture/events/workforce.yaml` by this PR, see that section); four terms (`terms.yaml`).

Not signed (separate gate runs): any `platform_identity` table or CHECK change (proposal slice 9: needs the user's answer to Q-A1); approval routing (slice 11, Q-A2); read models; migration-in (there is no legacy data to bring in: the pack is evidence only). The schema does not depend on Q-A1 to Q-A5: Q-A3 (several stand-ins at once) is already allowed by the data and a limit would be a command check; Q-A4 (who may act) and Q-A5 (approval first) change command permissions and flow, not columns.

## Columns and constraints

Conventions as the existing workforce tables: UUIDv7 ids generated by the application; enums are `text` with a named `ck_<table>_<column>`; free text has `char_length` and `btrim` CHECKs; every nullable column's comment says 「为空表示」; `created_at`, `created_by`, `updated_at`, `version bigint NOT NULL DEFAULT 0`; dates are `date`, `[)` ranges (`ends_before` exclusive).

### acting_duties (grain: one row per acting duty)

| Column | Type | Rule |
|---|---|---|
| `acting_duty_id` | uuid | pk `pk_acting_duties`; `uk_acting_duties_id_employee` `(acting_duty_id, employee_id)` (target of the command key) |
| `employment_relationship_id`, `employee_id` | uuid NOT NULL | composite `fk_acting_duties_relationship` to `uk_employment_relationships_id_employee`, RESTRICT (verified in `V20261105120000`); index `ix_acting_duties_relationship` `(employment_relationship_id, employee_id)` |
| `covered_org_unit_id` | uuid NOT NULL | `fk_acting_duties_covered_org_unit_id` to `org_units` RESTRICT; `ix_acting_duties_covered_org_unit_id` `(covered_org_unit_id, starts_on)` |
| `covered_position_id` | uuid null | 为空表示 the unit head's duties; FK to `positions` RESTRICT; partial index where not null. That the post belongs to the unit is a command check (the pair lives in position versions, cross-table) |
| `covered_employee_id` | uuid null | 为空表示 no particular person is covered; FK to `employees` RESTRICT; partial index where not null; `ck_acting_duties_not_self` `covered_employee_id IS DISTINCT FROM employee_id` (rule 4) |
| `starts_on`, `ends_before` | date NOT NULL | `ck_acting_duties_period` `starts_on < ends_before` (rule 1); `isfinite` on both |
| `ended_on`, `end_cause` | date null, text null | 为空表示 still open; `ck_acting_duties_end_pair` `(ended_on IS NULL) = (end_cause IS NULL)`; `ck_acting_duties_end_cause` in `EXPIRED`, `ENDED_EARLY`, `SEPARATION`; `ck_acting_duties_ended_range` `ended_on IS NULL OR (ended_on > starts_on AND ended_on <= ends_before)` (rule 8; expiry sets `ended_on = ends_before`, also when the job is late) |
| `reason` | text NOT NULL | 1 to 500 characters, `btrim` (copied from the start command) |
| `source_personnel_command_id` | uuid NOT NULL | composite `fk_acting_duties_source_command` `(source_personnel_command_id, employee_id)` to `uk_personnel_commands_id_employee` (exists, baseline) RESTRICT; `uk_acting_duties_source_command` unique; index is the unique itself |

Exclusion constraints (rule 2; `btree_gist` is created in the workforce baseline, verified at line 241): the nullable post forces two constraints, one per shape:
- `ex_acting_duties_unit_head_overlap` `EXCLUDE USING gist (employee_id WITH =, covered_org_unit_id WITH =, daterange(starts_on, coalesce(ended_on, ends_before), '[)') WITH &&) WHERE (covered_position_id IS NULL)`;
- `ex_acting_duties_position_overlap` the same with `covered_position_id WITH =` `WHERE (covered_position_id IS NOT NULL)`.

Back-to-back duties do not overlap under `[)`. Business key (O3): "in a window, one person has at most one duty for the same covered post" (proposal rule 2, lead decision #1519 Q1) is these two constraints.

Trigger `tg_acting_duties_change` and `tg_acting_duties_truncate` (refuses TRUNCATE): the full list of legal writes. (1) Insert as open (`ended_on` and `end_cause` null). (2) On an open row: `ends_before` may only grow (extend); no other column. (3) Open to closed: `ended_on` and `end_cause` set once, nothing else. (4) A closed row never changes. `version` and `updated_at` move with each step. DELETE only by the table owner (the purge function, ADR-0068 item 7 and W2 section 8); UPDATE of any other column refused. The history of `ends_before` is kept by the append-only command rows (`ACTING_START` and `ACTING_EXTEND` each carry `acting_ends_before`), so the single mutable end loses nothing (O7).

Hot state (O10): `ix_acting_duties_open_due` `(ends_before) WHERE ended_on IS NULL` serves the due step; open rows are far below 10% of the table over time. Person path `ix_acting_duties_employee_id` `(employee_id, starts_on DESC, acting_duty_id DESC)`.

New nullable columns: `acting_covered_org_unit_id`, `acting_covered_position_id`, `acting_covered_employee_id` (FKs RESTRICT to `org_units`, `positions`, `employees`, each with a partial index where not null), `acting_ends_before date`, `target_acting_duty_id uuid` (composite `fk_personnel_commands_target_acting_duty` `(target_acting_duty_id, employee_id)` to `uk_acting_duties_id_employee`, RESTRICT, partial index), `reason text` (verified: the table has only `withdrawal_reason`, so the proposal's "if the table has none" is resolved: add it).

- `ck_personnel_commands_command_kind` redefined with the three values appended to the list of `V20261103130000` (verified the last redefinition there; the baseline list is not the current one).
- `ck_personnel_commands_acting_columns`: `ACTING_START` requires `acting_covered_org_unit_id`, `acting_ends_before`, `reason`, and `effective_date < acting_ends_before`, and `target_acting_duty_id` null; `ACTING_END` requires `target_acting_duty_id`, `reason`, and the three covered columns and `acting_ends_before` null; `ACTING_EXTEND` requires `target_acting_duty_id`, `acting_ends_before`, `reason`, covered columns null; every other kind has all six columns null. Also: `acting_covered_position_id` implies `acting_covered_org_unit_id`; `acting_covered_employee_id IS DISTINCT FROM employee_id`; `reason` 1 to 500 characters, `btrim`; the six existing target columns (`target_org_unit_id`, `target_position_id`, `target_reports_to_employee_id`, `is_target_fee_earner`, `target_employment_phase_kind`, `is_target_on_unpaid_leave`) and `target_assignment_id` null for the three kinds; `employment_relationship_id` not null (the existing rule for all kinds but `CHANGE_LEGAL_ENTITY`).
- `ck_personnel_commands_correction_immediate` widened to `command_kind NOT IN ('CORRECTION', 'ACTING_EXTEND') OR status = 'EFFECTIVE'` (extend is applied when entered, with `effective_date` the business day it is entered).
- Index changes (see difference 2): `uk_personnel_commands_open_per_relationship_day` gets `command_kind NOT IN ('START_CONCURRENT', 'ACTING_START', 'ACTING_END', 'ACTING_EXTEND')` in place of `command_kind <> 'START_CONCURRENT'`; new `uk_personnel_commands_open_acting_start` unique `(employee_id, acting_covered_org_unit_id, coalesce(acting_covered_position_id, '00000000-0000-0000-0000-000000000000'::uuid), effective_date) WHERE command_kind = 'ACTING_START' AND status = 'PENDING'`; new `uk_personnel_commands_open_acting_end` unique `(target_acting_duty_id) WHERE command_kind = 'ACTING_END' AND status = 'PENDING'`.
- Comments updated on `command_kind` (three kinds added) and a comment on each new column.
- The append-only trigger on `personnel_commands` is unchanged: all six columns are written at insert.

## Differences from the proposal's section 4 (the record governs)

1. **Expiry is not a scheduled system command.** The proposal had `ACTING_START` create a pending system `ACTING_END` due on `ends_before`, withdrawn and re-created on each extension, and asked (unverified) whether a system-created command is allowed. Found: `uk_personnel_commands_open_per_relationship_day` (verified, `V20261105120000`) allows one open command per relationship per day, so an expiry command would refuse or be refused by a TRANSFER, SEPARATE or REGULARIZE due the same day, and it would need a system actor and a withdraw-and-recreate on every extension. Decision: `PersonnelCommandDueJob` gets one extra step that closes open duties with `ends_before <= today` (`ended_on = ends_before`, `end_cause = EXPIRED`, one transaction per duty, event with `personnelCommandId` empty). The proposal's U-item is closed this way. Slices 3 to 5 and done-when 2, 8, 9 are amended accordingly.
2. **The three acting kinds are out of the one-open-command-per-relationship-day index.** An acting start or end on the day of a TRANSFER is legitimate (acting is not an assignment); two acting starts for the same post on one day, and two pending early-ends for one duty, are refused by the two new unique indexes above.
3. **`ACTING_EXTEND` is immediate, not a "no date" command.** `effective_date` is NOT NULL for every kind; it takes the entry day and the status is `EFFECTIVE` at insert, as `CORRECTION` (`ck_personnel_commands_correction_immediate`, verified).
4. **The acting duty row carries `employment_relationship_id`** (the proposal's table listed only the employee). The events carry it (ADR-0086) and every dated workforce fact after `V20261105120000` is tied to a relationship.
5. **`acting_duties` is not a pure append-only table:** `ends_before` may grow while open and the closing pair is set once (trigger above); the proposal said "append-only except the closing columns" and left the trigger question open (unverified item closed here: the triggers on `personnel_commands` are by design, and this table has its own).
6. **Purge order** (retention, below) is part of the signed design.
