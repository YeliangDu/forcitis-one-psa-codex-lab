# #1310 标准工时版本（AGG-108）数据设计审查

- 审查：one-design（受 lead 指派代签），2026-11-04；草案：one-dev-org 的 `1310-standard-hours-data-design-draft.md`（共享笔记夹）；卡：issue #1310 正文。
- 结论：**数据设计：通过，附改动 C1–C6 与 Q1–Q5 裁决**；改完在表结构 PR 的预期 diff 里体现，我复核实际 diff 后签表结构 PR。
- 依据：INV-116（无默认工时）、RULE-398、RULE-510、`planned.yaml` AGG-108、同 schema 先例 `V20261021170000__organization_attendance_work_calendar_versions.sql`。

## 一、Q1–Q5 裁决

1. **Q1 关闭上一版本：选 (a)，沿用工作日历先例。** `effective_to_date` 只由「发布下一版本」的库触发器把空改成日期，其余任何更新都拒绝；排他约束保留（卡完成标准第 2 条原文就是排他约束，且先例同款）。不选 (b)：它把「不重叠」的证明从排他约束换成唯一索引，读取要多一步「取不晚于该日的最新一行」，与先例两套写法并存是熵增。另加三条库内守护（同先例的 guard 触发器）：①新版本的 `effective_from_date` 必须晚于同范围已有 IN_EFFECT 版本的最大 `effective_from_date`（顺序追加；想插到未来版本前面须先作废该未来版本再重发）；②新版本发布时，同范围仍开放的上一版本（`effective_to_date IS NULL`）被关闭为新版本的生效日（不含）；③只允许两种更新：关闭（空→日期，仅由发布触发器在同事务里做）和作废（IN_EFFECT→VOIDED 并同时填全作废三列）；不允许删除与清空。
2. **Q2 追溯：不追溯。** 新版本的 `effective_from_date` 不得早于库的事务日期（按库时间取日，同先例），**例外：该范围（默认或某法人）的第一个版本不受此限**，因为之前没有任何版本，也没有按它拆分过的日子，迁入与补录历史需要它。理由：RULE-510 请假按每天分钟数存储，已拆分的日子是快照，不随新版本重算；所以改今天之前的版本没有下游可套用，也不该有。已生效或已过去的版本不可作废（见 C4），错值用「今天起的新版本」更正，过去的日子保持原样；是否要追溯更正过去的请假日是业务问题，本卡不做，需要时另走用户。
3. **Q3 无版本：同意。** `minutesOn` 找不到版本抛错并出一行 `ALERT`，不返回默认值，不吞异常；错误码按 `AttendanceError` 的现有命名并登记错误码表；调用方（请假、工时）自己决定拒绝。
4. **Q4 默认范围兜底：同意，加一条防混用。** 解析顺序：该法人**有自己的 IN_EFFECT 版本时，以它自己的时间线为准**（日期落在它的时间线空档里，包括早于它第一个自有版本，直接报错，不退回默认）；该法人没有任何自有 IN_EFFECT 版本，才用默认范围的版本；默认也没有则报错。理由：避免同一法人历史上一部分取自有值、一部分取默认值。`minutesOn` 的返回里带上「取自哪个范围」（自有 / 默认），供调用方展示与测试。不播种任何值（FD-10 的 7.5 小时是用户的决定，由用户经发布命令录入）。
5. **Q5 事件载荷：同意含分钟数。** 事件 `StandardHoursVersionPublished` 载荷：版本 ID、范围类别、法人 ID（默认范围为空）、生效日、两个分钟数、版本号。分钟数不是个人信息，不入 RESTRICTED 分级；不含 `basis_ref` 原文、确认人以外的人员信息。仅用于分析，消费方走 api（S-42）。

## 二、对草案表结构的改动

- **C1 `confirmed_by` / `confirmed_at` 保留为「命令里写明的确认人与确认时间」**，注释写清它可以等于操作人（卡没有待确认状态，不做四眼）；操作人看 `decision_audit_entry_id` 指向的审计记录。是否要第二人确认是用户的事，若日后要，新迁移加待确认状态，不在本卡预设。
- **C2 唯一性**：`UNIQUE (scope key, version_number)` 含表达式 `coalesce(legal_entity_id, '00000000-0000-0000-0000-000000000000')`，须建成唯一索引（表达式不能进 UNIQUE 约束）；版本号从 1 起逐个加 1，由 insert 守护触发器校验，作废版本也占号。
- **C3 `legal_entity_id` 不建外键**（跨 schema，只存 ID；存在性由应用经 api 校验），同 `work_calendars`。列注释写明。
- **C4 作废（VOIDED）**：仅允许 `effective_from_date` 晚于库事务日期的版本作废；作废触发器校验。作废三列 `voided_by/voided_at/void_reason`「全空或全填」，原因 1..500 字符且已 trim，同先例撤回列。**作废命令不在卡的完成标准里**：表结构按有作废建，命令由 lead 决定是否并入 #1310；我的建议是并入（小：仅限未来版本），否则错填的未来版本无法更正。若不并入，列与状态仍建（改约束要新迁移，比多一个未用列贵）。
- **C5 日期覆盖表 `standard_hours_date_overrides`**：`minutes` 改为 `CHECK 1..1440`（0 不要：非工作日由工作日历决定、RULE-510 按零计，用覆盖写 0 会与日历打架）；`work_date` 必须 `>=` 父版本生效日；读取先按日期选版本，再找该版本该日的覆盖，**落在版本生效区间之外的覆盖行永远不被读**（版本被后继关闭后，其后的覆盖行是死数据，不删、不读）。覆盖行只追加（禁更新、删除、清空），且只能在创建父版本的同一事务里插入（对已提交的版本插入覆盖行须被库拒绝，机制由实现选，测试须证明）。`reason_text` 1..200 字符已 trim。
- **C6 其余列与约束**：`workday_minutes`、`adjusted_workday_minutes` 1..1440 同意；`basis_ref` 1..200 已 trim 同意；`status` 只有 IN_EFFECT / VOIDED；`effective_to_date >= effective_from_date`（空表示开放）；`(scope_kind='DEFAULT') = (legal_entity_id IS NULL)` 同意；排他约束同草案但守卫条件为 `status='IN_EFFECT'`，区间 `[)`；扩展 `btree_gist` 沿用先例的存在性检查，不在迁移里建扩展。所有列要有 COMMENT；`created_at/updated_at` 由应用写入，`updated_at` 等于 `created_at`，关闭与作废不改它（同先例）。

## 三、核对

- 范围：只涉及 `organization_attendance` 两张新表，不动 `work_calendar*` 表（卡「不得做」）；不涉及 leave、timesheet、workforce 的表。
- 个人信息：表内无个人信息（确认人、作废人是账号 ID，沿用先例）；数据分级与保存期：永久保留（工时历史是计算依据，不删），登记数据访问注册表时按此写。
- 权限与审计：`organization.attendance:standard-hours:publish`（符合 NamingSurfaceTest G43 的 `module:resource:action` 形式）；审计动作 `organization.attendance.standard-hours.published`；作废若并入则另需 `…:void` 与 `…voided`。
- 测试要求（表结构 PR 之后的验收测试须覆盖）：重叠版本被排他约束拒绝；第二个版本发布后上一版本的 `effective_to_date` 被关闭；早于事务日期的非首版被拒；首版可早于事务日期；不顺序追加被拒；任何其他更新、删除、清空被拒；对已提交版本插入覆盖行被拒；默认与自有范围的解析顺序（含自有时间线空档报错）；无版本报错并出 ALERT；主代码里 grep 无 450/480/7.5 字面默认值。

数据设计：通过（one-design 代签，2026-11-04，依据 issue #1310 正文与上述草案文件；范围：`standard_hours_versions`、`standard_hours_date_overrides` 两表按 C1–C6 改后）。
