请定

能力还要不要用？

能力对账是循环论证。BIZBOK 原本主张先有能力图，但现有能力清单不是按对象命名的，拿它对账也对不上。
建议用 BIZBOK §8.6 通用参考模型的一级能力作外部查漏参照，只出漏项清单；不再写「一个能力只改一个对象」，以免滑回能力驱动 BC。另一种做法是重建一份按对象命名的能力图，代价是多维护一份交付物。

发票这类「法定登记的事实」算不算业务对象？

BIZBOK 点名发票是单据，不是对象；但中国增值税发票由税务系统登记，有蓝字、红冲状态链，ADR-0016 已把它当聚合。
建议加一条本地化判据：由外部权威登记的法律事实（税票、登记证书）是对象；票面、确认单、回单只是证据。并写明这是对 BIZBOK 的偏离和理由。

全企业梳理做到多深？

你定过全部梳理完再一次性调 ADR。评审提示：全部段都做到聚合和 BC，工作量大，也与「只实现当前阶段」有张力。
建议全企业做到业务对象和范围（含价值流、阶段门映射），聚合和 BC 只对下一阶段做；但 BC 的依赖方向骨架全企业先定，避免后面成环。

「子域」怎么定位？

在我们这里，子域名是 Java 包、schema、URL、权限码的前缀，已建模块改名要另开 ADR。DDD 原意中子域属问题空间，应先于 BC。
建议如实定为「命名空间分组」，在 BC 时一起定，已建模块以代码为准；不再冒称 DDD 子域分类。

BIZBOK 与 TOGAF 三份指南要不要补走适配评审？

按 ADR-0041 决定 6，新加框架要先出不预选的决策页。评审认为真正需要的只是几条概念：一级 / 次级依附、类型不拆对象、单据不是对象、状态作阶段门、价值流和阶段的要素。
按规则补走：我出一页适配评审决策页（写明要求、代价、收益，不预选），再登记。框架类决策页按规则不显示推荐。

员工邮箱、企业微信 ID 的分级：要不要开 ADR 改成两个维度？

个人信息保护法第四条：邮箱、企业微信 ID 是个人信息；第二十八条列的敏感个人信息不含它们。现在登记文件把凡个人信息都记成「敏感」，和你定的 L2 冲突，守护测试也强制邮箱必须「敏感」。
建议开小 ADR：访问级别（沿用 L1–L4）+ 个人信息标记（非个人信息 / 个人信息 / 敏感个人信息）两个维度；邮箱、企业微信 ID = L2 + 个人信息；守护改为要求标个人信息标记。
